# 0. 开场：本模块在考试里的位置 + 黑话速查表

## 0.1 它在考试中是什么地位

| 项目 | 说明 |
|------|------|
| 属于 | **题型 5 · 专项架构与新技术**（**选做题**） |
| 卷面结构 | 全卷 5 道大题：**第 1 题必答 + 后 4 题选 2**，每题约 **25 分**，满分 75 分，**45 分及格** |
| 本模块特点 | **不稳定**：12 个方向随机抽，今年考大数据、明年可能考车载嵌入式 |
| 难度 | 概念新、名词陌生，但**深度浅** —— 不考代码、不敲命令、几乎不算公式 |
| 定位 | **第三优先级**：必答题（架构评估）+ Redis 专项 + 分布式云原生拿下后，本模块作"**备胎主力**" |

> **给新手的定心丸**：
> 这一块最大的特点不是"难"，是"**生**"。你看到 `SOME/IP` 不会，别人也不会 —— 大家都是第一次见。
> 所以它的得分逻辑是：**谁把"关键词 + 模板"背得更熟，谁得分**。它考的是"**认脸能力**"，不是"研发能力"。
>
> 培训机构的统计也印证了这点：2024 年 11 月改版后"只有试题一还在教材范围内"，**超纲题占比越来越高**。
> 这意味着：考场上你一定会遇到没见过的名词 —— **本模块就是专门用来对付"陌生架构图"的训练**。

## 0.2 新手黑话速查表（**先扫一遍，后面就不卡壳了**）

| 黑话 | 人话解释 |
|------|----------|
| **批处理** | 攒一批数据**一起算**（像月底结账），慢但准 |
| **流处理** | 来一条**算一条**（像收银台实时计数），快但可能有误差 |
| **批处理视图 / 实时视图** | 两套计算结果，最后要**合并**成一个答案给用户看 |
| **水位线 Watermark** | 流处理里的"**催交作业截止时间**"，过了这个点就认为数据到齐了、开始计算 |
| **Exactly‑Once** | 数据**不丢也不重复**，恰好被处理一次（靠 Checkpoint 快照实现） |
| **数据倾斜** | 活儿全压在**一个节点**上，别的节点闲着（热点 key 问题） |
| **ECU** | 汽车里的**电子控制单元**，一个功能一个小电脑（刹车、车窗、发动机各一个） |
| **RTOS** | 实时操作系统 —— **说到做到**的管家，高优先级任务可以立刻打断低优先级 |
| **硬实时 / 软实时** | 硬：超时会**出人命**（飞控、机械臂）；软：超时只是**体验差**（视频卡顿） |
| **RM / EDF 调度** | RM：**周期越短，优先级越高**（静态）；EDF：**截止期越早越先做**（动态） |
| **QoS** | 服务质量保障 —— 约定"**多久送到、能不能丢、占多少带宽**" |
| **SOME/IP** | 汽车以太网上的**面向服务**通信协议（打电话：先查号 → 再呼叫） |
| **DDS** | 高实时**数据分发**中间件（订报纸：订阅某频道，自动送到，带 QoS） |
| **ROS / ROS2** | 机器人操作系统（其实是框架），ROS2 底层换成了 **DDS** |
| **MQTT** | 物联网**轻量级发布/订阅**协议（设备界的"微信公众号推送"） |
| **CoAP** | 受限版 HTTP，跑在 **UDP** 上，给资源极小的设备用 |
| **端 / 边 / 云** | 端=设备（采集）；边=**就近**处理（省时延省带宽）；云=全局存储与训练 |
| **训练 / 推理** | 训练 = **读书**（耗算力、一次性）；推理 = **答题**（要快、天天做） |
| **RAG** | **开卷考试** —— 回答前先去知识库翻资料，解决大模型胡编（幻觉） |
| **微调 Fine‑tune** | **改模型脑子**（调参数）；RAG 是**外挂资料**，微调是**改脑子** |
| **Agent** | 会**规划 → 调工具 → 记事 → 自查**的 AI 实习生 |
| **RDMA** | **绕过 CPU 直接读对方内存**，万卡训练刚需，极低时延 |
| **ECMP / 包喷洒** | 多条等价路径分流；ECMP 容易分不均，**包喷洒**把一条流打散到多路径 |
| **PagedAttention** | 显存的"**虚拟内存分页**"，把 KV Cache 分页复用，提升吞吐 |
| **量化 / 蒸馏** | 量化 = 把浮点换成低精度整数（**变小变快**）；蒸馏 = **大模型教小模型** |
| **投机采样** | 小模型**先打草稿**，大模型**批量批改**，加速生成 |
| **零信任** | "**永不信任，始终验证**" —— 内网也不可信，每次都要验身份 |
| **RBAC / ABAC / ReBAC** | 按**角色**授权 / 按**属性+策略**授权 / 按**关系**授权 |
| **等保 2.0** | 网络安全等级保护，分**五级**，政务金融核心通常要**三级** |
| **国密 SM2/SM3/SM4** | SM2＝**非对称/签名**（替 RSA）；SM3＝**摘要**（替 MD5/SHA）；SM4＝**对称**（替 AES） |
| **ROI / TCO** | 投资回报率 / 总拥有成本（可行性研究的经济指标） |
| **联盟链** | 几个**互相认识**的机构一起维护的区块链（半开放，比公链快） |
| **共识机制** | 多个节点怎么**达成一致**（PoW/PoS 适合公链；**PBFT 适合联盟链**） |
| **智能合约** | 部署在链上、条件满足就**自动执行**的代码（**部署后不可改**） |
| **默克尔树** | 用哈希把一堆交易**层层压缩成一个指纹**，便于快速校验 |
| **信创** | 国产化替代：芯片 + OS + 数据库 + 中间件**全套换国产** |
| **联邦学习** | 各家**数据不出本地**，只交换模型参数，联合训练（"数据可用不可见"） |
| **数据血缘** | 数据的"**溯源码**"，记录从产生到消费的全链路，便于溯源和影响分析 |
| **可靠度 R(t)** | 规定时间内**不坏**的概率 |
| **MTBF / MTTR** | 平均**无故障**运行时间 / 平均**修复**时间；可用性 ≈ MTBF/(MTBF+MTTR) |
| **N 版本程序设计** | 同一功能**独立写 N 份**，投票取多数，防软件设计缺陷 |
| **绞杀者 / 防腐层 / 抽象分支** | 遗留改造三模式：**拦流量** / **隔离模型** / **内部换组件** |
| **敏感点 / 权衡点** | 敏感点＝一个旋钮**显著影响**某质量属性；权衡点＝**多个敏感点交集**，动它有好有坏 |

# 2. 大数据架构（Lambda / Kappa）（最高频独立模块）

> 对应原文第 1 章 ｜ **本模块出现频率最高、套路最固定的方向，优先掌握**

## 🧊 直觉：月底结账 vs 收银台计数

想象你开了一家连锁超市，老板每天问你两个问题：

**问题 A："今天到目前为止，营业额多少？"**
→ 你必须**立刻**回答。做法：每成交一笔，就在计数器上 +1。**快，但可能算错**（比如有一笔退货还没处理）。

**问题 B："上个月全月的精确营业额是多少？"**
→ 你可以慢慢算。做法：晚上打烊后，把**所有小票重新核对一遍**，逐笔累加，还要扣除退货、优惠券。**慢，但绝对准**。

**这两个问题的答案，你都需要。** 这就是大数据系统的核心矛盾。

| 生活场景 | 大数据里的名字 | 特点 |
|---------|--------------|------|
| 收银台计数器，实时 +1 | **流处理（速度层）** | **快**，但结果是**近似**的 |
| 月底把所有小票重算一遍 | **批处理（批处理层）** | **准**，但**慢**（小时/天级） |

### Lambda 的解法：**两套都干**

```
                    ┌─────────────────────────────────────┐
   原始数据 ────────┤                                     │
                    ├─→ 【批处理层】把所有小票重算  ─→ 批处理视图（准、慢） ─┐
                    │     MapReduce / Spark                │                  ├→【服务层】合并 → 用户
                    └─→ 【速度层】 实时 +1         ─→ 实时视图（快、近似）─┘
                          Spark Streaming / Flink                              HBase / MemSQL / Druid
```

用户查的时候，服务层把"**准的历史结果 + 快的增量结果**"拼在一起，给出一个既准又新的答案。

> **关键理解（很多人卡在这里）**：速度层不是"最终答案"，它是**临时工**。
> 它负责填补"批处理还没算完的那段时间空档"。等批处理层把这段时间的账算完了，**实时的近似结果会被批处理的精确结果覆盖/修正**。

### Kappa 的解法：**录像回放**

Lambda 有个大麻烦：**同一套业务逻辑要写两遍**（一份 Spark 批处理代码、一份 Flink 流处理代码）。
两份代码由不同人写、在不同时间改，必然出现"**实时报表 1001 万、离线报表 998 万**"的尴尬。

> **Kappa 说：那我干脆只写一份代码。**
> 秘诀是 —— **把所有原始数据都录成"录像带"永久保存**（存在 Kafka 里），
> 需要算历史时，就**按快进把录像带重新播放一遍**，用**同一套流处理程序**再跑一次。

```
所有原始数据 ──→ 【Kafka：可重放的日志，存很久】 ──→ 【Flink：唯一一套流程序】 ──→ 结果存储
                        ↑                                      │
                        └────── 需要重算？把历史数据当流重放 ────┘
```

**一句话记住区别**：
- **Lambda** = 两条管道，批管准、流管快，**代价是两套代码**；
- **Kappa** = 一条管道，**一套代码管一切，代价是重放历史时很吃资源**。

## 📖 原理拆解

### 2.1 Lambda 三层（**必背，填空/简答直接考**）

| 层级 | 职责（踩分词） | 典型技术 |
|------|---------------|---------|
| **批处理层 Batch Layer** | 处理**全量历史数据**，生成**批处理视图**；追求**全量精准、容错高**，延迟高 | Hadoop **MapReduce**、**Spark** |
| **速度层 / 加速层 Speed Layer** | 处理**实时增量流数据**，生成**实时视图**；追求**低延迟**，结果**允许近似**，后续被批结果修正 | **Spark Streaming**、**Flink**、**Storm** |
| **服务层 Serving Layer** | **合并**批处理视图与实时视图，对外提供**统一查询** | **HBase**、**MemSQL**、**Druid** |

> 🔥 **隐藏踩分词**：批处理层存储的是 **不可变的原始数据（Immutable Master Dataset）**。
> 题干出现"**历史数据要求以不可变方式存储以保证准确**"，就是在暗示你选 **Lambda**。

### 2.2 Lambda vs Kappa 对比表（**简答高频，务必背到能默写**）

| 对比维度 | Lambda | Kappa |
|----------|--------|-------|
| 数据处理 | **批处理 + 流处理双管道** | **仅流处理单管道** |
| 架构复杂度 | **高**（两套系统） | **低**（一套流系统） |
| 数据一致性 | 批/流两层差异，**一致性较难** | 单一链路，**一致性好** |
| 代码维护 | **同一逻辑写两遍，维护成本高** | **一套代码** |
| 历史数据处理 | **精准、容错高** | 依赖流引擎**重放**，**吞吐/存储压力大** |
| 典型场景 | **实时 + 历史并重** | **实时为主、偶回溯** |

### 2.3 技术栈分层（**架构图填空直接考**）

```
素材采集层  ：Flume（日志采集）、Sqoop（关系库↔HDFS 导入导出）、Kafka（消息管道）
     ↓
数据存储层  ：HDFS（分布式文件）、HBase（列式 NoSQL）
     ↓
业务逻辑层  ：├─ 批处理层：MapReduce、Spark
              └─ 速度层  ：Spark Streaming、Flink、Storm
     ↓
服务层      ：HBase、MemSQL、Druid（对外查询）；ETL（数据加工）
     ↓
接入/前端    ：Nginx
```

> **填空口诀**：**"Flume/Sqoop/Kafka 采集，HDFS/HBase 存，Spark/MapReduce 算批，Flink/Streaming 算流，HBase/MemSQL 出结果，Nginx 站门口"**

### 2.4 流处理三个进阶概念（**填空/名词解释常考**）

| 概念 | 人话 | 答题关键词 |
|------|------|-----------|
| **Watermark 水位线** | 数据流里插一个"**时间进度标记**"，表示"这个时间点之前的数据基本到齐了"；**容忍乱序与迟到数据**，等满宽限期再触发窗口计算 | 处理**乱序**、容忍**迟到**、窗口**触发**时机 |
| **Exactly‑Once** | 每条数据**有且仅被处理一次**，故障重启**不丢也不重**；Flink 靠 **Checkpoint 状态快照** + **两阶段提交** / **幂等写入** 实现 | **Checkpoint** + **两阶段提交** / **幂等** |
| **CDC 变更捕获** | 监听数据库 **Binlog**（Debezium / Canal），把增删改变成事件流，驱动下游实时更新 | **Binlog**、实时同步 |

### 2.5 数据仓库建模（与题型 3 呼应）

- **星型模型**：**事实表**在中间，直接连一圈**维表**，只有一级维 → **查询效率高**（最常用）；
- **雪花模型**：维表再规范化拆分（地区维 → 省/市维）→ **省存储但 Join 多，查询慢**；
- **数据湖 vs 数据仓库**：数仓 = **结构化、已建模、Schema‑on‑Write**；数据湖 = **原始多类型、Schema‑on‑Read**，支持数据科学与 AI 训练；
- **湖仓一体 Lakehouse**：统一对象存储 + 开放表格式（**Iceberg / Delta Lake / Parquet**）+ **ACID 事务** + **Schema Evolution** + **存算分离**。

**【模板 A：Lambda 三层职责（问题 1 直接默写）】**
> ① **批处理层**：保存全部**不可变的原始历史数据集**，离线计算生成**批处理视图**，结果**精确**但**延迟较高**；技术：Hadoop MapReduce、Spark。
> ② **速度层**：处理最新流入的**实时增量数据流**，生成**实时视图**，用于**填补批处理结果的时间缺口**；实时结果**允许近似**，后续会被批结果**修正**；技术：Spark Streaming、Flink、Storm。
> ③ **服务层**：接收查询请求，**合并批视图与实时视图**，对外提供**统一查询服务**；技术：HBase、MemSQL、Druid。

> - **素材采集层**：Flume、Sqoop、Kafka；
> - **数据存储层**：HDFS、HBase；
> - **业务逻辑层—批处理层**：MapReduce、Spark；**—速度层**：Spark Streaming、Flink；
> - **服务层**：HBase、MemSQL、Druid、ETL；
> - **接入/前端**：Nginx。
> （⚠️ 按实际架构图空白位置调整；**判卷看的是"流/批有没有归对层"**。）

**【模板 C：Lambda vs Kappa 选型论述（问题 3 通用骨架，换场景可直接套）】**
> **结论**：应基于 **Lambda**（或 Kappa）架构。
> **理由**：题干存在两类数据处理需求 ——
> ① **"当日概览"** 为千万级**实时增量**数据，要求**秒级低延迟**，对应 **速度层（流处理）**；
> ② **"赛事回顾"** 为**海量历史**数据、要求**不可变存储保证准确**，对应 **批处理层（全量批处理）**。
> Lambda 通过"**批处理 + 流处理**"**双管道**分别满足"**历史全量精准**"与"**实时低延迟**"两类需求，并由**服务层合并结果**，最贴合本系统**实时与历史并重**的特征。
> （若选 Kappa 则反向论述：Kappa 为**单流管道**，适合**实时为主、偶尔回溯**的场景，可用**一套代码**同时完成实时计算与离线重算，避免两套代码不一致。）

**【模板 D：批流结果不一致的找茬题】**
> 根因：业务统计逻辑分别在**流处理代码、批处理代码两份代码中独立实现**，两份程序逻辑很难做到完全一致，造成指标结果偏差。
> 改进：迁移 **Kappa 流批一体**架构，用**同一套流处理代码**，通过**重放 Kafka 历史数据**完成离线重算，从根本上消除双实现差异。

**【模板 E：迁移 Kappa 后的挑战（8 分送分题）】**
> ① **存储压力**：Kafka 需**长期保存海量历史数据流**，存储成本高；
> ② **算力压力**：**回放海量历史数据**重算会消耗大量集群算力；
> ③ 对流处理引擎**性能与稳定性要求极高**。

## ⚠️ 丢分点（**本模块丢分最集中的地方**）

1. ❌ **批处理层和速度层的特点写反** → 记住：**批处理层 = 慢 + 准**；**速度层 = 快 + 近似**。
2. ❌ **服务层只答"存储数据"** → 关键词是"**合并**批处理视图与实时视图，提供**统一查询**"。漏"合并"丢分。
3. ❌ **技术栈归错层** → 最容易错的三个：**Kafka 是采集/管道（不是存储层主力）**、**HBase 既在存储层也在服务层**（看空白在哪）、**ETL 在数据加工/服务环节**。
4. ❌ **选型题只写"选 Lambda"不结合题干** → 必须**把题干的两个场景分别对应到两层**（如"当日概览→速度层，赛事回顾→批处理层"），这才是给分点。
5. ❌ **Kappa 的缺点答不出来** → 必须答出"**历史重放吞吐/存储压力大**"和"**对流引擎性能要求高**"两条。
6. ❌ **漏掉"实时结果会被批结果修正"** → 这是**拉开差距的加分点**，写上它比别人多一分。
7. ❌ **Lambda 缺点只答"架构复杂"** → 标准答法是"**需维护两套独立的业务处理代码，同一逻辑两份实现易不一致，维护成本高**"，"两套代码"是核心踩分词。

# 3. 嵌入式系统架构（含 SOME/IP、DDS、ROS）

> 对应原文第 2 章 ｜ **2024 年考了两次（5 月 SOME/IP+DDS、11 月 ROS），是近年最稳定的专项赛道**

## 🧊 直觉：从"手机 App"到"心脏起搏器"

| | 你熟悉的普通软件 | 嵌入式系统 |
|---|---|---|
| 运行环境 | 手机/服务器，内存 8G 起步 | **芯片上，内存可能只有 几十 KB** |
| 慢一点会怎样 | 卡一下，用户骂两句 | **可能出人命**（飞控、机械臂） |
| 升级 | 随时发版 | 可能装在天上/车里，**十年不动** |
| 用途 | 通用 | **专用**，软硬件深度绑定 |

**核心特征四个词**：**资源受限、实时性高、可靠性/安全性高、专用性强**。

### 硬实时 vs 软实时（**送分题，别答错**）

- **硬实时**：**必须在截止期内完成，超时 = 灾难**。例：飞控、工业机器人、心脏起搏器、汽车刹车。
- **软实时**：**尽量按时，偶尔超时只是体验差**。例：视频直播、语音通话、音乐播放。

### 两个通信协议的直觉

想象一辆智能汽车里有 100 多个小电脑（ECU）要互相说话：

**SOME/IP = 打电话**
1. 先查通讯录找到对方 → **服务发现（SOME/IP SD）**；
2. 拨号，说"帮我算个东西"，对方回结果 → **远程过程调用（RPC）**；
3. 也可以订阅："有事你通知我" → **事件通知 / 发布订阅**。
→ 本质是**面向服务（SOA）**：每个 ECU 把自己的能力包装成"服务"挂出来，谁需要谁来调。

**DDS = 订报纸**
1. 你不需要知道"报社在哪"，只需要说"**我要订《体育版》**" → **发布/订阅，去中心化发现**；
2. 还能约定"**每天早上 7 点前必须送到、丢了要补送**" → **QoS 策略**；
3. 数据自动送到，中间不需要你打电话问。
→ 本质是**数据中心化分发**：适合"一堆节点高速互相同步数据"的场景（机器人各关节、工业产线）。

> **选型口诀（背死）**：
> **"汽车以太网 / 车载 SOA / 要 RPC" → SOME/IP；"高实时数据分发 / 机器人多机协同 / 要 QoS" → DDS。**

### ROS 四种通信方式的直觉（**选词填空必考**）

ROS 是机器人的"**神经系统**"，四种通信方式就像四种说话方式：

| 方式 | 生活类比 | 场景 |
|------|---------|------|
| **话题 Topic** | **校园广播**：我喊，谁想听谁听，我不关心谁在听 | 传感器数据（激光雷达、摄像头持续发数据） |
| **服务 Service** | **问路**：我问一句你答一句，问完就结束 | 单次查询/操作（"当前电量多少？"） |
| **动作 Action** | **派快递任务**：时间很长，中途会汇报进度，**还能取消** | 机器人导航、机械臂抓取等长任务 |
| **参数 Parameter** | **控制面板上的旋钮**：全局共享，随时可调 | 系统运行参数（最大速度、PID 系数） |

## 📖 原理拆解

### 3.1 RTOS 实时操作系统

提供 **任务调度、中断处理、任务间通信**（消息队列 / 信号量 / 共享内存）。
常见 RTOS：**VxWorks、RT‑Thread、FreeRTOS、QNX**（车载/工业）。

### 3.2 实时调度算法（**计算/简答点，别丢**）

| 算法 | 核心规则 | 特点 |
|------|---------|------|
| **RM 速率单调调度** | **任务周期越短，优先级越高**；优先级**静态固定**，运行期不变 | 简单、可预测；CPU 利用率上界 **n(2^(1/n) − 1)**，n→∞ 时约 **69%** |
| **EDF 最早截止期优先** | **截止时间越早，优先级越高**；优先级**动态变化** | 利用率可达 **100%**，更充分；但过载时行为难预测 |

> 答题话术：**RM 静态简单、EDF 动态高效**。

### 3.3 SOME/IP 六大特点（**2024.05 真题第 1 问，9 分，逐条背**）

1. **服务导向架构（SOA）**；
2. 支持**远程过程调用（RPC）**；
3. **轻量级**，适合资源受限的车载环境；
4. **多种通信方式**：请求/响应、事件通知、发布/订阅；
5. **二进制编码**，效率高；支持 **TCP/UDP**；
6. **动态服务发现（SOME/IP SD）**。
> 适用：**车载 ECU 间面向服务通信、智能网联汽车、自动驾驶**。

### 3.4 DDS 特点

- **高实时性**；
- **QoS 控制**（可靠性 / 时延 / 带宽 等策略可配）；
- **去中心化发现**，基于**发布/订阅**；
> 适用：**工业自动化、航空航天、机器人**等高实时性场景。

### 3.5 ROS2 相比 ROS1 的五大改进（**2024.11 真题，简答高频**）

| # | 改进 | 关键词 |
|---|------|--------|
| 1 | **通信机制升级** | ROS1 用 TCPROS/UDPROS，ROS2 采用 **DDS**，支持更高效分布式通信 |
| 2 | **跨平台增强** | 支持 Linux / Windows / Mac / **RTOS** |
| 3 | **实时性提升** | DDS 提供 **QoS 控制**，适用于时延敏感实时系统 |
| 4 | **安全性提升** | 提供**身份验证、加密通信** |
| 5 | **生命周期管理** | 引入**节点生命周期**（启动 / 挂起 / 恢复） |

> **记忆口诀**：**"通信换 DDS、跨平台、QoS、安全、生命周期"**（谐音："**通跨 Q 生安**"）。

### 3.6 ROS 定义与特点（**真题第 1 问**）

面向机器人的**开源操作系统框架**，提供**硬件抽象、底层设备控制、进程间通信（IPC）、工具库**。
特点：**分布式（Pub/Sub）、消息传递、包管理、多语言（C++ / Python）**。

## ✍️ 怎么答（模板）

**【模板 A：SOME/IP 特点（9 分题直接默写 3.3 的六条）】**
> SOME/IP（Scalable service‑Oriented MiddlewarE over IP）是 **AUTOSAR 发布的、面向汽车以太网的可扩展面向服务 IP 中间件**。其特点为：①采用**服务导向架构（SOA）**；②支持**远程过程调用（RPC）**；③**轻量级**，适合资源受限环境；④支持多种通信方式（**请求/响应、事件通知、发布/订阅**）；⑤**二进制编码**高效，支持 **TCP/UDP**；⑥支持**动态服务发现（SOME/IP SD）**。适用于**车载 ECU 间面向服务通信、智能网联汽车与自动驾驶**场景。

**【模板 B：DDS 特点】**
> DDS（Data Distribution Service）是基于**发布/订阅**的实时高效**数据分发中间件**。特点：**高实时性**、提供丰富的 **QoS 控制**（可靠性/时延/带宽）、**去中心化发现**。适用于**工业自动化、航空航天、机器人**等高实时性场景。

**【模板 C：SOME/IP vs DDS 框图填空（6 分送分）】**
> - **车载 SOA 通信层 / 服务调用层** → 填 **SOME/IP**；
> - **高实时数据分发层 / 传感器数据分发层** → 填 **DDS**。
> （判分逻辑：看到"**服务、RPC、服务发现**"填 SOME/IP；看到"**实时分发、QoS**"填 DDS。）

**【模板 D：ROS 四种通信方式选词填空】**
> - 传感器数据持续共享、**单向异步** → **话题（Topic）**；
> - **单次**查询/操作、**请求/响应** → **服务（Service）**；
> - **长时间**任务、需要**中途反馈进度/可取消** → **动作（Action）**；
> - **全局配置变量**、运行中可动态调整 → **参数（Parameter）**。

**【模板 E：嵌入式可靠性保障措施（8 分，写 4 条）】**
> ① **硬件冗余**（关键部件双冗余/三冗余）；
> ② **软件容错**：**N 版本程序设计**（多版本独立实现 + 多数表决）、**恢复块**（主模块 + 后备模块）；
> ③ **信息冗余**：校验码 / CRC / 纠错编码；
> ④ **故障检测**：**心跳检测、超时探测、看门狗（Watchdog）、BIT 内置自测**，配合故障切换与降级。

## ⚠️ 丢分点

1. ❌ **SOME/IP 和 DDS 写混（最高频失分）** → 死记：**车 + SOA + RPC + 服务发现 = SOME/IP**；**高实时 + 发布订阅 + QoS + 机器人 = DDS**。
2. ❌ **ROS2 改进的 5 条漏"DDS"或"QoS"** → 这两条是**核心得分点**，漏一条扣大分。
3. ❌ **动作（Action）和服务（Service）分不清** → **服务 = 短、一次响应**；**动作 = 长、有进度反馈、可取消**。填空看到"导航/抓取/长任务"选**动作**。
4. ❌ **硬实时/软实时举错例子** → 硬实时：**飞控、工业机器人、医疗生命设备**；软实时：**视频直播、语音通话**。
5. ❌ **写 ROS 特点漏"分布式"和"多语言"** → 标准四条：**分布式（Pub/Sub）、消息传递、包管理、多语言**。
6. ❌ **嵌入式特征漏"资源受限"** → 四个词一起背：**资源受限、实时性高、可靠安全、专用性强**。
7. ❌ **RM/EDF 说反** → **RM 看周期（周期短优先，静态）**；**EDF 看截止期（截止早优先，动态）**。

# 4. IoT / 边缘计算架构（端边云）

> 对应原文第 3 章

## 🧊 直觉：10 万路摄像头该往哪传？

某市要装 **10 万路高清摄像头**做智慧城市。

**方案 A（全传云）**：所有视频流 7×24 传回中心云。
→ 结果：**带宽爆炸**（每月网费几千万）、**延迟高**（识别到人再报警已经晚了 10 秒）、**隐私风险**（所有街景传到云端）。

**方案 B（边缘计算）**：在**小区机房**放一台边缘盒子，视频**就地分析**，只把"**发现可疑人员**"这样的**结构化结果 + 关键截图**传回云端。
→ 结果：**时延从 10 秒降到 100 毫秒**、**带宽省 95%**、**原始视频不出小区**（隐私）、**断网也能本地报警**。

> **一句话记住边缘计算的价值**：**"数据在哪里产生，就在哪里先处理一遍。"**

### 端边云三层

```
【端 设备层】传感器/执行器/嵌入式设备  →  采集数据、执行动作
      ↓
【边 边缘层】边缘网关/边缘节点        →  就近处理、实时响应、协议转换、断网自治
      ↓
【云 中心云】                        →  海量存储、全局分析、模型训练、跨区域协同
```

> ⚠️ **边缘不是来取代云的** —— 它们是**分工**：**边做"快"的事（实时响应），云做"大"的事（全局训练、长期存储、跨域分析）**。
> 答题时写"**边云协同**"，别写"用边缘替代云"。

### 两个协议的直觉

- **MQTT**：**设备界的"公众号推送"**。设备是发布者，云端是订阅者，中间有个"**Broker 中转站**"。**极轻量**（头部只有 2 字节）、支持**低带宽不稳定网络**、支持**断线重连和遗嘱消息**。→ **设备→云端的主流协议**。
- **CoAP**：**"迷你版 HTTP"**。长得像 HTTP（也有 GET/POST），但跑在 **UDP** 上，二进制格式，专为**资源极度受限**的设备设计。
- **HTTP/HTTPS**：与云端 **API** 交互时才用（比如设备上报到业务系统）。

## 📖 原理拆解

### 4.1 边缘计算四大核心价值（**简答必写全**）

1. **低时延**：数据**就近处理**，满足实时响应；
2. **省带宽**：减少**回源流量**，降低传输成本；
3. **隐私保护**：原始数据**不出本地**，只上传结果；
4. **离线可用**：网络中断时**本地自治**，不依赖云端。

> **记忆口诀**：**"快、省、私、稳"**（低时延 / 省带宽 / 隐私 / 离线可用）。

### 4.2 典型场景

**智能工厂**（产线质检毫秒级剔除）、**车路协同**（路侧单元就近计算）、**智慧城市摄像头**、**远程医疗**、**AR/VR**。

## 🎯 怎么考

| 问法 | 典型提问 |
|------|---------|
| ① 概念题 | "简述端边云三层架构及各层职责。" |
| ② 价值题 | "说明边缘计算相比全部上云的优势。" |
| ③ 协议填空 | "设备与云端通信应采用什么协议？说明理由。"（MQTT） |
| ④ 方案设计 | "某工厂有 5000 台设备，请设计物联网平台架构。" |

## ✍️ 怎么答（模板）

**【模板：端边云架构 + MQTT 选型】**
> 采用**端—边—云三层架构**：
> ① **端（设备层）**：由传感器/执行器/嵌入式设备构成，负责**数据采集与指令执行**，通过 **MQTT** 协议经**边缘网关**接入（MQTT 为**轻量级发布/订阅**协议，**开销小、支持低带宽不稳定网络、支持断线重连**，适合海量设备接入）；
> ② **边（边缘层）**：部署**边缘网关/边缘节点**，实现**协议转换、数据预处理与就近实时处理**，达到**低时延响应、减少回源带宽、原始数据不出厂区（隐私保护）、断网时本地自治**四项价值；
> ③ **云（中心云）**：负责**海量数据存储、全局分析、模型训练与跨区域协同**，并将训练好的模型**下发到边缘**执行。
> 三者**边云协同**，边负责"**快**"、云负责"**大**"。

## ⚠️ 丢分点

1. ❌ **把 MQTT 说成"请求/响应"协议** → 它是**发布/订阅**（Broker 中转），这是最高频错误。
2. ❌ **边缘价值只答"低时延"一条** → 四条都要写：**低时延、省带宽、隐私保护、离线可用**。
3. ❌ **说"用边缘计算替代云"** → 正确表述是**边云协同**（边管实时，云管全局训练与存储）。
4. ❌ **CoAP 和 MQTT 混用场景** → **设备↔云端主流选 MQTT**；**极度受限的传感器节点、类 HTTP 语义**才提 CoAP。
5. ❌ **漏了"模型下发"这一环** → 完整的边云协同是"**边缘采集 → 云端训练 → 模型下发边缘执行**"的闭环。

# 5. AI 系统架构（2026 新大纲重点）

> 对应原文第 4 章 ｜ **新大纲约占 25%，2025 年已经考了两次，是最值得投入的新方向**

## 🧊 直觉：读书 vs 答题

| | 训练（Training） | 推理（Inference） |
|---|---|---|
| 类比 | **读十年书** | **上考场答题** |
| 频率 | 一次性/周期性 | **每秒成千上万次** |
| 关心什么 | **吞吐**、**互联带宽**、算力 | **延迟**、**成本**、**并发** |
| 硬件 | 万卡 GPU 集群 | 少量 GPU / 推理卡 |

**考点提示**：题目问"**训练平台**"和"**推理服务**"，答案几乎完全不同。先分清是哪一个。

### 训练平台 = 解释器风格（**2025 上真题**）

> **直觉**：你写了一段 Python 模型代码，点击"运行"。
> 系统需要：① **读懂**你的代码（解析）；② 把它变成能**执行**的任务；③ 给你**分配** GPU。
> 这跟 **Java 虚拟机 / Python 解释器** 干的事一模一样 —— 所以叫 **解释器风格（Interpreter）**。

```
用户代码（Python） → 解析器（Parser） → 执行引擎 → 资源调度器 → GPU/计算资源（硬件平台）
```

> **为什么适合解释器风格？** 因为**用户用高级语言描述"要算什么"，系统负责翻译成底层可执行任务并调度资源**，
> **用户无需关心底层硬件**。解释器风格的本质就是"**定义一种语言的表示，并用一个解释器去解释执行它**"。

### RAG = 开卷考试（**超高频**）

> **闭卷考试**：大模型只靠训练时记住的知识答题 → 遇到没见过的、或最新的信息，就会**一本正经地胡说** = **幻觉（Hallucination）**。
> **开卷考试（RAG）**：答题前先去**资料库翻一翻**，把相关内容放在面前，再结合资料作答，还能**标注引用出处**。

```
用户提问 → 【向量化】→ 【向量数据库检索召回相关片段】→ 【拼进 Prompt 上下文】→ 【大模型生成】→ 带引用来源的答案
```

> **RAG 解决两件事**：**幻觉** + **知识时效性**（改知识库即可更新，不用重新训练）。

### Agent = 会自己想办法的实习生

```
感知（Perception）→ 规划（Planning，ReAct/CoT 思维链）→ 行动（Action，调用工具）→ 记忆（Memory）→ 反思（Reflection）
```
- **工具调用 Tool Use**：查天气、算数学、查数据库、调 API；
- **记忆 Memory**：短期 = 对话上下文；长期 = 持久化存储/向量库；
- **多智能体**：**父 Agent 编排、子 Agent 执行**，角色分工（CrewAI / AutoGen）。

### 推理加速三件套的直觉

| 技术 | 生活类比 |
|------|---------|
| **PagedAttention（vLLM）** | 显存的**"虚拟内存分页"** —— 把 KV Cache 切成小块分页复用，显存利用率从 20% 提到 90%+ |
| **量化（INT8/INT4）** | 把"精确到小数点后 8 位"改成"**保留整数**" —— 模型变小、算得快，精度略降 |
| **模型蒸馏** | **老师（大模型）教学生（小模型）** —— 小模型学到老师的本事，但体积小 10 倍 |
| **投机采样 Speculative Decoding** | **小模型先打草稿，大模型批量批改** —— 一次验证多个 token，速度翻倍 |

## 📖 原理拆解

### 5.1 典型 AI 架构模式（**四种，认脸用**）

| 模式 | 组成/流程 | 考点 |
|------|-----------|------|
| **训练平台架构** | 用户代码 → 解析器 → 执行引擎 → 资源调度器 → GPU 资源 | **解释器风格**（2025 上真题） |
| **推理服务架构** | 模型仓库 → 模型服务（推理引擎）→ API 网关 → 业务应用 | **模型版本管理、灰度发布、A/B 测试** |
| **RAG 架构** | Query → 向量检索 → 召回上下文 → 大模型生成 | 解决**幻觉**与**知识时效性** |
| **Agent 架构** | 规划 → 工具调用 → 记忆 → 反思；支持分层委托 | **工具注册发现、上下文压缩、Guardrails 护栏** |

### 5.2 AI 关键质量属性（**与题型 1 结合，必答**）

- **推理延迟**（性能）：**端到端响应时间**、**首 Token 延迟**；
- **吞吐**（性能）：**QPS / TPS** 并发推理能力；
- **模型准确率 / 可用率**（功能 / 可用性）；
- **可解释性**：决策**可追溯**、**审计日志**；
- **数据隐私与安全**：训练/推理数据**脱敏**、**访问控制**。

### 5.3 AI 集群高性能网络（**2025 真题方向**）

| 技术 | 要点 |
|------|------|
| **RDMA / RoCE** | **远程直接内存访问，绕过 CPU**，极低时延；**万卡训练刚需** |
| **ECMP** | 等价多路径负载均衡；**易出现哈希不均（哈希极化）** |
| **包喷洒 Packet Spraying** | 把**一条流打散到多条路径**，缓解 ECMP 不均与拥塞 |
| **拥塞控制（如 APSCC）** | **动态调整拥塞阈值**，保障训练稳定性 |
| **弹性伸缩 + 高可靠** | 节点扩容拓扑快速调整；**故障恢复时间达标（如 ≤5 分钟）** |

### 5.4 推理加速与成本优化战术（**高频踩分**）

- **推理加速**：**PagedAttention**（vLLM，显存分页复用 KV Cache）、**算子融合**（TensorRT）、**投机采样**；
- **量化压缩**：**INT8 / INT4 量化**、**模型蒸馏**；
- **弹性伸缩**：基于**队列长度 / GPU 利用率**的 **HPA**、**Spot 实例**混合部署；
- **成本控制**：**模型路由**（简单问题走小模型）、**语义缓存**（相似请求直接复用）、**离线批量推理**；
- **可观测**：**Token 消耗监控、链路追踪、幻觉检测**。

## ✍️ 怎么答（模板）

**【模板 A：解释器风格（填空 + 理由，送分题）】**
> **组成（按顺序填）**：**用户代码 → 解析器（Parser）→ 执行引擎 → 资源调度器 → GPU/计算资源（硬件平台）**。
> **适合理由**：用户使用 **Python 等高级语言描述模型与训练逻辑**，系统需要**对其进行解析、转换为可执行的计算任务，并根据任务需求动态匹配与调度底层计算资源**（GPU 等），**用户无需关心底层硬件**。这正符合解释器风格"**定义一种语言的表示，并提供解释器对该语言进行解释执行**"的特征，且具备良好的**可移植性与可扩展性**。

**【模板 B：AI 需求"功能 + 非功能"双答（★ 最重要的答题习惯）】**
> 当题目涉及 AI 需求时，**必须同时回答功能实现与非功能保障**：
> ① **功能**：采用 **RAG 架构**（向量检索 + 大模型生成）提升回答准确率，并**标注引用来源**以支持溯源；
> ② **性能**：通过**向量缓存 + 模型量化（INT8）+ PagedAttention**，将 **P99 延迟控制在 500ms 内**，支撑 **XX QPS** 并发；
> ③ **安全**：部署 **Guardrails 安全护栏**，防止**敏感信息泄露与越权访问**，并对训练/推理数据**脱敏**；
> ④ **可观测**：建设 **Token 消耗监控、链路追踪、幻觉检测**；
> ⑤ **成本**：采用**模型路由**（简单问题走小模型）+ **语义缓存**，降低推理成本。

**【模板 C：AI 集群网络问题诊断与优化（10 分题）】**
> **① ECMP 负载不均** → 采用 **包喷洒（Packet Spraying）** 将流打散到多条等价路径，缓解哈希极化；
> **② 拥塞控制收敛不足/速率波动** → 采用 **APSCC 等自适应拥塞控制**，**动态调整拥塞阈值与降速步长**，配合 **PFC / ECN** 实现端到端无损网络；采用 **RDMA/RoCE** 绕过 CPU 降低时延；
> **③ 扩容慢** → 基于 **GPU 利用率 / 队列长度的 HPA 自动扩缩容**，预置**资源池与拓扑感知调度**，缩短扩容时间；
> **④ 故障恢复 12 分钟不达标** → 建设**健康探测与故障自动发现**（心跳/探针）、**Checkpoint 周期性保存训练状态**、**故障节点自动隔离与任务重调度**、**断点续训**，将恢复时间压到 **≤5 分钟**；并定期开展**故障演练**。

## ⚠️ 丢分点

1. ❌ **只答功能实现，不答非功能保障** → AI 题**必须同时答"功能 + 性能 + 安全 + 成本"**，这是本方向最大的丢分点。
2. ❌ **解释器风格四件套顺序写错** → 必须是 **用户代码 → 解析器 → 执行引擎 → 资源调度器 → 硬件平台**。
3. ❌ **RAG 答成"微调"** → **RAG = 外挂知识库，不改模型**；**微调 = 改模型参数**。判断口诀：**知识更新频繁 / 要引用出处 → RAG**；**风格格式固定 / 任务专一 → 微调**。
4. ❌ **训练和推理需求混为一谈** → **训练关心吞吐与互联带宽（RDMA）**；**推理关心延迟与成本（量化/PagedAttention）**。
5. ❌ **漏 "Guardrails 护栏" 和 "幻觉检测"** → 涉及安全/合规的 AI 题，这两个词是**标准配置**。
6. ❌ **只说"用 GPU"不说调度** → 完整答法要含**资源调度器、弹性伸缩（HPA）、Spot 实例降本**。
7. ❌ **质量属性题漏"可修改性"** → "功能扩展 3 天内完成"对应**可修改性**，不是性能，别被"3 天"骗了。

# 6. 安全架构（零信任 / 等保 / 国密）

> 对应原文第 5 章

## 🧊 直觉：从"城堡"到"机场安检"

**传统安全（城堡+护城河）**：
> 公司在网络边界修一道高墙（防火墙）。**进了墙 = 自己人**，墙内可以自由走动。
> **问题**：一旦有人混进来（钓鱼邮件、内鬼、笔记本带病毒），就能**横向移动**，如入无人之境。

**零信任（机场安检）**：
> **没有"里面"和"外面"的区别**。每一道门都要**验身份**，而且**不是验一次就完事**——
> 你**从候机区到登机口、再到飞机上**，每一道都要再验一次，还要看你的**登机牌（权限）、体温状态（设备合规性）、目的地（访问目标）**。

**零信任八字真言**：**永不信任，始终验证（Never Trust, Always Verify）**。

### 三种授权模型的直觉

| 模型 | 一句话 | 生活类比 |
|------|--------|---------|
| **RBAC 基于角色** | **你是谁** | **工牌**：财务经理的工牌能刷开财务室 |
| **ABAC 基于属性** | **什么条件** | **动态规则**："仅工作时间内 + 公司设备 + 密级匹配 + 在公司内网"才能访问 |
| **ReBAC 基于关系** | **你跟谁有关系** | **社交关系**："因为你是这个文档的协作者，所以你能看" |

> **组合用法（答题加分）**：**常规系统用 RBAC；敏感/复杂场景叠加 ABAC；社交/文档协作类用 ReBAC**。

### 国密三件套（**口诀：2 非、3 摘、4 对**）

| 算法 | 类型 | 替代谁 | 用途 |
|------|------|--------|------|
| **SM2** | **非对称**加密 / 数字签名 | RSA | 身份认证、签名验签、密钥交换 |
| **SM3** | **哈希 / 摘要** | MD5 / SHA‑1 | 完整性校验、防篡改 |
| **SM4** | **对称**加密 | AES / 3DES | 数据加密存储与传输 |

> 口诀：**"2 非对称、3 摘要、4 对称"**。

## 📖 原理拆解

### 6.1 零信任五大关键能力（**简答必写全**）

**身份认证**、**设备合规检查**、**最小权限**、**微隔离**、**持续监测**。

> ⚠️ 别只答"加强认证"—— **五条缺一不可**。

### 6.2 等保 2.0

- 网络安全等级保护 2.0，分 **一至五级**，等级越高要求越严；
- **政务 / 金融核心系统常要求等保三级**；
- 要点：**安全物理环境、安全通信网络、安全区域边界、安全计算环境 + 安全管理中心**（"**一个中心、三重防护**"）。

### 6.3 安全架构设计要点（**万能清单，方案题直接套**）

**身份认证**（OAuth2 / OIDC + JWT）→ **权限控制**（RBAC / ABAC）→ **传输加密**（TLS）→ **存储加密**（AES / SM4）→ **数据脱敏** → **审计日志** → **入侵检测/防护（IDS/IPS）** → **灾备与恢复**。

### 6.4 数据脱敏

对敏感字段（**身份证 / 手机号 / 姓名 / 银行卡**）进行**变形/遮蔽**，**保留数据可用性**（格式、长度、统计特征）的同时**防止泄露**，常用于**测试 / 分析 / 开发环境**。

## 🎯 怎么考

| 问法 | 典型提问 |
|------|---------|
| ① 概念题 | "简述零信任架构的核心原则与关键能力。" |
| ② 对比题 | "比较 RBAC、ABAC、ReBAC 并说明各自适用场景。" |
| ③ 方案设计 | "为某政务系统设计安全架构。"（常与信创捆绑） |
| ④ 填空题 | "国密算法 SM2/SM3/SM4 分别用于什么场景？" |
| ⑤ 找茬题 | "指出该系统在安全方面存在的问题并给出改进建议。" |

## ✍️ 怎么答（模板）

**【模板：安全架构方案设计（万能六条）】**
> ① **身份认证**：采用 **OAuth2 / OIDC + JWT** 统一身份认证，支持**多因素认证（MFA）**；
> ② **访问控制**：采用 **RBAC** 做基础授权，**敏感操作叠加 ABAC** 实现细粒度动态授权（基于用户/资源/环境属性 + 策略决策点），遵循**最小权限原则**；
> ③ **传输与存储安全**：传输层 **TLS**；存储层敏感字段采用 **SM4 对称加密**；完整性校验采用 **SM3 摘要**；签名与身份认证采用 **SM2 非对称算法**，满足**国产化合规**；
> ④ **数据保护**：对身份证/手机号/姓名等敏感字段进行**脱敏**（测试与分析环境），生产环境**加密存储**；
> ⑤ **网络安全**：按**等保三级**要求建设，落实**安全物理环境、通信网络、区域边界、计算环境**防护与**安全管理中心**，并引入**零信任**理念实现**微隔离与持续验证**；
> ⑥ **审计与应急**：全量**审计日志**留存，**入侵检测/防护（IDS/IPS）**，**安全态势感知**与**应急响应预案**，并开展**等保测评与定期演练**。

## ⚠️ 丢分点

1. ❌ **SM2 / SM3 / SM4 三个搞混（超高频）** → 背死"**2 非对称签名、3 摘要、4 对称加密**"。
2. ❌ **零信任只答"加强身份认证"** → 五条要全：**身份认证、设备合规、最小权限、微隔离、持续监测**。
3. ❌ **ABAC 说成"按角色"** → ABAC 是**按属性 + 策略动态决策**，关键词是"**细粒度、动态**"。
4. ❌ **等保等级说成"三级最高"** → 等保分**五级**，只是**政务/金融核心通常要求三级**。
5. ❌ **脱敏答成"加密"** → 脱敏是**变形/遮蔽后仍可用**（如 138****1234），加密是**密文不可直接用**；**脱敏用于测试/分析环境**。
6. ❌ **漏"审计日志"** → 合规类题目中审计是**必答项**，涉及溯源与追责。

# 7. 系统计划（立项 / 可行性研究 / 技术方案论证）

> 对应原文第 6 章 ｜ **官方独立模块，不是边缘考点**

## 🧊 直觉：要不要盖这栋楼？

老板说要在城东盖一栋 30 层的写字楼。你作为总设计师，要先回答**四个问题**（缺一个方案都过不了会）：

| 问题 | 大白话 | 对应可行性维度 |
|------|--------|--------------|
| 1. **这楼盖得起来吗？** | 地质行不行？我们有没有这个技术？有没有会盖 30 层的人？ | **技术可行性** |
| 2. **划不划算？** | 投入多少钱？多久回本？ | **经济可行性** |
| 3. **盖完能用起来吗？** | 有没有物业管？员工愿不愿意搬？流程跟得上吗？ | **操作/运行可行性** |
| 4. **合法吗？** | 符不符合规划、消防、环保法规？ | **法律/合规可行性** |

> ⚠️ **四个维度缺一不可** —— 新手最常犯的错就是**只答"技术 + 经济"，漏掉"运行"和"法律"**。

## 📖 原理拆解

### 7.1 可行性研究四维度（**必背，一字不差**）

| 维度 | 核心问题 |
|------|---------|
| **技术可行性** | 技术方案是否**成熟**、团队是否**具备能力**、技术**风险是否可控** |
| **经济可行性** | **成本/收益分析**，**投资回报率（ROI）**、**回收期**是否合理 |
| **操作/运行可行性** | **组织/人员/流程**是否支持系统上线运行 |
| **法律/合规可行性** | 是否符合**法律法规、行业标准**、**数据安全/隐私**要求 |

### 7.2 项目立项

- **立项依据**：**业务需求、战略匹配、政策/合规要求**；
- **产出**：**立项建议书、项目章程**，明确 **目标 / 范围 / 约束 / 干系人（stakeholders）**。

### 7.3 技术方案论证（**方案设计题抓手**）

- **多方案对比**（候选架构 / 技术栈），从 **功能满足度、性能、成本、风险、可扩展性、合规性** 六个维度论证；
- **必须给出推荐方案及理由**（只罗列对比不给结论 = 丢分）；
- **经济指标**：**ROI**（投资回报率）、**TCO**（总拥有成本）、**投资回收期**；
- **里程碑规划**：**分阶段交付**，设置**验收标准**；
- **风险识别**：识别 **技术 / 人员 / 进度 Top3 风险**，给出**缓解措施**；
- **产出**：**可行性研究报告、技术方案选型报告**。

## 🎯 怎么考

| 问法 | 典型提问 |
|------|---------|
| ① 概念题 | "可行性研究包括哪几个方面？各自解决什么问题？" |
| ② 论证题 | "请从可行性角度论证该项目是否应该立项。" |
| ③ 方案对比题 | "给出三套候选方案，请设计对比维度并推荐一套。" |
| ④ 风险题 | "识别该项目的 Top3 风险并给出缓解措施。" |

## ✍️ 怎么答（模板）

**【模板 A：可行性研究四维度（直接默写表格）】**

**【模板 B：方案论证/推荐（万能骨架）】**
> ① **候选方案**：方案 A（…）、方案 B（…）、方案 C（…）；
> ② **对比维度**：从**功能满足度、性能、成本、风险、可扩展性、合规性**六个维度对比（做成表格最佳）；
> ③ **推荐结论**：**推荐方案 X**；
> ④ **推荐理由**：该方案在 **XX 维度**上最契合本项目约束（如"团队已有 Java 技术积累，技术风险最低""存算分离，后续可扩展性强""采用国产组件，满足自主可控合规要求"），**TCO 最低 / ROI 最高**；
> ⑤ **经济指标**：预计投资 **XX 万**，**投资回收期 X 年**，**ROI 约 XX%**；
> ⑥ **里程碑**：分 **X 期**交付，各阶段设**验收标准**；
> ⑦ **风险与缓解**：识别**技术/人员/进度** Top3 风险，逐条给出**缓解措施**（如"国产数据库兼容性风险 → 提前做兼容性验证与双轨运行"）。

## ⚠️ 丢分点

1. ❌ **四维度只答两条** → **技术、经济、操作（运行）、法律（合规）** 四条全写，漏"运行"和"合规"是新手通病。
2. ❌ **只做方案对比，不给推荐结论** → 题目要的是"**论证 + 决策**"，**没有推荐 = 没有结论 = 丢大分**。
3. ❌ **ROI 和 TCO 说不清** → **ROI = 投资回报率（赚多少/投多少）**；**TCO = 总拥有成本（买 + 运维 + 人力 + 升级的全部成本）**。
4. ❌ **经济可行性只写"成本低"** → 要答出**成本/收益分析、ROI、投资回收期**三个词。
5. ❌ **风险题只列风险不给缓解措施** → 每题必须"**风险 → 缓解措施**"成对出现。

# 8. 通信系统架构

> 对应原文第 7 章 ｜ **官方独立模块，时延四要素是简答高频**

## 🧊 直觉：寄一个快递要多久？

你从北京寄一个包裹到上海，总耗时由**四段**组成 —— 这就是**时延四要素**：

| 时延类型 | 快递类比 | 技术定义 | 跟什么有关 |
|---------|---------|---------|-----------|
| **传输时延** | **装车时间**：把包裹搬上车要多久 | 把数据的所有比特**推到链路上**的时间 | **数据块大小 / 带宽**（包越大、带宽越小 → 越慢） |
| **传播时延** | **路上跑的时间**：车在路上开多久 | 信号在**介质中传播**的时间 | **距离 / 传播速度**（约光速） |
| **处理时延** | **分拣中心处理**：扫码、分拣 | 路由器/交换机**检查首部、查路由表** | 设备性能 |
| **排队时延** | **堵车排队**：在收费站等着 | 在路由器**输出队列等待** | **网络拥塞程度** |

> 🔥 **最容易混的就是前两个**：
> **传输时延 = 往门外推（跟带宽有关）**；**传播时延 = 在路上跑（跟距离有关）**。
> 口诀：**"传输看出水口粗细，传播看路程远近。"**

**RTT（往返时间）**：你**喊一嗓子到听到回声**的时间（数据发出 → 收到 ACK）。

**QoS 四指标**：**带宽、时延、抖动、丢包率**。（**抖动 = 时延的变化量**，视频卡顿的元凶）

## 📖 原理拆解

### 8.1 网络拓扑

**总线型、星型、环型、树型、网状（Mesh）**。
- **星型**：好管理、易扩展，但**中心节点单点故障**；
- **网状 Mesh**：**可靠性最高**（多路径），但**成本高、布线复杂**。
> 拓扑选择影响 **可靠性、扩展性、成本** 三件事。

### 8.2 协议分层速记

**物理层 → 数据链路层（MAC） → 网络层（IP/路由） → 传输层（TCP/UDP） → 应用层（HTTP/MQTT/DDS/SOME‑IP）**

| | **TCP** | **UDP** |
|---|---------|---------|
| 连接 | **面向连接** | **无连接** |
| 可靠性 | **可靠**（重传、确认） | **可能丢包** |
| 顺序 | **有序** | 不保证 |
| 开销/时延 | 高 | **低时延** |
> 实时/车载场景常基于 **UDP** 或 **TCP+UDP 混合**。

### 8.3 通信中间件

- **消息队列**（Kafka / RocketMQ / MQTT Broker）、**DDS**、**SOME‑IP SD**：**屏蔽底层网络差异，提供统一通信抽象**；
- **协议转换/网关**：异构协议互通（HTTP↔MQTT、TCP↔UDP）；
- **RPC/服务调用**：**gRPC**（HTTP/2 + Protobuf，**强类型、低延迟**）vs **HTTP/REST**；**服务网格 Istio** 提供流量治理、**mTLS**、可观测；
- **QoS 保障**：**流量整形、优先级队列、拥塞控制**；**多链路冗余与故障链路切换**。

## 🎯 怎么考

| 问法 | 典型提问 |
|------|---------|
| ① 概念题 | "简述网络时延由哪几部分构成。" |
| ② 对比题 | "TCP 与 UDP 的区别及各自适用场景。" |
| ③ 拓扑题 | "比较星型与网状拓扑的优缺点并选型。" |
| ④ 中间件题 | "gRPC 与 REST 如何选型？" / "说明通信中间件的作用。" |
| ⑤ QoS 题 | "为保障实时业务质量，可采取哪些 QoS 措施？" |

## ✍️ 怎么答（模板）

**【模板 A：时延四要素（简答直接默写）】**
> 网络时延由四部分构成：
> ① **传输时延**：将数据的所有比特**推送到链路**所需时间，取决于**数据块大小与链路带宽**；
> ② **传播时延**：信号在**传输介质中传播**所需时间，取决于**传输距离与传播速率**（接近光速）；
> ③ **处理时延**：路由器/交换机**检查分组首部、查找路由表**等处理时间；
> ④ **排队时延**：分组在**输出队列等待转发**的时间，取决于**网络拥塞程度**。
> **RTT 为数据发出到收到 ACK 的往返耗时**；QoS 关键指标包括**带宽、时延、抖动（时延变化）、丢包率**。

**【模板 B：QoS 保障措施】**
> 采用**流量整形与优先级队列**保障关键业务带宽与时延；通过**拥塞控制**避免网络拥塞；部署**多链路冗余与故障链路自动切换**提升可用性；对实时业务选用 **UDP + 应用层补偿**或 **TCP+UDP 混合**传输。

## ⚠️ 丢分点

1. ❌ **传输时延和传播时延搞混（最高频）** → **传输 = 推出门（带宽）**；**传播 = 路上跑（距离）**。
2. ❌ **"抖动"答不出来** → 抖动 = **时延的变化量**（不是丢包、不是带宽）。
3. ❌ **QoS 四指标写不全** → **带宽、时延、抖动、丢包率**。
4. ❌ **UDP 说成"不可靠所以没用"** → 实时音视频/车载场景选 UDP 是因为**低时延**，可靠性由**应用层补偿**。
5. ❌ **拓扑题只说优点不说缺点** → 必须成对：**星型好管理但中心单点故障；网状可靠但成本高**。
6. ❌ **gRPC 和 REST 选型说反** → **内部服务间高性能调用选 gRPC**（HTTP/2 + Protobuf）；**对外开放、易调试选 REST**。

# 9. 区块链技术应用（2025 大纲新增）

> 对应原文第 8 章

## 🧊 直觉：村里的公共账本

想象一个村子，以前账本由**村会计一个人**记 —— 他想改就能改。

现在改成：**全村每家都发一本一模一样的账本**。

1. **去中心化**：账本不只在一处，**每家一本**；
2. **不可篡改**：每页账目末尾都**盖了上一页的"指纹"（哈希）**，形成**链条**。你想改第 100 页，那 101、102… 所有页的指纹都要重做，还得**让全村同步认可** —— 做不到；
3. **共识机制**：发生新交易时，全村要**商量一致**才记上去；
4. **智能合约**：把"**如果张三交了 100 斤粮，就自动给他 500 元**"这条规则**写成代码放到链上**，条件一到**自动执行，谁也赖不掉**。

### 联盟链 vs 公有链

| | 公有链（比特币） | **联盟链（考试重点）** |
|---|---|---|
| 谁参与 | 任何人 | **若干互相认识的机构**（银行、海关、医院） |
| 信任 | 完全不信任，靠算力和代币 | **半信任**，靠**身份认证 + 许可** |
| 速度 | 慢 | **快**（PBFT） |
| 典型平台 | Ethereum | **Hyperledger Fabric** |

> **考试 99% 考联盟链**。因为企业场景都是"**几个机构协作但彼此不完全信任**"。

### 🔥 上链 vs 链下（**最高频踩分点**）

> **错误做法**：把 100MB 的病历、视频、合同原件**全部写到链上**。
> → 链是**全网复制**的，每写 1MB 就要在几十个节点各存一份，又慢又贵，而且**隐私全泄露**。

> **正确做法**：
> - **原始数据（大数据/隐私数据）存链下**（业务数据库 / 对象存储）；
> - **把数据的哈希（指纹）+ 时间戳 + 存证编号写到链上**。
>
> 这样：链下数据被改了一点点 → 哈希对不上 → **立刻发现被篡改，且时间不可抵赖**。

## 📖 原理拆解

### 9.1 区块链五层经典架构（**必背，填空高频**）

| 层 | 内容 |
|----|------|
| 1. **数据层** | 区块、**链式结构**、哈希、**默克尔树**、非对称加密、时间戳 |
| 2. **网络层** | **P2P 对等网络**、数据传播与验证 |
| 3. **共识层** | 共识算法（**PoW / PoS / PBFT**） |
| 4. **激励层** | 代币奖励（**公有链特有**，联盟链通常没有） |
| 5. **应用层** | **智能合约、DApp** |

### 9.2 联盟链（Fabric）关键机制

**权限管理（CA 身份认证）**、**通道隔离（Channel）**、**链码/智能合约（Chaincode）**。
适用：**供应链金融、跨境支付、电子存证、政务数据共享**。

### 9.3 共识选型口诀（**送分**）

> **公链、大量匿名节点 → PoW / PoS**；
> **联盟链、许可链、企业内部多方可信节点 → PBFT**（**强一致、速度快、无挖矿**）。

### 9.4 智能合约要点

部署在链上、条件满足**自动执行**的代码（Solidity / WASM）；**部署后不可随意修改**，因此**上线前必须做形式化验证与安全审计**防漏洞。

### 9.5 适用 / 不适用（**论述题加分点**）

- ✅ **适合**：**多方不完全互信、需留痕审计防篡改** —— 供应链溯源、电子存证、跨境支付、政务数据共享；
- ❌ **不适合**：**高并发高频交易**（吞吐性能低）、**需要频繁修改数据**、**大文件存储**、**单点内部系统**（杀鸡用牛刀）。

## 🎯 怎么考

| 问法 | 典型提问 |
|------|---------|
| ① 概念题 | "简述区块链的核心特性。" / "画出/补全区块链五层架构。" |
| ② 方案设计 | "为跨机构数据共享设计区块链方案。"（**高频**） |
| ③ 共识选型 | "说明该项目应选用的共识机制及理由。" |
| ④ 上链设计 | "哪些数据上链、哪些数据链下存储？说明理由。"（**高频**） |
| ⑤ 适用性 | "区块链是否适用于该场景？说明理由。" |

## ✍️ 怎么答（模板）

**【模板：跨机构数据共享区块链方案（万能骨架）】**
> ① **链型选择**：采用**联盟链**（Hyperledger Fabric），由各参与机构共同维护，兼顾**信任与效率**；
> ② **参与方与角色**：明确各机构节点角色，通过 **CA 身份认证**实现**许可准入**；
> ③ **共识机制**：采用 **PBFT**（节点为已知可信机构，**强一致、出块快、无需挖矿**）；
> ④ **数据上链策略**：**原始数据/隐私数据链下存储**（业务库/对象存储），仅将**数据哈希、时间戳、存证编号上链**，实现**防篡改+可追溯+隐私保护**，兼顾**性能与合规**；
> ⑤ **隐私保护**：利用 **Fabric 通道（Channel）** 实现**数据隔离**，敏感交易仅在相关方之间可见；
> ⑥ **智能合约**：将共享规则、授权与结算逻辑编写为**链码**，**条件满足自动执行**；上线前进行**形式化验证与安全审计**（合约部署后不可修改）；
> ⑦ **审计追溯**：全量操作**留痕**，支持**监管审计与争议追溯**。

## ⚠️ 丢分点

1. ❌ **什么都往上链（最高频失分）** → 正确：**大数据/隐私数据链下存，哈希+凭证上链**。这条几乎是必考踩分点。
2. ❌ **共识机制选错** → **联盟链/许可链 → PBFT**；**公链匿名节点 → PoW/PoS**。别在联盟链题里答 PoW。
3. ❌ **五层架构漏"激励层"或答不出它的特性** → 激励层是**公有链特有**（代币奖励）。
4. ❌ **说"智能合约可以随时升级修改"** → **部署后不可随意修改**，所以要**形式化验证 + 安全审计**。
5. ❌ **适用性题无脑说"适合"** → 要能说出**不适合**的场景：**高并发高频交易、大文件存储、单点内部系统**。
6. ❌ **Fabric 的"通道"漏答** → 通道（Channel）= **数据隔离/隐私保护**机制，是联盟链方案题的常客。

# 10. 信创与国产化替代（极热隐藏考点）

> 对应原文第 9 章 ｜ **政务/金融核心系统改造必考，近年极热**

## 🧊 直觉：把家里的"进口货"整套换成国产

把信息系统想象成**一栋房子**，国产化替代就是**把关键部件全换成国产**：

| 部件 | 房子的什么 | 国产代表 |
|------|-----------|---------|
| **芯片** | **心脏/发电机** | 龙芯、**飞腾**、**鲲鹏**、海光 |
| **操作系统** | **大脑/管家** | **银河麒麟**、**统信 UOS**、中标麒麟 |
| **数据库** | **仓库**（放数据的） | **达梦 DM**、**人大金仓 KingbaseES**、**OceanBase**、**GaussDB** |
| **中间件** | **搬运工/管道** | **东方通**、金蝶中间件 |

> ⚠️ **新手最容易犯的错：只答"换数据库"**。
> 记住是**四类组件一起换**：**芯片 + 操作系统 + 数据库 + 中间件**。

### 四原则的直觉

1. **自主可控**：自己的命脉自己掌握，不被"卡脖子"；
2. **安全可靠**：达到**等保**要求，有加密、有权限、合规；
3. **适配兼容**：**不是推倒重来**，要能跑老业务，**平滑迁移**降成本；
4. **可扩展**：留好升级口子，以后还能加东西。

> 🔥 **第 3 条是答题高频失分点**：很多人写"全面重构"，标准答案恰恰是"**适配兼容、平滑迁移、降低改造成本**"。

## 📖 原理拆解

### 10.1 信创改造五步流程（**方案设计题抓手，按顺序默写**）

1. **需求分析**：明确**国产化替代目标、性能不降、数据安全、成本控制**；
2. **组件选型**：选用适配业务的国产化组件（**芯片 + OS + 数据库 + 中间件**）；
3. **架构设计**：**分层（表现层 / 业务层 / 数据层）+ 模块化**，**接口标准化**、组件兼容；
4. **迁移改造**：**数据迁移（全量 + 增量同步）**、**应用适配/兼容性测试**、**性能与安全测试**；
5. **运维保障**：建立**国产化组件运维体系**、**补丁/漏洞管理**、**监控告警**。

### 10.2 国产数据库迁移要点（**金融核心系统题高频**）

- **数据迁移**：**全量迁移 + 增量同步**（达梦/金仓迁移工具、KingbaseFlySync），**双轨运行**保障一致性；
- **兼容性**：优先选与原有库（如 Oracle）**兼容性好**的国产库（**达梦与 Oracle 兼容性业内领先**），**降低应用改造量**；
- **高可用**：
  - **达梦 DMDSC 共享存储集群**（**对等替换 Oracle RAC**）、数据守护/异步备库、**两地三中心**容灾；
  - **人大金仓**读写分离集群；
  - **OceanBase 多副本（Paxos）**；
- **目标**：**数据零丢失（RPO ≈ 0）**、**服务零中断/快速切换（RTO 分钟级）**。

## 🎯 怎么考

| 问法 | 典型提问 |
|------|---------|
| ① 组件题 | "列出信创国产化的四类核心组件及其代表产品。" |
| ② 原则题 | "简述信创架构设计的原则。" |
| ③ 流程题 | "给出某政务系统国产化改造的实施流程。" |
| ④ 迁移题 | "设计金融核心系统从 Oracle 迁移到国产数据库的方案。"（**高频**） |
| ⑤ 安全题 | "说明国密算法的应用场景。" |

## ✍️ 怎么答（模板）

**【模板 A：信创改造方案（万能）】**
> ① **芯片**：采用**鲲鹏/飞腾**等国产 CPU；
> ② **操作系统**：采用**银河麒麟 / 统信 UOS**；
> ③ **数据库**：采用**达梦 DM / 人大金仓 KingbaseES**（优先选与原库**兼容性好**的产品，**降低应用改造量**）；
> ④ **中间件**：采用**东方通 TongWeb** 等国产中间件；
> ⑤ **密码应用**：采用**国密算法** —— **SM2**（非对称加密与数字签名，用于**身份认证、签名验签**）、**SM3**（摘要，用于**完整性校验、防篡改**）、**SM4**（对称加密，用于**敏感字段存储加密**）；
> ⑥ **遵循四原则**：**自主可控、安全可靠、适配兼容（平滑迁移）、可扩展**；
> ⑦ **实施流程**：**需求分析 → 组件选型 → 架构设计（分层+模块化+接口标准化）→ 迁移改造（全量+增量同步、兼容性/性能/安全测试）→ 运维保障**；
> ⑧ **目标**：满足**等保与行业合规**要求，实现 **RPO ≈ 0、RTO 分钟级**。

**【模板 B：Oracle → 国产数据库迁移（高频大题）】**
> ① **选型**：选用**达梦 DM**（与 **Oracle 兼容性业内领先**，可大幅**降低应用改造量**）；
> ② **迁移**：使用迁移工具完成**全量迁移**，再通过 **KingbaseFlySync 等工具做增量同步**，期间**新旧系统双轨运行**并持续**一致性校验**，确认无误后再切换；
> ③ **高可用**：采用 **达梦 DMDSC 共享存储集群**对等替换 **Oracle RAC**，配合**数据守护/异步备库**与**两地三中心**容灾；
> ④ **验证**：开展**应用兼容性测试、性能压测、安全测试**与**回滚演练**；
> ⑤ **目标**：**RPO ≈ 0（数据零丢失）、RTO 分钟级（快速切换）**，全过程**可回退**。

## ⚠️ 丢分点

1. ❌ **只答"换数据库"** → 必须是**芯片 + OS + 数据库 + 中间件**四类，漏一类扣分。
2. ❌ **原则写成"全面重写/重构"** → 标准答案是**"适配兼容、标准化接口、平滑迁移、降低改造成本"**。
3. ❌ **迁移只说"导数据"** → 完整链条：**全量迁移 + 增量同步 + 双轨运行 + 一致性校验 + 回滚演练**。
4. ❌ **RPO/RTO 说反** → **RPO = 最多丢多少数据（目标≈0）**；**RTO = 停多久（分钟级）**。
5. ❌ **国密三个算法搞混** → **SM2 非对称签名、SM3 摘要、SM4 对称加密**。
6. ❌ **漏"等保"和"合规"** → 信创题几乎必带**合规要求**，要提**等保三级**。
7. ❌ **DMDSC 和 OceanBase 机制混** → **达梦 DMDSC = 共享存储集群（对标 Oracle RAC）**；**OceanBase = 多副本 Paxos（无共享）**。

# 11. 数据要素与数据资产（"数据二十条"导向）

> 对应原文第 10 章

## 🧊 直觉：三个生活类比

**① 数据血缘 = 食品的"溯源码"**

超市里一盒牛肉贴着二维码，扫一下能看到：**哪个养殖场 → 哪天屠宰 → 怎么运输 → 哪个货架**。
一旦出问题，能**立刻倒查到源头**，还能知道"**如果这批牛有问题，还影响了哪些产品**"。

数据血缘就是干这个的：记录数据**产生 → 加工 → 存储 → 消费**的完整流转链路。

**② 联邦学习 = 几家医院联合研究新药，但谁都不交出病人病历**

每家医院**在本地用自己的病历训练模型**，只把训练出来的"**经验（模型参数/梯度）**"交上去汇总。
**原始数据一步都没离开过医院**，但大家一起得到了一个更好的模型。
→ 这就是"**数据可用不可见**"、"**数据不出域**"。

**③ 数据资产化 = 把数据当"房子"来盘点确权**

以前数据就是"副产品"，现在要像盘点固定资产一样：**盘点（有哪些数据）→ 确权（归谁）→ 估值（值多少钱）→ 运营（怎么产生收益）**。

## 📖 原理拆解

### 11.1 数据治理体系（**五大块**）

**数据标准、数据质量、元数据管理、主数据管理（MDM）、数据资产管理**。
- **数据质量四性**：**完整性、一致性、准确性、及时性**。

### 11.2 数据血缘（**三个用途必写**）

记录数据从源头到消费的**完整流转链路**（产生 → 加工 → 存储 → 消费），用于：
① **影响分析**（改了这个字段会影响哪些下游报表）；
② **问题溯源**（数据错了，倒查是哪一步出的错）；
③ **合规审计**（证明数据来源与加工过程合规）。
> **实现**：通过**元数据平台/数据治理工具自动采集**血缘关系。

### 11.3 隐私计算

- **联邦学习**：各参与方**本地训练模型**，**仅交换模型参数/梯度**，**原始数据不出域**，实现"**数据可用不可见**"；
- 适用：**跨机构数据协作**（金融风控、医疗联合建模）且**数据隐私要求高**的场景。

### 11.4 数据资产化

将数据视为企业资产进行**盘点、确权、估值、运营**；**数据中台 / 数据湖**是数据资产化的常见载体。

## 🎯 怎么考

| 问法 | 典型提问 |
|------|---------|
| ① 概念题 | "什么是数据血缘？它有什么作用？" |
| ② 方案题 | "多家医院需联合建模但不能共享原始数据，请设计方案。" |
| ③ 论述题 | "结合'数据二十条'，论述企业数据治理与数据资产化的建设思路。" |
| ④ 对比题 | "数据湖与数据仓库的区别。" |

## ✍️ 怎么答（模板）

**【模板 A：数据血缘（简答）】**
> **数据血缘**是记录数据从**源头到消费的完整流转链路**（**产生 → 加工 → 存储 → 消费**）的元信息。
> 作用：① **影响分析** —— 评估上游变更对下游的影响范围；② **问题溯源** —— 数据异常时快速定位到出问题的加工环节；③ **合规审计** —— 证明数据来源与加工过程合法合规。
> **实现**：通过**元数据平台/数据治理工具**自动采集与可视化血缘关系。

**【模板 B：跨机构数据协作（联邦学习）】**
> 采用**联邦学习**架构：各参与方在**本地利用自有数据训练模型**，仅将**模型参数/梯度**上传至协调节点进行**安全聚合**，**原始数据不出本地域**，实现"**数据可用不可见、数据不动模型动**"；聚合后的全局模型再下发各参与方迭代。该方案满足**数据安全与隐私保护合规要求**（如《数据安全法》《个人信息保护法》），适用于**金融联合风控、医疗联合建模**等场景。

## ⚠️ 丢分点

1. ❌ **联邦学习答成"把数据集中起来训练"** → 核心是**数据不出域，只交换参数/梯度**。
2. ❌ **数据血缘只答"溯源"一条** → 三个用途：**影响分析 + 问题溯源 + 合规审计**。
3. ❌ **数据质量四性写不全** → **完整性、一致性、准确性、及时性**。
4. ❌ **数据治理答成"数据库管理"** → 治理管的是**标准、质量、元数据、主数据、资产**，不是"建库建表"。
5. ❌ **数据湖与数据仓库的区别说反** → **数仓 = 结构化、已建模、Schema‑on‑Write**；**数据湖 = 原始多类型、Schema‑on‑Read**。

# 12. 可靠性设计（串并联可靠度）

> 对应原文第 11 章 ｜ **本模块唯一的"计算点"，公式很少，务必拿下**

## 🧊 直觉：圣诞灯串 vs 多根吊绳

**串联 = 老式圣诞彩灯**
一串灯，只要**有一个**坏了 —— **整串全灭**。
> 所以：**东西越多越不可靠**。这就解释了为什么是**乘法**（每个都小于 1，乘起来越来越小）。

**并联 = 用多根绳子吊一盏灯**
只要**还有一根**没断 —— 灯就掉不下来。**必须全都断**才出事。
> 所以：**东西越多越可靠**。这就解释了为什么是"**用 1 减去全坏的概率**"。

```
串联：R = R₁ × R₂ × … × Rₙ        （只要一个坏 → 全挂）
并联：R = 1 − (1−R₁)(1−R₂)…(1−Rₙ) （必须全坏  → 才挂）
```

### 举个算例（**考试就这么算**）

> 系统由 **A、B 两个部件并联**（各 R=0.9），再与 **C 串联**（R=0.99）。求系统可靠度。

```
第一步：先算并联块     R_AB = 1 − (1−0.9)(1−0.9) = 1 − 0.01 = 0.99
第二步：再按串联相乘   R    = R_AB × R_C = 0.99 × 0.99 = 0.9801
```

> ⚠️ **混合系统的铁律**：**先算并联块，把每个并联块当成一个"大部件"，再整体串联相乘**。

## 📖 原理拆解

### 12.1 可靠性指标（**三个词别搞混**）

| 指标 | 含义 | 记忆 |
|------|------|------|
| **可靠度 R(t)** | 系统在**规定时间内正常工作的概率** | "**一段时间不出事的概率**" |
| **MTBF** | **平均无故障时间**（平均能正常跑多久） | "**能跑多久**" —— 越长越好 |
| **MTTR** | **平均修复时间**（坏了平均多久修好） | "**修多久**" —— 越短越好 |

> **可用性 A ≈ MTBF / (MTBF + MTTR)**
> （⚠️ **可用性和可靠度不是一回事**：可靠度关注"**某段时间内不失效**"，可用性关注"**任意时刻能用的比例**"，可用性**把修复能力也算进去了**。所以"修得快"能提升可用性但不能提升可靠度。）

### 12.2 容错与可靠设计技术（**四条，简答常考**）

| 技术 | 做法 | 关键词 |
|------|------|--------|
| **冗余** | 硬件冗余（多副本）、软件冗余、**信息冗余（校验码）** | 多备一份 |
| **N 版本程序设计** | **独立编写 N 个功能等价版本**，**多数表决**输出 | 抵御**软件设计缺陷** |
| **恢复块** | **主模块 + 后备模块**，主模块失败则切换后备 | **主备切换** |
| **故障检测** | **心跳检测、超时探测、看门狗、BIT（内置自测）** | 及时发现 |

> 💡 **N 版本 vs 恢复块 的区别（易混）**：
> **N 版本 = N 个都跑，投票取多数（并行表决）**；
> **恢复块 = 先跑主模块，失败才切后备（串行切换）**。

## 🎯 怎么考

| 问法 | 典型提问 |
|------|---------|
| ① **计算题** | "已知各部件可靠度，求系统可靠度。"（串/并/混合） |
| ② 概念题 | "说明 MTBF、MTTR 与可用性的关系。" |
| ③ 容错题 | "说明 N 版本程序设计与恢复块的区别。" |
| ④ 措施题 | "给出 4 项提升系统可靠性的措施。" |

> 🧮 更深入的可靠度计算（TMR、马尔可夫模型、可用度综合计算）见 `06b-计算题专项（可靠性与可用性）.md`。

## ✍️ 怎么答（模板）

**【模板：可靠性设计措施（8 分写 4~5 条）】**
> ① **冗余设计**：关键部件**硬件冗余**（双机热备/多副本），**信息冗余**（校验码、CRC）；
> ② **软件容错**：关键功能采用 **N 版本程序设计**（多版本独立实现 + 多数表决），一般功能采用**恢复块**（主模块 + 后备模块切换）；
> ③ **故障检测**：部署**心跳检测、超时探测、看门狗、BIT 内置自测**，做到**故障早发现**；
> ④ **故障恢复**：**自动切换/故障转移**、**快速回滚**、**定期备份与恢复演练**；
> ⑤ **架构层面**：**冗余节点 + 负载均衡 + 熔断降级**，并进行**可靠性指标（MTBF/MTTR）度量与持续改进**。

## ⚠️ 丢分点

1. ❌ **串并联公式写反（最高频）** → **串联相乘（越串越差）**；**并联 1−连乘（越并越好）**。
2. ❌ **混合系统顺序错** → **先算并联块，再整体串联相乘**。
3. ❌ **MTBF 和 MTTR 说反** → **MTBF 是"能跑多久"（无故障）**；**MTTR 是"修多久"**。
4. ❌ **可靠度和可用性混为一谈** → 可用性 **= MTBF/(MTBF+MTTR)**，**把修复能力算进去了**；可靠度只看**不失效**。
5. ❌ **N 版本和恢复块混** → **N 版本 = 并行跑+投票**；**恢复块 = 串行主备切换**。
6. ❌ **N 版本程序设计的目的答成"提高性能"** → 它的目的是**抵御软件设计缺陷（共因失效）**，靠**独立性 + 多数表决**。
7. ❌ **计算题不写过程** → 计算题**分步写**，即使结果算错，**公式和中间步骤也有分**。

# 13. 架构演化（遗留系统改造三模式）

> 对应原文第 12 章

## 🧊 直觉：三个比喻（**背下这三个比喻就不会混**）

| 模式 | 比喻 | 从哪下手 |
|------|------|---------|
| **绞杀者 Strangler Fig** | **爬山虎缠树** —— 新藤一点点长，最后把老树完全包住取代它 | **从外面围攻**：新功能走新系统，逐步把老系统的流量"抢"过来 |
| **防腐层 ACL** | **海关检疫 / 翻译官** —— 外面的东西进来前先消毒翻译，脏东西不许进 | **在边界设卡**：隔离遗留系统的"脏模型"，防止污染新系统 |
| **抽象分支 Branch by Abstraction** | **装修先装总闸门** —— 新旧水管都接到闸门上，哪天切哪根都行 | **从内部改造**：先抽抽象接口，再逐步替换底层实现 |

```
【绞杀者】                       【防腐层】                    【抽象分支】
新系统逐渐长大 ──→ 老系统被掏空    新系统 ←[ACL 翻译]← 老系统      调用方 →[抽象接口]→ 旧实现/新实现
（流量拦截）                      （模型隔离）                    （内部替换，可并行运行）
```

## 📖 原理拆解

| 模式 | 核心含义 | 适用场景 | 关键词 |
|------|---------|---------|--------|
| **绞杀者模式** | 在遗留系统**外围逐步构建**新功能/服务，新需求走新系统，旧系统逐渐被"绞杀"替换 | **整体渐进替换，保业务连续** | **增量迁移**、降低一次性重写风险 |
| **防腐层 ACL** | 在新旧系统之间引入**适配层**，**隔离遗留模型的污染**，将遗留接口**翻译**为新模型 | **新旧模型语义不一致、需隔离** | **隔离**、**翻译**、DDD 配套 |
| **抽象分支** | 引入**抽象接口**，先把调用方切到抽象层，再**逐步替换底层实现** | **单体内部组件逐步替换** | **平滑迁移、并行运行** |

> 🎯 **区分口诀（背死）**：
> **流量拦截选绞杀者；新旧模型隔离选防腐层；单体内部组件逐步替换选抽象分支。**
>
> 💡 三者**不是互斥**的，实际改造中**常配合使用**（绞杀者负责整体节奏，防腐层负责边界隔离，抽象分支负责内部组件替换）。

## 🎯 怎么考

| 问法 | 典型提问 |
|------|---------|
| ① 概念题 | "简述绞杀者模式/防腐层/抽象分支的含义与适用场景。" |
| ② 方案题 | "某银行核心系统运行 20 年，请设计演进方案。"（**高频**） |
| ③ 对比题 | "比较三种遗留系统演化模式的区别与适用场景。" |

## ✍️ 怎么答（模板）

**【模板：遗留系统渐进演化方案（推荐渐进式）】**
> ① **推荐渐进式（绞杀者模式）**：在遗留系统外围**逐步构建新服务**，新需求优先走新系统，**逐步拦截并迁移流量**，最终替换老系统；
> ② **边界隔离（防腐层）**：在新旧系统之间引入**防腐层（ACL）**，**将遗留系统的接口与数据模型翻译为新模型**，**防止遗留脏模型污染新领域模型**；
> ③ **内部替换（抽象分支）**：对单体内部的组件，先**抽取抽象接口**，将调用方切换到抽象层，再**逐个用新实现替换旧实现**，支持**新旧并存、并行运行、随时回退**；
> ④ **数据迁移**：采用 **双写 → 对账 → 切读（再停旧写）** 三阶段，保证**数据零丢失、业务不停机、每步可回退**；
> ⑤ **配套保障**：**灰度/金丝雀发布**逐步切流，**可观测性**（日志/指标/链路）与**回滚预案**。
> **理由**：从**风险、成本、业务连续性**三维度看，渐进式**风险最低、业务不中断、每步可回退**，优于"一刀切重写"。

## ⚠️ 丢分点

1. ❌ **三个模式混用（最高频）** → **绞杀者 = 拦流量（从外）**；**防腐层 = 隔离模型（边界）**；**抽象分支 = 内部换组件（从内）**。
2. ❌ **只答一种模式** → 完整方案题应**三者配合**作答，体现"整体 + 边界 + 内部"三个层面。
3. ❌ **漏"每步可回退/业务不中断"** → 这是渐进式相对"一刀切重写"的**核心优势**，必须点明。
4. ❌ **数据迁移三阶段顺序写错** → **双写 → 对账 → 切读（再停旧写）**。
5. ❌ **防腐层说成"防火墙/网关"** → 它是**架构层的模型翻译与隔离层**（DDD 概念），不是网络安全设备。

# 14. 架构评估专题（ATAM 四"点"）

> 对应原文第 14 章 ｜ **与系统计划捆绑出题，也是试题一（必答题）的核心**

## 🧊 直觉：调音台上的旋钮

把架构设计想象成一个**调音台**，上面有一堆旋钮（架构决策/参数），每个旋钮会影响声音效果（质量属性）。

| 概念 | 调音台类比 | 一句话 |
|------|-----------|--------|
| **敏感点 Sensitivity** | **"这个旋钮特别灵"** —— 轻轻一拧，高音立刻明显变化 | 某个**组件/参数的单一属性变化**，会**显著影响某一质量属性** |
| **权衡点 Trade‑off** | **"这个旋钮左右为难"** —— 往左拧高音好但低音差，往右反之 | 某属性**变好必然导致另一属性变差**，**需要取舍**；**同时影响多个质量属性** |
| **风险点 Risk** | **"这么调可能翻车"** —— 当前设计下，某质量目标**可能达不到** | 架构设计中**可能造成质量目标无法达成**的**潜在隐患** |
| **非风险点 Non‑Risk** | **"这么调没问题"** —— 当前设计对该目标**有正面保障** | 当前设计**无隐患**，对质量目标**有保障** |

> 🔥 **最重要的一条关系（拉开差距的加分点）**：
> **"权衡点 = 多个敏感点的交集。"**
> 一个旋钮如果只影响一个质量属性 → 它是**敏感点**；
> 如果它**同时**是多个质量属性的敏感点，而且**效果相反** → 它就是**权衡点**。
> **所以：权衡点一定是敏感点，但敏感点不一定是权衡点。**

**典型权衡对**：**性能 ↔ 安全性**（加密越严越慢）、**性能 ↔ 可修改性**（抽象层越多越慢）、**可用性 ↔ 安全性**、**成本 ↔ 可用性**。

## 📖 原理拆解

### 14.1 ATAM 五个步骤（**简答/填空**）

1. **描述架构**（呈现架构视图与关键决策）；
2. **确定质量属性目标**（性能 / 可用性 / 安全性 / 可修改性等）；
3. **生成/识别架构方案**（含备选）；
4. **识别风险点、非风险点、敏感点、权衡点**；
5. **基于场景评估方案，做出取舍决策**。

### 14.2 四"点"标准定义（**必背**）

- **风险点**：架构设计中**可能造成质量目标无法达成**的**潜在隐患**；
- **非风险点**：当前设计对质量目标**有正面保障、无隐患**；
- **敏感点**：某个**组件/参数的单一属性变化**会**显著影响某一质量属性**；
- **权衡点**：某属性**变好必然导致另一属性变差**，**需要取舍**。

## 🎯 怎么考

| 问法 | 典型提问 |
|------|---------|
| ① 概念题 | "什么是敏感点、权衡点、风险点、非风险点？" |
| ② 判断题 | "判断下列属于敏感点还是权衡点，并说明理由。"（**高频**） |
| ③ 步骤题 | "简述 ATAM 的实施步骤。" |
| ④ 场景题 | "给出某系统的架构决策，识别其中的风险点与权衡点。" |

## ✍️ 怎么答（模板）

**【模板：四"点"判断（万能判据）】**
> - **只影响一个质量属性** → **敏感点**；
> - **同时影响两个及以上质量属性，且此消彼长** → **权衡点**（= 多个敏感点的交集）；
> - **当前设计下该质量目标可能达不到** → **风险点**；
> - **当前设计对该目标有正面保障、无隐患** → **非风险点**。
>
> **答题示例**："采用全链路 HTTPS + 字段级加密" —— 它**显著提升安全性**（安全属性的**敏感点**），但**加解密带来额外时延、降低性能**（性能属性的敏感点），**安全性提升以性能下降为代价**，因此它同时是一个**权衡点**。

## ⚠️ 丢分点

1. ❌ **敏感点和权衡点分不清（最高频）** → **一个属性 = 敏感点；多个属性此消彼长 = 权衡点**。
2. ❌ **答不出"权衡点是多个敏感点的交集"** → 这句话是**拉开差距的关键表述**，务必写上。
3. ❌ **风险点答成"已经发生的问题"** → 风险点是"**潜在的、可能造成目标无法达成**"的隐患，**还没发生**。
4. ❌ **ATAM 步骤漏"基于场景评估"** → 第 5 步的关键词是**"基于场景"**（场景驱动是 ATAM 的灵魂）。
5. ❌ **把"非风险点"答成"没有风险的系统"** → 它是针对**某个具体质量目标**而言的"当前设计无隐患"，**不是全局无风险**。

## 📝 模拟题一：城市交通大数据平台（Lambda / Kappa）

**【背景】**
某城市交通管理平台需同时支撑两类查询：
- ① **历史车辆通行精确统计报表**（日/小时级产出），要求**数据绝对准确**，历史数据**不可变存储**；
- ② **道路车流实时拥堵指数**（**秒级刷新**）。
初期采用纯离线批处理方案，报表准确但**延迟达 4 小时**，无法展示实时路况。

**【问题 1】（8 分）** 请简述 Lambda 架构三层的名称与职责。

**【问题 2】（9 分）** 现有如下技术组件：Flume、Kafka、HDFS、HBase、Spark、MapReduce、Flink、MemSQL、Nginx。请将它们填入"素材采集层 / 数据存储层 / 业务逻辑层（批处理层 + 速度层）/ 服务层 / 接入层"中。

**【问题 3】（8 分）** 系统上线后出现"实时拥堵指数与历史报表结果不一致"，请分析根因；若迁移到 Kappa 架构，请说明核心思想及仍面临的两项挑战。

---

### ✅ 参考答案

**【问题 1】**
- **批处理层**：保存全部**不可变的原始历史数据集**，离线计算生成**批处理视图**，结果**精确**但**延迟高**；技术：MapReduce、Spark。
- **速度层**：处理**实时增量流数据**，生成**实时视图**，**填补批处理结果的时间缺口**；结果**允许近似**，后续**被批结果修正**；技术：Flink、Spark Streaming。
- **服务层**：**合并**批处理视图与实时视图，对外提供**统一查询**；技术：HBase、MemSQL、Druid。

**【问题 2】**
- **素材采集层**：**Flume**、**Kafka**；
- **数据存储层**：**HDFS**、**HBase**；
- **业务逻辑层—批处理层**：**MapReduce**、**Spark**；**—速度层**：**Flink**；
- **服务层**：**HBase**、**MemSQL**；
- **接入/前端**：**Nginx**。

**【问题 3】**
- **根因**：业务统计逻辑分别在**流处理代码与批处理代码中独立实现**，两份程序逻辑难以完全一致，导致指标偏差。
- **Kappa 核心思想**：**取消独立的批处理层**，所有数据处理统一基于**流计算引擎**；**全部原始数据持久化保存在消息队列（Kafka）**中；通过**重放历史数据流**完成离线重算，实现**流批一体、一套代码**。
- **两项挑战**：① **Kafka 需长期保存海量历史数据流，存储压力大**；② **回放海量历史数据重算消耗大量集群算力**；③（补充）对**流处理引擎性能与稳定性要求极高**。

## 📝 模拟题二：智能网联汽车与机器人（嵌入式）

**【背景】**
某公司研发智能网联汽车与配套的智能巡检机器人。汽车内部有 **80 余个 ECU**，需实现**面向服务的通信**（如"查询当前车速""订阅车门状态变化"），并能**动态发现新接入的服务**；机器人的**激光雷达、摄像头数据需在多个计算单元之间高速分发**，且对**时延和可靠性有严格约定**；机器人还需执行"**从 A 点自主导航到 B 点**"这类**长时间任务，期间需持续反馈进度并可中途取消**。

**【问题 1】（9 分）** 请分析 **SOME/IP** 协议及其特点，并说明它适用于本案例哪个部分。

**【问题 2】（8 分）** 机器人的传感器数据分发应采用什么协议？说明其特点与理由。

**【问题 3】（8 分）** 机器人采用 ROS2 开发。请说明 ROS2 相比 ROS1 的五点改进；并指出"从 A 点导航到 B 点、需持续反馈进度且可取消"应使用 ROS 的哪种通信方式，说明理由。

---

### ✅ 参考答案

**【问题 1】**
**SOME/IP**（Scalable service‑Oriented MiddlewarE over IP）是 **AUTOSAR 发布的面向汽车以太网的可扩展面向服务 IP 中间件**。
**特点**：①采用**服务导向架构（SOA）**；②支持**远程过程调用（RPC）**；③**轻量级**，适合资源受限环境；④支持多种通信方式（**请求/响应、事件通知、发布/订阅**）；⑤**二进制编码**高效，支持 **TCP/UDP**；⑥支持**动态服务发现（SOME/IP SD）**。
**适用**：本案例中**汽车 80 余个 ECU 之间的面向服务通信**（查询车速为请求/响应、订阅车门状态为事件通知、动态发现新服务为 SOME/IP SD），以及**智能网联汽车/自动驾驶**场景。

**【问题 2】**
应采用 **DDS（Data Distribution Service）**。
**特点**：**高实时性**；提供丰富的 **QoS 控制**（**可靠性、时延、带宽**等策略可配）；**去中心化发现**；基于**发布/订阅**。
**理由**：机器人激光雷达/摄像头数据需在**多个计算单元之间高速、持续分发**，且对**时延与可靠性有明确约定**，恰需 DDS 的**实时数据分发 + QoS 保障**能力。
（对比：SOME/IP 面向**车载 SOA 的服务调用**，不适合这种高频数据分发场景。）

**【问题 3】**
**ROS2 五点改进**：① **通信机制升级** —— 由 ROS1 的 TCPROS/UDPROS 改为 **DDS**，支持更高效分布式通信；② **跨平台增强** —— 支持 Linux/Windows/Mac/**RTOS**；③ **实时性提升** —— DDS 提供 **QoS 控制**，适用于时延敏感实时系统；④ **安全性提升** —— 提供**身份验证、加密通信**；⑤ **生命周期管理** —— 引入**节点生命周期**（启动/挂起/恢复）。
**通信方式**：应使用 **动作（Action）**。
**理由**：Action 专为**长时间运行的任务**设计，支持**异步执行、持续反馈中间进度、可中途取消**；而**服务（Service）**仅适用于**请求/响应式的短任务**，**话题（Topic）**是单向异步的数据流广播，均不满足"长任务 + 进度反馈 + 可取消"的需求。

## 📝 模拟题三：政务大模型知识问答平台（AI + 安全 + 信创）

**【背景】**
某市政务服务中心拟建设**智能问答平台**，基于大模型为企业和市民提供政策咨询服务。需求如下：
- 政策文件**更新频繁**（每周数十份新文件），回答**必须准确无误并可标注出处**，**不允许编造**；
- 高峰并发 **2000 QPS**，要求 **P99 延迟 ≤ 500ms**；
- 涉及**市民身份信息**，需**满足等保三级**与**自主可控**要求；
- 需控制**推理成本**；
- 平台支持用户**提交自定义问答流程脚本**，由平台**解析后调度执行**。

**【问题 1】（9 分）** 为解决"回答准确、可标注出处、不允许编造"的问题，应采用什么架构？说明其流程与解决的问题。

**【问题 2】（8 分）** 针对"P99 ≤ 500ms、2000 QPS、控制成本"的需求，请给出推理侧的优化措施。

**【问题 3】（8 分）** 针对"等保三级 + 自主可控"要求，请给出安全与信创设计方案。

---

### ✅ 参考答案

**【问题 1】**
应采用 **RAG（检索增强生成）架构**。
**流程**：用户 **Query → 向量化 → 向量数据库检索召回相关政策片段 → 将召回上下文拼入 Prompt → 大模型基于上下文生成答案 → 输出答案并标注引用出处**。
**解决的问题**：① **幻觉** —— 答案基于检索到的真实政策文本生成，避免大模型编造；② **知识时效性** —— 政策更新时**只需更新知识库（向量库），无需重新训练模型**，适应"每周数十份新文件"的高频更新；③ **可追溯** —— 可**标注引用出处**，便于用户核对与合规审计。
（补充：政策更新频繁、要求引用出处 → **选 RAG 而非微调**；微调适用于风格/格式固定的任务，且无法解决知识时效性问题。）

**【问题 2】**
① **推理加速**：采用 **PagedAttention（vLLM）** 分页复用 **KV Cache**，提升显存利用率与吞吐；采用 **算子融合（TensorRT）**；采用**投机采样**（小模型打草稿 + 大模型批量验证）降低生成时延；
② **模型压缩**：采用 **INT8/INT4 量化**与**模型蒸馏**，降低显存与算力消耗；
③ **弹性伸缩**：基于 **GPU 利用率 / 请求队列长度的 HPA** 自动扩缩容，配合 **Spot 实例**混合部署降低成本；
④ **成本控制**：**模型路由**（简单问题路由到小模型）、**语义缓存**（相似请求直接复用结果）、**离线批量推理**处理非实时任务；
⑤ **可观测**：建设 **Token 消耗监控、链路追踪、幻觉检测**，持续度量 **P99 延迟**并优化。

**【问题 3】**
**安全方面**：
① **身份认证**：**OAuth2/OIDC + JWT** 统一认证，敏感操作**多因素认证**；
② **访问控制**：基础用 **RBAC**，涉隐私操作**叠加 ABAC**（基于用户/资源/环境属性动态决策），遵循**最小权限原则**；
③ **数据保护**：市民身份信息**脱敏**（测试/分析环境）与**加密存储**；
④ **密码应用（国密）**：**SM2**（非对称加密与签名，用于**身份认证、签名验签**）、**SM3**（摘要，用于**完整性校验、防篡改**）、**SM4**（对称加密，用于**敏感字段加密存储**）；
⑤ **合规**：按**等保三级**建设，落实**安全物理环境、通信网络、区域边界、计算环境**防护与**安全管理中心**；引入**零信任**实现**微隔离与持续验证**；全量**审计日志**与 **IDS/IPS**。
⑥ **AI 特有**：部署 **Guardrails 安全护栏**，防止**敏感信息泄露与越权访问**。

**信创方面**：
① **芯片**：鲲鹏/飞腾；② **操作系统**：银河麒麟/统信 UOS；③ **数据库**：达梦 DM / 人大金仓 KingbaseES；④ **中间件**：东方通 TongWeb；
⑤ **遵循四原则**：**自主可控、安全可靠、适配兼容（平滑迁移）、可扩展**；
⑥ **实施流程**：**需求分析 → 组件选型 → 架构设计（分层 + 模块化 + 接口标准化）→ 迁移改造（全量 + 增量同步、兼容性/性能/安全测试）→ 运维保障**；
⑦ **目标**：满足**等保三级与自主可控合规要求**，**RPO ≈ 0、RTO 分钟级**。

```
【流处理三概念】Watermark(乱序/迟到/窗口触发) · Exactly-Once(Checkpoint+两阶段提交/幂等) · CDC(Binlog)

【嵌入式】特征：资源受限·实时性高·可靠安全·专用性强
  硬实时(飞控/机械臂/生命设备·超时=灾难) vs 软实时(直播/语音·体验差)
  RM周期短优先(静态,上界≈69%) | EDF截止早优先(动态,可达100%)
  SOME/IP六特点：SOA·RPC·轻量·多通信方式(请求响应/事件/发布订阅)·二进制+TCP/UDP·动态服务发现SD
  DDS三特点：高实时·QoS·去中心化发布订阅
  ROS2五改进：DDS通信·跨平台·QoS·安全(认证加密)·生命周期
  ROS四通信：话题(广播/传感器) · 服务(问一句答一句/单次) · 动作(长任务/有进度/可取消) · 参数(全局旋钮)

【边缘计算四价值】低时延 · 省带宽 · 隐私保护 · 离线可用（边管快，云管大，边云协同）

【AI】训练(吞吐/互联带宽/RDMA) vs 推理(延迟/成本/量化·PagedAttention)
  解释器风格：用户代码 → 解析器 → 执行引擎 → 资源调度器 → 硬件平台
  RAG：Query → 向量检索 → 召回上下文 → 大模型生成 → 带引用（治幻觉·治时效·可追溯；≠微调）
  Agent：感知 → 规划(ReAct/CoT) → 行动(工具) → 记忆 → 反思
  加速降本：PagedAttention(KV Cache分页) · 算子融合 · 投机采样 · INT8/INT4量化 · 蒸馏
            · HPA(GPU利用率/队列长度) · Spot实例 · 模型路由 · 语义缓存 · 离线批量
  安全可观测：Guardrails护栏 · 数据脱敏 · Token监控 · 链路追踪 · 幻觉检测
  AI 集群网络：RDMA/RoCE(绕CPU) · ECMP(易哈希不均) → 包喷洒 · APSCC拥塞控制 · 故障恢复≤5min

【安全】零信任五能力：认证·设备合规·最小权限·微隔离·持续监测（永不信任，始终验证）
  授权：RBAC(你是谁/角色) · ABAC(什么条件/属性+策略·细粒度动态) · ReBAC(你跟谁有关系)
  国密：SM2非对称+签名(替RSA) · SM3摘要(替MD5/SHA) · SM4对称(替AES)
  等保2.0：五级，政务/金融核心常三级；一个中心三重防护
  脱敏：变形遮蔽·保留可用性·用于测试/分析环境（≠加密）

【系统计划】四维度：技术·经济(ROI/TCO/回收期)·操作运行·法律合规
  论证六维度：功能满足度·性能·成本·风险·可扩展性·合规性 → 必须给推荐结论
  风险三识别：技术·人员·进度 → 逐条给缓解措施

【通信】时延四要素：传输(数据/带宽·推出门) · 传播(距离/光速·路上跑) · 处理 · 排队(拥塞)
  RTT=往返 | QoS四指标：带宽·时延·抖动(时延变化)·丢包率
  拓扑：星型(好管·中心单点故障) vs 网状(可靠·成本高)
  gRPC(HTTP/2+Protobuf·内部高性能) vs REST(对外开放·易调试)

【区块链】五层：数据层(区块/哈希链/默克尔树) · 网络层(P2P) · 共识层(PoW/PoS/PBFT)
                · 激励层(公有链特有·代币) · 应用层(智能合约/DApp)
  四特性：去中心化·不可篡改·共识机制·智能合约
  上链策略：数据链下存 · 哈希+时间戳+存证编号上链（★高频）
  共识：联盟链/许可链 → PBFT(强一致·快) | 公链匿名 → PoW/PoS
  Fabric：CA认证 · 通道Channel(数据隔离) · 链码Chaincode · 合约部署后不可改→形式化验证+审计
  不适用：高并发高频交易·大文件存储·单点内部系统

【信创】四类组件：芯片(龙芯/飞腾/鲲鹏/海光) · OS(麒麟/统信UOS) · 数据库(达梦/人大金仓/OceanBase/GaussDB)
                  · 中间件(东方通/金蝶)
  四原则：自主可控 · 安全可靠 · 适配兼容(平滑迁移) · 可扩展
  五流程：需求分析 → 组件选型 → 架构设计(分层+模块化+接口标准化) → 迁移改造(全量+增量·兼容性/性能/安全测试) → 运维保障
  迁移：达梦与Oracle兼容性领先 · DMDSC共享存储集群(对等替换RAC) · OceanBase多副本Paxos
        · 双轨运行+一致性校验 · RPO≈0 · RTO分钟级

【数据要素】治理：标准·质量(完整/一致/准确/及时)·元数据·主数据MDM·数据资产
  血缘(产生→加工→存储→消费)：影响分析 + 问题溯源 + 合规审计
  联邦学习：本地训练·只交换参数/梯度·数据不出域（数据可用不可见）

【可靠性】串联 R=连乘(越串越差) | 并联 R=1−连乘(越并越好) | 混合：先算并联块再串联
  MTBF(能跑多久) · MTTR(修多久) · 可用性=MTBF/(MTBF+MTTR)
  容错：冗余(硬件/信息校验码) · N版本(并行跑+多数表决·御设计缺陷) · 恢复块(主失败切备·串行)
        · 故障检测(心跳·超时·看门狗·BIT)

【架构演化】绞杀者(爬山虎·从外拦流量) | 防腐层(海关检疫·边界隔离脏模型) | 抽象分支(装总闸·内部换组件)
  数据迁移：双写 → 对账 → 切读(再停旧写) | 灰度发布 | 每步可回退

【ATAM】敏感点(一属性显著受影响) | 权衡点(多属性此消彼长 = 多个敏感点交集) | 风险点(潜在隐患) | 非风险点(有保障)
  五步骤：描述架构 → 定质量目标 → 生成方案 → 识别四点 → 基于场景评估取舍
```

# 18. 考场选做题决策 + 学习建议

## 18.1 考场选做顺序（**原文第 15 章，非常重要**）

```
第 1 优先：分布式 / 微服务 / 云原生大题   —— 题目常规、套路稳定
    ↓ 偏难
第 2 优先：大数据（Lambda / Kappa）       —— 结构化强、模板清晰（本模块性价比最高）
    ↓ 仍偏难
第 3 优先：熟悉的专项赛道                  —— 嵌入式 / IoT / AI / 通信 / 区块链 / 信创
```

**3 分钟选题判据**：能否**写出 3 个小问**？能否**分条**？是否**完全陌生只能靠猜**？
→ **不选完全陌生的题**，选能写满、能分点、能结合案例的题。

## 18.2 各赛道选题抓手（**看到这些词就选它**）

| 赛道 | 抓手关键词 |
|------|-----------|
| **大数据** | "实时 + 历史双需求" → Lambda / Kappa |
| **嵌入式 / 通信** | 有硬件/汽车/工业背景，抓 **SOME/IP、DDS、RM/EDF** |
| **AI 工程** | 出现 **RAG / Agent / 训练推理分离 / MLOps** 直接套模板 |
| **区块链** | **多方协作、防篡改、存证溯源** → 联盟链（Fabric + PBFT） |
| **信创 / 安全** | **自主可控、等保、国密、国产替代** → 信创四原则 + 国密 |

## 18.3 学习建议

| 目标 | 建议动作 |
