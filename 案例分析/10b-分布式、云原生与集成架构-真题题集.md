### 真题 1 · 基于微服务架构的统一网关与权限控制设计（高仿/模拟真题）
**背景**：企业协同办公系统（Spring Cloud + K8s），多服务暴露独立端口、各自认证、高频接口瓶颈、配置变更需重启、无统一日志链路。
**考查问题**：
1. 微服务引入 API 网关的目的与核心功能
2. 设计统一身份认证与权限控制机制（多服务共享认证）
3. 高频接口（文件上传/下载）的网关高可用与性能优化
4. 引入配置中心保障灵活配置与安全
5. 基于 API 网关的综合安全治理方案
**考点**：API 网关功能清单、OAuth2/JWT + RBAC/ABAC、网关限流/CDN/分片上传、Nacos/Apollo 配置中心、安全治理（认证/权限/限流/审计/加密）。

### 真题 2 · 大型制造企业 ESB + API 网关集成（信息孤岛治理）
**背景**：20+ 独立系统（ERP/CRM/MES/WMS），点对点集成形成 190 条链路，数据不一致。
**考查问题**：分析"信息孤岛/点对点混乱/数据不一致"根因；设计 ESB + API 网关分层集成方案（数据/应用/业务/界面四层）；从数据架构解决信息孤岛。
**考点**：ESB 功能与解耦价值、集成层次与技术选型、主数据管理/数据中台/ETL+数据湖。

### 真题 3 · 银行核心系统"单元化 + 分布式"架构（2025 上半年真题方向）
**背景**：城商行核心系统，每单元承担 200 万账户，单元内账户/交易/支付三微服务，MySQL Group Replication 三节点（RPO=0）。跨单元转账平均 2.5s（单单元 200ms）。
**考查问题**：
1. 分析跨单元转账耗时高的根因（≥3 点）
2. 设计"账户归属单元"与"事务一致性"平衡的优化方案（不改 RPO），给时序
**参考答案要点**：
- **根因**：①跨单元两阶段提交（XA prepare/commit 网络 RTT 翻倍）；②单元间公网 SSL 加密 RTT 放大（20ms→80ms）；③热点账户行锁竞争，跨单元无法用本地 MVCC；④幂等检查在 DB 层增加 SELECT。
- **优化（Saga 事务 + 异地单元记账 + 日终清算）**：发起方本地扣减并插"转出事件表(INIT)"→ 发 Kafka → 接收方本地增加并插"转入事件表"→ 回 ACK → 发起方更新事件 SUCCESS；超时未 ACK 则定时任务冲正/Compensate；日终批量对账。RPO 仍=0（事件表在同一 MySQL 组复制）。
- **【踩分·拓展】Saga 实现方式**：银行跨单元转账属复杂长流程，应点明采用**编排式 Saga**（协调器集中驱动），事件表+Kafka 只是其底层载体；并强调"事件表与业务表同本地事务提交"是 RPO=0 根本保证。
**考点**：分布式事务（Saga vs XA）、消息队列最终一致、事件表/对账补偿、RPO/RTO、Saga 编排式。

> 💡 **答案解析（讲给小白听）**：真题 3 是银行"跨分行转账慢"的经典题。为什么慢？把分行想成两家独立银行：两家都不敢先动钱，要来回确认两次（XA 两阶段，网络翻倍）；两家之间走互联网还要加密（RTT 从 20ms 拖到 80ms）；都抢同一个大账户时排长队等锁；转账前还得多查一次"是不是重复了"。优化思路是把"实时对账"改成"先各自记账、事后补齐"：A 行先扣钱并记一笔"我转出了"，发消息给 B 行；B 行收到后加钱、回个"搞定"；B 没回就退款重来（冲正），晚上再对一遍总账。两个必写踩分点：①用**编排式 Saga**（有个中央协调器像"转账调度员"统一指挥每一步，比"大家各干各的"更适合长流程）；②RPO=0（钱绝不丢）靠的不是消息队列可不可靠，而是"A 行扣钱和记事件是在自己家里一次性办妥的"（同本地事务 + MySQL 三节点同步），哪怕消息丢了，A 行记录还在，能重发。

**考点**：分布式事务（Saga vs XA）、消息队列最终一致、事件表/对账补偿、RPO/RTO、Saga 编排式。

### 真题 4 · 电商云原生架构迁移（2025 上半年真题方向）
**背景**：电商单体架构，部署慢、故障恢复慢、资源利用率低，迁移至云原生，目标日均 5000 万请求、峰值 QPS 10 万、故障恢复<15min、资源利用率>70%。
**考查问题**：
1. 对比"一刀切/渐进式/重写式"三种迁移方案（风险/成本/业务连续性三维），推最优
2. Service Mesh 相较传统 API 网关的优势，及需重点关注的 4 项服务治理功能
3. 设计"检测—隔离—恢复"三阶段容灾方案
**参考答案要点**：
- **方案对比**：一刀切风险最高、重写式成本最高且需停机；**渐进式**复用现有系统、灰度/金丝雀/蓝绿保持连续，三维最佳 → 推渐进式。
- **Mesh 优势**：网关管南北向，Mesh 管东西向（服务间），提供非侵入式、更细粒度流量治理；重点关注：流量管控（限流/熔断/路由）、通信安全（mTLS）、可观测性（指标/链路）、超时重试。
- **容灾**：检测（存活/就绪探针 + 心跳/监控告警）→ 隔离（熔断驱逐故障 Pod）→ 恢复（HPA 自动扩容 + 滚动更新/一键回滚 + 多副本）。
**考点**：迁移策略论证、Service Mesh 核心能力、容灾三阶段。

> 💡 **答案解析（讲给小白听）**：真题 4 三大问。①迁移方案对比——"一刀切"像把老店炸了直接开新店，风险最高；"重写式"像边营业边把整栋楼拆了重盖，成本最高还长期没收益；**渐进式**是外头先开新柜台、一间间把客人挪过去，老柜台慢慢关，风险最低、不停业、能回退，三维都最优，所以推它。②Mesh vs 网关——网关是"门口保安"，管顾客进门那点事（南北向）；Mesh 是"店里每个部门配的通讯助理"，管部门之间互相传话（东西向），不用改部门自己的代码（非侵入）、管得更细。重点记四点：流量管控（限流/熔断/路由）、通信加密（mTLS）、可观测（指标/链路）、超时重试。③容灾三阶段——先"发现"(探针+监控告警)、再"隔开"(熔断把坏掉的 Pod 赶走)、最后"恢复"(自动加实例 HPA + 滚动更新/回滚 + 多副本)。

**考点**：迁移策略论证、Service Mesh 核心能力、容灾三阶段。

### 真题 5 · 微服务集群高并发雪崩与分布式事务（2025 真题方向）
**背景**：电商微服务（Nacos + Gateway + OpenFeign + RocketMQ + MySQL 分库分表 + Redis + K8s + Prometheus/SkyWalking）。问题：①库存超卖（大促瞬时流量，乐观锁仍回滚/超卖）；②订单与库存异步扣减偶尔不一致（订单成功库存失败）；③营销服务慢拖垮订单服务（雪崩）。
**考查问题**：
1. 结合 Redis + MQ 设计高性能库存扣减方案并保证 DB 一致性
2. 说明"本地消息表/事务消息"如何保证订单创建与库存扣减原子性
3. 解释雪崩效应，除舱壁外还有哪些防雪崩机制，结合网关/调用配置
**参考答案要点**：
1. **库存方案**：Redis 预加载库存（SET stock NX）；Lua 脚本原子执行"检查-扣减-记录"；库存为 0 直接返回；异步通过 MQ（Kafka/RocketMQ）将扣减结果同步 DB（仅成功订单）；DB 层乐观锁（版本号）兜底；定时对账补偿。
2. **事务消息/本地消息表**：本地事务与消息表同库写入（同事务）→ 异步投递消息 → 下游消费处理 → 确认/重试；保证"订单创建成功"与"库存扣减"要么都成功、失败可补偿的最终一致。
3. **雪崩**：下游故障导致上游线程阻塞、连锁扩散。【踩分】必写"雪崩定义 + 故障传播路径"；防雪崩机制：熔断（失败率阈值切断链路）、降级（返回预设提示）、超时（短超时快速失败）、重试+退避、限流（网关/Sentinel 限流）——5 条措施中任写 4 条即可满分。配置：Gateway/Sentinel 设失败率熔断 + 订单服务 5s 超时 + 2 次重试 + 对营销服务限流。
**考点**：Redis 原子扣减 + Lua + MQ 最终一致、分布式事务方案、雪崩防护体系。

> 💡 **答案解析（讲给小白听）**：真题 5 是综合大题。①库存方案——几万人抢 100 件商品，让所有人挤在数据库门口会挤爆，所以把"发号"放到超快的 Redis：开抢前把 100 写进 Redis，每人来用一段"不可分割的脚本"一次性完成"看还有没有→有就减→记下谁"，没票了直接回售罄（不烦数据库）；只有真抢到的，才慢慢通过消息队列通知数据库记账；数据库自己再保险一次（乐观锁），半夜对账补差。②事务消息/本地消息表——解决"订单成了库存没减"：把"下订单"和"通知减库存"绑在同一次数据库操作里（要么都成、要么都不成），提交后再发消息让库存服务去减，没确认就重发，保证两边最终对得上。③雪崩——必写"定义（一个下游慢，沿调用链放大拖垮全局）+ 传播路径"。防雪崩 5 选 4：熔断（对方老失败就先断链）、降级（返回"稍后再试"保核心）、超时（等太久就放弃）、重试+退避（失败隔会儿再试）、限流（门口拦峰值）。配置写：网关设熔断 + 订单 5 秒超时 + 重试 2 次 + 对营销服务限流。

**考点**：Redis 原子扣减 + Lua + MQ 最终一致、分布式事务方案、雪崩防护体系。

# 模拟题 1｜单体电商系统改造微服务（25分）
## 案例背景
某传统电商平台，使用单体架构，所有业务模块（用户、商品、订单、支付、库存）部署在一台应用服务器。随着业务增长，系统迭代速度慢；每次发布需要整体重启；促销高峰期经常出现卡顿；团队人数扩张，多个开发组代码合并冲突严重。架构师计划将单体系统改造为微服务架构。

## 问题1（8分）
请简述将单体电商拆分为微服务架构的主要优点。

## 问题2（9分）
改造为微服务之后，系统会出现一系列新的技术挑战，请列出4项主要问题，并给出对应的解决思路。

## 问题3（8分）
在微服务架构中，需要建设完整的服务治理体系。请说明微服务治理平台至少包含哪些核心组件，每个组件的作用。

## 问题4（补充练手 · 对比辨析）
"单体架构"和"烟囱式架构"常被混淆。请说明二者的本质区别，并指出云原生转型应分别解决它们的什么问题。

### 参考答案
**问题1**
1. 服务独立部署，单个模块升级发布不会影响整个系统；
2. 按照业务域拆分，团队可以并行开发，减少代码冲突；
3. 故障隔离，单一服务故障不会造成全站瘫痪；
4. 可针对高负载服务独立弹性扩容，资源利用率提升；
5. 技术栈解耦，不同微服务可按需选用合适技术方案。

> 💡 **答案解析（讲给小白听）**：想象一家小饭店，厨师、服务员、收银员全挤在一个岗位上，这就是"单体"——所有功能搅在一起。拆成微服务，相当于把饭店分成"炒菜部、面点部、收银部"几个独立小厨房，各有各的灶台。好处就出来了：①某个部（比如面点部）想升级设备，不影响炒菜部营业（**独立部署**）；②两个部可以同时招人干活，不用等对方（**并行开发，少冲突**）；③面点部着火了，炒菜部照样开（**故障隔离**）；④周末炒菜爆单，就给炒菜部加灶台，面点部不动（**按需扩容，省资源**）；⑤炒菜部用电磁炉、面点部用蒸箱，各用各合适的工具（**技术栈自由**）。这五条考试照答即可。

**问题2（问题+对策）**
1. **分布式事务、数据一致性问题**：采用Saga、可靠消息队列实现最终一致性；
2. **远程调用失败、服务雪崩风险**：引入熔断、降级、超时重试策略；
3. **服务实例地址动态变化、调用方难以感知**：搭建注册中心实现服务注册发现；
4. **运维监控难度上涨**：建设指标监控、日志、分布式链路追踪，实现可观测。

> 💡 **答案解析（讲给小白听）**：饭店拆成几个独立小厨房后，麻烦也来了，四个新坑：①**账对不上**——炒菜部记了一笔、收银部没记，两家账目不一致（这就是"分布式事务"问题）。解决办法是别强求瞬间两边同步，而是"先记个条子，稍后对账补齐"（Saga/消息队列，最终一致）。②**一家卡住拖垮全场**——面点部慢了，炒菜部一直在等它、资源被占满，最后炒菜部也瘫了（"雪崩"）。所以要装"保险丝"：等太久就放弃、这家不行就走备用方案（熔断/降级/超时）。③**人老换位置**——小厨房今天在三楼明天在二楼，别人找不到（"地址动态变化"）。解决办法是弄个"总服务台"登记每个人当前在哪（注册中心）。④**出事查不清**——饭做砸了，不知道是哪个部的问题。所以要装监控、记日志、能追踪一道菜从哪到哪（可观测）。四个坑对应四件套：事务、熔断、注册、观测。

**问题3**
1. **注册中心**：保存所有微服务实例地址，实现服务注册与发现；
2. **配置中心**：集中管理配置，配置与代码分离，动态生效；
3. **容错治理组件**：熔断、降级、限流，保障服务韧性；
4. **分布式链路追踪组件**：追踪请求全链路，定位跨服务性能瓶颈；
5. **监控告警平台**：采集各项性能指标，异常告警。

> 💡 **答案解析（讲给小白听）**：微服务拆开后，得像管理一家连锁店一样有套"管理后台"，这 5 个组件就是：①**注册中心**=花名册，谁在哪个岗位、今天来没来，一查就知道，调用方不用死记地址；②**配置中心**=统一公告栏，要改营业时间、调价格，在公告栏改一下全员生效，不用挨个通知、也不用每家店关门重开（配置与代码分离、动态生效）；③**容错治理**=应急预案，哪家店出问题就熔断/降级/限流，别让一家拖垮整个品牌；④**链路追踪**=外卖小票，一道菜从下单到出锅经过哪些环节、卡在哪，一扫小票就明白；⑤**监控告警**=店里装摄像头和警报，异常（排队过长、出错率飙升）立刻报警。这五个是治理标准五件套。

**问题4（烟囱式 vs 单体 · 对比辨析）**
- **本质区别**：**单体架构**是"**一个系统内代码耦合**"——所有功能塞在一个应用、一个数据库里，改一处全量发布；**烟囱式架构**是"**多个独立系统之间数据不互通**"——库存一个系统、订单一个系统、会员一个系统，各自独立建设、独立库，系统间靠人工导出数据合并。
- **云原生转型分别解决什么**：
  - 单体 → 用**微服务拆分（DDD 限界上下文）+ 独立库**解决"代码耦合、无法独立部署"；
  - 烟囱式 → 用**微服务拆分 + 共享服务中心（统一用户中心/商品中心）+ 数据中台**解决"数据孤岛、重复建设"，实现数据融通与能力复用，再配合容器化与 DevOps 实现弹性伸缩。
- **答题话术**：烟囱式架构初期开发快，但后期**数据孤岛、重复建设、维护成本高**；云原生转型通过微服务拆分、共享服务中心、数据中台实现数据融通与能力复用，配合容器化与 DevOps 实现弹性伸缩和快速迭代。

> 💡 **答案解析（讲给小白听）**：这两个词常被搞混，但毛病完全不同，用饭店比喻就清楚了：**单体**是"一家饭店里，炒菜、收银、进货全由同一个人兼着，账本也只有一本"——问题是内部搅在一起，动一下就得全店停业重开（代码耦合、不能独立部署）。**烟囱式**是"一条街上开了三家互不说话的饭店：库存一家、订单一家、会员一家，各记各的账，要合并数据只能靠老板手动把三家账本抄到一起"——问题是店和店之间数据不通（数据孤岛、重复建设）。所以治法也不同：单体要"**拆**"（拆成独立小厨房，各有各的账本）；烟囱要"**通**"（建个统一的会员中心、商品中心，让各店共用，再上数据中台打通账本）。答题先说清"一个是内部搅、一个是外部不通"，再分别讲怎么治。

# 模拟题 2｜SOA遗留系统升级（25分）
## 背景
某银行内部有多套异构业务系统，早年基于SOA+重型ESB企业服务总线完成系统集成。随着业务迭代，ESB单点压力越来越大，所有服务之间调用流量全部经过总线，总线修改升级会造成所有业务中断，扩展困难。架构团队计划逐步迁移到微服务架构，将重型ESB替换。

## 问题1（7分）
简述ESB（企业服务总线）在原有SOA架构中的主要功能。

## 问题2（9分）
请对比SOA架构（ESB）与微服务架构的差异，并说明为什么重型ESB不再适合新的互联网业务。

## 问题3（9分）
迁移后使用轻量API网关替代ESB，请说明API网关适合承担哪些工作，哪些东西不应该放到网关。

### 参考答案
**问题1**
1. 协议转换，屏蔽异构系统通信协议差异；
2. 消息路由，实现服务请求转发；
3. 数据格式转换；
4. 服务编排，组合多个服务完成业务流程；
5. 统一安全认证、日志审计、异常处理。

> 💡 **答案解析（讲给小白听）**：ESB 就像公司的"总机接线员 + 翻译官"。早年各家系统（ERP、CRM…）像说不同方言、用不同电话的老部门，互相打不通。ESB 这个"总机"干五件事：①**协议转换**——把 A 部门的"方言"翻译成 B 部门听得懂的（屏蔽通信协议差异）；②**消息路由**——谁找谁，总机帮你转接（请求转发）；③**数据格式转换**——把 A 的格式换成 B 要的格式；④**服务编排**——把多个部门的活串成一条流程（比如"先查库存再下单再扣款"）；⑤**统一安全/日志**——所有电话都过总机，方便统一查岗和记日志。记住"总机"这个比喻，五个功能就串起来了。

**问题2**
差异要点：
1. ESB属于重型集中式总线；微服务去掉集中总线，采用轻量点对点通信；
2. SOA服务粒度粗；微服务拆分粒度更细；
3. SOA偏向遗留异构系统集成；微服务面向快速迭代互联网业务。
ESB缺点：单点瓶颈；总线成为性能卡点；升级运维风险高；扩展困难。

> 💡 **答案解析（讲给小白听）**：ESB 为啥被淘汰？回到"总机"比喻就懂了。差异三点：①**结构**——ESB 是"所有电话必须经过总机"的集中式；微服务是"大家直接互拨"的点对点，轻量多了。②**粗细**——SOA 把"整个订餐流程"当一个大服务；微服务拆成"下单、支付、库存"等小服务，粒度细。③**场景**——SOB 当年是为了把一堆老系统缝在一起；微服务是为了让互联网业务能天天改、快速迭代。ESB 的死穴也来自"总机"：总机只有一台，它一升级全公司电话断（单点瓶颈、升级风险高）；电话太多总机忙不过来（性能卡点）；想扩容只能换更大的总机（扩展难）。一句话：**把所有鸡蛋放一个篮子里，篮子一坏全完**。

**问题3**
适合网关：南北流量路由、负载均衡、客户端认证授权、限流、灰度发布、日志采集。
不适合网关：复杂业务编排、重量级数据转换；这类逻辑下沉至后端微服务。

> 💡 **答案解析（讲给小白听）**：API 网关好比小区的"大门保安亭"。它适合干"谁来都一样的通用活"：问"你找哪栋楼"然后指路（路由）、把访客均分给几栋楼（负载均衡）、查身份证（认证授权）、限流（一次只放这么多人进）、新楼试运行先放部分人看（灰度）、记进出日志。但它**不该**干"具体业务"——比如替某栋楼把快递拆包重新打包（复杂业务编排、重量级数据转换），这些细活要让楼里的人自己干（下沉到后端微服务）。原则：**保安亭只管进门那点通用事，楼里的业务别推给保安亭**。

# 模拟题3｜云原生K8s容器改造案例（25分）
## 背景
某互联网公司现有业务系统部署在虚拟机上，遇到以下痛点：新环境部署周期长，开发‑测试‑生产环境不一致；促销高峰流量突增，无法快速扩容；版本发布停机时间长。架构师计划进行云原生改造，采用Docker + Kubernetes集群部署。

## 问题1（8分）
简述Docker容器技术可以解决原有虚拟机部署模式下的哪些痛点？

## 问题2（8分）
云原生改造中强调应用无状态，请解释什么是无状态应用，改造时需要把哪些数据移出容器本地？

## 问题3（9分）
采用Kubernetes平台，请说明HPA、Deployment、Service三个核心资源对象各自作用。

### 参考答案
**问题1**
1. 将应用和依赖一起打包成镜像，解决环境不一致问题；
2. 容器启动速度远快于虚拟机，部署发布效率提升；
3. 资源开销更小，单机可以部署更多实例；
4. 镜像版本化管理，便于版本回滚。

> 💡 **答案解析（讲给小白听）**：把虚拟机（VM）想象成"给每个应用单独盖一栋带地基带家具的房子"，docker 容器是"同一栋楼里隔出来的独立房间"。VM 的毛病：盖房慢、占地方、每家家具还不一样（环境不一致，搬一次家就水土不服）。Docker 怎么治：①把应用和它需要的一切（家具）打包成一个"标准房间模板"（镜像），到哪都能原样建出来（环境一致）；②房间是现成的，秒级开门即用（启动快）；③同一栋楼隔很多间，省地（单机多实例）；④模板有版本号，这次布置丑了，一键退回上一版（可回滚）。抓住"盖房 vs 隔间"这个对比就懂了。

**问题2**
无状态：应用实例不保存会话、业务数据；任意实例可以随时销毁重建，实例之间无差异。
移出本地：Session会话、缓存数据、业务文件、持久化日志；放置Redis、对象存储、数据库。

> 💡 **答案解析（讲给小白听）**："无状态"用餐厅服务员比喻：有状态的服务员脑子记着"3号桌点了牛排、账单还没付"——他要是下班了，3号桌就懵了。无状态的服务员什么都不记，所有信息写在点单小票（外部存储）上，换哪个服务员来都能接着干。所以容器里不能存：顾客的"身份记忆"（Session）、临时放的"菜"（缓存）、顾客带来的"文件"、店里的"流水账"（日志）——这些全挪到外面专门的仓库（Redis、对象存储、数据库）。好处是：容器像一次性纸杯，随便扔掉、随便再造一个，系统完全不受影响。K8s 才能放心地把它调度到任何机器上。

**问题3**
1. Deployment：管理无状态应用Pod副本，负责滚动升级、版本回滚；
2. Service：一组Pod的统一访问入口，提供负载均衡；
3. HPA（水平自动扩缩）：依据CPU/QPS等指标，自动增减Pod副本数量。

> 💡 **答案解析（讲给小白听）**：K8s 里这三个对象可以想成"开连锁分店"的三样东西：①**Deployment（店长）**——负责按标准开几家分店（副本数），要升级就一家家慢慢换、出事了整批退回上一版（滚动升级、回滚）。②**Service（总机/招牌）**——不管你具体哪家分店、分店换了没，顾客都打这个统一电话、总机帮你转到有空的那家（统一入口+负载均衡），分店地址变了顾客也不感知。③**HPA（自动排班）**——看客流（CPU/请求量），人多就自动加开分店、人少就关几家（按指标自动扩缩）。一句话：Deployment 管"开几家、怎么换"，Service 管"顾客怎么找到"，HPA 管"忙了自动加人"。

# 模拟题4｜Service Mesh 服务网格（Istio）新热点（25分）
## 背景
企业已经上线了20余个微服务，使用Java、Go、Python多语言开发。目前熔断、限流、链路追踪治理逻辑需要在每个项目业务代码重复开发，多语言SDK维护成本很高。架构师决定引入Istio服务网格实现服务治理。

## 问题1（8分）
什么是Sidecar代理模式？说明服务网格的数据平面与控制平面各自职责。

## 问题2（8分）
简述采用Service‑Mesh治理微服务相比传统SDK埋点方案，有哪些优点？

## 问题3（9分）
请列出至少3项基于服务网格可以实现的服务治理功能。

### 参考答案
**问题1**
Sidecar是部署在每个微服务Pod内、和业务容器伴生运行的代理进程，拦截所有进出业务服务的网络流量。
- **数据平面（Envoy）**：实际执行流量治理，熔断、限流、加密通信；
- **控制平面（Istio Pilot）**：统一下发治理配置规则，不转发业务流量。

> 💡 **答案解析（讲给小白听）**：Sidecar 字面就是"边车"——摩托车旁边挂的那个小斗。给每个微服务配一个"贴身助理"（代理进程），它和业务程序住同一个"Pod 车厢"里，所有进出业务的信件都先过这个助理。两个平面就像公司：①**数据平面（Envoy）**=一线干活的员工，真正去执行"这封信拦下、那封加密、超时的切断"（熔断/限流/加密），所有实际 traffic 都它处理；②**控制平面（Pilot）**=总部发通知的，只负责把"该怎么管"的规则统一下发到各助理，自己不直接处理业务信件。比喻：数据面=手脚（干事），控制面=大脑（发令），各司其职。

**问题2优点**
1. 治理逻辑与业务代码解耦，**业务代码零侵入**；
2. 多语言微服务统一治理方案，不需要为不同语言开发SDK；
3. 治理规则可以动态下发，不需要重启业务服务；
4. 流量观测统一收集。

> 💡 **答案解析（讲给小白听）**：传统做法像让每个员工自己背"公司制度手册"（SDK 埋点）：Java 员工一本、Go 员工一本、Python 员工又一本，三套手册要分别维护，改一条制度三本都得改、还得让大家停下手头活重学（重启服务）。Service Mesh 改成：公司派一个"助理"跟着每个员工，制度由助理统一执行，员工自己什么都不用管（**零侵入**）；不管啥语言的员工，助理都一样干（**多语言统一**）；总部改了制度，助理实时收到，员工不用停手（**动态下发**）；所有助理的活动总部统一能看到（**观测统一**）。一句话：把"每人自学制度"变成"每人配个执行的助理"。

**问题3治理功能**
流量路由、灰度/金丝雀发布、熔断降级、限流、mTLS双向加密通信、分布式链路追踪、访问权限控制。

> 💡 **答案解析（讲给小白听）**：既然每个微服务都有个"助理"跟着，这个助理能帮着管的就是服务网格的治理功能。分四类好记：①**流量类**——助理决定这封信走哪条路（路由）、先放 5% 的信试水再全放（灰度/金丝雀）、太多信就拦下一些（限流）；②**韧性类**——对方回得太慢就先不发了（熔断）、对方挂了就回个"稍后再试"的客气话（降级）；③**安全类**——助理和助理之间说暗语，外人听不懂（mTLS 双向加密）、只放有权限的人通信（权限控制）；④**可观测类**——每封信走了哪些助理、花了多久，全程有记录（链路追踪）。这七项里任选 3 项以上即可。

# 模拟题 5｜微服务雪崩故障排查案例（25分）
## 背景
某微服务系统包含用户、订单、库存、支付四个服务。大促期间，库存服务响应变慢，大量订单服务请求库存接口超时，订单服务线程池耗尽，继而用户服务调用订单服务全部失败，整个系统近乎瘫痪。事后复盘，系统没有任何限流熔断机制。

## 问题1（8分）
请解释什么是微服务雪崩效应，描述本案例故障传播路径。

## 问题2（8分）
为了防止雪崩，请说明熔断、降级、限流三者的区别。

## 问题3（9分）
请给出5条整改优化措施，提高系统韧性。

### 参考答案
**问题1**
【踩分·必写】雪崩效应：一个下游服务故障，调用方不断重试，故障逐级向上传导，拖垮整条调用链，造成大面积服务不可用。
【踩分·必写】故障路径：库存服务变慢→订单服务大量超时，线程耗尽→订单服务不可用→用户服务调用订单失败→全站故障。

> 💡 **答案解析（讲给小白听）**："雪崩"就像高速上一起小追尾没处理好，后面车一辆接一辆撞上来，最后堵成一片。在这个案例里：库存服务像"上游收费站"变慢了→订单服务派去缴费的车（请求）全堵在门口，收费口排满后连新来的车都进不去（线程池耗尽）→订单服务自己动不了了（不可用）→用户服务要调订单，也跟着失败→整条路全瘫。这就是"一个下游慢，层层向上拖垮整条链"。答题时**定义**（一个故障沿调用链放大、拖垮全局）和**路径**（库存慢→订单堵→用户挂→全瘫）两条都必须写，缺一个丢分。

**问题2**
1. **熔断**：下游失败率到达阈值，短时间停止调用下游，快速失败；
2. **降级**：故障发生时关闭非核心功能，返回兜底数据，保障核心业务可用；
3. **限流**：限制流入系统的请求数量，保护服务不会被过量请求压垮。

> 💡 **答案解析（讲给小白听）**：这三个词常混，用"饭店爆满"比喻就清楚了：①**熔断**=厨房着火了，前台直接挂出"暂停接客"牌子，不再放人进去（下游已挂，主动切断调用，快速失败）。②**降级**=厨房忙不过来，先下架复杂菜品，只卖面条保住核心生意，没菜的就回"今日售罄"（关掉非核心功能、返回兜底，保核心可用）。③**限流**=门口保安按容量放人，排不下的直接在门外等或劝退（入口拦住过量请求，保护系统不被压垮）。三者层次不同：熔断是"下游挂了别去送死"、降级是"忙不过来保重点"、限流是"门口别让人挤爆"。

**问题3优化措施**
1. 在所有远程调用增加超时时间；
2. 引入熔断降级组件；
3. 在API网关层增加限流策略；
4. 增加异步消息队列，同步调用改异步解耦；
5. 建设监控告警系统，提前发现服务延迟异常。

> 💡 **答案解析（讲给小白听）**：五条整改是一套"从根上防雪崩"的组合拳：①**超时**——叫外卖等 30 秒没人接就挂断重叫，别一直举着电话占线（快速失败，别傻等把资源耗光）；②**熔断降级**——对方挂了就切断、返回兜底，别让故障传过来（断链防扩散）；③**限流**——门口按容量放人，突发大客流也扛得住（入口拦峰值）；④**异步解耦**——本来"你做完我才做"改成"你丢个纸条给我、我回头处理"，不实时互相等（用 MQ 把同步依赖切开）；⑤**监控告警**——装个仪表盘，对方开始变慢就报警，趁没崩先处理。按"超时→熔断→限流→异步→监控"顺序写最顺。

# 模拟题 6｜Web高可用架构设计大题（25分）
## 背景
一个面向公众的在线报名网站，高峰期短时间并发请求突增；用户登录后Session保存在应用服务器本地，当负载均衡分发到另一台服务器就会丢失登录状态；静态图片、视频文件下载消耗大量后端服务器资源。

## 问题1（8分）
指出当前系统两处明显缺陷，并给出解决方案。

## 问题2（8分）
请说明反向代理+负载均衡在Web架构中的作用。

## 问题3（9分）
设计高并发Web系统架构，包含客户端‑CDN‑反向代理‑应用‑缓存‑数据库，简述每层职责。

### 参考答案
**问题1**
缺陷1：Session保存在应用服务器本地，多实例登录丢失；
方案：Session会话集中存储到Redis缓存，实现会话共享。
缺陷2：静态资源请求消耗后端算力；
方案：动静分离，静态资源放到CDN加速。
缺陷3（**踩分·易漏**）：题目背景明确"高峰期短时间并发请求突增"，但系统**未在网关层配置限流策略**，突发流量直接打到后端，易引发资源耗尽甚至雪崩；
方案：在 **API 网关层配置令牌桶限流**（按 IP/用户等级），对突发流量排队放行、超限拒绝，保护后端。

> 💡 **答案解析（讲给小白听）**：这个网站有三个毛病，第三个最容易被忽略：①**登录状态丢了**——用户登录信息存在 A 服务器内存里，下次请求被分到 B 服务器，B 不认识他，又得重登。好比你在 1 号柜台办了会员，去 2 号柜台人家不认。治法是把会员信息存到大家都能查的公共柜子（Redis），不管去哪个柜台都认得。②**图片视频拖垮服务器**——这些静态文件占了后端大量算力。好比顾客全来问"厕所怎么走"把店员缠住。治法是把这类固定内容放"就近的公告栏"（CDN），顾客自己看，不麻烦店员。③**（易漏考点）突发流量无限流**——题目明说"高峰期并发突增"，但系统没在门口限流，洪水般请求直接冲进后端，容易把服务器压垮甚至雪崩。治法是门口保安按令牌桶规则放人，超了就拒。前两个是常考点，第三个才是命题人埋的坑，必须点出。

**问题2**
反向代理：接收用户请求，转发后端应用服务器，隐藏后端节点真实地址；
负载均衡：将用户流量分发至多台后端服务器，分摊压力，实现水平扩容、故障隔离。

> 💡 **答案解析（讲给小白听）**：这两个是网站的"前台接待 + 调度员"：①**反向代理**——像公司前台，外面的人只认识前台这个地址，真实的办公室（后端服务器）藏在后面，前台替你转达需求。好处是隐藏了后端真实地址（安全）、统一收口。②**负载均衡**——像叫号机，把涌进来的人均匀分到多个窗口（多台服务器），哪个窗口闲就给哪个，既能分摊压力，又能某窗口故障其他人照常办（故障隔离）。Nginx 这俩功能常一起用。记八字："代理隐藏、均衡分摊"。

**问题3架构分层**
1. CDN：缓存静态资源，就近访问；
2. 反向代理(Nginx)：负载均衡、请求路由；
3. API网关层：认证、限流；
4. 微服务应用层：执行业务逻辑；
5. Redis缓存层：热点数据缓存、会话存储；
6. 数据库层：持久化业务数据。

> 💡 **答案解析（讲给小白听）**：高并发网站像一家层层设防的大商场，从外到内逐级消化人流：①**CDN**=商场外的大广告牌/指引牌，固定的东西（海报=静态资源）就近就能看，不用进商场（挡静态、就近访问）；②**反向代理（Nginx）**=门口引导员，把人分到不同入口（路由+均衡）；③**API 网关**=安检口，查身份证、限流（认证+限流）；④**应用层**=真正干活的店员（业务逻辑）；⑤**Redis**=店门口的临时货架，热门商品（热点数据）和会员卡（会话）先放这，随取随用，不老往仓库跑；⑥**数据库**=最里面的总仓库，贵重数据才存这。原则：**越外层越该挡住流量，越往里越宝贵**，压力在前面就消化掉，别全压到仓库。这六层是标准骨架。

# 模拟题 7｜跨单元转账的分布式事务优化（银行核心系统）（25分）
## 背景
某城商行核心系统采用"单元化+分布式"架构，每单元承担 200 万账户，单元内账户/交易/支付三微服务，MySQL Group Replication 三节点（RPO=0）。上线后跨单元转账平均耗时 2.5s（单单元仅 200ms），业务要求不改变 RPO。

## 问题1（8分）
请分析跨单元转账耗时高的根因，给出至少 3 点。

## 问题2（9分）
提出一种基于"账户归属单元"与"事务一致性"平衡的优化方案（不改 RPO），说明核心思路并给出转账时序（文字描述）。

## 问题3（8分）
该方案如何保证"转账创建成功"与"对方单元入账"的最终一致？请说明 Saga 事务 + 消息队列 + 补偿/对账的实现思路。

## 问题4（补充练手 · 单元化设计要素）
若将该行核心系统进一步做"单元化 + 分片"改造，请说明：① 分片键（如用户/账户维度）的选取原则；② 如何避免热点单元；③ 单元化与微服务的关系。

### 参考答案
**问题1**
1. 跨单元需两阶段提交（XA），prepare/commit 网络 RTT 翻倍；
2. 单元间公网 SSL 加密，RTT 放大（20ms→80ms）；
3. 热点账户行锁竞争，跨单元无法利用本地 MVCC，锁等待概率高；
4. 幂等检查在 DB 层，增加一次 SELECT。

> 💡 **答案解析（讲给小白听）**：把"单元"想成"分行"。在一家分行内部转账，钱从 A 账户划到 B 账户，一步就成（200ms）。但跨两家分行转账就慢了，四个原因：①**两阶段提交（XA）**——两家分行都不敢先动钱，要先互相"预备…好、确认…好"两次确认（prepare/commit），一来一回网络就翻倍了；②**公网加密**——两家分行之间走的是互联网还要加密，本来 20 毫秒的路程被拖成 80 毫秒（RTT 放大）；③**热点账户行锁**——如果很多人都转同一个大账户（比如某商户），这家分行里大家排着队等锁，而跨分行还不能用"本地快速通道"（MVCC），等得更久；④**幂等检查**——转账前还要多查一次数据库"这单是不是重复了"，又多花时间。答题至少写 3 点，从"网络往返、加密开销、锁竞争、额外查询"里挑。

**问题2**
采用"异地单元记账 + 日终清算"+ Saga 长事务。时序：①发起方单元本地扣减，插"转出事件表"(INIT)；②发 Kafka 消息至接收方单元；③接收方消费后本地增加金额，插"转入事件表"，回 ACK；④发起方收 ACK 后更新事件 SUCCESS；⑤超时未 ACK → 定时任务冲正，发 Compensate 消息；⑥日终批量对账，差异人工介入。RPO 仍=0（事件表在同一 MySQL 组复制，本地事务提交即持久化）。

> 💡 **答案解析（讲给小白听）**：核心思路是"别再让两家分行实时对账了，改成先各自记账、事后补齐"。具体像这样走：①**发起方（A 分行）**先把你账户的钱扣了，同时在自己行里记一笔"我转出了"（事件表 INIT）；②给**接收方（B 分行）**发个消息"该给某某加钱了"；③B 分行收到后，给收款人加钱，也记一笔"我收到了"，然后回个"搞定"（ACK）；④A 分行收到 ACK，把那笔事件改成"成功"（SUCCESS）。如果 B 半天没回（超时），A 就启动**冲正**——把钱退给你，并发消息通知 B 也撤销；最后每天晚上**日终对账**，两边核一遍，差了就人工补。关键是：A 分行扣钱和记事件是在"同一家银行内部一次性办妥"的，所以哪怕消息途中丢了，A 这边钱和记录都不丢（RPO=0），定时任务还能重发。

**问题3**
【踩分】Saga 将跨单元转账拆为本地事务链（发起方扣减 + 接收方入账），每步有对应补偿动作（冲正）；通过 Kafka 可靠投递 + 事务消息/本地消息表保证消息不丢；下游消费确认后回 ACK；超时/失败触发补偿（冲正消息）+ 日终对账兜底，实现最终一致性，满足 RPO=0。
【踩分·拓展】本题应采用**编排式 Saga（Orchestration）**：由中央 Saga 协调器（状态机）集中驱动"扣减→通知→入账→确认"各步，状态可见、补偿顺序可控、强制幂等——比协作式（无中心、仅靠事件互相触发）更适配银行转账长流程；协作式仅适合简单短流程。
【踩分·关键论证】RPO=0 的**根本保证**是"转出/转入事件表与业务表在**同一本地事务**中提交"（MySQL 组复制同步到三节点），而非依赖 MQ 可靠性；即便 Kafka 投递延迟或丢消息，本地已持久化的事件可由定时任务重投/冲正，数据零丢失。

> 💡 **答案解析（讲给小白听）**："最终一致"的意思是"不用每一秒都对齐，但早晚会对齐、钱不丢"。三道防线：①**Saga 长流程**——把转账拆成"我扣钱 + 你加钱"两步，每步都配一个反操作（你没加成功，我就把钱退回来，这叫冲正）；②**消息队列（Kafka）+ 本地消息表**——A 分行扣钱的同时把"已转出"记进自己的表（同一次操作里），然后异步把消息发出去，B 收到并处理完回 ACK，没收到就不断重试；③**补偿 + 日终对账**——超时或失败就触发冲正，晚上睡觉前再把两边账本对一遍兜底。最关键的一点（必写）：RPO=0（钱零丢失）靠的不是消息队列可不可靠，而是"转出事件表和业务扣款在同一家银行内部一起提交"（MySQL 三节点同步），哪怕 Kafka 把消息弄丢了，A 行里那笔记录还在，定时任务能重发——所以数据绝不会丢。

**问题4（单元化设计要素）**
1. **分片键选取原则**：① **业务隔离性**（按用户/账户维度分片，使单笔交易尽量落在同一单元内，避免跨单元）；② **数据均匀性**（分片后各单元数据量均衡，避免倾斜）；③ **可扩展性**（后续增单元可平滑再分片，如 `hash(userId) % N`）；④ **不可变性**（分片键一旦选定不宜变更，否则引发大规模数据迁移）。
2. **热点单元避免（应急三板斧）**：① **两段随机**：顺序生成的账号（如自增 ID）易落到同一段，改为"顺序段 + 预随机跳号"打散；② **实时监测**：用 Flink 窗口计算各单元 QPS，热点单元提前预警；③ **应急三板斧**：**秒级限流**（保护热点单元不被冲垮）→ **秒级扩容**（单元内计算节点 HPA 快速加实例）→ **热点路由**（将热点账户/请求动态调度到空闲单元）。
3. **单元化与微服务的关系**：**二者正交**——**微服务是业务维度**（按业务能力拆分，如账户/交易/支付服务）；**单元是部署/数据维度**（按用户或订单维度分片，每个单元包含完整业务链路）。一个单元内通常部署全套微服务，单元间禁止跨库 Join、尽量不跨单元调用。

> 💡 **答案解析（讲给小白听）**：问题 4 三个子问：①**分片键怎么选**——分片键就是"按什么把客户分到不同分行"。原则：尽量让一笔业务落在同一家分行（业务隔离，少跨行）；各分行客户数要差不多（数据均匀，别一家挤爆）；以后加分行能平滑再分（可扩展）；分片键定下后别老改（不可变，否则要大规模搬数据）。②**热点单元（某家分行挤爆）怎么办**——三板斧：把顺序排号的账号改成"跳着号"打散（两段随机），别让新客户都落同一家；用监控实时看哪家忙（Flink 算 QPS）；应急时先限流保护它、再秒级加窗口（扩容）、还不行就把热点客户临时调去空闲分行（热点路由）。③**单元化 vs 微服务**——它俩是"两个不同方向"：微服务是"按业务种类切"（账户部、交易部、支付部）；单元是"按客户群切"（华东客户群、华南客户群，每个群里都有完整的账户/交易/支付部）。正交=互不冲突，一个单元里通常全套微服务都有，单元之间尽量不互相调用。

# 模拟题 8｜高并发秒杀系统的库存与一致性设计（25分）
## 背景
某电商平台大促秒杀场景，瞬时流量巨大，原有"DB 乐观锁"方案因大量回滚导致连接池耗尽且仍有少量超卖。系统采用 Redis 缓存热点库存、RocketMQ 异步扣减、MySQL 持久化。

## 问题1（8分）
请结合 Redis 与消息队列，设计高性能库存扣减方案，描述流程并说明如何保证与数据库的一致性。

## 问题2（9分）

## 问题3（8分）

3. 库存为 0 直接返回失败，避免击穿 DB；
4. 扣减成功后异步通过 RocketMQ 将结果同步 MySQL（仅处理成功订单）；
5. DB 层乐观锁（版本号）兜底防超卖；
6. 定时对账任务核对 Redis 与 DB 库存差异并补偿修正。

> 💡 **答案解析（讲给小白听）**：秒杀就像限量发放 100 张票，几万人同时抢。直接让几万人在数据库（DB）门口挤会挤爆，所以把"发号"的活放到 Redis（一个超快的内存小柜台）上：①开抢前先把 100 张票的数写到 Redis（预热）；②每个人来，Redis 用一段"原子脚本"一次性完成"看看还有没有票→有就减一张→记下谁抢到"，这中间别人插不进来（原子扣减）；③票没了（库存 0）直接回"售罄"，根本不用去打扰数据库；④只有真抢到的人，才通过消息队列（MQ）慢慢通知数据库"记一下这单"（异步落库）；⑤数据库自己再保险一次（乐观锁，版本号对不上就拒绝）；⑥半夜定时把 Redis 和数据库的数对一遍，差了就补（对账）。核心思想：**让 Redis 这个快柜台扛住所有人，数据库只管慢慢记成功的单子**。

**问题2**
Lua 脚本在 Redis 单线程内执行，保证"检查-扣减"不可分割，从根源防超卖；SET NX 保证库存初始化唯一。异步对账：定时核对 Redis 与 DB 库存，发现发现差异（如 MQ 消费失败/网络抖动导致的不一致）通过补偿任务修正，作为最终一致性的兜底保障。

> 💡 **答案解析（讲给小白听）**："超卖"就是 100 张票卖出了 101 张。为什么会超卖？因为"看还有票"和"减一张"要是分两步，可能两人同时看到"还有 1 张"，都去减，就卖出 2 张。Redis 有个好处：它一次只干一件事（单线程）。Lua 脚本把"看票+减票"打包成**一段不可分割的操作**，在 Redis 里一口气执行完，中间绝不会被别人插队，所以从根本上杜绝了两个请求同时抢到最后一张。SET NX 是"初始化库存时，只有第一个写的生效，防止重复初始化把库存冲掉"。异步对账是最后兜底：万一消息没送到数据库、两边数对不上，半夜的定时任务会把差的数补齐。

**问题3**
本地消息表——订单创建与"库存扣减消息"同库同事务写入（订单表 + 消息表），事务提交后异步投递 MQ；下游库存服务消费并扣减，成功后确认；失败/超时重试。事务消息（RocketMQ）——消息中间件保证消息可靠投递与本地事务的原子性，两操作要么都成功、失败可补偿重试，实现最终一致。

> 💡 **答案解析（讲给小白听）**：问题 3 解决"订单成了但库存没减"的尴尬（比如用户付了钱，库存却还是满的，又被人买了导致超卖）。办法是让"下订单"和"通知减库存"绑成一件事：①**本地消息表**——在同一家数据库里，既写"订单成了"，又写一张"待发消息"小条，这两步在同一次操作里完成（要么都成、要么都不成）。订单提交后，再把这张小条通过 MQ 发出去，库存服务收到就减库存，减完回个确认；没确认就按小条重发。②**RocketMQ 事务消息**——中间件帮你保证"本地订单成了，消息就一定送得出去"。核心就一句：**订单和减库存消息要么一起成功，要么能补偿重试，最终两边对得上**。记"同库绑定 + 可靠投递 + 补偿重试"。

# 模拟题 9｜K8s + Service Mesh + DevOps 协同与故障排查（25分）
## 背景
某电商 Web 系统（50+ 微服务）采用 K8s 容器编排 + Istio Service Mesh + Jenkins/GitLab CI DevOps 流水线。大促期间支付服务响应变慢，导致订单服务线程阻塞；同时新功能上线后出 bug 需快速回滚；多次微服务调用链路复杂，故障定位困难。

## 问题3（8分）
针对"调用链路复杂、故障定位难"与"新功能出 bug 需快速回滚"，分别说明应对方案及所用技术。

### 参考答案
**问题1**

> 💡 **答案解析（讲给小白听）**：把这套系统想成"开一家连锁店"，三者各管一段：①**K8s = 门店基建部**——负责盖店、关店、忙了多开几家、店出问题自动重启、升级时一家家换不歇业（生死扩缩、调度、HPA、回滚、探针自愈）。②**Service Mesh = 店与店之间的通讯部**——不管你用什么语言开的店，通讯部统一管"谁给谁打电话、电话断了怎么办、通话加密"（非侵入流量管控、熔断、mTLS、链路采集）。③**DevOps = 总部发布流水线**——程序员一提交代码，流水线自动测试、打包成"标准门店模板"、推送到 K8s 开新店、先放 5% 顾客试水（快上快回滚、灰度）。协同起来就是：写代码→流水线打包→K8s 开店（每店配个通讯助理 Sidecar）→Mesh 管店间通讯。三者一环扣一环，各管一摊。

**问题2**
Istio Sidecar（Envoy）自动接管订单→支付的服务间通信，无需改业务代码（非侵入）；Sentinel 与 Istio 集成做精细化熔断配置——当支付服务响应超时率>阈值（如 50%）或连续失败达阈值，触发熔断，切断订单→支付链路防扩散；熔断后订单服务返回降级提示（"支付繁忙"）；Sidecar 将调用数据（响应时间/错误率）同步 Sentinel 动态调整阈值。优势：非侵入接管 + 精细化配置，既防雪崩又降改造成本。

> 💡 **答案解析（讲给小白听）**：问题 2 是把"通讯部助理"和"熔断器"配合起来。订单服务要调支付服务，助理（Envoy Sidecar）自动在中间传话，不用改订单的代码（非侵入）。再让 Sentinel 定个规矩：如果支付那边超时或报错的比例超过 50%，就直接"挂断"订单→支付的电话（熔断），防止订单一直傻等把资源耗光、进而拖垮自己。熔断期间订单不再调支付，直接回个"支付繁忙请稍后"（降级）。助理还会把"通话成功率、耗时"报给 Sentinel，让它动态调整规矩。好处：既挡住了雪崩，又不用改业务代码、省钱省力。

**问题3**
1. 故障定位难——启用 Mesh 分布式追踪（Jaeger/SkyWalking），Sidecar 自动采集链路数据无需业务埋点，可视化"订单→支付→库存"完整调用链，快速定位超时/失败节点。
2. 快速回滚——K8s 滚动更新保留旧版本 ReplicaSet + DevOps 流水线一键回滚（回退 K8s 清单至上一版本），结合 Mesh 金丝雀发布（先 5%/10% 切流）降低风险。

> 💡 **答案解析（讲给小白听）**：两个痛点两套办法：①**链路复杂、查不出哪坏**——给每个服务配的通讯助理（Sidecar）会自动记"这笔请求从订单→支付→库存经过了谁、各花了多久"，拼成一张完整地图（分布式追踪，如 Jaeger/SkyWalking），哪环慢一眼就看出来，还不用在业务代码里插桩。②**新功能有 bug 要回退**——K8s 在升级时会先把旧版本留着（旧 ReplicaSet），DevOps 流水线一键就能退回上一版；再配合"金丝雀"策略：新功能先放 5%/10% 的流量试水，没问题再全量，出问题影响面也小。追踪靠 Mesh，回滚靠 K8s+DevOps，金丝雀降风险。

# 模拟题 10｜遗留单体系统渐进迁移改造大题（25分）
## 背景
某企业运行多年大型单体 ERP 系统，业务不能停机，直接重写风险高。架构师计划逐步迁移至微服务架构，需保证业务连续、数据零丢失、风险可控。

## 问题1（8分）
简述**绞杀者模式、防腐层模式（ACL）、抽象分支模式**三者核心含义以及各自的适用场景。

## 问题2（8分）
从**风险、业务连续性、资源成本**三个角度，对比"一刀切重写""渐进式绞杀迁移""重写式重构"三种迁移方案的优缺点，并给出推荐结论。

## 问题3（9分）
画出渐进迁移架构框图，标注关键组件（单体应用、防腐层、新建微服务、API 网关），并说明数据迁移"双写→对账→切读"三阶段如何保证零丢失。

### 参考答案
**问题1**
【踩分】三模式区分口诀：**流量拦截选绞杀者；新旧模型隔离选防腐层；单体内部组件逐步替换选抽象分支。**
1. **绞杀者模式（Strangler Fig）**：在单体前新建微服务，逐步把单体流量拦截到新服务，最终"绞杀"下线单体；适用整体渐进替换、保业务连续。
2. **防腐层（ACL）**：新旧系统之间加适配层，隔离遗留系统脏模型，防止污染新微服务领域模型（DDD 配套）；适用新旧语义不一致、需隔离。
3. **抽象分支模式（Branch‑by‑Abstraction）**：单体内部先抽抽象接口，旧实现与新微服务实现并存，逐步切换；适用单体内部组件替换、免大停机。

> 💡 **答案解析（讲给小白听）**：老系统像一棵大树，这三个模式是三种"慢慢把它换成新树"的办法，口诀："拦流量选绞杀者、隔模型选防腐层、内部换选抽象分支"。①**绞杀者（Strangler Fig）**——像藤蔓缠树：在老树（单体）前面种新苗（微服务），新来的活慢慢都交给新苗，老树的枝干一点点被取代，最后老树枯死下线。适合"整体渐进替换、不停业"。②**防腐层（ACL）**——新旧系统之间加一层"翻译 + 隔离罩"，挡住老系统那套乱七八糟的数据格式，别让它污染新系统的干净模型（DDD 配套）。适合新旧说法不一致、怕被带坏的场合。③**抽象分支（Branch-by-Abstraction）**——在老树内部先套一个"统一接口"，旧实现和新实现同时挂在接口下，慢慢把流量从旧切到新，全程不用大停机。适合"单体内部某个零件替换"。记住口诀就不会混。

**问题2**
| 方案 | 风险 | 业务连续性 | 资源成本 |
|------|------|-----------|---------|
| 一刀切重写 | 最高（新系统未验证即切换） | 需停机/双跑长 | 一次性投入巨大 |
| 重写式重构 | 高（长周期无收益） | 长周期中断风险 | 最高（人力+时间） |
| 渐进式绞杀 | 最低（逐步验证） | 不停机、灰度切换 | 适中（新旧并存期双倍运维） |
【踩分】推荐结论：选**渐进式绞杀迁移**——风险最低、业务连续、可灰度回滚，符合云原生"架构持续演进"原则。

> 💡 **答案解析（讲给小白听）**：问题 2 是方案选择题，从"风险、业务连续性、成本"三个角度比：①**一刀切重写**——把老房子炸了直接盖新的，新房子没住过人就搬进去，风险最高；还得停业（停机）或新旧同时跑很久；一次性砸钱巨大。②**重写式重构**——边住人边把整栋楼拆了重盖，工期极长、长期没收益，人力和时间成本最高。③**渐进式绞杀**——先在外头盖新楼，一间间把人挪过去，老楼慢慢空出来拆掉，风险最低、不用停业、能灰度回退、成本适中（新旧并存期运维翻倍）。结论必选渐进式，理由就是"风险最低 + 不停业 + 能回退 + 持续演进"。这种迁移题考试默认推渐进式，踩分点在"推荐结论"那句。

**问题3**
【踩分·框图组件链】客户端 → API 网关 →（路由分流）新建微服务 + 单体应用（经防腐层适配）→ 各自数据库。
- 防腐层位于"单体应用 ↔ 新建微服务"之间，转换新旧模型；
- API 网关按请求特征把流量逐步从单体切到微服务。
【踩分·数据迁移三阶段】①**双写**：新旧库同时写，读仍走旧库；②**对账**：定时任务校验双写一致性，差异修复；③**切读**：读流量切到新库，验证无误后停旧写。三阶段保证迁移零数据丢失、业务不停机。

> 💡 **答案解析（讲给小白听）**：问题 3 框图 + 数据迁移。框图可以这样想：顾客（客户端）进门先过保安亭（API 网关），保安按情况把人引到新开的专柜（新建微服务）或老柜台（单体），老柜台和新专柜之间有个"翻译员"（防腐层）帮两边对数据，各自有各自的仓库（数据库）。数据迁移"零丢失"靠三步走，像搬家用：①**双写**——新家旧家同时记账，但还只从旧家取东西看（读写分离，写双份、读旧库）；②**对账**——定时核对两边账本，不一样就改对；③**切读**——确认没问题了，改从新家取东西（读切新库），稳了之后停掉旧家记账。每一步都先验证再往前走，所以数据不会丢、生意不用停。

# 模拟题 11｜云原生架构框图填空专项训练（25分）
## 背景
某互联网公司拟设计一套云原生微服务架构，需补全下列架构分层图，并说明关键组件职责。本题训练"陌生架构图填空"机考高频题型。

## 问题1（12分）
请按请求流向，补全下列云原生架构图缺失的组件（在括号中填入组件名）：
```
客户端 → (   ①   ) → Nginx 反向代理 → (   ②   ) → 注册中心(   ③   )
      → Sidecar 代理(   ④   ) → (   ⑤   微服务 )
      → (   ⑥   Redis 缓存 /   ⑦   MQ 消息队列 ) → (   ⑧   数据库 )
```

## 问题2（7分）
说明 ③ 注册中心 与 ④ Sidecar 代理 各自职责，并指出两者分别属于"南北流量"还是"东西流量"治理。

## 问题3（6分）
若需在架构中补充"可观测性"与"安全防护"，应加入哪些组件（各举 2 例）？

### 参考答案
**问题1**
【踩分】① CDN（静态资源就近缓存）；② API 网关(Gateway，路由/认证/限流)；③ Nacos（或 Eureka/Consul，服务注册发现）；④ Envoy（Istio Sidecar，拦截服务间流量）；⑤ 微服务（业务服务）；⑥ Redis 缓存；⑦ MQ 消息队列（Kafka/RocketMQ）；⑧ 数据库（MySQL/分库分表）。
> 标准填空链：客户端→CDN→Nginx→API网关→注册中心(Nacos)→Sidecar(Envoy)→微服务→Redis/MQ→数据库。

> 💡 **答案解析（讲给小白听）**：问题 1 填空就是默写"一次请求从进门到落库"走过的路，把它想成"寄一封信"：①**CDN**=小区门口的公告栏，固定海报（静态资源）就近看，不进楼；②**Nginx 反向代理**=门房，把信分到不同窗口；③**API 网关**=安检口，查身份、限流；④**注册中心（Nacos）**=楼里的花名册，查"收信人（服务）现在在哪个房间"；⑤**Sidecar（Envoy）**=收信人门口的助理，替他收信；⑥**微服务**=真正处理信的业务员；⑦**Redis/MQ**=临时货架/传话筒（缓存热点、异步传话）；⑧**数据库**=最终存档的档案室。整条链"客户端→CDN→Nginx→网关→注册中心→Sidecar→微服务→Redis/MQ→DB"是机考高频默写，背下来直接套。

**问题2**
【踩分】③ 注册中心：维护服务实例地址，提供**服务注册与发现**，属于**东西流量**支撑（服务间寻址）；④ Sidecar(Envoy)：拦截并治理服务间调用（熔断/路由/mTLS/链路采集），属**东西流量**精细化治理。API 网关(②)才属**南北流量**（客户端↔服务）。

> 💡 **答案解析（讲给小白听）**：问题 2 考"南北流量 vs 东西流量"这对高频概念。先记住方向：①**南北流量**=从外面（客户端/顾客）进来的流量，像"顾客进门"；②**东西流量**=内部（服务之间）互相调用的流量，像"店里各个部门之间互相传话"。回到题目：注册中心（Nacos）管的是"服务之间怎么找到彼此"（部门间传话的通讯录），属东西流量；Sidecar（Envoy）管的是"部门之间传话时的治理"（熔断/加密/追踪），也属东西流量。只有 API 网关是守在门口、管顾客进来的，才属南北流量。一句话：网关管"进门"，注册中心和 Sidecar 管"内部传话"。

**问题3**
【踩分】可观测性：Prometheus（指标）+ SkyWalking/Jaeger（链路）+ ELK（日志）任选 2；安全防护：API 网关认证限流 + Mesh mTLS（零信任）+ K8s RBAC（权限隔离）任选 2。

> 💡 **答案解析（讲给小白听）**：问题 3 补两类组件。①**可观测性**=让你"看清楚系统里面在发生什么"，有三根支柱，任选 2：Prometheus 是"计数器"（指标，比如 CPU、请求数）、SkyWalking/Jaeger 是"监控回放"（链路，一笔请求走了哪些服务）、ELK 是"监控录像"（日志，系统记下的流水账）。②**安全防护**=把不该进的人挡在外面、把内部通信加密，任选 2：API 网关做"查身份证 + 限流"、Service Mesh 做"内部通话加密"（mTLS 零信任）、K8s 做"权限分级"（RBAC，谁能操作什么）。这题是开放题，举对类别即可，记"可观三件套、安全三选二"。

# 模拟题 12｜云原生数据库选型 + 云边协同架构（2025‑2026 新增热点）（25分）
> 🔴 **命题导向**：2025 下半年论文题"论基于云原生数据库的企业信息系统架构设计"直接考查**存算分离**；2025 真题选择题已出现"**边缘 KubeEdge 可在断网时自治**"。本模拟题覆盖这两个新热点。

## 案例背景（一）：云原生数据库选型
某 SaaS 平台原使用 MySQL 主从架构，大促期间需扩容只读副本以应对查询高峰，但每次扩容需**搬运数据、耗时数十分钟**，且主从复制存在**同步延迟**，读副本看不到最新数据；业务还要求存储层多副本容灾。架构师计划迁移到云原生数据库（如 PolarDB / TiDB / Aurora 类）。

## 问题1（9分）
请对比**传统数据库（MySQL 主从）**与**云原生数据库（存算分离架构）**的核心差异，至少从架构核心、扩容方式、读写延迟、容灾四个维度说明。

## 问题2（8分）
结合"大促突发流量"场景，说明云原生数据库为何能实现秒级扩容，并说明其适用边界（什么场景不适合）。

## 案例背景（二）：云边协同（KubeEdge）
该 SaaS 平台需在工厂车间部署边缘节点，做实时质检推理：摄像头在边缘采集图像、本地推理，仅把"异常帧"和聚合结果回传云端；车间网络时好时坏，偶尔断网。

## 问题3（8分）
请说明 KubeEdge 的云端与边缘核心组件，及其**云边协同**机制；并解释为何边缘节点能在**断网时自治**。

---

### 参考答案
**问题1（对比四维度）**
| 对比维度 | 传统数据库（MySQL 主从） | 云原生数据库（PolarDB/TiDB，存算分离） |
|---------|------------------------|--------------------------------------|
| **架构核心** | 计算与存储**耦合在同一节点** | **存算分离**：计算节点无状态，存储节点共享一份数据（分布式存储/共享存储） |
| **扩容方式** | **搬数据**（重做从库、耗时数十分钟） | **增加计算节点（秒级）**，存储按需独立扩展，无需搬数据 |
| **读写分离延迟** | 主从复制存在**同步延迟**，读副本可能看不到最新数据 | **共享存储消除复制延迟**，读节点实时可见最新数据 |
| **容灾能力** | 依赖主从切换，切换有抖动 | **存储层多副本 + 计算层多活**，故障自动转移 |

> 💡 **答案解析（讲给小白听）**：传统数据库像"每个员工配一台带抽屉的办公桌"——计算和抽屉（存储）绑死在一块。云原生数据库把这俩拆开：员工（计算节点）不配抽屉了，大家共用后面一个大档案室（共享存储）。四维差异就好懂了：①**架构**——传统"桌抽屉一体"；云原生"桌抽屉分离"。②**扩容**——传统要加人就得连抽屉带桌一起搬、还得把文件搬过去（搬数据，几十分钟）；云原生直接加张空桌子、连上大档案室就行（秒级，不搬数据）。③**读写延迟**——传统是新员工看的是旧抽屉的复印件，老板刚写的你看不到（主从同步延迟）；云原生大家看同一份档案室，实时一致（无复制延迟）。④**容灾**——传统靠"主桌坏了换备桌"，会卡一下；云原生档案室多副本、桌子多活，坏一张自动换（自动转移）。

**问题2**
- **秒级扩容原理**：计算节点**无状态**，不持有数据，扩容只是"拉起新的计算实例并挂载共享存储"，**无需搬运数据**，故可秒级完成；大促突发流量到来时直接增加计算节点即可。
- **适用边界（不适合）**：① 对**极致单机事务延迟**极度敏感、写放大严重的场景，存算分离的网络存储开销可能比本地盘略高；② 极简单业务、数据量小、无需弹性伸缩时，传统主从更轻量经济。一般**高弹性、读多、需快速扩缩容的互联网/SaaS 业务**最适合。

> 💡 **答案解析（讲给小白听）**：问题 2 接着上面的比喻。为什么能秒级扩容？因为新员工（计算节点）自己不带抽屉、不存文件，加人时只要"拉把空椅子、连上大档案室"就行，完全不用搬文件——这就是"无状态"带来的好处。所以大促来了，直接加椅子，瞬间顶上。但也要辩证说边界：①如果业务对"写一下的速度"极度敏感（极致低延迟、写很多），每次写都要走网络去档案室，比本地抽屉略慢，就不合适；②如果业务很小、基本不用伸缩，传统主从更省事便宜。最适合的是"读多、流量忽高忽低、要快速伸缩"的 SaaS/互联网业务。考这题就是验证你真懂"存算分离为什么快"。

**问题3（KubeEdge 云边协同）**
- **核心组件**：**CloudCore（云端管控）** 负责接收边缘上报、下发应用与配置、设备管理；**EdgeCore（边缘节点）** 在边缘侧管理容器生命周期、本地自治运行；**CloudHub / EdgeHub** 是云↔边双向通信桥梁（长连接），断网时 EdgeHub 缓存指令、恢复后续传。
- **云边协同机制**：云端 CloudCore 经 CloudHub 下发应用/配置，边缘 EdgeCore 经 EdgeHub 接收并执行，状态与事件反向回传，实现"云端管全局、边缘跑业务"。
- **断网自治原理**：EdgeCore 是**本地常驻管控**，断网期间仍能在边缘节点上**独立调度容器、本地运行推理业务**；网络恢复后 EdgeHub 与 CloudHub 重连，补齐缓存的元数据与事件。因此边缘节点具备**弱网自治**能力，满足车间断网不中断质检的要求。

> 💡 **答案解析（讲给小白听）**：问题 3 是"云端总部 + 车间本地"的协同。①**核心组件**——CloudCore 是"云端总部"，负责给下面发指令、收汇报；EdgeCore 是"车间里常驻的现场主管"，在边缘节点上管着本地设备的运行；CloudHub/EdgeHub 是"云和边之间的电话线"（长连接通道）。②**协同机制**——总部(CloudCore)经电话线(CloudHub)下发"用什么模型、怎么跑"的指令，车间主管(EdgeCore)经电话线(EdgeHub)收到后执行，并把现场情况反向汇报，即"云端管全局、边缘跑业务"。③**断网自治**——关键在 EdgeCore 是"常驻在车间的主管"，哪怕电话线断了，他还在车间里，照样能调度设备、本地做质检推理；等电话线恢复，再把断网期间攒下的汇报补传给总部。所以车间断网也不会停产。记"Cloud 管云、Edge 管边、Hub 做通道、EdgeCore 常驻能自治"。

> 💬 **答题话术（云原生数据库）**：云原生数据库采用**存算分离**架构——计算节点无状态、可秒级弹性扩缩；存储节点基于分布式/共享文件系统共享一份数据副本，消除传统主从复制的同步延迟。应对突发流量仅需增加计算节点，无需搬移数据。

> 💬 **答题话术（KubeEdge）**：**CloudCore 管云端、EdgeCore 管边缘、CloudHub/EdgeHub 做云边通道**；边缘节点因 EdgeCore 本地常驻而具备**断网自治**能力，仅上传处理结果/异常帧，实现低时延、省带宽、弱网可用。

# 附：本模块备考答题通用话术模板
1. **方案选型题**：先判"集成旧系统 vs 全新迭代"→ 整合异构/遗留选 SOA/ESB，全新互联网选微服务；迁移题默认推"渐进式"（绞杀者/防腐层/抽象分支三模式按需选）。
2. **问题诊断题**：先定位根因（网络 RTT/锁竞争/连接池/同步链路过长），再对应"限流/熔断/异步/缓存/分库分表/扩容"等机制。
3. **分布式一致性题**：先判 CP（金融/支付）还是 AP（社交/电商读多）→ 强一致用 XA/Seata AT，最终一致用 Saga/事务消息/本地消息表 + 补偿对账；**Saga 复杂长流程点明"编排式"（协调器集中驱动），简单短流程可用"协作式"**。
4. **云原生题**：围绕"K8s 资源层 + Mesh 通信层 + DevOps 交付层"三层分工展开；论述"为何云原生/遵循何原则"用**七大设计原则（服弹可观韧，自动零演进）**作答；发布策略默认推**金丝雀/渐进式**；涉及安全加**零信任 mTLS + RBAC**；涉及自主可控加**信创国产替代 + 国密 SMx**。
5. **云原生数据库题**：默认答**存算分离**——计算节点无状态、秒级扩缩，存储节点共享一份数据、消除主从复制延迟；突发流量只加计算节点、不搬数据；传统 MySQL 主从"搬数据慢、有同步延迟、依赖主从切换"。
6. **云边协同 / KubeEdge 题**：**CloudCore 管云端、EdgeCore 管边缘、CloudHub/EdgeHub 做云边通道**；边缘因 EdgeCore 本地常驻具备**断网自治**，仅上传结果/异常帧，实现低时延、省带宽、弱网可用。
7. **架构图填空题**：默写标准链 客户端→CDN→Nginx→API网关→注册中心(Nacos)→Sidecar(Envoy)→微服务→Redis/MQ→数据库；区分南北（网关）与东西（Mesh/注册中心）流量。
