## 1.2 近年真实案例题回顾（2024–2026 真题要点）
> ⚠️ 以下为公开备考资料/模拟卷中整理的真实或高仿真题要点（部分源自轩辕软考室、希赛、软考课堂、人人文库等公开整理），用于把握命题方向与提问口径，具体以当次官方试卷为准。

### 真题 1 · 基于微服务架构的统一网关与权限控制设计（高仿/模拟真题）
**背景**：企业协同办公系统（Spring Cloud + K8s），多服务暴露独立端口、各自认证、高频接口瓶颈、配置变更需重启、无统一日志链路。
**考查问题**：
1. 微服务引入 API 网关的目的与核心功能
2. 设计统一身份认证与权限控制机制（多服务共享认证）
3. 高频接口（文件上传/下载）的网关高可用与性能优化
4. 引入配置中心保障灵活配置与安全
5. 基于 API 网关的综合安全治理方案
**考点**：API 网关功能清单、OAuth2/JWT + RBAC/ABAC、网关限流/CDN/分片上传、Nacos/Apollo 配置中心、安全治理（认证/权限/限流/审计/加密）。

### 真题 2 · 大型制造企业 ESB + API 网关集成（信息孤岛治理）
**背景**：20+ 独立系统（ERP/CRM/MES/WMS），点对点集成形成 190 条链路，数据不一致。
**考查问题**：分析"信息孤岛/点对点混乱/数据不一致"根因；设计 ESB + API 网关分层集成方案（数据/应用/业务/界面四层）；从数据架构解决信息孤岛。
**考点**：ESB 功能与解耦价值、集成层次与技术选型、主数据管理/数据中台/ETL+数据湖。

### 真题 3 · 银行核心系统"单元化 + 分布式"架构（2025 上半年真题方向）
**背景**：城商行核心系统，每单元承担 200 万账户，单元内账户/交易/支付三微服务，MySQL Group Replication 三节点（RPO=0）。跨单元转账平均 2.5s（单单元 200ms）。
**考查问题**：
1. 分析跨单元转账耗时高的根因（≥3 点）
2. 设计"账户归属单元"与"事务一致性"平衡的优化方案（不改 RPO），给时序
**参考答案要点**：
- **根因**：①跨单元两阶段提交（XA prepare/commit 网络 RTT 翻倍）；②单元间公网 SSL 加密 RTT 放大（20ms→80ms）；③热点账户行锁竞争，跨单元无法用本地 MVCC；④幂等检查在 DB 层增加 SELECT。
- **优化（Saga 事务 + 异地单元记账 + 日终清算）**：发起方本地扣减并插"转出事件表(INIT)"→ 发 Kafka → 接收方本地增加并插"转入事件表"→ 回 ACK → 发起方更新事件 SUCCESS；超时未 ACK 则定时任务冲正/Compensate；日终批量对账。RPO 仍=0（事件表在同一 MySQL 组复制）。
- **【踩分·拓展】Saga 实现方式**：银行跨单元转账属复杂长流程，应点明采用**编排式 Saga**（协调器集中驱动），事件表+Kafka 只是其底层载体；并强调"事件表与业务表同本地事务提交"是 RPO=0 根本保证。
**考点**：分布式事务（Saga vs XA）、消息队列最终一致、事件表/对账补偿、RPO/RTO、Saga 编排式。

### 真题 4 · 电商云原生架构迁移（2025 上半年真题方向）
**背景**：电商单体架构，部署慢、故障恢复慢、资源利用率低，迁移至云原生，目标日均 5000 万请求、峰值 QPS 10 万、故障恢复<15min、资源利用率>70%。
**考查问题**：
1. 对比"一刀切/渐进式/重写式"三种迁移方案（风险/成本/业务连续性三维），推最优
2. Service Mesh 相较传统 API 网关的优势，及需重点关注的 4 项服务治理功能
3. 设计"检测—隔离—恢复"三阶段容灾方案
**参考答案要点**：
- **方案对比**：一刀切风险最高、重写式成本最高且需停机；**渐进式**复用现有系统、灰度/金丝雀/蓝绿保持连续，三维最佳 → 推渐进式。
- **Mesh 优势**：网关管南北向，Mesh 管东西向（服务间），提供非侵入式、更细粒度流量治理；重点关注：流量管控（限流/熔断/路由）、通信安全（mTLS）、可观测性（指标/链路）、超时重试。
- **容灾**：检测（存活/就绪探针 + 心跳/监控告警）→ 隔离（熔断驱逐故障 Pod）→ 恢复（HPA 自动扩容 + 滚动更新/一键回滚 + 多副本）。
**考点**：迁移策略论证、Service Mesh 核心能力、容灾三阶段。

### 真题 5 · 微服务集群高并发雪崩与分布式事务（2025 真题方向）
**背景**：电商微服务（Nacos + Gateway + OpenFeign + RocketMQ + MySQL 分库分表 + Redis + K8s + Prometheus/SkyWalking）。问题：①库存超卖（大促瞬时流量，乐观锁仍回滚/超卖）；②订单与库存异步扣减偶尔不一致（订单成功库存失败）；③营销服务慢拖垮订单服务（雪崩）。
**考查问题**：
1. 结合 Redis + MQ 设计高性能库存扣减方案并保证 DB 一致性
2. 说明"本地消息表/事务消息"如何保证订单创建与库存扣减原子性
3. 解释雪崩效应，除舱壁外还有哪些防雪崩机制，结合网关/调用配置
**参考答案要点**：
1. **库存方案**：Redis 预加载库存（SET stock NX）；Lua 脚本原子执行"检查-扣减-记录"；库存为 0 直接返回；异步通过 MQ（Kafka/RocketMQ）将扣减结果同步 DB（仅成功订单）；DB 层乐观锁（版本号）兜底；定时对账补偿。
2. **事务消息/本地消息表**：本地事务与消息表同库写入（同事务）→ 异步投递消息 → 下游消费处理 → 确认/重试；保证"订单创建成功"与"库存扣减"要么都成功、失败可补偿的最终一致。
3. **雪崩**：下游故障导致上游线程阻塞、连锁扩散。【踩分】必写"雪崩定义 + 故障传播路径"；防雪崩机制：熔断（失败率阈值切断链路）、降级（返回预设提示）、超时（短超时快速失败）、重试+退避、限流（网关/Sentinel 限流）——5 条措施中任写 4 条即可满分。配置：Gateway/Sentinel 设失败率熔断 + 订单服务 5s 超时 + 2 次重试 + 对营销服务限流。
**考点**：Redis 原子扣减 + Lua + MQ 最终一致、分布式事务方案、雪崩防护体系。

### 真题 6 · 宇航装备分布式综合化电子系统故障检测（希赛真题）
**背景**：四层层次化架构（模块支持层/OS 层/分布式中间件层/功能应用层），故障检测构建在分布式中间件内，用心跳检测/超时探测实现故障检测器。
**考查问题**：说明心跳检测与超时探测的基本原理及特点；判断若干故障（应用除零/看门狗/任务超时/网络诊断/BIT/堆栈溢出/OS 异常/模块掉电）分别属哪类监控器范围；说明数据驱动故障分析方法。
**考点**：心跳/超时探测、分布式监控器职责划分、故障诊断与智能决策库。

# 模拟题 1｜单体电商系统改造微服务（25分）
## 案例背景
某传统电商平台，使用单体架构，所有业务模块（用户、商品、订单、支付、库存）部署在一台应用服务器。随着业务增长，系统迭代速度慢；每次发布需要整体重启；促销高峰期经常出现卡顿；团队人数扩张，多个开发组代码合并冲突严重。架构师计划将单体系统改造为微服务架构。

## 问题1（8分）
请简述将单体电商拆分为微服务架构的主要优点。

## 问题2（9分）
改造为微服务之后，系统会出现一系列新的技术挑战，请列出4项主要问题，并给出对应的解决思路。

## 问题3（8分）
在微服务架构中，需要建设完整的服务治理体系。请说明微服务治理平台至少包含哪些核心组件，每个组件的作用。

---

### 参考答案
**问题1**
1. 服务独立部署，单个模块升级发布不会影响整个系统；
2. 按照业务域拆分，团队可以并行开发，减少代码冲突；
3. 故障隔离，单一服务故障不会造成全站瘫痪；
4. 可针对高负载服务独立弹性扩容，资源利用率提升；
5. 技术栈解耦，不同微服务可按需选用合适技术方案。

**问题2（问题+对策）**
1. **分布式事务、数据一致性问题**：采用Saga、可靠消息队列实现最终一致性；
2. **远程调用失败、服务雪崩风险**：引入熔断、降级、超时重试策略；
3. **服务实例地址动态变化、调用方难以感知**：搭建注册中心实现服务注册发现；
4. **运维监控难度上涨**：建设指标监控、日志、分布式链路追踪，实现可观测。

**问题3**
1. **注册中心**：保存所有微服务实例地址，实现服务注册与发现；
2. **配置中心**：集中管理配置，配置与代码分离，动态生效；
3. **容错治理组件**：熔断、降级、限流，保障服务韧性；
4. **分布式链路追踪组件**：追踪请求全链路，定位跨服务性能瓶颈；
5. **监控告警平台**：采集各项性能指标，异常告警。

# 模拟题 2｜SOA遗留系统升级（25分）
## 背景
某银行内部有多套异构业务系统，早年基于SOA+重型ESB企业服务总线完成系统集成。随着业务迭代，ESB单点压力越来越大，所有服务之间调用流量全部经过总线，总线修改升级会造成所有业务中断，扩展困难。架构团队计划逐步迁移到微服务架构，将重型ESB替换。

## 问题1（7分）
简述ESB（企业服务总线）在原有SOA架构中的主要功能。

## 问题2（9分）
请对比SOA架构（ESB）与微服务架构的差异，并说明为什么重型ESB不再适合新的互联网业务。

## 问题3（9分）
迁移后使用轻量API网关替代ESB，请说明API网关适合承担哪些工作，哪些东西不应该放到网关。

### 参考答案
**问题1**
1. 协议转换，屏蔽异构系统通信协议差异；
2. 消息路由，实现服务请求转发；
3. 数据格式转换；
4. 服务编排，组合多个服务完成业务流程；
5. 统一安全认证、日志审计、异常处理。

**问题2**
差异要点：
1. ESB属于重型集中式总线；微服务去掉集中总线，采用轻量点对点通信；
2. SOA服务粒度粗；微服务拆分粒度更细；
3. SOA偏向遗留异构系统集成；微服务面向快速迭代互联网业务。
ESB缺点：单点瓶颈；总线成为性能卡点；升级运维风险高；扩展困难。

**问题3**
适合网关：南北流量路由、负载均衡、客户端认证授权、限流、灰度发布、日志采集。
不适合网关：复杂业务编排、重量级数据转换；这类逻辑下沉至后端微服务。

# 模拟题3｜云原生K8s容器改造案例（25分）
## 背景
某互联网公司现有业务系统部署在虚拟机上，遇到以下痛点：新环境部署周期长，开发‑测试‑生产环境不一致；促销高峰流量突增，无法快速扩容；版本发布停机时间长。架构师计划进行云原生改造，采用Docker + Kubernetes集群部署。

## 问题1（8分）
简述Docker容器技术可以解决原有虚拟机部署模式下的哪些痛点？

## 问题2（8分）
云原生改造中强调应用无状态，请解释什么是无状态应用，改造时需要把哪些数据移出容器本地？

## 问题3（9分）
采用Kubernetes平台，请说明HPA、Deployment、Service三个核心资源对象各自作用。

### 参考答案
**问题1**
1. 将应用和依赖一起打包成镜像，解决环境不一致问题；
2. 容器启动速度远快于虚拟机，部署发布效率提升；
3. 资源开销更小，单机可以部署更多实例；
4. 镜像版本化管理，便于版本回滚。

**问题2**
无状态：应用实例不保存会话、业务数据；任意实例可以随时销毁重建，实例之间无差异。
移出本地：Session会话、缓存数据、业务文件、持久化日志；放置Redis、对象存储、数据库。

**问题3**
1. Deployment：管理无状态应用Pod副本，负责滚动升级、版本回滚；
2. Service：一组Pod的统一访问入口，提供负载均衡；
3. HPA（水平自动扩缩）：依据CPU/QPS等指标，自动增减Pod副本数量。

# 模拟题4｜Service Mesh 服务网格（Istio）新热点（25分）
## 背景
企业已经上线了20余个微服务，使用Java、Go、Python多语言开发。目前熔断、限流、链路追踪治理逻辑需要在每个项目业务代码重复开发，多语言SDK维护成本很高。架构师决定引入Istio服务网格实现服务治理。

## 问题1（8分）
什么是Sidecar代理模式？说明服务网格的数据平面与控制平面各自职责。

## 问题2（8分）
简述采用Service‑Mesh治理微服务相比传统SDK埋点方案，有哪些优点？

## 问题3（9分）
请列出至少3项基于服务网格可以实现的服务治理功能。

### 参考答案
**问题1**
Sidecar是部署在每个微服务Pod内、和业务容器伴生运行的代理进程，拦截所有进出业务服务的网络流量。
- **数据平面（Envoy）**：实际执行流量治理，熔断、限流、加密通信；
- **控制平面（Istio Pilot）**：统一下发治理配置规则，不转发业务流量。

**问题2优点**
1. 治理逻辑与业务代码解耦，**业务代码零侵入**；
2. 多语言微服务统一治理方案，不需要为不同语言开发SDK；
3. 治理规则可以动态下发，不需要重启业务服务；
4. 流量观测统一收集。

**问题3治理功能**
流量路由、灰度/金丝雀发布、熔断降级、限流、mTLS双向加密通信、分布式链路追踪、访问权限控制。

# 模拟题 5｜微服务雪崩故障排查案例（25分）
## 背景
某微服务系统包含用户、订单、库存、支付四个服务。大促期间，库存服务响应变慢，大量订单服务请求库存接口超时，订单服务线程池耗尽，继而用户服务调用订单服务全部失败，整个系统近乎瘫痪。事后复盘，系统没有任何限流熔断机制。

## 问题1（8分）
请解释什么是微服务雪崩效应，描述本案例故障传播路径。

# 模拟题 7｜跨单元转账的分布式事务优化（银行核心系统）（25分）
## 背景
某城商行核心系统采用"单元化+分布式"架构，每单元承担 200 万账户，单元内账户/交易/支付三微服务，MySQL Group Replication 三节点（RPO=0）。上线后跨单元转账平均耗时 2.5s（单单元仅 200ms），业务要求不改变 RPO。

## 问题1（8分）
请分析跨单元转账耗时高的根因，给出至少 3 点。

## 问题2（9分）
提出一种基于"账户归属单元"与"事务一致性"平衡的优化方案（不改 RPO），说明核心思路并给出转账时序（文字描述）。

## 问题3（8分）
该方案如何保证"转账创建成功"与"对方单元入账"的最终一致？请说明 Saga 事务 + 消息队列 + 补偿/对账的实现思路。

### 参考答案
**问题1**
1. 跨单元需两阶段提交（XA），prepare/commit 网络 RTT 翻倍；
2. 单元间公网 SSL 加密，RTT 放大（20ms→80ms）；
3. 热点账户行锁竞争，跨单元无法利用本地 MVCC，锁等待概率高；
4. 幂等检查在 DB 层，增加一次 SELECT。

**问题2**
采用"异地单元记账 + 日终清算"+ Saga 长事务。时序：①发起方单元本地扣减，插"转出事件表"(INIT)；②发 Kafka 消息至接收方单元；③接收方消费后本地增加金额，插"转入事件表"，回 ACK；④发起方收 ACK 后更新事件 SUCCESS；⑤超时未 ACK → 定时任务冲正，发 Compensate 消息；⑥日终批量对账，差异人工介入。RPO 仍=0（事件表在同一 MySQL 组复制，本地事务提交即持久化）。

**问题3**
【踩分】Saga 将跨单元转账拆为本地事务链（发起方扣减 + 接收方入账），每步有对应补偿动作（冲正）；通过 Kafka 可靠投递 + 事务消息/本地消息表保证消息不丢；下游消费确认后回 ACK；超时/失败触发补偿（冲正消息）+ 日终对账兜底，实现最终一致性，满足 RPO=0。
【踩分·拓展】本题应采用**编排式 Saga（Orchestration）**：由中央 Saga 协调器（状态机）集中驱动"扣减→通知→入账→确认"各步，状态可见、补偿顺序可控、强制幂等——比协作式（无中心、仅靠事件互相触发）更适配银行转账长流程；协作式仅适合简单短流程。
【踩分·关键论证】RPO=0 的**根本保证**是"转出/转入事件表与业务表在**同一本地事务**中提交"（MySQL 组复制同步到三节点），而非依赖 MQ 可靠性；即便 Kafka 投递延迟或丢消息，本地已持久化的事件可由定时任务重投/冲正，数据零丢失。

# 模拟题 8｜高并发秒杀系统的库存与一致性设计（25分）
## 背景
某电商平台大促秒杀场景，瞬时流量巨大，原有"DB 乐观锁"方案因大量回滚导致连接池耗尽且仍有少量超卖。系统采用 Redis 缓存热点库存、RocketMQ 异步扣减、MySQL 持久化。

## 问题1（8分）
请结合 Redis 与消息队列，设计高性能库存扣减方案，描述流程并说明如何保证与数据库的一致性。

## 问题2（9分）
说明如何利用 Redis 的原子操作（SET NX / Lua 脚本）防止超卖，并说明异步对账的作用。

## 问题3（8分）
针对"订单创建成功但库存扣减失败"的不一致问题，请说明"事务消息/本地消息表"的实现思路，保证两操作的原子性。

### 参考答案
**问题1**
1. 秒杀前将库存加载到 Redis（SET stock N NX）；
2. 用户下单时通过 Lua 脚本原子执行"检查库存>0—扣减—记录订单"，保证原子性；
3. 库存为 0 直接返回失败，避免击穿 DB；
4. 扣减成功后异步通过 RocketMQ 将结果同步 MySQL（仅处理成功订单）；
5. DB 层乐观锁（版本号）兜底防超卖；
6. 定时对账任务核对 Redis 与 DB 库存差异并补偿修正。

**问题2**
Lua 脚本在 Redis 单线程内执行，保证"检查-扣减"不可分割，从根源防超卖；SET NX 保证库存初始化唯一。异步对账：定时核对 Redis 与 DB 库存，发现差异（如 MQ 消费失败/网络抖动导致的不一致）通过补偿任务修正，作为最终一致性的兜底保障。

**问题3**
本地消息表——订单创建与"库存扣减消息"同库同事务写入（订单表 + 消息表），事务提交后异步投递 MQ；下游库存服务消费并扣减，成功后确认；失败/超时重试。事务消息（RocketMQ）——消息中间件保证消息可靠投递与本地事务的原子性，两操作要么都成功、失败可补偿重试，实现最终一致。

针对"调用链路复杂、故障定位难"与"新功能出 bug 需快速回滚"，分别说明应对方案及所用技术。

# 模拟题 10｜遗留单体系统渐进迁移改造大题（25分）
## 背景
某企业运行多年大型单体 ERP 系统，业务不能停机，直接重写风险高。架构师计划逐步迁移至微服务架构，需保证业务连续、数据零丢失、风险可控。

## 问题1（8分）
简述**绞杀者模式、防腐层模式（ACL）、抽象分支模式**三者核心含义以及各自的适用场景。

## 问题2（8分）
从**风险、业务连续性、资源成本**三个角度，对比"一刀切重写""渐进式绞杀迁移""重写式重构"三种迁移方案的优缺点，并给出推荐结论。

## 问题3（9分）
画出渐进迁移架构框图，标注关键组件（单体应用、防腐层、新建微服务、API 网关），并说明数据迁移"双写→对账→切读"三阶段如何保证零丢失。

### 参考答案
**问题1**
【踩分】三模式区分口诀：**流量拦截选绞杀者；新旧模型隔离选防腐层；单体内部组件逐步替换选抽象分支。**
1. **绞杀者模式（Strangler Fig）**：在单体前新建微服务，逐步把单体流量拦截到新服务，最终"绞杀"下线单体；适用整体渐进替换、保业务连续。
2. **防腐层（ACL）**：新旧系统之间加适配层，隔离遗留系统脏模型，防止污染新微服务领域模型（DDD 配套）；适用新旧语义不一致、需隔离。
3. **抽象分支模式（Branch‑by‑Abstraction）**：单体内部先抽抽象接口，旧实现与新微服务实现并存，逐步切换；适用单体内部组件替换、免大停机。

**问题2**
| 方案 | 风险 | 业务连续性 | 资源成本 |
|------|------|-----------|---------|
| 一刀切重写 | 最高（新系统未验证即切换） | 需停机/双跑长 | 一次性投入巨大 |
| 重写式重构 | 高（长周期无收益） | 长周期中断风险 | 最高（人力+时间） |
| 渐进式绞杀 | 最低（逐步验证） | 不停机、灰度切换 | 适中（新旧并存期双倍运维） |
【踩分】推荐结论：选**渐进式绞杀迁移**——风险最低、业务连续、可灰度回滚，符合云原生"架构持续演进"原则。

**问题3**
【踩分·框图组件链】客户端 → API 网关 →（路由分流）新建微服务 + 单体应用（经防腐层适配）→ 各自数据库。
- 防腐层位于"单体应用 ↔ 新建微服务"之间，转换新旧模型；
- API 网关按请求特征把流量逐步从单体切到微服务。
【踩分·数据迁移三阶段】①**双写**：新旧库同时写，读仍走旧库；②**对账**：定时任务校验双写一致性，差异修复；③**切读**：读流量切到新库，验证无误后停旧写。三阶段保证迁移零数据丢失、业务不停机。
