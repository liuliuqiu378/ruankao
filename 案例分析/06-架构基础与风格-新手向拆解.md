**一句话概括全章**：
> 架构设计 = **选一种结构（风格）** 去 **满足一组目标（质量属性）**，并且能 **说清楚这么选的代价是什么（评估/权衡）**。

**考试的本质**：命题人不是要你背出"微服务有 5 条优点"，而是要你**拿着一个具体项目背景，做出有依据的选择，并且承认这个选择的代价**。
只写优点不写代价 —— 这是新手丢分的第一大原因，没有之一。

# 第 0 章 · 先建立直觉（零基础也能看懂）

这一章**不谈任何考试**，只用生活里的例子，让你对三个核心概念有"手感"。
有了手感之后，后面所有的表格都会变得好记。

## 0.1 一句话：这一章在解决什么问题？

假设你要盖一栋楼。开工前有三类问题必须先回答：

| 问题 | 盖楼的例子 | 对应软件里的概念 |
|------|-----------|-----------------|
| ① 用什么结构？ | 砖混？框架？钢结构？装配式？ | **架构风格** |
| ② 要达成什么指标？ | 能抗几级地震？隔音多少分贝？几层？ | **质量属性** |
| ③ 这方案行不行、代价是什么？ | 钢结构结实但贵；框架便宜但跨度有限 | **架构评估 / 权衡** |

软件完全一样：

- **架构风格** = 系统的"结构类型"。选它，等于选定了"零件怎么切分、零件之间怎么说话、有什么规矩"。
- **质量属性** = 评价系统好坏的"指标表"。注意：**它不是功能**（不是"能不能下单"），而是"**下这个单要多久、会不会失败、能不能防住黑客、以后加功能好不好加**"。
- **架构评估** = 拿着质量属性这把尺子，去量你选的结构，找出"哪里好、哪里糟、哪个决定最危险"。

> 💡 **新手第一个要建立的认知**：
> **架构里没有"最好"，只有"最合适"。** 任何让某个指标变好的设计，几乎一定会让另一个指标变差。
> 考试所有高分的答案，都在讲**权衡**。

## 0.2 直觉一：架构风格 = 建筑的"结构类型"

下面 12 个比喻，请全部看完。**后面所有风格的原理，都是这些比喻的"技术翻译"**。

| 风格 | 生活比喻 | 一句话记住它 |
|------|---------|-------------|
| **主程序-子程序** | **一个人干到底**：老板自己写好了完整剧本，手下的手脚完全听他指挥，没有自主权 | 一个大脑，全部紧耦合 |
| **面向对象** | **每个人是自己领域的负责人**：每人管自己的资料柜，需要协作时互相"发消息" | 各自封装，消息协作 |
| **分层架构** | **公司层级汇报**：员工 → 主管 → 总监 → 老板，只能一层层往上报告，不能越级 | 上下层，单向依赖 |
| **管道-过滤器** | **工厂流水线**：原料 → 切割 → 打磨 → 喷漆 → 成品，每个工位只干一件事，干完往下传 | 数据像水一样流过去 |
| **事件驱动（隐式调用）** | **小区广播喇叭**：喊一嗓子"3 号楼停水了"，谁关心谁自己去处理，喊的人**根本不知道谁会响应** | 我喊我的，你爱听不听 |
| **仓库（知识库）** | **图书馆**：书全放中央书库，**读者自己决定什么时候去借**。书库不会主动叫你来 | 共享数据，读者主动 |
| **黑板** | **专家会诊**：一块白板，多位专家轮流上前面写、改；**主持人根据当前进度决定叫谁上**，专家之间互不说话 | 共享数据 + 主动调度 |
| **C2** | **极严格的大公司**：任何两个部门**不准直接沟通**，所有沟通必须走"行政中转站" | 禁止直接调用 |
| **SOA** | **商业街 + 统一物流调度中心(ESB)**：每家店都比较"大"，统一通过调度中心收发货物 | 大服务 + 中央总线 |
| **微服务** | **商业街 + 每家店独立经营**：每家店小、有自己的小仓库（独立数据库），随时能换招牌、能单独装修 | 小服务 + 独立数据库 |
| **解释器（虚拟机）** | **同声传译**：你说一句，他翻一句、执行一句，**不是一次性全部翻译完再去执行** | 边解释边执行 |
| **基于规则的系统** | **一堆 if-then 规则引擎**：把业务规则抽出来，改规则不改代码 | 规则外置，可配置 |

### 🔑 三组最重要的对比（比喻版）

这三组是考试最高频的辨析点，用比喻记最牢：

**① 仓库 vs 黑板（最高频错题）**
> - **仓库 = 图书馆**：书放那儿，**读者自己去取**。管理员（仓库）不主动叫你。
> - **黑板 = 专家会诊**：白板放那儿，**主持人主动点名**让哪个专家上场。专家之间不互相说话，都只看白板。
>
> **口诀**：`仓库存数据，别人主动读；黑板存数据，主动喊人干活。`
>
> **判断关键**：看**控制权在谁手里**。
> - 题干说"各模块自己决定何时读写" → 仓库
> - 题干说"系统根据进度自动调度各模块"、"多个知识源协同求解" → 黑板

**② 事件驱动 vs C2**
> - **事件驱动 = 小区广播**：可以广播，但你俩私底下也可以直接打电话（**没有强制约束**）。
> - **C2 = 严格公司**：**强制禁止**任何两个部门直接沟通，必须走中转站。
>
> **判断关键**：题干有没有说"**禁止构件之间直接调用 / 所有通信必须经过连接件**"。有 → C2。

**③ SOA vs 微服务**
> - **SOA = 商业街 + 统一物流中心**：店大，靠 ESB（企业服务总线）中转。**目的：把企业里各种老系统（异构系统）串起来**。
> - **微服务 = 商业街 + 各店独立**：店小，**每家店有自己的仓库（独立数据库）**。**目的：快速迭代、独立部署**。
>
> **判断关键**：有没有 **ESB 总线** → SOA；有没有 **独立数据库 + 独立部署** → 微服务。

## 0.3 直觉二：质量属性 = 买房看的那张"指标表"

买房子时你不会只问"能不能住人"（这是**功能**），你会问一堆"住得怎么样"的问题（这些就是**质量属性 / 非功能需求**）：

| 买房时你问的 | 软件里对应的质量属性 |
|-------------|-------------------|
| 上班通勤要多久？电梯快不快？ | **性能**（响应时间、吞吐量） |
| 会不会经常停水停电？坏了多久能修？ | **可用性**（能正常用的时间比例） |
| 门禁、防盗窗、监控怎么样？ | **安全性** |
| 以后想改户型、加个房间好不好改？ | **可修改性**（含可扩展性、可移植性） |
| 验收的时候好不好验？问题好不好查？ | **可测试性** |
| 老人小孩住着顺不顺手？ | **易用性** |
| 家里人口变多了，能不能加房间/换大房子？ | **可伸缩性**（Scalability） |

### 🔑 新手必须分清的两组词

**第一组：性能 vs 可伸缩性（超高频混淆）**

> - **性能**：**现在**快不快。（一个人跑 100 米要几秒）
> - **可伸缩性**：**人多了之后**还快不快。（再来 10 个人一起跑，能不能靠加跑道维持原来的速度）
>
> 📌 **考试口径**：可伸缩性是**可修改性的子属性**（因为"能扩展"本质上是一种修改能力）。
> 但答题时，如果题干说的是"**用户量增长 300%，系统可以通过增加节点支撑**"，**优先直接写「可伸缩性」** —— 这比写"可修改性"更精准，更贴阅卷踩分点。

**第二组：可用性 vs 可靠性（超高频混淆）**

> - **可靠性(Reliability)**：**不出故障**的能力。关注的是"故障发生的频率"。→ 指标：**MTBF**（平均无故障工作时间，越长越好）
> - **可用性(Availability)**：**出了故障还能用**的能力。关注的是"能用时间的比例"。→ 指标：**MTBF / (MTBF + MTTR)**，MTTR 是平均修复时间，越短越好
>
> 一句话：**可靠性 = 少坏；可用性 = 坏了也能快速恢复、不影响使用。**
>
> 📌 **考试口径**：如果题干写"**连续运行 720 小时无故障**"看起来像可靠性，但答案通常给**可用性**——因为这类题考查的是"系统持续提供服务的能力"这一整体指标。**具体以题干强调的重点为准。**

## 0.4 直觉三：架构评估 = 一份"验房报告"

验房师看完房子会给你一份报告，里面有四种"结论"。这四种结论就是 ATAM 的四大核心概念：

| 验房报告里的话 | ATAM 概念 | 含义 |
|---------------|----------|------|
| "这面墙的厚度，直接决定隔音效果" | **敏感点** | 某个**设计决策**会显著影响**一个**质量属性 |
| "加厚这面墙，隔音好了，但房间面积小了" | **权衡点** | 某个**设计决策**让**一个变好、另一个变差**（至少两个属性） |
| "这根承重梁被打了个洞，有隐患" | **风险点** | 某个设计决策**存在潜在负面后果** |
| "这个防水做法很成熟，没问题" | **非风险点** | 某个设计决策**不会带来负面影响** |

### ⚠️ 头号丢分点（现在就记住，别等到考前）

> **敏感点 / 权衡点 / 风险点 指的是「架构决策」，不是「质量属性指标」！**
>
> ❌ 错误写法："响应时间 0.5 秒是性能的敏感点。"
> - 错在哪？"响应时间 0.5 秒"是一个**指标**（质量属性的度量），它本身不是决策。
>
> ✅ 正确写法："**缓存策略**（或：CDN 节点数量、服务调用链路长度）是性能的敏感点，它显著影响系统响应时间能否达到 0.5 秒。"
>
> **记忆法**：**指标是"考试分数"，架构决策才是"学习方法"。** 考试问的是"哪个学习方法对分数影响最大"，不是"分数是不是学习方法"。

### 第二个高频丢分点

> **权衡点必须"一升一降"，至少涉及两个质量属性。**
> 只写收益、不写代价 → 那叫"优点"，不叫"权衡点"，**直接丢分**。
>
> ✅ 标准句式：`该决策提升了【A属性】，但降低了【B属性】，因此是 A 与 B 之间的权衡点。`

## 0.5 三条直觉拼起来 = 试题一的完整答题链条

把这三条直觉串起来，你就得到了考试时大脑里应该跑的**完整流水线**：

```
读到题干背景（比如：某电商系统要重构）
        ↓
【第1步】这系统现在/打算用什么结构？  →  识别架构风格

```

# 第 1 部分 · 原理篇：架构风格

> 学这部分的目标：**看到一段系统描述，能立刻说出"这是什么风格"，并说出它的优点、缺点、适用与不适用场景。**

---

## 1.1 到底什么是"架构风格"？（三个关键词）

官方定义背下来（填空题可能直接考）：

> **架构风格** = 描述特定应用领域中系统组织的**惯用模式**，它定义了：
> ① **构件（Component）** 是什么 —— 系统被切成哪些"零件"
> ② **连接件（Connector）** 是什么 —— 零件之间"怎么说话"（调用？消息？共享数据？）
> ③ **约束（Constraint）** 是什么 —— 有哪些"规矩"（能不能跨层？能不能直接调用？）

### 用"公司"来翻译这三个词

| 术语 | 人话 | 公司比喻 |
|------|------|---------|
| 构件 | 系统被切成的功能块 | 各个部门 |
| 连接件 | 构件之间的交互机制 | 部门之间怎么沟通（开会？邮件？共享文档？） |
| 约束 | 必须遵守的规矩 | 公司制度（能不能越级？能不能私下交易？） |

**所以"选架构风格" = 决定"部门怎么切 + 怎么沟通 + 有什么规矩"。**

### 为什么要"复用"现成的风格，而不是自己发明？

因为每种风格都是前人踩坑总结出来的**已知副作用清单**。
用了微服务，你不用等到上线才知道"分布式事务很麻烦"——**这是写在你选型说明书里的已知代价**。
考试考的就是：**你能不能提前说出这些已知代价。**

---

## 1.2 教材五大类（先分堆，再认脸）

教材把风格分成 5 大类。**考试时先判断大类，再锁定具体风格**，比直接猜快得多。

| 大类 | 包含的风格 | 一句话特征 | 题干关键词（看到就往这想） |
|------|-----------|-----------|--------------------------|
| **① 数据流风格** | 批处理序列、**管道-过滤器** | 数据像水一样流过去，一步步被加工 | 数据流、过滤器、管道、ETL、一步步处理、流水线 |
| **② 调用/返回风格** | **主程序-子程序**、**面向对象**、**分层** | **显式调用**：A 明确知道 B，A 喊 B，B 干完返回结果 | 显式调用、上下层、面向对象封装、层次化 |
| **③ 独立构件风格** | **进程通信**、**事件驱动（隐式调用）** | 构件各自独立跑，通过**消息/事件**沟通，**没有中央指挥** | 各构件独立运行、事件通信、发布-订阅、隐式调用 |
| **④ 虚拟机风格** | **解释器**、**基于规则的系统** | 用软件"模拟"一种执行机制 | 解析用户代码、规则引擎、解释执行、脚本、DSL |
| **⑤ 仓库风格** | **数据库系统**、**黑板系统**、超文本系统 | 有个**中央共享数据**，大家围着它转 | 共享数据存储、中央数据节点、多模块访问同一数据 |

### 🔑 分类的核心判据：看"谁在控制"

这是最快的大类判断法：

```
问自己一个问题：构件之间，是"我直接喊你" 还是 "我不知道谁在听"？
│
├── 我明确知道要调用谁，等它返回结果  →  调用/返回风格（分层、主子程序、面向对象）
│
├── 我喊一声/发个事件，谁爱听谁听，我不等  →  独立构件风格（事件驱动、进程通信）
│
├── 数据在流动，每个环节加工一下再传下去  →  数据流风格（管道-过滤器、批处理）
│
├── 大家不互相说话，都去读写同一个中央数据
│      ├── 中央数据是被动的，谁想用谁自己来  →  仓库
│      └── 中央数据会主动调度大家来干活      →  黑板
│
└── 系统在执行"用户写的代码/规则"，而不是执行编译好的程序 → 虚拟机风格（解释器/规则系统）
```

### ⚠️ 丢分提醒：大类和小类的关系要会"两套说法"

同一个风格，考试可能从**两个角度**问你，两种说法都要会：

| 从"具体风格"角度说 | 从"教材大类"角度说 |
|-------------------|-------------------|
| 管道-过滤器 | 属于**数据流风格** |
| 分层架构 | 属于**调用/返回风格** |
| 事件驱动 / 隐式调用 | 属于**独立构件风格** |
| 解释器 | 属于**虚拟机风格** |
| 黑板 | 属于**仓库风格** |

> 💡 **答题保险写法**：`该系统采用事件驱动架构（属于独立构件风格）……`
> 两个名字都写上，无论阅卷按哪个口径都踩得到分。

---

## 1.3 逐个风格拆开讲

每个风格统一按 **5 段式** 讲：
**① 一句话直觉 → ② 长什么样（结构图） → ③ 为什么这么设计（它想解决什么问题） → ④ 适合/不适合什么 → ⑤ 考试怎么写、怎么写会丢分**

---

### 1.3.1 分层架构（Layered）

**① 直觉**：公司层级汇报，员工 → 主管 → 总监 → 老板，**只能一层层往上，不能越级**。

**② 长什么样**
```
┌──────────────────┐
│   表示层（界面/API） │   用户看到的东西
├──────────────────┤
│   业务逻辑层        │   核心规则，比如下单校验
├──────────────────┤
│   数据访问层        │   屏蔽数据库细节
├──────────────────┤
│   数据存储层（DB）   │
└──────────────────┘
   ↑ 上层可以调用下层，下层不能调用上层（单向依赖）
```

**③ 为什么这么设计**
它想解决的问题是：**"改了数据库，别逼着我把界面也重写一遍"**。
每一层只依赖它下面那一层，下层的变化被"挡"在上层的视线之外。这就是所谓的**关注点分离**。

**④ 适合 / 不适合**
- ✅ 适合：企业信息系统（OA、ERP、进销存）、大多数传统业务系统、团队协作分工明确的场景
- ❌ 不适合：极低延迟的高性能场景（每一层都是一次函数调用开销）、层级划分不清的复杂业务

**⑤ 考试怎么写 / 怎么丢分**

| ✅ 该写 | ❌ 别写 |
|--------|--------|
| 层间解耦，职责清晰，**可修改性高**；每层可独立测试，**可测试性较好**；支持团队并行开发 | ❌ "分层架构一定可修改性高" —— **只有严格遵守单向依赖、职责清晰时才高**；分层混乱、到处跨层调用时，可修改性反而更差 |
| 缺点：**层级过多带来调用开销，性能下降**；层级太深调试链路长 | ❌ 只写优点不写性能代价 |

> ⚠️ **丢分点**：分层是**最常见、最容易被轻视**的风格。很多考生觉得"太简单了不用背"，结果第一问让"简述两种架构的区别"时，写不出**"显式调用 vs 隐式调用""耦合强 vs 耦合弱"**这种对比关键词，白丢分。

---

### 1.3.2 管道-过滤器（Pipes and Filters）

**① 直觉**：工厂流水线。原料从一头进，经过一个个工位加工，成品从另一头出。

**② 长什么样**
```
原始数据 ──管道──> [过滤器1: 清洗] ──管道──> [过滤器2: 转换] ──管道──> [过滤器3: 校验] ──> 结果
```
- **过滤器（Filter）**：一个独立的处理步骤，**只管"进来什么 → 出去什么"**，不管上下游是谁
- **管道（Pipe）**：传数据的通道

**③ 为什么这么设计**
想解决的问题：**"这些处理步骤要能随便换、随便插拔、随便重排"**。
因为每个过滤器只依赖"输入数据格式"，不依赖"谁给我数据"，所以它们是**可插拔**的。

**④ 适合 / 不适合**
- ✅ 适合：**数据加工流水线** —— 编译器（词法→语法→语义→代码生成）、图像处理、ETL 数据清洗、日志处理、音视频转码
- ❌ 不适合：**交互性强的系统**（比如一个需要来回确认的 UI 流程）、处理步骤之间需要共享大量状态的系统

**⑤ 考试怎么写 / 怎么丢分**

| ✅ 该写 | ❌ 别写 |
|--------|--------|
| **可修改性高**（过滤器可插拔、可替换、可重排）；**可复用性强**；每个过滤器可独立测试，**可测试性高**；过滤器之间可**并发执行** | ❌ "管道-过滤器性能好" —— 恰恰相反：数据在过滤器之间**反复拷贝、序列化/反序列化**，有额外 I/O 开销，**性能是它的代价** |
| 缺点：**不适合交互性强的系统**；数据转换有开销；过滤器之间传递数据**难以做权限控制（安全性弱）** | ❌ 只写优点 |

> 📌 **和 Lambda 架构的关系（重要）**：Lambda / Kappa 大数据架构的底层用的就是**管道-过滤器（数据流风格）**思想。题干出现"海量数据""批流一体"时，可以这么写：
> `本系统采用 Lambda 架构，底层采用管道-过滤器的数据流风格……`

---

### 1.3.3 事件驱动架构（Event-Driven）/ 隐式调用

**① 直觉**：小区广播喇叭。喊一嗓子，**喊的人完全不知道谁会响应、也不等结果**。

**② 长什么样**
```
                    ┌────事件总线 / 消息队列（Kafka/RabbitMQ）────┐
                    │                                          │
订单服务 ──发布"订单已支付"事件──>                              │
                    │────> 库存模块（订阅，自己去扣库存）        │
                    │────> 积分模块（订阅，自己去加积分）        │
                    │────> 短信模块（订阅，自己去发短信）        │
                    └──────────────────────────────────────────┘
```
关键点：**订单服务的代码里，一行关于"库存/积分/短信"的字都没有。** 它只管把事件丢出去。

> 📌 **术语**：这种模式叫 **发布-订阅（Publish-Subscribe）**，也叫 **隐式调用**。
> 相对的，分层那种 A 明确调用 B 的，叫 **显式调用**。

**③ 为什么这么设计**
想解决的问题：**"加一个新功能，别逼着我去改已有模块的代码"**。
以前加"发短信"，得改订单服务的代码；现在只要让短信模块去订阅事件就行 —— **订单服务零改动**。这就是**极致的解耦**。

**④ 适合 / 不适合**
- ✅ 适合：异步处理流程（下单后的连锁动作）、高并发写入削峰填谷、需要极高可扩展性的系统、IoT 数据采集、实时数据流
- ❌ 不适合：**要求强实时同步响应**的场景（用户点完必须立刻看到结果）、**强事务一致性**的场景（必须"要么都成功要么都失败"）

**⑤ 考试怎么写 / 怎么丢分**

| ✅ 该写 | ❌ 别写 |
|--------|--------|
| **可修改性高**（发布-订阅解耦，加订阅方不改发布方）；**可用性较好**（异步解耦，局部故障不扩散）；**吞吐量提升**（削峰填谷） | ❌ **"事件驱动一定提高性能"** —— 这是黑名单禁句！ |
| 缺点：**异步带来端到端延迟**；**可测试性/可调试性下降**（执行链路不可见）；消息顺序、重复消费（需幂等）、事务一致性难保证 | ❌ 只写"解耦"两个字就完事，不展开 |

> ⚠️ **丢分重灾区：事件驱动到底对性能是加是减？**
> 这是本章**最需要辩证理解**的一个点，命题人特别爱在这里设陷阱。必须分场景说：
>
> | 场景 | 对性能的影响 | 理由 |
> |------|------------|------|
> | 高并发写入 / 削峰填谷 | ✅ **提升吞吐量** | 请求先堆进队列，后端按自己的能力消费，不会被瞬时流量打垮 |
> | 异步通知（发短信、加积分） | ✅ **提升响应速度** | 主流程不用等这些慢动作，直接返回 |
> | **用户要立刻看到结果** | ❌ **增加延迟** | 消息要经过中间件转发、排队、被消费，比直接调用慢 |
> | 强事务一致性 | ❌ **更难** | 需要幂等设计、消息确认、分布式事务补偿 |
> | 排查问题 | ❌ **更难** | 链路不可见，调试困难 |
>
> **答题时必须写清楚"对哪个维度"**，笼统说"提高性能"或"降低性能"都可能扣分。

> ⚠️ **第二个丢分点**：**"用了消息中间件" ≠ "事件驱动架构"**。
> 判断标准是：**业务构件是否解耦、是否采用发布-订阅的隐式调用模式**。
> 一个单体系统内部用了个异步队列处理日志 —— 这是技术手段，**不是**事件驱动架构。

### 1.3.4 仓库架构（Repository）/ 知识库架构

**① 直觉**：**图书馆 / 共享网盘**。书全放在中央，**读者自己决定什么时候去借**。管理员（仓库）**从不主动叫你**。

**② 长什么样**
```
        ┌──────────────────┐
        │   中央数据仓库      │  ← 被动的，只存数据，不调度任何人
        └──────────────────┘
          ↑      ↑      ↑
       客户端A  客户端B  客户端C     ← 各客户端自己决定何时读写，业务逻辑在自己身上
```

**③ 为什么这么设计**
想解决的问题：**"多个模块要共享同一批数据，别复制来复制去搞出不一致"**。
把数据放中央，大家来这儿读，就只有一份"真相"。

**④ 适合 / 不适合**
- ✅ 适合：**数据驱动的系统** —— 进销存、ERP、数据库应用、IDE（共享语法树）、现代的向量数据库检索（RAG）
- ❌ 不适合：需要复杂协同求解的问题（那是黑板的事）

**⑤ 考试怎么写 / 怎么丢分**

| ✅ 该写 | ❌ 别写 |
|--------|--------|
| 共享数据无需传递副本，**减少数据冗余**；客户端可独立增删，**有一定可扩展性** | ❌ **"用了数据库就是仓库架构"** —— 严格说要看是否以"中央共享数据"为核心组织方式 |
| 缺点：**中央仓库是耦合点，可修改性受限**（改数据结构影响所有客户端）；**仓库若不做冗余设计易成单点故障（可用性风险）**；安全压力集中；业务逻辑分散在各客户端，**整体难以测试** | ❌ 只写优点不写单点故障风险 |

> 📌 **仓库 vs 黑板 —— 必考辨析（见 1.6.1，这里先记口诀）**
> `仓库存数据，别人主动读；黑板存数据，主动喊人干活。`

---

### 1.3.5 黑板架构（Blackboard）⭐ 高频考点

**① 直觉**：**专家会诊**。一块白板，多位专家（知识源）轮流上前写、改；**主持人根据当前进度决定叫谁上**；专家之间**互不说话**，全靠看白板。

**② 长什么样**
```
     ┌────────────────────────────────┐
     │      黑板（共享数据 + 控制调度）    │  ← 关键：黑板不只存数据，还负责"叫谁干活"
     └────────────────────────────────┘
        ↑ 读写      ↑ 读写      ↑ 读写
    [知识源1]    [知识源2]    [知识源3]
    声学模型     语言模型     语义分析
        └──── 互相不知道对方存在，只认黑板 ────┘
```

**③ 为什么这么设计**
想解决的问题：**"这个问题没有确定的解法，我不知道该按什么顺序调用哪些模块"**。
比如语音识别：你没法预先写死"先做 A 再做 B 再做 C"，只能让多个专家模块**各自贡献自己的判断**，逐步逼近答案。

所以黑板的适用前提是：**问题没有确定性算法 / 没有固定求解流程**。

**④ 适合 / 不适合**
- ✅ 适合：**AI 与复杂推理** —— 语音识别、图像理解、信号处理、故障诊断、复杂决策支持、**多 Agent 协作**
- ❌ 不适合：有明确流程的业务系统（用分层或管道-过滤器就够了）

**⑤ 考试怎么写 / 怎么丢分**

> 🎯 **看到这些关键词，优先考虑黑板**（这是送分题，务必背下来）：
> **无固定求解算法 / 多个知识源 / 共享黑板 / 协同求解 / 语音识别 / 图像识别 / 复杂推理 / 信号处理 / 多专家协作**

| ✅ 该写 | ❌ 别写 |
|--------|--------|
| 适合**无确定性解法**的复杂问题；**灵活性/扩展性高**（容易加新的知识源）；多个知识源协同求解 | ❌ **"黑板架构就是数据库系统"** —— 数据库只存储、不调度，那是仓库；黑板的核心是**主动调度知识源** |
| 缺点：**控制逻辑复杂**；多知识源竞争黑板资源，**调度开销大（性能差）**；黑板是**单点（可用性风险高）**；推理过程不透明，**极难调试（可测试性很差）** | ❌ 把黑板答成仓库 |

> 💡 **答题加分句**：`黑板不仅承担数据存储作用，还承担**控制调度**作用；知识源之间不直接通信，而是围绕黑板协同求解。`
> 这句话一写出来，阅卷就能确认你**真懂**了黑板和仓库的区别。

### 1.3.6 主程序-子程序（Main Program and Subroutine）

**① 直觉**：**一个人干到底**。主程序脑子里有完整剧本，子程序只是它的"手脚"，没有自主权。

**② 为什么这么设计**：最早的编程方式，结构简单直接。

**③ 特点**
- ✅ **性能好**：直接函数调用，没有网络、没有中间件，开销最小
- ❌ **可修改性最差**：紧耦合，改一处可能影响全局，"牵一发动全身"
- ❌ **可用性差**：主程序崩溃，整个系统完蛋
- ❌ **可测试性差**：模块间强依赖，难以单独做单元测试

**④ 考试定位**：它通常作为**被改造的对象**出现（题干说"某系统原为主程序-子程序结构，现要重构为……"），或者作为**对比项**出现（"请比较主程序-子程序与面向对象架构"）。

> 📌 **别名**：**显式调用** = 主程序-子程序风格。

---

### 1.3.7 面向对象架构（Object-Oriented）

**① 直觉**：**每个人是自己领域的负责人**，自己管自己的资料柜（封装），需要协作时互相"发消息"。

**② 特点**
- ✅ **可修改性较好**：封装、继承、多态使修改和扩展相对容易
- ❌ **性能一般**：对象间大量交互、方法调用有开销
- ❌ 对象之间依赖关系复杂时容易出现**调用混乱**

**③ 考试定位**：单独考得不多，通常在大类判断里出现（"面向对象属于哪种风格大类？" → **调用/返回风格**）。

---

### 1.3.8 虚拟机风格：解释器 & 基于规则的系统

**① 直觉**：**同声传译**。你说一句，翻译一句、执行一句，**不是一次性全翻译完再执行**。

**② 长什么样**
```
用户提交的脚本/代码/规则  ──>  [解释器引擎]  ──>  逐条解析并执行  ──>  结果
                                  ↑
                          屏蔽了底层硬件/平台的差异
```

**③ 两种子风格**

| 子风格 | 做什么 | 例子 |
|--------|-------|------|
| **解释器** | 解释执行用户写的**程序/脚本** | Python 解释器、JVM、SQL 执行引擎、工作流引擎、大模型训练平台解析用户提交的 Python 代码 |
| **基于规则的系统** | 把**业务规则**抽出来变成 if-then，改规则不改代码 | 规则引擎（Drools）、风控规则、促销规则引擎 |

**④ 为什么这么设计**
想解决的问题：**"用户需要自定义行为，但我不能为了每种行为都改一次代码、重新发一次版"**。
把"行为"变成"可被解释的数据"，就实现了**延迟绑定**（运行时才决定做什么）。

**⑤ 考试怎么写**
- ✅ 优点：**灵活性高**、**可修改性高**（改规则/改脚本不用改程序）、屏蔽平台差异（**可移植性**）
- ❌ 缺点：**性能差**（解释执行比编译执行慢得多）、**可测试性差**（用户写的东西难以预测和验证）

> 🎯 **2026 新大纲提示**：题干出现"**大模型训练平台需要解析用户提交的 Python 代码、动态调度 GPU**" → 直接答 **解释器风格（虚拟机风格子类）**。
> 理由写法：`系统需要"解释"执行用户提交的脚本，而非直接编译执行；解释引擎屏蔽底层硬件差异，可动态匹配 GPU 资源。`

---

### 1.3.9 C2 架构

**① 直觉**：**极其严格的大公司** —— 任何两个部门**不准直接沟通**，所有沟通必须走"行政中转站"。

**② 长什么样**
```
[构件A] ──> [连接器] <── [构件B]
                 ↑
             [连接器]  ← 连接器之间也能连
                 ↓
[构件C] ──> [连接器] <── [构件D]
```
**核心约束**：构件之间**禁止直接调用**，一切通信经由**连接器**（负责消息路由、事件传递）。

**③ 特点**
- ✅ **可修改性极高**（构件完全解耦，随便换）
- ❌ **性能较差**（连接器带来额外开销与延迟）

**④ 考试怎么写 / 怎么丢分**

> ⚠️ **丢分点**：C2 和事件驱动**思想相似**（都用消息/事件通信），但**考试中不要简单说"C2 是事件驱动的一种"**。
> 更稳妥的写法：强调 C2 的**"构件-连接器"结构特征**与**"禁止构件间直接调用"**这一硬约束。

| | 事件驱动（隐式调用） | C2 |
|---|---|---|
| 能否直接调用？ | **可以**，没有强制约束 | **严格禁止**，必须走连接器 |
| 核心特征 | 发布-订阅解耦 | 构件-连接器 + 硬性约束 |

---

### 1.3.10 SOA 面向服务架构

**① 直觉**：**商业街 + 一个统一的物流调度中心（ESB）**。每家店比较大，货物统一走调度中心。

**② 长什么样**
```
[服务A] ─┐
[服务B] ─┼──>  ESB 企业服务总线（协议转换/路由/编排）  ──>  [服务D]
[服务C] ─┘                                          ──>  [服务E]
```
> 📌 **ESB**（Enterprise Service Bus）：企业服务总线，负责**协议转换、消息路由、服务编排**。它是 SOA 的核心标志物。

**③ 特点**
- ✅ 服务松耦合，**可修改性高**；适合**大型异构企业系统集成**（把 Java 老系统、.NET 系统、数据库全都接进来）
- ✅ 服务可冗余部署，**可用性较好**
- ❌ **性能一般**：服务调用 + ESB 转发带来网络开销
- ❌ 跨服务调试链路长，**可测试性一般**

**④ 考试定位**：常与微服务对比出现（见 1.6.3）。

---

### 1.3.11 微服务架构（Microservices）⭐ 高频考点

**① 直觉**：**商业街 + 每家店独立经营**。每家店面小，**有自己的小仓库（独立数据库）**，随时能换招牌（独立部署）、单独装修（独立扩展）。

**② 长什么样**
```
用户 ──> [API 网关] ──> [订单服务] ──> 订单库
                    ──> [库存服务] ──> 库存库
                    ──> [支付服务] ──> 支付库
                    ──> [物流服务] ──> 物流库
        （每个服务：独立开发、独立部署、独立数据库、独立扩展）
```

**③ 为什么这么设计**
想解决的问题：**"改一个小功能，不用把整个系统重新测试、重新部署一遍"**。
单体架构（所有功能打成一个包）最大的痛就是 —— 改一行代码，整个系统都要重新发版，风险巨大。

**④ 特点（考试必背，每个字都可能踩分）**

| 收益 | 代价 |
|------|------|
| ✅ **可修改性极高**：每个服务独立开发、独立部署、独立迭代 | ❌ **性能下降**：大量远程调用（网络开销），分布式事务复杂 |
| ✅ **可用性较好**：单个服务故障被隔离，不拖垮整体（**前提是有完善的服务治理/熔断/监控**） | ❌ **可测试性/可调试性很差**：分布式系统，排查故障难度大 |
| ✅ **可伸缩性好**：哪个服务压力大就单独扩哪个 | ❌ **运维复杂**：服务发现、配置中心、监控、链路追踪、容器编排，一整套都要有 |
| ✅ **技术异构**：不同服务可以用不同语言/数据库 | ❌ **数据一致性挑战**：每个服务独立数据库，跨服务事务需要 TCC / Saga 等最终一致性方案 |

**⑤ 考试怎么写 / 怎么丢分**

> ❌❌❌ **头号禁句（整个架构科目最著名的陷阱）**：
> **"微服务架构可以提升系统整体性能。"** —— 写了几乎必然扣分！
>
> ✅ 正确：微服务**大量远程调用**，相比单体通常**性能会下降**；它的收益是**可修改性、可用性、可伸缩性**的提升。

> ⚠️ **第二个陷阱**：**"微服务可用性一定好"**
> ✅ 正确说法：微服务通过**故障隔离、独立部署、独立扩展**有**助**于提升可用性；
> 但**如果服务治理、监控、容错、熔断、链路追踪能力跟不上**，反而会因为分布式复杂度**降低**整体可用性。
> **答题时一定要加上"在具备完善服务治理能力的前提下"这个限定。**

## 1.4 一张表背下来：风格 → 质量属性收益 / 代价

> 📌 这是本章**最核心的一张表**。考试第二问"从 XX 质量属性角度分析收益与代价"，基本就是这张表的现场调用。
>
> ⭐ = 该风格通常**有利于**这个属性；⚠️ = 该风格通常**损害 / 带来额外负担**。
> **注意：答题必须结合题干场景，不能死套表格。**

| 架构风格 | 可修改性 | 性能 | 可用性 | 安全性 | 可测试性 | 备注 / 其他代价 |
|---------|---------|------|--------|--------|---------|----------------|
| **分层架构** | ⭐⭐⭐⭐ 层间解耦，改动局限一层 | ⚠️⚠️ 层级过多产生调用开销 | ⭐⭐ 可单独部署冗余层 | ⭐⭐ 可在网关层做权限控制 | ⭐⭐⭐ 每层可独立测试 | 层级太深时调试链路长 |
| **管道-过滤器** | ⭐⭐⭐⭐ 过滤器独立、可插拔 | ⚠️⚠️ 数据反复拷贝、流转开销 | ⭐⭐ 单过滤器故障可隔离 | ⚠️ 过滤器间传递数据难控权限 | ⭐⭐⭐⭐ 每个过滤器可单独测试 | 不适合交互强、需共享大量状态的系统 |
| **仓库（知识库）** | ⚠️ 中央数据仓库是耦合点 | ⭐⭐ 共享数据无需传递副本 | ⚠️ 无冗余设计易成单点故障 | ⚠️ 集中数据，安全压力集中 | ⚠️ 业务逻辑分散，难以整体测试 | 适合数据驱动类系统 |
| **黑板架构** | ⚠️ 知识源间通过黑板耦合 | ⚠️ 多知识源竞争资源，调度开销大 | ⚠️ 黑板单点风险高 | ⚠️ 数据全在黑板，安全管控难 | ⚠️⚠️ 推理过程不透明，极难调试 | 适合**无确定性求解算法**的问题（AI 推理、信号处理） |
| **主程序-子程序** | ⚠️⚠️ 紧耦合，改一处影响全局 | ⭐⭐⭐ 直接调用，开销小 | ⚠️ 主程序故障整体崩溃 | ⭐⭐ 权限集中控制 | ⚠️ 模块强依赖，单元测试困难 | 传统单体结构化程序 |
| **面向对象** | ⭐⭐⭐ 封装继承利于修改扩展 | ⚠️ 对象间大量交互，调用开销 | ⭐⭐ 可封装独立对象做冗余 | ⭐⭐ 封装可隐藏内部数据 | ⭐⭐ 对象可单独测试 | 依赖关系复杂时易调用混乱 |
| **事件驱动（隐式调用）** | ⭐⭐⭐⭐ 发布订阅解耦，发布者不知订阅者 | ⚠️⚠️ 异步延迟；事务一致性难保证 | ⭐⭐⭐ 生产者消费者解耦，故障不扩散 | ⚠️ 消息链路长，难追踪安全问题 | ⚠️⚠️ 执行链路不可见，调试困难 | **最典型权衡：高可修改性 换取 可调试性下降** |
| **C2** | ⭐⭐⭐⭐⭐ 组件完全解耦，只能经连接器通信 | ⚠️⚠️⚠️ 连接器带来额外开销 | ⭐⭐⭐ | ⚠️ | ⚠️ | 禁止构件直接调用 |
| **SOA** | ⭐⭐⭐⭐ 服务松耦合，可独立变更 | ⚠️⚠️ 服务调用 + ESB 转发开销 | ⭐⭐⭐ 服务可冗余部署 | ⭐⭐ 统一服务网关鉴权 | ⚠️ 跨服务调试链路长 | 适合大型异构企业系统集成 |
| **微服务** | ⭐⭐⭐⭐⭐ 每服务独立开发部署迭代 | ⚠️⚠️⚠️ 大量远程调用，分布式事务复杂 | ⭐⭐⭐ 单服务故障不拖垮整体 | ⚠️ 服务变多，安全管控面变大 | ⚠️⚠️⚠️ 分布式系统排查故障难 | **最典型权衡：可修改性、可用性提升，牺牲性能与可调试性** |

> 💡 **答题黄金句式（阅卷高频踩分点，务必背熟）**
> `采用 XX 架构风格，可以提升系统的【可修改性 / 可用性】；但会带来【性能下降、调试困难、分布式事务复杂】等代价，需要在方案中进行权衡。`

## 1.6 ⚠️ 丢分重灾区 #1：五组高频混淆对比

> 这五组是历年真题**反复出现**的辨析点。每一组都要能说出"**判断关键是什么**"。

---

### 1.6.1 仓库 vs 黑板（考生最高频错题）

| | 仓库（知识库） | 黑板 |
|---|---|---|
| **控制流（判断关键）** | **客户端自己决定**何时访问仓库、读写数据 | **黑板主动调度**各知识源，知识源之间互不感知 |
| 中央数据的角色 | **纯被动**：只存数据，不调度 | **存储 + 中央控制调度** |
| 典型场景 | 数据库驱动系统（进销存、ERP） | 语音识别、图像理解、问题求解、AI 推理 |
| 求解方式 | 有确定流程 | **没有固定求解流程 / 无确定性算法** |

> **速记口诀**：`仓库存数据，别人主动读；黑板存数据，主动喊人干活。`
>
> **一句话答题法**：
> - 仓库：`各业务模块根据自身需要主动访问中央数据仓库，仓库本身不参与调度，属于仓库架构。`
> - 黑板：`系统存在中央黑板，黑板根据当前求解进度主动调度各知识源协同求解，知识源之间不直接通信，属于黑板架构。`

---

### 1.6.2 事件驱动 vs C2

- **事件驱动（EDA）**：构件之间**可以直接调用，也可以走事件**，**没有强制约束**。
- **C2**：**严格禁止构件之间直接调用**，所有通信必须经过连接器（连接件负责消息路由、事件传递）。构件低耦合、可修改性高，但连接件带来额外性能开销。

> ⚠️ 答题提醒：C2 与事件驱动**思想相似**，但**不建议**简单说"C2 是事件驱动子类"。应强调其 **"构件-连接器"** 特征与**禁止直接调用**的硬约束。

---

### 1.6.3 SOA vs 微服务

| | SOA | 微服务 |
|---|---|---|
| **ESB** | 一般**依赖重型 ESB** 企业服务总线做中转 | 一般**无重型 ESB**（用 API 网关 + 轻量通信） |
| 服务粒度 | **偏大** | **更小** |
| 数据 | 常共享数据库 | **每个服务独立数据库** |
| 核心目标 | **企业异构系统集成** | **互联网业务快速迭代、独立部署扩展** |

---

### 1.6.4 分层 vs 主程序-子程序

| | 分层架构 | 主程序-子程序 |
|---|---|---|
| 依赖关系 | **层与层单向依赖**，每层职责独立 | 同一程序内部模块**直接调用** |
| 部署 | 可以**跨进程、跨机器**部署 | 单体紧耦合 |
| 归属 | 调用/返回风格 | 调用/返回风格 |

---

### 1.6.5 管道-过滤器 vs 事件驱动（易被题干混淆）

两者都有"流动"的感觉，判断看**流动的是什么**：

| | 管道-过滤器 | 事件驱动 |
|---|---|---|
| 流动的是什么 | **数据本身**被加工后传下去 | **事件通知**（消息），触发别人干活 |
| 拓扑 | 通常是**线性链**（A→B→C） | 通常是**广播/星形**（一对多，发布-订阅） |
| 关键词 | 加工、转换、流水线、ETL | 通知、订阅、响应、异步解耦 |

## 1.7 补充：Lambda / Kappa（大数据批流混合场景）

> 🎯 **触发条件**：题干背景是"**海量数据**" + "**既要实时又要离线准确**" → 优先考虑批流混合架构。

### Lambda 架构（三层）

| 层 | 干什么 | 特点 |
|---|-------|------|
| **批处理层（Batch Layer）** | 处理**全量历史数据** | 结果**准确**，但**延迟高** |
| **速度层（Speed Layer）** | 处理**实时增量数据流** | **低延迟**，但结果是**近似/增量** |
| **服务层（Serving Layer）** | **合并两层结果**，对外统一提供查询 | — |

> 📌 **底层思想**：Lambda 的底层采用 **管道-过滤器（数据流风格）** 的思想。

### Kappa 架构
**舍弃批处理层，全部采用流处理实现**（如 Kafka + Flink）。架构更简洁，**只维护一套流处理管道**。

> ✅ **答题模板（可直接套）**
> `本海量数据处理系统适合采用 Lambda 架构，采用管道-过滤器的数据流风格，分别通过速度层处理实时数据流、批处理层处理全量历史数据，最终由服务层对外统一提供查询服务。若追求架构简洁、认为实时数据即最终数据，也可采用 Kappa 架构，全部以流处理实现。`

## 1.8 补充：AI 场景风格映射（2026 新大纲）

> 📢 **命题趋势**：2026 新大纲强化 AI。第一题大概率仍考**经典架构**，但**题干背景**极可能换成"大模型训练平台""智能推荐系统""RAG 私有知识库"。
> **换汤不换药** —— 看到关键词按下表映射即可。

| 题干出现的 AI 场景 | 对应架构风格 | 为什么（答题逻辑） |
|------------------|-------------|------------------|
| 训练平台（**解析 Python 代码**、动态调度 GPU） | **解释器风格**（虚拟机风格子类） | 系统需要"**解释**"执行用户提交的脚本/规则，而非直接编译执行；解释引擎屏蔽底层硬件差异，动态匹配资源 |
| 推荐系统 / 推理流水线（清洗 → 特征提取 → 预测 → 输出） | **管道-过滤器风格**（数据流风格） | 数据像流水一样经过多个**独立的处理阶段**，每阶段职责单一、可插拔 |
| RAG 检索增强生成（向量检索 + 大模型生成） | **仓库风格 / 数据中枢** | 向量数据库作为核心"**仓库**"，检索服务与 LLM 生成服务围绕数据读写 |
| 智能体 Agent 协作（多个 AI 模型协同完成任务） | **黑板风格 / 事件驱动** | 多个专家模型（知识源）围绕**共享上下文**协同工作，无固定流程；或组件间通过事件异步协作 |

> 🎯 **一句话考点速记**：
> 看到"**解析代码/规则**" → 想 **解释器**；
> 看到"**数据一步步处理**" → 想 **管道-过滤器**；
> 看到"**多模型协作**" → 想 **黑板**；
> 看到"**向量库做核心存储**" → 想 **仓库**。

### 1.8.1 RAG 系统的典型权衡考点（新大纲高频预测）

RAG 流程：**文档 → 切块 → Embedding → 向量检索 → Prompt 组装 → 大模型生成**

- 该数据流本质上是 **管道-过滤器架构风格**：每个处理环节是独立过滤器，数据沿管道依次流转。
- ⭐ **经典权衡点：Top-K 召回数量**
  - 增大 Top-K → 召回的知识片段变多 → 问答**准确性提升**
  - 但检索数据量变多 → 查询时延增加 → **性能下降**
  - 因此是 **准确性 - 性能** 之间的权衡点

> ✅ **答题模板（RAG 权衡点，直接背）**
> `权衡点是影响多个质量属性且效果冲突的架构决策。增大向量检索的 Top-K 参数，召回的知识片段增多，问答准确性提升；但检索数据量增大，查询时延增加，性能下降。因此该决策是准确性与性能之间的权衡点。`

### AI 场景质量属性识别提示

| 题干 | 属于 |
|------|------|
| 训练任务 1 分钟内分配 GPU | **性能** |
| 新增 GPU 型号无需改核心代码 | **可修改性** |
| 恶意代码检测拦截 | **安全性** |
| 支持从 x86 迁移到 ARM | **可修改性（可移植性）** |
| 模型推理 P99 延迟 ≤ 2 秒 | **性能** |
| 多 Agent 协同失败可回滚 | **可用性** |

# 第 2 部分 · 原理篇：质量属性

> 学这部分的目标：**题干里随便一句需求，你能立刻判断它属于哪个质量属性，并说出对应的实现战术。**

---

## 2.1 什么是质量属性？为什么它是"架构的标尺"？

### 直觉：功能 vs 质量属性

| | 功能需求 | 质量属性（非功能需求） |
|---|---------|---------------------|
| 回答的问题 | 系统**能做什么** | 系统**做得怎么样** |
| 电商例子 | 能下单、能支付、能退款 | 下单**要 2 秒内**响应、支付**不能中断**、**防得住**黑客攻击、加个新功能**只要 2 周** |
| 能不能少 | **不能**，少了系统没用 | 少了系统**也能跑**，只是跑得差 |

### 为什么质量属性是"架构的标尺"？

**因为架构决策的价值，只能用质量属性来衡量。**

你说"我们要上微服务" —— 凭什么？凭它能提升**可修改性**和**可用性**。
你说"我们要加 Redis 缓存" —— 凭什么？凭它能提升**性能**。

> 💡 **核心认知**：**架构风格的选择，本质上是为了满足特定的质量属性需求。**
> 这就是为什么试题一总是把"架构风格"和"质量属性"**绑在一起考** —— 它们本来就是一件事的两面。

---

## 2.2 六大质量属性逐个讲

教材标准六大属性：**性能、可用性、安全性、可修改性、可测试性、易用性**。
（另外"可伸缩性"作为可修改性的重要子属性，新大纲常单独考。）

---

### 2.2.1 性能（Performance）

**① 直觉**：**快不快**。通勤要多久、电梯多快、1 小时能处理多少单。

**② 定义**：系统**及时提供服务**的能力。

**③ 三个可量化指标（答题要会写具体的）**

| 指标 | 含义 | 例子 |
|------|------|------|
| **响应时间** | 从发出请求到收到响应要多久 | 页面首屏 < 1 秒；API P99 < 200ms |
| **吞吐量** | 单位时间能处理多少 | 系统支持 10000 TPS；日处理订单 500 万 |
| **资源利用率** | 用了多少 CPU/内存/带宽 | CPU 峰值不超过 70% |

> 📌 **P99 是什么**：99% 的请求都在 X 毫秒内完成。比"平均响应时间"更能反映长尾用户的体验。题干出现 P99 / P95 一定是**性能**。

**④ 常见战术（第四部分有完整表）**：缓存（本地/分布式/CDN）、负载均衡、读写分离、分库分表、异步处理（消息队列）、并发与连接池、算法与数据结构优化、水平扩展

**⑤ 与其他属性的冲突**
- ↔ **可用性**：缓存越多，一致性维护越复杂，可能影响数据的正确可用
- ↔ **安全性**：加解密、鉴权、审计都会消耗算力、增加延迟

---

### 2.2.2 可用性（Availability）

**① 直觉**：**靠不靠谱**。会不会经常停水停电？坏了多久能修好？

**② 定义**：在**要求的外部资源得到保证**的前提下，系统在**规定的条件下**和**规定的时刻或时间区间**内处于**可执行规定功能状态**的能力。
> 人话：**在一定时间内，系统能正常工作的时间所占的比例。**

**③ 量化公式（必背，还可能考计算）**

```
可用性 = MTBF / (MTBF + MTTR) × 100%
```
- **MTBF**（Mean Time Between Failures）：平均无故障工作时间 —— **越长越好**（少出故障）
- **MTTR**（Mean Time To Repair）：平均修复时间 —— **越短越好**（坏了快点修）

> 💡 常说的"**几个 9**"：99.9%（年停机约 8.8 小时）、99.99%（约 53 分钟）、99.999%（约 5 分钟）。
> 📌 详细的串并联可靠度、TMR、马尔可夫模型计算，见 [06b-计算题专项（可靠性与可用性）.md](./06b-计算题专项（可靠性与可用性）.md)。

**④ 常见战术**：冗余部署（服务/数据多副本）、故障自动转移（心跳检测 / 主备切换 / 集群选举）、负载均衡、限流 / 降级 / 熔断、无状态设计、异步解耦、数据备份恢复

**⑤ 与其他属性的冲突**
- ↔ **性能**：冗余副本、同步机制会带来延迟
- ↔ **安全性**：复杂的安全策略（多因子认证、审计）会影响响应速度与可用性

---

### 2.2.3 安全性（Security）

**① 直觉**：**防不防得住**。门禁、防盗窗、监控。

**② 定义**：系统在向**合法用户**提供服务的同时，**阻止非授权使用**的能力。

**③ 四个维度（答题按这四类展开，很显专业）**

| 维度 | 含义 | 具体措施 |
|------|------|---------|
| **机密性** | 该看的才能看 | 加密（传输 TLS / 存储）、脱敏、访问控制 |
| **完整性** | 数据没被篡改 | 数字签名、哈希校验 |
| **可用性**（安全视角） | 合法用户用得上 | 抗 DDoS、防重放 |
| **可审计性** | 出事能追责 | 审计日志、操作留痕 |

**④ 常见战术**：认证（你是谁）、授权（你能干什么）、加密、数字签名、输入校验（防 SQL 注入 / XSS）、审计日志、入侵检测、漏洞扫描、最小权限原则、数据脱敏

**⑤ 与其他属性的冲突**
- ↔ **性能**：加解密、鉴权、审计都消耗算力，**增加延迟**
- ↔ **可用性**：过于复杂的安全策略影响用户体验与访问效率

---

### 2.2.4 可修改性（Modifiability）

**① 直觉**：**好不好改**。想改户型、加个房间，工程量多大？

**② 定义**：**修改**系统的**成本**高低。修改包括：新增功能、修改 bug、适配新业务、移植到新平台。

**③ 三个子属性（答题时写具体子属性更精准）**

| 子属性 | 含义 | 例子 |
|--------|------|------|
| **可扩展性（Extensibility）** | 加新功能容易吗 | 新增支付方式，2 周内完成 |
| **可伸缩性（Scalability）** | 负载涨了能靠加资源扛住吗 | 用户量涨 300%，加节点即可支撑 |
| **可移植性（Portability）** | 换个平台/环境容易吗 | 从 x86 迁移到 ARM；从 Windows 迁到 Linux |

**④ 常见战术**：高内聚低耦合、分层、接口隔离 / 依赖倒置、抽象层 / 中间件隔离变化、组件化 / 插件化、配置驱动（参数外部化）、**延迟绑定**（运行时才决定行为：配置文件、插件、多态、规则引擎）

**⑤ 与其他属性的冲突**
- ↔ **性能**：过多的抽象、分层、接口调用**增加链路长度，带来性能损耗**

---

### 2.2.5 可测试性（Testability）

**① 直觉**：**好不好验**。验收的时候，能不能快速验证每个部分都正常？出了问题好不好定位？

**② 定义**：系统**能够被有效地测试**、且**容易发现故障**的能力。

**③ 常见战术**：接口 Mock、测试桩、录制回放、日志与监控指标、链路追踪、依赖注入、接口隔离（模块可独立测试）

**④ 考试中的典型考法**：
> "重构为事件驱动架构之后，对**可测试性**有什么影响？"
> ✅ 答：`异步事件链路的执行顺序不可见，模块之间的执行时序难以追踪，系统整体可测试性下降。`

> ⚠️ **丢分点**：很多考生**只记得性能/可用性/可修改性/安全性四个**，题目专门问"**可测试性**"时当场懵住。
> **可测试性一定要单独准备**，它是事件驱动、微服务、黑板这些"异步/分布式/不透明"风格的**标准代价**。

---

### 2.2.6 易用性（Usability）

**① 直觉**：**顺不顺手**。老人小孩住着方便吗？

**② 定义**：用户**学习和使用系统的容易程度**，以及系统对用户的**支持程度**。

**③ 常见战术**：撤销/重做、操作提示、帮助文档、新手引导、多端适配、字体放大、无障碍设计、统一交互风格、合理的默认值、向导式操作

**④ 典型识别**：题干出现"**界面要支持老年人 / 残疾人使用**""**操作要简单，新员工培训 1 小时即可上手**" → **易用性**。

---

### 2.2.7 附：可伸缩性（Scalability）· 新大纲常考

**定义**：系统**负载增长时**，通过**增加硬件 / 服务节点**，**维持原有服务质量**的能力。

| 类型 | 做法 | 例子 |
|------|------|------|
| **水平扩展（Scale Out）** | **增加实例 / 节点** | 加服务器、加容器副本 |
| **垂直扩展（Scale Up）** | **升级单节点硬件** | 加 CPU、加内存、换更好的机器 |

**归属**：可伸缩性是 **可修改性的子属性 / 扩展分支**。

> ⚠️ **答题策略（重要）**：
> 虽然归属上它是可修改性的子属性，但**答题时如果题干强调"负载增长、加节点"，应优先直接写「可伸缩性」**，比写"可修改性"更精准、更贴合阅卷踩分点。
> 保险写法：`可伸缩性（可修改性的子属性）`。

---

## 2.3 ⚠️ 丢分重灾区 #2：易混淆质量属性判断表

> **第一问丢分，往往不是不懂，而是属性边界模糊。**
> 下面每一行都给了"**为什么**"，不要只背答案，要理解判断依据。

| 题干表达 | 容易误判成 | ✅ 正确判断 | 为什么 |
|---------|-----------|-----------|--------|
| 响应时间不超过 0.5 秒 | 可用性 | **性能** | "多久出结果" = 速度问题 = 性能。可用性是"能不能用" |
| 故障后 5 分钟恢复 | 性能 | **可用性** | "坏了多久能好" = MTTR = 可用性 |
| 连续运行 720 小时 | 可靠性 | **可用性** | 考查的是"系统持续提供服务的能力"这一整体指标 |
| 密码加密存储 | — | **安全性** | 机密性 |
| 防止黑客攻击 / 防注入 | — | **安全性** | 抵抗攻击 |
| 新增功能 2 周内完成 | 易用性 | **可修改性（可扩展性）** | "加东西的成本" = 可修改性。易用性是"用户用起来顺不顺手"，跟开发工期无关 |
| 新增 GPU 型号无需修改核心代码 | 性能 | **可修改性 / 可扩展性** | 强调"不用改代码" = 扩展成本低 = 可修改性 |
| 支持从 x86 迁移到 ARM | 可修改性 | **可修改性（可移植性）** | 换平台 = 可移植性 |
| 界面支持老年人、残疾人使用 | 可测试性 | **易用性** | 无障碍设计是易用性的典型战术 |
| 在模拟环境中进行压力测试 | 性能 | **可测试性** | 强调的是"**能不能测**"，不是"快不快" |
| 记录日志用于审计追溯 | 可测试性 | **安全性（优先）** | 日志既能测也能审计，但"**审计追溯**"是安全性的标准战术 |
| 系统可水平扩展应对用户增长 | 可修改性 | **性能 / 可伸缩性**，视题干 | 见下方灵活原则 |
| 消息队列削峰填谷 | 性能 | **性能 / 可用性**，看问题 | 强调"吞吐/抗住瞬时流量"→性能；强调"后端不被打垮、故障不扩散"→可用性 |
| 用户量增长 300%，系统可水平增加节点支撑负载 | 性能 / 可修改性 | **可伸缩性**（子属性） | 强调"**加节点就能扛住**"，优先写可伸缩性 |

### 🔑 灵活判断原则（考场上用来"二选一"）

> 题目只让写一个属性时，看**题干的"刺激"是什么**：

| 题干强调的重点 | 写什么 |
|---------------|--------|
| 强调"**快**、**多久**、**吞吐多少**" | **性能** |
| 强调"**负载增长后性能仍满足**" | **性能** |
| 强调"**系统能扩展部署、能加节点**" | **可伸缩性 / 可修改性** |
| 强调"**改起来成本低、加功能快**" | **可修改性** |
| 强调"**坏了能恢复、不停机**" | **可用性** |

> 📌 **总原则**：标准教材六大属性，**优先写最贴近的那一个**；不要死记表格，要看**题干的刺激到底是什么**。

## 2.4 架构战术速查表（第三问武器库）

> 📌 第三问常问："**为满足某质量属性，可采用哪些架构策略？**" 或 "**该设计采用了哪些质量属性实现策略？**"
> 战术表是"策略库"，**必须结合题干场景选最贴切的 2~3 条，不要全抄**。

### 性能战术

| 战术类别 | 具体措施 |
|---------|---------|
| **减少处理开销** | 缓存、压缩、减少中间转换、减少不必要调用 |
| **提高资源利用率** | 并发、线程池、连接池、异步处理 |
| **缩短响应时间** | 本地缓存、CDN、读写分离、负载均衡 |
| **提高吞吐量** | 消息队列、批处理、分片、水平扩展 |

> ⚠️ **读写分离的坑**：**传统自建主从**读写分离架构**存在秒级同步延迟**；
> 但**云原生存算分离**架构（如 PolarDB）共享底层存储，**可规避同步延迟，实现强一致读**。
> **答题需按题干背景判断是否写"主从延迟"** —— 题干没说是自建主从，就别自己挖坑。

### 可用性战术

| 战术类别 | 具体措施 |
|---------|---------|
| **故障检测** | 心跳检测、Ping/Echo、超时检测、健康检查 |
| **故障恢复** | 主备切换、集群选举、数据恢复、事务补偿 |
| **故障预防** | 冗余部署、熔断、限流、降级、隔离 |
| **容错设计** | 无状态服务、多副本、分布式存储、故障隔离 |

### 安全性战术

| 战术类别 | 具体措施 |
|---------|---------|
| **抵抗攻击** | 认证、授权、加密、数字签名、输入校验 |
| **检测攻击** | 入侵检测、异常行为检测、审计日志 |
| **从攻击中恢复** | 备份恢复、追踪定位、访问控制重置 |
| **隐私保护** | 脱敏、加密存储、最小权限、访问审计 |

### 可修改性战术

| 战术类别 | 具体措施 |
|---------|---------|
| **局部化修改** | 高内聚、低耦合、封装、接口抽象 |
| **防止连锁修改** | 中间层隔离、依赖倒置、接口隔离 |
| **延迟绑定** | 配置文件、插件机制、多态、规则引擎 |
| **提升扩展性** | 微服务拆分、模块化、组件化 |

### 可测试性战术

| 战术类别 | 具体措施 |
|---------|---------|
| **输入输出控制** | 接口 Mock、录制回放、测试桩 |
| **内部状态可见** | 日志、监控指标、执行链路追踪 |
| **模块可隔离** | 接口隔离、依赖注入、单元测试边界清晰 |

### 易用性战术

| 战术类别 | 具体措施 |
|---------|---------|
| **用户操作支持** | 撤销、操作提示、帮助、新手引导 |
| **界面适配** | 多端适配、字体放大、无障碍设计 |
| **降低学习成本** | 统一交互、默认值、向导式操作 |

> 💡 **记忆技巧**：可用性战术按 **"检测 → 恢复 → 预防 → 容错"** 这条时间线记；
> 可修改性战术按 **"改的范围小 → 改的不扩散 → 改的晚决定 → 改的能扩展"** 这条逻辑记。

# 第 3 部分 · 原理篇：架构评估（ATAM）

> 学这部分的目标：**能写出一条完整的质量属性场景，能分辨敏感点/权衡点/风险点/非风险点，知道什么时候用 ATAM / SAAM / CBAM。**

---

## 3.1 为什么需要"架构评估"？

因为架构方案**没有客观的对错**，只有"**在当前约束下的合适程度**"。
> 微服务好不好？对 10 人小团队做内部工具 —— 不好（运维成本远大于收益）；
> 对 500 人团队做电商平台 —— 好（可修改性价值巨大）。

**所以需要一个方法，把"合适不合适"变得可讨论、可分析、可记录。** 这就是架构评估。

> 💡 **ATAM 的核心目标（不是评判好坏！）**：
> **识别架构决策带来的质量属性收益与代价，找到权衡关系。**

---

## 3.2 三种评估方法怎么选（SAAM / ATAM / CBAM）

| 评估方法 | 核心关注点 | 典型适用场景 | 一句话选择依据 |
|---------|-----------|-------------|--------------|
| **SAAM** | **场景分析**，早期架构评估，**偏可修改性** | 架构方案**早期选择**、可修改性分析 | 处于架构**早期**、主要分析场景对架构的影响 → SAAM |
| **ATAM** | **多质量属性权衡**，敏感点 / 权衡点 / 风险点 | 架构**设计阶段**，关注质量属性冲突 | 分析**多个质量属性冲突**和架构决策敏感性 → **ATAM**（最常考） |
| **CBAM** | **成本效益分析**，架构决策经济性排序 | 需要在**成本、收益**之间做投资决策 | 需要对**多个改进方案做成本效益排序** → CBAM |

> ⚠️ **丢分点**：题目问"可采用什么架构评估方法"，**只答 ATAM 不够稳**（虽然大概率是它）。
> **建议三种都储备**，答题时先给结论（如 ATAM），再说明为什么不是另外两种，这样最稳。

> ✅ **答题写法**：
> `若重点是分析多个质量属性冲突和架构决策敏感性，应采用 ATAM；若处于架构早期、主要分析场景对架构的影响，可采用 SAAM；若需对多个改进方案做成本效益排序，可采用 CBAM。本题中……，因此采用 ATAM。`

---

## 3.3 质量属性场景六要素（必考书写格式）

### 直觉：把一句模糊的需求，拆解成 6 个精确的零件

> 模糊说法："系统要快。"
> 精确说法：**"在 10 万并发的环境下**，**用户** 对 **播放服务** 发起 **播放请求**，系统 **返回视频流**，**首帧延迟不超过 500ms**。"
>
> 后者才是一个**可度量、可验证**的质量属性场景。考试要的就是后者。

### 六要素清单（务必背到条件反射）

| # | 要素 | 回答什么问题 | 示例 |
|---|------|-------------|------|
| 1 | **刺激源 (Source)** | **谁/什么**触发了这个事件？ | 外部用户、管理员、黑客、定时任务 |
| 2 | **刺激 (Stimulus)** | **发生了什么事**？ | 发起请求、提交订单、发起攻击、节点宕机 |
| 3 | **环境 (Environment)** | 事件发生时，系统处于**什么状态**？ | 正常运行、高负载、10 万并发、降级状态 |
| 4 | **制品 (Artifact)** | **系统的哪一部分**受到影响？ | 订单服务、数据库、缓存、消息中间件、整个系统 |
| 5 | **响应 (Response)** | 系统**做出了什么反应**？ | 返回结果、切换备用节点、拒绝请求、记录日志 |
| 6 | **响应度量 (Response Measure)** | **怎么衡量**响应好不好？**必须可量化** | 3 秒内返回、年停机 < 2 小时、成功率 99.99% |

### ✅ 书写模板（直接套）

> `在【环境】条件下，【刺激源】对【制品】发起【刺激】，系统需要完成【响应】，并且达到【响应度量】。`

### ⚠️⚠️ 头号丢分点：漏写"制品"

> **制品（Artifact）= 受该场景影响的架构元素**，可以是某个模块、服务、数据库、消息中间件、网络链路、整个系统等。
>
> **答题没写"制品"，容易被判定场景不完整，直接丢分。**
> 这是**最高频的漏写点**，没有之一 —— 因为很多考生根本不知道还有这一项。
>
> 📌 **术语提示**：官方教材中这一项有时表述为 "**制品 / 构架 / 受影响的架构元素**"（英文 Artifact）。
> **答题时写"制品"最稳妥**（阅卷老师习惯看这个词），心里清楚它 = "受影响的架构元素" 即可。

### 完整示例（照着这个格式练）

**示例 1 · 可用性场景**
> `在正常运行环境下，外部用户对支付服务发起一次请求，支付服务在 3 秒内返回结果，且服务中断时间每年不超过 2 小时。`

| 要素 | 内容 |
|------|------|
| 刺激源 | 外部用户 |
| 刺激 | 发起支付请求 |
| 环境 | 正常运行 |
| 制品 | **支付服务** |
| 响应 | 返回支付结果 |
| 响应度量 | 3 秒内返回；年中断 ≤ 2 小时 |

**示例 2 · 性能场景（直播）**
> `在高峰期并发 10 万用户观看直播的环境下，外部用户对播放服务发起播放请求，播放服务返回视频流，平均首帧延迟不超过 500ms。`

| 要素 | 内容 |
|------|------|
| 刺激源 | 外部用户 |
| 刺激 | 发起播放请求 |
| 环境 | 高峰期并发 10 万用户观看 |
| 制品 | **播放服务 / CDN 分发服务** |
| 响应 | 返回视频流 |
| 响应度量 | 平均首帧延迟 ≤ 500ms |

### ⚠️ 场景书写的三个扣分陷阱

1. ❌ **只写定性描述，没有响应度量** → 场景不完整，丢分
   - ✅ 必须有数字："3 秒内""99.99%""≤ 500ms"
2. ❌ **漏写"制品"** → 场景不完整，丢分（**最高频**）
3. ❌ **场景过于宽泛，没对应到具体系统组件** → 脱离题干，丢分
   - ✅ 要写"播放服务"，不要只写"系统"

## 3.4 效用树（Utility Tree）

### 直觉：把"系统要好"这句话，拆成一棵可管理的树

```
效用(Utility)                        ← 根节点：系统的整体"好"目标
├── 性能                              ← 第二层：质量属性
│   └── 高峰期查询响应 < 500ms          ← 第三层：具体质量属性场景
│        └── (H, M)                  ← 叶子：场景优先级(H/M/L) + 实现难度(H/M/L)
├── 可用性
│   └── 单节点宕机后 30 秒内自动切换
│        └── (H, H)
└── 可修改性
    └── 新增支付方式 2 周内上线
         └── (M, M)
```

### 考试要写清楚的四层含义

1. **根节点** = 系统整体效用（Utility）
2. **第二层** = 质量属性（性能 / 可用性 / 可修改性 / 安全性 / 可测试性……）
3. **第三层** = 具体的质量属性场景
4. **叶子节点** = 标注 **场景优先级** 与 **实现难度**（如 `(H, H)` = 高优先级、高难度）

### 标注示例
```
性能(H)   ── (i) 查询响应 < 0.3s  (H, M)
可用性(H) ── (b) 故障自动切换      (H, H) ── (j) 3 分钟内发现故障 (M, M)
```

> 📌 **考试一般不会要求画完整树**。
> 常考形式是：**给出效用树，让你从中找出敏感点、权衡点**。
> 也可能让你**补全某个质量属性下的场景**（此时按六要素写）。

---

## 3.5 ⚠️ 丢分重灾区 #3：敏感点 / 权衡点 / 风险点 / 非风险点

> 这是 ATAM 的**四个核心概念**，也是**最容易混淆、最容易丢分**的地方。
> 请记住一个大前提：

> ⭐ **大前提（头号考点）**：
> **敏感点、权衡点、风险点指的是「架构决策 / 架构要素」，而不是「质量属性需求 / 指标」本身。**
> 例如："响应时间 0.5 秒"是**性能指标**；影响它的**缓存策略、调用链路长度、CDN 节点数**才是**性能的敏感点**。

---

### 3.5.1 敏感点（Sensitivity Point）

**定义**：**某一个架构决策**会显著影响**单一一项**质量属性。改变它，该属性明显变化。

**✅ 正确例子**
- **缓存的最大内存大小**是**性能**的敏感点：调大 → 命中率上升、响应时间显著改善；调小 → 性能明显下降。
- **CDN 节点的部署位置与数量**是**性能（延迟）**的敏感点：离用户越近、节点越多，延迟越低。
- **数据库索引设计**是**查询性能**的敏感点。
- **副本数量**是**可用性**的敏感点。

**❌ 错误说法（高频丢分）**
> ❌ "响应时间 0.5 秒是性能的敏感点。"
> - **错在哪**：响应时间是指标，不是决策。
> ✅ 应为："**缓存策略**是性能的敏感点，它显著影响响应时间能否达到 0.5 秒的要求。"

**速记**：`敏感点 → 一个决策，影响一个属性。`

---

### 3.5.2 权衡点（Tradeoff Point）

**定义**：**某一个架构决策**，**同时**正向影响**一个**质量属性、负向影响**另一个**质量属性。

**✅ 正确例子**
- **引入冗余服务**：提升**可用性**（利），但增加成本与运维复杂度、**性能**因同步开销下降（弊） → **可用性-性能权衡点**
- **引入消息中间件**：提升**可用性**（异步解耦、故障隔离），但增加转发开销、**性能**下降 → **可用性-性能权衡点**
- **微服务拆分粒度**：拆得越细，隔离性和可扩展性越好，但运维与分布式事务复杂度越大 → **可修改性-性能/可测试性权衡点**
- **增大 RAG 的 Top-K**：问答**准确性**提升，但**性能**（时延）下降 → **准确性-性能权衡点**
- **增加数据副本数**：**可用性**提升，**一致性/性能**下降 → **可用性-一致性权衡点**

**❌ 错误说法**
> ❌ "引入缓存是权衡点，它提升了性能。"（只写了收益）
> - **错在哪**：只写一个属性变化，那是"敏感点"或"优点"，不是权衡点。

**✅ 标准答题句式（背下来）**
> `【某决策】提升了【A 质量属性】，但同时导致【B 质量属性】下降，因此它是 A 与 B 之间的权衡点。`

**速记**：`权衡点 → 一个决策，一升一降，至少两个属性。`

---

### 3.5.3 风险点（Risk）

**定义**：**当前某个架构决策**存在**潜在负面后果**，未来有可能引发质量属性问题。

**答题三要素**：`【架构决策】 + 【潜在影响】 + 【涉及的质量属性】`

| 架构决策 | 风险点说明 |
|---------|-----------|
| 数据库**单点部署** | 数据库故障导致整个系统不可用，是**可用性**风险点 |
| 消息中间件**单点部署** | 所有事件依赖该中间件，一旦故障影响系统通信，是**可用性**风险点 |
| 微服务之间**强耦合** | 一个服务变更影响多个服务，是**可修改性**风险点 |
| 缓存与数据库**一致性策略不明确** | 可能导致脏读或数据错误，是**一致性/可靠性**风险点 |
| **未做限流降级** | 流量突增可能压垮核心服务，是**可用性**风险点 |

**速记**：`风险点 → 一个决策，有隐患（决策 + 影响）。`

---

### 3.5.4 非风险点（Non-Risk）

**定义**：**当前某个架构决策**对于**某项质量属性不会带来负面影响**，是安全、可靠的选择。

> ⚠️ **丢分点（非常重要）**：
> **非风险点 ≠ 优点！**
> 非风险点是对"**某项决策不会造成负面影响**"的**判断**，而不是在夸这个决策多好。
> 很多考生要么**忘了写非风险点**，要么**把非风险点写成了优点的罗列** —— 都丢分。

**✅ 通用答题模板（防漏分必背）**
> `【架构决策，如：数据库主备部署】对于【质量属性，如：可用性】而言属于非风险点。因为该决策采用了【具体策略，如：冗余机制】，能够有效避免【潜在风险，如：单点故障】，在当前业务量级下不会造成负面影响。`

**✅ 示例**
> `采用 Redis 集群部署对于系统可用性而言属于非风险点。因为集群模式提供了数据分片与副本冗余，有效避免了缓存单点故障导致的数据丢失和服务中断，在当前并发量级下不会造成可用性风险。`

| 架构决策 | 非风险点说明 |
|---------|-------------|
| 使用成熟关系型数据库并配置主备 | 对**可用性**不构成明显风险 |
| 用户界面采用统一组件库 | 对**可修改性**通常无明显负面影响 |
| 对日志进行异步写入 | 合理设计下不会显著影响核心业务的**可用性** |

**速记**：`非风险点 → 一个决策，无隐患。`

---

### 3.5.5 四概念速记口诀 + 一张表总览

> 🎵 **口诀**：
> ```
> 敏感点 → 影响一个属性（决策层面）
> 权衡点 → 一升一降，两个属性
> 风险点 → 有隐患（决策 + 影响）
> 非风险点 → 无隐患
> ```

| 概念 | 涉及几个属性 | 方向 | 指的是 | 一句话 |
|------|------------|------|--------|--------|
| **敏感点** | 1 个 | 单一方向 | 架构决策 | "改它，这个属性就明显变" |
| **权衡点** | ≥ 2 个 | 一升一降 | 架构决策 | "改它，一个变好、一个变差" |
| **风险点** | ≥ 1 个 | 有负面隐患 | 架构决策 | "这个决策埋了雷" |
| **非风险点** | ≥ 1 个 | 无负面影响 | 架构决策 | "这个决策没问题" |

## 3.6 ABSD · 基于架构的软件开发方法（六步必背）

### 3.6.1 核心思想

**ABSD（Architecture-Based Software Design）**：强调**架构先行**，以**质量属性 + 功能需求**双驱动，**自顶向下递归细化**。

三个要点：
1. **不是**等需求完全明确才开始设计 —— 而是**架构驱动**：先识别关键质量属性与功能需求，再派生架构
2. 采用**递归分解**：系统 → 构件（粗粒度） → 子构件，逐层细化
3. **复用架构风格/模式**：以成熟风格（分层、微服务、事件驱动等）作为构件组织依据

### 3.6.2 开发流程（六步，必背答题链）

| # | 阶段 | 做什么 |
|---|------|--------|
| 1 | **架构需求** | 获取需求，标识**质量属性**与功能需求，建立**需求质量属性场景** |
| 2 | **架构设计** | 选择架构风格/模式，生成候选架构，用**效用树**组织质量属性 |
| 3 | **架构文档化** | 产出架构规格说明书、各种视图（逻辑/进程/部署视图等），便于传递与评审 |
| 4 | **架构复审（评估）** | 用 **ATAM / SAAM / CBAM** 评估架构，识别**风险点/敏感点/权衡点** |
| 5 | **架构实现** | 按架构构件化开发，构件按接口契约实现，控制耦合 |
| 6 | **架构演化** | 随需求变化迭代演化，**回到需求/设计闭环** |

> ✅ **答题模板（ABSD 流程题，直接背）**
> `ABSD 以架构为核心，依次经历 **架构需求 → 架构设计 → 文档化 → 复审评估（ATAM）→ 实现 → 演化** 六个阶段；其中复审阶段用 ATAM 识别质量属性权衡与风险点，需求变化会触发架构演化，回到需求/设计闭环。`

### 3.6.3 CBAM 六步（成本效益分析详细步骤）

| # | 步骤 |
|---|------|
| 1 | **整理 ATAM 候选策略**（来自效用树中的架构策略） |
| 2 | **确定场景与优先级**（对质量属性场景按重要性排序） |
| 3 | **量化收益 Benefit**（每个策略对场景的质量属性提升打分，0~100 相对效用） |
| 4 | **估算成本 Cost**（开发/迁移/运维成本、进度影响） |
| 5 | **计算 ROI / 优先级**（ROI = 收益 / 成本，按 ROI 与风险排实施顺序） |
| 6 | **输出决策建议**（给出"先投入哪个策略"的排序） |

> ✅ **答题模板**
> `在 ATAM 评估的基础上，采用 CBAM 对候选架构改进策略做成本效益分析：先量化各策略对质量属性场景的**收益**，再估算**成本**，计算 **ROI = 收益 / 成本**，按 ROI 与实施风险排序，优先实施高收益低成本的策略。`

# 第 4 部分 · 实战篇：考试怎么考、怎么答

> 到这里原理都讲完了。这一部分回答三个问题：
> **① 题目长什么样？② 我该怎么组织答案？③ 哪些话一写就扣分？**

---

## 4.1 试题一的三问套路（看清命题人的心思）

试题一（必答，25 分）**几乎恒定是三问**，而且三问的**难度和功能是固定分工**的：

| 问 | 典型分值 | 考什么 | 命题人的目的 | 新手常见死法 |
|---|---------|-------|-------------|-------------|
| **问题 1** | 6~8 分 | **识别与概念**：这是什么架构风格？两个风格有什么区别？某需求属于什么质量属性？ | 送分题，看你会不会认 | 概念没分清（仓库 vs 黑板），或者**不结合题干**只默写定义 |
| **问题 2** | 8~10 分 | **分析**：从 XX 质量属性角度，分析该方案的**收益与代价** | 拉开差距的题，看你有没有**权衡思维** | **只写收益不写代价**（丢一半分）；或**只默写理论不提场景**（丢一半分） |
| **问题 3** | 9~12 分 | **论证**：解释什么是权衡点/敏感点，并结合项目说明；或给出改进方案并说明道理 | 最高分题，看你能不能**论证** | 定义写对了但**不结合项目**；或权衡点只写一个属性 |

### 🔑 命题的底层逻辑（看透这个，答题就不慌）

```
问题1（是什么）  →  问题2（好在哪、坏在哪）  →  问题3（凭什么这么判断、代价怎么权衡）
    ↓                      ↓                            ↓
  考识别                 考分析                      考论证
```

**所有三问加起来，考的就是一件事：你能不能有依据地做架构决策，并且诚实地承认代价。**

---

## 4.2 五大题型逐一给模板

### 题型 A · 风格识别题（"该系统采用了什么架构风格？"）

**答题结构**：`结论 + 2~3 条题干依据 + 一句话归属大类`

**✅ 模板**
> `该系统采用了【XX 架构风格】（属于【XX 风格大类】）。判断依据：
> ① 题干提到"【原文关键词1】"，符合该风格【特征1】；
> ② 题干提到"【原文关键词2】"，符合该风格【特征2】；
> ③ 该风格适用于【场景特点】，与本系统【场景描述】相符。`

**⚠️ 丢分点**
- ❌ 只写结论不写依据 —— 万一结论错了，**一分都拿不到**；写了依据，即使结论有争议，也能拿到过程分
- ❌ 不写"归属于哪个大类" —— 少一个踩分点

**✅ 保险写法示例**
> `该系统采用事件驱动架构（属于独立构件风格）。依据：题干中"订单服务通过事件消息异步通知库存、积分、短信模块，且不需要感知下游模块的存在"，符合事件驱动架构"发布-订阅、隐式调用、构件解耦"的核心特征。`

---

### 题型 B · 风格对比题（"请简述 A 与 B 的主要区别"）

**答题结构**：`分点对比，每点"一个维度 + A 怎样 + B 怎样"`

**对比维度清单**（不知道比什么时，从这里面挑 3~4 个）：

| 可比的维度 | 说明 |
|-----------|------|
| **通信方式** | 显式调用 vs 隐式调用 / 直接调用 vs 经由中间件 |
| **耦合程度** | 紧耦合 vs 松耦合；构件是否知道对方存在 |
| **控制方式** | 集中控制 vs 无中央控制 vs 主动调度 |
| **数据管理** | 共享数据库 vs 独立数据库 |
| **部署方式** | 单体部署 vs 独立部署 |
| **适用/不适用** | 各自适合什么场景 |

**✅ 示例：分层架构 vs 事件驱动架构**
> `1. 通信方式：分层架构中，模块之间通过**显式调用**完成通信，调用方必须知道被调用方；事件驱动架构采用**发布-订阅的隐式调用**，发布方不需要知道订阅方。
> 2. 耦合程度：分层架构**依赖明确、耦合较强**；事件驱动架构模块之间**解耦**，新增订阅方无需改动发布方。
> 3. 控制方式：分层架构由上层**逐层向下调用**，控制流清晰；事件驱动架构**没有中央控制**，各构件独立响应事件。`

**⚠️ 丢分点**
- ❌ 写成"A 的优点是……；B 的优点是……" —— 这叫**罗列**，不叫**对比**。对比必须在**同一个维度**上说两者的差异。
- ❌ 只说一面（"分层的缺点是耦合强"），没说另一面。

---

### 题型 C · 收益代价分析题（"从 XX 属性角度分析收益与代价"）⭐ 最高频

**这是决定你能不能上 20 分的题。** 结构必须完整。

**答题结构（四段式，缺一不可）**

```
【第1段】总述：该方案采用了【XX 架构/策略】。
【第2段】收益（逐属性展开，每个属性：属性名 + 具体表现 + 结合题干场景）
【第3段】代价（逐属性展开，同上）
【第4段】权衡结论（用黄金句式收尾）
```

**✅ 完整示例（某电商重构为事件驱动架构）**
> **收益：**
> 1. **可修改性（收益）**：业务模块之间解耦，新增、修改下游业务模块（如新增"发优惠券"）时，不需要改动订单服务的代码，可修改性提升。
> 2. **可用性（收益）**：模块之间异步解耦，单个订阅模块故障不会反向影响发布方，故障得到隔离，可用性提升。
>
> **代价：**
> 3. **性能（代价）**：事件消息需经中间件转发，产生异步延迟；高并发场景下消息队列堆积可能造成响应变慢，带来性能损耗。
> 4. **可测试性（代价）**：异步事件链路的执行顺序不可见，模块之间的执行时序难以追踪，系统整体可测试性下降。
>
> **权衡结论：**
> 采用事件驱动架构能够提升系统的可修改性与可用性；但是会带来性能损耗与可测试性下降的代价，需要在架构设计中进行权衡。可通过幂等设计、消息确认机制、链路追踪等手段缓解上述代价。

**⚠️ 三大丢分点（本题型的命门）**
1. ❌ **只罗列通用优缺点，完全不提题干场景** → 扣一半分数
   - ✅ 每个属性后面**必须带上题干里的具体东西**（"新增发优惠券模块""订单服务""10 万并发"）
2. ❌ **只写收益不写代价** → 不是分析，是推销，直接丢一半分
3. ❌ **说违背架构规律的话**（"事件驱动一定提升性能""微服务提升性能"）→ 见 4.3 禁句黑名单

---

### 题型 D · 概念论证题（"什么是权衡点？为什么本项目的 XX 决策属于权衡点？"）

**答题结构**：`定义（准确，带关键限定词） + 结合题干分析（一升一降） + 结论`

**✅ 模板（权衡点）**
> `**定义**：权衡点是指一个架构决策，**同时**正向影响一个质量属性、负向影响另一个质量属性，即影响多个质量属性且效果相互冲突。
>
> **结合本项目**：本项目中引入【XX 决策】：
> - **正向收益（【属性A】）**：……（说明它如何让 A 变好）
> - **负面代价（【属性B】）**：……（说明它如何让 B 变差）
>
> **结论**：因此，该决策是【属性A】与【属性B】之间的权衡点。`

**✅ 模板（敏感点）**
> `**定义**：敏感点是指某个架构决策会显著影响**单一一项**质量属性。
> **结合本项目**：【XX 决策】是【属性】的敏感点，因为调整它会直接导致【该属性的量化指标】发生明显变化（如：调大缓存容量，响应时间显著下降）。`

**✅ 模板（风险点 / 非风险点）**
> `**风险点**：【架构决策】存在【潜在负面后果】，是【质量属性】的风险点。
> **非风险点**：【架构决策】对于【质量属性】而言属于非风险点，因为该决策采用了【具体策略】，有效避免了【潜在风险】，在当前【业务量级】下不会造成负面影响。`

**⚠️ 丢分点**
- ❌ 定义写对了，但**不结合项目** → 只能拿定义的分（约 1/3）
- ❌ 权衡点**只写收益不写代价** → 直接判定为不理解权衡点
- ❌ 把**指标**当成敏感点（"响应时间 0.5 秒是敏感点"）

---

### 题型 E · 改进方案题（"请给出改进方案并说明理由"）

**答题结构**：`决策陈述 → 具体措施 → 支持的质量属性 → 代价与缓解`

**✅ 模板**
> `**决策**：建议采用【XX 方案】。
> **措施**：具体包括 ①…… ②…… ③……
> **收益**：该方案能够提升系统的【属性A】，因为……
> **代价与缓解**：但该方案会带来【属性B】的下降，可通过【缓解措施】加以控制。
> **结论**：综合来看，在当前【约束条件】下，该方案是合理的权衡。`

## 4.3 ⚠️ 致命禁句黑名单（写了大概率扣分）

> **考前必背。以下句子一旦写出，整道小题分数几乎清零。**

| # | ❌ 禁句 | ✅ 正确说法 |
|---|--------|------------|
| 1 | **微服务架构可以提升系统整体性能** | 微服务大量远程调用通常**带来性能下降**；收益是**可修改性、可用性、可伸缩性**提升 |
| 2 | **事件驱动架构 / 消息队列一定降低响应延迟 / 一定提高性能** | 事件驱动可提升**吞吐量、可用性、可修改性**；但异步通信可能**增加端到端延迟**，并带来事务一致性难题 |
| 3 | **读写分离架构一定存在主从延迟** | **传统自建主从**确实有秒级同步延迟；但**云原生存算分离**共享存储架构（如 PolarDB）可规避，实现强一致读 |
| 4 | **黑板架构就是数据库系统 / 使用了数据库就是仓库架构** | 数据库只是**存储**，属于**仓库架构**；黑板的核心是"**主动调度知识源**" |
| 5 | **权衡点只会提升某一项质量属性（无负面影响）** | 权衡点**必须同时带来收益 + 负面影响**，**至少涉及两个质量属性** |
| 6 | **质量属性指标（如响应时间 0.5 秒）是敏感点** | 敏感点永远是**架构决策**，不是指标本身；指标是度量，影响它的决策才是敏感点 |

### 配套的八条避雷清单（理解版）

| # | ❌ 错误观点 | ✅ 正确结论 |
|---|------------|------------|
| 1 | 微服务一定性能更好 | 微服务大量远程调用，相比单体通常**性能下降**；收益是可修改性、可用性 |
| 2 | 分层架构一定可修改性高 | **只有严格遵守单向分层、职责清晰时**才高；分层混乱、跨层调用时可修改性反而更差。**一切以题干描述为准** |
| 3 | 只要出现消息、异步，就是事件驱动架构 | 异步消息只是**技术手段**；要看**业务构件是否解耦、是否采用发布-订阅的隐式调用模式**。普通单体内部异步队列 ≠ 事件驱动架构 |
| 4 | 黑板架构 = 使用了数据库 | 数据库只是存储；黑板核心是**主动调度知识源模块**，普通数据库系统属于**仓库架构** |
| 5 | 架构风格优点可以无脑全写上 | **优点缺点必须结合场景**，题干中不存在的特点不要凭空罗列 |
| 6 | 事件驱动架构一定提高性能 | 见上方"分场景"分析（吞吐↑、可用↑、可修改↑，但端到端延迟↑、可测试↓、一致性保障难度↑） |
| 7 | 微服务架构可用性一定好 | 微服务**有助于**提升可用性，但**服务治理/监控/容错/熔断/链路追踪能力不足时**，反而因分布式复杂度**降低**整体可用性 |
| 8 | 响应时间 0.5 秒是敏感点 | 响应时间是**性能指标**；**缓存策略、调用链路长度、CDN 节点数**等架构决策才是敏感点 |

### 句式 1 · 黄金权衡句（最高频踩分点）
> `采用 XX 架构风格，可以提升系统的【可修改性/可用性】；但会带来【性能下降、调试困难、分布式事务复杂】等代价，需要在方案中进行权衡。`

### 句式 2 · 收益代价句
> `XX 方案在【A 质量属性】方面收益为……；代价为……；该决策同时带来收益和负面影响，属于 XX 与 XX 之间的权衡点。`

### 句式 3 · 风格识别句
> `该系统采用【XX 架构风格】（属于【XX 风格大类】），判断依据为：题干中"……"符合该风格"……"的核心特征。`

### 句式 4 · 场景书写句
> `在【环境】条件下，【刺激源】对【制品】发起【刺激】，系统需要完成【响应】，并且达到【响应度量】。`

### 句式 5 · 战术选择句
> `为满足【某质量属性】需求，可采用以下架构战术：①【战术类别1】，具体措施为……；②【战术类别2】，具体措施为……。`

### 句式 6 · 缓解措施句（写了这个显得你考虑周全，容易加分）
> `针对上述代价，可通过【幂等设计 / 消息确认机制 / 分布式链路追踪 / 熔断降级 / 分布式事务补偿】等手段加以缓解。`

## 4.5 时间分配与卷面组织

| 项目 | 建议 |
|------|------|
| **试题一时间** | **35~40 分钟**（必答题，值得多花时间） |
| 审题 | 5 分钟：**圈出题干关键词**（架构词、数字、需求词） |
| 构思 | 5~10 分钟：在草稿上列出"风格 / 属性 / 收益 / 代价 / 权衡点"五个关键词 |
| 作答 | 20~25 分钟 |
| 检查 | 2~3 分钟：检查**有没有漏答**、**场景六要素全不全**、**权衡点有没有写代价** |

### 卷面组织的三条建议

1. **分点编号，每点一个属性**：阅卷是踩点给分，结构清晰 = 不漏点。
   ```
   1. 可修改性（收益）：……
   2. 可用性（收益）：……
   3. 性能（代价）：……
   4. 可测试性（代价）：……
   ```
2. **把属性名写在句首加粗**：让阅卷老师一眼看到踩分点。
3. **每点都要带题干里的具体名词**：这是"结合场景"的最低成本做法。

## 5.1 例题 A 组：风格识别（5 小题，打基础）

### 习题 A1
> 某图像处理系统，存在一个公共的数据存储区。多个算法模块读取存储区中的图像数据，**各个算法模块独立决定何时读取、何时写入结果**。该系统最可能采用哪种架构风格？

<details>
<summary>👉 点击查看答案与解析</summary>

**答案：仓库（知识库）架构**

**解析**：
- 判断关键在"**各个算法模块独立决定何时读取**" → 说明**控制权在各个模块自己手里**，中央数据是**被动**的。
- 这正是仓库与黑板的分水岭：仓库被动，黑板主动调度。
- 注意陷阱：虽然是"图像处理"，容易联想到黑板；但题干**没有**"根据进度自动调度""多个知识源协同求解""无确定解法"等黑板关键词，所以不是黑板。

**答题写法**：
> 该系统采用**仓库（知识库）架构**。依据：系统存在中央共享数据存储区，各算法模块**主动、自主**地决定读写时机，中央数据存储区仅提供数据共享、不参与调度，符合仓库架构"共享数据中心 + 客户端主动访问"的特征。
</details>

---

### 习题 A2
> 一个语音识别系统，待识别音频数据放入公共缓冲区。系统**会根据当前识别进度，自动调度**声学模型、语义分析等多个模块轮流工作。**模块之间互不直接通信**。请判断架构风格。

<details>
<summary>👉 点击查看答案与解析</summary>

**答案：黑板架构**

**解析**：三个关键词全部命中：
1. "**根据当前识别进度，自动调度**" → 中央数据主动调度 → 黑板
2. "**模块之间互不直接通信**" → 知识源之间不直接通信，只看黑板 → 黑板
3. "语音识别" → 无确定性求解算法的典型场景 → 黑板

**答题写法**：
> 该系统采用**黑板架构**（属于仓库风格）。依据：① 系统存在中央共享数据区（黑板），存放待求解数据；② 黑板**根据当前求解进度主动调度**各知识源轮流工作，承担了**控制调度**职责；③ 各知识源之间**互不直接通信**，仅通过黑板协同求解；④ 语音识别属于**无确定性求解算法**的复杂问题。以上特征符合黑板架构。
</details>

### 习题 A3
> 电商系统采用**发布-订阅模式**，订单完成之后，通过**事件消息异步通知**库存、积分、短信模块；**订单服务不需要感知下游模块的存在**。该架构风格为？

<details>
<summary>👉 点击查看答案与解析</summary>

**答案：事件驱动架构（隐式调用），属于独立构件风格**

**解析**："发布-订阅""异步通知""不需要感知下游模块的存在" —— 三个都是事件驱动的标准关键词。

**答题写法**：
> 该系统采用**事件驱动架构（隐式调用）**，属于**独立构件风格**。依据：订单服务作为事件发布方，通过事件消息异步通知下游模块；发布方**不需要感知订阅方的存在**，双方通过消息中间件解耦，符合"发布-订阅、隐式调用、构件独立运行"的特征。
</details>

### 习题 A4
> 企业内部系统所有业务模块**必须经过一条中央总线**完成通信，各个异构系统通过总线完成数据交互。该架构偏向？

<details>
<summary>👉 点击查看答案与解析</summary>

**答案：SOA（面向服务架构，ESB 企业服务总线）**

**解析**："**中央总线**" + "**异构系统**" = ESB + 企业集成 = SOA。
注意：如果是"禁止构件直接调用、必须经过连接器"→ C2；这里是"企业异构系统通过总线集成" → SOA。

**答题写法**：
> 该系统偏向 **SOA 面向服务架构**。依据：系统采用**企业服务总线（ESB）**作为中央通信枢纽，各异构业务系统通过总线完成协议转换、消息路由与数据交互，符合 SOA"服务松耦合 + ESB 集中集成"的特征，适用于**大型异构企业系统集成**场景。
</details>

### 习题 A5
> 系统严格规定**上层模块可以调用下层模块，下层不能反向调用上层**，每层职责独立。该架构风格是？

<details>
<summary>👉 点击查看答案与解析</summary>

**答案：分层架构，属于调用/返回风格**

**答题写法**：
> 该系统采用**分层架构**，属于**调用/返回风格**。依据：系统按职责划分为若干层，层与层之间**单向依赖**，上层通过**显式调用**访问下层，下层不得反向调用，符合分层架构"关注点分离、单向依赖"的核心约束。
</details>

## 5.2 例题 B 组：质量属性判断（6 小题）

### 习题 B1
> "系统需在**故障后 5 分钟内恢复**服务。" 属于什么质量属性？
<details><summary>👉 答案</summary>

**可用性**。
理由：强调的是"坏了多久能恢复"，这是 **MTTR（平均修复时间）**，属于可用性范畴。
**答题注意**：可靠性关注"多久坏一次"（MTBF），可用性关注"坏了多久能好 + 能用时间的比例"（MTTR 与 MTBF 共同决定）。本题说的是恢复时间 → 可用性。
</details>

### 习题 B2
> "新增一种支付方式，需在 **2 周内**完成开发上线。" 属于什么质量属性？
<details><summary>👉 答案</summary>

**可修改性（可扩展性）**。
理由：考查的是"**增加新功能的成本与速度**"。
**易错点**：不要答成易用性 —— 易用性是"**用户**用起来顺不顺手"，跟开发工期无关。
</details>

### 习题 B3
> "系统需支持**从 x86 架构迁移到 ARM 架构**。" 属于什么质量属性？
<details><summary>👉 答案</summary>

**可修改性（可移植性）**。
理由：更换运行平台/环境的能力 = 可移植性，是可修改性的子属性。
</details>

### 习题 B4
> "用户量增长 300% 后，系统可通过**增加服务器节点**维持原有响应速度。" 属于什么质量属性？
<details><summary>👉 答案</summary>

**可伸缩性（Scalability）** —— 它是可修改性的子属性。
**答题策略**：优先直接写"**可伸缩性**"，比写"可修改性"更精准、更贴合阅卷踩分点。
保险写法：`可伸缩性（可修改性的子属性）`。
**辨析**：如果题干只说"高峰期响应要 < 1 秒" → 那是**性能**；加上"**靠加节点**维持" → 才是**可伸缩性**。
</details>

### 习题 B5
> "**模型推理 P99 延迟 ≤ 2 秒**。" 属于什么质量属性？
<details><summary>👉 答案</summary>

**性能**。
理由：P99 延迟是性能指标（99% 的请求在 2 秒内完成）。
**提示**：看到 P99 / P95 / 响应时间 / 吞吐量 / TPS / QPS → 一律是性能。
</details>

### 习题 B6
> "系统需支持**老年人和残障人士**使用界面。" 属于什么质量属性？
<details><summary>👉 答案</summary>

**易用性**。
理由：无障碍设计（字体放大、屏幕阅读器适配、操作简化）属于易用性的典型战术。
**易错点**：不要因为"要测试能不能用"就答成可测试性 —— 易用性关注的是**用户的使用体验**。
</details>

## 5.4 例题 D：三个概念辨析

### 题目
> 某系统架构中有以下三个决策，请分别判断它们是**敏感点、权衡点还是风险点**，并说明理由：
> ① 将缓存容量从 2GB 调整为 8GB；
> ② 数据库采用单点部署，未做主备；
> ③ 引入消息中间件实现模块间异步解耦。

<details>
<summary>👉 点击查看参考答案</summary>

**① 缓存容量调整 → 性能的敏感点**
> 缓存容量是一个**架构决策**，它显著影响**单一**质量属性——**性能**：调大缓存容量，缓存命中率上升，系统响应时间明显下降；调小则命中率下降、性能明显变差。因此它是**性能的敏感点**。
>
> ⚠️ 注意：如果题干要求分析"缓存容量增大虽然提升性能，但增加内存成本和数据不一致风险"，那么它同时也可以作为**性能-一致性/成本的权衡点**。**判断取决于题目给了你几个属性**。

**② 数据库单点部署 → 可用性的风险点**
> 数据库单点部署是一个**架构决策**，它存在**潜在负面后果**：一旦该数据库发生故障，整个系统将无法提供服务。因此它是**可用性的风险点**。
>
> 📌 答题三要素：**决策（单点部署） + 影响（整体不可用） + 质量属性（可用性）**。

**③ 引入消息中间件 → 可用性-性能的权衡点**
> 引入消息中间件是一个**架构决策**，它**同时**影响两个质量属性且方向相反：
> - **正向收益（可用性）**：实现模块间异步解耦，单个订阅方故障不会反向影响发布方，故障被隔离，可用性提升；
> - **负面代价（性能）**：消息需经中间件转发、排队与存储，产生额外开销与异步延迟，性能下降。
>
> 因此该决策是**可用性与性能之间的权衡点**。
>
> ⚠️ 如果只写"提升可用性"→ 那是敏感点/优点，**不是**权衡点，直接丢分。
</details>

## 5.5 例题 E：完整真题大题（25 分）· 五步法示范

> 这一题是**最接近真实考试**的完整演练。请务必先自己写一遍，再看解析。

### 【题干】

> 某软件公司拟开发一套线上教育平台，初期采用**单体分层架构**。随着用户规模快速增长，出现**模块迭代困难**、**某一个业务故障会造成整个平台不可用**等问题。项目组计划将系统重构为**事件驱动架构**，采用**发布-订阅模式**完成模块之间的通信。

**问题 1（6 分）**：请简述分层架构与事件驱动架构的主要区别。

**问题 2（9 分）**：从**可修改性、可用性、性能、可测试性**四个质量属性角度，分析重构为事件驱动架构之后可能带来的**收益与代价**。

**问题 3（10 分）**：项目组引入**消息中间件作为事件总线**。该决策被评估为**可用性-性能之间的权衡点**。请解释**什么是权衡点**，并结合本项目说明**为什么该决策属于权衡点**。

---

### 📖 五步法解析

#### 第 1 步：题干线索标注（从原文抓取关键信息）

在草稿纸上圈出这些词：

| 线索 | 内容 | 它能推出什么 |
|------|------|-------------|
| 现状 | **单体分层架构** | 问题1 要对比的对象 |
| 痛点 1 | **模块迭代困难** | → 可修改性差（为什么要重构） |
| 痛点 2 | **某业务故障导致整个平台不可用** | → 可用性差，缺故障隔离 |
| 改造方案 | **事件驱动架构 + 发布-订阅** | 问题1、2 的核心 |
| 新增组件 | **消息中间件事件总线** | 问题3 的分析对象 |
| 关键词 | **权衡点、可用性-性能** | 问题3 已经告诉你方向了！ |

> 💡 **审题技巧**：问题 3 里那一句"可用性-性能的权衡点"，**等于命题人把一半答案告诉你了**。
> 你只需要论证：**为什么对可用性是收益、对性能是代价**。这大大降低了难度。
> **所以一定要把三问都读完再动笔** —— 后面的问题常常给前面的问题提示。

#### 第 2 步：解题思路推导

| 问题 | 要答什么 | 用什么工具 |
|------|---------|-----------|
| 问题1 | 对比两种架构的**核心通信方式与耦合度** | 1.6 对比维度清单（通信方式 / 耦合度 / 控制方式） |
| 问题2 | **逐属性**写明收益与代价，**必须结合线上教育平台场景** | 1.4 风格-质量属性对照表 + 4.2 题型 C 四段式 |
| 问题3 | 先默写**权衡点定义**，再分析**一升一降** | 3.5.2 权衡点 + 4.2 题型 D 模板 |

#### 第 3 步：高分参考答案

##### 问题 1 参考答案（6 分）

> **1. 通信方式不同**：分层架构中，模块按照层级划分，模块之间通过**显式调用**完成通信，调用方必须明确知道被调用方，依赖关系明确；事件驱动架构中，模块之间采用**发布-订阅的隐式调用**，发布方不需要知道订阅方的存在。
>
> **2. 耦合程度不同**：分层架构上层调用下层，**耦合较强**；事件驱动架构发布方与订阅方通过事件总线**解耦**，新增或删除订阅方无需改动发布方代码。
>
> **3. 控制方式不同**：分层架构由上层逐层向下调用，**控制流清晰**；事件驱动架构各构件独立运行、独立响应事件，**没有中央控制**。

**踩分点**：显式调用 vs 隐式调用（2分） / 耦合强 vs 解耦（2分） / 控制流清晰 vs 无中央控制（2分）

---

##### 问题 2 参考答案（9 分）

> **收益：**
> **1. 可修改性（收益）**：业务模块之间通过事件解耦，平台后续新增、修改下游业务模块（如新增"课程推荐""学习提醒"）时，不需要改动上游发布方代码，可修改性提升。
>
> **2. 可用性（收益）**：模块之间异步解耦，单个订阅模块故障（如短信服务不可用）不会反向影响发布方与其他模块，**故障得到隔离**，不会重演"一个业务故障导致整个平台不可用"的问题，可用性提升。
>
> **代价：**
> **3. 性能（代价）**：事件消息需要经过消息中间件转发与排队，产生**异步延迟**；在高并发场景（如大量学生同时提交作业）下消息队列可能堆积，导致响应变慢，带来性能损耗。
>
> **4. 可测试性（代价）**：异步事件链路的**执行顺序不可见**，模块之间的执行时序难以追踪，出现问题时定位困难，系统整体**可测试性下降**。
>
> **权衡结论**：采用事件驱动架构能够提升线上教育平台的可修改性与可用性，解决当前迭代困难与故障扩散的问题；但会带来性能损耗与可测试性下降的代价，需要通过幂等设计、消息确认机制、分布式链路追踪等手段缓解，在架构设计中进行权衡。

**踩分点**：
- 每个属性 2 分（共 8 分），**必须带上题干场景**（"新增课程推荐""短信服务不可用""学生提交作业"）
- 权衡结论 1 分
- ⚠️ 如果**四个属性只写收益不写代价**，或**完全不提线上教育平台**，**扣一半分数**

---

##### 问题 3 参考答案（10 分）

> **一、权衡点的定义**：
> 权衡点是指**一个架构决策**，**同时**正向影响一个质量属性、负向影响另一个质量属性，即**影响多个质量属性且效果相互冲突**。改变该决策会同时带来"利"与"弊"。
>
> **二、结合本项目分析**：
> 本项目中引入消息中间件作为事件总线：
>
> - **正向收益（可用性）**：消息中间件实现了模块之间的**异步解耦**与**削峰填谷**。发布方将事件投递至消息中间件后即可返回，下游订阅方即使暂时不可用，也不会反向影响发布方，**故障被隔离**，系统可用性提升。
>
> - **负面代价（性能）**：事件消息需要经过消息中间件的**转发、持久化与排队**，引入了额外的网络跳数与 I/O 开销；同时异步通信会**增加端到端延迟**，在高并发时可能因队列堆积进一步降低响应速度，性能下降。
>
> **三、结论**：
> 综上，引入消息中间件这一架构决策**既提升了可用性，又降低了性能**，同时影响了两个质量属性且效果相互冲突，因此该决策是**可用性与性能之间的权衡点**。

**踩分点**：定义准确（3分，必须包含"同时""一升一降""≥2 个属性"） / 可用性收益分析（3分） / 性能代价分析（3分） / 结论（1分）

#### 第 4 步：失分陷阱提醒（本题三个坑）

1. ❌ **低分坑**：问题 2 只罗列事件驱动的**通用优缺点**，完全不提"线上教育平台"场景。
   → 阅卷判定"脱离题干"，**扣一半分数**。
2. ❌ **低分坑**：问题 3 回答权衡点时，**只写收益，不提代价**。
   → 那叫"敏感点/优点"，**不属于权衡点，直接丢分**。
3. ❌ **低分坑**：答题时说"**事件驱动一定可以提升性能**"。
   → 违背架构规律，属于禁句黑名单，**几乎清零**。

#### 第 5 步：答题模板沉淀（同类题目直接套）

> `XX 架构方案在【A 质量属性】方面收益为……；代价为……；
> 该决策同时带来收益和负面影响，属于 XX 与 XX 之间的权衡点。`

## 6.2 考前 1 小时速记清单

### 🎯 一句都不能错的（禁句反向记忆）
```
✗ 微服务提升性能        → ✓ 微服务降低性能，提升可修改性/可用性

数据一步步处理 → 管道-过滤器
多模型协作    → 黑板
向量库做核心存储 → 仓库
```
