# 通用答题五步法（每题都套用，绝不丢分）
1. **标注题干线索**：圈出数据量（千万级→分片）、读写比（读多→读写分离）、一致性要求（金融→强一致）等关键信号；
2. **判断技术方案**：读多写少用分离，数据量大才分片，强一致用 2PC，高并发用 TCC/Saga；
3. **写出收益**：对应技术能解决什么痛点；
4. **写出代价**：必然带来的一致性/复杂度/运维成本上升；
5. **给出改进**：针对代价的缓解手段（强制路由主库、Binlog 同步、一致性哈希等）。

# 题型一：反规范化 + 数据不一致（最高频，约 25 分大题）

## 题 1.1（反规范化方法识别）
**【背景】**
某医药销售系统规范化设计后，查询药品需 `药品表 JOIN 供应商表 JOIN 库存表`，多表关联性能差。
改造后药品关系结构为：
`药品（药品ID，药品名称，药品型号，药品价格，供应商ID，供应商名称，当前库存数量）`

**【问题 1】（9 分）** 说明常见反规范化设计方法，并指出本案例采用哪种。
**高分参考答案：**
常见反规范化 4 种：
① 增加冗余列：在多个表中保留相同列，避免 JOIN；
② 增加派生列：增加由其他列计算生成的列，避免实时聚合；
③ 重新组表/合并表：将经常一起查询的多张表合并为一张宽表；
④ 分割表：水平分割按行拆分，垂直分割按列拆分冷热数据。
本案例在药品表中增加了"供应商名称"（原属供应商表）和"当前库存数量"（原属库存表），属于 **增加冗余列**，消除了与供应商表、库存表的 JOIN。

**【问题 2】（9 分）** 王工认为反规范化会带来数据不一致。请说明解决数据不一致的 3 种常见方法，并指出本系统应采用哪种。
**高分参考答案：**
3 种方法：
① 事务内同步更新：冗余字段更新放在同一数据库事务中，利用事务原子性保证一致；
② Binlog 异步同步：监听 MySQL Binlog，异步同步冗余字段；
③ 消息队列异步同步：通过 Kafka/RocketMQ 通知其他表更新冗余数据。
本系统建议采用 **Binlog 异步同步**。理由：药品信息查询实时性要求不高，Binlog 方式解耦应用、降低侵入、保证最终一致性，性能影响小。

**【问题 3】（7 分）** 系统用 Redis 实现热销药品排名，请说明（1）使用哪种 Redis 数据类型；（2）Redis 与 MySQL 实时同步的常见方案。
**高分参考答案：**
（1）使用 **ZSet（有序集合）**，以 score 记录热度值，天然支持按分数排序。
（2）同步方案：① Cache‑Aside（先更新 DB 再删除缓存，可延迟双删）；② 订阅 Binlog（Canal）异步更新 Redis；③ 事务提交成功后再更新缓存。

**评分关键词：** 增加冗余列 / 事务同步·Binlog·MQ / ZSet / 延迟双删

# 题型二：读写分离 + 主从延迟（必考小题 5‑10 分）

## 题 2.1（读写分离辨析选择题）
**【题干】** 某电商"双十一"采用读写分离和分库分表。以下说法正确的是？
A. 读写分离主要解决单表数据量过大的查询性能问题
B. 分库分表主要解决写入压力过大导致的性能瓶颈
C. 读写分离实现的基础是数据库的主从复制（Master‑Slave）
D. 分库分表只能垂直拆分，不能水平拆分
**答案：C**
**解析：** A 错（单表过大需分库分表）；B 错（表述片面）；C 对（主从复制是前提）；D 错（含水平拆分）。
**口诀：** 读多写少用分离，数据量大才分片。

## 题 2.2（主从延迟案例）
**【背景】** 某电商读请求远大于写请求，引入 1 主 3 从。上线后用户提交订单，立刻刷新订单页偶尔看不到刚生成的订单。
**【问题】** 分析原因并给出改进方案。
**高分参考答案：**
成因：主库写入成功后数据尚未同步到从库，查询路由从库读到旧数据，即主从同步延迟。
改进：
① 强制路由主库：写入后立刻读的实时查询（如支付状态）通过 Hint 强制走主库；
② 会话一致性：同一会话内写后读走主库，其余读走从库；
③ 半同步复制：对一致性要求高的关键链路采用半同步，减少丢数据风险。
权衡：读写分离提升读性能与可用性，但牺牲强一致性，换来最终一致性。

**评分关键词：** 主从同步延迟 / 强制主库 / 会话一致性 / 半同步复制

# 题型三：分库分表 + 分片键选择（近年高频大题）

## 题 3.1（分片键选择）
**【背景】** 库存服务数据量极大，查询热点集中在"商品ID"。架构师引入分库分表。
**【问题 1】** 如何选择分片键并说明理由。
**高分参考答案：** 选 **商品ID** 作为分片键。理由：① 区分度高、分布均匀，避免热点；② 查询条件普遍携带商品ID，避免跨分片；③ 采用哈希分片保证负载均衡。

**【问题 2】** 引入后带来哪些挑战？如何应对？
**高分参考答案：**
① 跨分片查询复杂 → ES 异构索引或服务层聚合；
② 分布式事务 → Saga/TCC 最终一致；
③ 全局唯一 ID → 雪花算法/号段模式；
④ 扩容迁移 → 一致性哈希降低迁移量；非分片键查询 → 映射表/基因法。

## 题 3.2（分片类型选择题）
**【题干】** 订单表按时间范围分片（order_2024、order_2025），属于？
A. 垂直分片 B. 水平分片 C. 反规范化 D. 合并表
**答案：B**（按行拆分，结构相同）。
**速记：** 垂直切字段，水平切行记录。

## 题 3.3（分片键陷阱默写）
**【默写】** 订单表按用户ID哈希分片，有哪些隐藏问题？
**参考：** 用户维度查询友好；但按订单号查询、时间范围查询、商家维度查询需额外索引表/映射表/搜索引擎；且需全局唯一 ID 替代单库自增。

**评分关键词：** 分片键四原则 / 全局唯一 ID / 一致性哈希 / 跨分片查询

# 题型四：缓存一致性与缓存三大问题（希赛案例原型）

## 题 4.1（一致性与一致性哈希）
**【背景】** 全国仓储系统采用缓存集群，讨论缓存与数据库一致性方案。
**【问题 1】（9 分）** 李工建议实时同步，张工建议异步准实时。介绍两种思路并指出本系统采用哪种。
**高分参考答案：**
实时同步：事务提交后再更新缓存，或 2PC 强一致；一致性高但性能影响大。
异步准实时：Cache‑Aside（先更新 DB 再删除缓存），或订阅 Binlog 经 MQ 异步更新；保证最终一致，性能优。
本系统建议 **异步准实时**：仓储实时性要求不高，性能更优、可扩展。

**【问题 2】（9 分）** 缓存分片用哈希还是一致性哈希？说明原理与选择理由。
**高分参考答案：**
哈希：分片键取模，分布均匀但节点变化大量迁移。
一致性哈希：哈希空间成环，数据顺时针找最近节点；节点变化只影响相邻数据，迁移量小。
选 **一致性哈希**：节点动态扩缩容时数据迁移影响最小。

**【问题 3】（7 分）** 黑客非法查询造成缓存击穿/穿透，用布隆过滤器解决，解释原理与优缺点。
**高分参考答案：**
原理：长二进制向量+多个哈希函数；添加时多位置置1，查询时任一为0则必不存在，全1则可能不存在（有误判）。
优点：空间效率高，查询 O(k)，快速拦截不存在的查询。
缺点：有误判率（假阳性），不支持删除。
应用：缓存穿透防护，拦截非法 ID 查询。

## 题 4.2（缓存三大问题速查表）
| 问题 | 原因 | 解决方案 | 考查频率 |
| --- | --- | --- | --- |
| 缓存穿透 | 查询不存在的数据，缓存和 DB 都没有 | 布隆过滤器、缓存空值、参数校验、限流 | ★★★★★ |
| 缓存击穿 | 热点 key 过期瞬间海量请求打 DB | 互斥锁、逻辑过期、热点 key 永不过期、预热 | ★★★★★ |
| 缓存雪崩 | 大量 key 同一时刻过期 | 随机 TTL、多级缓存、预热、限流降级、Redis 高可用 | ★★★★☆ |

**口诀：** Cache‑Aside：读—先查缓存，未命中查 DB 并写回；写—先更新 DB，再删除缓存。

**评分关键词：** Cache‑Aside / 一致性哈希 / 布隆过滤器 / 穿透·击穿·雪崩

# 题型五：数据仓库建模（星型 vs 雪花）

## 题 5.1（选择题）
**【题干】** 数据仓库的（ ）模式中，每个维度属性被组织成层次结构，数据冗余较少。
A. 星型 B. 雪花 C. 星座 D. 事实星座
**答案：B**（雪花是对维度表规范化，冗余少）。

## 题 5.2（星型模型设计）
**【问题】** 为电商设计数据仓库，支持按时间/商品/用户分析销售。设计星型模型并说明 ETL 关键点。
**高分参考答案：**
事实表：销售事实表（订单ID、用户ID、商品ID、时间ID、销售金额、数量）
维度表：时间（年/月/日/节假日）、用户（地区/会员等级）、商品（类别/品牌）
ETL：① 抽取增量（日志表记录变更）；② 转换（统一格式、SCD Type2 保留历史）；③ 加载（按时间分区）。
**权衡句：** 星型查询性能高但冗余；雪花冗余低但 JOIN 多、性能降。常采用适度反规范化。

**评分关键词：** 事实表+维度表 / ETL 三步 / SCD Type2 / 星型 vs 雪花权衡

# 题型六：范式识别与规范化分解（★★★★★ 必出硬分题）

## 题 6.1（订单关系范式判断与分解）
**【背景】**
电商系统关系模式：`订单明细(订单编号, 商品编号, 商品名称, 单价, 数量, 客户编号, 客户姓名, 客户电话)`
业务规则：
- 一个订单只属于一个客户；
- 一个订单可含多个商品，一个商品在一个订单中只出现一次；
- 商品编号 → 商品名称、单价；
- 客户编号 → 客户姓名、客户电话。
主键：`(订单编号, 商品编号)`

**【问题 1】** 判断最高满足第几范式，并说明理由。
**高分参考答案：**
最高满足 **1NF**。
- 所有属性均为原子值，满足 1NF；
- 主键为复合键 `(订单编号, 商品编号)`；
- 存在非主属性对候选键的**部分函数依赖**：客户姓名、客户电话只依赖订单编号；商品名称、单价只依赖商品编号；
- 因此不满足 2NF，最高为 1NF。

**【问题 2】** 分解为 3NF。
**高分参考答案：**
```
订单表(订单编号, 客户编号, 下单时间)       主键:订单编号, 外键:客户编号
客户表(客户编号, 客户姓名, 客户电话)       主键:客户编号
商品表(商品编号, 商品名称, 单价)           主键:商品编号
订单明细表(订单编号, 商品编号, 数量)       主键:(订单编号,商品编号), 外键:订单编号,商品编号
```
分解后消除了部分依赖与传递依赖，满足 3NF。

**评分点**：判断主键 → 指出部分依赖 → 说明非 2NF → 正确拆分为 4 表 → 写清主键外键 → 说明消除依赖。
**易错点**：只写"不满足 3NF"无具体依赖；漏复合主键；拆后忘外键；把明细合并回订单。

## 题 6.2（员工项目关系范式判断）
**【背景】** `员工项目(员工编号, 员工姓名, 部门编号, 部门名称, 项目编号, 项目名称, 参与角色)`
规则：员工与项目多对多；员工编号 → 员工姓名、部门编号；部门编号 → 部门名称；项目编号 → 项目名称；`(员工编号,项目编号)` → 参与角色。

**【问题 1】** 候选键。**【问题 2】** 最高范式。**【问题 3】** 分解为 3NF。
**高分参考答案：**
- 问题1 候选键：`(员工编号, 项目编号)`（两者组合才能唯一标识一条参与记录）。
- 问题2 最高 **1NF**：存在部分依赖（员工姓名/部门编号只依赖员工编号；项目名称只依赖项目编号）与传递依赖（部门名称经部门编号传递依赖候选键）。
- 问题3 分解：
```
员工表(员工编号, 员工姓名, 部门编号)   主键:员工编号, 外键:部门编号
部门表(部门编号, 部门名称)             主键:部门编号
项目表(项目编号, 项目名称)             主键:项目编号
员工项目表(员工编号, 项目编号, 参与角色)  主键:(员工编号,项目编号), 外键:员工编号,项目编号
```
**答题要点**：M:N 联系必须单独建关系；中间表保留两外键组成主键；员工-部门存在传递依赖需拆出部门表。

# 题型七：E‑R 图转关系模式（★★★★★）

## 题 7.1（学校课程系统）
**【背景】** 实体：学生(学号,姓名,性别)、课程(课程编号,课程名称,学分)、教师(教师编号,姓名,职称)。
联系：学生↔课程 **M:N**（带成绩属性）；教师→课程 **1:N**（一门课由一名教师主讲，一名教师可讲多门）。

**【问题】** 转换为关系模式并指出主键、外键。
**高分参考答案：**
```
学生(学号, 姓名, 性别)                  主键:学号
教师(教师编号, 姓名, 职称)              主键:教师编号
课程(课程编号, 课程名称, 学分, 教师编号) 主键:课程编号, 外键:教师编号→教师
选课(学号, 课程编号, 成绩)              主键:(学号,课程编号), 外键:学号→学生, 课程编号→课程
```
**评分点**：M:N 单独建选课表且主键含两外键；1:N 在 N 端（课程）加教师编号外键；成绩属性落在选课表。
**易错点**：省略选课表；把教师编号放学生表；选课主键只写一边；漏成绩。

## 题 7.2（医院门诊系统）
**【背景】** 患者(患者编号,姓名,性别)、医生(医生编号,姓名,科室)、处方(处方编号,开药时间,药品清单,总金额)。
联系：医生 1:N 处方；患者 1:N 处方（一张处方对应一个患者，一个患者多张处方）。

**【问题】** 转换为关系模式并指出主键外键。
**高分参考答案：**
```
患者(患者编号, 姓名, 性别)              主键:患者编号
医生(医生编号, 姓名, 科室)              主键:医生编号
处方(处方编号, 开药时间, 药品清单, 总金额, 医生编号, 患者编号)
    主键:处方编号, 外键:医生编号→医生, 患者编号→患者
```
**高分补充**：处方表满足 1NF；若药品清单为多值需进一步规范化（如拆处方明细表）便于统计。

# 题型八：反规范化优化（含派生列）

## 题 8.1（冗余客户名称）见题 1.1 / 例题5 类比
**【背景】** 订单页频繁展示订单编号、下单时间、客户姓名、手机号；原设计订单表与客户表分离需 JOIN，数据量增长后变慢。架构师在订单表增加客户姓名、手机号。
**【问题 1】** 优化方法。**【问题 2】** 收益代价。**【问题 3】** 一致性措施。
**高分参考答案：**
- 问题1：**反规范化（增加冗余列）**，减少订单表与客户表 JOIN。
- 问题2 收益：减 JOIN、降复杂度、提查询性能、适合读多写少。代价：冗余↑、客户信息变更时冗余字段可能未更新、写成本↑、不一致风险。
- 问题3：同事务同步更新；触发器自动更新；定时任务同步；MQ 异步；Binlog 监听；实时性不高可允许最终一致。
**答题金句**：反规范化以牺牲数据一致性、增加存储冗余为代价换取查询性能，需权衡。

## 题 8.2（订单总金额派生列）
**【背景】** 订单表与明细表分离，列表页展示总金额需实时汇总明细，性能差。项目组在订单表加"订单总金额"字段，提交/明细变化时更新。
**【问题 1】** 优化类型。**【问题 2】** 优缺点与改进。
**高分参考答案：**
- 问题1：**反规范化中的增加派生列**（由明细计算预存）。
- 问题2 优点：免实时聚合、降计算压力、提列表性能。缺点：冗余字段、明细变更须同步更新、逻辑复杂、更新失败会不一致。
- 改进：明细变更同事务更新总金额；触发器维护；异步/Binlog 补偿；定时校验总额与明细汇总。

# 题型九：索引优化与慢查询

> 💡 **本题型为简版**。索引/慢 SQL 的完整套路（5 大出题套路、题干特征→条件反射表、毛病-改法配对表、5 道仿真大题）见 👉 **题型二十三：慢 SQL 优化专项**。
> 建议顺序：先做本题型 9.1/9.2 建立概念，再刷题型二十三。

## 题 9.1（联合索引优化订单查询）
**【背景】** orders(user_id, status, create_time, ...)，查询 `WHERE user_id=? AND status=? ORDER BY create_time DESC LIMIT 20`，执行计划 type=ALL，rows 很大。
**【问题 1】** 慢的原因。**【问题 2】** 索引建议。
**高分参考答案：**
- 问题1：无合适索引→全表扫描；数据量大扫描行多；排序字段无索引可能产生 filesort；索引无法覆盖导致回表。
- 问题2：建联合索引 `idx_user_status_time(user_id, status, create_time)`，等值字段在前、排序字段在后可利用索引排序；若只返少量字段可建覆盖索引减少回表。
**评分点**：识别全表扫描、联合索引、最左前缀、排序利用、覆盖索引、减少回表。

## 题 9.2（函数导致索引失效）
**【背景】** users(create_time 有索引)，SQL `SELECT * FROM users WHERE DATE(create_time)='2026-08-18'` 很慢。
**【问题 1】** 慢因。**【问题 2】** 优化。
**高分参考答案：**
- 问题1：对索引列使用 DATE() 函数，无法利用 B+ 树索引定位，索引失效退化为全表扫描。
- 问题2：改为范围查询 `WHERE create_time >= '2026-08-18 00:00:00' AND create_time < '2026-08-19 00:00:00'`；避免 SELECT *，必要时覆盖索引。
**高频考点**：索引列用函数/运算→失效；日期查询改范围；不要 SELECT *。

# 题型十：分库分表（水平+垂直完整）

## 题 10.1（订单表水平分片，含隐藏问题）见题 3.1/3.3
**【背景】** orders 8000 万行；场景：用户查自己订单、后台按订单号查、商家查店铺订单、运营按时间统计。考虑按 user_id 哈希分片。
**【问题 1】** 水平 or 垂直。**【问题 2】** 收益。**【问题 3】** 问题及解决。
**高分参考答案：**
- 问题1：**水平分片**（按行拆，结构相同）。
- 问题2：单表数据量降、查询性能升；分散存储扩展容量；分散读写压力；用户按 user_id 查询可定位分片。
- 问题3 问题：订单号查询无分片信息难定位；商家维度跨分片；时间统计跨所有分片；跨分片分页/排序/聚合复杂；跨分片事务复杂；扩容迁移。
  解决：订单号嵌入 user_id 分片因子；建订单号→分片键映射表；商家维度建异构索引；复杂统计同步 ES/数仓；预分片/一致性哈希降迁移；全局唯一 ID（雪花/号段）。

## 10.2（用户表垂直拆分）
**【背景】** user(用户名,密码,手机号,个人简介,兴趣,生日...)，登录高频字段与低频扩展字段分离为 user_base / user_profile。
**【问题 1】** 水平 or 垂直。**【问题 2】** 收益代价。
**高分参考答案：**
- 问题1：**垂直分片**（按字段列拆，通常保留相同主键以便关联）。
- 问题2 收益：减单行大小、降 IO；高频登录只访问 user_base；降低热点字段锁竞争。代价：查完整信息需 JOIN；应用逻辑复杂；需维护两表一致；跨表事务复杂。
**易错点**：误判为水平；只写收益不写代价；未提主键通常相同；未说 JOIN 成本。

# 题型十一：分布式事务（含 TCC 注意事项）

## 题 11.1（银行转账 2PC 选择）
**【背景】** 银行转账两节点须强一致。方案：2PC / TCC / 本地消息表+MQ。
**【问题 1】** 强一致选哪个。**【问题 2】** 2PC 缺点。**【问题 3】** 最终一致可选。
**高分参考答案：**
- 问题1：选 **2PC**，金融强一致、短事务、不能长时间不一致；TCC/消息表为最终一致不适用。
- 问题2：同步阻塞性能低；协调者单点故障；二阶段部分未收到可能不一致；锁资源长；不适合高并发长流程。
- 问题3：最终一致可选 TCC、Saga、本地消息表、可靠消息最终一致、最大努力通知；需补偿/重试/幂等/可靠投递。

## 题 11.2（电商下单扣库存 TCC/消息）
**【背景】** 下单含创建订单、扣库存、加积分、核销券；高并发、允许短暂不一致但最终必须一致。
**【问题 1】** 是否适合 2PC。**【问题 2】** 更适合方案。**【问题 3】** 注意事项。
**高分参考答案：**
- 问题1：**不适合**：高并发下 2PC 同步阻塞、锁长、性能差、协调者故障影响大。
- 问题2：TCC（Try 预留/Confirm 提交/Cancel 回滚）或可靠消息最终一致（订单本地事务后发消息，下游消费）。
- 问题3：接口**幂等**；Cancel **空回滚**识别；防止**悬挂**（Cancel 先于 Try）；Confirm/Cancel 可重试；消息可靠投递；消费失败重试+对账兜底。

# 题型十二：缓存一致性与三大问题

## 题 12.1（更新DB后缓存策略）
**【背景】** 商品详情 Redis 缓存，改信息后用户仍看到旧数据。讨论：方案A先删缓存再更DB；方案B先更DB再删缓存。
**【问题 1】** 推荐。**【问题 2】** 仍可能问题。**【问题 3】** 降风险。
**高分参考答案：**
- 问题1：推荐 **方案B（Cache Aside）**：更DB后删缓存，并发下比方案A更不易脏数据。
- 问题2：极端并发仍可能短暂不一致（缓存失效+读旧值+写DB+删缓存+读回写旧值）；删缓存失败也会不一致。
- 问题3：删缓存重试；延迟双删；MQ 异步删；Binlog 监听异步删；合理过期时间兜底；写后立读直查DB/主库。

## 题 12.2（三大问题识别）
**【背景】** 现象一：大量查不存在商品ID，DB 压力升；现象二：热点 key 过期瞬间海量请求打 DB；现象三：大批缓存同时过期 DB 激增。
**【问题】** 判断并给方案。
**高分参考答案：**
- 现象一 **缓存穿透**：布隆过滤器、缓存空值、参数校验、限流。
- 现象二 **缓存击穿**：互斥锁重建、逻辑过期、热点 key 永不过期、预热。
- 现象三 **缓存雪崩**：随机 TTL、多级缓存、预热、限流降级、Redis 高可用。
**口诀**：穿透=查不到（布隆/空值）；击穿=热点过期（锁/逻辑过期）；雪崩=批量过期（随机TTL/多级）。

# 题型十七：Redis 专项真题训练（核心必考）

## 题 17.1（Redis 数据类型选型）
**【背景】** 某系统需支持以下场景：① 分布式锁控制库存扣减；② 用户画像标签去重与集合运算；③ 商品销售周排行榜按销量排序；④ 购物车存储用户‑商品‑数量。
**【问题】** 分别说明应使用的 Redis 数据类型，并说明理由。
**高分参考答案：**
- ① 分布式锁 → **String**：基于 `SET key value EX NX` 原子命令实现，可附带唯一标识防误删；
- ② 用户画像标签 → **Set**：无序不可重复，支持交集/并集等集合运算，天然适合标签去重；
- ③ 周排行榜 → **ZSet（有序集合）**：按销量作为 score 排序，元素唯一，天然支持排行榜；
- ④ 购物车 → **Hash**：以 field=商品ID、value=数量 存储，支持按商品维度读写。
**答题金句**：缓存和分布式锁用 String，标签去重用 Set，排行榜用 ZSet，购物车/对象用 Hash。

## 题 17.2（持久化机制 RDB vs AOF）
**【背景】** 2025 上半年真题：请介绍 Redis 两种持久化方法，并说明优缺点。
**【问题】** 给出两种持久化方式及其优缺点，并说明高安全场景选择。
**高分参考答案：**
- **RDB（快照）**：定时生成内存二进制快照 `dump.rdb`。优点：文件紧凑、恢复快、适合备份容灾；缺点：可能丢失最后一次快照后数据，fork 大内存时可能阻塞主线程。
- **AOF（追加日志）**：记录写命令追加到 `appendonly.aof`。优点：数据安全（everysec 最多丢 1 秒）、可读可修复；缺点：文件大、恢复慢、需重写优化。
- 选择：数据安全性要求高 → AOF（everysec）或 Redis 4.0+ **混合持久化**（AOF 重写时先 RDB 全量再 AOF 增量）。
**评分关键词**：RDB 快但丢数据 / AOF 安全但慢 / 混合持久化兼顾

## 题 17.3（内存淘汰策略）
**【背景】** Redis 内存达到 maxmemory，配置了 `volatile‑lru`。运维发现未设置过期时间的键始终不被淘汰。
**【问题 1】** 解释 `volatile‑lru` 与 `allkeys‑lru` 区别。**【问题 2】** 若要所有键均可被淘汰，应选什么策略。
**高分参考答案：**
- 问题1：`volatile‑lru` 仅从**设置了过期时间的键**中按 LRU 淘汰；`allkeys‑lru` 从**所有键**中按 LRU 淘汰。本例未设过期时间的键不会被 `volatile‑lru` 淘汰。
- 问题2：选 `allkeys‑lru`（或 `allkeys‑lfu`）。两者均遵循局部性原理，优先淘汰最近最少/最不经常使用的数据。

## 题 17.4（分布式锁死锁场景）
**【背景】** 2024 年 5 月真题：某系统用 `SETNX` 加锁后单独执行 `EXPIRE` 设置过期时间。
**【问题】** 分析死锁场景及解决方案。
**高分参考答案：**
- 死锁场景：`SETNX` 成功但 `EXPIRE` 未执行（如服务宕机），锁永不过期，形成死锁。
- 解决方案：① 用原子命令 `SET key value EX 30 NX` 一次性设值+过期；② 锁值用 UUID 唯一标识，释放时校验避免误删；③ 业务超时用看门狗（Redisson）自动续期；④ 高可靠场景用 RedLock（多独立节点过半成功）。
**评分关键词**：SETNX+EXPIRE 非原子 / SET NX 原子 / UUID 防误删 / 看门狗续期

## 题 17.5（缓存击穿互斥锁序列图填空）★★★★★
**【背景】** 2025 年 11 月真题：热点 Key 缓存失效瞬间，海量并发请求同时回源。采用互斥锁方案重建缓存。线程1先到，线程2后到。
**【问题】** 补全下方两个线程的时序（序列图填空）。
**高分参考答案（填空后）：**
```
线程1：查缓存(未命中) → 获取互斥锁(成功) → 查数据库 → 写缓存 → 释放锁 → 返回
线程2：查缓存(未命中) → 获取互斥锁(失败) → 休眠重试 → 再次查缓存(命中) → 返回
```
**填空要点（踩分点）：**
1. 两线程均先**查缓存**且未命中；
2. 线程1 用 `SETNX/NX` **成功获取锁**；
3. 线程2 获取锁**失败**，**不能查数据库**，进入休眠重试；
4. 线程1 持锁执行 查库→写缓存→释放锁；
5. 线程2 唤醒后**先再次查缓存**（非直接加锁）→ 命中重建好的数据。
**⚠️ 失分陷阱**：漏掉"再次查询缓存"——必须体现"等别人重建后自己复用"的思想。

## 题 17.6（缓存三大问题辨析）
**【问题】** 区分穿透/击穿/雪崩，并各给一种解决方案。
**高分参考答案：**
- 穿透：查缓存和 DB 都不存在的数据 → 布隆过滤器/缓存空值/参数校验；
- 击穿：单热点 Key 过期瞬间海量打 DB → 互斥锁/逻辑过期/热点永不过期/预热；
- 雪崩：大量 Key 同刻过期或服务不可用 → 随机 TTL/多级缓存/预热/限流降级/高可用集群。
**口诀**：穿透=查不到（布隆）；击穿=单热点过期（锁/逻辑过期）；雪崩=批量过期（随机TTL）。

# 题型二十二：RAG 与向量数据库（2026 新大纲 AI 热点·超车弯道）

## 题 22.1（智能客服知识库选型）
**【背景】** 某企业希望基于自有产品手册、售后制度文档搭建"智能客服问答机器人"。原方案拟用 MySQL 存储文档并做 LIKE 模糊查询。架构师指出该方案无法理解语义、召回不准。要求设计数据架构。
**【问题 1】（9 分）** 说明为何 MySQL LIKE 不适用，应采用何种架构。
**【问题 2】（9 分）** 描述 RAG 核心数据流转（离线 + 在线）。
**【问题 3】（7 分）** 向量数据库与 MySQL 如何分工。
**高分参考答案：**
- 问题1：MySQL LIKE 仅支持关键词字面匹配，无法理解语义相似（如"怎么退款"与"退钱流程"）；应采用 **RAG（检索增强生成）+ 向量数据库** 架构，解决大模型知识陈旧与幻觉问题。
- 问题2（核心数据流）：① 离线——私有文档切片后经 Embedding 模型转向量，存入向量数据库（如 Milvus / Elasticsearch）；② 在线——用户 Query 向量化后在向量库做 ANN（近似最近邻）检索，召回 Top‑K 相关片段；③ 将片段与 Query 拼接成 Prompt 调用大模型生成答案。
- 问题3：**向量数据库**负责语义相似召回（非结构化文本向量）；**MySQL** 负责结构化元数据管理（文档来源、版本、权限、更新时间），二者互补。
**评分关键词**：RAG / Embedding 向量化 / 向量数据库 ANN 检索 / Top‑K 召回 / 元数据存 MySQL

## 题 22.2（RAG vs 直接微调大模型辨析）
**【问题】** 题干问"为何不微调大模型而用 RAG"。请给答题要点。
**高分参考答案：**
- RAG 知识可热更新（更新文档即可，无需重训模型），成本低、时效强；
- RAG 回答可溯源（召回片段即出处），降低幻觉、便于审计；
- 微调成本高、周期长、知识更新慢，适合固化通用能力而非频繁变动的私有知识。
**答题金句**：RAG 以"检索外部知识 + 大模型生成"的方式，兼顾知识时效性与可溯源性，适合企业私有、频繁更新的知识库场景；相较微调大模型，更新成本低、幻觉可控。

# 题型二十一：数据架构与 Lambda/Kappa 真题

## 题 21.1（数据平台架构设计）
**【背景】** 某企业多业务系统数据孤岛严重，希望建设统一数据平台，支持**离线报表**和**实时分析**。
**【问题】** 设计数据架构并说明理由。
**高分参考答案：**
- 通过 ETL/CDC 将业务数据接入数据湖/数据仓库，按 ODS→DWD→DWS→ADS 分层建模；
- 离线报表走数据仓库（批处理）；实时分析走实时数仓（Kafka+Flink）；
- 若同时需离线准确与实时快速，采用 **Lambda 架构**（批处理层+速度层+服务层）；若希望降低批流两套代码维护成本且数据可重放，采用 **Kappa 架构**或流批一体；
- 通过 OLAP 查询、数据 API、报表服务支撑经营分析与实时大屏。
**答题金句**：统一数据平台以 ETL/CDC 接入，分层建模，离线用数仓、实时用流处理；按需求选 Lambda 或 Kappa/流批一体。

## 题 21.2（Lambda vs Kappa 对比）
**【问题】** 比较 Lambda 与 Kappa 架构的优缺点与适用场景。
**高分参考答案：**
| 架构 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| Lambda | 离线准确，实时快速 | 两套逻辑，维护复杂 | 既需历史准确又需实时 |
| Kappa | 架构简单，统一流处理 | 对消息存储/计算要求高 | 实时性高，数据可重放 |
**答题金句**：同时需离线与实时 → Lambda；希望降低批流维护成本且可重放 → Kappa/流批一体。

## 题 21.3（云原生数据库选型论证）
**【背景】** 促销峰值数据库连接池爆满、主从延迟高、扩容困难。
**【问题】** 论证为何选用云原生数据库（如 PolarDB/Aurora）。
**高分参考答案：**
传统 MySQL 扩容需搬数据、耗时长，主从同步有延迟。云原生数据库存算分离：计算节点无状态秒级弹性扩缩容；共享存储避免主从同步延迟；存储按量付费。契合促销峰值弹性与低延迟诉求。
**答题金句**：存算分离使计算节点秒级扩缩容无需搬数据；共享存储消除主从延迟。

> - **本节的 ①~⑥**（①缺索引 ②索引失效 ③`SELECT *`与回表 ④排序/分组 ⑤大数据量 ⑥EXPLAIN 验证）＝ **毛病清单**，管"写什么"。
>
> **考场动作**：先用四步法搭骨架，再往第①步里填毛病编号、往第②步里填对应改法、第③步写索引代价、第④步写验证与效果。

## 23.2 五道真题风格例题（逐个拆）

### 题 23.1 综合型（缺索引 + `SELECT *` + 排序）—— 命中 ①③④⑤

**【背景】**
某电商系统订单表 `orders` 约 3000 万行，字段：`order_id`(主键)、`user_id`、`status`、`create_time`、`amount`、`address`、`remark`（备注，文本较大）。**现仅有主键索引**。以下 SQL 执行约 8 秒：

```sql
SELECT * FROM orders
WHERE user_id = 10086 AND status = 1
ORDER BY create_time DESC
LIMIT 20;
```

**【问题 1】（8 分）** 分析查询缓慢的原因。

| 得分点 | 你要写的话（关键词已加粗） | 命中 |
|---|---|---|
| ① | `user_id`、`status` 字段上**无索引**，导致**全表扫描**（type=ALL），需扫描 3000 万行，产生大量磁盘 I/O | ① |
| ② | `ORDER BY create_time` 无可用有序索引，产生 **`Using filesort`**，需额外排序，代价高 | ④ |
| ③ | 使用 **`SELECT *`**，`remark` 等大字段参与返回，**无法命中覆盖索引**，且回表与网络传输开销大 | ③ |
| ④ | 单表 3000 万行，**数据量过大**，随业务增长性能持续恶化 | ⑤ |

**【问题 2】（10 分）** 提出优化方案。**（三层递进，体现系统性）**

**第一层：索引层（成本最低，首先做）**

```sql
CREATE INDEX idx_user_status_time ON orders(user_id, status, create_time);
```

> **设计依据（这句必写，是拉分点）**：`user_id`、`status` 为**等值查询** → 置于联合索引前部；`create_time` 为**范围/排序** → 按最左前缀原则置于最后；排序字段纳入索引后，`ORDER BY` 可直接利用索引有序性，消除 `Using filesort`。

**第二层：SQL 层**
- 避免 `SELECT *`，只查业务所需字段；
- 若查询列可全部纳入索引，进一步扩展为**覆盖索引**（`Extra: Using index`），避免回表与随机 I/O。

**第三层：架构层（数据量继续增长时）**
- **分库分表**：按 `user_id` 做水平分片，将单表降至千万级以下；
- **读写分离**：此类查询路由到只读从库，减轻主库压力；
- **数据归档**：超过 1 年的历史订单迁移至归档库/数据仓库，缩小热表体积；
- **分区表**：按 `create_time` 做 Range 分区，便于按时间裁剪与历史数据归档；
- **缓存 / ES**：热点查询结果放缓存；复杂检索引入 Elasticsearch。

**第三点：说明代价（四步法第③步，最常漏，写了就多拿 1~2 分）**

> 索引并非越多越好：索引**占用额外存储空间**，且每次 INSERT/UPDATE/DELETE 都要同步维护索引，**降低写入性能**；因此索引数量应适度控制，优先建联合索引而非多个单列索引。

**第四点：验证与效果（第④步）**

> 用 **EXPLAIN** 对比优化前后：`type` 由 **ALL 提升至 ref**（本例两列均为等值匹配，故为 `ref`；若含范围条件则为 `range`），`key` 命中新索引，`rows` 显著下降，`Extra` 中 `Using filesort` 消失。

> ⚠️ **严谨补充（防追问）**：排序列必须是索引的**连续后缀**、且**排序方向一致**才能免 filesort。MySQL 支持索引**反向扫描**，因此 `ORDER BY create_time DESC` 用升序索引同样可免排序；MySQL 8.0 可显式建**降序索引** `(user_id, status, create_time DESC)`，仅在**多列排序方向混用**（如 `a ASC, b DESC`）时才必须依赖降序索引。

**评分关键词**：全表扫描 / 联合索引（等值在前·范围在后）/ `Using filesort` / 覆盖索引 / 索引代价 / EXPLAIN 验证

### 题 23.2 索引失效型（函数 + 隐式转换）—— 命中 ②③（最高频坑）

**【背景】**
用户表 `user`（1000 万行）：`id`(主键)、`phone VARCHAR(20)`、`create_time DATETIME`、`name`、`city`。
已建索引：`idx_phone(phone)`、`idx_ct(create_time)`。以下 SQL 仍很慢：

```sql
SELECT * FROM user
WHERE phone = 13800138000
  AND YEAR(create_time) = 2024;
```

**【问题】** 索引为何未生效？如何改写？

**原因（两个失效点，各 3 分）：**

| 失效点 | 原因 | 命中 |
|---|---|---|
| `phone = 13800138000` | `phone` 是 VARCHAR，却传入数字，触发**隐式类型转换**，等价于对索引列做 `CAST(phone AS ...)`，**即对索引列使用了函数 → 索引失效** | ② |
| `YEAR(create_time) = 2024` | 对索引列使用函数，**B+ 树存的是原始值**，无法"先计算再比较" → 索引失效 | ② |
| `SELECT *` | 无法命中覆盖索引，需回表 | ③ |

**改写方案：**

```sql
-- ① 字符串加引号，消除隐式转换
-- ② 把函数移到"常量侧"，改为范围查询，让索引列"裸露"
-- ③ 只查必要字段，尝试覆盖索引
SELECT id, phone, name FROM user
WHERE phone = '13800138000'
  AND create_time >= '2024-01-01'
  AND create_time <  '2025-01-01';
```

> 💡 **反例对照（选择题常考）**：若字段是 **INT 却传字符串 `'123'`** → MySQL 转换的是**常量侧**，索引**仍然有效**。
> **口诀：列变则失效，常量变则无碍。**

> ⚠️ **严谨补充（是拉分点）**：改写后 `idx_phone` 与 `idx_ct` 仍是两个**单列索引**，优化器通常只能选其一（或 Index Merge），优化不彻底。**更彻底的做法是建联合索引 `(phone, create_time)`**，让两个条件都参与索引定位；若再把 `name` 纳入则形成覆盖索引（`Using index`）。
> 另：MySQL 8.0 支持**函数索引**（表达式索引）`CREATE INDEX idx_year ON t((YEAR(create_time)))`，知道即可，**不推荐**（维护成本高、迁移性差），答卷上优先写"改范围查询"。

**评分关键词**：隐式类型转换 / 对索引列用函数 / 改范围查询 / 联合索引 `(phone, create_time)`

### 题 23.3 联合索引顺序设计 —— 命中 ②（最左前缀，必考判断）

**【背景】** 表 `t` 有联合索引 `(a, b, c)`。判断下列查询对该索引的利用情况，并说明原因。
① `WHERE a=1 AND b=2 AND c=3`　② `WHERE a=1 AND c=3`　③ `WHERE b=2 AND c=3`　④ `WHERE a=1 AND b>2 AND c=3`

**【问题】** 分别说明哪些字段能用于索引定位。

| 序号 | 能用于定位的字段 | 原因（答题关键词） |
|---|---|---|
| ① | **a、b、c 全部** | 满足最左前缀，等值精确匹配，最完美 |
| ② | **仅 a**；c 只能 **ICP** 过滤 | 跳过中间的 b，b 之后的 c 在索引中**无序**，无法用于定位 |
| ③ | **无**（索引无法用于定位） | 缺失最左列 a，不满足最左前缀，导致全表/全索引扫描 |
| ④ | **a、b**；c 无法定位（只能 ICP） | b 是**范围查询**，范围列之后的 c 无序，无法继续利用索引 |

**一句话答题金句（背）：**

> 联合索引遵循**最左前缀匹配原则**：必须从最左列开始、且**遇到范围查询即停止**，范围列之后的字段无法再用于索引定位（仅能做**索引下推 ICP** 过滤）。

**延伸：设计题怎么答**

> 若高频查询是 `WHERE a=? AND b=? AND c>?`，正确索引是 **`(a, b, c)`**——**等值在前、范围在后**；若建成 `(a, c, b)`，则因 c 是范围，b 失效。

> ⚠️ **严谨补充**：
> - ③ 严格说：若查询字段**全部被索引覆盖**，优化器可能选择**全索引扫描**（`type=index`，`Extra: Using index`）而非全表扫描，但代价仍远高于索引定位；`SELECT *` 时通常直接全表扫描。
> - MySQL 8.0.13+ 引入 **Skip Scan**（跳跃索引扫描），首列区分度极低时可能跳过首列用索引——**软考一律按最左前缀答，不要写 Skip Scan**，以免节外生枝。

### 题 23.4 LIKE 前导模糊 + 深分页 —— 命中 ②③⑤（坑王）

**【背景】** 商品表 `goods`（500 万行），`name` 上有索引 `idx_name`。搜索分页 SQL 极慢：

```sql
SELECT * FROM goods
WHERE name LIKE '%手机%'
LIMIT 100000, 20;
```

**【问题】** 为何有索引还慢？如何优化？

**原因：**

| 得分点 | 关键词 |
|---|---|
| `LIKE '%手机%'` 为**前导模糊查询**，`%` 在开头导致 B+ 树**无法利用有序性快速定位**，索引失效（或退化为全索引扫描） | 前导模糊 / 无法定位 |
| `LIMIT 100000, 20` 为**深分页**，需先扫描并丢弃前 10 万行，代价极高 | 深分页 |
| `SELECT *` 无法覆盖索引，大量回表 | 回表 |

**优化方案：**

1. **改写模糊查询**：能用 `LIKE '手机%'`（**前缀匹配**）就用前缀；确实需要中间匹配 → 引入 **全文索引 / Elasticsearch 倒排索引**承担搜索。
2. **优化深分页**：
   - **延迟关联**（先用覆盖索引分页拿到 id，再回表取详情）：
     ```sql
     SELECT g.* FROM goods g
     INNER JOIN (SELECT id FROM goods WHERE name LIKE '手机%' LIMIT 100000, 20) t
     ON g.id = t.id;
     ```
   - **游标分页**（记录上一页最大 id，用 `WHERE id > 上页最大id LIMIT 20`），彻底避免大偏移。
3. 避免 `SELECT *`，只查必要字段，尽量覆盖索引。

> ⚠️ **严谨补充（关键，否则会被认为没答到点子）**：
> **延迟关联的前提**是子查询 `SELECT id FROM goods WHERE name LIKE '手机%' ...` 能命中 `idx_name` 的**覆盖索引**（`id` 存在二级索引叶子节点中），只扫索引不回表，把 100020 次回表压缩到 20 次。
> **但若保留前导 `%`，子查询本身仍是全索引扫描**——延迟关联只省下回表，**没有解决"定位"问题**。根治必须靠 **ES / 全文索引**。答题时这两句都要写。

**评分关键词**：前导 % / 覆盖索引 / 延迟关联（Deferred Join）/ 游标分页 / Elasticsearch

### 题 23.5 架构层（大数据量综合）—— 命中 ⑤

**【背景】** 某业务单表数据已达 8000 万行，且每日新增 50 万，读写性能均严重下降，主从延迟明显。请给出系统级优化方案。

**【问题】** 给出系统级优化方案。

| 层次 | 措施 | 得分关键词 |
|---|---|---|
| SQL/索引层 | 优化慢 SQL，建立合理**联合索引**与**覆盖索引**，消除 filesort | 索引优化、覆盖索引 |
| 反规范化 | 增加**冗余字段**减少 JOIN；建立汇总表/中间表 | 反规范化、空间换时间 |
| 读写分离 | 主库写、从库读，分散压力；解决主从延迟（中间件 / 强制走主库） | 读写分离 |
| 分库分表 | 按 `user_id` 做**水平分片**（哈希/范围），将单表降至千万级以内；**垂直拆分**大字段 | 水平分片、分库分表 |
| 分区表 | 按时间做 Range 分区，便于按时间裁剪与历史分区归档 | 分区表 |
| 数据归档 | 冷数据（如 1 年前）迁移至归档库/数据仓库，缩小热表 | 冷热分离、归档 |
| 缓存 | 热点数据放 Redis，减少数据库读压力 | 缓存 |

> 💡 **答题金句**：**逻辑设计追求减少冗余、保证一致性；物理设计追求查询性能，可牺牲范式换取时间**——用这句话解释"为什么可以反规范化"。
>
> 💡 **作答顺序原则**：**先 SQL/索引层，再做架构改造**。索引优化成本最低、风险最小；分库分表改造成本高、引入分布式事务与跨分片查询复杂度，应在单表优化到极限后再做。

## 23.4 「毛病 → 改法」配对表（两种问法通吃，必背）

| 毛病（原因） | 改法（方案） |
|---|---|
| 缺索引 → 全表扫描 | 建索引 / 联合索引，**等值在前、范围在后** |
| 对索引列用函数 | **函数移到常量侧**，改范围查询 |
| 隐式类型转换 | **类型对齐**（加引号/去引号） |
| 前导模糊 | 改前缀匹配 / 上 **ES、全文索引** |
| 违反最左前缀、范围阻断 | **调整索引顺序** / 重建索引 |
| `SELECT *` → 回表多 | 只查必要字段，建**覆盖索引** |
| 排序/分组无索引 | 纳入联合索引，消除 **filesort / temporary** |
| 深分页 | **延迟关联 / 游标分页** |
| 单表过大 | 分库分表、读写分离、归档、缓存、分区表、反规范化 |
| 索引过多 | 适度控制，索引占空间且**降低写入性能**（代价必写） |

# 附录 A：案例题答题万能结构（每题都套）
- **结构一·判断类**：先给结论，再给理由。例："该优化属于反规范化，原因是增加了冗余列以减少 JOIN。"
- **结构二·原因分析类**：现象 → 根因 → 机制。例："看不到订单，根因是主从延迟，机制是异步复制未同步。"
- **结构三·收益代价类**：收益 1/2/3 + 代价 1/2/3，务必成对写。
- **结构四·改进措施类**：针对每一条代价给缓解手段（强制主库、Binlog、一致性哈希…）。
- **结构五·权衡总结类**：以 XX 代价换取 XX 收益，需权衡。

# 附录 B：高频答题金句（直接背）
1. 反规范化：通过增加冗余字段减少多表连接，提高查询性能；但带来数据冗余与不一致风险，需权衡。
2. 水平分片：降低单表数据量提升查询性能；但带来跨分片查询、分布式事务复杂等代价。
3. 垂直分片：按字段列拆分减少单表 IO 与锁冲突；但查完整信息需 JOIN。
4. 读写分离：分散读压力提升性能与可用性；但存在主从延迟，牺牲强一致性。
5. 缓存一致性：Cache Aside 更新 DB 后删缓存，避免并发脏数据，降低无效更新成本。
6. 分布式事务：强一致选 2PC 牺牲性能；最终一致选 TCC/Saga/消息提升吞吐。
7. 数据仓库：OLAP 面向统计分析，ETL 定期导入，星形模型性能好但冗余、雪花冗余低但 JOIN 多。
8. 星型 vs 雪花：星型查询性能高、维度冗余；雪花冗余低、查询复杂度升。
9. RAG/向量库：智能问答/知识库场景采用 RAG，文档切片 Embedding 存向量库做 ANN 召回，元数据存 MySQL，解决大模型知识陈旧与幻觉。

# 附录 D：考场关键词 → 写什么（快速定位）
| 题干关键词 | 优先写的技术 |
| --- | --- |
| 表几千万、查询慢 | 分库分表（水平分片）+ 分片键/全局 ID |
| 读多写少、查询压力大 | 读写分离；热点数据再加缓存 |
| 多表 JOIN 慢、冗余字段 | 反规范化（收益/代价/一致性维护） |
| 提交后立即刷新看不到 | 主从延迟 → 强制主库/会话一致性 |
| 强一致、转账、库存不能错 | 2PC（CP） |
| 高并发、允许最终一致 | TCC / Saga / 可靠消息 |
| 统计分析、报表、历史数据 | 数据仓库 + ETL + 星形模型（OLAP） |
| 企业私有知识库、智能客服、大模型问答 | RAG + 向量数据库（Milvus/ES）+ 元数据存 MySQL |
| 慢 SQL、查询缓慢、给了 EXPLAIN | 索引三兄弟（缺索引/索引失效/`SELECT *`回表）→ 覆盖索引 → 见题型二十三 |
| `LIKE '%xx'`、`LIMIT 100000,20` | 前导模糊（ES/全文索引）+ 深分页（延迟关联/游标分页） |
| 索引列用函数、VARCHAR 传数字 | 索引失效 → 改范围查询 / 类型对齐 |
