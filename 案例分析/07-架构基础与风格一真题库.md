## 🔑 质量属性识别速记口诀

| 质量属性 | 关键词信号 |
|----------|------------|
| **性能** | 响应时间、吞吐量、延迟、并发、XX 秒内 |
| **可用性** | 故障恢复、切换、连续运行、MTBF、正常运行时间 |
| **安全性** | 加密、认证、攻击、防御、隐私、审计、权限 |
| **可修改性** | 新增功能、修改、扩展、迁移、XX 天内完成、模块化 |
| **可测试性** | 测试、模拟、验证、日志、调试 |
| **易用性** | 界面、操作、用户友好、学习成本、无障碍 |

> 答题技巧：写出质量属性**名称**即得分，无需展开。拿不准时优先写六大属性中最匹配的一个。

## 真题一 · 2024 年 5 月（上半年）：网络约车调度服务平台

### 【题干】
某公司拟开发网络约车调度服务平台。需求与质量属性描述：
- (a) 参与者包括乘客、出租车司机和平台管理员三类
- (b) 具备安全防护措施，能对黑客攻击行为进行检测与防御
- (c) 正常负载下，必须在 0.5 秒内响应用户操作
- (d) 7×24 小时运行，硬件故障时能在 5 分钟内自动恢复
- (e) 2 个月内完成新增"拼车"功能的开发与部署
- (f) 界面方便老年用户使用，字体可放大、操作流程不超过 3 步
- (g) 支持在模拟 10 万并发下进行压力测试
- (h) 采用微服务架构，服务间通过 RESTful API 通信
- (i) 某地区用户量增长 300% 时，可通过水平扩展应对
- (j) 记录所有操作日志，支持审计追溯

### 【问题 1】（12 分）识别每条对应的质量属性
| 编号 | 质量属性 | 判断依据 |
|------|----------|----------|
| (a) | 非质量属性（功能/参与者） | 描述用户角色 |
| (b) | 安全性 | 抵御黑客攻击、检测防御 |
| (c) | 性能 | 响应时间 0.5 秒 |
| (d) | 可用性 | 故障恢复时间、持续运行 |
| (e) | 可修改性 | 规定时间内完成新功能开发 |
| (f) | 易用性 | 界面操作便捷、适合特殊用户 |
| (g) | 可测试性 | 模拟环境压力测试 |
| (h) | 可修改性（架构服务于可修改性） | 微服务解耦便于修改 |
| (i) | 性能（可扩展性为子属性）/ 可修改性 | 应对负载增长；强调"负载增长后性能仍满足"写性能，强调"系统能够扩展部署"写可修改性或可扩展性，视题干刺激而定 |
| (j) | 安全性（优先）/ 可测试性 | 日志审计追溯；"审计追溯"是安全性典型关键词，考试优先写安全性；仅当题干强调"便于测试、回放、定位问题"才更偏可测试性 |

### 【问题 2】（6 分）敏感点 / 权衡点
- **敏感点**：
  - (c) 描述的是**性能质量属性场景**（响应时间 0.5 秒）。影响该场景的架构决策——如服务拆分粒度、服务调用链路长度、负载均衡策略——才是**性能的敏感点**（服务拆分过细、多次网络调用显著增加延迟）。
  - (d) 描述的是**可用性质量属性场景**（5 分钟恢复）。影响该场景的架构决策——如冗余部署、心跳检测、自动切换机制——才是**可用性的敏感点**。
- **权衡点**：
  - (h)+(i) 微服务架构 = 性能与可修改性的权衡点。提升可修改性（独立开发部署），但服务间通信增加延迟影响性能。
  - (b)+(c) 安全防护 vs 性能 = 权衡点。加密/认证增加响应时间，需安全等级与性能间取舍。

### 【问题 3】（7 分）微服务架构适用性
- **适用性**：含乘客端、司机端、调度引擎、支付、评价等独立业务域，符合"按业务能力拆分"。
- **优点**：独立部署支持快速迭代（满足 e）；热点服务（调度引擎）可独立水平扩展（满足 i）；技术栈灵活。
- **缺点**：服务间通信增加延迟（影响 c）；分布式复杂度高、运维成本大；数据一致性保障困难（需分布式事务/最终一致性）。

## 真题二 · 2025 年 5 月（上半年）：在线大模型训练平台

### 【题干】
开发在线大模型训练平台，支持 Python 代码编写、模型训练和部署。用户提交 Python 代码，系统解析并匹配计算机资源，用户无需关心底层硬件。李工认为适合采用**解释器风格架构**。
- (a) 错误时异常请求不影响用户正常工作，并通知管理员
- (b) 方便操作，提供快捷键设置
- (c) 界面适配用户屏幕尺寸比例
- (d) 提交训练任务应在一分钟内提供硬件和资源
- (e) 新增 GPU 型号时无需修改核心代码即可适配
- (f) 对用户提交的恶意代码进行检测和拦截
- (g) 可在模拟环境下进行全链路压力测试
- (h) 响应时间不超过 2 秒
- (i) 支持未来从 x86 迁移到 ARM 平台
- (j) 连续运行时间不低于 720 小时
- (k) 运维人员更换时无需修改系统代码
- (l) 操作界面提供新手引导

### 【问题 1】（12 分）质量属性
| 编号 | 质量属性 | 关键词 |
|------|----------|--------|
| (a) | 可用性 | 错误不影响运行、通知管理员 |
| (b) | 易用性 | 快捷键、方便操作 |
| (c) | 易用性 | 界面适配、屏幕尺寸 |
| (d) | 性能 | 一分钟内响应 |
| (e) | 可修改性 | 新增 GPU 无需改核心代码 |
| (f) | 安全性 | 恶意代码检测拦截 |
| (g) | 可测试性 | 模拟环境、压力测试 |
| (h) | 性能 | 响应时间 2 秒 |
| (i) | 可修改性（可移植性） | 平台迁移 |
| (j) | 可用性 | 连续运行时间 |
| (k) | 可修改性 | 运维更换无需修改 |
| (l) | 易用性 | 新手引导 |

### 【问题 2】（6 分）解释器风格架构图填空
```
用户接口层（输入）→ 解释引擎（核心）→ 存储区（状态管理）→ 输出接口（执行层）
   Python代码编辑器      词法→语法→语义分析      代码仓库/状态      GPU/CPU资源调度
                         →代码优化→资源匹配        /资源分配表        →训练任务执行
```
填空要点：① 输入接口（用户提交的 Python 代码）② 解释引擎（解析/编译/调度）③ 存储区（保存中间状态和配置）④ 输出接口（解析结果映射到硬件资源执行）

> 📌 **解释器架构标准四组成部分（教材口径）**
> | 组成部分 | 作用 |
> |----------|------|
> | 输入接口 | 接收用户输入的规则、脚本、语言或配置 |
> | 解释引擎 | 完成语法分析、语义解释、规则匹配、执行控制 |
> | 存储区 | 保存解释过程中的状态、数据、配置、中间结果 |
> | 输出接口 | 输出执行结果，或驱动外部设备/模块执行 |
>
> 考试答题规范写法（可直接套）：本系统需解析用户提交的 Python 代码，并根据资源调度规则解释执行，符合解释器架构特征。解释引擎负责代码解析与资源匹配，存储区保存任务状态与资源配置，输出接口驱动底层 GPU/CPU 资源执行训练任务。

### 【问题 3】（7 分）为何适合解释器风格
1. **语言解析需求**：需对 Python 代码做词法/语法/语义解释，正是解释器核心能力。
2. **灵活性**：不同结构代码动态解析执行，无需预编译，满足可修改性。
3. **平台无关性**：解释引擎屏蔽底层硬件差异（GPU/CPU/x86/ARM），实现抽象层。
4. **可扩展性**：新增 GPU/框架只需在解释引擎加适配规则，不改核心架构。
5. **逐步执行与调试**：支持逐步执行，便于调试模型代码、查看中间结果。

## 真题四 · 2026 年 5 月（上半年）：智慧养老家居系统

### 【题干】
开发智慧养老家居系统。张工提出典型物联网系统应采用**分层架构**；李工提出边缘网关层采用**时序数据库**。
需求：传感器（温湿度、烟雾、红外、门磁）实时采集；本地初步处理与异常判断（跌倒、烟雾报警）；数据上传云端长期存储与大数据分析；家属 APP 远程查看；异常 10 秒内推送告警。

### 【问题 1】（7 分）物联网分层架构
| 层次 | 本系统功能 |
|------|------------|
| 感知层 | 温湿度/烟雾/红外/门磁传感器，采集环境与行为数据 |
| 网络层 | WiFi/ZigBee/蓝牙传至边缘网关，再经 4G/5G/宽带上传云端 |
| 平台层 | 边缘网关预处理与异常判断；云端存储、大数据分析、规则引擎 |
| 应用层 | 家属 APP、告警推送、健康报表、紧急呼叫联动 |

### 【问题 2】（8 分）为何边缘网关用时序数据库
传感器数据是典型时间序列数据（带时间戳、反映指标随时间变化趋势）。优势：
- **高写入性能**：针对高频写入优化，适合持续产生数据
- **时间范围查询高效**：支持"过去 24 小时温度变化"等窗口查询
- **数据压缩率高**：相邻点相似度高，压缩比可达 10:1 以上
- **内置降采样**：自动聚合（秒级→小时级），节省存储
- **边缘部署轻量**：适合资源有限的边缘网关

### 【问题 3】（10 分）质量属性角度的架构决策
| 质量属性 | 架构决策 | 分析 |
|----------|----------|------|
| 性能 | 边缘计算（本地预处理） | 异常判断本地完成，避免全量上云往返，确保 10 秒内告警 |
| 可用性 | 边缘网关离线自治 | 网络中断时本地仍可告警（如烟雾报警），不依赖云端 |
| 可修改性 | 分层架构 + 模块化 | 新增传感器/修改规则只改对应层 |
| 安全性 | 数据加密传输 + 访问控制 | 老人隐私数据加密，APP 需身份认证 |

## 真题六 · 2022 年下半年（系统架构设计师 案例‑1）：客户服务系统事件驱动重构

### 【题干】
某企业计划升级现有客户服务系统，原系统采用分层架构，随着业务扩张，出现如下问题：
1. 每新增一类客服业务，都需要修改核心业务模块代码，改动范围大；
2. 某一个子模块异常时，经常造成整个客服系统停止服务；
3. 模块之间调用链路长，高峰期用户查询响应缓慢。

架构团队计划重构系统，采用事件驱动架构，引入消息队列完成模块之间通信，实现业务解耦。

### 【问题 1】（6 分）分层架构与事件驱动架构的区别
| 对比维度 | 分层架构 | 事件驱动架构 |
|----------|----------|--------------|
| 调用方式 | 显式调用，上层直接调用下层 | 隐式调用（发布‑订阅），组件通过事件通知 |
| 耦合度 | 组件直接依赖，耦合度高 | 发布者无需感知订阅者，解耦，耦合度低 |

### 【问题 2】（9 分）引入事件驱动架构的收益与代价
| 质量属性 | 收益 / 代价 | 说明 |
|----------|------------|------|
| 可修改性 | 收益 | 业务模块解耦，新增客服业务只需新增订阅者，不需修改发布方代码，改动范围缩小 |
| 可用性 | 收益 | 订阅模块故障不会反向影响发布方，故障隔离，单个业务异常不会导致整个客服系统瘫痪 |
| 性能 | 代价 | 消息队列增加异步转发开销；高峰期消息堆积时查询延迟增加，带来性能损耗 |

### 【问题 3】（10 分）消息队列作为权衡点
**权衡点**：一个架构决策，同时正向影响一项质量属性，负向影响另一项质量属性。

本项目引入消息队列：
- 正向收益（可用性）：实现模块解耦、故障隔离，避免局部故障扩散，可用性提升；
- 负面代价（性能）：消息存储与转发产生额外开销，高峰期消息堆积增大请求延迟，降低系统性能。

因此，引入消息队列属于**可用性‑性能之间的权衡点**。

## 真题七 · 2021 年（案例‑1，质量属性改进题）：智慧水务监控系统

### 【题干】
某城市智慧水务监控系统，当前采用仓库架构，数据库作为中央共享数据存储区。各个监测终端客户端独立读取数据库中的配置数据，上报水务监测数据。运行一段时间后项目组发现如下问题：
1. 数据库压力过大，高峰期查询缓慢；
2. 数据库为单点，一旦故障，全部监测终端无法工作；
3. 各个客户端业务逻辑分散，后期维护修改成本很高。

### 【问题 1】（7 分）仓库架构特点与本系统问题
**仓库架构特点**：存在一个中央共享数据仓库，各客户端模块主动访问仓库读写数据；仓库被动存储，不主动调度客户端。

**本系统问题**：
1. 所有终端直接访问数据库，数据库压力过高，性能下降；
2. 数据库为唯一数据节点，存在单点故障风险，可用性差；
3. 业务逻辑分散在各个监测客户端，修改维护困难，可修改性差。

### 【问题 2】（8 分）引入缓存集群的收益与代价
| 质量属性 | 收益 / 代价 | 说明 |
|----------|------------|------|
| 性能 | 收益 | 热点监测数据存入缓存集群，终端优先读缓存，减少数据库访问，查询响应速度提升 |
| 一致性 | 代价 | 缓存与数据库主库数据可能出现不一致，需额外设计缓存更新与失效策略，增加系统复杂度 |

### 【问题 3】（10 分）完整的质量属性场景（性能）
在系统高峰期并发 300 台监测终端上报数据的运行环境下，水务监测终端对水务监控平台发起水质数据查询请求，监控平台的数据查询模块返回水质监测结果，查询平均响应时间小于 400ms。

> **六要素对照**：环境（高峰期并发 300 台终端）→ 刺激源（监测终端）→ 刺激（水质数据查询请求）→ 制品（数据查询模块）→ 响应（返回水质监测结果）→ 响应度量（平均响应时间 < 400ms）

# 📝 第一题答题模板库（考试直接套用）

## 模板 1：质量属性识别模板
**题目问**：请指出表中编号分别对应哪种质量属性。
**答题格式**（只要求名称就写名称，要求理由就按"属性 + 依据"）：
> (a) 性能 —— 关键词"响应时间 0.5 秒"
> (b) 可用性 —— 关键词"故障恢复 5 分钟内"

## 模板 2：架构风格优缺点模板
**题目问**：分析采用某架构风格的收益与代价。
> 该方案采用【事件驱动架构】。
> 从可修改性看：订单服务发布事件通知库存/积分/短信模块，新增下游模块不需修改订单服务代码，有利于快速新增业务功能。
> 从可用性看：模块通过消息中间件异步解耦，单个订阅模块故障不直接影响订单主流程，有利于提升可用性。
> 但事件驱动带来异步延迟、消息顺序、重复消费、事务一致性问题，也增加调试和测试难度。
> 因此该方案是在可修改性、可用性与性能、可测试性之间权衡。

## 模板 3：敏感点答题模板
> 敏感点是指某个架构决策对某一个质量属性有显著影响。
> 本系统中，【缓存策略】是性能的敏感点。原因是：缓存命中率显著影响订单查询响应时间；提高命中率可减少数据库访问、缩短响应时间，设计不合理则性能下降。

## 模板 4：权衡点答题模板
> 权衡点是指某个架构决策同时影响多个质量属性，且影响相互冲突。
> 本系统中，引入【消息中间件】是可用性与性能之间的权衡点。一方面实现异步解耦、故障隔离，提升可用性；另一方面消息存储转发带来额外延迟，高峰期可能堆积，降低性能。因此需权衡。

## 模板 5：质量属性场景六要素模板
> 在【高峰期并发 10 万用户观看直播】的环境下，【外部用户】对【播放服务】发起【视频播放请求】，系统需要【返回视频流】，且【平均首帧延迟不超过 500ms】。
> 对应六要素：刺激源=外部用户；刺激=播放请求；环境=高峰并发10万；制品=播放服务/CDN；响应=返回视频流；响应度量=首帧≤500ms。


# 🚀 新增预测练习题 · AI / 云原生新场景（2026 新大纲兜底）

## 预测题 A · 私有知识库 RAG 系统（新大纲高频预测题）
### 【题干】
某企业搭建私有知识库问答系统，流程：加载 PDF 文档 → 文本切块 → 生成向量嵌入 → 存入向量数据库；用户提问后查询向量库召回相关片段，拼接上下文送入大模型生成答案。
