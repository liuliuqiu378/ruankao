## 二、案例第1题必做25分·答题模板

> 这 25 分是过线地基。任何场景题都按下面五步走，几乎不绕脑。

**第一步：判质量属性（场景 → 属性）**

| 题干关键词 | 对应质量属性 |
|-----------|-------------|
| 并发/响应时间/吞吐/峰值 | 性能 |
| 数据加密/越权/审计 | 安全性 |
| 改一个模块影响面/上线不停机改 | 可修改性 |
| 故障后恢复/不中断 | 可用性 |
| 易学/界面友好 | 易用性 |
| 多端/跨平台/扩展新业务 | 可扩展性（可修改性子类） |
| 多用户同时操作不出错 | 功能性/并发正确性 |

**第二步：填效用树（质量属性 → 具体场景）**

把"质量属性"往下拆成"具体能验证的场景"。例如：
```
效用（根）
├─ 性能
│   ├─ 1000 并发下响应 < 2s
│   └─ 峰值 TPS ≥ 5000
├─ 安全性
│   ├─ 越权访问拦截率 100%
│   └─ 密码加盐存储
└─ 可修改性
    └─ 新增报表类型 < 1 人日
```

**第三步：标优先级 H / M / L（不是加权算分！）**

对每个叶子场景，按 **重要程度 × 实现难度** 标 H（高）/ M（中）/ L（低）。ATAM **不求和、不排名次**，只是帮助聚焦哪些场景最关键。

**第四步：辨四"点"**（见第五节，必考约 12 分）

**第五步：架构风格对比**（见第六节）

## 三、质量属性与战术（背多分素材库）

> 给"属性"要能写出"战术（怎么实现）"，这是第1题的半壁江山。

| 质量属性 | 常用战术（背 2~3 个即可） |
|----------|--------------------------|
| 性能 | 资源调度（优先级队列）、负载均衡、引入缓存、异步化、增加计算资源 |
| 可用性 | 冗余（双机热备/集群）、故障转移、心跳检测、优雅降级、限流 |
| 安全性 | 身份认证、授权（RBAC）、加密（传输 TLS/存储加盐）、审计日志、输入校验防注入 |
| 可修改性 | 降低耦合（接口抽象/事件解耦）、模块化、配置化、插件化 |
| 易用性 | 统一交互规范、默认值、向导、Feedback 提示 |

## 四、效用树正确填法

> **ATAM 的效用树只做三件事：填树 + 标 H/M/L + 后续辨四"点"。不考加权求和。**

- 根：效用（系统总目标）
- 一层：质量属性（性能/安全性/可修改性/可用性…）
- 二层：具体质量属性场景（可度量、可验证）
- 标注：每个场景标 **重要度(H/M/L)** 与 **难度(H/M/L)**

> ❌ **旧版错误**：把效用树当"加权评分表"（权重×得分求和）是错的，ATAM 不这么算。
> ✅ 考场要写的是：树结构 + 每个场景的 H/M/L 标注 + 一两句为何标这个级别。

## 五、四"点"辨析（风险点/非风险点/敏感点/权衡点）

> 第1题高频约 12 分。每个"点"都要能**下定义 + 举一个题干里的例子**。

| 点 | 定义 | 举例 |
|----|------|------|
| **风险点 (Risk)** | 某个架构决策**可能导致失败/出问题**的地方 | 单库单表，数据量持续翻倍 → 性能风险 |
| **非风险点 (Non-risk)** | 已被证明可行、**不会带来风险**的决策 | 采用成熟 ORM 框架，团队已踩坑多次 |
| **敏感点 (Sensitivity point)** | 某个**参数/构件的变化**会显著影响某一质量属性 | 线程池大小 → 显著影响响应时间 |
| **权衡点 (Tradeoff point)** | 影响**多个质量属性且相互冲突**的决策点 | 数据加密：↑安全性 但 ↓性能/↑开销 |

> 口诀：**敏感看"一个参数动→一个属性变"；权衡看"动一处→多个属性互相拉扯"。**

## 六、架构风格对比模板

> 第1题常要你"比较两种架构风格适用场景"。背这个通用模板。

| 风格 | 特点 | 适用 | 缺点 |
|------|------|------|------|
| 管道-过滤器 | 数据流式、阶段独立 | 编译器、ETL、流式处理 | 交互性差、共享状态难 |
| 仓库（数据共享） | 中央数据 + 独立构件 | IDE、DBMS、黑板系统 | 中心瓶颈、耦合高 |
| 事件驱动 | 构件通过事件解耦 | GUI、微服务异步 | 流程难追踪、调试难 |
| 分层 | 上层调下层 | 绝大多数企业应用 | 性能损耗、层间依赖 |
| 微服务 | 按业务拆、独立部署 | 复杂业务、弹性伸缩 | 分布式复杂度高 |
| 面向服务(SOA) | 服务通过 ESB 集成 | 企业系统集成 | ESB 中心化瓶颈 |

> 答题句式："风格 A 适合 __（因为__），但 __；本场景要求 __，故选 __。"

## 七、可靠性公式备查（一页纸，够用）

> 只用于：① 选做题万一出一小问"算几个9/乘可靠度"；② 上午选择题。案例大题不考手算。

```
串联：R = R1 × R2 × … × Rn        （越串越低）
并联：R = 1 − (1−R1)(1−R2)…       （越并越高）
TMR 三模冗余：R = 3R² − 2R³        （少数服从多数）
可用性：A = MTTF / (MTTF + MTTR)   MTBF = MTTF + MTTR
```

| 几个9 | 年停机 | 场景 |
|-------|--------|------|
| 99.9% | ~8.76h | 企业核心 |
| 99.99% | ~52.6min | 金融交易 |
| 99.999% | ~5.26min | 电信级 |

> 用例：0.98×0.95×0.90 ≈ 0.837；99.5%/99.8%/99.9% 串联 ≈ 99.2%。

## 八、选做题里的可靠性（背对比，不背手算）

> 可靠性若出现在选做题，本质是**概念/对比/填空**，背下面这些即可。

**N版本程序(NVP) vs 恢复块(Recovery Block)**：

| | N版本程序(NVP) | 恢复块(Recovery Block) |
|--|----------------|------------------------|
| 原理 | N个独立开发版本并行，多数表决 | 主模块 + 备份模块 + 接受测试(AT) |
| 恢复方式 | 故障屏蔽（后向无关） | 前向恢复（主失败切备份） |
| 关键 | 版本独立性（不同团队/算法） | 接受测试必须可靠 |
| 代价 | N份开发成本 | 1份主+备份，成本较低 |

**双机/冗余模式对比**：

| 模式 | 含义 | 特点 |
|------|------|------|
| 双机热备 | 主运行，备实时同步待命 | 切换快，备也耗资源 |
| 双机互备 | 两台各跑部分业务，互备对方 | 资源利用率高 |
| 双机双工 | 两台同时跑相同业务 | 负载高，复杂度高 |
| 冷备 | 备机关机待命，故障后启动 | 切换慢，成本低 |
| 集群 | 多节点，故障自动转移 | 高可用常用 |

**容错四手段**：冗余（结构/信息/时间/冗余附加）、错误检测、错误恢复（前向/后向）、防卫式程序设计。

## 九、马尔可夫：只理解概念，应付选择题

> 教材第9章有马尔可夫可靠性模型，但**案例从不要求手算 λ/μ 状态方程**，投入产出比极低。选择题最多考"理解"。

- **理解状态转移图**：S0（两机好）→ S1（一好一坏，仍可用）→ S2（两坏，不可用）。
- **退化态**：系统从"冗余态"退化到"单模运行态"。
- **冷备 vs 热备**：热备切换快但备机也耗资源；冷备切换慢但省资源。
- **选择题可能考**：给状态图，问"哪个状态系统仍可用" → S0/S1 可用，S2 不可用。

> ❌ 不要练带拉普拉斯变换的 λ/μ 稳态可用度手算——案例不会让你算，选择题只考概念。
