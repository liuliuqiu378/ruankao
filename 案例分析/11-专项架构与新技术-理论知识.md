# 1、大数据架构（Lambda / Kappa）（高频独立模块）

## 1.1 大数据架构的核心矛盾
大数据系统需同时处理两类数据：
- **历史全量数据**：量大、追求精准，但允许较高延迟（小时/天级）；
- **实时增量数据**：追求低延迟（秒/分钟级），只处理增量。

由此催生 Lambda 与 Kappa 两种主流架构。**2024 年 11 月真题以"奥运转播千万级实时数据 + 海量历史数据"大题考查，是题型 5 高频独立模块。**

## 1.2 Lambda 架构（"批 + 流"双管道）（必背）
Lambda 将数据处理拆为**实时流处理**和**离线批处理**两条管道，最后合并结果。

| 层级 | 职责 | 典型技术 |
|------|------|----------|
| **批处理层（Batch Layer）** | 处理全量历史数据，生成批处理视图，追求全量精准、容错高 | Hadoop MapReduce、Spark |
| **速度层 / 加速层（Speed Layer）** | 处理实时增量流数据，生成实时视图，追求低延迟 | Spark Streaming、Flink、Storm |
| **服务层（Serving Layer）** | 合并批处理视图与实时视图，对外提供统一查询 | HBase、MemSQL、Druid |

**特点**：高容错、历史数据精准；**缺点**：维护两套系统（批+流），架构复杂、一致性难以保证。
**适用**：需同时保障"历史全量精准"和"实时低延迟"的业务（如电商日销统计 + 实时热销榜、奥运转播当日概览 + 赛事回顾）。

## 1.3 Kappa 架构（"流处理"单管道）（必背）
Kappa **只用一套流处理引擎**统一处理实时与历史数据——历史数据被"模拟成流"重放处理，不再区分批与流。

**特点**：架构简单（只维护一套流系统）、数据一致性好（无批/流两层差异）；**缺点**：对流处理引擎性能要求极高，处理海量历史回溯时吞吐量受限。
**适用**：以实时为主、偶尔回溯历史的业务（如直播弹幕实时分析 + 历史弹幕回溯）。

## 1.4 Lambda vs Kappa 对比（简答题高频）

| 对比维度 | Lambda | Kappa |
|----------|--------|-------|
| 数据处理 | 批处理 + 流处理双管道 | 仅流处理单管道 |
| 架构复杂度 | 高（两套系统） | 低（一套流系统） |
| 数据一致性 | 批/流两层差异，一致性较难 | 单一链路，一致性好 |
| 历史数据处理 | 精准、容错高 | 依赖流引擎重放，性能压力大 |
| 典型场景 | 实时+历史并重 | 实时为主、偶回溯 |

## 1.5 大数据技术栈速记（架构图填空高频）
- **数据采集/接入**：Flume、Sqoop、Kafka；
- **数据存储**：HDFS（分布式文件）、HBase（列式 NoSQL）、数据仓库（维度建模）；
- **批处理计算**：MapReduce、Spark；
- **流处理计算**：Spark Streaming、Flink、Storm；
- **ETL / 数据集成**：ETL 工具；
- **服务/查询层**：HBase、MemSQL、Druid；
- **Web/Nginx**：前端接入。

> 💡 **真题答题抓手**：题干出现"实时（当日/秒级）+ 历史（不可变存储/回溯）"双需求 → 选 **Lambda**；仅"实时流 + 偶尔回溯" → 选 **Kappa**。

## 1.6 数据仓库 / 数据湖与维度建模（与题型 3 呼应）
- **星型模型**：事实表直接关联维表，单级维，查询效率高（最常用）；
- **雪花模型**：维表进一步规范化拆分，节省存储但查询 Join 多；
- **事实表**：事务事实表 / 周期快照事实表 / 累积快照事实表；
- **数据湖 vs 数据仓库**：数据仓库存结构化、已建模数据（Schema-on-Write）；数据湖存原始多类型数据（Schema-on-Read），支持数据科学与 AI 训练。

## 1.7 数据湖仓一体（Lakehouse）（新增热点）
- **核心特征**：统一存储（对象存储/HDFS）、开放表格式（Parquet/Iceberg/Delta Lake）、Schema Evolution、ACID 事务支持；
- **vs 传统数仓**：支持非结构化数据、存算分离、低成本海量存储；
- **实时计算关键概念**：
  - **Watermark 水位线**：处理乱序数据，容忍迟到记录；
  - **Exactly-Once 语义**：Checkpoint + 两阶段提交（Flink）/ 幂等写入；
  - **CDC 变更捕获**：Debezium/Canal 监听 Binlog，驱动下游实时更新。

# 2、嵌入式系统架构

## 2.1 嵌入式系统核心特征
- **资源受限**：CPU、内存、存储有限，需精简设计；
- **实时性要求高**：硬实时（必须在截止期内完成，如飞控）vs 软实时（尽量按时，如多媒体）；
- **可靠性/安全性高**：常运行于无人值守或关键场景；
- **专用性强**：软硬件协同，面向特定功能。

## 2.2 实时操作系统（RTOS）
- 提供任务调度、中断处理、任务间通信（消息队列/信号量/共享内存）；
- 常见 RTOS：VxWorks、RT-Thread、FreeRTOS、QNX（车载/工业）。

## 2.3 嵌入式高频通信协议（真题热点）
### （1）SOME/IP（汽车以太网，2024 上半年真题）
SOME/IP（Scalable service-Oriented Middleware over IP）：面向汽车以太网的可扩展面向服务 IP 中间件，AUTOSAR 发布。
- 特点：**服务导向架构（SOA）**；支持**远程过程调用（RPC）**；轻量级；多种通信方式（请求/响应、事件通知、发布/订阅）；二进制编码高效；支持 TCP/UDP；**动态服务发现（SOME/IP SD）**。
- 适用：车载 ECU 间面向服务通信、智能网联汽车、自动驾驶。

### （2）DDS（数据分发服务，2024 上半年真题）
DDS（Data Distribution Service）：实时高效的数据分发中间件，基于发布/订阅。
- 特点：高实时性、QoS 控制（可靠性/时延/带宽）、去中心化发现；
- 适用：工业自动化、航空航天、机器人等高实时性场景。

> **SOME/IP vs DDS 选型口诀**：汽车以太网/车载 SOA 通信 → SOME/IP；高实时数据分发/机器人多机协同 → DDS。

## 2.4 ROS / ROS2（机器人操作系统，2024 下半年真题）
- **ROS**：面向机器人的开源操作系统框架，提供硬件抽象、底层设备控制、进程间通信（IPC）、工具库；特点：分布式（Pub/Sub）、消息传递、包管理、多语言（C++/Python）。
- **ROS2 相对 ROS1 改进**（简答高频）：
  1. 通信机制升级：ROS1 用 TCPROS/UDPROS，ROS2 采用 **DDS**，支持更高效分布式通信；
  2. 跨平台增强：ROS2 支持 Linux/Windows/Mac/RTOS；
  3. 实时性提升：DDS 提供 **QoS 控制**，适用于时延敏感实时系统；
  4. 安全性提升：ROS2 提供身份验证、加密通信；
  5. 生命周期管理：引入节点生命周期（启动/挂起/恢复）。

### ROS 四种通信方式（选词填空高频）
| 通信方式 | 机制 | 适用场景 |
|----------|------|----------|
| **话题（Topic）** | 发布/订阅（Pub/Sub），单向异步 | 传感器数据共享 |
| **服务（Service）** | 请求/响应（Request/Response） | 单次查询/操作 |
| **动作（Action）** | 长时任务，支持异步反馈 | 机器人导航等长时间任务 |
| **参数（Parameter）** | 全局配置变量，可动态调整 | 系统运行参数配置 |

# 3、IoT / 边缘计算架构

## 3.1 端边云三层架构
- **端（设备层）**：传感器/执行器、嵌入式设备，负责数据采集与执行；
- **边（边缘层）**：边缘网关/边缘节点，就近处理数据，降低时延与回源带宽；
- **云（云端）**：中心云，负责海量数据存储、全局分析与模型训练。

## 3.2 物联网通信协议
- **MQTT**：轻量级发布/订阅，适合低带宽、不稳定网络（设备→云端主流）；
- **CoAP**：受限应用协议，基于 UDP，类 HTTP 语义，适合资源受限设备；
- **HTTP/HTTPS**：与云端 API 交互。

## 3.3 边缘计算核心价值
- 低时延（数据就近处理）、减少云端带宽压力、本地隐私保护、离线可用；
- 典型场景：智能工厂、车路协同、智慧城市摄像头就近分析。

# 4、AI 系统架构（2026 新大纲重点，约 25%）

## 4.1 AI 系统架构的核心需求
- **训练侧**：大规模集群、高速网络（RDMA/RoCE）、分布式训练（数据并行/模型并行/流水线并行）、GPU/AI 加速卡资源调度；
- **推理侧**：低推理延迟、高吞吐、模型服务化（Model-as-a-Service）、弹性扩缩。

## 4.2 典型 AI 架构模式
- **训练平台架构**：用户代码 → 解析器/编译器 → 执行引擎 → 资源调度器 → GPU/计算资源（**解释器风格**，2025 上半年真题考点）；
- **推理服务架构**：模型仓库 → 模型服务（推理引擎）→ API 网关 → 业务应用；支持模型版本管理、灰度发布、A/B 测试；
- **RAG（检索增强生成）架构**：用户 Query → 向量检索（知识库/向量数据库）→ 召回上下文 → 大模型生成 → 结果返回；解决大模型"幻觉"与知识时效性；
- **Agent / 多智能体架构**：规划（Planner）→ 工具调用（Tool Use）→ 记忆（Memory）→ 反思（Reflection），支持分层委托（父 Agent 编排、子 Agent 执行复杂子任务）。

## 4.3 AI 架构关键质量属性（与题型 1 质量属性结合）
- **推理延迟**（性能）：端到端响应时间、首 Token 延迟；
- **吞吐（QPS/TPS）**：并发推理能力；
- **模型准确率 / 可用率**（功能/可用性）；
- **可解释性**：决策可追溯、审计日志；
- **数据隐私与安全**：训练/推理数据脱敏、访问控制。

## 4.4 AI 集群高性能网络（2025 真题方向）
- **RDMA / RoCE**：远程直接内存访问，绕过 CPU 降低时延，万卡训练刚需；
- **ECMP 负载均衡**：等价多路径，但易出现哈希不均；**包喷洒（Packet Spraying）** 可将流打散到多路径，缓解拥塞；
- **拥塞控制算法**（如 APSCC）：动态调整拥塞阈值，保障训练稳定性；
- **弹性伸缩 + 高可靠**：节点扩容拓扑调整快速、故障恢复时间达标（如 ≤5 分钟）。

## 4.5 推理加速与成本优化战术（高频踩分）
- **推理加速**：PagedAttention（vLLM，显存分页复用 KV Cache）、算子融合（TensorRT）、投机采样（Speculative Decoding，小模型草稿+大模型验证）；
- **量化压缩**：INT8/INT4 量化、模型蒸馏，降低显存与算力消耗；
- **弹性伸缩**：基于队列长度/GPU 利用率的 HPA、Spot 实例混合部署；
- **成本控制**：模型路由（简单问题路由小模型）、语义缓存（相似请求直接复用）、离线批量推理；
- **可观测**：Token 消耗监控、链路追踪、幻觉检测。

## 4.6 Agent 智能体架构与编排（2026 新大纲）
- **核心循环**：感知（Perception）→ 规划（Planning，ReAct/CoT）→ 行动（Action，Tool Use）→ 记忆（Memory，短期上下文+长期持久化）；
- **编排模式**：单 Agent、多 Agent 协作（CrewAI/AutoGen 角色分工）、人机协同（HITL）；
- **工程考点**：工具注册与发现、上下文压缩策略、Guardrails 安全护栏（防敏感信息泄露/越权）、可观测性。

> 💡 **案例答题话术**：当题目涉及 AI 需求时，必须同时回答**功能实现 + 非功能保障**。例如："采用 RAG 架构提升回答准确率（功能），通过向量缓存+模型量化将 P99 延迟控制在 500ms 内（性能），并部署 Guardrails 防止敏感信息泄露（安全）。"

# 5、安全架构（独立模块）

## 5.1 零信任架构（Zero Trust）
- 核心原则：**永不信任，始终验证**；默认不信任内外网，基于身份/设备/环境动态授权；
- 关键能力：身份认证、设备合规检查、最小权限、微隔离、持续监测。

## 5.2 身份认证与访问控制模型（必背）
- **RBAC（基于角色）**：权限分配给角色，用户通过角色获得权限，适合常规系统；
- **ABAC（基于属性）**：基于用户/资源/环境属性 + 策略决策，细粒度、动态，适合敏感/复杂场景；
- **ReBAC（基于关系）**：基于关系图模型（如 Google Zanzibar），适合社交网络、文档协作等关系驱动的权限场景；
- 组合用法：常规用 RBAC，敏感场景叠加 ABAC，关系协作场景用 ReBAC。

## 5.3 数据加密与脱敏
- **加密**：传输层 TLS，存储层 AES/RSA；国密算法 **SM2（非对称）/SM3（哈希）/SM4（对称）** 用于国产化合规场景；
- **数据脱敏**：对敏感字段（身份证/手机号/姓名）进行变形/遮蔽，保留可用性同时防泄露，常用于测试/分析环境。

## 5.4 等保 2.0 分级保护
- 网络安全等级保护 2.0，分五级（一至五级，等级越高要求越严）；
- 政务/金融核心系统常要求**等保三级**；要点：安全物理/网络/主机/应用/数据安全 + 安全管理中心。

## 5.5 安全架构设计要点
- 身份认证（OAuth2/OIDC + JWT）、权限控制（RBAC/ABAC）、传输/存储加密、数据脱敏、审计日志、入侵检测/防护、灾备与恢复。

# 6、系统计划（项目立项 / 可行性研究 / 技术方案论证）

> 官方独立模块，原五分法遗漏，属重点补充（非边缘）。案例题常以"系统计划类论述/方案论证"出现。

## 6.1 项目立项
- 立项依据：业务需求、战略匹配、政策/合规要求；
- 产出：立项建议书、项目章程，明确目标/范围/约束/ stakeholders。

## 6.2 可行性研究（四方面，必背）
| 维度 | 核心问题 |
|------|----------|
| **技术可行性** | 技术方案是否成熟、团队是否具备能力、技术风险是否可控 |
| **经济可行性** | 成本/收益分析，投资回报率（ROI）、回收期是否合理 |
| **操作/运行可行性** | 组织/人员/流程是否支持系统上线运行 |
| **法律/合规可行性** | 是否符合法律法规、行业标准、数据安全/隐私要求 |

## 6.3 技术方案论证
- 多方案对比（候选架构/技术栈），从**功能满足度、性能、成本、风险、可扩展性、合规性**等维度论证，给出推荐方案及理由；
- **经济指标**：ROI（投资回报率）、TCO（总拥有成本）、投资回收期；
- **里程碑规划**：分阶段交付，设置验收标准；
- **风险识别**：识别技术/人员/进度 Top3 风险，给出缓解措施；
- 产出：可行性研究报告、技术方案选型报告。

# 7、通信系统架构

> 官方独立模块，原五分法遗漏，重点补充。

## 7.1 网络拓扑
- 总线型、星型、环型、树型、网状（Mesh）；拓扑选择影响可靠性、扩展性、成本。

## 7.2 通信协议分层（OSI/TCP-IP 速记）
- 物理层/数据链路层（MAC）/网络层（IP/路由）/传输层（TCP/UDP）/应用层（HTTP/MQTT/DDS/SOME-IP）；
- **TCP vs UDP**：TCP 可靠、面向连接、有序；UDP 无连接、低时延、可能丢包；实时/车载场景常基于 UDP 或 TCP+UDP 混合。

## 7.3 通信中间件
- 消息队列（Kafka/RocketMQ/MQTT Broker）、DDS、SOME-IP SD：屏蔽底层网络差异，提供统一通信抽象；
- 协议转换/网关：异构协议互通（如 HTTP↔MQTT、TCP↔UDP）；
- **RPC/服务调用**：gRPC（HTTP/2 + Protobuf，强类型、低延迟）vs HTTP/REST；服务网格（Istio）提供流量治理、mTLS、可观测；
- **QoS 保障**：流量整形、优先级队列、拥塞控制；多链路冗余与故障链路切换。

## 7.4 时延构成与 RTT（简答题高频）
- **时延四要素**：传输时延（数据块/带宽）、传播时延（距离/光速）、处理时延（路由/设备）、排队时延（拥塞）；
- **RTT 往返时间**：数据发出到收到 ACK 的往返耗时；
- **QoS 指标**：带宽、时延、抖动（时延变化）、丢包率。

# 8、区块链技术应用（2025 大纲新增）

## 8.1 核心特性
- **去中心化 / 分布式账本**：数据多节点共同维护，无单点；
- **不可篡改**：区块按哈希链相连，篡改需重构后续所有区块；
- **共识机制**：节点间达成一致（PoW/PoS/PBFT 等）；
- **智能合约**：部署在链上的可执行合约代码，自动执行约定逻辑。

## 8.2 联盟链架构（考纲明确"联盟链架构设计"）
- 联盟链：由若干可信组织共同维护，半开放，兼顾信任与效率；
- 典型平台：**Hyperledger Fabric**（权限管理、通道隔离、链码/智能合约、CA 身份认证）；
- 适用：跨机构可信协作（供应链金融、跨境支付、电子存证、政务数据共享）。

## 8.3 区块链应用方案设计要点
- 明确参与方/节点角色、共识机制选型、智能合约逻辑、数据上链 vs 链下存储分工（大数据/隐私数据链下存、哈希/凭证上链）、权限与隐私保护（通道/隐私交易）、审计追溯。

## 8.4 区块链五层经典架构
1. **数据层**：区块、链式结构、哈希、默克尔树、非对称加密；
2. **网络层**：P2P 对等网络、数据传播与验证；
3. **共识层**：共识算法（PoW/PoS/PBFT）；
4. **激励层**：代币奖励（公有链特有）；
5. **应用层**：智能合约、DApp。

## 8.5 智能合约与共识选型
- **智能合约**：部署在链上、条件满足自动执行的代码（Solidity/WASM），部署后不可随意修改，需**形式化验证**防漏洞；
- **共识选型口诀**：公链、大量匿名节点 → PoW/PoS；联盟链、许可链、企业内部多方可信节点 → PBFT（强一致、速度快）；
- **适用 / 不适用**：适合多方不完全互信、需留痕审计防篡改（供应链溯源、电子存证）；不适合高并发高频交易（吞吐性能低）。

# 9、信创与国产化替代（近年极热隐藏考点）

> 随"数据二十条"与国家信创战略，政务/金融核心系统国产化改造频繁出现在架构选型/安全架构论述题中。

## 9.1 信创四类核心国产化组件（必背，举例优先高频代表）
| 组件类别 | 典型代表 |
|----------|----------|
| **国产化芯片** | 龙芯、飞腾、鲲鹏、海光 |
| **国产化操作系统** | 银河麒麟、统信 UOS、中标麒麟 |
| **国产化数据库** | 达梦 DM、人大金仓 KingbaseES、OceanBase、GaussDB |
| **国产化中间件** | 东方通、金蝶中间件 |

## 9.2 信创架构设计四大核心原则（必背）
1. **自主可控原则**：核心软硬件全部国产化，打破国外技术垄断，保障信息安全；
2. **安全可靠原则**：满足等保要求，具备数据加密、权限控制、安全合规；
3. **适配兼容原则**：适配原有业务系统，标准化接口，实现平滑迁移，降低改造成本；
4. **可扩展原则**：预留升级接口，支持业务扩展与国产化组件迭代。

## 9.3 信创改造核心流程（方案设计题抓手）
1. **需求分析**：明确国产化替代目标、性能不降、数据安全、成本控制；
2. **组件选型**：选用适配业务的国产化组件（芯片+OS+数据库+中间件）；
3. **架构设计**：分层（表现层/业务层/数据层）+ 模块化，接口标准化、组件兼容；
4. **迁移改造**：数据迁移（全量+增量同步）、应用适配/兼容性测试、性能与安全测试；
5. **运维保障**：建立国产化组件运维体系、补丁/漏洞管理、监控告警。

## 9.4 国产化数据库迁移要点
- **数据迁移**：全量迁移 + 增量同步（如达梦/金仓迁移工具、KingbaseFlySync），双轨运行保障一致性；
- **兼容性**：优先选与原有库（如 Oracle）兼容性好的国产库（达梦与 Oracle 兼容性业内领先），降低应用改造量；
- **高可用**：达梦 DMDSC 共享存储集群（对等替换 Oracle RAC）、数据守护/异步备库、两地三中心容灾；人大金仓读写分离集群、OceanBase 多副本（Paxos）；
- **目标**：数据零丢失（RPO≈0）、服务零中断/快速切换（RTO 分钟级）。

## 9.5 国密算法应用场景
- SM2（非对称加密/签名，替代 RSA）、SM3（哈希，替代 MD5/SHA-1）、SM4（对称加密，替代 AES/3DES）；用于身份认证、数据加密存储/传输、数字签名、合规审计。

# 10、数据要素与数据资产（"数据二十条"导向）

> 随"数据二十条"发布，数据治理、数据血缘、隐私计算在架构设计中比重增加，可能以论述题出现。

## 10.1 数据治理体系
- 数据标准、数据质量（完整性/一致性/准确性/及时性）、元数据管理、主数据管理（MDM）、数据资产管理。

## 10.2 数据血缘
- 记录数据从源头到消费的完整流转链路（产生→加工→存储→消费），用于影响分析、问题溯源、合规审计；
- 实现：通过元数据平台/数据治理工具自动采集血缘关系。

## 10.3 隐私计算（跨域数据共享的架构角色）
- **联邦学习**：各参与方本地训练模型、仅交换模型参数/梯度，原始数据不出域，实现"数据可用不可见"；
- 适用：跨机构数据协作（金融风控、医疗联合建模）且数据隐私要求高的场景。

## 10.4 数据资产化
- 将数据视为企业资产进行盘点、确权、估值、运营；数据中台/数据湖是数据资产化的常见载体。

# 11、可靠性设计

## 11.1 可靠性指标
- **可靠度 R(t)**：系统在规定时间内正常工作的概率；
- **失效率 λ**：单位时间失效概率（常数时符合指数分布）；
- **MTBF（平均无故障时间）**、**MTTR（平均修复时间）**；可用性 ≈ MTBF/(MTBF+MTTR)。

## 11.2 串并联系统可靠度计算（必背公式）
- **串联系统**：任一部件失效则系统失效，可靠度 **R = R₁ × R₂ × … × Rₙ**（乘积）；
- **并联系统**：所有部件均失效才系统失效，可靠度 **R = 1 − (1−R₁)(1−R₂)…(1−Rₙ)**；
- 混合系统：先算并联子系统可靠度，再按串联相乘。

## 11.3 容错与可靠设计技术
- **冗余**：硬件冗余、软件 N 版本程序设计、信息冗余（校验码）；
- **N 版本程序设计**：独立编写 N 个功能等价版本，多数表决输出，抵御软件设计缺陷；
- **恢复块**：主模块 + 后备模块，主模块失败则切换后备；
- **故障检测**：心跳检测、超时探测、看门狗、BIT（内置自测）。

# 12、架构演化（遗留系统改造）

## 12.1 绞杀者模式（Strangler Fig）
- 在遗留系统外围逐步构建新功能/服务，新需求走新系统，旧系统逐渐被"绞杀"替换；降低一次性重写风险，支持增量迁移。

## 12.2 防腐层（ACL，Anti-Corruption Layer）
- 在新系统与遗留系统之间引入适配层，隔离遗留模型的污染，将遗留接口翻译为新模型；2024H2–2025 真题更易踩分。

## 12.3 抽象分支（Branch by Abstraction）
- 通过引入抽象接口，先切换调用方到抽象层，再逐步替换底层实现，实现平滑迁移、并行运行；与绞杀者常配合使用。

# 13、案例题通用答题话术模板（题型 5 通适）

1. **架构选型题（Lambda/Kappa/端边云/联盟链）**：先判业务核心特征（实时+历史并重 → Lambda；实时为主 → Kappa；跨机构可信协作 → 联盟链；低时延近端处理 → 边缘计算），再列候选方案对比，给出推荐及理由。
2. **方案设计题（信创/安全/数据治理）**：按"原则/组件 + 对应需求 + 简要解释"作答，紧扣题干关键词（如"自主可控""等保三级""数据零丢失"）。
3. **问题诊断题**：先定位根因（网络/资源/一致性/安全），再对应机制（限流熔断/冗余容错/加密脱敏/对账补偿）。
4. **嵌入式/协议填空**：抓协议特征关键词（SOME/IP→车载 SOA/RPC/服务发现；DDS→高实时/QoS/发布订阅；MQTT→轻量发布订阅/低带宽）。
5. **可行性/立项论述**：从技术/经济/运行/合规四方面逐条论证，结合题干约束给出结论。

# 14、架构评估专题（ATAM）（与系统计划捆绑出题）

## 14.1 核心概念（必背，简答/填空高频）
- **风险点（Risk）**：架构设计中可能造成质量目标无法达成的潜在隐患；
- **非风险点（Non-Risk）**：当前设计对质量目标有正面保障、无隐患；
- **敏感点（Sensitivity）**：某个组件/参数的单一属性变化会显著影响某一质量属性；
- **权衡点（Trade-off）**：某属性变好必然导致另一属性变差，需要取舍；典型：性能 ↔ 安全性、性能 ↔ 可修改性。

## 14.2 ATAM 架构权衡分析方法步骤
1. 描述架构（呈现架构视图与关键决策）；
2. 确定质量属性目标（性能/可用性/安全性/可修改性等）；
3. 生成/识别架构方案（含备选）；
4. 识别风险点、非风险点、敏感点、权衡点；
5. 基于场景评估方案，做出取舍决策。

# 15、考场选做题决策指南（非常重要）

> 下午案例选做题（题型 5）通常提供多个专项方向供三选一，按熟悉度与稳定性决策。

## 15.1 优先选做顺序
1. **先看分布式/微服务/云原生大题**：题目常规、套路稳定，优先选；
2. **若微服务偏难，转向大数据（Lambda-Kappa）**：结构化强、模板清晰；
3. **前两道都难，再选熟悉的专项赛道**：嵌入式/IoT、AI、通信、区块链等。

## 15.2 各专项赛道选题抓手
- **大数据**：题干出现"实时+历史双需求"直接选 Lambda/Kappa；
- **嵌入式/通信**：有硬件/汽车/工业背景，抓 SOME/IP、DDS、RM/EDF 关键词；
- **AI 工程**：出现 RAG/Agent/训练推理分离/MLOps 关键词直接套模板；
- **区块链**：出现多方协作、防篡改、存证溯源选联盟链（Fabric+PBFT）；
- **信创/安全**：出现自主可控、等保、国密、国产替代直接套信创四原则+国密。
