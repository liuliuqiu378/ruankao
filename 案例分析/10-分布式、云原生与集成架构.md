# 1、微服务架构
## 1.1 定义
微服务是一种架构风格，将**单体大应用拆分为一组小型自治服务**，每个服务围绕单一业务能力构建、可独立部署，服务之间通过轻量通信机制协作。

## 1.2 微服务六大核心特征（案例踩分关键词）
1. **单一职责**：一个服务只负责一块业务能力；
2. **独立部署**：服务互不依赖，可以单独上线、回滚，不影响其他服务；
3. **去中心化治理**：每个服务可自主选择开发语言、技术栈；
4. **去中心化数据管理**：**一服务一数据库**，禁止共享数据库；
5. **轻量级通信**：REST‑HTTP、gRPC、消息队列（Kafka/RabbitMQ）；
6. **面向失败设计**：天然考虑远程调用失败，使用熔断、降级、超时、重试。

## 1.3 微服务优点
- 模块解耦，独立迭代，发布速度快；
- 技术栈异构；
- 故障隔离，局部故障不会拖垮整个系统；
- 便于弹性伸缩，高并发场景资源利用率高；
- 适合大团队并行开发。

## 1.4 微服务缺点（案例高频：分析系统存在问题）
- **分布式复杂度上升**：网络延迟、丢包、调用失败；
- 分布式事务、数据一致性难题；
- 运维复杂度暴涨，大量实例需要监控管理；
- 服务依赖关系复杂，出现调用雪崩风险；
- 开发调试难度增加；
- 需要配套完整服务治理基础设施。

## 1.5 微服务拆分策略
- 按业务域拆分；
- 基于DDD限界上下文拆分；
- 避免循环依赖；
- 粒度适中，不要过细造成"纳米服务"。

# 2、SOA / ESB 企业服务总线（集成架构）
## 2.1 SOA面向服务架构
SOA是一种组件模型，将应用功能封装成可互操作的服务，通过网络进行调用，实现业务复用与系统集成。

## 2.2 ESB企业服务总线
ESB是SOA架构中的**中间件总线**，作为服务请求者和提供者之间的中间层。
### ESB核心功能（案例高频考点）
1. **位置透明性**：服务消费者无需感知服务提供者的物理位置（新增，10文件原缺）；
2. **协议转换**：HTTP、WebService、REST、TCP、JMS之间协议互转；
3. **消息路由**：根据条件/内容转发消息；
4. **数据格式转换**：XML‑JSON、报文等数据格式适配；
5. **消息增强**：补充/校验消息头、安全凭证等；
6. **服务编排**：组合多个服务完成业务流程；
7. **安全、日志审计、监控管理及异常处理**。

### 采用ESB的三方面理由（案例标准答法）
| 维度 | ESB带来的价值 |
|------|--------------|
| 部署方式 | 支持灵活部署结构（C/S、P2P等），总线统一接入 |
| 耦合程度 | 待集成系统只与总线通信，彼此解耦，改一个不影响其他 |
| 可扩展性 | 新增系统以"插件式"接入，仅需适配协议与数据格式 |

## 2.3 SOA vs 微服务（高频对比简答题）

|对比维度|SOA|微服务|
|---|---|---|
|通信中枢|强依赖ESB（智能管道）|哑管道，无重型总线，网关轻量化|
|服务粒度|粗粒度服务|细粒度业务服务|
|数据库|常出现共享数据库|每个服务独立数据库|
|治理模式|集中治理|去中心化治理|
|部署模式|集中部署|每个服务独立部署|
|适用场景|遗留系统集成、大型企业异构系统打通|互联网业务、快速迭代高并发业务|

>答题话术：从SOA演进到微服务，通常需要**去掉重型ESB，换成轻量API网关**。

# 3、API网关
## 3.1 作用
所有客户端请求统一入口，**反向路由**，屏蔽后端微服务地址。

## 3.2 核心功能（简答题背诵）
1. 请求路由；
2. 负载均衡；
3. 认证授权、安全校验；
4. 限流熔断；
5. 请求日志、监控；
6. 协议转换；
7. 灰度发布；
8. 缓存。

>网关和ESB区别：API网关侧重**南北流量（客户端→后端）**；ESB侧重**东西流量（服务‑服务之间集成）**。

## 3.3 统一身份认证与权限控制设计（案例高频）
- **认证**：OAuth2 / OpenID Connect 统一认证，网关颁发/校验 Access Token（JWT）；
- **权限**：微服务内部用 **RBAC**（基于角色）鉴权，敏感场景叠加 **ABAC**（基于属性：组织/标签/状态）；
- **Token传递**：客户端登录获 JWT → 网关校验后转发认证信息 → 各服务解析 JWT 实现**无状态验证**。

## 3.4 网关层高可用与性能优化（针对高频接口）
- 网关层限流（令牌桶/漏桶），按 IP/用户等级限流；
- CDN 边缘缓存静态资源/文件下载；大文件分片上传/断点续传；
- 异步处理 + 任务队列解耦；文件处理服务独立部署、水平扩展。

# 4、微服务完整治理体系（案例大题高频）
微服务治理 = 注册中心 + 配置中心 + 熔断限流容错 + 链路追踪 + 监控告警

1. **注册中心（Nacos/Eureka/Consul）**：服务注册、服务发现，解决服务实例地址动态变化；
2. **配置中心**：将配置文件从代码剥离，集中管理，动态更新配置，无需重启服务；
3. **容错组件（Sentinel、Hystrix）**
    - **熔断**：当下游失败率到达阈值，直接快速失败，防止雪崩；
    - **降级**：故障时返回兜底结果，牺牲非核心功能保障核心链路；
    - **限流**：限制请求QPS，保护服务不被打垮；
    - **超时、重试**；
4. **可观测性三支柱（必背）**
    - **指标(Metrics)**：CPU、内存、QPS、响应延迟；
    - **日志(Logging)**：业务日志；
    - **链路追踪(Tracing)**：Jaeger、SkyWalking，追踪一条请求经过的所有微服务调用链，定位性能瓶颈。

# 5、分布式系统核心难题
## 5.1 CAP理论
- **C一致性**：所有节点同一时刻看到相同数据；
- **A可用性**：每个请求都收到响应；
- **P分区容错性**：网络分区故障，系统仍然可以运行；
>分布式系统中P不可避免，只能选择 CP / AP。
> **CP vs AP 选型**：支付/金融 → **CP**（保数据一致，如 ZooKeeper）；社交/电商读多 → **AP**（保服务可用，如 Eureka）。

## 5.2 BASE理论（最终一致性）
- 基本可用（BA）+ 软状态（S）+ 最终一致性（E）；互联网微服务系统大多采用BASE，放弃强一致，换取高可用。

## 5.3 分布式事务常见方案
1. **2PC 两阶段提交**：协调者发 prepare → 参与者投票 → commit/rollback；强一致、短事务，跨库转账；同步阻塞、性能差，适合低并发；
2. **TCC**：Try‑Confirm‑Cancel；业务侵入性高，需业务层三阶段（预留资源→确认→取消），如支付；
3. **Saga模式**：长事务拆分为本地事务链 + 补偿动作，微服务最常用；**长流程、跨服务**（订单→库存→支付），2025 真题考点；
4. **本地消息表**：本地事务与消息表同库写入 → 异步投递 → 下游消费，最终一致性、解耦；
5. **事务消息（RocketMQ）**：消息中间件保证"消息可靠投递 + 本地事务"的原子性，如订单创建与库存扣减；
6. **Seata**：阿里开源分布式事务框架，支持 AT/TCC/Saga，一站式解决方案。

> 💡 **案例题答题要点**：优先判断业务是"强一致（CP）"还是"最终一致（AP）"；互联网高并发场景多用**最终一致性 + 消息队列 + 补偿/对账**。

## 5.4 分布式数据方案
- **分库分表**：水平分片（按用户 ID 哈希），中间件 ShardingSphere / MyCat；
- **读写分离**：主库写、从库读，降低主库压力；
- **数据一致性**：缓存与数据库一致性（Cache Aside + 延迟双删 / Canal 订阅 binlog）；
- **分布式锁**：Redis `SET NX PX` + 防误删 + 看门狗续期。

# 6、云原生架构
云原生四大支柱：**微服务 + 容器(Docker)+ DevOps + 持续交付**

## 6.1 12‑Factor 云原生十二要素（案例高频改造踩分点）
>当题目问：如何改造应用适配云原生？尽量覆盖下面要点
1. 基准代码：一份代码库，多部署环境；
2. 依赖：显式声明所有依赖；
3. 配置：配置与代码分离，环境变量保存配置，禁止硬编码；
4. 后端服务：把数据库、消息队列当作附加资源；
5. 构建、发布、运行严格分离；
6. 无状态进程：实例无本地会话数据；
7. 端口绑定：通过端口对外提供服务；
8. 并发：水平扩展，多实例；
9. 可丢弃：进程快速启动、优雅关闭；
10. 开发/生产环境等价；
11. 日志：当作事件流，不存本地；
12. 管理进程：后台任务一次性运行。

>**无状态**：云原生改造最高频关键词，会话、缓存数据不能保存在容器本地。

# 7、Docker容器
- 镜像：只读模板；容器：镜像运行实例；
- 解决痛点：**开发‑测试‑生产环境不一致**问题；
- 轻量级，进程隔离，相比虚拟机开销小，启动速度快。

# 8、Kubernetes（K8s）核心考点
## 8.1 定位：容器编排平台，大规模自动化管理容器集群。
## 8.2 基础概念
1. **Pod**：K8s最小调度单元；一个Pod可以封装1个或多个容器；
2. Deployment：无状态应用管理，实现副本扩缩、滚动更新、灰度；
3. StatefulSet：有状态应用（数据库）；
4. Service：一组Pod的统一访问入口，负载均衡；
5. Ingress：七层HTTP反向路由；
6. ConfigMap/Secret：存放配置、敏感密码；
7. HPA：水平Pod自动扩缩容，CPU/QPS指标自动增减实例数。

## 8.3 K8s高频场景
- 自动故障自愈，重启异常Pod；
- 滚动升级、不停机发布，保留旧版本支持一键回滚；
- 弹性伸缩应对流量高峰（HPA 基于 CPU/自定义指标如 QPS 扩容，流量结束自动缩容）；
- **Namespace 隔离**：多环境/多租户隔离，如"测试环境数据污染"→ 每 PR 独立 Namespace；
- **探针/自愈**：存活探针（liveness）失败自动重启 Pod，就绪探针（readiness）差异化设置，保障流量只进健康实例。

> 🎯 **K8s / Service Mesh / DevOps 三者分工一句话记忆**：**K8s 管"生死扩缩容"（资源层），Service Mesh 管"调用与可靠"（通信层），DevOps 流水线管"快上快回滚"（交付层）**。案例高频论述题标准答法。

# 9、Service Mesh 服务网格（2025‑2026新增热点）
## 9.1 核心定义
一种**非侵入式**的微服务治理方案，将流量治理逻辑从业务代码剥离出来，放到Sidecar代理进程。
## 9.2 两大平面
1. **数据平面（Sidecar‑Envoy）**：拦截服务之间流量，处理限流、熔断、mTLS加密、链路追踪；
2. **控制平面(Istio Pilot)**：下发治理规则，不需要修改业务代码。

>优点：业务代码零侵入；多语言微服务统一治理；
>缺点：额外增加网络开销，运维复杂度上升。
>与 API 网关区别：网关管**南北向**（外部→服务）；Service Mesh 管**东西向**（服务间调用），治理更细粒度。

## 9.3 高频协同场景（案例答题话术）
- **Mesh + Sentinel**：Istio Sidecar 接管通信（非侵入），Sentinel 做精细化熔断降级配置（如失败率>50% 触发熔断）；
- **Mesh + SkyWalking/Jaeger**：Sidecar 自动采集链路数据，无需业务埋点，实现全链路可视化定位故障节点。

# 10、Serverless无服务器架构
特点：无需管理服务器，按实际资源消耗计费；平台自动弹性扩缩。
优点：运维成本低、自动弹性；缺点：冷启动延迟，运行环境受限；
适用场景：事件驱动、定时任务、短生命周期接口；**不适合长连接、高延迟敏感业务**。

---

# 11、Web高可用基础架构
- **反向代理(Nginx)**：客户端统一入口，隐藏后端服务器；
- **负载均衡**：轮询、加权轮询、最小连接数，分发流量；
- **CDN**：静态资源就近访问，降低源站压力；
- **动静分离**：静态资源交给CDN，后端只处理动态请求；
- **会话共享方案**：Redis存储Session，禁止会话绑定单台服务器（保证无状态）。

# 13、案例答题万能框架
## 场景A：单体系统改造为微服务，问改造步骤
1. 需求分析，业务域识别；
2. 基于DDD限界上下文拆分微服务，划分服务边界；
3. 搭建基础设施：注册中心、配置中心、API网关；
4. 数据库拆分，每个微服务独立库；
5. 增量迁移，绞杀者模式逐步替换单体；
6. 建设服务治理、监控告警、链路追踪体系；
7. 容器化，云原生改造，CI/CD流水线。

## 场景B：系统出现雪崩/稳定性差，请给出对策
1. API网关增加限流；
2. 微服务引入熔断、降级、超时重试策略；
3. 增加监控告警与链路追踪；
4. 优化分布式事务方案，减少长同步调用；
5. 异步解耦，消息队列削峰填谷。

## 场景C：云原生改造方案设计答题模板
1. **容器化**：Docker打包应用，解决环境不一致；
2. **编排调度**：部署K8s集群，实现自动扩缩容、故障自愈；
3. **无状态改造**：会话、配置外置，禁止本地存储；
4. **配置分离**：配置放到ConfigMap，环境变量注入；
5. **服务治理**：网关 + 注册中心；复杂场景引入Service‑Mesh；
6. **可观测建设**：日志、指标、链路追踪三支柱；
7. **CI/CD流水线**，实现自动化发布回滚。

# 14、中间件与消息队列
| 中间件 | 角色 | 案例题考点 |
|--------|------|-----------|
| **RocketMQ / Kafka** | 异步解耦、削峰填谷、日志采集 | 事务消息保证最终一致；Kafka 分区/副本/Consumer Group |
| **Redis** | 缓存热点、分布式锁、限流计数 | 与消息队列配合做库存原子扣减（Lua 脚本） |
| **Elasticsearch** | 日志/全文检索 | 配合 ELK(EFK) 做日志实时查询 |
| **ShardingSphere / MyCat** | 分库分表中间件 | 水平分片、读写分离 |

# 15、高并发 Web / 云原生架构设计模式（综合考法）
| 模式/技术 | 作用 |
|-----------|------|
| **负载均衡（Nginx/SLB）** | 分发流量到多实例，提升吞吐 |
| **CDN + 边缘计算** | 静态资源就近缓存，降低回源延迟 |
| **动静分离** | 动态请求走应用，静态资源走 CDN/对象存储 |
| **无状态设计** | 服务不存本地状态，Session 外置 Redis，便于水平扩展 |
| **Session 共享** | Redis 集中存储 Session |
| **多级缓存** | 本地缓存 + Redis + CDN，防缓存雪崩 |
| **限流熔断 + 降级** | 网关/Sentinel/Mesh 多层防护，保核心链路 |
| **读写分离 / CQRS** | 读多写少场景优化，命令与查询分离 |
