# 1、微服务架构
## 1.1 定义
微服务是一种架构风格，将**单体大应用拆分为一组小型自治服务**，每个服务围绕单一业务能力构建、可独立部署，服务之间通过轻量通信机制协作。

## 1.2 微服务六大核心特征（案例踩分关键词）
1. **单一职责**：一个服务只负责一块业务能力；
2. **独立部署**：服务互不依赖，可以单独上线、回滚，不影响其他服务；
3. **去中心化治理**：每个服务可自主选择开发语言、技术栈；
4. **去中心化数据管理**：**一服务一数据库**，禁止共享数据库；
5. **轻量级通信**：REST‑HTTP、gRPC、消息队列（Kafka/RabbitMQ）；
6. **面向失败设计**：天然考虑远程调用失败，使用熔断、降级、超时、重试。

## 1.3 微服务优点
- 模块解耦，独立迭代，发布速度快；
- 技术栈异构；
- 故障隔离，局部故障不会拖垮整个系统；
- 便于弹性伸缩，高并发场景资源利用率高；
- 适合大团队并行开发。

## 1.4 微服务缺点（案例高频：分析系统存在问题）
- **分布式复杂度上升**：网络延迟、丢包、调用失败；
- 分布式事务、数据一致性难题；
- 运维复杂度暴涨，大量实例需要监控管理；
- 服务依赖关系复杂，出现调用雪崩风险；
- 开发调试难度增加；
- 需要配套完整服务治理基础设施。

## 1.5 微服务拆分策略
- 按业务域拆分；
- 基于DDD限界上下文拆分；
- 避免循环依赖；
- 粒度适中，不要过细造成"纳米服务"。

# 2、SOA / ESB 企业服务总线（集成架构）
## 2.1 SOA面向服务架构
SOA是一种组件模型，将应用功能封装成可互操作的服务，通过网络进行调用，实现业务复用与系统集成。

## 2.2 ESB企业服务总线
ESB是SOA架构中的**中间件总线**，作为服务请求者和提供者之间的中间层。
### ESB核心功能（案例高频考点）
1. **位置透明性**：服务消费者无需感知服务提供者的物理位置（新增，10文件原缺）；
2. **协议转换**：HTTP、WebService、REST、TCP、JMS之间协议互转；
3. **消息路由**：根据条件/内容转发消息；
4. **数据格式转换**：XML‑JSON、报文等数据格式适配；
5. **消息增强**：补充/校验消息头、安全凭证等；
6. **服务编排**：组合多个服务完成业务流程；
7. **安全、日志审计、监控管理及异常处理**。

### 采用ESB的三方面理由（案例标准答法）
| 维度 | ESB带来的价值 |
|------|--------------|
| 部署方式 | 支持灵活部署结构（C/S、P2P等），总线统一接入 |
| 耦合程度 | 待集成系统只与总线通信，彼此解耦，改一个不影响其他 |
| 可扩展性 | 新增系统以"插件式"接入，仅需适配协议与数据格式 |

## 2.3 SOA vs 微服务（高频对比简答题）

|对比维度|SOA|微服务|
|---|---|---|
|通信中枢|强依赖ESB（智能管道）|哑管道，无重型总线，网关轻量化|
|服务粒度|粗粒度服务|细粒度业务服务|
|数据库|常出现共享数据库|每个服务独立数据库|
|治理模式|集中治理|去中心化治理|
|部署模式|集中部署|每个服务独立部署|
|适用场景|遗留系统集成、大型企业异构系统打通|互联网业务、快速迭代高并发业务|

>答题话术：从SOA演进到微服务，通常需要**去掉重型ESB，换成轻量API网关**。

# 3、API网关
## 3.1 作用
所有客户端请求统一入口，**反向路由**，屏蔽后端微服务地址。

## 3.2 核心功能（简答题背诵）
1. 请求路由；
2. 负载均衡；
3. 认证授权、安全校验；
4. 限流熔断；
5. 请求日志、监控；
6. 协议转换；
7. 灰度发布；
8. 缓存。

>网关和ESB区别：API网关侧重**南北流量（客户端→后端）**；ESB侧重**东西流量（服务‑服务之间集成）**。

## 3.3 统一身份认证与权限控制设计（案例高频）
- **认证**：OAuth2 / OpenID Connect 统一认证，网关颁发/校验 Access Token（JWT）；
- **权限**：微服务内部用 **RBAC**（基于角色）鉴权，敏感场景叠加 **ABAC**（基于属性：组织/标签/状态）；
- **Token传递**：客户端登录获 JWT → 网关校验后转发认证信息 → 各服务解析 JWT 实现**无状态验证**。

## 3.4 网关层高可用与性能优化（针对高频接口）
- 网关层限流（令牌桶/漏桶），按 IP/用户等级限流；
- CDN 边缘缓存静态资源/文件下载；大文件分片上传/断点续传；
- 异步处理 + 任务队列解耦；文件处理服务独立部署、水平扩展。

## 3.5 网关限流算法对比（案例深挖踩分点）
案例题常追问"为什么选令牌桶而不是漏桶 / 计数器有什么问题"，需能展开对比：

| 算法 | 核心机制 | 优点 | 缺点 | 适用 |
|------|---------|------|------|------|
| **计数器（固定窗口）** | 单位时间计数，超阈值拒绝 | 实现简单 | 窗口临界**突发翻倍**（如 1s 末+1s 初各打满）、不平滑 | 粗粒度限流 |
| **漏桶（Leaky Bucket）** | 请求入桶，恒定速率出水（处理） | 速率**绝对平滑**，保护后端 | 无突发能力，突发请求被排队/丢弃 | 需严格恒定速率 |
| **令牌桶（Token Bucket）** | 恒定速率生成令牌入桶，桶有容量，请求取令牌 | **允许一定程度突发**（桶内积攒的令牌），最常用 | 实现稍复杂 | 互联网网关默认 |

> 💡 **答题话术**：网关默认用令牌桶——既能平滑限流，又允许合理突发（桶容量内）；漏桶适合必须恒定速率的场景；计数器仅用于粗粒度，因窗口临界会突发翻倍，不适合精确限流。

# 3b、网关 / ESB / Service Mesh 三者分工（统一背诵版）
- **API 网关**：管**南北流量**（客户端 ↔ 后端服务）——对外暴露、认证、限流、路由入口；
- **ESB**：遗留 SOA 时代管**东西流量**的**重型集中总线**（协议/数据转换、服务编排）；
- **Service Mesh（Istio‑Sidecar）**：新一代微服务**东西流量**治理，**非侵入式**精细化治理（熔断/路由/mTLS/链路）。
> Mesh **不替代**网关：网关负责对外入口（认证/限流），Mesh 负责内部服务间流量治理；两者"南北+东西"互补，常协同部署。

# 4、微服务完整治理体系（案例大题高频）
微服务治理 = 注册中心 + 配置中心 + 熔断限流容错 + 链路追踪 + 监控告警

1. **注册中心（Nacos/Eureka/Consul）**：服务注册、服务发现，解决服务实例地址动态变化；
2. **配置中心**：将配置文件从代码剥离，集中管理，动态更新配置，无需重启服务；
3. **容错组件（Sentinel、Hystrix）**
    - **熔断**：当下游失败率到达阈值，直接快速失败，防止雪崩；
    - **降级**：故障时返回兜底结果，牺牲非核心功能保障核心链路；
    - **限流**：限制请求QPS，保护服务不被打垮；
    - **超时、重试**；
4. **可观测性三支柱（必背）**
    - **指标(Metrics)**：CPU、内存、QPS、响应延迟；
    - **日志(Logging)**：业务日志；
    - **链路追踪(Tracing)**：Jaeger、SkyWalking，追踪一条请求经过的所有微服务调用链，定位性能瓶颈。

# 5、分布式系统核心难题
## 5.1 CAP理论
- **C一致性**：所有节点同一时刻看到相同数据；
- **A可用性**：每个请求都收到响应；
- **P分区容错性**：网络分区故障，系统仍然可以运行；
> **严谨表述（考试踩分）**：网络分区（P）是客观存在的**客观风险**，并非"任何时候只能三选二"；只有**当分区真正发生时**，才需要在 C 与 A 之间做权衡。P 必须被满足（分布式系统跨越网络，分区不可避免），所以平时常说"CAP 三选二"实际指"发生分区时选 CP 还是 AP"。
> **CP vs AP 选型**：
> - 支付/金融 → **CP**（保数据一致，如 ZooKeeper）：在网络分区时牺牲可用性，保证数据强一致；
> - 社交/电商读多 → **AP**（保服务可用，如 Eureka）：放弃强一致，优先保证服务可用。
> 💡 **标准答题话术**："网络分区客观存在，发生分区时需 CP/AP 权衡；互联网业务优先保可用选 AP（Eureka 放弃强一致优先可用性）；金融核心优先保一致选 CP（ZooKeeper 在网络分区时牺牲可用性保证数据一致）。"

## 5.2 BASE理论（最终一致性）
- 基本可用（BA）+ 软状态（S）+ 最终一致性（E）；互联网微服务系统大多采用BASE，放弃强一致，换取高可用。

## 5.3 分布式事务常见方案
1. **2PC 两阶段提交**：协调者发 prepare → 参与者投票 → commit/rollback；强一致、短事务，跨库转账；同步阻塞、性能差，适合低并发；
2. **TCC**：Try‑Confirm‑Cancel；业务侵入性高，需业务层三阶段（预留资源→确认→取消），如支付；
3. **Saga模式**：长事务拆分为本地事务链 + 补偿动作，微服务最常用；**长流程、跨服务**（订单→库存→支付），2025 真题考点；
4. **本地消息表**：本地事务与消息表同库写入 → 异步投递 → 下游消费，最终一致性、解耦；
5. **事务消息（RocketMQ）**：消息中间件保证"消息可靠投递 + 本地事务"的原子性，如订单创建与库存扣减；
6. **Seata**：阿里开源分布式事务框架，支持 AT/TCC/Saga，一站式解决方案。

> 💡 **案例题答题要点**：优先判断业务是"强一致（CP）"还是"最终一致（AP）"；互联网高并发场景多用**最终一致性 + 消息队列 + 补偿/对账**。

### 5.3.1 Saga 两种实现模式对比（2025 真题高频踩分点，必背）
Saga 不仅是"本地事务链+补偿"，其**实现模式**是简答题明确考点（如"跨单元转账"隐藏踩分点）：

| 模式 | 核心机制 | 优点 | 缺点 | 适用场景 |
|------|---------|------|------|---------|
| **协作式（Choreography / 协同）** | 无中心协调器；各服务监听/触发**领域事件**，互相驱动下一步 | 耦合低、去中心、易扩展简单流程 | 流程分散、状态不可见、补偿顺序难控 | 简单短 Saga（步骤少、无复杂补偿） |
| **编排式（Orchestration / 协调）** | 中央**Saga 协调器**（状态机）主动发命令、集中控制流程 | **状态可见、补偿顺序可控、强制幂等**、易监控 | 协调器可能成中心节点（需高可用） | 步骤多、需补偿的复杂长流程（支付/订单/转账） |

> 💡 **答题话术**：支付/银行转账等复杂长流程**推荐编排式**——协调器（状态机）集中控制，状态可见、补偿顺序可控、强制幂等，便于排障与对账；简单事件驱动流程可用协作式降低中心依赖。
> 银行"跨单元转账"模拟题应点明采用**编排式 Saga**（事件表+消息队列为协作式表现，真正的复杂版是协调器驱动），并强调"事件表与业务表在**同一本地事务**提交"是 RPO=0 的根本保证，而非依赖 MQ 可靠性。

## 5.4 分布式数据方案
- **分库分表**：水平分片（按用户 ID 哈希），中间件 ShardingSphere / MyCat；
- **读写分离**：主库写、从库读，降低主库压力；
- **数据一致性**：缓存与数据库一致性（Cache Aside + 延迟双删 / Canal 订阅 binlog）；
- **分布式锁**：Redis `SET NX PX` + 防误删 + 看门狗续期。
  > ⚠️ **生产级可靠锁**：Redisson 等成熟客户端提供**自动看门狗续期 + Lua 原子释放**，避免"业务未执行完锁已过期"导致并发写。考试答法：命令级骨架（SET NX PX + 唯一 value 防误删 + 看门狗续期）即可，生产推荐 Redisson。

# 6、云原生架构
云原生四大支柱：**微服务 + 容器(Docker)+ DevOps + 持续交付**

## 6.0 云原生四类设计原则 & 七大架构原则（案例/论文双考，必背）
当题目问"为何采用云原生""改造方案遵循哪些原则/违反哪条原则"，直接用下列原则作答：

### A. 四类设计原则（基础版，论述"为何采用云原生"最规范）
1. **服务化**：微服务拆分、API 化，服务自治独立部署；
2. **弹性**：HPA、无状态、按需扩缩，流量高峰自动扩容；
3. **可观测性**：日志 / 指标 / 链路**三支柱**统一采集；
4. **自动化**：CI/CD、IaC、自动恢复（故障自愈）。

### B. 七大架构设计原则（新版官方教材高频，选择题+案例辨析踩分点）
> 口诀：**服弹可观韧，自动零演进**
1. **服务化原则**：微服务拆分、API 化；
2. **弹性原则**：按需扩缩、无状态、故障自愈；
3. **可观测原则**：Metrics/Logs/Traces 三支柱；
4. **韧性原则**（容错）：熔断、降级、故障隔离——即"雪崩防护"的顶层原则；
5. **所有过程自动化原则**：CI/CD、自动化运维、IaC；
6. **零信任原则**：安全，不默认内网可信，始终验证（见第 9 章）；
7. **架构持续演进原则**：绞杀者、防腐层渐进迁移（见第 13 章）。

> 三层体系：12‑Factor（应用改造规范）+ 四大/七大原则（架构设计原则）+ K8s/Mesh（落地技术底座）。

## 6.1 12‑Factor 云原生十二要素（案例高频改造踩分点）
>当题目问：如何改造应用适配云原生？尽量覆盖下面要点
1. 基准代码：一份代码库，多部署环境；
2. 依赖：显式声明所有依赖；
3. 配置：配置与代码分离，环境变量保存配置，禁止硬编码；
4. 后端服务：把数据库、消息队列当作附加资源；
5. 构建、发布、运行严格分离；
6. 无状态进程：实例无本地会话数据；
7. 端口绑定：通过端口对外提供服务；
8. 并发：水平扩展，多实例；
9. 可丢弃：进程快速启动、优雅关闭；
10. 开发/生产环境等价；
11. 日志：当作事件流，不存本地；
12. 管理进程：后台任务一次性运行。

>**无状态**：云原生改造最高频关键词，会话、缓存数据不能保存在容器本地。

## 6.2 容灾指标 RPO / RTO（案例论述踩分点）
- **RPO（恢复点目标）**：故障发生时**允许丢失的数据量**（时间维度，如"丢失最近 5 分钟数据"）；
- **RTO（恢复时间目标）**：故障发生后**允许的业务中断时长**（如"恢复<15min"）。
> 关联：金融核心追求 **RPO≈0**（同步复制，如 MySQL Group Replication，事件表与业务表同事务提交）；互联网业务可接受**分钟级 RPO**（异步复制 + 对账补偿）。
> 容灾三阶段：检测（探针/心跳）→ 隔离（熔断/驱逐）→ 恢复（HPA/滚动更新/回滚）。

# 7、Docker容器
- 镜像：只读模板；容器：镜像运行实例；

# 8、Kubernetes（K8s）核心考点
## 8.1 定位：容器编排平台，大规模自动化管理容器集群。
## 8.2 基础概念
1. **Pod**：K8s最小调度单元；一个Pod可以封装1个或多个容器；
2. **Deployment**：无状态应用管理，实现副本扩缩、滚动更新、灰度；
3. **StatefulSet**：有状态应用管理（数据库、Redis 集群、ZooKeeper）——提供**稳定网络标识、有序启动/停止、持久化存储**；对比 Deployment 只适合无状态；
4. **DaemonSet**：保证**每个（或指定）节点运行且只运行一个 Pod**，典型场景：日志采集代理（Filebeat）、监控探针（node‑exporter/Prometheus）；
5. **Service**：一组Pod的统一访问入口，负载均衡；
6. **Ingress**：七层HTTP反向路由；
7. **ConfigMap/Secret**：存放配置、敏感密码；
8. **HPA（水平扩缩）**：增减 Pod **实例数**（加机器），基于 CPU/自定义指标如 QPS 自动扩缩；
9. **VPA（垂直扩缩）**：修改 Pod **内部 CPU/内存资源规格**（不加减实例），对比 HPA 是"换更大机器"而非"加机器"；案例常让 HPA vs VPA 选型对比。

> **StatefulSet vs Deployment 速记**：有状态（数据库/中间件集群）必须 StatefulSet；无状态（Web/微服务）用 Deployment。

## 8.3 K8s探针（独立考点，2025 真题填空/简答高频）
探针是 K8s 实现"检测—隔离—恢复"容灾三阶段的核心机制，必须单列背诵：

| 探针 | 作用 | 失败后果 |
|------|------|---------|
| **liveness 存活探针** | 检测容器进程是否活着 | 失败 → **重启 Pod** |
| **readiness 就绪探针** | 检测容器是否准备好接流量 | 失败 → **摘除流量（不重启）**，从 Service 后端摘除 |
| **startup 启动探针** | 保护慢启动应用，启动阶段不触发 liveness | 失败 → 重启；启动成功后交由 liveness 接管，避免慢启动被误杀 |

> 典型：readiness 失败只摘流量保业务连续；liveness 失败才重启；startupProbe 给慢启动应用更长宽限期。

## 8.4 不可变基础设施（云原生核心概念）
容器镜像一旦构建**不再修改**；任何配置/代码变更都**构建新镜像 + 滚动发布**，禁止登录容器 `exec` 改配置。好处：环境一致、可回溯、杜绝"雪花服务器"、故障可整体替换。

## 8.5 K8s高频场景
- 自动故障自愈，重启异常Pod；
- 滚动升级、不停机发布，保留旧版本支持一键回滚；
- 弹性伸缩应对流量高峰（HPA 基于 CPU/自定义指标如 QPS 扩容，流量结束自动缩容）；
- **Namespace 隔离**：多环境/多租户隔离，如"测试环境数据污染"→ 每 PR 独立 Namespace；
- **探针/自愈**：存活探针（liveness）失败自动重启 Pod，就绪探针（readiness）差异化设置，保障流量只进健康实例（详见 8.3）。

> 🎯 **K8s / Service Mesh / DevOps 三者分工一句话记忆**：**K8s 管"生死扩缩容"（资源层），Service Mesh 管"调用与可靠"（通信层），DevOps 流水线管"快上快回滚"（交付层）**。案例高频论述题标准答法。

# 9、Service Mesh 服务网格（2025‑2026新增热点）
## 9.1 核心定义
一种**非侵入式**的微服务治理方案，将流量治理逻辑从业务代码剥离出来，放到Sidecar代理进程。
## 9.2 两大平面
1. **数据平面（Sidecar‑Envoy）**：拦截服务之间流量，处理限流、熔断、mTLS加密、链路追踪；
2. **控制平面(Istio Pilot)**：下发治理规则，不需要修改业务代码。

>优点：业务代码零侵入；多语言微服务统一治理；
>缺点：额外增加网络开销，运维复杂度上升。
>与 API 网关区别：网关管**南北向**（外部→服务）；Service Mesh 管**东西向**（服务间调用），治理更细粒度。
> **Mesh 能否替代网关？** 不能。网关负责**对外暴露、认证、限流入口**；Mesh 负责**内部服务间流量治理**。两者"南北+东西"互补，常协同部署（网关入口 + Mesh 内部治理）。

## 9.3 高频协同场景（案例答题话术）
- **Mesh + Sentinel**：Istio Sidecar 接管通信（非侵入），Sentinel 做精细化熔断降级配置（如失败率>50% 触发熔断）；
- **Mesh + SkyWalking/Jaeger**：Sidecar 自动采集链路数据，无需业务埋点，实现全链路可视化定位故障节点；
- **Mesh + OAuth2 Proxy / 零信任认证**：Sidecar 或入口网关集成 OAuth2 Proxy / mTLS 实现服务间**零信任认证**（见 9.4）。

## 9.4 微服务 / 分布式安全架构（案例高频小问，云原生必背）
案例题常附带安全治理小问，需掌握：
1. **零信任架构（Zero Trust）**：永不信任、始终验证；微服务之间用 **mTLS 双向加密**（Istio Sidecar 自动注入实现），不默认内网可信；
2. **跨服务身份传递**：JWT 令牌透传，服务间身份认证；
3. **最小权限原则**：服务账号 RBAC，K8s **RBAC + 命名空间**权限隔离；
4. **策略引擎 OPA（Open Policy Agent）**：服务网格细粒度访问控制（如"订单服务只允许调支付服务"）；
5. **网关安全边界**：API 网关做统一认证/限流入口，与 Mesh 东西向 mTLS 形成南北+东西双层防护。

# 10、Serverless无服务器架构（论文/案例新热点）
特点：无需管理服务器，按实际资源消耗计费；平台自动弹性扩缩。
优点：运维成本低、自动弹性；缺点：**冷启动延迟**，运行环境受限（运行时/执行时长/并发限制）；
适用场景：事件驱动、定时任务、短生命周期接口、文件处理；
**不适合**：长连接、高延迟敏感、有状态长任务业务。
> 答题话术模板：Serverless 核心是"无服务器管理 + 按量计费 + 自动弹性"；权衡点是冷启动延迟，适用事件驱动/短时任务，不适长连接。

# 12、DDD领域驱动设计‑微服务拆分（近年权重显著提升，微服务拆分标准答案）
- 领域、子域、**限界上下文（Bounded Context）**：微服务的拆分边界 ≈ 限界上下文边界；限界上下文定义模型的有效范围，避免"大泥球"模型；
- 聚合根：聚合的唯一访问入口，外部只能通过聚合根操作；
- 防腐层（ACL）：新旧系统迁移中隔离遗留系统脏模型（见 13.1），防止污染新微服务领域模型；
- 实体 / 值对象 / 领域服务 / 领域事件：支撑领域建模。
> 💡 **考点权重**：DDD 已是微服务拆分和架构设计的"标准答案"；答题时"按业务域+限界上下文拆分"比"按技术层拆分"更规范，常与模拟题/真题联动。

# 13、案例答题万能框架
## 场景A：单体系统改造为微服务，问改造步骤
1. 需求分析，业务域识别；
2. 基于DDD限界上下文拆分微服务，划分服务边界；
3. 搭建基础设施：注册中心、配置中心、API网关；
4. 数据库拆分，每个微服务独立库；
5. 增量迁移，绞杀者模式逐步替换单体；
6. 建设服务治理、监控告警、链路追踪体系；
7. 容器化，云原生改造，CI/CD流水线。
> **数据迁移三阶段（单体拆微服务落地细节，案例常考）**：**双写**（新旧库同时写）→ **对账**（校验双写一致性）→ **切读**（读流量从旧库切到新库，再停旧写）。保证迁移零数据丢失、业务不停机。

## 场景A2：遗留系统渐进演化迁移三大模式（独立考点，2024‑2025真题）
> 答题区分口诀：**流量拦截选绞杀者；新旧模型隔离选防腐层；单体内部组件逐步替换选抽象分支。**

| 模式 | 核心含义 | 适用场景 |
|------|---------|---------|
| **绞杀者模式（Strangler Fig）** | 新建微服务，逐步拦截单体流量，最终"绞杀"杀死单体 | 整体渐进替换，保业务连续 |
| **防腐层（ACL‑Anticorruption Layer）** | 新旧系统中间加适配层，隔离遗留系统脏模型，防止污染新领域模型（DDD 配套） | 新旧模型语义不一致、需隔离 |
| **抽象分支模式（Branch‑by‑Abstraction）** | 单体内部先抽抽象接口，旧实现与新微服务实现并存，逐步切换 | 单体内部组件逐步替换，免大停机 |

## 场景B：系统出现雪崩/稳定性差，请给出对策
1. API网关增加限流；
2. 微服务引入熔断、降级、超时重试策略；
3. 增加监控告警与链路追踪；
4. 优化分布式事务方案，减少长同步调用；
5. 异步解耦，消息队列削峰填谷。

## 场景C：云原生改造方案设计答题模板
1. **容器化**：Docker打包应用，解决环境不一致；
2. **编排调度**：部署K8s集群，实现自动扩缩容、故障自愈；
3. **无状态改造**：会话、配置外置，禁止本地存储；
4. **配置分离**：配置放到ConfigMap，环境变量注入；
5. **服务治理**：网关 + 注册中心；复杂场景引入Service‑Mesh；
6. **可观测建设**：日志、指标、链路追踪三支柱；
7. **CI/CD流水线**，实现自动化发布回滚。

## 场景D：灰度/发布策略选型对比（改造迁移大题高频）
| 策略 | 机制 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **滚动发布** | 逐个替换 Pod，不停机 | 资源占用低、无停机 | 版本混合共存一段时间 | 常规升级 |
| **蓝绿发布（红黑）** | 两套完整环境，切流量 | 零停机、回滚快（切回旧环境） | 双倍资源开销 | 关键系统、需秒级回滚 |
| **金丝雀（灰度）** | 小流量切新版本，观察后全量 | 风险最低，可早发现问题 | 需流量路由能力 | 云原生改造首选 |
| **红黑发布** | 类似蓝绿，新（红）起全量接管旧（黑）即下线 | 快速切换、回滚靠旧环境兜底 | 同蓝绿资源翻倍 | 与蓝绿同族 |

> 默认推**金丝雀/渐进式**：风险最低、业务连续，配合 K8s + Mesh 流量切分。

# 14、中间件与消息队列
| 中间件 | 角色 | 案例题考点 |
|--------|------|-----------|
| **RocketMQ / Kafka** | 异步解耦、削峰填谷、日志采集 | 事务消息保证最终一致；Kafka 分区/副本/Consumer Group |
| **Redis** | 缓存热点、分布式锁、限流计数 | 与消息队列配合做库存原子扣减（Lua 脚本） |
| **Elasticsearch** | 日志/全文检索 | 配合 ELK(EFK) 做日志实时查询 |
| **ShardingSphere / MyCat** | 分库分表中间件 | 水平分片、读写分离 |

## 14.1 消息队列可靠性设计（微服务治理 + 分布式事务交叉高频考点，必背三句话）
> 2025 真题"订单与库存偶尔不一致"即此类问题，需能独立成节作答：

1. **消息丢失** → 生产者确认（**publisher confirm**）+ 消息**持久化**（磁盘）+ 消费者**手动 ACK**（处理完才确认，不自动提交）；
2. **重复消费** → 消费端**幂等**：业务**唯一键 + 去重表 / Redis SETNX**，消费前查重；
3. **消息乱序** → 同一**业务键（订单 ID）路由到同一分区/队列**，单分区内 FIFO，保证顺序消费。

> 答题话术（考场可直接默写）：丢失三件套（confirm+持久化+手动ACK）；重复靠幂等（唯一键去重表）；乱序靠同键同分区。

## 14.2 可观测性深化（OpenTelemetry 统一标准，2025‑2026 趋势）
- **OpenTelemetry（OTel）**：统一采集标准，**Collector 同时接收 Metrics/Logs/Traces** 三支柱，取代零散 SDK；
- **eBPF**：无侵入式内核级监控（如 Cilium Hubble 网络观测）；
- **SLO / SLI / Error Budget**：SLI（服务等级指标，如成功率）、SLO（目标值）、错误预算（允许失败额度），用于告警与发布门禁；
- 与 4.4 三支柱关系：OTel 是统一采集层，三支柱是数据形态。

## 14.3 信创与国产化（论述题加分项，安全/自主可控场景必提）
- **国产中间件替代**：东方通 TongWeb / 宝兰德 BES 替代 Tomcat / WebLogic；达梦 DM / 人大金仓 Kingbase 替代 Oracle / MySQL；
- **国密算法**：**SM2**（非对称加密/数字签名，网关认证）、**SM3**（摘要/完整性校验）、**SM4**（对称加密/数据存储）；在网关认证、传输加密、敏感字段加密中使用；
- 答题话术模板："若项目有自主可控要求，XX 组件可选用国产 YY 替代，并采用国密 SMx 算法保障安全合规。"

## 14.4 AI Infra 与云原生融合（2026 新大纲热点）
- **AI Serving 架构**：Triton Inference Server / vLLM / Ollama 在 K8s 中以 Deployment/StatefulSet 部署，GPU 资源声明；
- **GPU 虚拟化与调度**：NVIDIA Device Plugin（暴露 GPU 资源）、**MIG 多实例 GPU**、GPU 共享/分时复用提升利用率；
- **RAG 架构组件**：向量数据库（Milvus / Faiss）选型、Embedding 服务独立部署、语义搜索结果缓存；
- **Agent 编排**：LangChain / LlamaIndex 在微服务中集成（工具调用→后端服务）。
> 命题预测：可能以"设计支持大模型推理的云原生架构"形式出题，既考 K8s 又考 AI 基础设施。

## 14.5 边缘计算与端边云协同（IoT/AI 场景延伸）
- **架构职责**：云端（中心管控/训练/全局决策）、边缘端（近场计算/低时延推理/弱网自治）、终端（数据采集/展示）；
- **框架**：KubeEdge / SuperEdge 等边缘容器编排；
- **设备接入协议**：MQTT / CoAP 在设备接入层角色；
- 协同：边缘 AI 推理 + 云端训练，应对弱网/离线场景（与题型 5 嵌入式/IoT 交叉）。

# 17、质量属性 × 分布式/云原生 绑定 & 一页纸速查清单
## 17.1 质量属性与具体技术绑定（试题一架构评估联动）
题目给出需求，需判断对应质量属性，再把技术对应上：
- **性能/效率**：HPA、缓存多级、CDN、读写分离、MQ 削峰；
- **可用性**：多副本、探针自愈、熔断、蓝绿/金丝雀、RPO/RTO；
- **可修改性/可维护性**：微服务拆分、DDD 限界上下文、配置中心、CI/CD；
- **安全性**：零信任 mTLS、RBAC、国密 SMx、网关认证限流；
- **可伸缩性**：无状态、HPA/VPA、容器化；
- **可观测性**：Metrics/Logs/Traces 三支柱、OpenTelemetry。
