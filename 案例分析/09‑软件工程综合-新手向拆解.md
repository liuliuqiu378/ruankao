# 第 0 章 开考之前：这 25 分是怎么拿的

## 0.1 🧊 先建立总直觉：软件工程到底在管什么？

如果你以前没接触过软件工程，请先把这四件事记住 —— **整门学科就围着它们转**：

想象你要造一栋楼。客户说："我要一栋舒服的房子。"

这句话让人抓狂，因为你没法照着它施工。于是你被迫问出一串问题：

| 你问的问题 | 软件工程里的对应概念 |
|---|---|
| "你到底要几间房、什么功能？会不会中途改主意？" | **需求工程 + 开发模型选择** |
| "咱们怎么盖？先搭架子还是一层层盖？万一塌了怎么办算谁的钱？" | **开发模型 + 风险管理** |
| "房子要抗震几级、隔音多好、几年后好不好改造？" | **质量属性** |
| "多少钱、多少天？干到一半钱花超了、工期拖了，怎么算出来？" | **成本估算 + 挣值分析 EVM** |
| "盖好了怎么把人从旧楼搬进新楼？搬的过程中能停水停电吗？" | **系统切换策略** |
| "咱们这套施工队水平到底算不算专业？能不能一直稳定发挥？" | **CMMI** |

**一句话总结软件工程：它研究的是"如何在需求会变、人会有情绪、工期会拖的前提下，把软件按时、按质、按预算交出去"。**

所以它的考点**天然不是技术深度，而是"规范性"和"权衡能力"**——
这门课的考题几乎不问你"怎么写代码"，只问你"**遇到这种情况，应该走什么流程、选什么方案、做哪些权衡**"。

> 🎁 **给新手的定心丸**：
> 软件工程综合是**全卷最适合零基础逆袭**的方向。
> 因为它**不需要你会写一行代码**，只需要你会"**按流程说话**"。
> 它的判卷逻辑是**关键词给分**：写出"需求基线""变更控制委员会""高内聚低耦合""并行切换"，分就来了。

## 0.2 它在考试里的位置

| 项目 | 说明 |
|---|---|
| 卷面结构 | 全卷 5 道大题：**第 1 题必答 + 后 4 题选 2**，每题约 **25 分**，满分 75 分，**45 分及格** |
| 考试时间 | 综合知识与案例连考 240 分钟；**案例平均每题 18 分钟（审题 3 分钟 + 作答 15 分钟）** |
| 本方向性质 | **选做题之一**，且**是第 1 道必答题（架构评估）的理论底座** |
| 双重价值 | ① 直接作为选做题拿 25 分 ② 必答题的质量属性/ATAM/架构风格全在这里 ③ 论文高频考点 |
| 难度 | 概念多、术语杂，但**每块都不深**，且**套路化程度极高** |

> 💡 **战略结论**：
> 软件工程综合是**必答题的"母题"**。就算你在考场上不打算选它作答，**第 3 章（质量属性与 ATAM）你也必须学会**——因为必答题一定会用到。
> 反过来，**第 6 章 EVM 挣值计算**则是"选做性价比之王"：有公式、有标准答案，背熟就是白送 8~10 分。

## 0.3 判卷的第一法则：这是"找关键词"的考试，不是写作文

**先破除一个误解**：案例分析不是写作文，它更接近**填空 + 简答**。

- 阅卷老师手里有一张**评分要点表**，每个要点 1~2 分，他拿着你的答案**在找关键词**；
- 找到就给分，找不到就不给；**写得多不加分，写得乱反而把关键词埋没了**；
- 所以第一法则：**分条写、每条一个要点、把专业名词写在句首**。

> ❌ 错误示范：我觉得这个项目问题挺多的，需求老是变，开发人员又直接改代码，这样下去肯定要延期，建议还是要规范一点……
>
> ✅ 正确示范：
> 1. **需求失控**：开发人员未经评审直接修改代码，违反了**需求变更控制流程**，导致需求基线失去约束力。
> 2. **缺少影响分析**：变更前未评估对进度、成本、质量与已有测试用例的影响，变更风险不可控。
> 3. **正确做法**：应执行"提交变更申请 → 影响分析 → CCB 审批 → 更新需求基线 → 修改设计/代码/用例 → 测试验证 → 发布"的流程。

**一句话口诀：一条一分，宁可多写三条不同角度的，也不要把一条写三段。**

## 0.4 本方向的 8 种长相（先看脸，再动笔）

**这一步决定生死**：认错题型 = 写满也是 0 分。开考先花 30 秒对号入座。

| 类型 | 题干里的"暗号" | 你该答什么 | 千万别答什么 |
|---|---|---|---|
| **① 开发模型选型** | "需求不明确""分批交付""试点上线""大型高风险""需求稳定变更少" | 瀑布/原型/增量/螺旋/喷泉/V 模型 + **给理由** | ❌ 只写模型名不给理由（理由占一半分） |
| **② 需求工程** | "需求分类""需求获取方法""需求变更""需求跟踪" | 功能/非功能/约束三类；RTM；变更控制七步；CCB | ❌ 把"部署环境""工期预算"归为功能需求 |
| **③ 质量属性与 ATAM** | "响应时间""7×24""宕机""加密""新增功能""敏感点""权衡点""效用树" | 六大质量属性 + 战术 + 四"点" + 场景六要素 | ❌ 把可用性答成性能；把可靠性答成可用性 |
| **④ 架构风格** | "各构件独立处理，通过管道传递""发布-订阅""上层调用下层""独立部署小服务" | 管道-过滤器 / 事件驱动 / 分层 / 微服务 + 优缺点 | ❌ 自创词汇，不用标准术语 |
| **⑤ 风险管理** | "识别到某项风险""给出应对策略""规避/减轻/转移/接受" | 四步 + 四策略 + **针对该风险的具体措施** | ❌ 把"事后应急"当成"事前应对" |
| **⑥ 挣值计算 EVM** | "PV/EV/AC""成本偏差""进度滞后""完工估算 EAC" | 写公式 → 代入 → 判状态 → 给纠偏措施 | ❌ 只写结果不写公式；把 CV/SV 正负号判反 |
| **⑦ 敏捷/DevOps/CMMI** | "Scrum""每日站会""产品待办列表""CI/CD""成熟度等级""标准化流程""量化数据" | 3 角色/3 工件/5 事件；DevOps 三支柱；CMMI 五级关键词 | ❌ 说 Scrum Master 是项目经理；说 DevOps=CI/CD |
| **⑧ UML 建模** | "顺序图/活动图/状态图""include/extend""类之间的关系""部署图" | 各图用途辨析；用例关系方向；六种关系强弱 | ❌ 活动图与状态机图说反；聚合与组合说反 |

## 0.5 万能答题四段式（任何"给出方案/分析"题都能套）

只要题目问"**请分析 / 请给出方案 / 请说明 / 请评价**"，就按这 4 步写，**保证不漏点**：

```
① 判定/定位：该说法(做法)错误 / 该场景本质是XXX问题
② 理由：根据XXX理论(原则)，应为XXX
③ 正确做法/方案：应改为XXX，或应增加XXX流程/机制
④ 代价或补充：但会带来XXX代价，需通过XXX缓解
```

> ⚠️ **最大的丢分点：只写收益不写代价 / 只写结论不写理由。**
> 案例题的评分要点几乎都是"**收益 X 分 + 代价 X 分**"或"**判断 1 分 + 理由 2 分 + 做法 2 分**"。
> **看到"分析""评价""说明"这类词，就必须写两面；看到"判断是否正确"，就必须写三段。**

# 第 1 章 开发模型：选模型的本质是"给不确定性排序"

## 1.1 🧊 先建立直觉：盖房子的四种方式

客户要一栋房子。**不同模型 = 面对"不确定"的不同策略**：

| 做法 | 直觉 | 风险在哪 |
|---|---|---|
| **先出完整图纸，图纸不改，照图施工**（瀑布） | 稳，但**图纸错了就得拆墙** | 客户改主意 = 灾难 |
| **先用泡沫板搭个 1:1 样板间，客户看满意了再真盖**（快速原型） | 客户"说不清想要什么"时最好用 | 泡沫板不能住人，得重来 |
| **先盖主卧+卫生间能住人，再逐步加盖客厅、厨房**（增量） | 早点住进去，边住边盖 | 后面加盖时要动前面的管线 |
| **每盖一层就停下来做一次"安全评估"再决定下一步**（螺旋） | 怕塌的项目用这个 | 评估要花钱花时间 |
| **房子是乐高，模块之间没明显先后，反复迭代**（喷泉） | 面向对象项目 | 不好管理进度 |

> **一句话直觉：选模型，本质是在回答一个问题——"这个项目最大的不确定性是需求、是进度、还是技术风险？"**
> - 最大的不确定性是**需求** → 用**原型**
> - 最大的不确定性是**交付压力** → 用**增量**
> - 最大的不确定性是**技术/整体风险** → 用**螺旋**
> - 什么都不确定、全都稳定 → 用**瀑布**

## 1.2 📖 再讲原理：生命周期与七大模型

### 生命周期的八个阶段（顺序要背）

```
可行性分析 → 需求分析 → 概要设计 → 详细设计 → 编码实现 → 测试 → 部署实施 → 运维维护
```

> 💡 记忆：**可行 → 需求 → 概设 → 详设 → 编码 → 测试 → 部署 → 运维**（"可需概详，编测部运"）
> 案例题常在这一条上做文章："**项目经理要求编码完成后才制定测试计划**" → 错（见 1.6）。

---

### ① 瀑布模型 Waterfall

- **特点**：阶段**串行**，上一阶段完成才进下一阶段；**文档驱动**；每个阶段有里程碑与评审。
- **优点**：流程清晰、职责明确、便于管理与控制、文档完备。
- **缺点**：① 前提苛刻——**需求必须完整、明确、稳定**；② 后期修改代价巨大；③ **用户直到最后才能看到可运行软件**；④ 早期错误到测试阶段才暴露。
- **适用**：需求稳定、变更少、技术成熟的**大型定制项目**（军工、航天、政府定制）。

### ② 快速原型模型 Rapid Prototype

- **做法**：**快速**构造一个可运行的原型（**强调"快"，可以粗糙**）→ 和用户反复确认 → 需求澄清后再正式开发。
- **关键区分**：
  - **抛弃型（探索型）原型**：原型只为澄清需求，确认后**丢弃**，重新正式开发。**案例标准答案默认这个**。
  - **演化型原型**：原型逐步演化为最终产品。
- **适用**：**需求模糊、用户难以一次性说清需求**的项目。
- ⚠️ **不适用**：需求已明确的项目（白搭成本）；大型复杂系统整体（原型做不了那么大的骨架）。

### ③ 增量模型 Incremental

- **做法**：软件被拆分为**多个增量构件**，**分批交付**，每一个增量都交付一部分**可用**功能。
- **关键点（常考）**：**第一个增量通常是核心功能**（即"最值钱、最急需"的那部分），后续增量不断增强。
- **优点**：① 用户**较早**获得可用产品；② 风险分散，单个增量失败影响小；③ 核心功能先上线，优先级高的先受益；④ 人员可分批投入。
- **缺点**：① 需要**开放式的体系结构**（架构必须具备足够灵活性容纳后续增量）；② 增量间接口设计复杂；③ 后期增量可能要求修改前期构件。
  > 🔥 **"要求体系结构必须是开放的"是增量模型的隐藏考点**，很多答案里漏掉这一条。
- **适用**：需求较稳定但**需要分批交付**、有明确优先级、希望尽快见到成果的项目。
- ⚠️ **易混**：增量 = **分批交付完整功能**；迭代 = **反复打磨同一功能**。考试答"分批交付"更稳。

### ④ 螺旋模型 Spiral

- **四个象限（背）**：**制定计划 → 风险分析 → 实施工程 → 客户评估**，每转一圈就是一个迭代。
- **核心特点：强调风险分析**（每个迭代都先做风险分析，需要**风险分析专家**）。
- **优点**：① 支持用户需求的动态变化；② 便于风险管控；③ 用户参与度高可用性强。
- **缺点**：① **需要丰富的风险评估经验和专门知识**，风险分析失误会导致更严重问题；② 迭代次数多，**成本高、周期长**；③ 只适合大型项目。
- **适用**：**大型、复杂、高风险**项目（尤其内部开发的大项目）。

### ⑤ 喷泉模型 Fountain

- **特点**：**迭代** + **无间隙**（各阶段没有明显边界，分析与设计、设计与编码可交叉进行）。
- **关键词**：**面向对象**、以**对象**为驱动、可重复演进。
- **适用**：**面向对象**的软件项目。
- ⚠️ 缺点：需要大量开发人员，不利于项目管理（各阶段重叠，难以严格管理文档与评审）。

### ⑥ V 模型（测试模型）

- **核心思想**：**测试活动与开发阶段一一对应**，**测试计划在编码之前就制定**（测试前移）。
- **四条对应关系（必背，年年考）**：

| 测试级别 | 对应开发阶段 | 验证什么 |
|---|---|---|
| **单元测试** | **详细设计** | 单个模块/函数的逻辑是否正确 |
| **集成测试** | **概要设计** | 模块之间的接口与调用 |
| **系统测试** | **需求分析** | 整个系统是否满足需求规格 |
| **验收测试** | **用户需求** | 是否满足用户真实业务需要 |

> 💡 记忆：**"单详、集概、系需、验用"**（谐音："单详即改，细虚沿用"）。
> 更好的记法：从下往上，**越往上越贴近用户**——单元测试最底层只管代码细节，验收测试最顶层只管用户满不满意。

### ⑦ 补充两个"隐藏模型"（考试遇到过，教材里有）

| 模型 | 关键点 | 一句话 |
|---|---|---|
| **构件组装模型（CBSD）** | 用**可复用构件**组装系统，含构件库、构件获取/评价/组装 | "买现成零件拼装"；提升**复用性**与开发效率 |
| **统一过程 RUP** | **用例驱动、以架构为中心、迭代与增量**；四阶段：**初始 → 细化 → 构建 → 移交** | "按阶段打磨骨架"；**每个阶段都是一个完整的小瀑布** |

> RUP 的三个特点（**"用例驱动、以架构为中心、迭代增量"**）是经典填空三连，记住这 12 个字即可。
> 敏捷/演化模型见第 7 章。

## 1.3 一张选型决策树（考场上在草稿纸上默这个）

```
Q1. 需求是否【完整、明确、稳定、变更少】？
    ├─ 是 → 瀑布模型（大型定制/军工/政府项目）
    └─ 否 → 进入 Q2

Q2. 不确定的是【需求本身】（用户说不清要什么）？
    ├─ 是 → 快速原型模型（先做样品确认）
    └─ 否 → 进入 Q3

Q3. 是否需要【分批交付 / 试点上线 / 尽快见到成果】？
    ├─ 是 → 增量模型（或增量 + 原型）
    └─ 否 → 进入 Q4

Q4. 项目是否【大型、复杂、高风险】（技术不确定/集成多）？
    ├─ 是 → 螺旋模型（强调风险分析）
    └─ 否 → 回归瀑布或增量

补充触发词：
  "面向对象、各阶段无边界、反复迭代"   → 喷泉模型
  "测试计划提前、测试与开发阶段对应"   → V 模型
  "用可复用构件组装、有构件库"         → 构件组装模型
  "用例驱动、以架构为中心、四阶段"     → RUP
  "需求频繁变更、小团队、快速交付"     → 敏捷/Scrum（见第 7 章）
```

> 💡 **答题口诀（背）**：
> **需求稳定选瀑布；需求模糊用原型；分批交付选增量；高风险项目螺旋模型；面向对象喷泉模型；测试前置 V 模型。**
>
> 🔥 **救场金句（实在判断不出模型时用，几乎不会扣分）**：
> "考虑到本项目同时存在需求不确定与交付压力，建议采用**混合模型**——**总体上采用增量模型分批交付**，对需求模糊的模块**先用快速原型澄清需求**，对高风险模块**引入螺旋模型的风险分析环节**。"

## 1.4 🎯 怎么考 + ✍️ 怎么答

**最经典的问法（真题改编 1 原题）**：

> **题干**：某公司开发企业办公自动化系统。初期客户能提主要业务流程，但**部分审批流程、表单格式和权限规则不明确**，客户表示**需系统演示后才能确认**。项目经理原计划用瀑布模型，先完成完整需求规格说明书再进入设计编码。执行中客户提新审批流程需求，**开发人员认为简单，未正式评审直接改代码并部署测试环境**。
>
> 【问题 1】（8 分）瀑布模型是否适合？说明理由。
> 【问题 2】（8 分）针对需求不明确，建议采用哪些模型？说明理由。
> 【问题 3】（9 分）开发人员直接改代码是否合适？说明正确变更流程。

**【问题 1】参考答案**：

> **不完全适合（1 分）。**
> **理由**：
> ① 瀑布模型要求项目**需求在前期完整、明确、稳定**（2 分），而本题客户尚有审批流程、表单格式、权限规则不明确，**难以在前期形成准确的需求规格说明书（SRS）**（2 分）；
> ② 瀑布模型**阶段串行、文档驱动**，前期需求若不准确，缺陷将在后期测试阶段才暴露，**后期修改代价巨大**（2 分）；
> ③ 瀑布模型下**用户直到最后才能看到可运行软件**，而本题客户明确表示"需系统演示后才能确认"，瀑布无法满足这一诉求（1 分）。

**【问题 2】参考答案**：

> 建议采用**快速原型模型**与**增量模型**相结合的混合方式：
> ① **快速原型模型**：针对审批流程、表单格式、权限规则不明确的部分，**快速构造可运行原型供客户演示确认**，通过反复迭代澄清需求，待需求明确后再正式开发（对应"客户需系统演示后才能确认"）；
> ② **增量模型**：办公系统功能相对独立（如公文流转、日程、会议、人事），可**按模块分批交付**，使客户较早获得可用功能，风险分散；
> ③ 若项目整体还存在较高技术或集成风险，可在每个增量迭代中**引入螺旋模型的风险分析环节**。

**【问题 3】参考答案**：

> **不合适（1 分）。**
> **理由**：开发人员未经评审直接修改代码并部署，**违反了需求变更控制流程**，使变更未经过影响分析与审批，**需求基线失去约束力，导致需求蔓延与项目失控**（2 分）；同时未经评审的代码变更可能引入新缺陷，并造成设计与代码、测试用例不一致（2 分）。
>
> **正确做法——需求变更控制流程**：
> ① **提交变更申请**：由变更提出方填写书面变更申请单；
> ② **变更影响分析**：评估变更对**范围、进度、成本、质量、架构及其他需求**的影响；
> ③ **CCB（变更控制委员会）审批**：由 CCB 决定是否批准；
> ④ **更新需求基线**：批准后修改需求规格说明书并**更新配置管理基线**；
> ⑤ **同步修改**：相应修改**设计文档、代码与测试用例**；
> ⑥ **测试验证**：执行回归测试，确认变更未引入新缺陷；
> ⑦ **发布并通知干系人**：版本发布，通知所有相关人员。
>
> 此外应通过**需求跟踪矩阵（RTM）**确保变更被设计、编码、测试完整覆盖。

## 1.5 ⚠️ 丢分点

- ❌ **只写模型名不给理由** → 案例里"模型 + 理由"通常各占一半分，理由必须引用题干原话（"因为需求不明确/因为要分批交付"）。
- ❌ **混淆增量与螺旋**：**增量的核心是分批交付**，**螺旋的核心是风险分析**。题干出现"高风险"而答"增量"，必扣分。
- ❌ **混淆增量与原型**：原型解决"**需求说不清**"，增量解决"**想早点拿到东西**"。
- ❌ **认为原型模型可以用原型直接交付** → 标准答案默认**抛弃型原型**（澄清需求后正式开发）。
- ❌ **漏掉增量模型"要求开放的体系结构"** → 这是增量模型的**隐性必答点**。
- ❌ **V 模型对应关系写反** → 背死：**单元↔详细设计，集成↔概要设计，系统↔需求，验收↔用户**。
- ❌ **认为 V 模型就是"编码完成后才开始测试"** → 恰恰相反，V 模型强调**测试计划在编码之前制定**（测试前移）。
- ❌ **答"瀑布适合小项目"** → 标准表述是"**需求明确稳定、变更少的项目**"，大小不是判断标准。

# 第 2 章 需求工程：三分靠写，七分靠管

## 2.1 🧊 先建立直觉：装修前的需求清单

你去装修房子，跟工头说："我要装得舒服点。"

工头立刻追问并记下来：

| 他记下的内容 | 类别 |
|---|---|
| "要有三个卧室、两个卫生间、开放式厨房" | **功能性需求**（要干什么） |
| "隔音要好、甲醛达标、冬天保温" | **非功能性需求**（质量属性：做得怎么样） |
| "只能用 XX 品牌的水管""总预算 30 万""必须在孩子开学前完工" | **约束需求**（外部限制） |

然后工头做三件事：

1. **需求开发**（弄明白要什么）：问你、量房、出效果图（**获取 → 分析 → 写 SRS → 验证**）
2. **需求管理**（防止变来变去）：
   - **需求基线**：签字确认的那一版，**改就要走流程**
   - **变更控制**：你突然想加个衣帽间，工头说"可以，但加钱加工期，您签个字"
   - **需求跟踪矩阵**：一张表，确保你说的每一条**都有对应的设计、施工和验收**

> **一句话直觉：需求工程 = 把"想要什么"变成"白纸黑字"，再用流程锁住它。**

## 2.2 📖 再讲原理（一）：需求的三个来源 —— 三类需求

| 类别 | 含义 | 例子 | 判断技巧 |
|---|---|---|---|
| **功能性需求** | 系统**必须完成的功能**、业务逻辑 | 患者预约号源、医生查看出诊、下单支付 | 能回答"**做什么**" |
| **非功能性需求**（质量属性） | 系统运行的**品质指标** | 支持 10000 并发、响应≤2 秒、数据加密、7×24 可用 | 能回答"**做得怎么样**" |
| **设计约束**（约束需求） | 外部**限制条件**：技术、政策、环境、预算、工期 | 部署在现有私有云、必须兼容 IE、工期≤8 个月、预算 600 万 | 能回答"**被什么限制**" |

> 🔥 **高频分类题的暗号（直接背这张映射表）**：

| 题干表述 | 归哪类 |
|---|---|
| 用户能查询/下单/预约/审批 | **功能** |
| 并发数、响应时间、吞吐量、TPS/QPS | **非功能（性能）** |
| 7×24、宕机、故障恢复时间、双机热备 | **非功能（可用性）** |
| 加密、权限、越权、审计日志、防攻击 | **非功能（安全性）** |
| 界面友好、新手培训时间、操作步骤数 | **非功能（易用性）** |
| 新增功能耗时、移植到其他平台 | **非功能（可修改性/可移植性）** |
| **部署在现有私有云 / 必须使用 XX 数据库** | **约束（环境/技术）** |
| **工期 8 个月 / 预算 600 万 / 符合国家 X 标准** | **约束（进度/成本/法规）** |

> ⚠️ **最大的坑**：**"部署环境""工期""预算""政策法规"属于约束，不属于功能需求，也不属于质量属性。**
> 很多人顺手把"部署在私有云"写成"非功能需求"→ 错。

## 2.3 📖 再讲原理（二）：需求开发的四个步骤

```
需求获取 → 需求分析 → 需求规格说明书(SRS)编写 → 需求验证
```

**① 需求获取的方法（常考列举，答 4 种即可，给 6 种保险）**：

| 方法 | 适用 |
|---|---|
| **用户访谈** | 深度了解，适合关键用户；但耗时 |
| **问卷调查** | 用户多、分布广时批量收集 |
| **现场观察（跟班作业）** | 用户说不清实际怎么做时，观察真实流程 |
| **文档分析（现有资料分析）** | 有旧系统时，从旧系统文档和表单反推 |
| **原型演示（情节串联板）** | **需求模糊**时通过可运行原型确认 |
| **头脑风暴 / 联合需求计划会 JRP** | 多方干系人集中碰撞、快速达成共识 |
| **用例分析** | 从用户使用场景出发导出功能需求 |
| **抽样调查** | 样本量大、无法逐一调研时 |

> 💡 **答题技巧**：题目问"**针对需求不明确，可采用哪些获取方法**" → 优先写**原型演示、用户访谈、现场观察、JRP**（这四个最贴合"说不清"的场景）。

**② 需求分析**：建立**逻辑模型**。
- 面向**结构化分析（SA）**：**数据流图 DFD + 数据字典 + E-R 图 + 状态转换图 + 加工逻辑说明**
- 面向**对象分析（OOA）**：**用例模型 + 领域模型（类图）+ 交互模型（顺序图/状态图）**

**③ 需求规格说明书 SRS**：
- **定义**：需求开发的结果，是**软件开发、测试、验收和项目管理的重要依据**；
- **特点（常考多选/简答）**：**正确性、无二义性、完整性、一致性、可验证性、可修改性、可追溯性**；
- ⚠️ SRS **只描述"做什么"，不描述"怎么做"**（不含设计方案、不含实现细节）。

**④ 需求验证**：以 SRS 为输入，通过**需求评审**（正式评审/技术评审）和**需求测试**（写验收测试计划）确认需求正确；**需用户签字确认**。

## 2.4 📖 再讲原理（三）：需求管理三件套

| 工具 | 是什么 | 作用（踩分句） |
|---|---|---|
| **需求基线** | 经正式评审并**签字确认**的需求规格说明书，此后**变更须走变更控制流程** | 为需求变更提供**基准**，防止需求随意变动 |
| **需求变更控制** | 由 **CCB（变更控制委员会）** 审批变更 | 防止**需求蔓延（Scope Creep）**，控制变更对进度/成本/质量的影响 |
| **需求跟踪矩阵 RTM** | 一张表，建立"**需求 ID ↔ 设计元素 ↔ 代码模块 ↔ 测试用例**"的**双向**追溯关系 | ① **防止需求遗漏**；② 分析**变更影响范围**；③ 验证需求是否被完整实现与测试 |

> 🔥 **RTM 几乎是必考的一个填空/简答**。
> **标准答案句式**：
> "需求跟踪矩阵（RTM）建立了**需求与设计、代码、测试用例之间的双向追溯关系**，能够**验证需求是否被完整覆盖与实现、防止需求遗漏**，并支持**变更影响分析**与**回归测试范围确定**。"

## 2.5 📖 再讲原理（四）：验证 vs 确认 V&V（高频辨析，年年有人写反）

| | **验证 Verification** | **确认 Validation** |
|---|---|---|
| **英文问题** | Are we building the product **right**? | Are we building the **right** product? |
| **中文问题** | 我们**正确地**构建产品了吗？ | 我们构建了**正确的**产品吗？ |
| **关注点** | **符合规范与标准**（与 SRS、设计文档比对） | **满足用户真实业务需要** |
| **典型手段** | **评审、审查、走查、静态分析、单元测试、集成测试、系统测试** | **用户验收测试、α/β测试、原型演示、用户试用** |
| **执行者** | 主要是**开发方内部** | 主要是**用户/客户** |
| **时机** | 贯穿**开发全过程**（每个阶段结束） | 主要在**项目后期/交付时** |

> **口诀：验证看"做对了没"（符合规格），确认看"做对的东西没"（满足业务）。**
> 再简化：**验证 = 对照文档查；确认 = 让用户看。**

## 2.6 🎯 怎么考 + ✍️ 怎么答

**经典问法（真题改编 2 原题）**：

> **题干**：某医院预约挂号系统需求如下：
> ① 患者可通过小程序预约号源；② 医生可查看当日出诊患者；③ 系统应支持 10000 并发用户；
> ④ 页面响应时间不超过 2 秒；⑤ 患者隐私数据需加密存储；⑥ 系统须部署在医院现有私有云；
> ⑦ 系统需保留完整操作日志以备审计；⑧ 项目工期不超过 8 个月。
>
> 【问题 1】（8 分）请将上述需求划分为功能性需求、非功能性需求和设计约束。
> 【问题 2】（8 分）请列举至少 4 种需求获取方法，并说明本项目适合采用的方法。
> 【问题 3】（9 分）项目采用什么工具防止需求遗漏？说明其作用。

**【问题 1】参考答案**：

> - **功能性需求**：① 患者通过小程序预约号源；② 医生查看当日出诊患者。
> - **非功能性需求**：③ 支持 10000 并发（**性能**）；④ 响应时间不超过 2 秒（**性能**）；⑤ 隐私数据加密存储（**安全性**）；⑦ 保留操作日志以备审计（**安全性/合规性**）。
> - **设计约束**：⑥ 部署在医院现有私有云（**环境约束**）；⑧ 工期不超过 8 个月（**进度约束**）。

**【问题 2】参考答案**：

> 需求获取方法包括：**用户访谈、问卷调查、现场观察（跟班作业）、文档分析、原型演示、头脑风暴、联合需求计划会（JRP）、用例分析、抽样调查**（列出 4 种以上即可）。
>
> 本项目为医疗业务系统，业务规则专业且涉及患者、医生、管理员多类角色，建议采用：
> ① **用户访谈**：面向医生与管理员深入了解挂号业务规则与出诊流程；
> ② **现场观察**：观察挂号窗口实际操作流程，发现用户未言明的隐性需求；
> ③ **原型演示**：患者端小程序界面与交互需求较模糊，通过原型让患者直观确认；
> ④ **文档分析**：分析医院现有 HIS 系统的表单与流程文档，复用已有业务规则；
> ⑤ **联合需求计划会（JRP）**：集中患者代表、医生、院方管理者一次性达成共识，减少后续返工。

**【问题 3】参考答案**：

> 应采用**需求跟踪矩阵（RTM）**。
> **作用**：
> ① 建立"**需求 ID ↔ 设计元素 ↔ 代码模块 ↔ 测试用例**"的**双向追溯**关系，确保每条需求都有对应的设计、编码与测试覆盖，**防止需求遗漏**；
> ② 在需求变更时，可**快速分析变更的影响范围**（影响到哪些设计、哪些代码、哪些测试用例），支撑变更决策；
> ③ 在测试阶段可**验证需求的完整实现程度**，并确定回归测试范围；
> ④ 作为**需求验证与验收**的依据，支持确认（Validation）活动。
>
> 同时应配套建立**需求基线**与**变更控制流程（CCB）**，共同防止需求失控。

## 2.7 ⚠️ 丢分点

- ❌ **"部署环境/工期/预算"归类错误** → 它们是**约束**，不是功能，也不是质量属性。
- ❌ **"操作日志审计"归为功能需求** → 它是**非功能性需求（安全性/合规性）**。判断标准：它不是用户主动提出的一个"业务功能"，而是对系统运行的品质要求。
- ❌ **验证与确认写反** → 背英文：`right`（验证=做得对） vs `right product`（确认=做对的东西）。
- ❌ **说"需求验证就是用户验收"** → 用户验收是**确认**；验证主要是**内部评审**。
- ❌ **只答"需求跟踪矩阵"六个字** → 必须写"**双向追溯 + 覆盖设计/编码/测试 + 防止遗漏 + 支持变更影响分析**"，这四个点才是分。
- ❌ **认为需求基线一旦确定就不能改** → 可以改，但**必须走变更控制流程**。
- ❌ **变更流程漏掉"影响分析"或"CCB 审批"** → 这两步是评分表里单独的要点，缺一步扣 1~2 分。

# 第 3 章 质量属性与架构评估 ATAM（全篇最值钱的一章）

> 🔥 **本章是整份文档的重中之重**：
> ① 它是**第 1 题必答题的核心**（几乎每年必考）；
> ② 它是许多"软件工程综合"选做题的第一小问；
> ③ 它是**论文的常用框架**（"某系统的质量属性分析与架构评估"）。
> **如果时间只够学一章，就学这一章。**

## 3.1 🧊 先建立直觉：买房子时你关心的六个指标

你去看一套房子，中介给你一堆参数：

| 参数 | 翻译成质量属性 |
|---|---|
| "通勤 20 分钟到公司，电梯不用等" | **性能**（快不快） |
| "物业 24 小时有人，停电有备用发电机" | **可用性**（能不能一直用） |
| "门禁刷卡、监控全覆盖" | **安全性**（别人进不进得来） |
| "承重墙少，想改格局很容易" | **可修改性**（好不好改） |
| "水电管线都留了检修口" | **可测试性**（好不好验） |
| "户型方正，老人小孩一学就会用" | **易用性**（好不好上手） |

**关键洞察来了**：这六个指标**互相打架**。

- 门禁刷卡、人脸识别搞得越严（**安全性↑**），你进门就越慢（**性能↓**）；
- 为了停电也能住（**可用性↑**），你得买发电机、交双份电费（**成本↑、复杂度↑**）；
- 为了让格局好改（**可修改性↑**），你得少用承重墙、多用隔断，房子就不那么结实安静（**可靠性/性能↓**）。

> **一句话直觉（本章的灵魂）：架构设计没有"最优解"，只有"权衡"。**
> **案例题里 90% 的分数，就在"你能否说出"——这个决策提升了什么、牺牲了什么。"**

## 3.2 📖 再讲原理（一）：六大核心质量属性

> 六大质量属性**全部属于非功能性需求**。

| 质量属性 | 含义 | 典型场景（题干暗号） | 常用战术（优化手段） |
|---|---|---|---|
| **性能 Performance** | 系统**响应速度、吞吐量、延迟** | 页面打开慢、并发高时卡顿、TPS/QPS 不达标 | 并行计算、资源池、缓存、异步队列（削峰填谷）、限流、CDN |
| **可用性 Availability** | 系统**正常运行时间比例**；故障后**恢复速度** | 宕机、需 7×24 运行、MTBF/MTTR、故障快速恢复 | **集群、冗余、故障转移、双机热备、心跳检测、状态镜像、Checkpoint/回滚** |
| **安全性 Security** | 防止**非法访问**；防攻击、数据保密完整 | 黑客、越权、数据泄露、加密、权限、审计 | **认证、授权、审计、加密**；入侵检测、限制暴露 |
| **可修改性 Modifiability**（可维护性） | **快速、低成本**地修改系统、新增功能 | 新增业务功能、平台移植、模块解耦 | **低耦合高内聚、模块化、接口稳定、配置化、中间件解耦、泛化模块** |
| **可测试性 Testability** | 便于开展测试、容易**发现缺陷** | 测试覆盖率、缺陷定位难、需要 Mock | **内置日志、接口 Mock、故障注入、记录/回放、内置监视器** |
| **易用性 Usability** | 用户**上手简单**、操作体验好 | 新手培训时间、操作步骤数、界面友好 | 界面与逻辑分离、用户模型、反馈提示、撤销重做 |

**其他常考质量属性（补充）**：

| 属性 | 含义 | 区分 |
|---|---|---|
| **可靠性 Reliability** | **长时间运行不出错**的能力（不出故障） | 关注"**别出错**"；靠**冗余、容错、故障隔离** |
| **可伸缩性/可扩张性 Scalability** | 通过**增加资源**提升容量（横向/纵向扩展） | 关注"**加机器能不能变强**" |
| **可扩展性 Extensibility** | **新增业务功能**时改动小 | 关注"**加功能是否容易**"（≈可修改性） |
| **可移植性 Portability** | 移植到其他平台/环境的难易 | 与可修改性相近，但强调环境变化 |
| **互操作性 Interoperability** | 与其他系统交换信息、协同工作的能力 | 常与集成架构一起考 |

> 🔥 **最容易丢分的三个辨析（背死）**：

| 辨析 | 结论 |
|---|---|
| **可用性 vs 性能** | **可用性 = 能用多久/停了多久恢复**（宕机、7×24、MTBF）；**性能 = 快不快**（响应、并发、吞吐）。二者**完全独立** |
| **可靠性 vs 可用性** | **可靠性 = 一段时间内不出错的概率**；**可用性 = 一段时间内能工作的概率（含故障后恢复）**。系统可靠但恢复慢 → 可用性仍可能低 |
| **可伸缩性 vs 可扩展性** | **可伸缩性 = 加资源扩容**（Scalability）；**可扩展性 = 加功能改得动**（Extensibility，≈可修改性）。**微服务主要提升可伸缩性与部署独立性** |

## 3.3 📖 再讲原理（二）：质量属性场景六要素（常考填空）

**为什么需要"场景"？** 因为"性能好"是不可验证的废话，**"在 1000 并发下，90% 请求响应时间小于 2 秒"才是需求**。

| 要素 | 含义 | 例子（性能场景） |
|---|---|---|
| **刺激源 Stimulus Source** | **谁**发出的刺激 | 用户 / 外部系统 |
| **刺激 Stimulus** | **发生了什么** | 发起查询请求 |
| **环境 Environment** | 系统处于**什么状态** | 正常模式 / **高峰负载（1000 并发）** |
| **制品 Artifact** | 被刺激的**系统哪一部分** | 查询服务 / 整个系统 |
| **响应 Response** | 系统**如何处理** | 处理请求并返回结果 |
| **响应度量 Response Measure** | 用什么**指标衡量**（必须可量化） | **90% 请求响应时间 < 2 秒；TPS ≥ 500** |

> 🔥 **最大丢分点：漏掉"响应度量"或写得不可量化。**
> **"响应快"不是响应度量，"响应时间 < 2 秒"才是。** 场景描述题里，这一项通常单独占 1~2 分。

## 3.4 📖 再讲原理（三）：质量属性战术 Tactics（"给出优化方案"万能答案库）

**战术 = 为了达到某个质量属性而采取的具体架构手段。**
题干问"**如何提升 XX 属性**"，就从这里取弹药。

### 性能战术（三大方向）

| 方向 | 手段 | 例子 |
|---|---|---|
| **资源需求**（少干活） | 减少要处理的事件、降低计算开销、**限制执行时间**、限制队列长度 | 算法优化、压缩传输、限流 |
| **资源管理**（多干活） | **引入并发**、**增加可用资源**、**维持多份副本（缓存）** | 线程池、多实例、Redis 缓存、CDN |
| **资源仲裁**（排好队） | 优先级调度（FIFO / 固定优先级 / 动态优先级 / 静态调度） | 核心业务优先、VIP 通道 |

> **答题简化版（写这几条就够）**：**缓存、资源池（线程/连接池）、并行计算、异步化（消息队列削峰填谷）、限流降级、读写分离、CDN**。

### 可用性战术（三大方向）

| 方向 | 手段 |
|---|---|
| **错误检测** | **心跳检测、Ping/Echo、异常监测** |
| **错误恢复** | **主动冗余（双活）、被动冗余（主备）、备件、检查点/回滚（Checkpoint/Rollback）、状态重新同步** |
| **错误预防** | **移除服务（重启）、事务、进程监视器** |

### 安全性战术（三大方向）

| 方向 | 手段 |
|---|---|
| **抵抗攻击** | **认证 Authentication（你是谁）、授权 Authorization（你能干啥）、加密 Encryption、完整性校验、限制暴露、限制访问** |
| **检测攻击** | 入侵检测系统 IDS、日志分析、异常行为监测 |
| **从攻击中恢复** | **恢复状态（冗余/备份）、审计追踪 Audit、识别攻击者** |

> **答题简化版（"4A"口诀）**：**认证 Authentication、授权 Authorization、审计 Audit、加密 Encryption**。

### 可修改性战术（三大方向）

| 方向 | 手段 |
|---|---|
| **局部化变更** | **高内聚低耦合、泛化模块（参数化）、限制选择、维持语义一致性** |
| **防止连锁反应** | **信息隐藏、维持现有接口、限制通信路径、使用中介（适配器/中间件/外观）、命名服务** |
| **推迟绑定时间** | **配置文件、运行时注册、多态、组件更换、遵守已定义协议** |

### 可测试性战术

- **管理输入输出**：**记录/回放、将接口与实现分离、特化访问接口（预留测试接口）**
- **内部监视**：**内置监视器、断言、日志、故障注入**

> 💡 **万能答题句式（任何"给出优化方案"都能套）**：
> "为提升系统**〔某质量属性〕**，可采用以下战术：①〔战术1〕；②〔战术2〕；③〔战术3〕。
> 该方案通过引入**〔X 机制〕**提升了**〔Y 属性〕**，但由于增加了**〔Z 开销，如网络 IO / 加解密 CPU 消耗〕**，导致**〔T 属性〕**下降。这属于典型的**敏感点与权衡点**，需要进行权衡。"

## 3.5 📖 再讲原理（四）：架构评估方法 ATAM / SAAM

### 两种方法的定位

| 方法 | 全称 | 评估重点 | 考试地位 |
|---|---|---|---|
| **SAAM** | 软件架构分析方法 | **最早**的方法，主要评估**可修改性、可扩充性**；也可用于**比较多个架构方案** | 基础，考得少 |
| **ATAM** | **架构权衡分析方法** | 在 SAAM 基础上发展，**关注多个质量属性之间的权衡** | ⭐ **最常考，几乎每年** |

### ATAM 的四个阶段 / 九个步骤

**考试简化版（4 步，够用）**：
1. **场景收集**（生成**质量属性效用树 Utility Tree**）
2. **架构介绍**（架构师描述架构与所采用的架构方法）
3. **场景分析**（识别**敏感点、权衡点、风险点、非风险点**）
4. **结果呈现**（输出评估报告）

**完整版（9 步，论文/高分答案用）**：

```
1. 描述 ATAM 方法        2. 描述业务动机        3. 描述架构
4. 确定架构方法          5. 生成质量属性效用树   6. 分析架构方法
7. 讨论与分级场景        8. 再次分析架构方法     9. 描述评估结果
```

### 🔥 四大核心概念（**必考，年年出**）

| 概念 | 定义 | 例子 |
|---|---|---|
| **敏感点 Sensitivity Point** | 影响**某一个**质量属性的架构决策（或构件特性） | "**服务器数量**"影响**性能**（只影响性能） |
| **权衡点 Tradeoff Point** | 影响**多个**质量属性的架构决策，且**影响方向不一致（有得有失）** | "**加密级别**"同时影响安全性↑与性能↓ → 权衡点 |
| **风险点 Risk Point** | **可能**导致负面后果的架构决策（潜在隐患） | 数据库**单点故障（SPOF）**、未做冗余 |
| **非风险点 Non-Risk Point** | 经分析**被确认为良好**、不会带来风险的架构决策 | 已做双机热备的应用服务器 |

> 🔥 **最大的丢分点：敏感点 vs 权衡点分不清。**
> **判断标准只有一句：看它影响了几个质量属性。**
> - **影响 1 个** → 敏感点
> - **影响 ≥2 个（且此消彼长）** → 权衡点
>
> **口诀：敏感"一点"，权衡"多点"。所有权衡点都是敏感点，但敏感点不一定是权衡点。**

### 质量属性效用树 Utility Tree

```
效用（Utility）
├── 性能
│   └── 响应时间
│       └── (H,M) 1000 并发下，90% 请求响应时间 < 2 秒
├── 可用性
│   └── 故障恢复
│       └── (H,H) 主库宕机后 30 秒内自动切换到备库
├── 安全性
│   └── 数据保密
│       └── (M,L) 敏感字段加密存储，密钥由 KMS 统一管理
└── 可修改性
    └── 新增业务
        └── (H,M) 新增一种支付方式的工作量 ≤ 10 人日
```

> 三个层级：**质量属性 → 质量属性细分（属性求精）→ 具体场景**。
> 括号里的两个字母是**优先级**：第一个 = **场景对系统成功的重要性**（H/M/L），第二个 = **实现该场景的难易程度**（H/M/L）。
> 常考填空：**(重要性, 难易度)**，写反会扣分。

## 3.6 🎯 怎么考 + ✍️ 怎么答

**最经典的三连问（必答题 / 选做题第一小问的标准长相）**：

> 【问题 1】（6 分）请指出题干中"XXX"属于哪种质量属性，并说明判断依据。
> 【问题 2】（9 分）架构师为提升安全性对传输数据加密，请分析该决策对哪些质量属性产生影响，指出**敏感点**与**权衡点**。
> 【问题 3】（10 分）请给出提升〔某属性〕的具体架构战术，并说明其带来的代价。

**【问题 1】答题模板**：

> 该场景属于**〔质量属性〕**。
> **判断依据**：题干中"〔引用原话，如'要求 7×24 小时不间断运行'〕"，关注的是系统**〔该属性的本质，如'持续提供服务的能力'〕**，符合**〔属性名〕**的定义。
> ⚠️ 注意：**〔辨析对象，如'可用性'〕**关注的是"能否持续可用"，与**〔易混属性，如'性能'〕**关注的"响应快慢"是**相互独立的质量属性**，不应混淆。

**【问题 2】答题模板（权衡分析）**：

> ① **识别影响的属性**：该决策（对传输数据加密）主要影响**安全性**与**性能**两个质量属性。
> ② **判断敏感点**："**加密强度**"这一参数的变化会显著影响**安全性**与**性能**，因此它是一个**敏感点**。
> ③ **判断权衡点**：提高加密强度会**提升安全性**，但同时增加**加解密的 CPU 开销与处理延迟**，导致**性能下降**，即该决策**同时影响多个质量属性且影响方向不一致**，因此"**加密强度（或加密级别）**"是一个**权衡点**。
> ④ **权衡结论**：应在安全性与性能之间权衡，例如**仅对敏感字段加密 / 采用硬件加速的对称加密（AES）/ 对高敏感数据用非对称加密交换密钥、用对称加密传输数据（数字信封）**，以兼顾两者。

**【问题 3】答题模板（优化方案）**：

> 为提升系统**〔属性〕**，建议采用以下战术：
> ① 〔战术 1 + 如何做〕；
> ② 〔战术 2 + 如何做〕；
> ③ 〔战术 3 + 如何做〕。
> **代价**：该方案会引入**〔X 开销/复杂度/成本〕**，导致**〔某属性〕**下降（或成本上升），需要权衡。

## 3.7 ⚠️ 丢分点（本章最多，重点看）

- ❌ **把可用性当成性能** → 7×24、宕机、故障恢复 = 可用性；响应、并发、吞吐 = 性能。
- ❌ **把可靠性等同于可用性** → 可靠性=**不出错**，可用性=**能用（含恢复）**。
- ❌ **敏感点与权衡点判定错误** → 记死"**影响 1 个 = 敏感点，影响多个 = 权衡点**"。
- ❌ **只写"这是权衡点"不写"为什么"** → 必须写"**同时影响 A 与 B，A 提升、B 下降，方向不一致**"。
- ❌ **场景六要素漏掉"响应度量"或写得不含数字** → 必须可量化（"< 2 秒""≤ 5 分钟"）。
- ❌ **效用树优先级 (重要性, 难易度) 顺序写反**。
- ❌ **把 ATAM 说成"只评估可修改性"** → 那是 **SAAM**；ATAM 评估**多质量属性的权衡**。
- ❌ **认为风险点 = 已经发生的问题** → 风险点是**尚未发生但可能导致问题的架构决策**（潜在隐患）。
- ❌ **给出优化方案时不写代价** → 案例题"收益 + 代价"各占一半分。
- ❌ **说"微服务提升了可扩展性"** → 精准表述：微服务提升的是**可伸缩性（Scalability）与部署独立性**；新增业务功能容易与否是**可修改性/可扩展性（Extensibility）**，两者不同。

# 第 4 章 架构风格：五种"厨房布局"

## 4.1 🧊 先建立直觉：餐厅后厨怎么布局？

开一家餐厅，后厨怎么安排，直接决定出餐效率和改菜单的难度：

| 布局 | 做法 | 像什么架构风格 |
|---|---|---|
| **流水线** | 洗菜→切菜→炒制→装盘，每人只做一道工序，传送带传菜 | **管道-过滤器** |
| **中央备料台** | 所有人围着一个大备料台取料、放半成品 | **仓库（黑板）** |
| **明确上下级** | 主厨指挥组长，组长指挥厨师，**只能上级叫下级干活** | **分层** |
| **喊一嗓子** | 菜好了就喊一声"3 号桌取餐"，谁有空谁来取，不用点名 | **事件驱动（隐式调用）** |
| **分店制** | 凉菜间、热菜间、面点间**各自独立**，谁出问题关谁 | **微服务** |

> **一句话直觉：架构风格 = 构件之间"怎么连、怎么说话"的规矩。**

## 4.2 📖 再讲原理（一）：五大类经典架构风格（**分类本身常考填空**）

| 大类 | 包含的具体风格 | 核心特征 |
|---|---|---|
| **① 数据流风格** | **批处理序列**、**管道-过滤器** | 数据驱动，**前一步的输出是后一步的输入** |
| **② 调用/返回风格** | **主程序-子程序**、**面向对象**、**分层架构** | 显式调用，**控制权在调用方** |
| **③ 独立构件风格** | **进程通信**、**事件驱动（隐式调用）** | 构件独立，**通过消息/事件交互** |
| **④ 虚拟机风格** | **解释器**、**规则系统** | 用"虚拟层"解释执行自定义逻辑 |
| **⑤ 仓库风格** | **数据库系统**、**超文本系统**、**黑板系统** | **中央共享数据**，周围构件读写仓库 |

> 🔥 **高频坑（原文特别强调）**：
> **主程序-子程序、面向对象、分层架构三者是"平级"关系，同属【调用/返回风格】，不是谁包含谁。**

### 逐个详解

**① 管道-过滤器（Pipe-Filter，数据流风格）**
- **构成**：**过滤器（Filter）**独立处理数据；**管道（Pipe）**负责传递数据。
- **特点**：过滤器**相互独立**，只知道输入格式和输出格式，**不知道上下游是谁**。
- **优点**：① 高内聚低耦合；② **过滤器可重用、可替换、可并行**；③ 支持流式处理，**延迟低**；④ 易于扩展（插入新过滤器）。
- **缺点**：① 不适合的交互性强的应用；② 数据传输解析开销大；③ 需要**统一的数据格式**。
- **典型例子**：**编译器**（词法分析→语法分析→语义分析→代码生成）、**UNIX 管道**、**批处理数据流**。
- **对比批处理序列**：批处理要求**每个阶段全部完成**才进入下一阶段（**延迟高**）；管道-过滤器是**流式**（边处理边传，**延迟低**）。

> ⭐ 真题考过：**实时入侵检测告警系统**（抓包→清洗→特征提取→规则匹配→告警）→ 选**管道-过滤器**，因为**实时性 + 流式数据 + 过滤器独立**。

**② 仓库风格 / 知识库**
- **构成**：**中央共享数据仓库** + 多个**独立构件**围绕仓库读写。
- **三个子类**：
  - **数据库系统**：中央是传统数据库，构件通过**被动**的方式获取（自己查）。
  - **黑板系统**：中央是**黑板（共享知识库）**，构件**被动响应**黑板上的状态变化，**谁有能力谁上**。
  - **超文本系统**：如网页链接结构。
- **黑板系统适用**：**没有确定解法的问题**——AI、信号处理、语音识别、知识推理。

**③ 分层架构（Layered，调用/返回风格）**
- **规则**：**上层调用下层**，**下层不能反向调用上层**；每层只与**相邻层**交互。
- **优点**：① **解耦、可维护性高**；② 支持**逐层抽象**与复用；③ 便于**分工开发**与局部替换。
- **缺点**：① 层与层之间的方法调用带来**性能损耗**；② 层级过多导致**系统复杂、调用链长**；③ 并非所有系统都易分层。
- **典型例子**：**OSI 七层模型**、表现层/业务逻辑层/数据访问层三层架构。

**④ 事件驱动架构（隐式调用，独立构件风格）**
- **机制**：构件**发布（广播）事件** → 其他构件**注册/订阅**该事件 → 事件触发时**被动调用**相应过程。
- **优点**：**松耦合**、可扩展性好（新增订阅者无需改发布者）、支持异步、适合分布式。
- **缺点**：① **构件放弃了对系统计算的控制**；② **事件调试困难**（不知道谁响应了）；③ **事务难以控制**（数据一致性难保证）；④ 正确性推理困难。
- **典型例子**：**GUI 事件处理**、**消息中间件/事件总线**、**发布-订阅模式**。

**⑤ 微服务架构**
- **做法**：按**业务**把系统拆成多个**独立部署、独立运行**的小服务，服务间通过 **RPC/HTTP/消息队列**通信。
- **收益（背）**：① **独立迭代、独立部署**；② **可伸缩性 Scalability**（可**针对特定服务扩容**）；③ 技术异构灵活；④ 故障隔离，局部失败不影响全局；⑤ 团队自治。
- **代价（背，写不全就丢一半分）**：① **分布式系统复杂度上升**；② **服务调用增加网络延迟，性能下降**；③ **分布式事务与数据一致性难保证**；④ **运维复杂度急剧上升**（需配套**完善的 DevOps 平台、服务治理、监控、链路追踪**）；⑤ 服务拆分带来**接口治理与版本管理**成本；⑥ 测试与排错难度上升。

> ⚠️ **原文勘误提醒**：微服务提升的是**"可伸缩性 / 部署独立性"**，并非绝对优于单体的"**可扩展性（Extensibility，新增业务功能）**"。
> 答题时写全：微服务**提升可伸缩性与部署独立性，代价是分布式复杂度和运维成本上升**。

**⑥ 调用/返回风格（Call/Return）**
- **主程序-子程序**：传统模块化调用，单线程控制。
- **面向对象**：对象之间通过**方法调用**交互，强调**封装、继承、多态**。
- **分层架构**：见上文 ④。

> **三者平级，同属调用/返回风格** —— 这是改错题的高频陷阱（"面向对象风格包含分层架构"→ 错）。

## 4.3 📖 再讲原理（二）：三种主流风格对比表

| 架构风格 | 核心特征 | 优点 | 缺点 |
|---|---|---|---|
| **分层架构** | 上层调用下层 | **可维护性高**、解耦、易分工、易替换 | 层级过多**性能下降**，调用链长 |
| **事件驱动** | 发布-订阅、**隐式调用** | **松耦合**、可扩展、支持异步 | **调试困难**、**事务难控制**、放弃流程控制 |
| **微服务** | 服务拆分、**独立部署** | **独立迭代部署、可伸缩性强**、故障隔离 | **分布式复杂度高**、网络延迟、运维成本急剧上升 |
| **管道-过滤器** | 数据流经管道、过滤器独立处理 | **可重用、可并行、延迟低** | 需统一数据格式，不适合交互式应用 |

## 4.4 🎯 怎么考 + ✍️ 怎么答

**题型特征**：**填空题为主**，答案几乎**隐藏在题干描述里**。

> 💡 **"原词重现"原则（本章最实用技巧）**：
> 案例填空的答案，**往往就是题干描述词的技术术语**。你只需要"翻译"：

| 题干原话 | 填什么 |
|---|---|
| "各构件独立运行，通过**事件总线/消息队列**通信" | **事件驱动（隐式调用）** |
| "**数据依次流经**各处理单元，每个单元独立处理并向后传递" | **管道-过滤器** |
| "系统分为**核心层/业务层/UI 层**，**上层调用下层**" | **分层架构** |
| "多个构件**共享一个中央数据仓库**，构件围绕仓库读写" | **仓库风格（知识库）** |
| "系统需要**实时处理流式数据**" | **管道-过滤器**（而非批处理） |
| "无确定解法、需要多知识源协同推理（AI/信号处理）" | **黑板系统** |
| "业务拆分为**多个独立部署**的小服务，通过 HTTP/RPC 通信" | **微服务** |
| "上层模块**调用下层函数/方法**，控制权在调用方" | **调用/返回风格** |

**注意**：**尽量用标准术语，不要自创词汇**（写"分层式""流水线式""消息式"都可能得不到分）。

**例题（真题变形：实时入侵检测告警系统）**：

> **题干**：某网络安全公司开发实时入侵检测告警系统，需**实时捕获**网络流量，并依次进行**过滤、分析、告警**。架构师在"**批处理**"与"**管道-过滤器**"两种风格间选型。
> 【问题 1】（10 分）请说明两种风格的特征，并给出选型建议及理由。
> 【问题 2】（8 分）请补充该管道-过滤器架构的核心构件。

**【问题 1】参考答案**：

> **批处理风格特征**：数据**按批集中处理**，每个处理阶段**必须全部完成**才能进入下一阶段；各阶段之间有明确的顺序和数据传递；**整体延迟高**，适合离线、大数据量、对实时性要求不高的场景。
>
> **管道-过滤器风格特征**：数据**以流的形式**经管道在过滤器之间传递，**每个过滤器独立地**对输入数据进行处理并输出到下一个管道；过滤器之间**相互独立、不知道彼此的存在**；**可并行、可重用、延迟低**。
>
> **选型建议**：应选择**管道-过滤器**风格。
> **理由**：
> ① **实时性**：本系统需实时捕获流量并告警，批处理需等待整批数据处理完成，**延迟高，无法满足实时告警要求**；管道-过滤器是**流式处理**，边捕获边处理，延迟低。
> ② **数据流特征**：系统处理的是**连续的流式网络数据**，天然契合"输入→处理→输出"的管道模型。
> ③ **过滤器独立**：捕获、清洗、特征提取、规则匹配、告警各环节**职责单一、相互独立**，符合**高内聚低耦合**原则，便于单独替换规则库或增加新的检测过滤器。
> ④ **可并行**：各过滤器可并行执行，提升吞吐量。

**【问题 2】参考答案**：

> - **数据源**：网络**抓包器**（如 libpcap / 流量镜像探针），捕获原始网络数据包；
> - **管道**：**缓冲区 / 消息队列**，在各过滤器之间传递数据包；
> - **过滤器 1（数据清洗）**：过滤无效包、重传包、去重；
> - **过滤器 2（特征提取）**：提取 IP、端口、协议、载荷特征等；
> - **过滤器 3（规则匹配/检测）**：与攻击特征库（规则库）比对，识别入侵行为；
> - **过滤器 4（告警触发）**：命中规则后生成告警，推送至告警平台/短信/邮件。

## 4.5 ⚠️ 丢分点

- ❌ **自创术语** → 必须写"**管道-过滤器**""**事件驱动（隐式调用）**""**分层架构**""**仓库（知识库）**""**微服务**"这类标准词。
- ❌ **把"分层架构"说成"包含面向对象"** → 三者**平级**，同属调用/返回风格。
- ❌ **批处理与管道-过滤器不分** → 关键区别是"**是否流式**"（批处理 = 整批完成后才下一步，**延迟高**）。
- ❌ **事件驱动的缺点漏写"事务难以控制"** → 这是评分表里的独立要点。
- ❌ **微服务只写收益不写代价** → 代价至少写 3 条：**分布式复杂度、网络延迟、运维成本（需 DevOps 平台）**。
- ❌ **说"微服务提升可扩展性（新增功能）"** → 精准说法是"提升**可伸缩性**与**部署独立性**"。
- ❌ **黑板系统用于确定性问题的场景** → 黑板系统适合**无确定解法的问题**（AI、信号处理、语音识别）。

# 第 5 章 风险管理：出门前带伞，还是买保险？

## 5.1 🧊 先建立直觉：天气预报说有雨

明天要出门，天气预报说 **60% 概率下雨**，一旦淋雨你会损失 200 元的西装。

你会怎么做？

| 做法 | 对应策略 | 本质 |
|---|---|---|
| **干脆不出门了** | **风险规避** | **改变计划，从根本上消除风险** |
| **带把伞** | **风险减轻** | 事还照样做，**降低概率或损失** |
| **打车（把淋雨风险转移给司机）** | **风险转移** | **让别人替你承担后果** |
| **不去管它，淋湿了回家换衣服** | **风险接受** | **认了，但准备了后手（家里有干衣服）** |

> **风险曝光度（风险值）= 风险发生的概率 × 风险造成的损失**
> 淋雨风险 = 60% × 200 元 = **120 元**。带伞花 5 分钟（成本），显然划算。

> 🔥 **核心直觉（本章的灵魂，也是最大的丢分点）**：
> **风险应对是"事前行动"——事情还没发生，你在提前做准备。**
> **事情已经发生之后再去处理，那叫"应急措施/补救措施"，不属于风险应对策略。**

## 5.2 📖 再讲原理（一）：风险管理四步

```
风险识别 → 风险分析(评估) → 风险规划(应对) → 风险监控
```

**① 风险识别**：找出所有潜在风险，形成**风险清单（风险登记册）**。
- **常用方法**：**头脑风暴、德尔菲法（专家匿名多轮）、访谈、SWOT 分析、检查单法、假设分析、鱼骨图（因果分析）、历史项目经验库**。
- **常见风险类别**：技术风险（新技术不成熟、接口不稳）、人员风险（骨干离职）、需求风险（需求变更频繁）、进度风险、成本风险、外部风险（政策、第三方）。

**② 风险分析（风险评估）**：
- **定性分析**：评估**发生概率**与**影响程度**，得出**风险等级**（高/中/低），常用**概率-影响矩阵**。
- **定量分析**：给出**数值化**的影响，如**风险曝光度 RE = 概率 × 损失金额**、**蒙特卡洛模拟**、**决策树/EMV（预期货币价值）**。

**③ 风险规划（应对策略）**——四种策略（**必背**）：

| 策略 | 定义 | 例子 | 适用 |
|---|---|---|---|
| **规避 Avoid** | **改变项目计划**，以**消除风险本身或其产生条件** | 放弃某高风险技术方案；**更换不靠谱的外包商**；取消高风险功能 | 风险高且无法承受 |
| **减轻 Mitigate** | 采取措施**降低风险发生的概率或造成的影响**（**事情照做**） | 增加**重试、熔断、降级**；**备用接口**；加强测试；AB 角制度 | 最常见、最通用 |
| **转移 Transfer** | 把风险的**后果与责任转移给第三方**（**不改变风险本身**） | **购买保险**、**外包**、**合同条款约定**（违约金/质保金） | 财务类、责任类风险 |
| **接受 Accept** | 承认风险存在，**不主动改变计划**，但**准备应急预案** | 编制**应急计划**、预留**应急储备（时间/资金）** | 风险低或应对成本高于损失 |

> ⚠️ **四个策略的边界（判卷抠字眼的地方）**：
> - **规避 vs 减轻**：规避 = **改计划，不做这件事了**（换方案/换供应商）；减轻 = **还是做，但加防护**。
> - **减轻 vs 转移**：**外包、买保险、签合同 = 转移**（责任给了别人）；**重试、熔断、备份、冗余、测试 = 减轻**（自己扛，但降低概率/损失）。
> - **接受 ≠ 不管**：**接受必须写"制定应急预案 / 预留应急储备"**，否则算错。

**④ 风险监控**：项目**全过程**跟踪已识别风险、识别新风险、评估应对措施的有效性。
- 手段：**风险再评估、风险审计、储备金分析（应急储备/管理储备）、状态例会、技术绩效测量**。

## 5.3 📖 再讲原理（二）：两种储备金（冷门但会考）

| 储备 | 用途 | 谁控制 |
|---|---|---|
| **应急储备** | 应对**已识别**的风险（"已知的未知"） | **项目经理可直接动用** |
| **管理储备** | 应对**未识别**的风险（"未知的未知"） | **需高层批准**才能动用 |

## 5.4 🎯 怎么考 + ✍️ 怎么答

**典型问法（真题改编 6 原题）**：

> **题干**：某银行核心系统升级项目，识别出以下风险：① 第三方征信接口不稳定；② 核心开发人员可能离职；③ 测试期客户提出大量新需求；④ 上线后可能出现严重故障；⑤ 项目预算不足。
>
> 【问题 1】（8 分）请写出四种常见的风险应对策略并说明其含义。
> 【问题 2】（9 分）针对"第三方征信接口不稳定"，请给出**减轻策略**的具体措施。
> 【问题 3】（8 分）针对"核心开发人员可能离职"，请给出应对措施。

**【问题 1】参考答案**：

> ① **风险规避**：通过**改变项目计划**消除风险或其产生条件，从而**彻底避免**该风险。如放弃某高风险技术方案、更换不达标的外包商。
> ② **风险减轻**：采取措施**降低风险发生的概率**或**降低风险发生后的影响**，但**不放弃原方案**。如增加冗余、重试机制、加强测试。
> ③ **风险转移**：将风险的**后果与责任转移给第三方**，风险本身并未消除。如**购买保险、外包、在合同中约定违约责任（质保金/违约金）**。
> ④ **风险接受**：承认风险存在且**不主动改变计划**，但**制定应急预案**并**预留应急储备**（时间/资金），风险发生时按预案处置。

**【问题 2】参考答案（减轻措施，尽量写 6 条）**：

> ① **重试机制**：对调用失败的请求设置**有限次数的重试**与**退避策略**（如指数退避），降低偶发抖动造成的失败；
> ② **超时与熔断**：设置合理**超时时间**，引入**熔断器**，接口持续故障时快速失败，避免线程阻塞导致**故障扩散（雪崩）**；
> ③ **服务降级与兜底**：接口不可用时返回**兜底数据 / 缓存数据 / 默认值**，保证主流程可用（如征信不可用转为人工审核）；
> ④ **备用接口**：对接**备用征信服务商**，主接口故障时自动切换；
> ⑤ **提前联调与压测**：在项目早期完成接口联调与**压力测试**，提前暴露性能与稳定性问题；
> ⑥ **监控告警**：对接口**成功率、响应时间、超时率**建立监控与告警，及时发现异常；
> ⑦ **异步化与补偿**：非关键路径改为**异步调用 + 消息队列补偿**，降低对接口可用性的同步依赖。

**【问题 3】参考答案（人员风险，多策略组合）**：

> ① **减轻（降低影响）**：实行 **AB 角制度**，核心模块**双人熟悉**；关键代码**强制代码评审（Code Review）**；建立**知识沉淀机制**（设计文档、接口文档、运行手册）；引入**结对编程/老带新**。
> ② **减轻（降低概率）**：完善**激励机制与团队建设**，提升人员稳定性；改善工作条件，减少加班。
> ③ **转移**：将**非核心模块外包**，降低对单一人员的依赖；与供应商签订**人员保障条款**。
> ④ **接受 + 应急**：建立**后备人员储备池**，一旦离职可快速补充；在进度计划中**预留缓冲时间**。

## 5.5 ⚠️ 丢分点

- ❌ **把"事后补救"当成风险应对** → 风险应对必须是**事前行动**。事故发生了再修复 = **应急措施/问题处置**。
- ❌ **"规避"写成"放弃项目"** → 规避是"**改变计划消除该风险产生的条件**"（如**放弃某个方案/更换外包商**），不是整个项目不干。
- ❌ **把"外包、买保险"写成减轻** → 那是**转移**（关键：后果由第三方承担）。
- ❌ **把"重试、熔断、降级、备份、冗余、加强测试"写成转移** → 那是**减轻**（自己还在做这件事，只是加了防护）。
- ❌ **"接受"只写"接受风险"四个字** → 必须补"**制定应急预案 + 预留应急储备**"。
- ❌ **答措施太笼统**（如"加强管理""提高重视"）→ 必须**针对具体风险给出技术手段**（重试/熔断/降级/备用/AB角/监控）。
- ❌ **漏写"风险监控"这一步** → 四步里"监控"常被忽略，是独立要点。
- ❌ **风险曝光度公式写错** → **RE = 概率 × 损失**（不是相加）。

# 第 6 章 挣值分析 EVM（计算专项，最好拿的分）

> 🎁 **本章是整份文档里"性价比最高"的一章**：
> 公式固定、有唯一标准答案、不依赖任何工程经验。**背熟 8 个公式，考到就是白送 8~10 分。**

## 6.1 🧊 先建立直觉：装修到一半，钱花超了吗？

你装修房子，**预算 10 万（BAC）**，计划 **10 天**完工。现在**第 6 天结束**：

| 三个问题 | 对应概念 | 数值 |
|---|---|---|
| **按计划，到现在为止"应该"完成多少活？** | **PV**（计划价值） | 计划每天 1 万 → 第 6 天该完成 **6 万** |
| **实际完成了多少活（按预算算值多少钱）？** | **EV**（挣值） | 实际只干完 **4.8 万** 的活 |
| **为了干这些活，实际花了多少钱？** | **AC**（实际成本） | 实际花了 **5.6 万** |

于是：
- **进度**：该干 6 万的活，只干了 4.8 万 → **落后**了（SV = 4.8 - 6 = **-1.2 万**）
- **成本**：干了 4.8 万的活，却花了 5.6 万 → **超支**了（CV = 4.8 - 5.6 = **-0.8 万**）

> **一句话直觉：EVM 就是用"钱"当统一尺子，同时量"进度"和"成本"。**
> **核心技巧：看"活"和"钱"谁多谁少——活干得比计划少 = 落后；钱花得比挣得多 = 超支。**

## 6.2 📖 再讲原理（一）：三个基本参数

| 参数 | 全称 | 定义 | 记忆 |
|---|---|---|---|
| **PV** | Planned Value **计划价值** | **计划**要完成的工作量的**预算**成本 | "**该**干多少" |
| **EV** | Earned Value **挣值** | **实际已完成**工作量的**预算**成本 | "**实际**干了多少"（按预算折算） |
| **AC** | Actual Cost **实际成本** | 已完成工作量的**实际**花费 | "**花**了多少" |
| **BAC** | Budget At Completion **完工预算** | 项目的**总预算** | "总盘子" |

> 💡 **三个字记忆法**：
> **PV = 计划的价值（该干的）**
> **EV = 挣到的价值（干了的）**
> **AC = 实际的成本（花了的）**
>
> ⚠️ 注意 **EV 是"按预算算的"**，不是按实际成本算的！这是 EVM 最反直觉但最关键的一点。

## 6.3 📖 再讲原理（二）：四个评价指标（**必须背到条件反射**）

| 指标 | 公式 | 判断 | 记忆 |
|---|---|---|---|
| **成本偏差 CV** | **CV = EV − AC** | **CV > 0 成本节约**；CV < 0 **成本超支** | 挣的 − 花的 |
| **进度偏差 SV** | **SV = EV − PV** | **SV > 0 进度提前**；SV < 0 **进度滞后** | 挣的 − 该干的 |
| **成本绩效指数 CPI** | **CPI = EV / AC** | **CPI > 1 成本节约**；CPI < 1 **成本超支** | 效率：挣的 ÷ 花的 |
| **进度绩效指数 SPI** | **SPI = EV / PV** | **SPI > 1 进度提前**；SPI < 1 **进度滞后** | 效率：挣的 ÷ 该干的 |

> 🔥 **万能判断口诀（背死，永不失分）**：
> **偏差用减法，指数用除法。**
> **"减"出来小于 0 就是不好（超支/滞后）；"除"出来小于 1 就是不好（超支/滞后）。**
> **正数 = 好，负数 = 差；大于 1 = 好，小于 1 = 差。**
>
> 换句话说：
> - **CV < 0 或 CPI < 1 → 成本超支**（花钱比干活快）
> - **SV < 0 或 SPI < 1 → 进度滞后**（干活比计划慢）

## 6.4 📖 再讲原理（三）：完工预测 EAC / ETC / VAC / TCPI

**核心关系（记这一个就够）**：
```
EAC（完工估算） = AC（已花的） + ETC（完工尚需估算）
```

**ETC 分两种情况**：

| 情况 | 假设 | ETC 公式 | EAC 公式 |
|---|---|---|---|
| **典型偏差**（默认） | **未来按当前效率继续**（问题会持续） | **ETC = (BAC − EV) / CPI** | **EAC = BAC / CPI**<br>或严谨式 **EAC = AC + (BAC − EV) / CPI** |
| **非典型偏差** | **未来回归原计划**（当前问题是偶然的） | **ETC = BAC − EV** | **EAC = AC + (BAC − EV)** |
| **同时受 CPI 与 SPI 影响**（冷门） | 进度与成本都影响 | — | **EAC = AC + (BAC − EV) / (CPI × SPI)** |

> 💡 **两个公式数学上等价**：`BAC / CPI` 与 `AC + (BAC − EV) / CPI` 结果相同。
> **建议写严谨式**（`AC + (BAC−EV)/CPI`），因为它能体现你对 ETC 的理解，**万一算错也能拿步骤分**。

**其他指标**：

| 指标 | 公式 | 含义 |
|---|---|---|
| **VAC** 完工偏差 | **VAC = BAC − EAC** | **> 0 预计结余；< 0 预计超支** |
| **TCPI** 完工绩效指数 | 基于 BAC：**TCPI = (BAC − EV) / (BAC − AC)**<br>基于 EAC：**TCPI = (BAC − EV) / (EAC − AC)** | 剩余工作**必须达到的效率**才能按预算/按新估算完工。**TCPI > 1 表示剩余工作必须比过去更高效**（或比当前计划更高效）才能达标 |

> ⚠️ **TCPI 是近两年新出现的冷门考点**，"冷门"意味着**别人不会你会**。记一句话即可：
> **TCPI 衡量"剩余工作量需要多高效完成"；TCPI 越大，说明压力越大。**

## 6.5 🎯 计算题四步法（考场上按这个写，永不丢步骤分）

```
第1步：列出已知（抄题干）
      BAC = ？，PV = ？，EV = ？，AC = ？
第2步：算偏差（写公式 → 代入 → 给结论）
      CV = EV − AC = xx − xx = xx      → CV < 0，成本超支
      SV = EV − PV = xx − xx = xx      → SV < 0，进度滞后
第3步：算指数（写公式 → 代入 → 给结论）
      CPI = EV / AC = xx / xx ≈ x.xx   → CPI < 1，成本超支（成本效率为 xx%）
      SPI = EV / PV = xx / xx = x.xx   → SPI < 1，进度滞后（进度效率为 xx%）
第4步：预测 + 纠偏
      EAC = AC + (BAC − EV)/CPI = ...  （或 EAC = AC + (BAC − EV)）
      状态结论 + 改进措施（5 选 3）
```

## 6.6 🎯 例题（真题改编 5 原题，务必动手算一遍）

> **题干**：某项目 **BAC = 1000 万元**，工期 **10 个月**。第 **6 个月末**检查：**PV = 600 万，EV = 480 万，AC = 560 万。**
>
> 【问题 1】（8 分）计算 CV、SV，判断项目当前状态。
> 【问题 2】（8 分）计算 CPI、SPI 并说明含义。
> 【问题 3】（9 分）在典型偏差条件下，计算完工估算 EAC，并给出纠偏措施。

**【问题 1】参考答案**：

> - **CV = EV − AC = 480 − 560 = −80（万元）**
>   → **CV < 0，项目成本超支**（完成同样的工作量，实际花费超出了预算 80 万元）。
> - **SV = EV − PV = 480 − 600 = −120（万元）**
>   → **SV < 0，项目进度滞后**（按计划应完成 600 万元的工作量，实际只完成 480 万元，落后 120 万元）。
> - **结论：项目当前处于【成本超支 + 进度滞后】的不利状态。**

**【问题 2】参考答案**：

> - **CPI = EV / AC = 480 / 560 ≈ 0.857**
>   → **CPI < 1，成本超支**。**含义：每支出 1 元，只挣得 0.857 元的价值**，成本效率约为 85.7%，**成本使用效率低于预期**。
> - **SPI = EV / PV = 480 / 600 = 0.8**
>   → **SPI < 1，进度滞后**。**含义：项目实际完成进度仅为计划进度的 80%**，即只完成了计划工作量的八成。
> - **综合判断**：CPI 与 SPI 均小于 1，项目**既超支又拖期**，需要立即采取纠偏措施。

**【问题 3】参考答案**：

> **EAC 计算（典型偏差，即未来按当前效率继续）**：
> - 简化式：**EAC = BAC / CPI = 1000 / 0.857 ≈ 1166.7（万元）**
> - 严谨式：**EAC = AC + (BAC − EV) / CPI = 560 + (1000 − 480) / 0.857 ≈ 560 + 606.8 ≈ 1166.8（万元）**
>
> **预测结论**：项目完工预计需要约 **1166.7 万元**，比原预算 **超支约 166.7 万元**（VAC = BAC − EAC ≈ −166.7 万元）。
>
> **纠偏措施**：
> ① **赶工（Crashing）**：对**关键路径**上的任务**增加资源**（加班、增派人员），以成本换时间；
> ② **快速跟进（Fast Tracking）**：将原本**串行**的工作改为**并行**（如设计与开发部分重叠），**不增加成本但增加返工风险**；
> ③ **优化资源配置**：将**高素质/高效率人员**投入关键路径任务，提升工作效率；
> ④ **改进技术与方法**：引入**自动化测试、代码复用、成熟构件/框架**，减少返工，提升生产率；
> ⑤ **缩减范围（最实用）**：与甲方沟通，将**非核心功能移至下一期**，优先保证核心功能按期交付；
> ⑥ **加强成本与进度监控**：缩短监控周期，**加强变更控制**，防止范围蔓延；
> ⑦ **外包**：将非核心模块外包，转移部分进度压力。

> 💡 **答题提示**：**纠偏措施要"点名道姓"**（赶工/快速跟进/缩减范围/优化资源/改进方法），写"加强管理""提高效率"不给分。
> 另外，**赶工与快速跟进的代价要写清楚**：**赶工增成本，快速跟进增风险**。这是区分度所在。

## 6.7 ⚠️ 丢分点

- ❌ **只写结果不写公式** → 计算题**公式和步骤都是分**，即使最终数字算错也能拿大部分分。
- ❌ **CV / SV 的被减数与减数写反** → 记住：**都是 EV 打头**（CV = **EV** − AC，SV = **EV** − PV），因为 EV 是"实际挣到的"，是主角。
- ❌ **判断方向写反** → "**小于 0 / 小于 1 = 不好**"。考场上紧张时最容易反。
- ❌ **EAC 公式选错（典型 vs 非典型）** → **题干说"按当前趋势/偏差持续下去"→ 典型（除以 CPI）**；**说"后续工作将按原计划效率完成/当前偏差是偶然的"→ 非典型（不除）**。**没说明就默认典型偏差。**
- ❌ **只写 `EAC = BAC/CPI` 不写严谨式** → 建议**两个都写**（"即 `AC + (BAC−EV)/CPI`"），万无一失。
- ❌ **算完就收笔** → **必须给"状态结论 + 纠偏措施"**，案例题通常这两部分占一半分。
- ❌ **纠偏措施写"加快进度""节约成本"** → 必须写**专业术语**（赶工、快速跟进、缩减范围、优化资源配置、改进方法）。
- ❌ **单位丢失** → 写明"万元"，保留 1~2 位小数。

# 第 7 章 敏捷、Scrum 与 DevOps

## 7.1 🧊 先建立直觉：敏捷宣言的四句"与其……不如……"

传统做法（瀑布）是"**先签合同、写厚文档、按图施工、拒绝变更**"。
2001 年一群程序员受不了了，发表了**敏捷宣言**，四句话：

| 敏捷宣言 | 人话解释 | ⚠️ 注意 |
|---|---|---|
| **个体和互动** 高于 流程和工具 | 人对人当面说清楚，比写一堆流程文档管用 | **"高于"不是"取代"**！右边的东西**依然有价值** |
| **可工作的软件** 高于 详尽的文档 | 能跑起来的程序，比 200 页的设计文档有说服力 | 不是"不写文档"，是"**够用就好**" |
| **客户合作** 高于 合同谈判 | 客户跟我们一起干，比在合同上互相防备强 | |
| **响应变化** 高于 遵循计划 | 计划赶不上变化，能改才是本事 | |

> 🔥 **高频填空题**：敏捷宣言四句话（**个体和互动、可工作的软件、客户合作、响应变化**）。
> 🔥 **高频陷阱**：问"敏捷是不是不要文档？"→ **不是**。原文是"**高于**"，右边的东西**仍有价值**，只是左边的**更重要**。

## 7.2 📖 再讲原理（一）：Scrum（最常考的敏捷框架）

### 三个角色（必背）

| 角色 | 职责 | ⚠️ 常见错误认知 |
|---|---|---|
| **产品负责人 PO**（Product Owner） | **管理产品待办列表 Product Backlog**，**对需求排序定优先级**，明确"**做什么**"；对产品价值负责 | PO 不是"写需求的文员"，是**价值决策者** |
| **Scrum Master（SM）** | **服务型领导**，**保障团队遵循 Scrum 流程**、**移除团队遇到的障碍**、促成自组织、保护团队不受干扰 | 🔥 **SM 不是项目经理！不分配任务、不考核绩效、不做技术决策** |
| **开发团队 Dev Team** | **自组织、跨职能**的团队（通常 5~9 人），自行决定"**怎么做**"和"**谁来做**" | 团队**自己领任务**，不是被派活 |

### 三个工件（必背）

| 工件 | 是什么 |
|---|---|
| **产品待办列表 Product Backlog** | 产品**所有**待做事项的有序列表，由 **PO 维护并排序** |
| **迭代待办列表 Sprint Backlog** | 当前 Sprint 要做的事项，由**开发团队**从 PB 中挑选并拆解 |
| **增量 Increment** | 每个 Sprint 结束时产出的**可用的、潜在可交付的**软件增量 |

> 补充：**三大承诺**（Scrum Guide 2020）：**产品目标 Product Goal、Sprint 目标 Sprint Goal、完成的定义 DoD（Definition of Done）**。

### 五个事件（⚠️ 原文写 4 个，标准为 5 个）

| 事件 | 时间 | 干什么 |
|---|---|---|
| **Sprint（迭代）** | **固定时长，通常 2~4 周**（时间盒，不可延长） | Scrum 的核心容器，其他所有事件都在其中 |
| **① Sprint 计划会** | Sprint 开始时 | 确定**本次 Sprint 目标**，团队从 PB 中选取条目形成 Sprint Backlog |
| **② 每日站会 Daily Scrum** | 每天 **15 分钟**，站着开 | 每人回答三句话：**昨天做了什么、今天要做什么、遇到了什么障碍** |
| **③ Sprint 评审会 Review** | Sprint 结束时 | 向**干系人演示**增量，收集反馈，**调整 Product Backlog** |
| **④ Sprint 回顾会 Retrospective** | 评审会后 | 团队**内部**复盘：哪些做得好、哪些要改进，**改进流程本身** |

> ⚠️ **重要**：原文写"四个主要事件"，**但 Scrum 官方标准是 5 个事件（含 Sprint 计划会）**。
> **答题时务必写 5 个，并说明"Sprint 本身也是一个事件"**，避免被判"漏项"。

### 其他常考名词

| 名词 | 含义 |
|---|---|
| **用户故事 User Story** | 从用户视角描述需求："**作为〔角色〕，我想要〔功能〕，以便〔价值〕**" |
| **故事点 / 速率 Velocity** | 用**相对单位**估算工作量；**速率** = 团队每个 Sprint 平均完成的故事点数 |
| **燃尽图 Burndown Chart** | 展示**剩余工作量随时间下降**的趋势，判断是否如期完成 |
| **看板 Kanban** | **可视化**工作流 + **限制在制品 WIP** + **拉动式**，强调**持续流动**而非固定迭代 |
| **XP 极限编程** | **结对编程、测试驱动开发 TDD、持续集成、重构、简单设计、集体代码所有权、小版本发布、现场客户、编码标准、每周 40 小时** |

## 7.3 📖 再讲原理（二）：DevOps

**定义**：打通**开发（Dev）— 测试 — 运维（Ops）**的**文化、实践与工具**体系，目标是**缩短上线周期、提升交付频率与质量**。

> 🔥 **原文勘误（高频扣分点）**：
> **CI/CD 是技术实践，不是 DevOps 的全部。**
> **DevOps 的三大支柱（核心基础）是：人（文化，打破部门墙）、流程（精益）、工具（自动化）。**
> **答题时除了 CI/CD，务必加上"自动化运维（自动化部署、监控、自愈）"和"文化/组织协作"。**

| 概念 | 含义 |
|---|---|
| **CI 持续集成** | 开发人员**频繁**（每天多次）将代码合并到主干，每次合并都**自动构建 + 自动测试**，尽早发现集成错误 |
| **CD 持续交付** | 代码随时处于**可部署**状态，可**手动**一键发布 |
| **CD 持续部署** | 通过自动化流水线，**自动**发布到生产环境 |
| **持续测试** | 自动化测试贯穿流水线 |
| **IaC 基础设施即代码** | 用代码定义和管理基础设施（Terraform、Ansible、K8s YAML），环境可复现 |
| **监控与可观测性** | 日志、指标、链路追踪，快速定位故障 |

**发布策略（近年热点）**：

| 策略 | 做法 | 特点 |
|---|---|---|
| **蓝绿部署** | 同时运行新旧两套环境，切换流量 | 切换快、**回退极快**，但**资源消耗翻倍** |
| **金丝雀（灰度）发布** | 先放**少量流量**到新版本，验证后逐步放量 | **风险可控**，发现问题只影响少量用户 |
| **滚动发布** | 逐批替换实例 | 资源友好，但回退较慢 |
| **特性开关 Feature Flag** | 用配置控制功能是否对用户可见 | 发布与**功能上线解耦**，出问题秒级关闭 |

### DORA 四大关键度量指标（2024–2025 新兴热点，背）

| 指标 | 英文 | 衡量什么 |
|---|---|---|
| **① 部署频率** | Deployment Frequency | 多久交付一次（**吞吐**） |
| **② 变更前置时间** | Lead Time for Changes | 从代码提交到上线要多久（**吞吐**） |
| **③ 服务恢复时间** | **MTTR** | 故障时多久恢复（**稳定性**） |
| **④ 变更失败率** | Change Failure Rate | 有多少比例的变更导致故障（**稳定性**） |

> **口诀：两个"快"（部署频率、前置时间）+ 两个"稳"（MTTR、变更失败率）。**

## 7.4 🎯 怎么考 + ✍️ 怎么答

**典型问法（真题改编 8 原题）**：

> **题干**：某团队采用 Scrum 开发：PO 维护 Backlog 并确定优先级；**SM 给团队分配任务并考核绩效**；开发团队负责交付。迭代周期 2 周，Sprint 结束时召开评审会和回顾会。团队同时引入了**持续集成、自动化测试与自动化部署**。
>
> 【问题 1】（7 分）SM 的职责描述是否正确？说明理由。
> 【问题 2】（9 分）请说明 Scrum 的三个角色、三个工件和主要事件。
> 【问题 3】（9 分）持续集成与自动化部署体现了什么实践？有什么作用？

**【问题 1】参考答案**：

> **不正确。**
> **理由**：
> ① **SM 不是项目经理**，**没有分配任务和考核绩效的权力**。Scrum 中开发团队是**自组织**的，由团队成员**自行认领**任务并决定如何完成。
> ② **SM 的正确职责**是：作为**服务型领导**，**保障团队理解并遵循 Scrum 流程**；**识别并移除团队遇到的障碍**（如协调外部资源、解决跨部门依赖）；**保护团队不受外部干扰**；**促进团队自组织与持续改进**；辅导 PO 与团队有效使用 Scrum。
> ③ 若由 SM 分配任务并考核绩效，会**破坏团队自组织**，违背敏捷"**个体和互动高于流程和工具**"的核心理念。

**【问题 2】参考答案**：

> **三个角色**：
> ① **产品负责人 PO**：维护**产品待办列表 Product Backlog**，对需求**排序定优先级**，对产品价值负责；
> ② **Scrum Master**：服务型领导，**移除障碍**、保障流程、促进自组织；
> ③ **开发团队**：**自组织、跨职能**，自行决定工作分配与实现方式，交付可用增量。
>
> **三个工件**：
> ① **产品待办列表 Product Backlog**；② **迭代待办列表 Sprint Backlog**；③ **增量 Increment**。
>
> **主要事件（标准 5 个）**：
> ① **Sprint**（固定时长，通常 2~4 周，时间盒不可延长）；
> ② **Sprint 计划会**：确定 Sprint 目标与 Sprint Backlog；
> ③ **每日站会**：每天 15 分钟，同步"昨天做了什么/今天做什么/有什么障碍"；
> ④ **Sprint 评审会**：向干系人演示增量，收集反馈并调整 Product Backlog；
> ⑤ **Sprint 回顾会**：团队复盘流程本身，持续改进。

**【问题 3】参考答案**：

> 体现了 **DevOps 实践**（具体为 **CI/CD 持续集成与持续交付/部署**）。
>
> **持续集成（CI）的作用**：开发人员**频繁将代码合并到主干**，每次合并触发**自动构建与自动测试**，能够**尽早发现集成错误**，避免"集成地狱"；提升代码质量与交付速度。
>
> **自动化部署的作用**：将部署过程**标准化、自动化、可重复**，**减少人工操作失误**，**缩短发布周期**，支持**高频次、低风险**的发布；配合**蓝绿部署/金丝雀发布/特性开关**，可进一步降低上线风险并实现**快速回退**。
>
> **补充说明**：DevOps 不仅仅是 CI/CD 工具链，其**三大基础（支柱）为**：
> ① **人（文化）**：打破开发、测试、运维之间的部门墙，建立**责任共担**的协作文化；
> ② **流程（精益）**：**价值流**梳理、减少浪费、小批量快速流动、持续反馈；
> ③ **工具（自动化）**：**自动化构建、测试、部署、监控与运维**。
> 此外可引入 **DORA 四大度量指标**（部署频率、变更前置时间、服务恢复时间 MTTR、变更失败率）持续衡量改进效果。

## 7.5 ⚠️ 丢分点

- ❌ **说"Scrum Master 是项目经理，负责分配任务和考核绩效"** → **全卷最高频的送命题**。SM 是**服务者、障碍清除者**。
- ❌ **只答 4 个事件** → 标准是 **5 个**（含 **Sprint 计划会**）。
- ❌ **说"敏捷不需要写文档"** → 宣言是"**高于**"不是"**取代**"，右侧内容仍有价值。
- ❌ **把 DevOps 等同于 CI/CD** → 必须补"**文化（人）+ 精益流程 + 自动化运维**"。
- ❌ **混淆持续交付与持续部署** → **持续交付 = 随时可发布（手动发布）**；**持续部署 = 自动发布到生产**。
- ❌ **每日站会写成"汇报进度给领导"** → 站会是**团队内部同步与暴露障碍**，不是向上级汇报。
- ❌ **漏掉"Sprint 是时间盒，不可延长"** → 常考判断点。
- ❌ **把 Sprint 评审会与回顾会搞混** → **评审会 = 对外演示产品、收集需求反馈**；**回顾会 = 对内复盘流程、改进工作方式**。

# 第 8 章 CMMI：从"野路子厨师"到"米其林"

## 8.1 🧊 先建立直觉：餐馆的五个段位

| 段位 | 状态 | 类比 |
|---|---|---|
| **1 级 · 初始级** | **全靠大厨个人发挥**。大厨心情好菜就好，大厨一走，味道全变。 | **混乱无序、不可预测**，成功依赖**个人英雄** |
| **2 级 · 受管理级** | **每桌客人的单子都有记录、有跟踪**，这桌菜做了什么、花了多少成本，都能查 | **项目层面**有**计划、有跟踪、有管理**；类似项目可**重复**成功 |
| **3 级 · 已定义级** | **全店有标准化菜谱（SOP）**，所有分店都按同一套流程做 | **组织层面**建立**标准化过程**，**所有项目**都采用组织的标准过程 |
| **4 级 · 定量管理级** | **用数据管**：出餐时间、成本、客户满意度都有**量化指标和统计控制** | 用**量化数据**度量和管控过程性能 |
| **5 级 · 优化级** | **持续改进**：定期研究"怎么做得更好"，**主动预防**问题而不是等它发生 | 基于量化的**持续过程改进**与**缺陷预防** |

> **一句话直觉：CMMI 就是"从靠人 → 靠项目 → 靠组织 → 靠数据 → 靠改进"的五个台阶。**

## 8.2 📖 再讲原理：五级详解 + 关键词锚点

| 级别 | 名称 | 关键词（**判级别的唯一依据**） | 特征 |
|---|---|---|---|
| **1 级** | **初始级**（Initial） | **混乱、无序、不可预测、依赖个人** | 过程无规范，成功靠个人能力与英雄主义，**项目常超期超支** |
| **2 级** | **受管理级**（Managed） | **项目级**、**有规划有跟踪**、**可重复** | 在**项目层面**建立了基本的项目管理过程，对**进度、成本、质量**进行跟踪与控制；类似项目能**重复**以往的成功 |
| **3 级** | **已定义级**（Defined） | **组织级**、**标准化**、**全组织统一** | 在**组织层面**建立**标准化的过程**并**制度化**，**所有项目**都采用**经裁剪的组织标准过程** |
| **4 级** | **定量管理级**（Quantitatively Managed） | **量化数据、统计控制、可预测** | 对过程与产品质量进行**定量度量**与**统计控制**，过程性能**可量化、可预测** |
| **5 级** | **优化级**（Optimizing） | **持续改进、缺陷预防、技术创新** | 基于量化反馈**持续改进过程**，**主动预防缺陷**，能够**引入新技术**进行过程创新 |

> 🔥 **判级口诀（考试秒杀）**：
> **2 级管项目；3 级管组织（标准化）；4 级管数据（量化）；5 级管改进（持续优化）。**
>
> 对应题干暗号：
> - "**每个项目都制定了计划并跟踪**" → **2 级受管理级**
> - "**建立了组织级的标准化流程，所有项目统一遵循**" → **3 级已定义级**
> - "**用量化数据/统计方法度量和控制过程**" → **4 级定量管理级**
> - "**持续改进、主动预防缺陷、技术创新**" → **5 级优化级**

## 8.3 ⚠️ 两个"译名坑"（原文特别勘误，每年都有人栽）

> ⚠️ **坑 1：第 2 级的标准译名是"受管理级"（Managed），不要写成"可管理级"。**
> ⚠️ **坑 2：第 4 级的标准译名是"定量管理级"（Quantitatively Managed），千万不要写成"已管理级"** —— 因为"已管理级"会与第 2 级"受管理级"混淆，**阅卷会扣分**。

**补充（防冷门）**：CMMI 有**两种表示法**：

| 表示法 | 等级 | 说明 |
|---|---|---|
| **阶段式**（常用） | 1~5 级（**成熟度等级**）：初始级、受管理级、已定义级、定量管理级、优化级 | 组织整体成熟度，**逐級上升，不可跳级** |
| **连续式** | 0~3 级（**能力等级**）：**不完整级、已执行级、已管理级、已定义级** | 针对**单个过程域**的能力评估 |

> ⚠️ 注意：**连续式的"已管理级/已定义级"和阶段式的"受管理级/已定义级"名字很相似但含义不同**，属于两套体系，**不要混答**。

## 8.4 🎯 怎么考 + ✍️ 怎么答

**典型问法（真题改编 7 第三问）**：

> **题干**：某市社保系统升级，……管理部门希望**建立标准化的流程体系**，并能够**用量化数据控制过程**。
> 【问题】建立标准化流程达到 CMMI 几级？用量化数据控制过程达到 CMMI 几级？

**参考答案**：

> ① **建立标准化流程 → CMMI 3 级（已定义级）**。
> 理由：3 级的核心特征是**在组织层面建立标准化的软件过程并将其制度化，所有项目均采用经裁剪的组织标准过程**，与"建立标准化流程体系"直接对应。
>
> ② **用量化数据控制过程 → CMMI 4 级（定量管理级）**。
> 理由：4 级的核心特征是**对过程与产品质量进行定量度量与统计控制**，过程性能**可量化、可预测**，与"用量化数据控制过程"直接对应。
>
> ③ 若进一步要求**持续改进、主动预防缺陷**，则对应 **CMMI 5 级（优化级）**。
>
> ⚠️ 注意：CMMI 成熟度等级是**逐级递进、不可跨越**的，组织必须先达到 3 级才能评估 4 级。

## 8.5 ⚠️ 丢分点

- ❌ **第 4 级写成"已管理级"** → 标准译名是**"定量管理级"**。
- ❌ **2 级与 3 级混淆** → **2 级 = 项目层面有管理；3 级 = 组织层面标准化**。题干出现"**组织**""**所有项目统一**""**标准化**"→ 一定是 3 级。
- ❌ **4 级与 5 级混淆** → **4 级 = 用数据度量和控制**（量化）；**5 级 = 用数据持续改进和预防缺陷**（优化）。
- ❌ **忘记"逐级递进不可跨越"** → 常作为判断干扰项。
- ❌ **把 CMMI 当成"产品质量等级"** → CMMI 衡量的是**过程成熟度**，不是产品本身的质量。

# 第 9 章 UML 建模：图纸族辨认指南

## 9.1 🧊 先建立直觉：UML = 一整套建筑图纸

造一栋楼需要不同图纸，每张图纸回答不同问题：

| 图纸 | 回答的问题 | UML 图 |
|---|---|---|
| **房间清单与功能分区** | "这楼有哪些房间、给谁用" | **用例图** |
| **结构图（几根柱子、承重在哪）** | "这楼由什么构成" | **类图、对象图、构件图** |
| **水电管线走向（装在哪台设备上）** | "软件跑在什么硬件上" | **部署图** |
| **施工图（施工先后顺序）** | "流程怎么走" | **活动图** |
| **电梯运行规则（停靠→开门→关门→运行）** | "单个东西的状态怎么变" | **状态机图** |
| **多人协作时序表（谁先做什么谁后做什么）** | "对象之间按什么顺序对话" | **顺序图（时序图）** |

> **一句话直觉：UML 就是"用不同的图，从不同角度描述同一个系统"。**
> **案例题 90% 考的是"哪张图干什么用"——也就是"辨认图纸"。**

## 9.2 📖 再讲原理（一）：UML 图的两大家族

### 结构图（静态，描述"系统由什么组成"）

| 图 | 描述什么 | 关键词 |
|---|---|---|
| **类图 Class Diagram** | **类、类的属性与方法、类之间的关系** | **最常用**；静态结构 |
| **对象图 Object Diagram** | 类图在**某一时刻的实例**（快照） | 对象是类的实例 |
| **构件图 Component Diagram** | **构件（组件）之间的组织与依赖关系** | 可替换的物理部件 |
| **部署图 Deployment Diagram** | **软件构件部署在哪些硬件节点上** | **硬件节点 + 节点间的连接** |
| **包图 Package Diagram** | 包（命名空间）及其依赖关系 | 分组/模块化 |
| **组合结构图** | 类或构件的**内部结构** | 冷门 |
| **制品图** | 物理文件（jar、dll、文档） | 冷门 |

### 行为图（动态，描述"系统怎么动"）

| 图 | 描述什么 | ⚠️ 高频混淆点 |
|---|---|---|
| **用例图 Use Case** | **参与者（Actor）与系统功能（用例）**，描述**用户的功能需求** | 用例图**只描述功能**，不描述实现 |
| **顺序图（时序图）Sequence** | 对象之间**按时间顺序**传递消息 | 🔥 **强调时间先后顺序** |
| **通信图（协作图）Communication** | 对象之间的**交互与链接关系** | **不强调时间顺序**（与顺序图的区别） |
| **活动图 Activity** | **业务流程、工作流、分支与并发** | 🔥 **像流程图**；描述"**做什么**"的流程 |
| **状态机图 State Machine** | **单个对象**在其生命周期内**状态的变迁** | 🔥 **一个对象自己**的状态变化（订单状态、电梯状态） |
| **定时图 Timing** | 状态随时间变化，强调**时间约束** | 实时系统 |
| **交互概览图** | 活动图与顺序图的结合 | 冷门 |

> 🔥 **最高频的三图辨析（年年考，年年有人错）**：
>
> | 图 | 一句话 | 判断技巧 |
> |---|---|---|
> | **顺序图（时序图）** | **对象之间消息交互的时间先后顺序** | 看"**谁先谁后**""消息" |
> | **活动图** | **业务流程 / 工作流**（含分支、并发、泳道） | 看"**流程**""步骤""分支""并发" |
> | **状态机图** | **单个对象**自身生命周期内的**状态变迁** | 看"**一个对象的状态**"（订单从待付款→已付款→已发货） |
>
> **口诀：顺序看先后，活动看流程，状态看自己。**

## 9.3 📖 再讲原理（二）：用例图的两种关系（**方向极易搞反**）

| 关系 | 语义 | **箭头方向** | 例子 |
|---|---|---|---|
| **包含 «include»** | **基础用例必须执行**被包含用例（**一定发生**）；提取公共的、必须的行为 | **从基础用例 → 指向被包含用例** | "**购物**" —«include»→ "**登录**"（购物必须先登录） |
| **扩展 «extend»** | 扩展用例是**可选的、条件性的**行为（**可能发生**） | **从扩展用例 → 指向基础用例** | "**使用优惠券**" —«extend»→ "**购物**"（购物时可选使用） |
| **泛化 «generalize»** | 子用例继承父用例的行为 | **从子用例 → 指向父用例** | "**微信支付**" —▷ "**支付**" |

> 🔥 **方向口诀（背死）**：
> **include 指向"被调用的"（基础 → 被包含）**；
> **extend 指向"被扩展的"（扩展 → 基础）**。
> **简单记：include 箭头"向外"（去拿必要的东西），extend 箭头"向内"（往里加可选的东西）。**
>
> 更实用的判定法：
> - 去掉它，基础用例**不完整/无法执行** → **include**
> - 去掉它，基础用例**仍然完整**（只是少了个可选功能） → **extend**

## 9.4 📖 再讲原理（三）：类之间的六种关系（**必考，按强弱排**）

**耦合强度从弱到强**：**依赖 < 关联 < 聚合 < 组合 < 泛化（继承）/ 实现**

| # | 关系 | 含义 | UML 画法 | 代码体现 |
|---|---|---|---|---|
| 1 | **依赖 Dependency** | **临时使用**，用完即走；一个类的变化可能影响另一个 | **虚线 + 箭头** | **方法参数**、**局部变量**、静态方法调用 |
| 2 | **关联 Association** | **长期持有**的结构化连接 | **实线**（可带箭头表示方向）+ 多重度 | **成员变量**（属性） |
| 3 | **聚合 Aggregation** | **整体-部分**，但**部分可以脱离整体独立存在** | **空心菱形**（在整体一端）+ 实线 | 成员变量（弱拥有） |
| 4 | **组合 Composition** | **整体-部分**，**部分生命周期依赖整体**（同生共死） | **实心菱形**（在整体一端）+ 实线 | 成员变量（强拥有，整体销毁部分也销毁） |
| 5 | **泛化（继承）Generalization** | **父类 ↔ 子类**（is-a） | **实线 + 空心三角**（三角指向父类） | `extends` |
| 6 | **实现 Realization** | **接口 ↔ 实现类** | **虚线 + 空心三角**（三角指向接口） | `implements` |

> 🔥 **四大辨析（本章的丢分重灾区）**：

| 辨析 | 关键区别 |
|---|---|
| **依赖 vs 关联** | **依赖 = 方法参数/局部变量（临时、用完即走）**；**关联 = 成员变量（长期持有）**。案例改错题常把"依赖"误画成"关联"，导致**耦合度分析错误** |
| **聚合 vs 组合** | 看**部分能否脱离整体独立存在**：能 = **聚合（空心菱形）**；不能（同生共死）= **组合（实心菱形）** |
| **泛化 vs 实现** | **泛化 = 类继承类**（实线空心三角）；**实现 = 类实现接口**（虚线空心三角） |
| **关联的多重度** | `1`（恰好一个）、`0..1`（零或一个）、`*`/`0..*`（零或多个）、`1..*`（一个或多个） |

**生活例子巩固**：

| 例子 | 关系 |
|---|---|
| 人 **使用** 电脑（人调用电脑的方法，电脑是参数传进来的） | **依赖** |
| 老师 **教** 学生（长期关系） | **关联** |
| 汽车 **与** 轮胎（轮胎拆下来还能装到别的车上） | **聚合** |
| 人 **与** 心脏（人没了心脏也没了） | **组合** |
| 学生/老师 **都是** 人 | **泛化** |
| 汽车 **实现** "可驾驶"接口 | **实现** |

## 9.5 🎯 怎么考 + ✍️ 怎么答

**典型问法（真题改编 3 原题）**：

> **题干**：组员对 UML 图有以下说法：
> ① 用例图描述参与者与系统的交互以及系统功能需求；
> ② 顺序图描述对象之间消息传递的时间顺序；
> ③ 活动图描述对象在其生命周期内的状态变化；
> ④ 状态机图描述业务流程的分支与循环；
> ⑤ 类图描述系统中的类、类的属性与方法以及类之间的关系；
> ⑥ 部署图描述软件构件在硬件节点上的部署情况。
>
> 设计阶段发现：订单处理函数中**同时完成了金额计算、库存扣减、短信通知和日志记录**。
>
> 【问题 1】（9 分）判断上述 ①~⑥ 说法是否正确，错误的请改正。
> 【问题 2】（8 分）请指出该订单函数存在的问题并给出改进方案。
> 【问题 3】（8 分）请说明内聚与耦合的含义及设计原则。

**【问题 1】参考答案**：

> ① **正确**。用例图用于描述**参与者（Actor）与系统之间的交互**以及系统提供的**功能需求**。
> ② **正确**。顺序图（时序图）用于描述**对象之间消息传递的时间先后顺序**。
> ③ **错误**。**活动图**描述的是**业务流程/工作流，包括分支、并发（分叉与汇合）与循环**，类似于流程图；**描述对象生命周期内状态变化的是状态机图**。
> ④ **错误**。**状态机图**描述的是**单个对象**在其生命周期内**由于事件触发而导致的状态变迁**；**描述业务流程分支与循环的是活动图**。
> ⑤ **正确**。类图描述系统中的**类、类的属性与方法以及类之间的关系**，属于静态结构图。
> ⑥ **正确**。部署图描述**软件构件在硬件节点上的部署情况**以及节点之间的通信连接。

**【问题 2】参考答案**：

> **存在的问题**：
> 该函数**同时承担了金额计算、库存扣减、短信通知、日志记录四项职责**，属于**职责过多、职责不单一**，导致：
> ① **内聚性低**（函数内部各功能之间联系松散，属于**逻辑内聚/偶然内聚**）；
> ② **耦合度高**（与库存、短信、日志等多个模块直接依赖）；
> ③ 可维护性差：任一功能变更都要修改该函数，易引入缺陷；
> ④ 可测试性差：测试金额计算逻辑需连带构造库存、短信、日志环境；
> ⑤ 可复用性差：各功能无法单独复用。
>
> **改进方案**：
> ① **职责拆分**：按**单一职责原则**将函数拆分为**金额计算模块、库存扣减模块、消息通知模块、日志记录模块**，各自内聚、接口清晰；
> ② **异步解耦**：将**短信通知**与**日志记录**等非核心、非实时的操作**改为异步处理**（通过**事件机制 / 消息队列 / 观察者模式**发布"订单已处理"事件，由订阅方各自处理），**降低模块间的同步耦合**；
> ③ **引入中间件/接口层**：模块间通过**稳定接口**通信，降低直接依赖；
> ④ 最终实现**高内聚、低耦合**，提升系统的**可修改性、可测试性与可维护性**。

**【问题 3】参考答案**：见第 11 章。

## 9.6 ⚠️ 丢分点

- ❌ **活动图与状态机图说反** → **活动图 = 业务流程/工作流；状态机图 = 单个对象的状态变化**。这是**最高频错误**，务必背死。
- ❌ **include / extend 箭头方向画反** → **include 指向被包含者，extend 指向基础用例**。
- ❌ **依赖与关联混淆** → **依赖 = 方法参数/局部变量（虚线箭头）；关联 = 成员变量（实线）**。
- ❌ **聚合与组合混淆** → **空心菱形 = 聚合（部分可独立存在）；实心菱形 = 组合（同生共死）**。
- ❌ **忽略多重度** → 类图题中常要求标注 `1`、`0..*`、`1..*`，漏写扣分。
- ❌ **把"用例图"归为静态结构图** → UML 2.x 中用例图属于**行为图**（描述系统的功能行为）。
- ❌ **顺序图与通信图不分** → **顺序图强调时间顺序；通信图强调对象间的结构关系（链接）**。
- ❌ **部署图与构件图不分** → **部署图 = 软件装在哪些硬件节点上**；**构件图 = 软件构件之间的依赖关系**。

# 第 10 章 系统切换：给飞行中的飞机换引擎

## 10.1 🧊 先建立直觉：老店换新收银台

一家开了十年的超市要换新收银系统。三种换法：

| 换法 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **直接切换** | 今晚打烊时把旧的拆了装新的，明早直接用新的 | **省钱省事** | 明早新系统一崩，**整个超市没法结账** |
| **并行切换** | **新旧两套系统同时跑一个月**，每天对账，确认无误再拆旧的 | **最保险**，旧系统是天然的备份 | **员工要录两遍**，累死，成本翻倍 |
| **分段切换** | **先换食品区，再换日用品区，最后换生鲜区** | 折中，出问题只影响一个区 | 需要**新旧系统能共存对接**，协调复杂 |

> **一句话直觉：切换方案的本质是在"切换成本"和"业务中断风险"之间权衡。**
> **核心判断依据：这个系统停了，会造成多大损失？**

## 10.2 📖 再讲原理：三种切换方案

### ① 直接切换（一次性切换）

- **做法**：在**某一时刻**旧系统停止运行，直接启用新系统。
- **优点**：**成本最低**、操作简单、人员投入少。
- **缺点**：**风险最高**；新系统一旦出现严重故障**没有退路**，会造成业务中断。
- **适用**：**小型、非核心、低风险**的系统（如内部公告系统、小型工具类系统）。

### ② 并行切换

- **做法**：**新旧系统同时运行一段时间**（并行期），持续**比对结果**，确认新系统正确无误后再关停旧系统。
- **优点**：**风险最低**，旧系统作为**备份**随时可回退；可通过**结果比对验证**新系统的正确性。
- **缺点**：**成本最高**（需维护两套系统、两套数据），**工作量翻倍**，人力成本高；并行期数据同步复杂。
- **适用**：**核心、重要、不能中断**的业务系统（**银行、证券、社保、政务、电力、医院**）。

### ③ 分段切换（试点/逐步切换）

- **做法**：**分模块、分部门、分区域、分批次**逐步上线（如先试点一个部门/一条产线，再推广）。
- **优点**：**风险与成本折中**；问题影响面小，可在试点中**积累经验、完善系统**；用户有适应过程。
- **缺点**：**周期长**；新旧系统需在过渡期**共存并交换数据**，接口与协调复杂；整体管理难度大。
- **适用**：**大型、复杂、跨多部门**的系统；有明确试点条件的系统（先一条产线、先一个分公司）。

### 三种方案对比表（必背）

| 切换方案 | 风险 | 成本 | 适用场景 |
|---|---|---|---|
| **直接切换** | **高** | **低** | 小型、非核心、可容忍短暂中断的系统 |
| **并行切换** | **低** | **高**（双倍工作量） | 银行、证券、社保、政务等核心系统 |
| **分段切换** | **中等** | **中等** | 大型复杂系统、可分批推广的系统 |

> 🔥 **回退策略 Rollback（原文强调的标准采分点）**：
> **无论采用哪种切换方式，答案末尾都必须补一句：**
> "**必须提前制定完善的回退计划（Rollback Plan）**，明确回退**触发条件**、**回退步骤**与**责任分工**，确保新系统出现致命故障时能在**X 分钟/小时**内切回旧系统，保障业务连续性。"
>
> 同时建议补充：**数据迁移方案与数据校验**、**切换演练**、**切换窗口选择（业务低峰期）**、**切换后的监控与应急响应**。

## 10.3 🎯 怎么考 + ✍️ 怎么答

**典型问法（真题改编 7 原题）**：

> **题干**：某市社保系统升级，涉及**社保缴纳、查询、待遇发放**等核心业务，**系统中断将造成严重社会影响**。项目组提出直接切换、并行切换、分段切换三种方案。
>
> 【问题 1】（10 分）请分别分析三种切换方案的优缺点。
> 【问题 2】（8 分）给出该社保系统推荐的切换方案并说明理由。

**【问题 1】参考答案**：

> **① 直接切换**
> **优点**：实施简单，**人力与成本最低**，不需要同时维护两套系统。
> **缺点**：**风险最高**；新系统一旦发生故障**没有旧系统兜底**，将直接导致业务中断；适用于小型非核心系统。
>
> **② 并行切换**
> **优点**：**风险最低**；新旧系统同时运行，新系统出现问题时旧系统仍可继续对外提供服务，起到**备份与兜底**作用；可通过**新旧系统结果比对**验证新系统的正确性。
> **缺点**：需要**同时维护两套系统**，**工作量翻倍**，**人力与成本最高**；并行期间的数据同步与核对复杂。
>
> **③ 分段切换**
> **优点**：**风险与成本折中**；可按模块/部门/区域逐步上线，故障**影响范围可控**；可在试点阶段**发现问题并完善系统**，用户有适应过程。
> **缺点**：**切换周期长**；新旧系统在过渡期需**共存并交换数据**，接口与协调复杂；整体管理难度大。

**【问题 2】参考答案**：

> **推荐：并行切换方案。**
>
> **理由**：
> ① 社保系统承载**社保缴纳、查询、待遇发放**等**核心民生业务**，一旦中断将造成**严重的社会影响**，属于**不可中断的关键业务系统**；
> ② 并行切换**风险最低**，旧系统作为**备份**持续可用，新系统出现严重故障时可**立即切回旧系统**，最大限度**降低上线失败带来的业务风险与社会影响**；
> ③ 可通过**新旧系统业务结果比对**，验证新系统在待遇计算、账务处理等关键逻辑上的**正确性**，这对涉及资金发放的社保系统尤为重要；
> ④ 虽然并行切换**成本最高、工作量翻倍**，但相对于社保业务中断的**巨大社会代价**，该成本是**值得且必要**的。
>
> **补充措施（必须写，通常有分）**：
> ① 必须提前制定**完善的回退计划（Rollback Plan）**，明确回退触发条件、操作步骤与责任人，确保新系统出现致命故障时能在**最短时间内切回旧系统**；
> ② 制定完整的**数据迁移与数据校验方案**，确保历史数据完整、准确地迁移到新系统，并进行一致性核对；
> ③ 切换窗口选择**业务低峰期**（如节假日、夜间），并提前**发布公告**告知市民；
> ④ 切换前进行**切换演练**，切换后加强**运行监控**与**技术支持值班**。

> 💡 **变式**：若题干改为"某大型集团 ERP 系统，跨 20 个分公司，无法承担双倍人力成本"，则答案倾向于**分段（试点）切换**——先选 1~2 个分公司试点，成熟后推广。

## 10.4 ⚠️ 丢分点

- ❌ **说"并行切换风险高"** → 恰恰相反，**并行切换风险最低**（旧系统兜底），只是**成本高**。
- ❌ **忘记写回退计划** → 这是**标准采分点**，任何切换题都必须在末尾补上。
- ❌ **只分析优缺点不给推荐结论** → 案例题第二问通常要求"**给出推荐方案并说明理由**"，缺结论扣分。
- ❌ **推荐方案不考虑业务重要性** → **核心业务（银行/社保/政务/生产）→ 并行或分段**；**小型非核心 → 直接**。
- ❌ **漏掉数据迁移** → 切换必然涉及历史数据迁移，写上"**数据迁移 + 数据校验**"是加分项。
- ❌ **分段切换写成"分时间段"** → 分段切换是**按模块/部门/区域分批**，不是按时间分批。

# 第 11 章 内聚与耦合：厨房分工学

## 11.1 🧊 先建立直觉：餐厅后厨怎么分工？

**好的分工**：洗菜的只管洗菜，切菜的只管切菜，炒菜的只管炒菜。**每个人职责单一、内部紧密配合**（**高内聚**），**彼此只通过"把菜递过去"这一个简单接口交互**（**低耦合**）。

**糟糕的分工**：一个人"顺便"干洗菜、切菜、炒菜、端盘子、记账 —— 他一请假，整个后厨停摆。

换成软件：

- **内聚（Cohesion）**：**一个模块内部**各元素之间联系有多紧密。**越高越好。**
- **耦合（Coupling）**：**模块与模块之间**的依赖有多强。**越低越好。**

> **设计目标（必背）：高内聚，低耦合。**
> **为什么？** 高内聚 → 改一个功能只动一个模块；低耦合 → 改这个模块不会连累别的模块。
> **最终目的：提升【可修改性/可维护性】，同时提升可测试性与可复用性。**

## 11.2 📖 再讲原理（一）：内聚七级（**从优到差，背死**）

> ⚠️ **顺序非常重要**，选择题和判断题都考排序。

| 排名 | 内聚类型 | 定义 | 例子 |
|---|---|---|---|
| 1（**最高**） | **功能内聚** | 模块内所有元素**共同完成且仅完成一个功能** | "计算个人所得税"模块 |
| 2 | **顺序内聚** | 模块内各处理元素**顺序执行**，**前一个的输出是后一个的输入** | "读入数据 → 校验 → 计算"，且都在同一模块 |
| 3 | **通信内聚** | 模块内各元素**操作同一数据集（同一输入/输出）** | 对同一张表的"增删改查"放在一个模块 |
| 4 | **过程内聚** | 模块内元素**按特定次序执行**，但**未必共享数据** | 一个"初始化模块"依次初始化 A、B、C（彼此无关） |
| 5 | **时间内聚** | 模块内元素**在同一时间内执行**（因时间关系被放一起） | "系统启动时执行的初始化模块" |
| 6 | **逻辑内聚** | 模块内元素**逻辑上相似**，由参数决定执行哪一个 | "输出模块"，参数决定输出到打印机/屏幕/文件 |
| 7（**最低**） | **偶然内聚** | 模块内元素**之间没有任何联系**，纯属偶然放在一起 | 一个"工具箱"模块里放了日期格式化和字符串加密 |

> 💡 **记忆口诀（背）**：**功顺通过时逻偶**（功能 → 顺序 → 通信 → 过程 → 时间 → 逻辑 → 偶然）。
> 谐音故事："**功**夫**顺**利通过了，时间到了，逻辑就偶然出现了"。

## 11.3 📖 再讲原理（二）：耦合七级（**从优到差，背死**）

| 排名 | 耦合类型 | 定义 | 例子 |
|---|---|---|---|
| 1（**最低/最好**） | **无直接耦合**（非直接耦合） | 两模块**之间没有任何直接关系**，通过上级模块调用 | 两个完全独立的模块 |
| 2 | **数据耦合** | 模块间仅通过**简单数据参数**传递（值传递） | `func(int a, int b)` |
| 3 | **标记耦合**（特征耦合） | 模块间传递**数据结构（记录/对象）**，但只用到其中一部分 | 传整个"用户信息对象"，但只用其中一个字段 |
| 4 | **控制耦合** | 模块间传递**控制信息（标志/开关）**，**被调模块的逻辑受其控制** | 传一个 `flag`，被调函数根据 flag 走不同分支 |
| 5 | **外部耦合** | 模块**共同依赖同一外部环境**（如同一全局数据结构之外的外部设备、协议、文件格式） | 都依赖同一个文件格式或同一通信协议 |
| 6 | **公共耦合** | 多个模块**共享同一个公共数据区（全局变量/共享内存）** | 都读写同一个全局变量 |
| 7（**最高/最差**） | **内容耦合** | 一个模块**直接访问/修改另一个模块的内部数据**，或直接跳入其内部 | 直接 `goto` 到别的模块内部；直接改另一个模块的私有变量 |

> 💡 **记忆口诀（背）**：**无数标控外公内**（无直接 → 数据 → 标记 → 控制 → 外部 → 公共 → 内容）。
> 谐音故事："**无数**个**标**志被**控**制，**外**面的**公**共区域里**内**部被改了"。

> 🔥 **两个高频辨析**：
> - **标记耦合 vs 数据耦合**：传**简单参数** = 数据耦合；传**整个数据结构但只用了其中一部分** = 标记耦合。
> - **公共耦合 vs 外部耦合**：**公共耦合 = 共享全局数据区（全局变量）**；**外部耦合 = 共享外部环境（外部设备/文件格式/通信协议）**。

## 11.4 🎯 怎么考 + ✍️ 怎么答

**典型问法**：

> 【问题】（8 分）请说明内聚与耦合的含义，并说明软件设计应遵循的原则及其意义。
> 【变式】（10 分）请分析下列模块设计属于哪种内聚/耦合类型，并给出改进建议。

**标准答案模板**：

> **含义**：
> ① **内聚**：指**一个模块内部**各元素（语句、处理元素）之间联系紧密程度的度量，**内聚性越高越好**。高内聚意味着模块**职责单一**、功能完整。
> ② **耦合**：指**模块与模块之间**相互依赖程度的度量，**耦合性越低越好**。低耦合意味着模块间接口简单、相互影响小。
>
> **设计原则**：**高内聚、低耦合**。
>
> **意义（写全 4 条）**：
> ① **提高可修改性/可维护性**：变更被**局部化**在单个模块内，修改一个模块不影响其他模块，降低**连锁反应（涟漪效应）**；
> ② **提高可测试性**：模块职责单一、依赖简单，便于独立测试与缺陷定位；
> ③ **提高可复用性**：高内聚的功能模块可在其他系统中复用；
> ④ **降低系统复杂度**：模块边界清晰、接口明确，便于**分工协作**与理解维护。
>
> **改进措施**：
> ① 按**单一职责原则**拆分**职责过多**的模块（如将"计算+扣库存+发短信+记日志"拆分）；
> ② **信息隐藏**，通过**稳定的接口**通信，减少模块间的直接依赖；
> ③ 减少**公共耦合**（少用全局变量），避免**内容耦合**；
> ④ 对非核心、非实时的功能采用**事件机制/消息队列**异步解耦；
> ⑤ 引入**中间件/接口层/适配器**降低模块间的直接依赖。

## 11.5 ⚠️ 丢分点

- ❌ **内聚七级顺序记反** → 内聚是"**越高越好**"，**功能内聚最高，偶然内聚最低**。
- ❌ **耦合七级顺序记反** → 耦合是"**越低越好**"，**无直接耦合最好，内容耦合最差**。
- ❌ **把"时间内聚"当高内聚** → 时间内聚排第 5，**偏低**。只有"**功能内聚**"才是最高。
- ❌ **混淆公共耦合与外部耦合** → **公共 = 全局数据区；外部 = 外部环境/设备/协议**。
- ❌ **只写"高内聚低耦合"六个字** → 必须说明**含义 + 原则 + 意义（至少 3 条）**。
- ❌ **改进措施太笼统** → 要写**单一职责拆分、信息隐藏、减少全局变量、事件机制异步解耦**等具体手段。
- ❌ **漏掉与"可修改性"的关联** → 高内聚低耦合的**最终目的是提升可修改性/可维护性**，答到这一点才完整。

# 第 12 章 补丁知识点（防冷门，各 2~4 分）

> 这些点冷门但**一旦考到就是白送分**，花 20 分钟过一遍性价比极高。

## 12.1 McCabe 环路复杂度（高频计算点）

**它是什么**：衡量程序**逻辑复杂程度**的度量。值越大，程序越复杂、越难测试维护。
**另一个含义**：**V(G) = 独立路径数 = 至少需要的测试用例数（实现语句覆盖/路径覆盖的最少用例数）。**

**三种算法（背）**：

| 公式 | 说明 |
|---|---|
| **V(G) = 判定节点数 + 1** | **最常用**；判定节点 = `if`、`while`、`for`、`case`、条件表达式 |
| **V(G) = E − N + 2** | E = 流图中的**边数**，N = **节点数** |
| **V(G) = 封闭区域数 + 1** | 数流图被线条围成的**封闭区域**个数 |

**例题（真题改编 4）**：

> 某程序段有两个判定：`if (x>0 && y>0)` 和 `if (z>10)`，求环路复杂度及至少需要的测试用例数。

**答案**：

> **V(G) = 判定节点数 + 1 = 2 + 1 = 3**
> 因此该程序段包含 **3 条独立路径**，**至少需要 3 个测试用例**才能实现路径覆盖。

> ⚠️ **口径提醒**：`if (x>0 && y>0)` 是**一个**判定语句，但包含**两个**简单条件。
> **考试默认按"判定语句个数 + 1"计算**（本题 = 3）。
> 若题目明确要求"**按简单条件计数**"（条件覆盖口径），则为 `3 + 1 = 4`。**按题干要求走，默认用前者。**

## 12.2 DFD 数据流图平衡原则（常考找错）

**DFD 四要素**：

| 元素 | 图形 | 含义 |
|---|---|---|
| **外部实体（数据源/终点）** | 矩形 | 系统之外的人或系统 |
| **加工（处理）** | 圆角矩形/圆 | 对数据的处理变换 |
| **数据存储** | 双横线/开口矩形 | 存放数据的地方（表、文件） |
| **数据流** | 箭头 | 数据的流向 |

**三大平衡/正确性规则（找错题的标准答案）**：

1. **父图与子图平衡**：**父图中某个加工的输入/输出数据流**，必须与**该加工分解后的子图的输入/输出数据流完全一致**（数量与名称都要对上）。**不一致即为错误点。**
2. **加工的完整性**：每个加工**必须既有输入数据流，又有输出数据流**。
   - **黑洞**：**只有输入没有输出**
   - **奇迹**：**只有输出没有输入**
3. **数据存储与外部实体**：**数据不能直接在外部实体与数据存储之间流动**，必须经过**加工**处理。

**其他常见错误**：数据流**缺名称**或名称用了动词（数据流名应为**名词**）；加工**没有编号**或编号不规范；外部实体之间直接有数据流；数据流方向画反。

## 12.3 系统可靠性设计与计算（必考计算）

### 两个公式（背死）

| 系统类型 | 可靠度公式 | 特点 |
|---|---|---|
| **串联系统** | **R = R₁ × R₂ × … × Rₙ** | 任一失效则整体失效；**串联越多，可靠性越低** |
| **并联系统（冗余）** | **R = 1 − (1−R₁) × (1−R₂) × … × (1−Rₙ)** | 任一可用则整体可用；**并联越多，可靠性越高** |

**例题**：两个子系统可靠度均为 0.9。
- 串联：R = 0.9 × 0.9 = **0.81**（**下降**）
- 并联：R = 1 − (1−0.9) × (1−0.9) = 1 − 0.01 = **0.99**（**上升**）

> **直觉：串联是"一环断全断"，并联是"多留几条命"。**

### 常用指标

| 指标 | 含义 | 公式 |
|---|---|---|
| **MTTF** | 平均无故障时间 | 系统**平均能正常运行多久** |
| **MTTR** | 平均故障修复时间 | 出故障后**平均多久能修好** |
| **MTBF** | 平均故障间隔时间 | **MTBF = MTTF + MTTR** |
| **可用性 A** | 可用时间占比 | **A = MTBF / (MTBF + MTTR)** = **MTTF / (MTTF + MTTR)** |

> ⚠️ **可用性公式别写反**：分子是"**能工作的时间**"（MTTF 或 MTBF）。

### 三种容错设计技术（必背辨析）

| 技术 | 做法 | 恢复方式 |
|---|---|---|
| **N 版本程序设计** | **多个版本同时运行**，结果送**表决器**，少数服从多数 | **前向恢复**（继续往下走，不回退） |
| **恢复块方法** | **主块**执行，执行后做**接受测试**；不通过则切换到**备用块** | **后向恢复**（回退到执行前状态） |
| **防卫式程序设计** | 对**所有可能的错误**做预防性检查与处理 | 预防性 |

> **口诀：N 版本 = 同时跑 + 表决（前向）；恢复块 = 主失败换备（后向）。**
> **N 版本属于静态冗余，恢复块属于动态冗余。**

### 可靠性 vs 可用性（再次强调）

> **可靠性 = 一段时间内不出错的概率（别出错）**
> **可用性 = 一段时间内能工作的概率（能用，含故障后恢复）**
> **集群 Cluster 主要提升可用性；冗余 Redundancy 主要提升可靠性。**

## 12.4 信息安全与加密（简版）

| 算法类型 | 特点 | 代表算法 | 用途 |
|---|---|---|---|
| **对称加密** | 加解密**同一把密钥**，**速度快**，适合大量数据 | **DES、3DES、AES、RC-5、IDEA** | 加密**数据本身** |
| **非对称加密** | **公钥加密、私钥解密**（或反之），**速度慢** | **RSA、ECC、ElGamal** | 加密**密钥**、**数字签名** |
| **摘要/散列** | **不可逆**、定长输出，用于完整性校验 | **MD5、SHA-1、SHA-256**、国密 **SM3** | **完整性**校验 |

**数字签名（高频考点）**：

- **做法**：发送方用**自己的私钥**对摘要加密（签名）；接收方用**发送方的公钥**解密验证。
- **作用（背三条）**：**防篡改（完整性）、防抵赖（不可否认性）、身份认证**。
- 🔥 **注意：数字签名不能保证数据的机密性**（因为任何人都能用公钥解开签名，只是不能伪造）。

**数字信封**：

- **做法**：① 用**对称密钥**加密**数据本体**（快）；② 用**接收方的公钥**加密**该对称密钥**（安全）。
- **目的**：**兼顾对称加密的效率与非对称加密的密钥分发安全性**。

> ⚠️ **丢分点**：把"数字签名"说成能保证机密性 → 错！**保证机密性靠加密，数字签名只保证完整性、不可否认与身份认证。**

## 12.5 高并发与分布式（软件工程视角的踩分词）

> 📌 本章内容与 `10-分布式、云原生与集成架构.md` 有重叠，**此处只给"软件工程案例"里最常出现的踩分词**，深度学习请移步 10 号文件。

**高并发三件套**：**负载均衡（Nginx/F5/DNS 轮询）→ 缓存（Redis）→ 消息队列 MQ（异步、削峰填谷、解耦）**；数据库层面 **读写分离 + 分库分表**。

**缓存三大坑（必考，年年出）**：

| 问题 | 一句话 | 解决方案 |
|---|---|---|
| **缓存穿透** | 查询**根本不存在**的数据，绕过缓存直击 DB | **布隆过滤器**、**缓存空对象（短 TTL）**、参数校验、限流 |
| **缓存击穿** | **某个热点 Key** 失效瞬间，高并发直击 DB | **热点 Key 永不过期**、**互斥锁重建缓存**、逻辑过期、缓存预热 |
| **缓存雪崩** | **大量 Key 同时失效**或缓存服务整体宕机 | **过期时间加随机值**打散、**多级缓存**、缓存预热、**限流降级**、Redis 高可用集群 |

**CAP 与 BASE**：

- **CAP**：**一致性 C、可用性 A、分区容错性 P**，三者**最多同时满足两项**。
  - **关键结论**：**P 不可放弃**（网络一定会出问题），实际只能在 **CP** 与 **AP** 之间选择。
  - **CP**：银行账务、ZooKeeper；**AP**：电商、社交（最终一致）。
- **BASE**：**基本可用 BA、软状态 S、最终一致性 E** —— CAP 中 **AP 方案的延伸**，大型互联网系统常用。

# 第 13 章 综合实战：一道完整大题走一遍全流程

## 13.1 真题（综合模拟：某制造企业 MES 系统）

> **题干**：
> 某制造企业计划建设 **MES（制造执行系统）**，功能包括：生产计划管理、工单管理、质量追溯、设备数据采集、报表统计。项目特点如下：
> 1. **各车间生产流程差异较大**，需求难以一次性明确；
> 2. 企业希望**尽快在一条产线上试点上线**；
> 3. 系统需与**设备接口、质检系统、ERP 系统**集成，集成风险较高；
> 4. 工期 **9 个月**，预算 **600 万元**；
> 5. **上线不能影响正常生产**，数据必须准确可追溯；
> 6. 项目组部分成员**没有 MES 项目经验**。
>
> 项目执行到第 **5 个月末**检查，数据为：**PV = 300 万元，EV = 240 万元，AC = 280 万元。**

| 问题 | 分值 |
|---|---|
| 【问题 1】请说明该项目适合采用哪种开发模型，并说明理由。 | 8 分 |
| 【问题 2】请用挣值分析法分析项目当前状态，计算 CV、SV、CPI、SPI。 | 9 分 |
| 【问题 3】请针对该项目的主要风险给出应对措施。 | 8 分 |

## 13.2 ① 审题：划线索（3 分钟，这步不能省）

| 题干原话 | 翻译成技术语言 | 指向的考点 |
|---|---|---|
| "各车间生产流程差异较大，需求难以一次性明确" | **需求不确定** | **快速原型模型** |
| "**尽快在一条产线上试点上线**" | **分批交付、试点** | **增量模型**（+ **分段切换**） |
| "需与设备接口、质检、ERP 集成，**集成风险较高**" | **高风险** | **螺旋模型**（风险分析）；**风险管理** |
| "上线不能影响正常生产" | **核心业务不能中断** | **并行/分段切换 + 回退计划** |
| "部分成员没有 MES 项目经验" | **人员风险** | **风险减轻**（培训、老带新、引入专家） |
| "PV=300，EV=240，AC=280" | **超支 + 滞后** | **EVM 计算 + 纠偏措施** |

> 💡 **这道题的题眼**：**三个问题分别对应三个不同模块**（开发模型 + EVM + 风险管理）。
> 命题人想看的是：你会不会把**题干的每一句话都"翻译"成对应的知识点**。
> **审题技巧：边读边在草稿纸上把题干拆成"考点清单"，写完对着清单逐条确认，绝不漏点。**

## 13.3 ② 配分规划（决定写多少）

- **8 分题** → 写 **2~3 个要点**，每个要点配**题干理由**；
- **9 分题** → 写公式 + 计算 + 判断 + 措施，**四个步骤缺一不可**；
- **8 分题（风险）** → **至少覆盖 3 类风险**，每类给 **2 条具体措施**。

**经验公式**：**1 分 ≈ 1 个要点 ≈ 1~1.5 行字**。8 分的题写到 8~12 行比较合适。

## 13.4 ③ 参考答案

### 【问题 1】（8 分）

> 建议采用**增量模型为主、结合快速原型与螺旋风险分析的混合模型**。
>
> **理由**：
> ① **采用增量模型**：MES 系统包含生产计划、工单管理、质量追溯、设备采集、报表统计等**相对独立的业务模块**，适合**按模块分批交付**；企业希望"**尽快在一条产线上试点上线**"，增量模型可使**核心功能优先交付**，让用户**较早获得可用系统**，并**分散风险**、尽早验证系统价值。
> ② **结合快速原型**：由于"**各车间生产流程差异较大，需求难以一次性明确**"，对需求模糊的模块（如各车间的工艺流程配置、质量追溯规则）应**先构造快速原型**与各车间用户反复确认，澄清需求后再正式开发，避免后期大量返工。
> ③ **引入螺旋模型的风险分析环节**：系统需与**设备接口、质检系统、ERP** 集成，**集成风险较高**，应在每个增量迭代中**设置风险分析环节**，提前识别与应对集成风险（如提前联调、接口契约约定）。
> ④ **增量模型的前提**：增量模型要求系统具备**开放的体系结构**，本项目应在架构设计阶段**重点设计模块间的稳定接口**，保证后续增量可平滑接入。
>
> **补充**：若采用敏捷思想，可在每个增量内采用 **Scrum 迭代**，每 2~4 周交付一个可用增量，配合 PO 排序需求优先级，进一步加快反馈。

### 【问题 2】（9 分）

> **已知**：BAC = 600 万元，PV = 300 万元，EV = 240 万元，AC = 280 万元。
>
> **① 计算偏差**：
> - **CV = EV − AC = 240 − 280 = −40（万元）**
>   → **CV < 0，项目成本超支**（完成 240 万元的工作量，实际花费了 280 万元）。
> - **SV = EV − PV = 240 − 300 = −60（万元）**
>   → **SV < 0，项目进度滞后**（按计划应完成 300 万元的工作量，实际只完成 240 万元）。
>
> **② 计算绩效指数**：
> - **CPI = EV / AC = 240 / 280 ≈ 0.857**
>   → **CPI < 1，成本超支**，即**每支出 1 元只挣得 0.857 元的价值**，成本使用效率约为 85.7%。
> - **SPI = EV / PV = 240 / 300 = 0.8**
>   → **SPI < 1，进度滞后**，即**实际完成进度仅为计划进度的 80%**。
>
> **③ 状态结论**：项目当前处于**成本超支 + 进度滞后**的不利状态，且**两项指标明显偏离计划**，需要**立即采取纠偏措施**。
>
> **④ 完工预测（典型偏差）**：
> **EAC = BAC / CPI = 600 / 0.857 ≈ 700（万元）**
> （或严谨式：EAC = AC + (BAC − EV) / CPI = 280 + (600 − 240) / 0.857 ≈ 280 + 420 = 700 万元）
> → 预计**完工将超支约 100 万元**（VAC = BAC − EAC = 600 − 700 = −100 万元）。
>
> **⑤ 纠偏措施**：
> ① **赶工**：对**关键路径**上的任务增加资源（增派人员、适度加班），以成本换取进度；
> ② **快速跟进**：将原本串行的任务（如部分模块的设计与开发）改为并行，**不增加成本但会增加返工风险**；
> ③ **缩减范围**：与甲方沟通，将**非核心功能（如报表统计的高级分析）移至下一期**，优先保证试点产线的核心功能按期上线；
> ④ **优化资源配置**：将**有经验的骨干投入关键路径**与集成联调任务，提升效率；
> ⑤ **改进方法**：引入**自动化测试、成熟构件与代码复用**，减少返工；
> ⑥ **加强监控**：缩短监控周期，**加强变更控制**，防止范围蔓延导致成本与进度进一步恶化。
>
> ⚠️ 需注意：**赶工会增加成本，快速跟进会增加风险**，须结合项目实际情况权衡。

### 【问题 3】（8 分）

> ① **需求风险**（车间流程差异大、需求不明确）
> - **减轻**：采用**快速原型**与用户反复确认；建立**需求基线**与**变更控制流程（CCB）**，所有变更须经**影响分析**与审批；使用**需求跟踪矩阵**防止需求遗漏。
>
> ② **集成风险**（设备接口、质检系统、ERP 集成）
> - **减轻**：**提前开展接口联调**与**压力测试**；明确**接口契约**并做**版本管理**；引入**重试、熔断、降级**机制；建立**监控告警**；
> - **转移**：在合同中约定**第三方系统配合的条款与违约责任**；
> - **规避**：对技术不成熟或响应不力的供应商，及时**更换或调整集成方案**。
>
> ③ **人员风险**（部分成员无 MES 经验）
> - **减轻**：开展 **MES 业务培训**；采用**老带新/结对**方式；引入**外部领域专家**；建立**知识沉淀机制**（设计文档、接口文档、运行手册）；实行**关键模块 AB 角**与**代码评审**。
>
> ④ **进度与成本风险**（已出现超支滞后）
> - **减轻**：采取**赶工、快速跟进、优化资源配置、改进方法**等措施纠偏；
> - **接受**：在计划中**预留应急储备（时间与资金）**，并制定**应急预案**。
>
> ⑤ **上线风险**（不能影响正常生产）
> - **减轻**：采用**分段（试点）切换**——**先在一条产线试点上线**，验证稳定后再推广到其他产线；或对新旧系统关键数据采用**并行运行+结果比对**。
> - **必须制定完善的回退计划（Rollback Plan）**：明确回退触发条件、操作步骤与责任人，确保新系统出现致命故障时能在最短时间内切回原方式，保障生产不中断；
> - 制定**数据迁移与校验方案**，确保历史生产数据完整、准确迁移并可追溯；切换窗口选择**停产检修期/业务低峰期**。

## 13.5 ④ 失分陷阱复盘

| 陷阱 | 说明 |
|---|---|
| ❌ 只写"增量模型"四个字 | 本题的**理由**才是主体分数，必须**逐条对应题干**（试点→增量、需求模糊→原型、集成风险→螺旋风险分析） |
| ❌ 漏掉"增量模型要求开放的体系结构" | 这是增量模型的**隐性必答点** |
| ❌ EVM 只写结果不写公式 | **公式与步骤都是分**，算错也能拿步骤分 |
| ❌ CV / SV 的正负号判断反 | 记住"**小于 0 = 不好**" |
| ❌ EVM 算完就收笔 | **必须给状态结论 + 纠偏措施**，这部分通常占一半分 |
| ❌ 纠偏措施写"加强管理" | 必须写**赶工/快速跟进/缩减范围/优化资源/改进方法** |
| ❌ 风险措施太笼统 | 措施要**对应具体风险**（接口→联调/熔断/降级；人员→培训/AB角/老带新） |
| ❌ 上线风险漏写回退计划 | **回退计划是标准采分点**，必写 |

## 模板 2 · 需求变更控制

```
该做法不合适。开发人员未经评审直接修改代码，违反【需求变更控制流程】，
导致需求基线失去约束力，可能引发需求蔓延与项目失控。
正确流程：①提交变更申请 → ②变更影响分析（范围/进度/成本/质量/架构/测试）
```

## 模板 3 · 需求分类


## 模板 4 · 验证 vs 确认

```
验证 Verification：我们【正确地】构建产品了吗？——关注是否符合规范与标准（SRS/设计文档），
```

## 模板 7 · 架构风格识别

```

  业务拆分、独立部署、HTTP/RPC通信 → 微服务
  上层调用下层方法、控制权在调用方 → 调用/返回风格
⚠️ 主程序-子程序、面向对象、分层架构【三者平级】，同属调用/返回风格。
```

## 模板 8 · 风险管理

```
风险 = 概率 × 损失（风险曝光度）。四步：识别 → 分析 → 规划（应对） → 监控。
① 规避：改变项目计划，消除风险或其产生条件（放弃某方案、更换外包商）
② 减轻：降低概率或影响，但事照做（冗余/重试/熔断/降级/备份/测试/AB角）
③ 转移：后果与责任转移给第三方（外包、保险、合同条款/质保金）
④ 接受：不主动改变计划，但制定应急预案 + 预留应急储备（时间/资金）
⚠️ 风险应对是【事前行动】；风险发生后的处理叫【应急措施】。
   应急储备 = 应对已识别风险（PM可动用）；管理储备 = 应对未识别风险（需高层批准）。
```

## 模板 9 · 挣值分析 EVM

```
已知：BAC=？，PV=？，EV=？，AC=？
CV = EV − AC = 〔 〕   → CV<0 成本超支（CV>0 节约）
SV = EV − PV = 〔 〕   → SV<0 进度滞后（SV>0 提前）
CPI = EV / AC = 〔 〕  → CPI<1 成本超支（每花1元只挣得CPI元）
SPI = EV / PV = 〔 〕  → SPI<1 进度滞后（完成计划的SPI比例）
EAC（典型）= BAC/CPI = AC + (BAC−EV)/CPI = 〔 〕
EAC（非典型）= AC + (BAC−EV) = 〔 〕
VAC = BAC − EAC = 〔 〕  → VAC<0 预计超支
TCPI = (BAC−EV)/(BAC−AC)  → 剩余工作需达到的效率
纠偏措施：①赶工（增成本）②快速跟进（增风险）③缩减范围（最实用）
        ④优化资源配置（骨干上关键路径）⑤改进方法（自动化测试/复用）
        ⑥加强监控与变更控制
```

## 模板 10 · 敏捷 Scrum

```
敏捷宣言：个体和互动 > 流程和工具；可工作软件 > 详尽文档；
        客户合作 > 合同谈判；响应变化 > 遵循计划。（右边仍有价值，"高于"非"取代"）
三角色：PO（管Product Backlog、定优先级、对价值负责）
       SM（服务型领导，移除障碍、保障流程、促进自组织）
       开发团队（自组织、跨职能，自行认领任务）
三工件：Product Backlog、Sprint Backlog、Increment（增量）
五事件：Sprint（2~4周，时间盒不可延长）、Sprint计划会、每日站会（15分钟/三句话）、
       Sprint评审会（对外演示、收集反馈）、Sprint回顾会（对内复盘、改进流程）
⚠️ SM【不是项目经理】，不分配任务、不考核绩效。
```

## 模板 11 · DevOps

```
DevOps 三大支柱（基础）：【人（文化，打破部门墙）】+【流程（精益）】+【工具（自动化）】。
CI 持续集成：频繁合并到主干 + 自动构建 + 自动测试，尽早发现集成错误。
CD 持续交付：随时处于可部署状态，手动一键发布。
CD 持续部署：自动化流水线自动发布到生产。
发布策略：蓝绿部署（双环境、回退快、资源翻倍）、金丝雀/灰度（小流量验证、风险可控）、
        滚动发布、特性开关（发布与功能上线解耦，可秒级关闭）。
DORA 四指标：部署频率、变更前置时间、MTTR（服务恢复时间）、变更失败率。
⚠️ DevOps ≠ CI/CD，务必补充"文化"与"自动化运维"。
```

## 模板 12 · CMMI

```
1级 初始级：混乱无序、不可预测、依赖个人英雄
2级 受管理级：项目级，有规划有跟踪、可重复
3级 已定义级：组织级标准化，所有项目采用组织标准过程
4级 定量管理级：量化数据度量与统计控制，过程可预测
5级 优化级：持续改进、主动预防缺陷、过程创新
口诀：2管项目、3管组织（标准化）、4管数据（量化）、5管改进（优化）。
⚠️ 第2级标准译名"受管理级"；第4级"定量管理级"，勿写"已管理级"。
   成熟度等级逐级递进，不可跨越。
```

## 模板 13 · UML 辨析

```
用例图：参与者与系统功能需求
类图：类、属性、方法、类之间关系（静态）
对象图：类图在某一时刻的实例快照
构件图：构件之间的组织与依赖
部署图：软件构件部署在哪些硬件节点上
顺序图（时序图）：对象之间消息交互的【时间先后顺序】
通信图：对象交互，【不强调】时间顺序
活动图：【业务流程/工作流】，分支、并发、泳道（像流程图）
状态机图：【单个对象】生命周期内状态变迁
🔥 口诀：顺序看先后，活动看流程，状态看自己。
用例关系：include → 指向【被包含】（必须执行）；extend → 指向【基础】（可选执行）
类关系（弱→强）：依赖 < 关联 < 聚合 < 组合 < 泛化/实现
  依赖=方法参数/局部变量（虚线箭头）；关联=成员变量（实线）
  聚合=空心菱形（部分可独立）；组合=实心菱形（同生共死）
  泛化=实线空心三角（继承）；实现=虚线空心三角（接口）
```

## 模板 14 · 系统切换

```
① 直接切换：成本最低、风险最高、无退路 → 小型非核心系统
② 并行切换：风险最低（旧系统兜底）、成本最高（工作量翻倍）→ 银行/社保/政务/核心系统
③ 分段切换（试点/逐步）：风险与成本适中、周期长、需新旧共存 → 大型复杂系统
判断依据：核心业务不可中断 → 并行或分段。
必写补充：【回退计划 Rollback Plan】（触发条件/步骤/责任人/回退时限）
         +【数据迁移与校验方案】+【切换窗口选业务低峰期】+【切换演练与监控】
⚠️ 并行切换风险【最低】不是最高。
```

## 模板 15 · 内聚耦合

```
内聚（模块内部，越高越好）：功能>顺序>通信>过程>时间>逻辑>偶然   【功顺通过时逻偶】
耦合（模块之间，越低越好）：无直接<数据<标记<控制<外部<公共<内容   【无数标控外公内】
原则：高内聚、低耦合。
意义：①提升可修改性/可维护性（变更局部化、减少连锁反应）
     ②提升可测试性 ③提升可复用性 ④降低系统复杂度，便于分工
改进：单一职责拆分、信息隐藏、稳定接口、减少全局（公共）耦合、
     事件机制/消息队列异步解耦、引入中间件/适配器
```

## 模板 16 · 找错改错题三段论（**拿满分必备，缺一段只给一半分**）

```
① 错误点：XXX 的说法/做法是错误的。（1分）
② 理由：根据 XXX 理论/原则/标准，应为 XXX。（1~2分）
③ 正确做法：应改为 XXX / 应增加 XXX 流程或机制。（1~2分）
```

## 模板 17 · 填空题"原词重现"原则

```
案例填空的答案常隐藏于题干，只需"翻译"成标准术语：
  "各构件独立运行、通过事件总线通信"        → 事件驱动（隐式调用）
  "数据依次流经各处理单元，每单元独立处理"  → 管道-过滤器
  "系统分核心层/业务层/UI层，上层调下层"    → 分层架构
  "多个构件共享中央数据仓库"                → 仓库风格
  "无确定解法、多知识源协同推理（AI）"      → 黑板系统
  "业务拆分为多个独立部署小服务"            → 微服务
⚠️ 尽量用标准术语，勿自创词汇。
```

# 第 15 章 十五大丢分点总清单

| # | 丢分点 | 正确表述 |
|---|---|---|
| 1 | **螺旋模型的核心是"原型迭代"** | 螺旋模型的**核心是风险分析**；四象限 = 制定计划→风险分析→实施工程→客户评估 |
| 2 | **可用性 = 性能** | **可用性 = 能持续可用多久/故障恢复多快（7×24、MTBF）**；**性能 = 快慢（响应、并发、吞吐）**，二者独立 |
| 3 | **Scrum Master 是项目经理，分配任务、考核绩效** | SM 是**服务者/障碍清除者**，**不分配任务、不考核**；团队**自组织** |
| 4 | **并行切换风险高** | **并行切换风险最低**（旧系统兜底），只是**成本最高** |
| 5 | **SV < 0 表示进度提前** | **SV = EV − PV，小于 0 = 进度滞后**；"**小于 0 / 小于 1 = 不好**" |
| 6 | **风险规避 = 放弃整个项目** | 规避 = **改变计划消除风险产生条件**（放弃某方案/**更换外包商**）；减轻 = 事照做 + 加防护 |
| 7 | **把"外包、买保险、签合同"写成减轻** | 那是**转移**（后果给第三方）；**重试/熔断/降级/冗余/备份/测试 = 减轻** |
| 8 | **把事后补救当风险应对** | 风险应对是**事前行动**；风险已发生后的处理 = **应急措施** |
| 9 | **活动图与状态机图说反** | **活动图 = 业务流程/工作流**；**状态机图 = 单个对象的状态变化**。口诀：**活动看流程，状态看自己** |
| 10 | **include / extend 箭头方向画反** | **include 指向被包含者**（基础→被包含，必须执行）；**extend 指向基础用例**（扩展→基础，可选） |
| 11 | **CMMI 第 4 级写成"已管理级"** | 第 2 级 = **受管理级**；第 4 级 = **定量管理级**。口诀：**2 管项目、3 管组织、4 管数据、5 管改进** |
| 12 | **把"部署环境/工期/预算"归为功能需求** | 它们是**设计约束**；"日志审计/并发/加密"是**非功能需求** |
| 13 | **只写收益不写代价 / 只写结论不写理由** | 看到"**分析/评价/说明**"就必须写**两面**；看到"**判断是否正确**"就必须写**错误点+理由+正确做法**三段 |
| 14 | **敏感点与权衡点判定错误** | **影响 1 个属性 = 敏感点；影响多个且此消彼长 = 权衡点**。所有权衡点都是敏感点，反之不然 |
| 15 | **质量属性场景漏写"响应度量"或写得不可量化** | 响应度量**必须含数字**（如"**90% 请求响应时间 < 2 秒**""**MTTR ≤ 30 分钟**"） |

**补充五个"表述安全"提醒**：

1. **"敏捷不需要文档"** → 错。宣言是"**高于**"不是"**取代**"，右侧内容仍有价值。
2. **"DevOps = CI/CD"** → 不完整。必须补"**文化（人）+ 精益流程 + 自动化运维**"。
3. **"微服务提升可扩展性"** → 精准说法是提升**可伸缩性（Scalability）与部署独立性**，且**必须写出代价**（分布式复杂度、网络延迟、运维成本）。
4. **"数字签名保证数据机密性"** → 错。数字签名保证**完整性、不可否认性、身份认证**，**不保证机密性**（机密性靠加密）。
5. **"增量模型不需要好的架构"** → 错。增量模型**要求开放的体系结构**，便于后续增量接入。
