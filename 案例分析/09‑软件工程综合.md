# 1 软件开发生命周期与过程模型
生命周期阶段：可行性分析 → 需求分析 → 概要设计 → 详细设计 → 编码实现 → 测试 → 部署实施 → 运维维护

## 1.1 瀑布模型
- 特点：阶段串行，一个阶段完成后才进入下一阶段；文档驱动。
- 优点：流程清晰、便于管理。
- 缺点：前期需求必须完整明确；后期修改代价巨大；不适用于需求频繁变更项目。
- 适用场景：需求稳定、变更少，例如军工、政府大型定制项目。

## 1.2 快速原型模型
- 先快速构造可运行原型，和用户反复确认需求；原型迭代优化后再开发最终产品。
- 适用场景：需求模糊、用户很难一次性说清需求。

## 1.3 增量模型
软件被拆分为多个增量构件；分批交付，每一个增量完成一部分功能。
优点：用户可以较早看到可用版本；风险分散。

## 1.4 螺旋模型
四个象限：制定计划 → 风险分析 → 执行工程 → 用户评估。
**核心特点：强调风险分析**。
适用：大型、高风险项目。

## 1.5 喷泉模型（面向对象）
迭代与无间隙；各阶段没有明显边界；面向对象项目。

## 1.6 V模型
测试活动与开发阶段一一对应；编码之前就制定测试方案。
单元测试 ↔ 详细设计；集成测试 ↔ 概要设计；系统测试 ↔ 需求分析；验收测试 ↔ 用户需求。

> 💡答题口诀：
> 需求稳定选瀑布；需求模糊用原型；分批交付选增量；高风险项目螺旋模型。
> 救场金句（无法判断模型时）：采用**混合模型**——总体增量分批交付，模糊模块用原型澄清需求，高风险模块引入螺旋风险分析环节。架构师考的是权衡与融合，不是单选。

# 2 需求工程
需求分为三大类：
1. **功能性需求**：系统必须完成什么功能；业务逻辑、功能特性。
2. **非功能性需求（质量属性）**：系统运行的品质指标，性能、安全性、可用性、可维护性等。
3. **约束需求**：技术、政策、硬件、预算等外部限制条件。

## 2.1 需求开发流程
需求获取 → 需求分析 → 需求规格说明书SRS编写 → 需求验证

## 2.2 需求管理
需求基线；需求变更控制流程；需求跟踪矩阵。
需求跟踪矩阵作用：跟踪需求是否被设计、编码、测试覆盖，防止需求遗漏。

## 2.3 需求验证与确认 V&V（高频辨析）
- **验证 Verification（我们正确地构建产品了吗？）**：检查文档、设计、代码是否符合规范与标准（评审、审查、原型）。
- **确认 Validation（我们构建了正确的产品吗？）**：用户验收，是否满足真实业务需求（验收测试、用户试用）。
> 口诀：验证看"做对了没"（符合规格），确认看"做对的东西没"（满足业务）。

# 3 软件架构与质量属性（案例最高频考点）
质量属性全部属于**非功能需求**，案例题最常考：识别质量属性；权衡取舍；给出优化方案。

### 3.1 六大核心质量属性
1. **性能 Performance**：系统响应速度、吞吐量、延迟。
    - 场景：页面打开慢、并发用户多时卡顿。
2. **可用性 Availability**：系统正常运行时间比例；故障后恢复速度。
    - 场景：服务宕机；需要7×24小时不间断运行；故障快速恢复。
    - 优化手段：集群、冗余、故障转移、双机热备。
3. **安全性 Security**：防止非法访问；数据加密；防攻击、权限控制。
4. **可修改性（可维护性）Modifiability**：快速低成本修改系统、新增功能。
    - 优化：低耦合高内聚、模块化、良好文档。
5. **可测试性 Testability**：便于开展测试、容易发现缺陷。
6. **易用性 Usability**：用户上手简单，操作体验好。

### 3.2 其他常考质量属性
- **可扩展性**：增加资源、增加业务功能时系统改动小；横向扩展、纵向扩展。
- **可靠性 Reliability**：长时间运行不出错；容错、故障隔离。

> ⚠️ 质量属性权衡（必考权衡考点）
几乎所有架构决策都是质量属性之间做取舍：
- 增加安全加密校验 → **安全性上升，性能下降**
- 增加集群冗余提升可用性 → **可用性上升，成本、复杂度上升**
- 模块拆分解耦提升可修改性 → **可维护性上升，性能略有下降**

> 💡答题万能权衡句：
> 该架构方案提升XX质量属性，但是会牺牲XX质量属性，需要进行权衡。
> 降维打击句：该方案通过引入X机制提升了Y属性，但由于增加了Z开销（如网络IO/加解密CPU消耗），导致T属性下降。这属于典型的敏感点与权衡点。

### 3.3 质量属性战术 Tactics（案例"给出优化方案"万能答案）
- **性能战术**：并行计算、资源池（线程池/连接池）、缓存、异步队列（削峰填谷）。
- **可用性战术**：心跳检测、主动/被动冗余（主备/双活）、状态镜像、故障恢复（Checkpoint/Rollback）。
- **安全性战术**：认证 Authentication、授权 Authorization、审计 Audit、加密 Encryption。
- **可测试性战术**：内置日志、接口 Mock、故障注入。
- **可修改性战术**：降低模块耦合（设计模式）、引入中间件解耦。

### 3.4 架构评估方法（ATAM / SAAM）⭐案例必考大题
- **SAAM（软件架构分析方法）**：最早的方法，主要评估可修改性、可扩充性。
- **ATAM（架构权衡分析方法）**：最常考。步骤：①场景收集（效用树）；②架构介绍；③场景分析（敏感点、权衡点）；④结果呈现。
- **四大核心概念**：
  - 敏感点：影响**某一个**质量属性的架构决策（如增加服务器数影响性能）。
  - 权衡点：影响**多个**质量属性的架构决策（如加密级别↑安全性↑但性能↓，加密级别即权衡点）。
  - 风险点：可能导致问题的架构决策（如单点故障）。
  - 非风险点：被确认良好的架构决策。
- **质量属性场景六要素（常考填空）**：刺激源（谁发出）、刺激（发生什么）、环境（什么状态下）、制品（系统哪部分）、响应（系统如何处理）、响应度量（用何指标衡量，如延迟<2秒）。
- **架构风险识别**：单点故障 SPOF（未冗余的DB/负载均衡）、技术异构过度（一套系统5种DB）、过度设计（小项目硬上微服务，成本>收益）。

> 💡质量属性识别万能法（秒杀填空）：
> 响应时间/吞吐量/并发/TPS/QPS → 性能；宕机/集群/MTBF/双机热备 → 可用性；
> 黑客/加密/越权/审计 → 安全性；新增功能/移植/解耦 → 可修改性；
> 测试覆盖率/Mock/注入 → 可测试性；新手培训/界面友好 → 易用性。

# 4 常见架构风格
1. **管道‑过滤器（数据流风格）**：每个过滤器独立处理数据；管道传递数据；例子：编译器。
2. **仓库风格（知识库）**：中央共享数据仓库，周围多个构件读写仓库；分为黑板系统、数据库系统。黑板系统适合不确定性问题，AI信号处理。
3. **分层架构**：上层调用下层；下层不能反向调用上层；解耦、可维护性高；过多层级带来性能损耗。
4. **事件驱动架构（隐式调用）**：构件发布事件；订阅者被动响应事件；松耦合；缺点：事件调试困难，事务难以控制。
5. **微服务架构**：业务拆分为多个独立部署小服务；服务之间通过RPC/HTTP通信。
    - 收益：独立迭代部署、可伸缩性 Scalability（针对特定服务扩容）、部署独立性；
    - 代价：分布式复杂度上升、服务调用延迟、分布式事务（数据一致性难保证）、运维复杂度急剧上升（需完善DevOps平台）、服务间通信增加网络延迟。
    > 注：微服务提升的是"可伸缩性/部署独立性"，并非绝对优于单体的"可扩展性(Extensibility)新增业务功能"。
6. **调用/返回风格（Call/Return）**：以下三者**平级**同属此风格，并非包含关系：
    - 主程序‑子程序：传统模块化调用；
    - 面向对象：对象方法调用；
    - 分层架构：上层调用下层（见第4点）。

# 5 风险管理
风险 = 风险发生概率 × 风险造成损失

## 5.1 风险管理四步
1. **风险识别**：列出所有潜在风险；风险清单。
2. **风险分析（风险评估）**：分析概率、影响、风险等级。
3. **风险规划（风险应对策略）**
    - 风险规避：放弃引发风险的方案；
    - 风险减轻：采取措施降低发生概率或损失；
    - 风险转移：转移给第三方，购买保险、外包；
    - 风险接受：接受风险后果，准备应急预案。
4. **风险监控**：项目全程跟踪风险状态。

> ❗高频坑点：风险应对是**事前行动**；风险发生之后进行处理叫**应急措施**。

# 6 项目进度、成本与挣值分析 EVM
挣值计算题属于软件工程选做题高频计算考点。
三个基础参数：
- PV：计划工作量的预算成本
- EV：已完成工作量的预算成本（挣值）
- AC：已完成工作量实际成本

## 评价指标
1. 成本偏差 CV = EV − AC
    - CV>0：成本节约；CV<0：成本超支
2. 进度偏差 SV = EV − PV
    - SV>0：进度提前；SV<0：进度滞后
3. 成本绩效指数 CPI = EV / AC
    - CPI>1成本节约；CPI<1成本超支
4. 进度绩效指数 SPI = EV / PV
    - SPI>1进度提前；SPI<1进度滞后

## 完工预测
- EAC完工估算 = BAC / CPI （典型偏差，未来绩效和当前一致）
- EAC = AC + (BAC‑EV)（非典型偏差，后续工作回归原计划效率）
- 统一记忆：**EAC = AC + ETC**，再分情况算ETC：
  - 典型偏差（未来按当前效率）：**ETC = (BAC‑EV) / CPI**
  - 非典型偏差（未来按原计划）：**ETC = BAC ‑ EV**
- **TCPI 完工绩效指数** = (BAC‑EV) / (EAC‑AC)：衡量剩余工作量需要多高效完成才能不超预算（冷门考点，近两年出现）。

> 💡答题模板：根据计算结果，项目当前成本超支/节约；进度滞后/提前；给出改进措施：
> ①赶工（加人/加班，增成本）；②快速跟进（串行改并行，增风险）；③使用高素质人才（降成本提质量）；
> ④改进技术/方法（引入自动化测试）；⑤削减范围（与甲方沟通，非核心功能放下一期）——最实用手段。

# 7 敏捷开发、Scrum、DevOps
## 7.1 敏捷宣言核心
个体和互动高于流程和工具；可工作软件高于详尽文档；客户合作高于合同谈判；响应变化高于遵循计划。

## 7.2 Scrum（最常考敏捷框架）
角色：
1. 产品负责人PO：管理产品待办列表Product Backlog，决定需求优先级；
2. Scrum Master：团队服务者、障碍清除者，不是项目经理；
3. 开发团队：自组织团队。

工件：
- 产品待办列表 PB；
- 迭代待办列表 Sprint Backlog；
- 增量（迭代产出可用软件）

事件：
- Sprint迭代（固定时长2‑4周）；
- 每日站会；
- Sprint评审会；
- Sprint回顾会。

## 7.3 DevOps
打通开发(Dev)‑测试‑运维(Ops)；目标持续交付、缩短上线周期；
- CI持续集成：开发频繁把代码合并到主干仓库，自动构建自动测试。
> ⚠️ 勘误：CI/CD 是技术实践，不是 DevOps 的全部。DevOps 三大支柱/核心基础是：**人（文化，打破部门墙）、流程（精益）、工具（自动化）**。答题时除 CI/CD 外，务必加"自动化运维"和"文化"。
> 💡 DORA 四大关键度量指标（2024‑2025新兴热点）：
> ①部署频率 Deployment Frequency；②变更前置时间 Lead Time for Changes；③服务恢复时间 MTTR；④变更失败率 Change Failure Rate。

# 8 CMMI软件能力成熟度模型
CMMI分为5个等级，逐级向上：
1. **初始级**：过程混乱无序，成功依靠个人能力。
2. **受管理级（Managed）**：项目层面过程有规划、跟踪管理（强调项目级有规划）。
3. **已定义级（Defined）**：组织层面建立标准化过程；所有项目采用组织标准过程。
4. **定量管理级（Quantitatively Managed）**：使用量化数据度量、管控过程性能。
5. **优化级（Optimizing）**：持续过程改进，主动预防缺陷。

> ⚠️ 勘误：第2级标准译名为"受管理级"，第4级为"定量管理级"；切忌把第4级写成"已管理级"（会和第2级混淆扣分）。
> 考点区分：2级管项目；3级管组织；4级管数据（量化）；5级管优化。

# 9 UML建模考点
## 9.1 UML结构图（静态）
- 类图：类、属性、方法、关系；
- 对象图；构件图；部署图（硬件节点上部署哪些软件构件）；包图。

## 9.2 UML行为图（动态）
- 用例图：参与者、用例、关系；描述用户功能需求；
- 顺序图（时序图）：对象之间消息交互，强调**时间顺序**；
- 通信图：对象交互，不强调时间顺序；
- 活动图：工作流、分支循环；类似流程图；
- 状态机图：一个对象自身生命周期内状态变迁。

> 高频辨析题：
> 顺序图：侧重消息交互的时间先后；状态图：单个对象自身状态变化；活动图：业务流程。

### 9.2.1 用例图关系（方向极易搞反）
- **包含 include**：基础用例**必须**执行被包含用例；箭头指向**被包含**用例（如"购物"→«include»→"登录"）。
- **扩展 extend**：扩展用例**可选**执行；箭头指向**基础**用例（如"购物"←«extend»—"使用优惠券"）。

## 9.3 类之间4种关系
1. 依赖：临时使用；虚线箭头；
2. 关联：长期连接；实线；双向/单向；
3. 聚合：整体‑部分，部分可以脱离整体独立存在；空心菱形；
4. 组合：整体‑部分，部分生命周期依赖整体；实心菱形。

> ⚠️ 类图关系共6种，另两种必考：
> - **泛化（继承）**：实线空心三角，父类↔子类。
> - **实现**：虚线空心三角，接口↔实现类。
> 关联 vs 依赖辨析：依赖是方法参数/局部变量（用完即走）；关联是成员变量（长期持有）。案例改错常把"依赖"误画成"关联"，导致耦合度分析错误。

# 10 系统切换 / 转换策略
旧系统→新系统上线，三种切换方案
1. **直接切换（一次性切换）**：某一时刻旧系统停止，直接启用新系统。
    - 优点：成本最低；
    - 风险：一旦新系统故障无退路；适合低风险小型系统。
2. **并行切换**：新旧系统同时运行一段时间，验证无误之后关停旧系统。
    - 优点：风险最低，旧系统作为备份；
    - 缺点：双倍工作量、成本高；适合核心重要业务系统。
3. **分段切换（试点/逐步切换）**：分模块、分部门逐步上线。
    - 折中方案；风险中等。

> ⚠️ 回退策略 Rollback（2023案例"上线风险"标准采分点）：无论采用何种切换方式，末尾必须补一句——"必须提前制定完善的回退计划（Rollback Plan），确保新系统出现致命故障时能在X分钟内切回旧系统。"

# 11 软件质量、可维护性、内聚耦合
## 11.1 内聚（模块内部元素联系紧密程度，越高越好）
从优到差：功能内聚 > 顺序内聚 > 通信内聚 > 过程内聚 > 时间内聚 > 逻辑内聚 > 偶然内聚。

## 11.2 耦合（模块之间依赖程度，越低越好）
从优到差：无直接耦合 > 数据耦合 > 标记耦合 > 控制耦合 > 外部耦合 > 公共耦合 > 内容耦合。

> 架构优化目标：**高内聚、低耦合**，提升可修改性。

# 13 答题误区避雷清单
❌误区1：螺旋模型核心是原型迭代
✅正确：螺旋模型**核心是风险分析**。

❌误区2：可用性等于性能
✅正确：可用性代表系统正常可用时长；性能代表响应快慢，二者独立质量属性。

❌误区3：Scrum Master是项目经理，给团队分配任务
✅正确：Scrum Master负责移除障碍，团队自组织，不分配任务。

❌误区4：并行切换风险高
✅正确：并行切换风险最低，新旧系统同时运行兜底。

❌误区5：SV<0进度提前
✅正确：SV=EV‑PV，小于0表示进度滞后。

❌误区6：风险规避 = 放弃引发风险的方案（含放弃外包商）
✅正确：规避是改变项目计划以消除风险产生条件（如放弃某外包商）；减轻是降低概率/影响（继续做但加防护）。两者不同，防判卷抠字眼。

## 14.2 中型场景分析题
### 场景
某城市政务平台准备上线新版本系统，系统承载市民社保查询等核心业务，不能长时间中断服务，一旦故障会造成严重社会影响。项目团队正在选择系统切换方案。
【问题1】请分析直接切换、并行切换各自优缺点。
【问题2】给出该政务平台推荐的切换方案并说明理由。

#### 高分参考作答
##### 问题1
直接切换
优点：实施简单，人力成本低。
缺点：风险高；新系统故障时没有旧系统兜底，业务中断。

并行切换
优点：风险最低；新旧系统同时运行，新系统出现问题旧系统仍然可以对外提供服务。
缺点：需要同时维护两套系统，工作量翻倍，人力成本高。

##### 问题2
推荐并行切换方案。
理由：政务社保查询属于核心业务，中断风险后果严重；并行切换能够最大程度降低上线失败带来的业务风险。

## 14.3 完整历年软件工程选做题真题‑五步解析范例
### 真题题干
某企业智慧办公系统项目，前期需求模糊，用户无法一次性给出全部清晰需求；项目规模较大，存在较多不确定风险。架构团队计划采用增量模型进行项目开发。

【问题1】（7分）简述增量模型的特点以及优缺点。
【问题2】（8分）判断该项目选用增量模型是否合适？如果需求极不稳定，还有哪些可选开发模型？
【问题3】（10分）项目执行过程中，团队识别到“第三方接口服务不稳定”这一项技术风险；请写出四种常见的风险应对策略，并针对该风险给出减轻策略的具体措施。

---
#### ①题干线索标注
1. 现状：需求模糊、不确定风险多；
2. 开发方案：增量模型；
3. 考点：增量模型特点、开发模型选型、4种风险应对策略（规避/减轻/转移/接受）。

#### ②解题思路推导
问题1：回忆增量分批交付特点，分别写出优缺点。
问题2：增量适合，但需求非常模糊优先原型模型；
问题3：默写4种风险策略；减轻策略即降低第三方接口不稳定带来的风险：增加重试、熔断降级、备用接口。

#### ③高分参考答案
##### 问题1
增量模型将软件拆分为多个可交付增量构件；项目分批迭代交付，每一个增量交付一部分可用功能。
优点：
1. 用户较早获得可用产品；
2. 风险分散，单个增量失败影响范围小；
缺点：
1. 需要做好增量之间接口设计；后期增量可能对前期构件产生修改，架构需要具备灵活性。

##### 问题2
选用增量模型具备一定合理性，可以分批交付降低整体风险。但是当前项目需求模糊，增量模型并不能很好解决早期需求不明确问题；还可以选择快速原型模型，通过原型迭代澄清用户需求。

##### 问题3
四种风险应对策略：风险规避、风险减轻、风险转移、风险接受。
第三方接口不稳定风险的减轻措施：
1. 增加接口重试机制；
2. 设置熔断、降级方案，接口故障时返回兜底数据；
3. 准备备用第三方接口；
4. 增加监控告警，及时发现接口异常。

#### ④失分陷阱提醒
1. ❌混淆螺旋模型和增量模型；螺旋核心是风险分析；增量核心分批交付；
2. ❌风险发生之后再补救属于应急措施，不属于事前风险应对策略；
3. ❌风险减轻不等于风险转移（外包、买保险才属于转移）。

#### ⑤答题模板沉淀‑风险题模板
> 风险减轻措施：增加冗余备份、重试、熔断降级、备用方案、加强测试监控，降低故障概率或故障损失。

# 14 架构师专属高频考点（高并发 / 可靠性 / 安全 / 度量）
> 架构师案例第2、3题核心：架构评估、高并发设计、可靠性与安全。以下为必补充硬菜。

## 14.1 Web 高并发与分布式架构设计 ⭐⭐⭐⭐⭐
- **负载均衡**：Nginx、F5、DNS轮询。
- **缓存架构**：Redis / Memcached。必考三大坑：
  - 缓存穿透：查询不存在的数据，绕过缓存打穿DB → 布隆过滤器/空值缓存。
  - 缓存雪崩：大量缓存同时失效 → 过期时间加随机值。
  - 缓存击穿：热点 Key 失效瞬间高并发打DB → 互斥锁/热点不过期。
- **消息队列 MQ**：Kafka / RabbitMQ，作用：异步处理、削峰填谷、系统解耦。
- **数据库扩展**：读写分离（主库写、从库读，解决读多写少）、分库分表 Sharding（解决单表过大）。代价：数据一致性问题（CAP理论）。
- **CAP 定理**：一致性C、可用性A、分区容错性P，分布式最多满足两项。
- **BASE 理论**：基本可用 BA、软状态 S、最终一致性 E，是 CAP 中 AP 方案的延伸，大型互联网常用。

## 14.2 系统可靠性设计与计算 ⭐⭐⭐⭐（必考计算）
- **串联系统**：R = R1 × R2 × ...（任一失效则整体失效，可靠性最低）
- **并联系统（冗余）**：R = 1 − (1−R1) × (1−R2) × ...（任一可用则整体可用）
- **容错设计技术**：
  - N版本程序设计：多版本同时运行，表决器决断（前向恢复）。
  - 恢复块方法：主块失败切备用块（后向恢复，接受测试）。
  - 防卫式程序设计：对所有可能错误做预防性检查。
- 可靠性 vs 可用性：可靠性=一段时间内不出错的概率；可用性=一段时间内能工作的概率（含故障后恢复）。集群 Cluster 提升可用性；冗余 Redundancy 提升可靠性。

## 14.3 信息安全与加密架构 ⭐⭐⭐⭐
- **对称加密**（DES、AES）：速度快，加密数据本体。
- **非对称加密**（RSA、ECC）：速度慢，加密密钥 + 数字签名。
- **数字签名**：私钥签名、公钥验证。作用=防篡改、防抵赖、身份认证；**注意不能保证数据机密性**。
- **数字信封**：对称加密数据 + 接收方公钥加密对称密钥，兼顾效率与安全。
