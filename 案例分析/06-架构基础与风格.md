# 06 · 架构基础与风格（必做题专章）

> 本模块是案例分析题的**基石**，分值约 25 分（第 1 题必答）。
> 核心：掌握常见**架构风格**及其适用场景，并能结合**质量属性**（性能、可用性、安全性、可修改性）进行分析与权衡。
> 本文结合两个完整实例，帮你真正理解并能应用。

---

## 一、核心掌握内容

### 1. 架构风格（Architectural Style）

架构风格 = 特定背景下系统组织的惯用模式，定义了**组件、连接件、约束**及它们的交互规则。

| 架构风格 | 核心思想与特点 | 典型适用场景 | 关键优点 | 主要缺点 / 挑战 |
|----------|----------------|--------------|----------|------------------|
| **分层架构 (Layered)** | 系统分为若干层，上层只能调用相邻下层，实现关注点分离 | 企业级应用、传统信息系统、需清晰分层与逐步抽象的复杂系统 | 结构清晰、易理解、支持并行开发、可复用性好 | 多层调用可能成性能瓶颈；严格分层易过度设计；不适合高性能低延迟场景 |
| **微服务 (Microservices)** | 应用构建为一组小型自治服务，每服务围绕特定业务能力，通过轻量 API（HTTP/REST）通信 | 大型复杂互联网应用、需独立部署扩展的异构系统、业务快速迭代场景 | 通过故障隔离、独立部署扩展，有助于提升可用性与可修改性 | 复杂度高（服务发现/配置/监控/分布式事务）；运维成本高；数据一致性挑战；若服务治理/监控/容错能力不足，反而因分布式复杂度降低整体可用性 |
| **事件驱动 (Event-Driven)** | 组件间通过事件（消息）异步通信，一个组件的事件触发其他组件操作 | 高并发异步处理（订单）、需高响应性与松耦合的系统、实时数据流 | 可提升吞吐量、可扩展性与可用性（异步解耦） | 测试难度大；数据一致性保障复杂；消息顺序与可靠性需额外处理；异步通信可能增加端到端延迟，并带来重复消费、事务一致性难题 |
| **管道-过滤器 (Pipes-Filters)** | 每个处理步骤（过滤器）封装独立功能，数据经管道在过滤器间流动，各自独立处理 | 数据处理密集型（编译器、图像处理、ETL）、需模块化复用与并发处理的场景 | 模块复用强、可维护可扩展性高、具并发性、模块独立性高 | 不适交互性强应用；存在关系的数据流需协调；可能有额外 IO 开销 |
| **仓库风格 / 黑板 (Blackboard)** | 多个专家组件（知识源）协同处理共享数据结构（黑板）中的问题数据，适用于无确定性解法的复杂问题 | 人工智能（语音识别、图像理解、信号处理）、复杂决策支持、多专家协作求解 | 解决复杂非结构化问题、灵活性扩展性高（易加新知识源） | 控制逻辑复杂、难测试；共享数据并发访问控制复杂；难预测求解时间 |

### 1.5 架构风格经典五大类（教材口径）

软考有时不直接问"这是什么风格"，而是从教材分类角度出题。看到描述要能快速映射到对应的子风格。

| 大类 | 子风格 | 典型特征 | 考试常见描述关键词 |
|------|--------|----------|-------------------|
| **数据流风格** | 批处理、管道-过滤器 | 数据按顺序流动，处理步骤相对独立，每个过滤器独立处理 | 数据流处理、过滤器链、管道连接、ETL处理 |
| **调用/返回风格** | 主程序-子程序、面向对象、分层架构 | 显式调用，控制流清晰，调用方知道被调用方 | 显式调用、上下层调用、面向对象封装、层次化 |
| **独立构件风格** | 进程、事件驱动/隐式调用 | 构件相对独立运行，通过消息/事件通信，无中央控制 | 各构件独立运行、通过事件通信、发布订阅、隐式调用 |
| **虚拟机风格** | 解释器、基于规则的系统 | 用软件模拟某种语言或规则执行机制 | 解析用户代码、规则引擎、解释执行、脚本处理 |
| **仓库风格** | 数据库系统、黑板系统、超文本系统 | 共享数据中心，多个构件围绕数据交互 | 共享数据存储、中央数据节点、多客户端访问 |

> 💡 **考试速判技巧**：
> - 题干说"各构件相对独立运行，通过事件进行通信" → 属于**独立构件风格**或**事件驱动架构**
> - 题干说"解析用户提交的代码/规则" → **虚拟机风格（解释器）**
> - 题干说"多个专家模块围绕共享数据协同求解，无固定算法" → **黑板架构（仓库风格子类）**

### 2. 质量属性（Quality Attributes）

质量属性是系统**非功能需求**的量化体现，是架构设计要解决的核心问题。架构风格的选择，很大程度上是为了满足特定的质量属性需求。

| 质量属性 | 定义与核心关注点 | 典型架构策略 | 与其他属性的权衡（冲突点） |
|----------|------------------|--------------|----------------------------|
| **性能 (Performance)** | 及时提供服务的能力，关注响应时间、吞吐量、资源利用率 | 引入缓存（多级）、负载均衡、优化算法与数据结构、异步处理（消息队列）、读写分离、分库分表 | 与可用性冲突：缓存越多，一致性维护越复杂可能牺牲可用性；与安全性冲突：加解密鉴权损耗性能 |
| **可用性 (Availability)** | 一定时间内正常工作时间所占比例，关注 MTBF（平均故障间隔）与 MTTR（平均修复时间） | 冗余（服务/数据）、故障自动转移（心跳/选举）、负载均衡、限流降级熔断、无状态设计、异步解耦 | 与性能冲突：冗余与同步机制带来延迟；与安全性冲突：安全审计可能影响响应速度 |
| **安全性 (Security)** | 兼顾向合法用户服务与阻止非授权使用，关注认证、授权、加密、审计 | 分层安全（网络/应用/数据层）、最小权限、数据加密（传输/存储）、输入验证（防注入）、审计日志、漏洞扫描 | 与性能冲突：加解密/鉴权/审计消耗算力增加延迟；与可用性冲突：复杂安全策略影响体验与访问效率 |
| **可修改性 (Modifiability)** | 修改系统（新增功能、修 bug、适配新业务）的成本高低，含可扩展/可移植/可装配性 | 高内聚低耦合、分层架构、接口隔离、抽象层/中间件隔离变化、组件化/插件化、配置驱动（参数外部化） | 与性能冲突：过多抽象分层与接口调用增加链路，带来性能损耗 |

> 💡 **核心理解**：架构设计本质上是在多个质量属性之间**权衡**。一个决策通常对多个属性产生正负两面影响。不存在"完美"架构，只有最适合当前业务阶段与技术约束的架构。

### 3. 敏感点 vs 权衡点（ATAM 高频考点）

- **敏感点 (Sensitivity Point)**：某一架构要素显著影响**某一个**质量属性。改变它，该属性明显变化。
  - 例子：缓存的最大内存大小是**性能**的敏感点。调大→响应时间显著提升；调小→性能明显下降。
- **权衡点 (Tradeoff Point)**：某一架构要素影响**多个**质量属性，且影响相互冲突。调整它同时带来"利"与"弊"。
  - 例子：引入**冗余服务**是可用性的权衡点。冗余提升可用性（利），但增加成本与运维复杂度（弊），并可能引入数据一致性问题（弊）。

> ATAM 中还有**风险点 (Risk)**：架构决策中可能导致问题的潜在隐患（如两个服务耦合度过高，影响独立扩展与故障隔离）。

## 二、结合实例深度理解

### 实例 1：在线教育平台直播系统架构选型

**场景需求**
- 高并发观看：高峰期 10 万+ 学生同时观看
- 低延迟：主播音画实时同步，延迟 < 500ms
- 高可用性：推流不中断，单点故障恢复 < 30 秒
- 可扩展性：易扩展弹幕、连麦、互动答题等新功能
- 开发效率：平均 2 周上线一个新功能

**架构决策**
- 推流端：主播 OBS 推流 → 流媒体服务器集群（Nginx-RTMP / SRS）
- 转码与录制：微服务架构，独立部署扩展
- 分发：CDN 分发网络，智能调度解决高并发低延迟
- 播放端：Web/APP 接入 HLS / HTTP-FLV
- 数据与消息：Kafka 消息总线解耦各模块、削峰填谷
- 实时互动：WebSocket / 自定义协议（弹幕、点赞、连麦）
- 监控治理：Prometheus + Grafana 实时监控、自动扩缩容

**分析**
- **架构风格**：微服务 + 事件驱动（Kafka）组合。微服务保证核心功能独立开发/部署/扩展（可修改性、可伸缩性）；事件驱动通过消息队列异步解耦、削峰填谷（性能、可用性）。
- **质量属性权衡**
  - 敏感点：CDN 节点部署位置与数量是性能与延迟的敏感点——越近用户，延迟越低。
  - 权衡点：转码服务拆分粒度——过细（每路流一服务）运维与一致性成本高，但隔离性极致；折中按转码类型（高清/标清）拆分。
  - 权衡点：引入消息队列是可用性与性能的权衡点，但带来数据一致性挑战（需幂等设计、消息确认机制应对）。
- **ATAM 视角（效用树）**：根="直播系统核心质量"；一级=性能/可用性/可修改性。
  - 性能场景："10 万并发观看（环境），主播推流（刺激），学生播放延迟 < 500ms（响应）" → 优先级 H
  - 可用性场景："单台流媒体宕机（环境），自动切换备用（刺激），30 秒内恢复（响应）" → 优先级 H
  - 风险点：转码与流媒体服务耦合度过高；敏感点：CDN 智能调度算法；权衡点：转码拆分粒度。

### 实例 2：传统电商订单系统架构演进

**问题**：单体架构，所有功能（订单/库存/支付/物流）打包，部署复杂、牵一发动全身（可修改性差），高并发性能瓶颈（可伸缩性差）。

**三阶段演进**
1. **分层架构**：表示层 / 业务逻辑层 / 数据访问层 / 数据存储层（单库）。
   - ✅ 结构清晰、易理解、便于协作
   - ❌ 部署耦合、整体扩展受限、可修改性仍差
2. **引入中间件**：Redis 缓存热点数据（提升读性能）+ Kafka 消息队列（下单后库存扣减、通知异步化，提升写吞吐与解耦）。
   - ✅ 性能与吞吐量极大提升
   - ❌ 可修改性提升有限（仍是单体）；数据一致性变复杂（缓存与 DB 同步、消息可靠性）
3. **微服务化**：拆分为订单/库存/支付/物流独立服务，各持独立数据库，通过 API 网关暴露，采用 TCC / Saga 实现最终一致性。
   - ✅ 可修改性与可伸缩性根本性提升，独立开发/部署/扩展
   - ❌ 运维复杂、分布式事务与一致性的巨大挑战
   - **权衡点**：拆分粒度——越细隔离性/扩展性越好，但运维与一致性挑战越大；需按业务边界与团队能力找平衡。
   - **权衡点**：分布式事务（TCC/Saga）保证最终一致性，但带来开发复杂度（补偿逻辑）与性能损耗（额外网络调用与日志）。

> 💡 **关键理解**：演进过程展示了架构风格如何为满足不同阶段的核心质量属性而被选择。**没有"最好"的风格，只有"最适合"当前约束的风格。**

## 三、如何掌握与备考

### 1. 构建知识体系，理解性记忆
理解每种风格背后的**设计哲学**（它试图解决什么问题）、典型场景与代价。用对比表（上文）辅助记忆。

### 2. 掌握分析框架，形成答题套路

**框架一：场景分析框架**
1. 明确场景：提取**刺激源**（谁/什么产生事件）、**环境**（何种情况）、**刺激**（发生了什么）、**响应**（系统如何反应、度量是什么）。
2. 关联质量属性：判断主要关联哪个/哪些质量属性。
3. 应用架构策略：针对该属性，说明采用了哪些策略（缓存、冗余、分层、解耦…）。
4. 识别敏感点 / 权衡点：哪些决策是敏感点（影响单属性）或权衡点（影响多属性且冲突）。

**框架二：架构决策论证框架**
1. **决策陈述**：明确指出支持的架构决策（如"采用微服务架构是合适的"）。
2. **优势分析（利）**：结合场景说明如何支持关键质量属性。
3. **劣势 / 挑战分析（弊）**：客观说明带来的问题。
4. **权衡与总结**：说明如何用其他策略缓解挑战（如"通过幂等设计与分布式事务补偿保证一致性"），总结在当前约束下是合理的权衡。

### 3. 高效刷题与复盘
- **精做真题**：研究参考答案的答题逻辑与结构，体会理论如何落地。
- **分类整理**：按架构风格或质量属性归类，总结常见提问方式与答题要点。
- **复盘错题**：
  - 错在哪？（概念不清 / 审题偏差 / 分析不深）
  - 为何错？（知识盲区 / 思路偏差）
  - 正确答案思路是什么？
  - 再遇类似题如何避免？

> ⚠️ **机考注意**：平时练习务必在电脑上输入答案，适应键盘与界面，避免考试操作不熟练浪费时间。

## 四、核心学习路径

```
架构基础与风格备考路径
├── 第一阶段：理解核心概念
│   ├── 理解 6+2 个核心质量属性（性能/可用性/安全性/可修改性…）及其典型架构策略
│   └── 理解 5+ 个常见架构风格（分层/微服务/事件驱动…）的原理、场景与优缺点
├── 第二阶段：掌握分析工具
│   ├── 熟练掌握"场景分析框架"（刺激源-环境-刺激-响应）与"架构决策论证框架"
│   └── 深入理解 ATAM 的敏感点 / 权衡点 / 风险点，能结合案例识别分析
└── 第三阶段：实战与精进
    ├── 精做历年真题，归纳不同类型题的答题套路
    └── 复盘错题，分析知识盲区与思路偏差，持续改进
        ↓
最终目标：快速识别案例关键场景 → 关联质量属性 → 分析架构策略 → 论证决策合理性
```

**核心要点**
- 概念是基础，理解是关键：不背概念，理解"为什么"。
- 场景是桥梁，质量属性是标尺：用场景连接业务与技术，用质量属性衡量架构有效性。
- 权衡是灵魂，决策是目标：时刻认识到架构是在约束下权衡，分析要体现权衡思维。
- 真题是向导，复盘是法宝：通过真题学组织表达，通过错题完善体系。

# 6.6 架构风格‑六大质量属性收益与代价对照表
> 软考案例试题一核心工具表。
> 收益：⭐ 代表该架构风格通常有利于该质量属性；
> 代价：⚠️ 代表该架构风格通常会损害/带来额外负担；
> 注意：所有结论均为通用规律，答题**必须结合题干场景**，不能死套表格。

|架构风格|可修改性|性能|可用性|安全性|可测试性|易用性/其他代价|
|---|---|---|---|---|---|---|
|分层架构|⭐⭐⭐⭐<br>层间解耦，改动局限一层|⚠️⚠️<br>层级过多产生调用开销|⭐⭐<br>可单独部署冗余层|⭐⭐<br>可在网关层做权限控制|⭐⭐⭐<br>每层可独立测试|层级太深时调试链路长|
|管道‑过滤器|⭐⭐⭐⭐<br>过滤器独立、可插拔|⚠️⚠️<br>数据反复拷贝、流转开销|⭐⭐<br>单个过滤器故障可隔离|⚠️<br>过滤器之间传递数据难控制权限|⭐⭐⭐⭐<br>每个过滤器可单独测试|不适合交互强、需要共享大量状态的系统|
|仓库（知识库）架构|⚠️<br>中央数据仓库是耦合点|⭐⭐<br>共享数据无需传递副本|⚠️<br>仓库若无冗余设计易成单点故障风险（采用复制/集群/备份可降低）|⚠️<br>集中数据，安全压力集中|⚠️<br>业务逻辑分散在各个客户端，难以整体测试|适合数据驱动类系统|
|黑板架构|⚠️<br>知识源之间通过黑板耦合|⚠️<br>多知识源竞争黑板资源，调度开销大|⚠️<br>黑板单点风险高|⚠️<br>数据全部存放黑板，安全管控难|⚠️⚠️<br>推理过程不透明，极难调试|适合无确定性求解算法的问题，AI推理、信号处理|
|主程序‑子程序|⚠️⚠️<br>紧耦合，改动一处影响全局|⭐⭐⭐<br>直接调用，开销小|⚠️<br>主程序故障整体崩溃|⭐⭐<br>权限集中控制|⚠️<br>模块之间强依赖，单元测试困难|传统单体结构化程序|
|面向对象架构|⭐⭐⭐<br>封装、继承利于修改扩展|⚠️<br>对象间大量交互，方法调用开销|⭐⭐<br>可封装独立对象做冗余|⭐⭐<br>封装可隐藏内部数据|⭐⭐<br>对象可单独测试|对象之间依赖关系复杂时容易出现调用混乱|
|事件驱动架构（隐式调用）|⭐⭐⭐⭐<br>发布订阅解耦，发布者无需知道订阅者|⚠️⚠️<br>异步消息带来延迟；事务一致性难保证|⭐⭐⭐<br>生产者消费者解耦，局部故障不扩散|⚠️<br>消息链路长，难以追踪安全问题|⚠️⚠️<br>异步调用，执行链路不可见，调试困难|最典型权衡：高可修改性换取可调试性下降|
|C2架构（构件‑连接器风格）|⭐⭐⭐⭐⭐<br>组件完全解耦，只能通过连接器通信|⚠️⚠️⚠️<br>连接器带来额外开销|⭐⭐⭐|⚠️|⚠️|禁止组件之间直接调用；与事件驱动思想相似但更强调构件‑连接器特征|
|SOA面向服务架构|⭐⭐⭐⭐<br>服务松耦合，可独立变更|⚠️⚠️<br>服务调用、ESB转发带来网络开销|⭐⭐⭐<br>服务可冗余部署|⭐⭐<br>统一服务网关鉴权|⚠️<br>跨服务调试链路长|适合大型异构企业系统集成|
|微服务架构|⭐⭐⭐⭐⭐<br>每个服务独立开发部署、迭代|⚠️⚠️⚠️<br>大量远程调用，网络开销上升，分布式事务复杂|⭐⭐⭐<br>单个服务故障不会拖垮整体系统|⚠️<br>服务数量变多，安全管控面变大|⚠️⚠️⚠️<br>分布式系统，排查故障难度大|最典型权衡：可修改性、可用性提升，牺牲性能与可调试性|

> 💡答题黄金句式（权衡句，阅卷高频踩分点）
> 采用XX架构风格，可以提升系统的【可修改性/可用性】；但会带来【性能下降、调试困难、分布式事务复杂】等代价，需要在方案中进行权衡。

# 6.7 高频易混淆架构风格横向对比（避坑专区）
## 6.7.1 仓库架构 VS 黑板架构（考生最高频错题）
### 仓库（知识库）架构
- 控制流：**由客户端自己决定什么时候访问仓库、读取数据**
- 仓库被动：只存放数据，不主动调度业务模块
- 使用场景：数据库驱动系统，如进销存系统

### 黑板架构
- 控制流：**黑板主动调度各个知识源，知识源之间互不感知对方存在**
- 黑板是中央控制+数据存储
- 使用场景：语音识别、图像识别、问题求解、没有固定求解流程的AI推理系统

> 速记口诀：仓库存数据别人主动读；黑板存数据主动喊别人干活。

> 💡 **黑板架构补充**：黑板不仅存储数据，还承担**控制调度**作用；知识源之间不直接通信，而是围绕黑板协同求解。考试考黑板时常见关键词：**无固定求解算法、多个知识源、共享黑板、协同求解、语音识别/图像识别/复杂推理**——看到这些关键词优先考虑黑板。

## 6.7.2 事件驱动架构（隐式调用） VS C2架构
- 事件驱动（EDA）：组件之间可以直接调用，也可以走事件；没有强制约束
- C2：**严格禁止组件之间直接调用，所有通信必须经过连接器**（连接件负责消息路由、事件传递）；构件之间低耦合、可修改性高，但连接件通信可能带来额外性能开销。C2 常采用消息/事件通信机制，与事件驱动思想有相似性，但考试中更建议强调其"构件‑连接器"特征，不建议简单说成"事件驱动子类"。

## 6.7.3 SOA VS 微服务
- SOA：一般依赖 ESB 企业服务总线做中转，服务粒度通常偏大，侧重企业异构系统集成；
- 微服务：一般无重型ESB，粒度更小，每个微服务独立数据库，侧重互联网业务快速迭代。

## 6.7.4 分层架构 VS 主程序‑子程序
- 分层：层与层之间单向依赖，每层职责独立；可以跨进程、跨机器部署；
- 主程序‑子程序：同一程序内部模块之间直接调用，属于传统单体紧耦合结构。

## 6.7.5 Lambda / Kappa 架构（大数据批流混合场景极简素材）
> 当题干背景是"海量数据 + 既要实时又要离线准确"时，优先考虑批流混合架构。

- **Lambda 架构**（大数据混合批流架构）：分为**批处理层（Batch Layer）+ 速度层（Speed Layer）+ 服务层（Serving Layer）**；底层采用**管道‑过滤器**思想（数据流风格），兼顾实时数据低延迟与离线大数据结果准确。
  - 批处理层：处理全量历史数据，结果准确但延迟高；
  - 速度层：处理实时增量数据流，低延迟但结果是近似/增量；
  - 服务层：合并两层结果对外统一提供查询。
- **Kappa 架构**：舍弃批处理层，全部采用**流处理**实现（如 Kafka + Flink），架构更加简洁，只维护一套流处理管道。

> **答题模板（可直接套）**：
> 本海量数据处理系统适合采用 Lambda 架构，采用管道‑过滤器数据流风格，分别通过速度层处理实时数据流、批处理层处理全量历史数据，最终由服务层对外统一提供查询服务。若追求架构简洁、实时数据即最终数据，也可采用 Kappa 架构，全部以流处理实现。

# 6.8 架构风格别名清单（考试避坑）
考试题干有时不会写常见名称，会用别名，看到下面名称直接对应：
1. 隐式调用 = 事件驱动架构
2. 知识库架构 = 仓库架构
3. 连接器‑组件架构 = C2架构
4. 显式调用 = 传统过程调用（主程序‑子程序）

# 6.9 考生高频误区避雷清单（本章必背）
> 错误观点 → 正确结论 + 答题提醒

1. ❌错误：微服务一定性能更好
> ✅正确：微服务大量远程调用，相比单体通常性能会下降；收益是可修改性、可用性提升。答题不能写微服务提高性能。

2. ❌错误：分层架构一定可修改性高
> ✅正确：只有严格遵守单向分层、职责清晰时可修改性才高；如果分层混乱、跨层调用，可修改性会变差。一切以题干描述为准。

3. ❌错误：只要出现消息、异步，就是事件驱动架构
> ✅正确：异步消息只是技术手段；要看业务组件是否解耦、是否采用发布‑订阅的隐式调用模式。普通单体内部异步队列≠事件驱动架构。

4. ❌错误：黑板架构 = 使用了数据库
> ✅正确：数据库只是存储；黑板核心是**主动调度知识源模块**，普通数据库系统一般属于仓库架构。

5. ❌错误：架构风格优点可以无脑全部写上
> ✅正确：答题优点缺点必须结合场景，题干中不存在的特点不要凭空罗列。

6. ❌错误：事件驱动架构一定提高性能
> ✅正确：事件驱动可提升吞吐量、可扩展性与可用性，但异步通信可能增加端到端延迟，并带来消息顺序、重复消费、事务一致性问题。不能简单说"事件驱动一定提高性能"。
> 场景细分：高并发写入/异步通知/削峰填谷→利吞吐量与可用性；强实时同步响应→可能增加延迟；强事务一致性→增加保障难度；链路调试→降低可测试性与可追踪性。

7. ❌错误：微服务架构可用性一定好
> ✅正确：微服务通过故障隔离、独立部署、独立扩展有助于提升可用性；但服务治理/监控/容错/熔断/链路追踪能力不足时，反而因分布式复杂度降低整体可用性。答题建议：微服务提升可修改性与局部可用性，但增加运维、分布式事务、故障排查难度。

8. ❌错误：响应时间 0.5 秒是敏感点
> ✅正确：响应时间 0.5 秒是**性能质量属性指标**；影响它的架构决策（缓存策略、调用链路长度、CDN 节点数）才是**性能的敏感点**。质量属性指标本身不是敏感点，架构决策才是。



# 6.9.1 质量属性"架构战术"对照表（第三问高频踩分表）
> 案例一题第三问常问："为满足某质量属性，可采用哪些架构策略？"或"该设计采用了哪些质量属性实现策略？"
> 下面按质量属性整理**战术类别 + 具体措施**，答题时按"属性 + 战术 + 题干结合"写。

### 性能战术
| 战术类别 | 具体措施 |

# 6.9.2 易混淆质量属性判断表（第一问防丢分必背）
> 第一问丢分往往不是不懂，而是属性边界模糊。下表覆盖高频误判。

| 题干表达 | 容易误判 | 更准确判断 |
|----------|----------|------------|
| 响应时间不超过 0.5 秒 | 可用性 | 性能 |
| 故障后 5 分钟恢复 | 性能 | 可用性 |
| 连续运行 720 小时 | 可靠性 | 可用性 |
| 密码加密 | 安全性 | 安全性 |
| 防止黑客攻击 | 安全性 | 安全性 |
| 新增功能 2 周内完成 | 易用性 | 可修改性 |
| 新增 GPU 无需修改核心代码 | 性能 | 可修改性/可扩展性 |
| 支持 x86 迁移到 ARM | 可修改性 | 可修改性（可移植性） |
| 界面支持老年人、残疾人 | 可测试性 | 易用性 |
| 模拟环境压测 | 性能 | 可测试性 |
| 日志审计追溯 | 可测试性 | 安全性（优先） |
| 系统水平扩展应对用户增长 | 可修改性 | 性能/可伸缩性，视题干 |
| 模块独立部署 | 可用性 | 可修改性/可用性，看题干 |
| 消息队列削峰填谷 | 性能 | 性能/可用性，看问题 |
| 用户量增长 300%，系统可水平增加节点支撑负载 | 性能 / 可修改性 | **可伸缩性**（子属性，属于可修改性的扩展分支；答题优先写可伸缩性） |

> 灵活判断原则：题干只让写一个时——强调"负载增长后性能仍满足"写**性能**；强调"系统能扩展部署"写**可修改性/可扩展性**；标准教材六大属性优先写最贴近的一个，**不要死记，看题干刺激是什么**。

### 可伸缩性补充定义（新大纲常考）
**可伸缩性（Scalability）**：系统负载增长时，通过增加硬件 / 服务节点，维持原有服务质量的能力。
- 分为**水平扩展**（增加实例 / 节点，如加服务器、加容器）与**垂直扩展**（升级单节点硬件，如加 CPU、加内存）。
- 归属：可伸缩性是**可修改性的子属性 / 扩展分支**，但答题时若题干强调"负载增长、加节点"应优先直接写**可伸缩性**，比写可修改性更精准、更贴合阅卷踩分点。

# 6.9.3 架构评估方法三剑客：SAAM / ATAM / CBAM
> 第一题最常见 ATAM，但有时问"可采用什么架构评估方法"，只答 ATAM 不够稳，建议三种都储备。

| 评估方法 | 核心关注点 | 适用场景 |
|----------|------------|----------|
| **SAAM** | 场景分析，早期架构评估，偏可修改性 | 架构方案早期选择、可修改性分析 |
| **ATAM** | 多质量属性权衡，敏感点、权衡点、风险点 | 架构设计阶段，关注质量属性冲突 |
| **CBAM** | 成本效益分析，架构决策经济性排序 | 需在成本、收益间做投资决策 |

> 答题写法：若重点是分析多个质量属性冲突和架构决策敏感性 → **ATAM**；若处于架构早期、主要分析场景对架构影响 → **SAAM**；若需对改进方案做成本效益排序 → **CBAM**。

# 6.9.4 ABSD · 基于架构的软件开发方法（试题一高频，常与架构评估绑定出题）
> ABSD（Architecture-Based Software Design）：强调**架构先行**，以质量属性与功能需求双驱动，自顶向下递归细化。真题常在"试题一"结合架构评估一起考。

## 6.9.4.1 ABSD 核心思想
- 不是需求完全明确才开始设计，而是**架构驱动**：先识别关键质量属性与功能需求，再派生架构。
- 采用**递归分解**：系统 → 构件（粗粒度）→ 子构件，逐层细化。
- 复用**架构风格/模式**：以成熟的风格（分层、微服务、事件驱动等）作为构件组织依据。

## 6.9.4.2 ABSD 开发流程（六步，必背答题链）
1. **架构需求**：获取需求，标识**质量属性**与功能需求，建立**需求质量属性场景**。
2. **架构设计**：选择架构风格/模式，生成候选架构，用**效用树**组织质量属性。
3. **架构文档化**：产出架构规格说明书、视图（逻辑/进程/部署视图等），便于传递与评审。
4. **架构复审（评估）**：用 **ATAM/SAAM/CBAM** 评估架构，识别风险点/敏感点/权衡点。
5. **架构实现**：按架构构件化开发，构件按接口契约实现，控制耦合。
6. **架构演化**：随需求变化迭代演化，回到需求/设计闭环。

> 💡 答题模板（ABSD 流程题）：ABSD 以架构为核心，依次经历**架构需求 → 架构设计 → 文档化 → 复审评估（ATAM）→ 实现 → 演化**六个阶段；其中复审阶段用 ATAM 识别质量属性权衡与风险点，需求变化触发架构演化回到闭环。

# 6.9.5 CBAM · 成本效益分析法（详细步骤，架构评估第三法）
> CBAM（Cost Benefit Analysis Method）：在 ATAM 识别出的架构策略基础上，量化**成本、收益、ROI、优先级排序**，辅助投资决策。用于"有多个改进方案，先改哪个"类题目。

## 6.9.5.1 CBAM 步骤（六步）
1. **整理 ATAM 候选策略**：来自效用树中的架构策略。
2. **确定场景与优先级**：对质量属性场景按重要性排序。
3. **量化收益 (Benefit)**：每个策略对场景的质量属性提升打分（0~100，相对效用）。
4. **估算成本 (Cost)**：开发/迁移/运维成本、进度影响。
5. **计算 ROI / 优先级**：ROI = 收益 / 成本，按 ROI 与风险排实施顺序。
6. **输出决策建议**：给出"先投入哪个策略"的排序。

## 6.9.5.2 答题模板
> 在 ATAM 评估的基础上，采用 CBAM 对候选架构改进策略做成本效益分析：先量化各策略对质量属性场景的**收益**，再估算**成本**，计算 **ROI = 收益 / 成本**，按 ROI 与实施风险排序，优先实施高收益低成本的策略。

# 6.9.4 试题一 · 致命禁句黑名单（写出来大概率扣分）
> 考前快速背诵：以下句子一旦写出，整道小题分数几乎清零。属于"绝对不能写"的致命错误清单。

1. ❌ 微服务架构可以提升系统整体性能。
   > ✅ 修正：微服务大量远程调用通常带来性能下降；收益是可修改性、可用性提升。
2. ❌ 事件驱动架构、消息队列一定降低响应延迟 / 一定提高性能。
   > ✅ 修正：事件驱动可提升吞吐量、可用性与可修改性，但异步通信可能增加端到端延迟，并带来事务一致性难题。
3. ❌ 读写分离架构一定存在主从延迟（传统自建主从架构确实如此，但云原生架构可规避）。
   > ✅ 修正：传统自建主从读写分离存在秒级同步延迟；云原生存算分离共享存储架构（如 PolarDB）可规避同步延迟，实现强一致读。
4. ❌ 黑板架构就是数据库系统 / 使用了数据库就是仓库架构。
   > ✅ 修正：数据库只是存储，属于仓库架构；黑板核心是"主动调度知识源"，普通数据库系统不是黑板。
5. ❌ 权衡点只会提升系统某一项质量属性（无负面影响）。
   > ✅ 修正：权衡点必须同时带来收益 + 负面影响，至少涉及两个质量属性。
6. ❌ 质量属性指标（如响应时间 0.5 秒）是敏感点。
   > ✅ 修正：敏感点永远是**架构决策**，不是指标本身；指标是质量属性度量，影响它的架构决策才是敏感点。

# 6.10 ATAM架构评估方法（试题一高频考点）
> ATAM：Architecture Tradeoff Analysis Method，架构权衡分析方法。
> 属于软考系统架构设计师案例试题一非常高频的知识点，常考：质量属性场景、效用树、敏感点、权衡点、风险点、非风险点。

## 6.10.1 ATAM方法核心目标
不是评判架构“好或坏”，而是**识别架构决策带来的质量属性收益与代价，找到权衡关系**。

## 6.10.2 质量属性场景（必考书写格式）
一条完整的质量属性场景由 **6个要素**组成：
1. 刺激源：是谁/什么外部对象触发事件
2. 刺激：发生了什么事情
3. 环境：事件发生时系统处于什么状态
4. 制品：系统中受影响的架构组件
   > 📌 **术语严谨性提醒（新书目口径一致）**：官方教材（如《系统架构设计师教程》第 2 版）中 ATAM 六要素有时表述为"刺激源、刺激、环境、**制品**、响应、响应度量"，其中"制品"在英文中对应 **Artifact**，也被翻译为"**构架 / 受影响的架构元素**"。答题时仍写"**制品**"一词（阅卷老师习惯看这个词，最稳妥），但心里要清楚它 = **受影响的架构元素**（某模块、服务、数据库、消息中间件、链路或整个系统）。
5. 响应：系统做出什么样的反应
6. 响应度量：衡量响应好坏、可量化指标

### ✅ 书写模板
> 在【环境】条件下，【刺激源】对【制品】发起【刺激】，系统需要完成【响应】，并且达到【响应度量】。

> ⚠️ **"制品"强提醒（高频漏写点）**：制品指受该场景影响的**架构元素**，可以是某个模块、服务、数据库、消息中间件、网络链路、整个系统等。**答题没写"制品"容易被判定场景不完整，直接丢分。**

### 示例1（可用性场景）
> 在正常运行环境下，外部用户对支付服务发起一次请求，支付服务在3秒内返回结果，且服务中断时间每年不超过2小时。

### 示例2（性能场景·直播标准格式）
> 在高峰期并发 10 万用户观看直播的环境下，外部用户对播放服务发起播放请求，播放服务返回视频流，平均首帧延迟不超过 500ms。

| 要素 | 内容 |
|------|------|
| 刺激源 | 外部用户 |
| 刺激 | 发起播放请求 |
| 环境 | 高峰期并发 10 万用户观看 |
| 制品 | 播放服务 / CDN 分发服务 |
| 响应 | 返回视频流 |
| 响应度量 | 平均首帧延迟不超过 500ms |

> ⚠️答题扣分陷阱：
> - 只写定性描述，没有响应度量 → 场景不完整，丢分
> - **漏写"制品"（受影响架构元素）→ 场景不完整，丢分**
> - 场景描述过于宽泛，没有对应系统组件 → 脱离题干

## 6.10.3 四大核心概念（高频名词解释）
> ⚠️ **核心提醒（易错）**：敏感点、权衡点、风险点通常指的是**架构决策或架构要素**，而**不是质量属性需求本身**。
> 例如"响应时间 0.5 秒"是性能质量属性指标，影响该指标的**缓存策略、调用链路长度、CDN 节点数**才是性能的敏感点。

1. **敏感点**
某个架构决策会显著影响**单一一项**质量属性。
> ⚠️ 严谨表达：不是"响应时间 0.5 秒是敏感点"，而是"影响响应时间的架构决策（如缓存策略、服务调用链路长度、CDN 节点数量）是性能的敏感点"。

2. **权衡点**
一个架构决策，**同时正向影响一个质量属性、负向影响另一个质量属性**。
> 举例：为提高可用性增加多副本；副本越多，一致性维护开销上升、性能下降。多副本部署就是可用性‑性能之间的权衡点。
> 💡 案例答题关键词：**权衡点一定至少涉及两个质量属性**。

3. **风险点**
当前某个架构决策，存在潜在负面后果，未来有可能引发质量属性问题。

**风险点示例**
| 架构决策 | 风险点说明 |
|----------|------------|
| 数据库单点部署 | 数据库故障导致整个系统不可用，是可用性风险点 |
| 消息中间件单点部署 | 所有事件依赖该中间件，一旦故障影响系统通信，是可用性风险点 |
| 微服务之间强耦合 | 一个服务变更影响多个服务，是可修改性风险点 |
| 缓存与数据库一致性策略不明确 | 可能导致脏读或数据错误，是一致性/可靠性风险点 |

4. **非风险点（无风险点）**
当前架构决策对于某项质量属性不会带来负面影响，是安全、可靠的选择。

**非风险点示例**
| 架构决策 | 非风险点说明 |
|----------|--------------|
| 使用成熟关系型数据库并配置主备 | 对可用性不构成明显风险 |
| 用户界面采用统一组件库 | 对可修改性通常无明显负面影响 |
| 对日志进行异步写入 | 合理设计下不会显著影响核心业务可用性 |

> 考试若问"指出风险点和非风险点"，按**决策 + 影响 + 质量属性**三要素写。

### 非风险点答题模板（防漏分必背）
> 考试中若问"指出风险点和非风险点"，很多考生只写风险点、不写非风险点，或把非风险点写成"优点"。非风险点 ≠ 优点，而是"某项架构决策对特定质量属性**不会带来负面影响**"的判断。务必用下面模板写出"决策 + 质量属性 + 策略 + 为什么无风险"。

**通用模板**：
> 【架构决策，如：数据库主备部署】对于【质量属性，如：可用性】而言属于非风险点。因为该决策采用了【具体策略，如：冗余机制】，能够有效避免【潜在风险，如：单点故障】，在当前业务量级下不会造成负面影响。

**示例**：
> 采用 Redis 集群部署对于系统可用性而言属于非风险点。因为集群模式提供了数据分片与副本冗余，有效避免了缓存单点故障导致的数据丢失和服务中断，在当前并发量级下不会造成可用性风险。

> 速记口诀：
> 敏感点→影响一个属性（决策层面）；
> 权衡点→一升一降两个属性；
> 风险点→有隐患（决策+影响）；
> 非风险点→无隐患。

## 6.10.4 效用树（标准考试写法）
效用树是ATAM中用来梳理质量属性需求的树形工具，标准结构：

```
效用(Utility)                         ← 根节点：系统整体效用目标
├── 质量属性（一级）：性能 / 可用性 / 可修改性 / 安全性 / 可测试性 …
│   ├── 质量属性场景（二级）：如"高峰查询响应<500ms"
│   │   └── 叶子节点：标注 场景优先级(H/M/L) + 实现难度(H/M/L)
```

> 考试答题建议写清楚三层含义：
> 1. 根节点 = 系统整体效用；
> 2. 第二层 = 质量属性；
> 3. 第三层 = 具体质量属性场景；
> 4. 叶子节点可标注**场景优先级**与**实现难度**（如 (H,H) 表示高优先级、高难度）。

若题目要求标优先级，常见标注：
```
性能(H) ── (i)查询<0.3s (H,M)
可用性(H) ── (b)故障切换 (H,H) ── (j)3分钟发现 (M,M)
```
> 考试一般不会要求画完整树；常考：根据效用树找出敏感点、权衡点。

# ## 6.13 权衡思维专项训练（案例答题得分灵魂） 6.11.1 什么是权衡
几乎所有架构改进方案，都是**有所得必有所失**。
答题只写收益，不写代价，只能拿到一半分数；完整回答必须写出权衡。

## 6.11.2 历年真题高频权衡组合
1. 可用性 ↑ → 成本↑、复杂度↑、性能↓
2. 可修改性 ↑ → 性能往往 ↓
3. 安全性 ↑ → 性能下降、开发复杂度上升
4. 一致性 ↑ → 系统可用性、性能下降（CAP理论）

## 6.11.3 万能权衡答题句式（可直接套用）
> 方案A能够提升系统XX方面的质量属性；但是该方案会带来XX代价，需要在架构设计时进行权衡。

示例：
> 引入微服务架构，能够提升系统的可修改性与可用性；但是大量远程调用会降低系统性能，并且带来分布式事务问题，需要进行权衡。

## 6.13.2 中型场景分析练习题（优缺点+权衡分析）
### 题目场景
某传统单体管理系统，打算重构为微服务架构。请从可修改性、性能、可用性三个角度分析重构之后带来的收益与代价，并写出一句权衡结论。

#### 参考高分作答
收益：
1. 可修改性：各个服务独立开发部署，业务迭代修改时只需要更新对应微服务，对其他模块影响小，可修改性得到提升。
2. 可用性：单个微服务故障可以隔离，不会造成整个系统瘫痪，整体可用性提升。

代价：
1. 性能：服务之间大量远程网络调用，相比单体会带来额外网络开销，整体性能下降。
2. 增加分布式事务、服务治理、链路排查的复杂度。

权衡结论：
> 采用微服务架构能够提升系统可修改性和可用性；但是会带来性能下降与分布式事务复杂等代价，需要架构设计中进行权衡。

## 6.13.3 完整历年试题‑1真题 · 五步深度解析范例
> 真题来源：系统架构设计师案例分析试题一（必答题）

### 【真题题干】
某软件公司拟开发一套线上教育平台，初期采用单体分层架构。随着用户规模快速增长，出现模块迭代困难、某一个业务故障会造成整个平台不可用等问题。项目组计划将系统重构为事件驱动架构，采用发布订阅模式完成模块之间的通信。

问题1（6分）：
请简述分层架构与事件驱动架构的主要区别。

问题2（9分）：
从可修改性、可用性、性能、可测试性四个质量属性角度，分析重构为事件驱动架构之后可能带来的收益与代价。

问题3（10分）：
项目组引入消息中间件作为事件总线。该决策被评估为可用性‑性能之间的权衡点。请解释什么是权衡点，并结合本项目说明为什么该决策属于权衡点。

> ----------------------
> 📖五步解析法示范（解题思考过程）

#### 第1步：题干线索标注（从原文抓取关键信息）
1. 现状：单体分层架构 → 迭代困难、单点故障导致整体瘫痪
2. 改造方案：事件驱动、发布‑订阅
3. 新增组件：消息中间件事件总线
4. 关键词：权衡点、可用性‑性能

#### 第2步：解题思路推导
问题1：对比两种架构核心通信方式、耦合度。
问题2：直接使用文档内【架构风格‑质量属性对照表】，逐条对应收益代价；**必须结合线上教育平台场景，不能只默写理论**。
问题3：先默写权衡点定义；再分析：消息中间件如何提升可用性，同时对性能造成负面影响。

#### 第3步：高分参考答案
##### 问题1参考答案
1. 分层架构：模块按照层级划分，模块之间通过显式调用完成通信，依赖关系明确；上层可调用下层，耦合较强。
2. 事件驱动架构：模块之间采用发布‑订阅、隐式调用；发布方不需要知道订阅方信息，模块之间解耦。

##### 问题2参考答案
1. 可修改性（收益）：业务模块之间解耦，新增、修改下游业务模块不会改动发布方代码，可修改性提升。
2. 可用性（收益）：模块之间异步解耦，单个订阅模块故障不会反向影响发布方，故障得到隔离，可用性提升。
3. 性能（代价）：事件消息经过中间件转发，产生异步延迟；高并发场景下消息队列堆积可能造成响应变慢，带来性能损耗。
4. 可测试性（代价）：异步事件链路执行顺序不可见，模块之间执行时序难以追踪，系统整体可测试性下降。

##### 问题3参考答案
权衡点：一个架构决策，同时正向影响一个质量属性，并且负向影响另一个质量属性。
本项目中引入消息中间件：
- 正向收益（可用性）：实现事件异步解耦，隔离故障，提升系统可用性；
- 负面代价（性能）：消息转发、队列存储带来额外开销，会降低系统性能。
因此，该决策是可用性‑性能二者之间的权衡点。

#### 第4步：失分陷阱提醒（避坑）
1. ❌低分坑：只罗列事件驱动通用优缺点，完全不提线上教育平台场景，会被扣一半分数。
2. ❌低分坑：回答权衡点的时候，只写收益，不提代价；不属于权衡点，直接丢分。
3. ❌低分坑：答题时说事件驱动一定可以提升性能，违背架构规律。

# 6.15 AI 系统架构风格映射表（应对 2026 新大纲 · AI 新场景）
> 2026 年新大纲强化 AI，第一题大概率仍考经典架构，但**题干背景**极可能变成"大模型训练平台""智能推荐系统""RAG 私有知识库"。
> 当题干出现"大模型、训练、推理、RAG、Agent"等字眼时，按下表逻辑匹配架构风格，做到"看到关键词就想到风格"。

| AI 场景特征 | 对应架构风格 | 答题逻辑（为什么） |
|------------|--------------|--------------------|
| 训练平台（解析 Python 代码、动态调度 GPU 资源） | **解释器风格**（虚拟机风格子类） | 系统需要"解释"执行用户提交的脚本/规则，而非直接编译执行；解释引擎屏蔽底层硬件差异，动态匹配资源 |
| 推荐系统 / 推理流水线（数据清洗 → 特征提取 → 预测 → 结果输出） | **管道‑过滤器风格**（数据流风格） | 数据像流水一样经过多个独立的处理阶段（过滤器），每个阶段职责单一、可插拔 |
| RAG 检索增强生成（向量检索 + 大模型生成） | **仓库风格 / 数据中枢** | 向量数据库作为核心"仓库"，检索服务与 LLM 生成服务围绕数据进行读写 |
| 智能体 Agent 协作（多个 AI 模型协同完成任务） | **黑板风格 / 事件驱动** | 多个专家模型（知识源）围绕共享上下文（黑板）协同工作，无固定流程；或组件间通过事件异步协作 |

> **一句话考点速记**：看到"解析代码/规则"想**解释器**；看到"数据一步步处理"想**管道‑过滤器**；看到"多模型协作"想**黑板**；看到"向量库做核心存储"想**仓库**。

### 6.15.1 RAG 系统的典型权衡考点（新大纲高频预测）
RAG 流程：文档 → 切块 → Embedding → 向量检索 → Prompt 组装 → 大模型生成。
- 该数据流本质是**管道‑过滤器架构风格**：每个处理环节作为独立过滤器，文档 / 向量数据沿管道依次流转。
- **经典权衡点**：Top‑K 召回数量。
  - 增大 Top‑K → 召回知识片段变多 → 问答**准确性（质量属性）提升**；
  - 但检索数据量变多 → 增加查询时延 → **性能下降**；
  - 因此是**准确性‑性能之间的权衡点**（权衡点必须"一升一降"两个质量属性冲突）。

> 💡 答题模板（RAG 权衡点）：权衡点是影响多个质量属性且效果冲突的架构决策。增大向量检索 Top‑K 参数，召回知识片段增多，问答准确性提升；但检索数据量增大，查询时延增加，性能下降。因此是准确性与性能之间的权衡点。

### 6.15.2 AI 场景质量属性识别提示
- "训练任务 1 分钟内分配 GPU" → 性能；
- "新增 GPU 型号无需改核心代码" → 可修改性；
- "恶意代码检测拦截" → 安全性；
- "支持从 x86 迁移到 ARM" → 可修改性（可移植性）；
- "模型推理 P99 延迟 ≤ 2 秒" → 性能；
- "多 Agent 协同失败可回滚" → 可用性。
