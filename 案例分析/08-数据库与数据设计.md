# 1 数据库设计基础考点
数据库设计分为：需求分析 → 概念结构设计(E‑R图) → 逻辑结构设计 → 物理结构设计 → 实施 → 运行维护。

案例当中最常考**物理优化阶段**的手段：
- 创建索引
- 反规范化（增加冗余字段、合并表）
- 数据分片
- 读写分离
- 分库分表

> 💡答题口诀：逻辑设计关注范式减少冗余；物理设计优先查询性能，可以牺牲范式。

## 1.5 索引优化核心知识点

> **四者关系总览（先建立层级，别把概念放错层）**：
> **B+ 树是"数据结构/载体"**（索引的物理形态），**聚簇索引与二级索引是"索引类型/实例"**（都长成 B+ 树，区别只在叶子节点里装什么）。
> 聚簇索引是"主索引 = 数据本身"，二级索引是"辅助索引 = 指向主键"，二者通过**回表**联动。
> 记忆句：**B+ 树是地基，聚簇索引是正房（叶子存整行），二级索引是偏房（叶子存主键）。**

### 1.5.1 B+树索引

主流关系数据库（MySQL-InnoDB）默认索引结构为 B+树。

- 全部真实数据保存在叶子节点；
- 叶子节点之间使用双向指针相连，非常适合范围查询；
- 查询磁盘 IO 次数≈树高度，一般 3‑4 次 IO 即可查到目标数据。

### 1.5.2 聚簇索引 VS 非聚簇索引

1. **聚簇索引**：索引叶子节点存放完整的一行数据；一张表只能有 1 个聚簇索引，InnoDB 主键就是聚簇索引。
2. **非聚簇索引（二级索引）**：叶子节点存储索引列 + 主键；查到后需要回到主键索引读取完整数据，这个过程称为**回表**。

### 1.5.3 高频优化索引类型

- **覆盖索引**：查询所需要的全部字段都包含在索引内，不需要回表读取数据行，大幅减少 IO 开销。
- **索引下推（ICP）**：存储引擎层利用索引提前过滤不满足条件的数据，减少回表次数。

### 1.5.4 创建索引基本原则

- 在 WHERE、JOIN、ORDER BY、GROUP BY 字段建立索引；
- 区分度极低的字段（性别、状态标记）不宜单独建索引；
- 更新非常频繁的列不宜建立过多索引；
- 联合索引严格遵守**最左前缀匹配原则**。

### 1.5.5 索引失效常见场景（答题高频坑）

1. 在索引字段上使用函数、算术运算；
2. 隐式类型转换，字符串字段传入数字；
3. 前导通配符模糊查询 `like '%xxx'`；
4. 联合索引查询不满足最左前缀。

> 💡答题金句：虽然创建了索引，但是发生索引失效、频繁回表，查询速度依然缓慢，可以采用覆盖索引进行优化。

### 1.5.6 联合索引字段顺序设计（高频答题点）

1. 等值查询字段放前面；
2. 区分度高的字段放前面；
3. 范围查询字段放后面；
4. 排序字段、分组字段尽量纳入联合索引；
5. 尽量覆盖查询字段，减少回表。

示例：
```sql
-- 高频条件：a 等值、b 等值、c 范围
SELECT * FROM t WHERE a=1 AND b=2 AND c>10;
-- 推荐：(a, b, c)
CREATE INDEX idx_ab ON t(a, b);
```
若范围查询字段在中间，则后续字段无法继续利用索引：
```sql
-- c 为范围查询，放在中间后，d 通常无法继续利用索引
SELECT * FROM t WHERE a=1 AND c>10 AND d=2;
-- 索引 (a, c, d) 中，c 为范围，d 通常无法走索引
```

### 1.5.7 索引失效的严谨表述

| 情况 | 是否走索引 |
| --- | --- |
| `LIKE 'abc%'` | 可能使用索引（前缀匹配） |
| `LIKE '%abc'` | 通常无法利用索引定位 |
| `LIKE '%abc%'` | 通常无法利用索引定位 |

注意：若查询字段全部包含在索引中，仍可能走覆盖索引扫描。

> 考试答题建议写：前导模糊查询无法利用 B+ 树索引进行快速定位，可能导致索引失效或退化为全索引扫描/全表扫描。

### 1.5.8 三者关系对比表（聚簇 vs 二级，默写级）

| 比较维度 | 聚簇索引（主键索引） | 二级索引（普通/唯一/联合索引） |
| --- | --- | --- |
| 底层结构 | B+ 树 | B+ 树（**与聚簇同一套结构，只是叶子内容不同**） |
| 叶子节点存什么 | **完整数据行**（所有列） | **索引列 + 主键值** |
| 一张表有几个 | **只能 1 个** | 可以有多个 |
| 是否需要回表 | 不需要（一次命中） | 大概率需要（除非覆盖索引） |
| 物理顺序 | 数据行按主键顺序物理存放 | 索引逻辑有序，数据行不动 |
| 典型场景 | `WHERE id = ?` | `WHERE name = ?`、`WHERE a=? AND b=?` |

### 1.5.9 InnoDB 聚簇索引的生成规则（易被忽略的送分点）

**聚簇索引是"强制存在"的**，InnoDB 按下述优先级自动选择：

1. 显式定义了 `PRIMARY KEY` → **主键即聚簇索引**；
2. 没有主键 → 选**第一个非空且唯一**的列（`NOT NULL UNIQUE`）作为聚簇索引；
3. 都没有 → InnoDB **自动生成隐藏列 `ROW_ID`** 作为聚簇索引（用户不可见、不可用）。

**二级索引是"选修"的**，但有两个隐式来源（考试挖坑点）：

| 写法 | 是否自动创建二级索引 |
| --- | --- |
| `PRIMARY KEY (id)` | 创建的是**聚簇索引** |
| `KEY / INDEX idx_name (name)` | ✅ 显式二级索引 |
| `phone VARCHAR(20) UNIQUE` | ✅ **隐式创建二级索引**（唯一索引） |
| `FOREIGN KEY (dept_id) REFERENCES dept(id)` | ✅ **自动创建二级索引**（加速外键检查） |
| 只写 `id INT PRIMARY KEY`，其余列不写 KEY | ❌ **没有任何二级索引**，该表只有聚簇索引 |

> 💡 **高频考点**：若表只有主键索引，执行 `SELECT * FROM user WHERE name='张三'` **能跑，但走全表扫描**（沿聚簇索引叶子节点链表逐行比对），数据量大时性能极差 → 需为 `name` 建二级索引。
>
> 💡 **延伸高频问法**："为什么推荐自增 ID 做主键而不用 UUID？"
> 答：聚簇索引叶子节点存放完整数据行，且**数据行按主键物理顺序存放**。自增 ID 顺序插入，只在 B+ 树尾部追加，**页分裂少**；UUID 随机无序，插入时频繁在 B+ 树中间位置插入，导致**大量页分裂、磁盘碎片与随机 IO**，写入性能与空间利用率都差。

### 1.5.10 物理页级查找过程与 IO 次数对比（理解"回表"的代价）

以表 `user(id PK, name, age, KEY idx_name(name))`、10 万行数据为例：

| 场景 | SQL | 查找路径 | IO 次数 |
| --- | --- | --- | --- |
| **聚簇索引查找** | `SELECT * FROM user WHERE id=520` | 根页 → 中间层页 → 叶子页（**数据页，直接含整行数据**） | 约 **3~4 次**（= 树高） |
| **二级索引 + 回表** | `SELECT * FROM user WHERE name='赵六'` | 二级索引树（根→中→叶，叶子只有 `(name, id)`）→ **拿到 id 后重新走一遍聚簇索引树** | 约 **6~8 次**（两棵树高度之和） |
| **二级索引 + 覆盖索引** | `SELECT id, name FROM user WHERE name='赵六'` | 二级索引树（根→中→叶），叶子页里 `id`、`name` 全都有，**直接返回** | 约 **3~4 次**（不回表） |

> **结论（答题句）**：只要查询条件走的是非主键二级索引，且 `SELECT` 后的字段**不在索引内**（典型是 `SELECT *`），就必然发生回表，IO 次数近似翻倍。优化方向是**避免 `SELECT *`，建立覆盖索引**。

### 1.5.11 覆盖索引 vs 索引下推 ICP（高频辨析）

**覆盖索引（Covering Index）**：
- 定义：**查询需要的所有字段都包含在索引里**，在二级索引叶子节点即可取到全部数据，**无需回表**；
- 判据：看 **SELECT 后面的字段列表**；
- 标志：执行计划 `Extra = Using index`；
- 例子：`KEY idx_name_age(name, age)` → `SELECT age FROM user WHERE name='张三'` 覆盖；`SELECT *` 不覆盖。

**索引下推（ICP，Index Condition Pushdown，MySQL 5.6+）**：
- 定义：把原本由 Server 层做的**索引字段筛选**，**下推到存储引擎层**执行；在**回表之前**就用索引页里的字段把不满足条件的记录丢掉，从而减少回表行数；
- 判据：看 **WHERE 里无法完全匹配索引的条件**（联合索引的范围列之后、前缀模糊匹配等）；
- 标志：执行计划 `Extra = Using index condition`；
- 经典例子：

```sql
-- 假设联合索引 (name, age)
SELECT * FROM user WHERE name LIKE '张%' AND age = 20;
```

| 是否开启 ICP | 执行过程 | 回表次数 |
| --- | --- | --- |
| 关闭 | 引擎取出所有 `name LIKE '张%'` 的 id（假设 10 万个）→ **全部回表** → Server 层再过滤 `age=20` | 10 万次 |
| 开启（默认） | 引擎在索引叶子页里**先判断 `age=20`**，丢弃不符的 → 只回表符合条件的少数记录 | 极少（本例 100 条级别） |

**对比表（考试默写）**：

| 对比维度 | 覆盖索引 | 索引下推（ICP） |
| --- | --- | --- |
| 解决什么问题 | **省掉回表动作**（查完二级索引就结束） | **减少回表行数**（回表前先过滤） |
| 针对 SQL 的哪部分 | **SELECT 后的字段列表** | **WHERE 后的筛选条件** |
| 生效前提 | 查询字段全部落在索引内 | 联合索引 + 存在无法精确匹配的条件（范围/前缀模糊） |
| 作用层次 | Server 层（优化器决定不回表） | **存储引擎层**（InnoDB 提前过滤） |
| 一句口诀 | "查询列全在索引里" | "联合索引 + 范围/前缀模糊 + 等值条件" |

### 1.5.12 慢 SQL 诊断题专用答题模板（案例题高频题型）

**先明确案例题的考查边界（避免复习过度或过浅）**：

- ❌ **不考**：B+ 树节点分裂/旋转的具体算法、叶子页的物理页号、精确的磁盘 IO 次数计算；
- ✅ **考**：给一段慢 SQL 或 EXPLAIN，判断**为什么慢**（索引失效 / 频繁回表 / 排序无法用索引），并给出**优化方案**。

**诊断题四步答题法（按点给分，直接套）**：

```
① 定位问题（2~3 分）：该 SQL 缓慢的原因是……
   候选要点：索引列上使用函数/运算 → 索引失效；
            隐式类型转换 → 索引失效；
            前导 % 模糊匹配 → 无法定位；
            违反最左前缀（跳过中间列 / 范围列之后的字段失效）；
            区分度极低的列建索引（性别、状态标记）→ 选择性差；
            SELECT * + 二级索引 → 频繁回表，随机 IO 剧增；
            排序/分组字段未纳入索引 → Using filesort。
② 给出方案（4~6 分）：建议……
   候选要点：改写 SQL，去掉索引列上的函数（YEAR(date)=2026 → BETWEEN）；
            避免 SELECT *，只查必要字段；
            建立覆盖索引（条件字段 + 查询字段一并入索引）；
            调整联合索引顺序：等值在前、区分度高在前、范围在后、排序字段纳入；
            为排序/分组字段单独建索引或纳入联合索引；
            深度分页改为游标分页。
③ 说明代价（1~2 分）：索引会带来额外存储空间与写入维护成本，
                      索引数量应适度控制。
④ 效果总结（1 分）：可减少全表扫描与回表次数，降低磁盘 IO，提升响应速度。
```

**万能答题金句（不会编时直接套）**：

> "当前查询虽然存在索引，但由于（索引列上使用函数 / 隐式类型转换 / 违反最左前缀匹配 / 范围查询阻断后续字段 / 区分度低）导致索引失效或频繁回表。建议修改查询条件，或将查询字段一并纳入索引建立覆盖索引 (xxx, xxx)，以减少回表次数与磁盘 IO 开销；必要时调整联合索引字段顺序，遵循'等值在前、范围在后'的原则，并将排序字段纳入索引以避免 Using filesort。"

# 2 规范化与反规范化
## 2.1 规范化（1NF、2NF、3NF、BCNF）
规范化目标：减少数据冗余，消除插入异常、删除异常、修改异常。
代价：表变多，查询时需要多表连接 join，查询性能下降。

## 2.2 反规范化
反规范化：**适当增加冗余数据，降低多表连接，换取查询性能提升**。
常见实现手段：
1. 增加冗余列：在一张表中加入其他表的字段，减少join；
2. 增加派生列：存储计算后的结果字段（如订单总金额）；
3. 合并表：将经常一起查询的多张表合并为一张大表；
4. 拆分表（垂直拆分）：将很少访问的字段拆分出去。

### 反规范化收益 & 代价对照表
|方案|收益|代价|
|---|---|---|
|反规范化|减少多表连接开销，查询性能提升|数据冗余上升；存在数据不一致风险；更新成本变高|

> ⚠️核心权衡考点：反规范化以**牺牲数据一致性、增加存储冗余**为代价换取查询性能。
> 案例答题万能权衡句：
> 通过反规范化可以提升查询性能，但是带来数据冗余，存在数据不一致风险，需要进行权衡。

## 2.3 反规范化后的一致性维护方案（常考追问）

采用反规范化增加冗余字段后，往往被追问"如何保证数据一致性"。常见维护方案：

| 方案 | 说明 |
| --- | --- |
| 事务内同步更新 | 业务更新主表时，在同一事务中同步更新冗余字段 |
| 数据库触发器 | 主表数据变化时，由触发器自动更新冗余表或冗余字段 |
| 物化视图 | 定期或实时刷新预计算结果 |
| 定时任务同步 | 定时批量更新冗余字段，实现简单，但实时性较差 |
| 消息队列异步同步 | 业务完成后发送消息，异步更新冗余数据，提高吞吐量 |
| Binlog 监听同步 | 通过 Canal 等组件监听数据库变更，异步更新冗余数据 |

> 答题金句：反规范化通过增加冗余字段减少多表连接，提高查询性能；但冗余字段可能与源数据不一致，需要通过事务同步、触发器、定时任务、消息队列或 Binlog 监听等方式维护一致性。

# 3 数据库分片（水平分片、垂直分片）
## 3.1 垂直分片（纵向拆分）
- 规则：按**字段列**拆分；一张大表拆成多张表，字段互不相同，通常保留相同主键以便关联查询。
- 例子：用户表拆分为 用户基础信息表、用户详情扩展表。
- 收益：减少IO、减少锁冲突；热点字段独立；
- 代价：查询完整数据需要多表join。

## 3.2 水平分片（横向拆分）
- 规则：按**行数据**拆分；每张分片表字段结构完全一样，数据行不一样。
- 分片策略：范围分片、哈希分片、列表分片。
- 例子：订单表按年份分片，订单2023、订单2024。
- 收益：单表数据量变少，查询速度提升；可分散存储到多台数据库节点；提升可用性。
- 代价：跨分片查询、跨分片事务变得复杂。

> 速记口诀：垂直切字段，水平切行记录。

## 3.3 分片键选择策略

分片键即水平分片时用来拆分数据的字段。

### 分片键选择原则

1. 字段取值分布均匀，避免热点分片；
2. 保证绝大多数查询条件携带分片键，减少跨分片查询；
3. 业务查询模式匹配：哈希分片适合随机单点查询；范围分片适合时间类范围查询；
4. 预留后期扩容方案，优先考虑一致性哈希降低扩容时数据迁移量。

> 反面案例：选择日期作为分片键，新生成数据全部落在最新分片，产生写入热点。

## 3.4 全局唯一 ID 与分片扩容迁移

### 3.4.1 全局唯一 ID
水平分片后，单库自增主键无法保证全局唯一，需要引入全局 ID 生成机制：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| UUID | 本地生成，简单 | 无序，占用空间大，不适合作为 InnoDB 主键 |
| 数据库号段模式 | 简单，性能较好 | 依赖数据库，需考虑高可用 |
| Redis 自增 | 性能高 | 依赖 Redis 可靠性 |
| Snowflake 雪花算法 | 趋势递增，性能高 | 依赖机器时钟，可能时钟回拨 |
| 分布式 ID 生成服务 | 统一管理 | 架构复杂度提高 |

> 答题句：水平分片后，单库自增主键无法保证全局唯一，需要引入全局唯一 ID 生成机制，如号段模式、雪花算法或独立 ID 生成服务。

### 3.4.2 分片扩容方案
- 预分片：提前创建过多分片，后续迁移分片；
- 一致性哈希：减少节点变化时数据迁移；
- 双写迁移：新旧分片双写，历史数据迁移后切换；
- 扩容后按规则重路由：适合范围分片或固定分片数量场景。

> 答题句：分片扩容可采用预分片、双写迁移、一致性哈希等方式，以减少数据迁移量和业务影响。

## 3.5 水平分片后的复杂查询问题

水平分片会带来：非分片键查询困难、跨分片 JOIN 困难、跨分片分页排序困难、跨分片聚合统计困难、分布式事务复杂。

非分片键查询常见方案：
- 建立映射表；
- 异构索引表；
- 搜索引擎支持，如 Elasticsearch；
- 数据冗余存储，按不同维度分片；
- 基因法：例如订单 ID 中嵌入用户 ID 分片因子。

> 示例：订单按用户 ID 分片，但需要按订单号查询，可在订单号中嵌入用户 ID 分片因子，这样根据订单号也能定位分片。

> 答题句：水平分片后，若查询条件不包含分片键，可通过映射表、异构索引表、搜索引擎或基因法等方式支持查询，但会增加系统复杂度和数据一致性维护成本。

# 4 读写分离架构
## 架构组成
1. 主库（Master）：负责接收**写操作（增删改）**
2. 从库（Slave）：负责接收**读操作（查询）**
主库的数据通过复制同步到各个从库。

### 收益
1. 读写压力分离，读请求分摊到多个从节点，提升查询性能；
2. 从库可以在一定程度上提高可用性，并可作为故障切换或备份恢复的基础，但不能替代完整的数据备份机制。

### 代价 & 考点坑点
1. **主从同步延迟（最常考）**：写完成立刻去从库查询，可能读到旧数据；
2. 增加架构复杂度；
3. 数据一致性问题（最终一致性而非强一致性）。

> 答题高频场景：用户提交表单之后立刻刷新页面看不到刚提交的数据 → 大概率是读写分离同步延迟。

## 4.1 主从复制方式与一致性读策略

### 4.1.1 主从复制方式
| 复制方式 | 特点 |
| --- | --- |
| 异步复制 | 主库提交后不等待从库确认，性能好，但可能丢数据 |
| 半同步复制 | 主库提交后等待至少一个从库确认接收日志，一致性增强 |
| 全同步复制 | 主库等待所有从库执行完成，一致性高但性能差 |

> 答题句：主从复制通常为异步复制，存在延迟；对一致性要求较高时，可采用半同步复制，或在关键业务查询主库。

### 4.1.2 一致性读策略
- **强一致读**：写后立即读，强制走主库；
- **会话一致性**：同一用户会话内，写后读走主库；其他读请求走从库；
- **最终一致读**：普通读请求走从库，允许短暂延迟。

> 答题句：对写后立即读场景，可强制路由主库或采用会话一致性策略；对实时性要求不高的查询，可继续访问从库，以发挥读写分离性能优势。

# 5 事务与并发控制
## 5.1 ACID特性
原子性、一致性、隔离性、持久性

## 5.2 并发带来的四类问题
1. 丢失更新（两个事务同时修改，彼此覆盖）
2. 脏读（读到了其他事务未提交的数据）
3. 不可重复读（同一事务内多次读同一行，结果不一致，侧重行内数据变化）
4. 幻读（同一事务内多次范围查询，结果集行数发生变化，侧重新增/删除行）

> 注意：原资料常写"三类问题"，与隔离级别表不一致，考试须统一写四类：丢失更新、脏读、不可重复读、幻读。

### 5.2.1 快照读与当前读（MySQL InnoDB 常考）
- **快照读**：普通 `SELECT` 语句读取历史版本数据，通过 MVCC 实现，读不加锁。
  ```sql
  SELECT * FROM t WHERE id = 1;
  ```
- **当前读**：读取最新已提交数据，并可能加锁。
  ```sql
  SELECT * FROM t WHERE id = 1 FOR UPDATE;
  SELECT * FROM t WHERE id = 1 LOCK IN SHARE MODE;
  UPDATE t SET ... WHERE ...;
  ```

> 答题句：InnoDB 通过 MVCC 支持快照读，减少读写冲突；通过行锁、间隙锁支持当前读下的并发控制。

### 5.2.2 MySQL 默认隔离级别
MySQL InnoDB 默认隔离级别是**可重复读 Repeatable Read**；在 RR 级别下，InnoDB 通过 MVCC 和 Next‑Key Lock 在很大程度上避免幻读。

> 答题写"基本解决幻读/很大程度上避免幻读"更稳，不宜写绝对化表述。

## 5.3 四个隔离级别（从低到高）
1. 读未提交
2. 读已提交
3. 可重复读
4. 串行化

> 权衡规律：隔离级别越高 → 并发性能越低，一致性越好；
> 隔离级别越低 → 并发性能越高，越容易出现并发异常。

## 5.4 慢查询与 SQL 调优

### 5.4.1 慢查询日志

记录执行时长超过预设阈值的 SQL 语句，是定位慢 SQL 最基础手段。

### 5.4.2 EXPLAIN 执行计划，核心字段考点

- `type`：访问类型，性能从优到差：`system > const > eq_ref > ref > range > index > ALL`；目标至少达到 `range` 级别，ALL 代表全表扫描，需要优化。
- `key`：实际使用到的索引，NULL 表示没有用到索引。
- `rows`：预估扫描的数据行数，数值越大代价越高。
- `Extra`：
  - `Using index`：命中覆盖索引，性能优秀；
  - `Using filesort`：无法利用索引排序，额外文件排序，必须优化。

### 5.4.3 SQL 优化通用方案

1. 禁止 `SELECT *`，只查询业务需要字段；
2. 不要在索引列上进行计算；
3. 大分页 `offset` 过大，改用游标、书签方式分页；
4. 优先 JOIN，谨慎使用子查询；
5. `UNION ALL` 代替 `UNION`，省去去重开销。

### 5.4.4 JOIN 优化
- 小表驱动大表；
- JOIN 字段建立索引；
- JOIN 字段类型一致，避免隐式转换；
- 避免过多表 JOIN；
- 避免在 JOIN 条件中对字段做函数运算。

> 答题句：多表连接时，应尽量保证连接字段有索引，并减少不必要的连接表数量，避免因连接字段类型不一致导致索引失效。

### 5.4.5 深度分页优化
原 SQL：
```sql
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;
```
问题：需要扫描并跳过 100 万条记录，性能差。

优化（游标/书签分页/seek method）：
```sql
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 20;
```

> 答题句：深度分页场景下，`LIMIT offset, size` 会扫描并丢弃大量前置数据，导致性能下降。可基于上一页最后一条记录的主键或有序字段进行游标分页，减少扫描行数。

## 5.5 锁、MVCC、并发问题对照表

### 5.5.1 锁分类

1. **乐观锁**：不加锁，版本号校验冲突；适合读多写少场景；
2. **悲观锁**：访问前加锁；适合写冲突高场景；
3. **行锁**：锁住单行记录；InnoDB；
4. **间隙锁**：锁定索引间隙，用于防止幻读。

### 5.5.2 四大隔离级别与并发问题对应关系

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | ✅存在 | ✅存在 | ✅存在 |
| 读已提交 | ❌解决 | ✅存在 | ✅存在 |
| 可重复读 | ❌解决 | ❌解决 | InnoDB 通过 MVCC + Next‑Key Lock 很大程度上避免幻读 |
| 串行化 | ❌解决 | ❌解决 | ❌解决 |

> MVCC（多版本并发控制）：生成数据快照版本，读不加锁，提升并发性能；读已提交、可重复读底层依靠 MVCC 实现。

# 6 分布式数据库高频概念
## CAP理论
在分布式系统中，一致性(C)、可用性(A)、分区容错性(P)三者**不能同时全部满足**。
分区容错P不可放弃，只能在C与A之间二选一。
- CP：优先一致性，牺牲可用性
- AP：优先可用性，牺牲强一致性，采用最终一致性

## BASE理论
Basically Available（基本可用）、Soft‑state（软状态）、Eventually consistent（最终一致性）
互联网分布式系统一般遵循BASE，接受最终一致性。

## 6.3 云原生数据库与 NewSQL

传统手动分库分表缺点：应用层侵入、分片规则修改困难、运维成本高。

### 云原生数据库（PolarDB、Aurora）

核心架构：**计算‑存储分离**

- 计算节点无状态，可快速弹性扩缩容；
- 底层存储分布式，自动分片；
- 优势：业务代码无需改动即可扩容，缓解读写分离同步延迟问题。

### NewSQL 数据库（TiDB、OceanBase）

特点：融合 NoSQL 水平扩展能力 + 传统数据库 ACID 事务能力

- 底层自动水平分片，不需要应用层手动分库分表；
- 支持分布式强一致性事务；
- 适用场景：海量数据同时又要求强一致性的业务。

> 💡答题场景判断：题干中分片规则频繁变更、运维压力大 → 优先推荐 NewSQL / 云原生数据库替代手动分库分表。

# 7 分布式事务与数据一致性方案

> CAP 理论给出了选择方向，本章给出工程落地方案。

## 7.1 两阶段提交 2PC

流程：协调者发起准备阶段 → 所有参与者执行事务但不提交；全部就绪后进入提交阶段。

- 优点：**强一致性（CP）**
- 缺点：同步阻塞性能差；协调者存在单点故障风险；第二阶段故障仍有可能出现不一致；
- 适用场景：金融短事务，一致性优先级高于性能。

## 7.2 三阶段提交 3PC

在 2PC 基础上拆分出预准备阶段，增加参与者超时机制，降低阻塞时长。

- 缺点：依然无法彻底消除数据不一致；工业界极少落地。

## 7.3 TCC（Try‑Confirm‑Cancel）

Try：预留锁定资源；Confirm：正式提交执行业务；Cancel：释放资源回滚补偿。

- 优点：性能高，无长事务锁等待；
- 缺点：业务侵入极强，需要手动编写补偿代码；
- 适用场景：电商下单扣减库存等高并发业务。

## 7.4 Saga 模式

将一个长分布式事务拆分成多条本地事务，每一步都编写逆向补偿操作。失败后执行补偿回滚。

- 优点：吞吐量高；
- 缺点：仅保证最终一致性，不保证隔离性；
- 适用场景：物流通知、优惠券发放等互联网业务。

### 7.4.1 TCC vs Saga：按"事务执行时长"选型（高频辨析）
原资料已分别介绍 TCC 与 Saga，但缺少"根据事务执行时长选型"这一关键维度。考场上题干描述"订单创建、库存扣减、物流调度、支付回调"这种长链条业务时，若选 TCC 会导致 Try 阶段锁资源太久、并发骤降，必挂；选 Saga 才是正解。

| 维度 | TCC | Saga |
| --- | --- | --- |
| 适用事务长度 | **短事务**、高并发 | **长事务**、跨多异构服务 |
| 资源锁定 | Try 阶段即锁定资源，长事务会长期占用 | 拆为本地短事务，完成即释放，不长期锁资源 |
| 一致性 | 最终一致（无长事务锁等待） | 最终一致（正向+反向补偿） |
| 典型场景 | 电商下单扣库存、秒杀等高并发短链路 | 订单+物流+支付回调等长链路编排 |

> 答题金句（长事务选 Saga）：因该分布式事务涉及多个异构服务且执行链路较长（长事务），不推荐 TCC（Try 阶段长事务会长期锁定库存等资源，降低并发）。建议采用 Saga 模式，将长事务拆解为多个本地短事务，通过正向操作与反向补偿（如订单取消时触发退款和释放库存）实现最终一致性，降低资源锁定时间。

## 7.5 本地消息表 + 消息队列

本地事务完成业务逻辑并写入一条待发送消息；独立进程轮询消息表投递 MQ；下游服务消费成功后回执更新消息状态。

- 优点：实现简单；
- 缺点：消息可靠性依赖消息队列。

> 💡答题万能权衡句：
> 如果业务需要强一致性，可选用 2PC，但会牺牲系统性能与可用性；业务允许短暂不一致，则优先选择 TCC、Saga、消息队列等最终一致性方案提升吞吐量。

## 7.6 可靠消息最终一致性、最大努力通知

### 7.6.1 可靠消息最终一致性（本地消息表的升级版）
流程：上游业务本地事务中写入业务数据和消息记录 → 通过可靠消息投递机制发送消息 → 下游消费消息并执行本地事务 → 消费失败则重试 → 最终达到数据一致。

> 答题句：可靠消息最终一致性方案通过本地事务保证业务数据与消息记录的一致性，再通过消息队列异步通知下游服务，适合对实时一致性要求不高但要求高吞吐的业务场景。

### 7.6.2 最大努力通知
适用于跨平台、跨系统通知，例如支付结果通知、银行回调、第三方支付通知商户系统。
特点：发起方多次重试通知；接收方也可以主动查询；只保证尽力通知，不保证强一致。

> 答题句：最大努力通知适用于跨系统、跨机构的数据一致性场景，一致性强度较低，通常还需要配合主动查询机制。

## 7.7 TCC 高频问题：幂等、空回滚、悬挂

TCC 在考试中若考到，很可能问风险与应对：
- **幂等**：Confirm 和 Cancel 可能被重复调用，必须保证幂等；
- **空回滚**：Try 未执行，但 Cancel 被调用（如 Try 请求超时，协调器触发 Cancel，但实际 Try 未到达服务方）。此时 Cancel 不能真正执行业务回滚，需要识别为空回滚；
- **悬挂**：Cancel 先执行，Try 后执行。若 Try 在 Cancel 之后才到达，不能再执行，否则资源被悬挂。

> 答题句：TCC 方案需要业务侧实现幂等、空回滚和悬挂控制，否则在网络超时或重试场景下可能导致数据异常。

# 8 缓存‑数据库一致性方案
## 方案1：先更新数据库，再删除缓存（Cache Aside 旁路缓存）
业界最推荐方案。

读流程：先读缓存 → 命中则返回 → 未命中则读数据库 → 将数据库数据写入缓存。
写流程：更新数据库 → 删除缓存。

为什么是删除缓存而不是更新缓存？
- 避免并发写导致缓存值覆盖错误；
- 删除缓存更简单；
- 避免无效计算，写多读少时更新缓存浪费资源。

风险：在极端并发和缓存失效叠加场景下，仍可能出现短暂不一致。可通过延迟双删、缓存删除重试、Binlog 异步删除等方式降低风险。

> 答题句：Cache Aside 模式采用更新数据库后删除缓存的策略，避免直接更新缓存在并发场景下产生脏数据，同时降低无效缓存更新成本。

## 方案2：先删缓存，再更新数据库
风险：高并发场景下容易出现脏数据。

## 8.1 其他写策略：Read/Write Through 与 Write Behind
- **Read Through**：缓存代理读取数据库，应用只和缓存交互；
- **Write Through**：写入缓存后，由缓存同步写入数据库；读写都经过缓存，缓存作为数据存储代理，实现较复杂，但可简化应用逻辑；
- **Write Behind / Write Back**：写缓存后不立即写数据库，异步批量写回数据库。优点：写入性能高、可合并写操作；缺点：数据可能丢失、一致性较弱。适用：日志、计数、监控指标等允许短暂不一致或可容忍少量丢失的场景。

## 8.2 延迟双删的严谨表述
先更新数据库再删除缓存仍可能在极端并发时序下出现短暂不一致。延迟双删可以降低部分场景下的不一致概率，但不能完全解决问题。更可靠的方式是结合 Binlog 订阅异步删除缓存、消息队列重试删除缓存等机制。

> 注意：延迟双删并非万能方案，考试若写得太绝对可能扣分。

## 一致性权衡总结
强一致性方案往往性能差；高性能方案只能做到最终一致性。

## 8.4 缓存三大高频问题

### 缓存穿透、击穿、雪崩

1. **缓存穿透**：查询缓存、数据库均不存在的数据；大量请求穿透缓存，直接打到底层数据库。
   - 解决方案：缓存空对象；布隆过滤器；参数合法性校验；接口限流。
2. **缓存击穿**：某一个热点 key 过期，海量并发请求瞬间打到数据库。
   - 解决方案：热点 key 永不过期；逻辑过期；互斥锁重建缓存；缓存预热。
3. **缓存雪崩**：大批量缓存 key 同一时刻过期；缓存整体失效，数据库压力瞬间过载。
   - 解决方案：过期时间加随机值；多级缓存；缓存预热；服务限流降级；高可用 Redis 集群。

# 9 高频易混淆概念对比表
## 9.1 反规范化 VS 水平分片 VS 垂直分片
|方案|拆分对象|核心目的|副作用|
|---|---|---|---|
|反规范化|不拆分表，增加冗余字段|优化查询，减少join|冗余，不一致风险|
|垂直分片|按字段列拆分表|减少单表IO压力|需要join查询完整信息|
|水平分片|按行拆分表|降低单表行数；扩容存储|跨分片查询复杂|

## 9.2 读写分离 VS 分库分表
- 读写分离：**不拆分数据**，主从复制，分担读压力；适合读多写少、单表数据量不大。
- 分库分表：**拆分数据**，把海量数据分散到多个库；适合单表千万级以上大数据量场景。

# 10 答题误区避雷清单
❌误区1：反规范化可以提升写入性能
✅正确：反规范化一般提升查询性能，写入更新代价上升（因需维护冗余字段）。但某些场景下也可能降低写压力，例如减少写后复杂查询、预计算统计值避免实时聚合；考试主流答案仍是"提升查询、增加写成本与一致性风险"最安全。

❌误区2：读写分离可以解决大数据量表查询慢问题
✅正确：读写分离只能分散读压力；单表数据量过大需要分库分表（水平分片）。

❌误区3：水平分片就是把字段拆开
✅正确：水平分片拆分行，所有分片字段完全一样；垂直分片拆分字段。

❌误区4：主从读写分离能够保证写完马上读到最新数据
✅正确：存在主从同步延迟，无法保证强实时。

# 11 范式识别答题专题

> 软考数据库选做题高频考点：E‑R 图转关系模式，判断范式等级，给出规范化改进方案。

## 11.1 范式快速判定口诀

- 1NF：属性不可再拆分，不存在复合字段；
- 2NF：满足 1NF；消除**非主属性对候选键的部分函数依赖**；主键为单字段则天然满足 2NF；
- 3NF：满足 2NF；消除**非主属性对候选键的传递函数依赖**；
- BCNF：满足 3NF；在满足 3NF 的基础上，进一步消除**主属性对候选键的部分和传递函数依赖**。

> 考试建议一律写"候选键"而非"主键"，表述更严谨。

### 11.1.1 范式判断标准（考试版）

| 范式 | 判断标准 |
| --- | --- |
| 1NF | 属性不可再分，每个属性都是原子值 |
| 2NF | 满足 1NF，并消除非主属性对候选键的部分函数依赖 |
| 3NF | 满足 2NF，并消除非主属性对候选键的传递函数依赖 |
| BCNF | 满足 3NF，并消除主属性对候选键的部分和传递函数依赖 |

## 11.2 范式答题万能模板

### 题目常见问法 1：判断当前关系最高属于第几范式，并说明理由

> 答题模板：该关系满足 xNF；但是存在 XX 依赖（部分依赖 / 传递依赖），不满足高一阶范式的要求，因此最高属于 xNF。

### 题目常见问法 2：将该关系分解至 3NF

> 答题模板：拆分出多张关系表；每张表消除传递依赖；标注每张表主键与外键。

## 11.3 函数依赖、候选键、主属性与非主属性（必考基础）

### 11.3.1 基本函数依赖概念
- **函数依赖**：若属性 A 的值能唯一确定属性 B 的值，则称 B 函数依赖于 A，记作 A → B。
  - 例如：学号 → 姓名；身份证号 → 姓名。
- **完全函数依赖**：若 A → B，且 B 不依赖于 A 的任何一个真子集，则称 B 完全函数依赖于 A。
  - 例如：（学号，课程号）→ 成绩，成绩完全依赖于整个复合主键。
- **部分函数依赖**：主键是复合主键时，非主属性只依赖于主键的一部分。
  - 例如：（学号，课程号）→ 商品名称，而商品名称只依赖于商品编号，属于部分依赖，导致不满足 2NF。
- **传递函数依赖**：若 A → B，B → C，且 B 不函数依赖于候选键 A，则 C 传递依赖于 A。
  - 例如：学号 → 学院，学院 → 学院地址，则学号 → 学院地址 为传递依赖，导致不满足 3NF。

### 11.3.2 候选键、主键、主属性、非主属性
- **候选键**：能够唯一标识元组的最小属性集。
  - 例如：学号和身份证号都能唯一标识学生，则两者都是候选键。
- **主键**：从多个候选键中选一个作为主键。
- **主属性**：包含在任何一个候选键中的属性。
- **非主属性**：不包含在任何候选键中的属性。

## 11.4 E‑R 图转关系模式规则与模板（常考）

### 11.4.1 转换规则
- **实体型转关系模式**：每个实体型转换为一个关系模式。
  - 例如：职工(职工编号, 姓名, 年龄)；部门(部门编号, 名称, 位置)。
- **1:1 联系**：可转为独立关系模式，或与任意一端实体合并。
  - 独立转换：管理(职工编号, 部门编号)，其中职工编号、部门编号都是候选键。
  - 若合并，通常把一方主键作为另一方外键。
- **1:N 联系**：在 N 端实体对应关系中加入 1 端主键作为外键。
  - 例如：部门与员工一对多：员工(员工编号, 姓名, 部门编号)，部门编号是外键。
- **M:N 联系**：必须转换为独立关系模式，主键由两端实体主键组成。
  - 例如：学生选课：学生(学号, 姓名)、课程(课程号, 名称)、选课(学号, 课程号, 成绩)；选课主键为 (学号, 课程号)，学号、课程号分别是外键。

### 11.4.2 答题模板
1. 实体转换为关系模式，实体主键作为关系主键；
2. 1:N 联系通常在 N 端实体对应关系中加入 1 端主键作为外键；
3. M:N 联系必须转换为独立关系模式，其主键由两端实体主键组成；
4. 若联系具有属性，则联系属性也加入对应关系模式中。

## 11.5 规范化拆分：保持无损连接与函数依赖

很多题会要求"分解为 3NF，并保持函数依赖和无损连接"。

> 答题句：规范化分解应尽可能保证无损连接和函数依赖保持。若仅满足 3NF 分解，通常可以保持函数依赖；若要求 BCNF，则不一定能同时保持函数依赖。

### 11.5.1 分解题必写的"加分话术"（避免只拿一半分）
软考官方教材判定范式分解正确性有两大定理：**无损连接性** 与 **函数依赖保持**。仅写出拆分后的 3NF 表往往只拿一半分，必须显式写出这两条检查结论。

- **无损连接性（Lossless Join）**：分解后的子关系通过自然连接可还原原始关系，不丢失、不增加信息。判定方法之一：存在某属性在 R1、R2 中均出现，且该属性是 R1 或 R2 的候选键（Chase 算法判定）。
- **函数依赖保持（Dependency Preservation）**：原关系中的所有函数依赖，在分解后的子关系中都被某一张子关系单独保持，无需跨表做额外连接才能验证约束。

> 答题金句（做完分解题后必写）：上述分解结果不仅满足 3NF 要求，且具有无损连接性（即通过自然连接可还原原始关系，不丢失信息），同时保持了函数依赖（即所有原始属性间的约束均在子关系中得以保留，无需额外的关联约束检查）。

# 12 数据仓库、ETL、星形模型、雪花模型

## 12.1 数据库 VS 数据仓库

- 业务数据库（OLTP 联机事务处理）：面向增删改日常业务；数据实时更新；
- 数据仓库（OLAP 联机分析处理）：面向统计分析报表；数据只读，定期批量导入；

## 12.2 ETL 流程

Extract（抽取源系统数据）‑Transform（清洗、转换）‑Load（加载进数据仓库）

## 12.3 两种多维建模模型

1. **星形模型**：1 张事实表，周围多张维度表；维度表之间互不相连；查询性能优秀；最常用。
2. **雪花模型**：事实表‑维度表‑子维度表；维度表继续规范化拆分；减少维度表冗余；但是查询需要更多 JOIN，性能下降。

> 答题权衡：星形模型查询性能高，但是维度表冗余；雪花模型冗余低，但查询复杂度上升。

## 12.4 缓慢变化维、事实表类型、OLAP 操作

### 12.4.1 缓慢变化维 SCD
维度数据会变化，例如用户地址变化、商品类目变化、组织机构变化。
| 类型 | 处理方式 |
| --- | --- |
| SCD Type 1 | 直接覆盖旧值，不保留历史 |
| SCD Type 2 | 新增记录，保留历史版本，最常用 |
| SCD Type 3 | 增加字段保存旧值，保留有限历史 |

> 答题句：维度数据发生变化时，可采用缓慢变化维策略处理。Type 1 直接覆盖，Type 2 保留历史版本，Type 3 增加字段保存部分历史。

### 12.4.2 事实表类型
| 类型 | 说明 |
| --- | --- |
| 事务事实表 | 记录业务事件，例如下单、支付 |
| 周期快照事实表 | 按固定周期记录状态，例如每日库存快照 |
| 累计快照事实表 | 记录业务生命周期关键节点，例如订单创建、支付、发货、完成 |

### 12.4.3 OLAP 基本操作
| 操作 | 含义 |
| --- | --- |
| 上卷 Roll‑up | 从细粒度汇总到粗粒度 |
| 下钻 Drill‑down | 从粗粒度到细粒度 |

| 切块 Dice | 固定多个维度取值范围 |

> 答题句：OLAP 支持上卷、下钻、切片、切块、旋转等多维分析操作。

## 13.2 中型场景分析题
### 场景
一个电商网站，读请求远大于写请求。项目组引入MySQL读写分离架构，1主3从。上线之后，用户提交订单，立刻刷新订单页面偶尔看不到刚生成的订单记录，请分析问题成因、收益代价，并给出改进方案。

#### 高分参考作答
成因：主库写入订单成功之后，数据还没有同步复制到从库；查询路由到从库，读取到旧数据，即主从同步延迟。

收益：
1. 读请求分发到三台从库，分担数据库查询压力，提升查询性能；
2. 从节点可作为备份，提升系统可用性。

代价：
1. 存在主从同步延迟，无法保证强一致性；
2. 架构复杂度上升，增加运维成本。

改进方案：
对于写入后立刻要读取的实时查询，强制查询主库；非实时查询走从库。

权衡结论：读写分离提升读性能，但是带来数据同步延迟，一致性下降的代价。

## 13.3 完整历年选做题真题‑五步解析范例
### 真题题干
某线上图书商城，初期数据库采用单库单表。随着用户规模增长，出现如下问题：
1. 图书订单表数据量超过2500万条，订单查询速度缓慢；
2. 网站商品详情页面访问量巨大，数据库读压力很高，写压力较小。

项目组给出两套优化方案：
方案A：引入读写分离架构，一主两从；
方案B：对订单表进行水平分片，按照用户ID哈希分片。

【问题1】（7分）
请分别说明方案A、方案B主要解决什么问题。
【问题2】（8分）
分析方案A带来的收益与代价。
【问题3】（10分）
采用方案B水平分片之后，请分析收益与代价。

---
#### ①题干线索标注
1. 订单表2500万条 → 单表海量数据，查询慢；
2. 读访问量大，写压力小 → 读多写少场景；
3. A方案：读写分离；B方案：订单表水平分片（用户ID哈希）。

#### ②解题思路推导
问题1：读写分离解决**读压力过高**；水平分片解决**单表数据量过大查询慢**。两个方案解决痛点不一样，不可混淆。
问题2：套用读写分离收益‑代价知识点，结合图书商城场景。
问题3：套用水平分片收益‑代价知识点，点明跨分片查询、分布式事务等代价。

#### ③高分参考答案
##### 问题1
方案A（读写分离）：将读请求分发到从库，减轻主库查询压力，解决网站商品详情页面读访问量巨大、读压力过高的问题；不能解决单表海量数据查询缓慢问题。
方案B（订单表水平分片）：将海量订单行数据拆分到多个分片，降低单表的数据量，解决订单表数据量过大、订单查询缓慢的问题。

##### 问题2‑方案A收益代价
收益：
1. 大量商品详情读请求分流至两台从库，减轻主库查询压力，提升查询性能；
2. 从库可以作为主库备份节点，提升数据库可用性。
代价：
1. 存在主从数据同步延迟，写后立刻查询有可能读到旧数据，牺牲一定数据一致性；
2. 增加主从复制运维复杂度。

##### 问题3‑方案B水平分片收益代价
收益：
1. 订单数据分散到多个分片，每个分片单表数据量下降，订单查询速度得到提升；
2. 数据分散存储，提升整体存储容量与可用性。
代价：
1. 如果查询条件不带用户ID分片键，则需要跨多个分片查询，查询复杂度上升；
2. 跨分片的事务实现难度大，分布式事务复杂度上升；
3. 分片之后架构运维复杂度增加。
补充：按用户 ID 哈希分片有利于用户维度查询，但订单号查询、时间范围查询、商家维度查询可能需要额外索引表、映射表或搜索引擎支持；水平分片后还需引入全局唯一 ID 生成机制替代单库自增主键。

#### ④失分陷阱提醒
1. ❌ 误区：读写分离能够解决单表千万条数据查询慢问题。读写分离无法减少单表行数；
2. ❌ 只写收益不写代价，缺少权衡分析丢失分值；
3. ❌ 将水平分片写成垂直分片。

#### ⑤答题模板沉淀
读写分离答题模板：
> 读写分离架构可分散读压力，提升查询性能与可用性；但是存在主从同步延迟，带来一致性方面的代价。

水平分片答题模板：
> 水平分片降低单表数据量，提升查询性能；但是带来跨分片查询、分布式事务复杂等代价。

# 14 答题模板合集（冲刺必背）

## 14.1 技术方案题万能模板
任何技术方案都可按以下结构作答：
1. **问题定位**：题干现象对应什么技术痛点；
2. **方案选择**：采用何种技术手段（给出名称）；
3. **收益**：该方案带来哪些正面效果；
4. **代价/风险**：带来哪些副作用、一致性/复杂度代价；
5. **适用场景/权衡结论**：什么场景适用，最终权衡结论。

## 14.2 反规范化答题模板
1. 指出手段：增加冗余字段/合并表，减少多表连接；
2. 收益：查询性能提升，减少 join；
3. 代价：数据冗余上升，存在不一致风险，写成本上升；
4. 一致性维护：事务同步、触发器、定时任务、消息队列或 Binlog 监听；
5. 结论：以一致性/存储为代价换查询性能，需权衡。

## 14.3 水平分片答题模板
1. 方案：按某分片键（哈希/范围）拆分数据到多个分片；
2. 收益：单表数据量下降，查询性能提升，可分散存储扩容；
3. 代价：跨分片查询、跨分片事务、跨分片聚合/分页复杂；
4. 补充：需全局唯一 ID；非分片键查询需映射表/异构索引/搜索引擎/基因法；
5. 结论：解决单表海量数据查询慢，代价是分布式复杂度上升。

## 14.4 垂直分片答题模板
1. 方案：按字段列拆分表，通常保留相同主键；
2. 收益：减少单表 IO、减少锁冲突、热点字段独立；
3. 代价：查询完整数据需多表 join；
4. 结论：缓解单表宽度与 IO 压力，代价是 join 复杂度。

## 14.5 读写分离答题模板
1. 方案：主库写、从库读，主从复制同步；
2. 收益：读压力分摊到多个从节点，查询性能与可用性提升；
3. 代价：主从同步延迟，无法保证写完立即读到最新，一致性下降；
4. 应对：写后强一致读走主库，或采用会话一致性；关键场景用半同步复制；
5. 结论：提升读性能，代价是数据同步延迟与一致性。

## 14.6 缓存一致性答题模板
1. 方案：Cache Aside，更新数据库后删除缓存；
2. 收益：避免并发写脏数据，降低无效缓存更新成本；
3. 风险：极端并发下仍可能短暂不一致；
4. 应对：延迟双删、删除重试、Binlog 异步删除；
5. 结论：高性能方案做到最终一致性，强一致需付出性能代价。

## 14.7 分布式事务答题模板
1. 强一致场景：2PC（牺牲性能/可用性，金融短事务）；
2. 最终一致场景：**TCC（高性能，适合短事务/高并发，需幂等/空回滚/悬挂）、Saga（长事务补偿，适合跨多异构服务的长链路）、本地消息表/可靠消息（高吞吐）**；
3. 选型关键维度——事务执行时长：短事务/高并发选 TCC，长事务/多服务编排选 Saga；
4. 跨系统：最大努力通知（配合主动查询）；
5. 结论：按一致性要求、性能与事务长度权衡选择，强一致牺牲性能，最终一致提升吞吐。

## 14.8 范式判断答题模板
1. 求候选键，区分主属性/非主属性；
2. 判断是否 1NF（属性原子）；
3. 判断有无非主属性对候选键的部分依赖 → 决定 2NF；
4. 判断有无非主属性对候选键的传递依赖 → 决定 3NF；
5. 判断有无主属性对候选键的部分/传递依赖 → 决定 BCNF；
6. 结论：最高满足 xNF，理由为存在 XX 依赖。

## 14.9 规范化拆分答题模板
1. 指出当前关系存在的异常（插入/删除/修改异常）；
2. 给出函数依赖分析；
3. 按 3 级范式分解为多张关系，标注主键/外键；
4. 显式说明分解**具有无损连接性**（自然连接可还原原关系，不丢信息）且**保持函数依赖**（所有约束在子关系中保留）；
5. 结论：消除冗余与异常，代价是查询需 join。

# 15 软考数据库案例补丁：传统数据库设计与数据架构

> 本章为"防冷门题"补丁，覆盖原讲义较薄弱的传统数据库设计（E‑R 图真题训练、关系代数/SQL/视图/触发器）、数据库安全、备份恢复容灾、数据治理、数据湖/湖仓一体、Lambda/Kappa 等方向。配合 `08b` 真题题集第 16~22 题型训练。

## 15.1 数据库设计流程与成果物

数据库设计过程：
`需求分析 → 概念结构设计 → 逻辑结构设计 → 物理结构设计 → 实施 → 运行维护`

各阶段成果物：
| 阶段 | 主要成果 |
| --- | --- |
| 需求分析 | 数据需求、数据字典、业务规则 |
| 概念结构设计 | E‑R 图 |
| 逻辑结构设计 | 关系模式、主键、外键、范式分析 |
| 物理结构设计 | 索引、分区、存储结构、反规范化 |
| 实施 | 建库、建表、数据迁移、测试 |
| 运维 | 备份、恢复、性能优化、安全管理 |

> 答题金句：数据库概念结构设计主要形成 E‑R 图；逻辑结构设计将 E‑R 图转换为关系模式并进行规范化处理；物理结构设计关注索引、分区、存储方式等性能优化手段。

## 15.2 数据字典

数据字典是数据库中各类数据对象的集合描述，通常包括：**数据项、数据结构、数据流、数据存储、处理过程**。在数据库需求分析阶段，数据字典用于明确数据名称、类型、长度、取值范围、业务含义。

> 答题金句：数据字典是数据库需求分析的重要成果，用于描述数据项、数据结构、数据存储及业务规则，为后续概念结构设计和逻辑结构设计提供依据。

## 15.3 数据库完整性约束

| 完整性类型 | 含义 |
| --- | --- |
| 实体完整性 | 主键唯一且非空 |
| 参照完整性 | 外键取值必须有效（引用有效主键）或为空 |
| 用户定义完整性 | 业务规则约束，如金额不能为负、年龄范围 |

> 答题金句：数据库完整性约束用于保证数据正确性和一致性。实体完整性通过主键保证，参照完整性通过外键保证，用户定义完整性通过业务约束、触发器或检查约束保证。

## 15.4 关系代数基础（软考高频）

关系代数是关系型数据库查询的理论基础，核心运算：

| 运算 | 含义 | 说明 |
| --- | --- | --- |
| 选择 σ | 按条件筛选**行** | 相当于 SQL 的 WHERE |
| 投影 π | 选取**列** | 相当于 SQL 的 SELECT 列 |
| 并 ∪ / 差 − / 交 ∩ | 集合运算 | 要求关系同构（属性个数、域一致） |
| 笛卡尔积 × | 两关系所有元组组合 | 无连接条件时产生大量冗余 |
| 连接 ⋈ | 按连接条件组合两关系 | 自然连接、等值连接、外连接 |
| 除 ÷ | 求解"包含了全部"语义 | 常用于"查询选修了全部课程的学生" |

常见连接类型：
- **自然连接**：按两关系中同名同域属性自动等值连接，并去除重复列；
- **等值连接**：按指定相等条件连接，保留重复列；
- **外连接（左/右/全）**：保留未匹配上的悬空元组，缺失侧补 NULL；左外连接保留左表全部，右外连接保留右表全部。

> 答题句：关系代数通过选择（筛选行）、投影（选取列）、连接（关联多表）和除（全集包含）等运算描述查询；自然连接按同名列自动等值连接并去重，外连接可保留未匹配记录。

## 15.5 视图、触发器、存储过程

| 对象 | 作用 |
| --- | --- |
| 视图 | 简化查询、提供安全控制（屏蔽敏感列）、屏蔽底层表结构变化（逻辑独立） |
| 触发器 | 自动执行数据校验、级联更新、审计日志 |
| 存储过程 | 封装业务逻辑，减少网络交互，提高执行效率 |

> 答题金句：视图可用于简化复杂查询并实现一定程度的数据安全控制；触发器适合自动维护数据一致性和审计；存储过程适合封装稳定的业务操作。

## 15.6 数据库安全设计

常见安全措施：用户身份认证；**权限最小化**；角色管理；视图隔离敏感字段；数据加密（存储加密、传输加密、字段加密）；数据脱敏（测试/开发环境保护敏感数据）；SQL 注入防护；审计日志。

> 答题金句：数据库安全应遵循最小权限原则，通过用户认证、角色授权、视图控制、数据加密和审计日志等手段保障数据的机密性、完整性和可用性。

## 15.7 数据库备份恢复与容灾

| 概念 | 含义 |
| --- | --- |
| 全量备份 | 备份全部数据 |
| 增量备份 | 备份上次备份以来变化的数据 |
| 差异备份 | 备份上次全量备份以来变化的数据 |
| 日志备份 | 备份事务日志，用于时间点恢复（PITR） |
| RPO | 恢复点目标：允许丢失多少数据 |
| RTO | 恢复时间目标：允许系统停机多久 |

主备切换：主库故障时，通过 VIP 漂移或中间件自动将读写流量切换至备库（或同城/异地容灾节点）。

> 答题模板：可采用全量备份、增量备份和事务日志备份相结合的方式。日常通过日志备份支持时间点恢复，同时建设主备或同城容灾架构。若业务要求数据丢失少（低 RPO），可采用同步或半同步复制；若要求恢复时间短（低 RTO），可采用自动故障切换和定期恢复演练。

## 15.8 数据架构：数据湖、湖仓一体、数据中台

| 概念 | 说明 |
| --- | --- |
| 数据仓库 | 面向分析的结构化数据集合（OLAP） |
| 数据湖 | 统一存储原始数据，支持结构化、半结构化、非结构化数据 |
| 湖仓一体 | 融合数据湖和数据仓库能力（湖的灵活性 + 仓的管理性） |
| 数据中台 | 将数据资产化、服务化，支撑多业务应用 |
| 实时数仓 | 基于 Kafka + Flink 的实时 ETL，支持实时大屏/监控 |
| CDC | 变更数据捕获（如 Binlog），实现业务库到数仓的近实时同步 |

数据分层（数据仓库经典分层）：
- **ODS**：操作数据层，贴源存储原始数据；
- **DWD**：明细数据层，清洗、规范化后的明细事实；
- **DWS**：汇总数据层，按主题轻度聚合；
- **ADS**：应用数据层，面向报表/接口的高度聚合结果。

> 答题模板：可建设统一数据平台，通过 ETL/CDC 将业务系统数据接入数据湖或数据仓库，经过清洗、转换、分层建模（ODS→DWD→DWS→ADS）后形成指标数据，并通过 OLAP 查询、数据 API、报表服务支撑经营分析、实时大屏和用户画像等应用。

## 15.9 数据治理

| 概念 | 含义 |
| --- | --- |
| 元数据 | 描述数据的数据（Schema、血缘、口径） |
| 主数据 | 企业核心共享数据，如客户、产品、组织 |
| 数据标准 | 统一数据定义、编码、格式 |
| 数据质量 | 准确性、完整性、一致性、及时性 |
| 数据血缘 | 数据来源、加工过程和流向 |
| 数据安全分类分级 | 按敏感程度分级管理（新大纲常考） |

> 答题金句：数据治理通过元数据管理、主数据管理、数据标准、数据质量监控和数据血缘分析，提升企业数据的一致性、可信性和可用性。

## 15.10 大数据处理架构：Lambda / Kappa / 流批一体

| 架构 | 核心思想 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| Lambda | 批处理层 + 速度层 + 服务层 | 离线准确，实时快速 | 两套逻辑，维护复杂 | 既要历史准确，又要实时统计 |
| Kappa | 全部通过流处理重放数据 | 架构简单，统一流处理 | 对消息存储和计算能力要求高 | 实时性要求高，可重放数据 |
| 流批一体 | 同一套逻辑支持批和流 | 降低开发维护成本 | 对引擎要求高 | 实时数仓、统一计算平台 |

答题金句：若系统同时需要离线统计和实时计算，可采用 Lambda 架构；若希望降低批流两套代码的维护成本，且数据可重放，可采用 Kappa 架构或流批一体方案。

# 16 模块一：Redis 专项（核心必考）

> 近年真题对 Redis 考查越来越深，尤其是分布式锁、缓存击穿互斥锁/逻辑过期序列图，几乎成为必考题型。本模块独立成章，配合 `08b` 第 16 题型训练。

## 16.1 Redis 数据类型与选型（高频）

| 数据类型 | 核心特性 | 典型应用场景 | 真题出处 |
| --- | --- | --- | --- |
| String | 二进制安全，最大 512MB | 缓存、计数器、分布式锁、共享 Session | 2025 真题：分布式锁选 String |
| Hash | 键值对嵌套（field‑value） | 购物车、用户对象存储、商品详情 | — |
| List | 双向链表，有序可重复 | 消息队列、最新评论列表、粉丝列表 | — |
| Set | 无序不可重复，支持集合运算 | 用户画像标签、抽奖、共同好友 | 2025 真题：用户画像标签选 Set |
| ZSet | 按分数排序，元素唯一 | 排行榜、延时队列、优先级队列 | 2025 真题：商品销售周排行榜选 ZSet |

> 答题金句：根据业务场景选择合适的数据类型——缓存和分布式锁用 String，结构化对象用 Hash，队列用 List，标签去重用 Set，排行榜用 ZSet。

## 16.2 持久化机制：RDB vs AOF vs 混合持久化（高频）

### 16.2.1 RDB（快照持久化）
- 原理：定时生成内存数据的二进制快照，保存为 `dump.rdb` 文件。
- 优点：文件紧凑，恢复速度快（直接加载二进制数据），适合备份、容灾和快速重启。
- 缺点：可能丢失最后一次快照后的数据（依赖备份频率）；BGSAVE 的 fork 操作在大内存场景下可能阻塞主线程。

### 16.2.2 AOF（追加日志）
- 原理：记录所有写操作命令，以文本格式追加到 `appendonly.aof` 文件。
- 优点：数据安全性高（最多丢失 1 秒数据，若配置 `everysec`）；可读性强（日志文件可人工修复或分析）。
- 缺点：文件体积大，恢复速度慢（需重放所有命令）；长期运行后文件膨胀，需定期执行 `BGREWRITEAOF` 重写优化。

### 16.2.3 混合持久化（Redis 4.0+）
- 原理：在 AOF 重写时，先以 RDB 格式保存当前全量数据，后续增量命令以 AOF 格式追加。
- 优势：兼顾 RDB 的快速恢复和 AOF 的数据安全。

> 答题模板：RDB 适合备份和快速恢复，但可能丢失数据；AOF 数据更安全但恢复慢；混合持久化兼顾两者优势。对数据安全性要求高的场景推荐 AOF（everysec）或混合持久化。

## 16.3 内存淘汰策略（高频）

当 Redis 缓存空间不足时，需要淘汰部分数据。

| 策略 | 作用范围 | 算法 |
| --- | --- | --- |
| volatile‑lru | 仅设置了过期时间的键 | LRU（最近最少使用） |
| volatile‑lfu | 仅设置了过期时间的键 | LFU（最不经常使用） |
| volatile‑ttl | 仅设置了过期时间的键 | 淘汰剩余 TTL 最小的键 |
| volatile‑random | 仅设置了过期时间的键 | 随机淘汰 |
| allkeys‑lru | 所有键 | LRU |
| allkeys‑lfu | 所有键 | LFU |
| allkeys‑random | 所有键 | 随机淘汰 |
| noeviction | — | 不淘汰，写入时报错 |

核心考点：
- `volatile‑*` 与 `allkeys‑*` 的区别：前者仅淘汰设置了过期时间的键，后者淘汰所有键。
- `volatile‑lru` 和 `allkeys‑lru` 的共性：均遵循**局部性原理**，优先淘汰最近未被访问的数据。

> 答题模板：缓存淘汰策略基于局部性原理，优先淘汰最近未被访问的数据。volatile‑lru 仅针对设置了过期时间的键，allkeys‑lru 针对所有键。

## 16.4 分布式锁（高频）

### 16.4.1 实现方式与死锁问题
Redis 分布式锁基于 `SETNX` 命令实现。

核心问题：`SETNX` 和 `EXPIRE` 分开执行时，若 `SETNX` 成功但 `EXPIRE` 未执行（服务宕机），锁将永不过期，形成死锁。

正确做法：使用原子命令 `SET key value EX 30 NX`，一次性完成"设值 + 过期时间"。

### 16.4.2 RedLock 算法
Redis 作者 Antirez 提出的高可用分布式锁算法，基于多个独立 Redis 节点（无副本）实现。原理：客户端向 N 个独立 Redis 节点请求加锁，过半节点成功才算有效加锁。适用场景：对锁可靠性要求极高的场景（如资金、对账核心链路）。

### 16.4.3 高频考点：死锁场景与解决方案

| 问题 | 原因 | 解决方案 |
| --- | --- | --- |
| 死锁 | SETNX 和 EXPIRE 非原子 | 使用 `SET key value EX NX` 原子命令 |
| 锁被误删 | 线程 A 的锁被线程 B 误删 | 设置锁值时用唯一标识（如 UUID），删除时校验 |
| 锁过期业务未完成 | 业务执行时间超过锁过期时间 | 看门狗机制（如 Redisson）自动续期 |

> 答题模板：Redis 分布式锁使用 `SET key value EX NX` 原子命令实现，避免死锁。锁值应使用唯一标识（如 UUID），释放时校验避免误删。对高可靠性要求场景可采用 RedLock 算法。

## 16.5 高可用架构：主从复制 → 哨兵 → 集群（高频）

| 特性 | 主从模式 | 哨兵模式 | Cluster 集群模式 |
| --- | --- | --- | --- |
| 数据分布 | 全量复制 | 全量复制 | 分片（16384 个槽位） |
| 故障转移 | 手动干预 | 自动选举新主节点 | 主节点故障时从节点自动晋升 |
| 优点 | 实现简单，读多写少 | 自动故障转移，高可用 | 水平扩展，数据分片 |
| 缺点 | 单点故障风险 | 写性能受限 | 架构复杂 |

主从复制：全量复制（从库首次连接或复制中断较久时，主库执行 `BGSAVE` 生成 RDB 快照发送给从库）；增量复制（主库持续将写命令传播给从库，从库重放执行）。

主从同步延迟：正常延迟通常为毫秒级；故障切换时可能出现秒级不可写窗口，并伴随秒级数据丢失风险（异步复制导致）；可用 `WAIT` 命令提升"写入被副本确认"的程度，但会牺牲吞吐与延迟。

> 答题模板：Redis 主从复制默认采用异步复制，存在同步延迟和数据丢失风险。对一致性要求高的场景可配置半同步复制或使用 WAIT 命令。

## 16.6 缓存三大问题（必考）

### 16.6.1 缓存穿透
定义：查询缓存和数据库中均不存在的数据，请求绕过缓存直击数据库。

解决方案：前端校验参数合法性；布隆过滤器拦截无效 ID；对空结果缓存短 TTL（如 30 秒）。

布隆过滤器缺点：存在误判率（假阳性），不能准确判断元素是否在集合中；一般不能删除元素；不能获取元素本身。

### 16.6.2 缓存击穿（最高频，必考序列图）
定义：热点 Key 在缓存失效的瞬间，大量并发请求同时回源，压垮数据库。

两种经典解决方案：

| 方案 | 核心思路 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 互斥锁（物理过期） | 缓存 TTL 正常过期，未命中时只有获取锁的线程查库重建 | 数据库只被一个线程访问，保护数据库 | 其他线程阻塞/轮询，影响响应时间 |
| 逻辑过期 | 缓存永不过期，存储"数据+逻辑过期时间"，过期时先返回旧数据，异步更新 | 响应快，不阻塞 | 可能返回旧数据，一致性弱 |

**互斥锁方案序列图（2025 年 11 月真题）：**
两个并发线程（线程1先到，线程2后到）的时间线：

```
线程1：查缓存(未命中) → 获取互斥锁(成功) → 查数据库 → 写缓存 → 释放锁 → 返回
线程2：查缓存(未命中) → 获取互斥锁(失败) → 休眠重试 → 再次查缓存(命中) → 返回
```

序列图填空要点：
1. 两个线程都先"查询缓存"，均未命中；
2. 线程1 成功获取互斥锁（用 SETNX/SET NX 实现）；
3. 线程2 获取锁失败，**不能去数据库**，进入"休眠重试"；
4. 线程1 持锁执行"查数据库 → 写缓存 → 释放锁"；
5. 线程2 被唤醒后先**重新查询缓存**（不是直接加锁），此时缓存已被重建 → 命中。

> ⚠️ 失分陷阱：序列图中容易漏掉"再次查询缓存"这一步，必须体现"等待别人重建好缓存后自己复用"的设计思想。

### 16.6.3 缓存雪崩
定义：大量缓存 Key 在同一时刻过期，或缓存服务不可用，导致数据库瞬间承受高并发压力。

解决方案：过期时间加随机偏移（如 `base + random(0,300)s`）；多级缓存（本地缓存兜底）；缓存预热；服务限流降级；Redis 高可用集群。

> 易错点：混淆"击穿"与"雪崩"——击穿是单个热点 Key，雪崩是批量 Key。

# 17 模块二：云原生数据库与 NewSQL（补强）

> 原 `06` 章已涵盖基本点，此处补充存算分离原理、NewSQL 对比、TiDB 架构等高频考点。2025 年 11 月论文真题"论基于云原生数据库的企业信息系统架构设计"说明该方向重要。

## 17.1 云原生数据库概述
云原生数据库（AWS Aurora、阿里云 PolarDB、TiDB 等）采用"存算分离"架构，结合了传统数据库的强一致性和云服务的弹性。

## 17.2 存算分离架构（核心原理）

### 17.2.1 传统数据库的问题
传统数据库将计算和存储耦合在同一节点：扩展时必须同时扩容，造成资源浪费；扩容需要搬数据，耗时长；运维成本高，故障恢复慢。

### 17.2.2 云原生数据库的存算分离架构
| 组件 | 职责 | 特性 |
| --- | --- | --- |
| 计算节点 | SQL 解析、执行计划生成 | 无状态，可秒级弹性扩缩容 |
| 存储层 | 数据持久化、副本管理、故障修复 | 分布式共享存储，一份数据副本 |

核心技术：
- **日志即数据（Log‑Structured Storage）**：通过 Redo Log 实现存储，避免传统脏页刷盘；
- **共享存储**：所有计算节点共享同一份数据，避免了传统主从复制的数据拷贝延迟。

### 17.2.3 核心优势
| 优势 | 说明 |
| --- | --- |
| 弹性扩容 | 传统 MySQL 扩容需搬数据（耗时），云原生 DB 只需增加计算节点（秒级） |
| 按量付费 | 存储按量付费，不需预购磁盘 |
| 读写分离无延迟 | 共享存储架构下，从库读到的数据与主库实时一致（无主从同步延迟） |
| 故障快速恢复 | 故障恢复时间从小时级压缩至秒级 |
| 单库容量大 | 单库容量可突破 128TB |

> 答题金句：云原生数据库采用存算分离架构，计算节点无状态、可秒级弹性扩缩容，存储层共享一份数据副本，解决了传统数据库扩容需搬数据、主从同步延迟等痛点。

### 17.2.4 上云场景答题金句（应对"传统架构痛点"题干）
当题干描述"主从延迟高、扩容需搬数据、促销峰值连接池爆满"等传统痛点并要求提出改进方案时，可写出如下句式直接得分：

> 本系统若上云，可选用存算分离架构（如 PolarDB / Aurora）。该架构下计算节点共享底层分布式存储，从物理层面消除了传统主从复制的日志回放延迟，读节点可见数据与主节点严格一致，无需在应用层做"强制读主库"的路由；同时计算节点无状态，支持秒级弹性扩容，契合促销峰值的弹性诉求。

> ⚠️ 注意：传统读写分离的主从延迟仍是必考基础知识点（见第 4 章），云原生存算分离是对其的"演进升级"答案，二者都应掌握——题干若限定"传统架构"就写主从延迟与强制主库，题干若问"云原生改进"就写存算分离。

## 17.3 典型产品
| 产品 | 特点 |
| --- | --- |
| AWS Aurora | 存算分离，兼容 MySQL/PostgreSQL，一写多读 |
| 阿里云 PolarDB | 存算分离，一写多读，最大 100TB |
| TiDB | NewSQL，水平扩展 + ACID 事务，计算‑存储分离 |

## 17.4 NewSQL 数据库

### 17.4.1 定义
NewSQL 数据库兼顾传统关系型数据库的 ACID 事务能力 与 NoSQL 系统的水平扩展能力。典型代表：Google Spanner、TiDB、CockroachDB。

### 17.4.2 与传统方案对比
| 方案 | 事务能力 | 水平扩展 | 典型产品 |
| --- | --- | --- | --- |
| 传统关系型数据库 | ✅ 强 ACID | ❌ 困难 | MySQL, Oracle |
| NoSQL | ❌ 弱 | ✅ 容易 | Redis, MongoDB, HBase |
| NewSQL | ✅ 强 ACID | ✅ 容易 | TiDB, CockroachDB |

### 17.4.3 TiDB 架构（高频考点）
TiDB 采用计算与存储分离设计，由三个核心组件构成：

| 组件 | 职责 |
| --- | --- |
| TiDB Server | SQL 解析、执行计划生成（无状态计算层） |
| PD (Placement Driver) | 集群调度、数据分片管理、再平衡决策 |
| TiKV | 分布式 KV 存储引擎，基于 Raft 协议保证多副本一致性 |

> 答题模板：NewSQL（如 TiDB）融合了关系型数据库的 ACID 事务能力和 NoSQL 的水平扩展能力，适用于海量数据同时又要求强一致性的业务场景。

## 17.5 RAG 架构数据存储（2026 新大纲 AI 热点·超车弯道）

> 2026 年新大纲明确新增"AI 系统架构设计"（AI 占比约 25%），案例题最爱考"结合具体场景选型"。若题干出现"企业私有知识库""智能客服""大模型问答"，仍答 MySQL 分库分表就完全跑题。必须用 **RAG（检索增强生成）+ 向量数据库** 来打。

### 17.5.1 核心概念
- **RAG（Retrieval‑Augmented Generation）**：先检索相关知识片段，再拼接进 Prompt 调用大模型，弥补大模型知识陈旧与幻觉问题。
- **向量数据库**：存储文本经 Embedding 后的向量，支持 ANN（近似最近邻）检索；如 Milvus、Elasticsearch（向量能力）、pgvector。
- **Embedding 模型**：将文本切片转为高维向量，使语义相近的文本在向量空间距离更近。

### 17.5.2 案例答题框架（当题干出现"AI 问答/知识库"时直接套用）
> 针对该智能问答/知识库场景，采用 RAG（检索增强生成）架构。核心数据流转如下：① 离线阶段，将私有文档切片后经 Embedding 模型转为向量，存入向量数据库（如 Milvus / Elasticsearch）；② 在线阶段，用户 Query 向量化后在向量库做 ANN（近似最近邻）检索，召回 Top‑K 相关片段；③ 将片段与 Query 拼接成 Prompt 调用大模型。该架构利用向量数据库解决大模型知识陈旧与幻觉问题，元数据（文档来源、版本、权限）则存放于 MySQL 以便管理版本与权限。

### 17.5.3 选型要点（答题补充）
- 向量检索解决"语义相似召回"，关系库（MySQL）管理"结构化元数据、权限、版本"；
- 切片策略（chunk size）影响召回质量；可结合混合检索（向量 + 关键词 BM25）提升准确率；
- 适用于企业私有知识库、智能客服、法规/制度问答等"知识密集型"场景。

> ⚠️ 注意：RAG 是数据库/数据架构方向在 AI 热点的延伸，核心考点是"向量数据库选型 + 检索增强生成数据流"，不要写成纯算法题。

# 18 考试策略：数据库方向选做题如何判断与作答

## 18.1 三类优先级（冲刺分层）

**第一优先级·必须背熟（拿分核心）：**
1. 范式与 E‑R 图（1NF~BCNF、候选键、主/非主属性、部分/传递依赖、E‑R 转关系模式、1:1/1:N/M:N、主键外键）；
2. 数据库优化（索引、覆盖索引、最左前缀、索引失效、反规范化、物化视图、SQL 优化）；
3. 分片与读写分离（水平/垂直分片、分片键、跨分片查询、全局唯一 ID、读写分离、主从延迟、一致性读）；
4. 缓存与分布式事务（Cache Aside、穿透/击穿/雪崩、2PC、TCC、Saga、本地消息表、可靠消息、最大努力通知）。

**第二优先级·建议掌握（拉分项）：**
1. 数据仓库（OLTP vs OLAP、ETL、星型/雪花、缓慢变化维、事实表、OLAP 操作）；
2. NoSQL 选型（Redis、MongoDB、HBase、Elasticsearch、Neo4j、时序库）；
3. NewSQL / 云原生数据库（TiDB、OceanBase、PolarDB、计算存储分离、弹性扩展）；
4. **RAG 与向量数据库（2026 新大纲 AI 热点）**：私有知识库、智能客服、大模型问答场景的检索增强生成架构（见第 17.5 节）。

**第三优先级·补丁内容（防冷门）：**
1. 数据库安全（权限、角色、审计、加密、脱敏）；
2. 备份恢复（全量/增量/差异/日志、RPO/RTO）；
3. 数据治理（元数据、主数据、数据标准、数据质量、数据血缘）；
4. 数据湖/湖仓一体/实时数仓、Lambda/Kappa、CDC。

## 18.2 五类数据库题型的识别与作答重点

| 类型 | 题干特征 | 重点作答 |
| --- | --- | --- |
| 类型1 传统数据库设计 | 给业务描述、补 E‑R 图、转关系模式、判主键外键、规范化 | E‑R 图、关系模式转换规则、主键/外键、范式分解 |
| 类型2 性能优化 | 数据量大、查询慢、读多写少、join 多、高峰压力大 | 索引、反规范化、分片、读写分离（见第 1~5、14 章） |
| 类型3 分布式一致性 | 多服务、多数据库、订单/库存/积分、跨系统调用 | 2PC/TCC/Saga/消息最终一致（见第 7 章） |
| 类型4 数据仓库/数据平台 | 数据孤岛、报表分析、经营决策、实时统计、用户画像 | OLAP/ETL/星型模型/数据分层/湖仓一体（见第 12、15 章） |
| 类型5 安全与容灾 | 数据泄露、敏感信息、故障恢复、数据丢失、容灾、备份 | 权限/加密/脱敏、全量/增量/日志备份、RPO/RTO（见第 15.6~15.7 节） |
| 类型6 AI 数据架构（RAG） | 企业私有知识库、智能客服、大模型问答、制度/法规问答 | RAG 检索增强生成 + 向量数据库（Milvus/ES/pgvector）+ 元数据存 MySQL（见第 17.5 节） |

> ⚠️ 类型1 不要大量写 Redis、TCC、分库分表，除非题干问性能优化；类型4 不要只答 MySQL 分库分表+Redis 缓存，应上升到数据架构（数据分层、湖仓一体）。

# 19 精简提示（避免工程化过深）

1. **B+ 树、ICP、MVCC、Next‑Key Lock**：题干未明确问 InnoDB/MySQL/索引结构/并发控制底层机制时，简化为"通过合理建立索引、使用覆盖索引、避免索引失效，减少全表扫描和回表次数，提升查询性能"。
2. **"基因法"一词谨慎使用**：建议写"可在订单号中嵌入用户 ID 分片因子，使根据订单号也能定位所在分片。这种方法本质是在业务主键中携带分片信息"。
3. **延迟双删不要写太绝对**：写"延迟双删可以在一定程度上降低不一致概率，但不能完全解决缓存与数据库一致性问题，通常需要结合消息重试或 Binlog 异步删除机制"。
4. **TCC、Saga、2PC 按题干选择**：银行转账强一致优先 2PC/XA/同步复制；电商下单高并发允许短暂不一致再写 TCC/Saga/可靠消息/最终一致。
