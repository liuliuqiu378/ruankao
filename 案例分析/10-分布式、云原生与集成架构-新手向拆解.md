## 0.2 新手黑话速查表（**先扫一遍，后面就不卡壳了**）

| 黑话 | 人话解释 |
|------|----------|
| **单体 / 单体应用** | 所有功能打成一个包、一个进程跑起来。改一行要整体重新发布 |
| **分布式** | 一个活儿分给多台机器干，机器之间靠网络说话 |
| **集群** | 一模一样的程序复制 N 份，同时对外服务（人多力量大） |
| **服务 / 微服务** | 按业务切成的小程序，各自独立部署 |
| **节点** | 一台机器 / 一个容器实例，泛指一个运行单位 |
| **实例** | 同一个程序运行起来的一份（跑 3 份 = 3 个实例） |
| **无状态** | 这个实例**不存任何"属于自己的数据"**，换一台机器接着干完全一样 |
| **有状态** | 它存了数据（数据库、Redis），搬家会丢东西 |
| **副本 / 多副本** | 同一个服务跑 N 个实例，挂一个还有别的顶上 |
| **南北流量** | **外部用户 → 内部服务** 的流量（从外面进来的） |
| **东西流量** | **服务 A → 服务 B** 的流量（内部之间互相调） |
| **注册中心** | 服务的"电话簿"：谁在哪台机器上，来这儿查 |
| **配置中心** | 配置的"总开关"：改配置不用重新打包发布 |
| **网关** | 所有外部请求的**唯一大门**（门卫） |
| **熔断** | 下游已经挂了，就**别再调了**，直接快速失败（保险丝） |
| **降级** | 保不住的功能先关掉/返回兜底结果（弃车保帅） |
| **限流** | 门口排队放行，超了就拒绝（地铁限流） |
| **雪崩** | 一个服务挂了 → 调用它的全卡住 → 连锁全挂 |
| **幂等** | **同一个操作做 1 次和做 100 次，结果一样**（不会重复扣款） |
| **削峰填谷** | 用消息队列把瞬时洪峰先存起来，后端慢慢消费 |
| **中间件** | 不属于业务、但业务要依赖的基础软件（MQ、缓存、网关……） |
| **容器 / 镜像** | 镜像 = 只读模板（像"安装光盘"）；容器 = 镜像跑起来的实例 |
| **编排** | 自动管理成百上千个容器：起、停、扩、缩、自愈 |
| **Sidecar（边车）** | 贴在每个服务旁边的小代理进程，替服务干网络相关的活儿 |
| **灰度 / 金丝雀** | 先放 1% 流量到新版本，观察没问题再全量 |
| **滚动更新** | 一个一个换实例，全程不停机 |
| **编排 vs 编制** | 编排 = **中央指挥**谁先谁后（Orchestration）；编制/协同 = **各服务自己**按事件接龙（Choreography） |
| **RPO** | 出事时**最多丢多少数据**（"丢 5 分钟的数据"） |
| **RTO** | 出事后**多久能恢复**（"15 分钟内恢复"） |
| **可观测性** | 出了问题能不能看清系统内部在干什么（日志+指标+链路） |
| **HPA / VPA** | HPA = 加机器（多开实例）；VPA = 换大机器（加大单机规格） |
| **探针** | K8s 定时"戳一下"容器看它还活着/能不能接客 |
| **零信任** | "内网也不可信"，每次调用都要验证身份 |
| **mTLS** | 双向 TLS，**双方互相验证对方证书**（不只是客户端验证服务端） |

# 1. 建立整体直觉：一个电商系统的十年演进

> **这一节不看会怎样**：后面每一章你都会觉得是"孤立的一堆名词"。
> **看完这一节你会得到**：一张能挂住所有知识点的"钩子地图"。

## 🧊 直觉：小卖部 → 连锁超市的进化史

小明开了个电商网站，我们跟着他踩一遍所有的坑。**每一次架构升级，都是被"上一个架构的痛"逼出来的。**

### 第 1 年：单体（Monolith）

```
[ 一台服务器：用户+商品+订单+支付+库存 全部塞在一个程序里 ]
```

- **爽在哪**：开发快、部署简单、本地一跑就起来、出问题一眼看全。
- **痛在哪**：
  - 改一个商品文案，要**整个网站重新发布**；
  - 想给"秒杀"扩容，只能**整站复制一份**，浪费；
  - 支付模块一个 Bug，能让**整个网站崩掉**（没有故障隔离）；
  - 团队 30 个人改同一份代码，天天冲突。

### 第 2 年：集群 + 负载均衡（解决"扛不住"）

```
用户 → [ Nginx ] → [ 服务器1 / 服务器2 / 服务器3 ]（同样的单体，复制3份）→ 同一个数据库
```

- **解决了**：并发量上去了，一台挂了还有别的。
- **新痛点**：数据库还是单点；代码还是一坨；改一处还是全量发布。

> 📌 对应章节：**第 13 章 Web 高可用**（Nginx、负载均衡、CDN、Session 共享）

### 第 3 年：拆微服务（解决"改不动"）

```
用户 → 网关 → [用户服务][商品服务][订单服务][支付服务][库存服务]
                    ↓各自独立数据库
```

- **解决了**：独立发布、故障隔离、按业务扩容、团队并行开发。
- **新痛点（这就是考点集中区！）**：
  - 服务之间怎么找对方？→ **注册中心**（第 6 章）
  - 外部请求从哪进？→ **API 网关**（第 4 章）
  - 一个服务挂了会不会带崩一片？→ **熔断/降级/限流**（第 6 章）
  - 下单要跨"订单+库存+支付"，怎么保证一起成功？→ **分布式事务 / Saga**（第 7 章）
  - 一个请求穿越 8 个服务，出问题去哪查？→ **链路追踪**（第 6 章）
  - 服务边界怎么划才合理？→ **DDD 限界上下文**（第 14 章）

### 第 4 年：容器化 + K8s（解决"部署运维地狱"）

- 服务从 5 个变成 80 个，每个还跑 3 个实例 = 240 个进程，人工部署不现实。
- **Docker** 解决"在我机器上能跑，上生产就崩"；**K8s** 解决"240 个容器谁来管理"。

> 📌 对应章节：**第 9 章 Docker、第 10 章 K8s**

### 第 5 年：Service Mesh + 云原生（解决"治理逻辑侵入业务代码"）

- 每个服务的代码里都写满了"熔断、重试、鉴权、埋点"，这些跟业务毫无关系，还每个语言都要重写一遍。
- **Mesh 的思路**：把这些活儿从业务代码里**抽出来**，放到服务旁边的 Sidecar 代理里。

> 📌 对应章节：**第 11 章 Service Mesh、第 8 章 云原生**

## 📖 原理：架构演进的"万能因果链"（**背下来，答题能用一辈子**）

```
单体扛不住并发 → 加集群/负载均衡
单体改不动、故障不隔离 → 拆微服务
微服务之间互相找不到、调不通 → 注册中心 + 网关 + 熔断限流
微服务数据不一致 → 分布式事务（Saga / 事务消息 / 最终一致 + 对账）
服务太多部署运维不动 → 容器 + K8s 编排
治理代码侵入业务 → Service Mesh（Sidecar）
```

> 💡 **考试的隐藏规律**：案例题的题干几乎永远是"**某公司原有 XXX 架构，现在遇到 YYY 问题，请你给出方案**"。
> 你只要能识别"它现在处在演进的哪一步、遇到了哪一步的痛点"，答案就已经出来了 —— **对应的下一步技术就是答案**。

## ⚠️ 丢分点

1. **只背技术不背"为什么"** → 题目问"为什么要用注册中心"，答不出"因为微服务实例地址会动态变化，硬编码 IP 会失效"。
2. **把"集群"和"分布式"混为一谈**：集群 = 复制多份干同样的活（人多）；分布式 = 拆成不同部分干不同的活（分工）。**集群解决"扛不扛得住"，分布式解决"改不改得动"**。
3. **答方案时不分层** → 阅卷按点给分，一定要**分条、加关键词**。

# 2. 微服务架构
> 对应原文第 1 章

## 🧊 一句话直觉

> **单体 = 一家大杂货铺，什么都在一个屋子里，掌柜一个人管。**
> **微服务 = 一家商场，每个专柜（服装、餐饮、影院）独立经营、独立装修、独立招人，一家着火不影响别家。**

再狠一点的类比：
- 单体是**一整块大理石**，改个角落要凿整块石头；
- 微服务是**乐高积木**，哪块坏了换哪块。

## 📖 原理拆解

### 2.1 定义（**必背关键词**）

微服务是一种架构风格，将**单体大应用拆分为一组小型自治服务**，每个服务**围绕单一业务能力**构建、**可独立部署**，服务之间通过**轻量级通信机制**协作。

> 拆关键词：**小型、自治、单一业务能力、独立部署、轻量通信**。答题时这 5 个词写全，定义题就满分。

### 2.2 六大核心特征（**踩分关键词，一个都不能漏**）

| # | 特征 | 人话 | 考试怎么用 |
|---|------|------|-----------|
| 1 | **单一职责** | 一个服务只干一件事 | 问"拆分原则"答它 |
| 2 | **独立部署** | 单独上线、单独回滚，不影响别人 | 问"微服务优点"必答 |
| 3 | **去中心化治理** | 每个服务可以自己选语言、技术栈 | 问"与 SOA 区别"必答 |
| 4 | **去中心化数据管理** | **一服务一数据库**，禁止共享数据库 | **问"为什么拆库"必答，超高频** |
| 5 | **轻量级通信** | REST/HTTP、gRPC、消息队列 | 与 ESB 重总线对比时用 |
| 6 | **面向失败设计** | 默认远程调用会失败，用熔断/降级/超时/重试 | 问"稳定性设计"必答 |

> 🔥 **第 4 条是新手最容易忽略、也最容易考的**：很多公司"拆分了服务但共用一个数据库"，这叫**假微服务**。考试问"指出该公司微服务改造存在的问题"，标准答案第一条就是"**服务间共享数据库，未做到去中心化数据管理，导致服务仍耦合，无法独立部署与演化**"。

### 2.3 优点（答题时至少写 4 条）

- 模块解耦，**独立迭代，发布速度快**；
- **技术栈异构**（不同服务可用不同语言）；
- **故障隔离**，局部故障不会拖垮整个系统；
- **便于弹性伸缩**，哪个服务压力大扩哪个，资源利用率高；
- 适合**大团队并行开发**（团队自治）。

### 2.4 缺点（**案例高频：分析系统存在的问题**）

- **分布式复杂度上升**：网络延迟、丢包、调用失败（原来一个函数调用，现在是一次网络请求）；
- **分布式事务、数据一致性**难题（本地事务失效了）；
- **运维复杂度暴涨**：大量实例需要监控、部署、管理；
- 服务依赖关系复杂，出现**调用雪崩**风险；
- 开发调试难度增加（一次请求跨 8 个服务）；
- 需要配套**完整服务治理基础设施**（注册中心、配置中心、网关、链路追踪……）。

> 💡 **答题灵感**：题目问"微服务改造后出现了哪些问题/微服务有什么缺点"，**优先答"分布式事务一致性"和"运维复杂度/服务治理"这两条**，命中率最高。

### 2.5 拆分策略

- **按业务域拆分**（最常用、最规范）；
- 基于 **DDD 限界上下文**拆分（**标准答案，见第 14 章**）；
- 避免循环依赖；
- **粒度适中**，不要过细造成"**纳米服务**"（Nano Service）。

> ⚠️ "纳米服务"是个送分/送命词：服务拆得太细 → 调用链暴涨、网络开销巨大、一个业务要改 10 个服务。题目出现"服务数量上百、单次请求调用 20 个服务"，立刻判断为**拆分粒度过细**。

## 🎯 怎么考（4 种常见问法）

| 问法 | 举例 |
|------|------|
| **① 概念题** | "什么是微服务？简述微服务架构的特征。" |
| **② 找茬题** | "某公司进行了微服务改造，但效果不理想，请指出存在的问题。" |
| **③ 方案题** | "请为该单体系统设计微服务拆分方案。" |
| **④ 对比题** | "比较 SOA 与微服务架构的异同。" |

## ✍️ 怎么答（模板）

**【模板 A：概念/特征题】**
> 微服务架构是将单体应用按**业务能力**拆分为一组**小型、自治、可独立部署**的服务，服务间通过**轻量级通信机制**（REST/gRPC/消息队列）协作的架构风格。其核心特征包括：①单一职责；②独立部署；③去中心化治理（技术栈异构）；④**去中心化数据管理（一服务一库）**；⑤轻量级通信；⑥面向失败设计（熔断/降级/超时/重试）。

**【模板 B：找茬题（微服务改造不理想）】**
> 存在的问题可能包括：
> ① **服务间共享数据库**，未实现去中心化数据管理，服务仍强耦合；
> ② **拆分粒度过细（纳米服务）**，调用链过长，网络开销大；
> ③ 缺乏**服务治理基础设施**（注册中心、配置中心、API 网关）；
> ④ 缺少 **熔断/降级/限流** 等容错机制，存在雪崩风险；
> ⑤ 跨服务**分布式事务**方案缺失，数据不一致；
> ⑥ 缺乏**可观测性**建设（日志/指标/链路追踪），故障定位困难。

## ⚠️ 丢分点

1. ❌ 把"微服务"答成"分布式"的同义词 → 微服务是**架构风格**，分布式是**部署形态**。
2. ❌ 忘记"**一服务一数据库**"这条 → 这是微服务最标志性的特征，也是找茬题的头号答案。
3. ❌ 只写优点不写缺点 → 案例题 60% 的情况是让你**找问题**，缺点背不熟直接丢一半分。
4. ❌ "独立部署"写成"独立开发" → 关键词是**部署**，因为是部署独立性带来了发布速度和故障隔离。

# 3. SOA / ESB 企业服务总线
> 对应原文第 2 章

## 🧊 一句话直觉

想象一家**老牌大企业**，20 年攒了 8 套系统：财务用 .NET、库房用 Java 老系统、CRM 买的成品软件、还有一堆存储过程。

现在老板说："我要一个页面看到客户从下单到回款的全流程。"

怎么办？让这 8 套系统**两两互连**（网状）？8 套系统需要 **28 条**连线，每加一套系统，就要跟前面所有系统对接一遍 —— 这就是**"集成地狱"**（N² 问题）。

> **ESB 的解法：中间放一根"万能转换插头"总线（Hub）。**
> 所有系统**只跟总线说话**，不管对方在哪、用的什么协议、什么数据格式。总线负责翻译、转发、编排。
> 8 套系统 → **8 条**线接入总线即可。

```
【没有 ESB】                        【有 ESB】
A ──┬── B                          A ──┐
│   ├── C      (网状，N² 条线)      B ──┤
├── D                               C ──┼── [ ESB 总线 ]  (N 条线)
└── E                               D ──┤
                                    E ──┘
```

**更形象的类比**：ESB 就像**老式电话总机**（或联合国同声传译）—— 你说中文、他说英文、她说法语，总机/译员负责让你们互相听懂。

## 📖 原理拆解

### 3.1 SOA 面向服务架构

SOA 是一种组件模型，将应用功能**封装成可互操作的服务**，通过网络调用，实现**业务复用与系统集成**。

> 一句话区分：**SOA 的重点是"集成"（把已有的系统连起来）；微服务的重点是"拆分"（把一个大系统切开）。** 这是所有对比题的总纲。

### 3.2 ESB 企业服务总线（**7 大功能，必背**）

ESB 是 SOA 架构中的**中间件总线**，作为服务请求者和提供者之间的中间层。

| # | 功能 | 人话 | 记忆钩子 |
|---|------|------|---------|
| 1 | **位置透明性** | 消费者不用知道提供者在哪台机器上 | "不用知道你在哪" |
| 2 | **协议转换** | HTTP / WebService / REST / TCP / JMS **互转** | "你说法语我说中文" |
| 3 | **消息路由** | 按条件/内容决定转发给谁 | "快递分拣" |
| 4 | **数据格式转换** | XML↔JSON、报文格式适配 | "翻译格式" |
| 5 | **消息增强** | 补充/校验消息头、安全凭证 | "贴标签" |
| 6 | **服务编排** | 组合多个服务完成一个业务流程 | "总指挥" |
| 7 | **安全、日志审计、监控管理及异常处理** | 旁路能力 | "管理" |

> 🎯 **记忆口诀**：**位协路增格，编安（位置透明、协议转换、路由、增强、格式转换、编排、安全审计）**
> 或者更土更好记：**"位置不用管，协议帮你转，路由帮你送，格式帮你翻，内容帮你补，流程帮你串，安全日志全包办"**。

### 3.3 采用 ESB 的三方面理由（**案例标准答法，一字不差背下来**）

| 维度 | ESB 带来的价值 |
|------|---------------|
| **部署方式** | 支持灵活部署结构（C/S、P2P 等），总线统一接入 |
| **耦合程度** | 待集成系统**只与总线通信**，彼此解耦，改一个不影响其他 |
| **可扩展性** | 新增系统以"**插件式**"接入，仅需适配协议与数据格式 |

> ⚠️ 这三行是**原文明确标注的"案例标准答法"**，如果题目问"为什么采用 ESB"，按这三个维度分条答，几乎就是标准答案。

## 🎯 怎么考

| 问法 | 典型题干 |
|------|---------|
| **① 功能题** | "ESB 具有哪些功能？请列举并说明。" |
| **② 理由题** | "说明该企业采用 ESB 进行系统集成的理由。" |
| **③ 对比题** | "比较 SOA 与微服务架构。" / "比较 ESB 与 API 网关。" |
| **④ 演进题** | "该企业现有 SOA 架构存在性能瓶颈，如何演进？" |

## ✍️ 怎么答

**【模板：SOA vs 微服务对比】**（**这张表是送分题，务必背熟**）

| 对比维度 | SOA | 微服务 |
|---------|-----|--------|
| **通信中枢** | 强依赖 ESB（**智能管道、重总线**） | **哑管道**，无重型总线，网关轻量 |
| **服务粒度** | **粗粒度**服务 | **细粒度**业务服务 |
| **数据库** | 常出现**共享数据库** | 每个服务**独立数据库** |
| **治理模式** | **集中治理** | **去中心化治理** |
| **部署模式** | 集中部署 | 每个服务**独立部署** |
| **适用场景** | **遗留系统集成**、大型企业异构系统打通 | 互联网业务、快速迭代高并发业务 |

> 💬 **收尾话术（必加，能多拿 1‑2 分）**：从 SOA 演进到微服务，通常需要**去掉重型 ESB，换成轻量 API 网关**；ESB 易成为**性能瓶颈与单点故障**。

**【模板：演进题】**
> 现有 SOA 架构中 ESB 承担了协议转换、路由、编排等大量职责，容易成为**性能瓶颈和单点故障**。演进思路：①将 ESB 的**服务编排、协议转换**能力下沉或移除，改为轻量级 **API 网关**承担对外统一入口；②服务间通信改用轻量协议（REST/gRPC）；③按业务域进一步**细粒度拆分**，实现**独立部署与去中心化数据管理**；④引入容器化与 K8s 提升弹性。

## ⚠️ 丢分点

1. ❌ **把 ESB 和 API 网关混为一谈** —— 见第 5 章，这是**头号送命题**。
2. ❌ 忘记"**位置透明性**"这条功能 —— 原文特别标注"10 文件原缺"，是易漏项。
3. ❌ 对比时**只写微服务的好** —— 正确姿势是"各有所适"：SOA 适合**集成遗留异构系统**，微服务适合**互联网快速迭代**。写"SOA 已过时"会丢分。
4. ❌ "智能管道 + 哑终端"（SOA）vs "哑管道 + 智能终端"（微服务）这对**经典表述**不会用 —— 写上去会显得非常专业。
5. ❌ 漏掉"**服务编排**"：ESB 能**组合多个服务完成业务流程**，这是它区别于普通消息中间件的关键。

# 4. API 网关
> 对应原文第 3 章

## 🧊 一句话直觉

> **网关 = 小区的"唯一大门 + 门卫室"。**

没有大门：外卖、快递、访客从四面八方翻墙进小区，你不知道谁进来了，也拦不住坏人。

有大门（网关）之后，所有进出**只走这一个门**，门卫统一干这些事：
- 查证件（**认证授权**）
- 指路（**路由**：3 号楼往左走）
- 人流管制（**限流**：高峰期一次只放 10 个人）
- 登记来访记录（**日志监控**）
- 把方言翻译成普通话（**协议转换**）
- 新门先给少数人试用（**灰度发布**）
- 门口放个快递柜（**缓存**）

> **为什么要这个门？** 因为后端有 80 个微服务，你不能让前端记住 80 个地址，也不能让每个服务**各自**实现一遍"查证件"和"限流"。

## 📖 原理拆解

### 4.1 作用

所有客户端请求的**统一入口**，**反向路由**，**屏蔽后端微服务地址**。

### 4.2 核心功能（**简答题 8 条，必背**）

1. **请求路由**
2. **负载均衡**
3. **认证授权、安全校验**
4. **限流熔断**
5. **请求日志、监控**
6. **协议转换**
7. **灰度发布**
8. **缓存**

> 🎯 **记忆口诀**：**"路负认限，监协灰缓"**（路由、负载、认证、限流、监控、协议、灰度、缓存）

### 4.3 统一身份认证与权限控制设计（**案例高频小问**）

| 层面 | 方案 |
|------|------|
| **认证（你是谁）** | **OAuth2 / OpenID Connect** 统一认证，网关颁发/校验 **Access Token（JWT）** |
| **授权（你能干啥）** | 微服务内部用 **RBAC**（基于角色的访问控制）；敏感场景叠加 **ABAC**（基于属性：组织/标签/状态） |
| **Token 传递** | 客户端登录获 **JWT** → 网关校验后**转发认证信息** → 各服务解析 JWT 实现**无状态验证** |

> 💡 **为什么用 JWT 而不是 Session**：JWT 自带用户信息且可本地校验，服务**不需要去查 Session 存储**，这才符合"无状态"和微服务去中心化。（Session 方案的对比见第 13 章）

### 4.4 网关层高可用与性能优化（针对高频接口）

- 网关层**限流**（令牌桶/漏桶），按 **IP / 用户等级**限流；
- **CDN** 边缘缓存静态资源/文件下载；大文件**分片上传/断点续传**；
- **异步处理 + 任务队列**解耦；文件处理服务**独立部署、水平扩展**。

### 4.5 🔥 限流三算法对比（**案例深挖踩分点，必背**）

> 题目常追问："**为什么选令牌桶而不是漏桶？计数器有什么问题？**"

**🧊 先建立直觉（三个水龙头）**

| 算法 | 生活类比 |
|------|---------|
| **计数器（固定窗口）** | **每分钟最多卖 100 张票**。问题：59.9 秒卖 100 张 + 00.1 秒卖 100 张 = **0.2 秒卖了 200 张** |
| **漏桶** | 桶底有个**固定大小的洞**，水（请求）只能以恒定速度滴出去。**不管你倒多猛，出水速度永远一样** |
| **令牌桶** | 桶里以恒定速度**生成令牌**，请求来了**拿一个令牌才能过**；桶满了令牌就攒着 —— 攒下的令牌可以**一次性应对突发** |

**📖 对比表**

| 算法 | 核心机制 | 优点 | 缺点 | 适用场景 |
|------|---------|------|------|---------|
| **计数器（固定窗口）** | 单位时间计数，超阈值拒绝 | 实现简单 | 窗口**临界突发翻倍**（1s 末 + 1s 初各打满）、不平滑 | **粗粒度**限流 |
| **漏桶（Leaky Bucket）** | 请求入桶，**恒定速率出水**（处理） | 速率**绝对平滑**，保护后端 | **无突发能力**，突发请求被排队/丢弃 | 需**严格恒定速率**的场景 |
| **令牌桶（Token Bucket）** | 恒定速率生成令牌入桶，桶有容量，请求取令牌 | **允许一定程度突发**（消耗桶内积攒的令牌），**最常用** | 实现稍复杂 | **互联网网关默认** |

> 💬 **标准答题话术（可直接默写）**：
> 网关默认采用**令牌桶**——既能平滑限流，又允许**桶容量内的合理突发**；**漏桶**适合必须**恒定速率**处理的场景（如保护下游能力固定的系统）；**计数器**实现简单但存在**窗口临界突发翻倍**问题（临界点 2 倍流量），只适用于**粗粒度**限流，不适合精确限流。

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 功能题** | "API 网关具有哪些功能？" |
| **② 设计题** | "请设计统一网关与权限控制方案。" |
| **③ 深挖题** | "网关限流采用什么算法？为什么不用计数器？" |
| **④ 优化题** | "某高频文件下载接口性能差，如何优化？" |

## ✍️ 怎么答

**【模板：统一网关 + 权限控制设计】**
> ① **统一入口**：在客户端与微服务之间部署 API 网关，作为**唯一入口**，实现请求路由、负载均衡、协议转换，屏蔽后端服务地址；
> ② **统一认证**：采用 **OAuth2 / OIDC**，用户登录后由认证中心颁发 **JWT（Access Token）**，网关统一校验签名与有效期，校验通过后**将用户身份信息透传**给后端服务，各服务本地解析 JWT 实现**无状态验证**，避免集中式 Session 瓶颈；
> ③ **授权**：服务内基于 **RBAC**（角色）做权限判断，敏感场景叠加 **ABAC**（属性：组织/标签/状态）做细粒度控制；
> ④ **防护**：网关层配置**令牌桶限流**（按 IP/用户等级）、熔断降级、黑白名单；
> ⑤ **可观测**：网关统一采集访问日志、QPS、响应延迟等指标，接入监控告警。

## ⚠️ 丢分点

1. ❌ **三算法只答名字不答机制** → 阅卷看的是"恒定速率出水""令牌积攒允许突发""临界翻倍"这些**机制描述词**。
2. ❌ **漏桶和令牌桶说反**：漏桶 = **出水恒定**（限制处理速率）；令牌桶 = **进水（令牌）恒定 + 允许突发**。记不住就想：**令牌可以攒，水攒不住**。
3. ❌ 忘记写"**限流维度**（按 IP / 用户 / 接口）"，只写"加限流"，显得单薄。
4. ❌ **把熔断放在网关就完事** → 熔断主要是**服务间（消费者侧）**的防护，网关做的是入口限流。两者层级不同。
5. ❌ 认证方案写"每个服务各自登录认证" → 严重错误，必须**统一认证（SSO）**。

# 5. 网关 / ESB / Service Mesh 三者分工（南北 vs 东西）
> 对应原文第 3b / 9 章

## 🧊 一句话直觉：**认准"南北"和"东西"这两个方向**

画一张架构图，习惯上把**外部用户画在上面、内部服务画在中间**：

```
        ☁️  外部用户 / 移动端 / 第三方
                  │
    ┌─────────────┼─────────────┐
    │        【 南北流量 】  ↓   │   从外面进来 = 南北
    │         [ API 网关 ]      │
    └─────────────┬─────────────┘
                  │
      ┌───────────┼───────────┐
      ↓           ↓           ↓
  [订单服务] ←→ [库存服务] ←→ [支付服务]     服务之间 = 东西
      │      【 东西流量 】     │
      └───────────┴───────────┘
```

- **南北流量**：**客户端 → 后端服务**（纵向，从外面进来）→ **API 网关**管
- **东西流量**：**服务 → 服务**（横向，内部互调）→ **ESB（旧）/ Service Mesh（新）** 管

## 📖 原理拆解

| 组件 | 管什么 | 时代 | 特点 |
|------|--------|------|------|
| **API 网关** | **南北流量**（客户端 ↔ 后端） | 现在 | 对外暴露、认证、限流、路由**入口** |
| **ESB** | **东西流量**（SOA 时代） | 旧 | **重型集中总线**：协议/数据转换、服务编排 |
| **Service Mesh（Istio / Envoy Sidecar）** | **东西流量**（微服务时代） | 新 | **非侵入式**精细化治理：熔断/路由/mTLS/链路 |

> 🔥 **必背结论：Mesh 不替代网关！**
> - 网关负责**对外入口**（认证/限流），Mesh 负责**内部服务间流量治理**；
> - 两者"**南北 + 东西**"**互补**，常**协同部署**。

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 概念辨析** | "API 网关与 ESB 有何区别？" |
| **② 判断题** | "引入 Service Mesh 后是否可以取消 API 网关？说明理由。" |
| **③ 方案题** | "请设计该系统的服务治理架构，说明各组件职责。" |

## ✍️ 怎么答

**【模板：三者分工（一句话记忆版）】**
> **API 网关管南北（对外入口：认证、限流、路由）；ESB 是 SOA 时代管东西的重型集中总线（协议/数据转换、服务编排）；Service Mesh 是云原生时代管东西的 Sidecar 代理（非侵入式熔断、mTLS、链路追踪）。Mesh 不能替代网关，二者南北+东西互补、协同部署。**

## ⚠️ 丢分点

1. ❌ **"南北/东西"说反** → 这是最经典的送命题。**外部进来是南北，服务之间横着走是东西**。
2. ❌ 认为"上了 Mesh 就不需要网关" → **错**，必须答"互补、协同部署"。
3. ❌ 只说"Mesh 是 Sidecar"，不说"**非侵入 / 业务代码零侵入**" → 少了最关键的关键词。
4. ❌ 把 ESB 说成"微服务时代的组件" → ESB 属于 **SOA/遗留集成**语境。

# 6. 微服务完整治理体系
> 对应原文第 4 章

## 🧊 一句话直觉：微服务是"城市"，治理体系是"城市基础设施"

拆完服务只是"盖好了楼"。要让城市运转，你还需要：

| 城市设施 | 微服务对应 | 没有它会怎样 |
|---------|-----------|-------------|
| **114 查号台 / 电话簿** | **注册中心** | 服务 A 不知道服务 B 在哪个 IP，调不通 |
| **市政总控开关** | **配置中心** | 改一个开关要重新打包发布 80 个服务 |
| **保险丝 / 限流栏杆** | **熔断 / 降级 / 限流** | 一个服务挂了全城停电（雪崩） |
| **监控摄像头 + 救护车** | **可观测性 + 告警** | 出问题两眼一抹黑，只能瞎猜 |

> **一句话公式**：**微服务治理 = 注册中心 + 配置中心 + 熔断限流容错 + 链路追踪 + 监控告警**

## 📖 原理拆解

### 6.1 注册中心（Nacos / Eureka / Consul）

**解决什么问题**：微服务实例地址**动态变化**（扩容、缩容、重启、故障漂移），**不能把 IP 写死在配置里**。

**工作流程**：
```
服务启动 → 向注册中心"报到"（注册自己的 IP:Port）
       → 定时发心跳（证明我还活着）
调用方   → 向注册中心"查询"（库存服务在哪些机器上？）
       → 拿到地址列表 → 本地负载均衡选一个 → 调用
服务下线 → 心跳停止 → 注册中心剔除 → 调用方更新列表
```

> 💡 **Nacos / Eureka / Consul** 是产品名，答题时**写"注册中心（如 Nacos）"**，显得既懂原理又懂落地。

### 6.2 配置中心

将配置文件**从代码剥离**，**集中管理**，**动态更新配置**，**无需重启服务**。

> **为什么必须外置**：80 个服务 × 3 环境 = 240 份配置，散落在代码里没法管；改个开关要全部重新发布，做不到"秒级生效"。

### 6.3 🔥 容错四件套：**熔断 / 降级 / 限流 / 超时重试**（**必考，必须分清楚**）

| 概念 | 一句话定义 | 生活类比 | 触发条件 | 关键词 |
|------|-----------|---------|---------|--------|
| **熔断** | 下游**失败率达到阈值**后，**直接快速失败**，不再调用 | **保险丝烧断** —— 电路有问题，直接断开保护电器 | 下游故障 | **快速失败、防止雪崩** |
| **降级** | 故障时**返回兜底结果**（默认值/缓存/关闭非核心功能） | **弃车保帅** —— 电梯坏了走楼梯 | 系统压力大/依赖不可用 | **兜底、牺牲非核心保核心** |
| **限流** | 限制**请求速率（QPS）**，超出的拒绝/排队 | **地铁限流** —— 人太多，门口拦着 | 流量超过容量 | **保护自己不被打垮** |
| **超时 + 重试** | 设置调用超时；失败后重试（注意幂等） | 打电话没人接，等 30 秒挂掉，再拨一次 | 单次调用失败 | **快速释放资源** |

> 🔥 **最容易混淆的一对：熔断 vs 降级**
> - **熔断**是**"断开"**（我不再调你了，直接报错）—— 保护的是**调用方**的资源；
> - **降级**是**"凑合"**（我给你个兜底答案）—— 保护的是**用户体验和核心链路**。
> - 实际中常常一起发生：熔断触发后**走降级逻辑**返回兜底值。

> ⚠️ **重试的暗坑（面试和案例都爱考）**：重试会**放大流量**（下游已经很慢了，你还重试 3 次 = 流量 ×3，加速雪崩）。所以必须配合：**重试次数限制 + 退避策略 + 熔断 + 幂等**。

### 6.4 🔥 可观测性三支柱（**必背，高频小问**）

| 支柱 | 英文 | 是什么 | 回答什么问题 | 典型工具 |
|------|------|--------|-------------|---------|
| **指标** | **Metrics** | CPU、内存、QPS、响应延迟等**数值型**数据 | "系统健不健康？趋势如何？" | Prometheus + Grafana |
| **日志** | **Logging** | 业务/系统产生的**离散事件记录** | "当时到底发生了什么？" | ELK / EFK（Elasticsearch + Filebeat + Kibana） |
| **链路追踪** | **Tracing** | 一次请求经过的**所有微服务调用链** | "这个请求慢在哪一步？" | **SkyWalking / Jaeger** |

> 💡 **记忆法**：
> - **Metrics**：体温计（看数值）→ "发烧了"
> - **Logging**：病历本（看过程）→ "记录发生了什么"
> - **Tracing**：**CT/造影**（看路径）→ "病灶在哪一段"

> 🎯 **答题话术**：微服务如何保障稳定运行 / 如何快速定位故障？
> 建设**可观测性三支柱**：①**指标（Metrics）**：采集 CPU、内存、QPS、响应延迟并设置告警阈值；②**日志（Logging）**：统一日志格式、集中采集检索（ELK/EFK）；③**链路追踪（Tracing）**：通过 SkyWalking/Jaeger 追踪一次请求经过的全部微服务调用链，快速定位性能瓶颈与故障节点。

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 组件题** | "微服务治理体系包含哪些组件？各自作用是什么？" |
| **② 辨析题** | "请说明熔断与降级的区别。" |
| **③ 稳定性题** | "系统出现雪崩，请分析原因并给出对策。" |
| **④ 可观测题** | "微服务环境下如何快速定位故障？" |

## ✍️ 怎么答

**【模板：服务雪崩的原因与对策】**（**超高频，务必背熟**）

> **原因分析**：服务间存在强依赖，当某个下游服务响应变慢或不可用时，上游调用**线程/连接被长时间占用不释放**，请求堆积，资源耗尽，故障沿调用链**向上蔓延**，最终导致整个系统不可用，即**服务雪崩**。
>
> **对策**：
> ① **入口限流**：API 网关配置**令牌桶限流**，按 IP/用户等级限制 QPS；
> ② **熔断**：引入 **Sentinel/Hystrix**，当下游**失败率或慢调用比例达阈值**时自动熔断，**快速失败**，避免资源耗尽；
> ③ **降级**：为核心链路配置**兜底策略**，牺牲非核心功能（如推荐、评价），保障下单、支付等核心链路；
> ④ **超时与重试**：设置合理超时时间，限制重试次数并采用退避策略，避免重试放大流量；
> ⑤ **异步解耦**：引入**消息队列削峰填谷**，将同步长调用改为异步；
> ⑥ **资源隔离**：线程池/信号量隔离，故障限制在单个依赖内；
> ⑦ **可观测与告警**：建设日志、指标、链路追踪三支柱，设置 SLO 告警，故障早发现早止损。

## ⚠️ 丢分点

1. ❌ **熔断、降级、限流三个词混着用** —— 见上面辨析表，这是**最高频丢分点**。
2. ❌ 可观测性只答"日志和监控" → **漏掉"链路追踪"就是缺一条支柱**，且链路追踪恰恰是微服务特色。
3. ❌ 雪崩题只写"加熔断" → 太单薄，按上面 7 条答才够分。
4. ❌ 把"注册中心"写成"服务中心/调度中心" → 关键词是**注册与发现**。
5. ❌ 忘记提"**心跳**" → 注册中心靠心跳判断实例存活，这是原理分。

# 7. 分布式系统核心难题：CAP / BASE / 分布式事务
> 对应原文第 5 章 · **本模块最难、也最容易拉开差距的一章**

## 7.1 CAP 理论

## 🧊 一句话直觉：**"断网的时候，你保数据对，还是保服务能用？"**

假设银行在**北京和上海各有一个机房**，两地通过光纤相连。某天施工队把光纤挖断了 —— 这就是**网络分区（P）**。

此时有个用户要在上海机房取款 100 万：

- 上海机房**看不到**北京机房的账户余额（因为断网），但它必须做个决定：
  - **选 C（一致性）**：我不知道北京那边有没有变动，**拒绝服务**，等网络恢复再说 → **数据绝对对，但用户取不到钱（不可用）**
  - **选 A（可用性）**：我先让你取，网络恢复后我再对账 → **服务能用，但可能数据暂时不一致**

> **所以 CAP 的核心不是"三选二"，而是：当网络分区真的发生时，你选择"拒绝服务"还是"带着可能不一致的数据继续服务"。**

## 📖 原理拆解

### 三个字母

| 字母 | 全称 | 定义 |
|------|------|------|
| **C** | **Consistency 一致性** | 所有节点**同一时刻看到相同的数据** |
| **A** | **Availability 可用性** | **每个请求都能收到响应**（不保证数据最新） |
| **P** | **Partition tolerance 分区容错性** | 出现**网络分区**时，系统**仍能继续运行** |

### ⚠️ 严谨表述（**这是考试踩分的关键，新手 90% 会答错**）

> ❌ **错误说法**："CAP 定理说三者只能选两个。"
> ✅ **正确说法**：**网络分区（P）是客观存在的风险，不是可选项**。分布式系统必然跨越网络，**分区不可避免**，所以 **P 必须满足**。所谓"三选二"，**实际是指"当分区真正发生时，需要在 C 和 A 之间做权衡"，即选 CP 还是 AP**。

### CP vs AP 选型（**必背**）

| 业务类型 | 选择 | 理由 | 典型代表 |
|---------|------|------|---------|
| **支付 / 金融 / 账务核心** | **CP** | 保数据一致，宁可暂停服务也不能记错账 | **ZooKeeper**、etcd、MySQL 半同步 |
| **社交 / 电商商品浏览 / 内容** | **AP** | 保服务可用，短暂不一致可以接受 | **Eureka**、Cassandra、DNS |

> 💬 **标准答题话术（可直接默写）**：
> "网络分区客观存在，分布式系统必须满足 P；**只有在分区真正发生时**才需要在 C 与 A 之间权衡。互联网业务优先保障可用性，选 **AP**（如 Eureka 放弃强一致、优先可用）；金融核心优先保障一致性，选 **CP**（如 ZooKeeper 在网络分区时**牺牲可用性**以保证数据一致）。"

## 7.2 BASE 理论（最终一致性）

## 🧊 直觉

CAP 告诉你"必须要做取舍"，BASE 告诉你"**AP 这条路具体怎么走**"。

| 字母 | 全称 | 人话 |
|------|------|------|
| **BA** | **Basically Available 基本可用** | 出故障时**允许损失部分可用性**（响应慢一点、部分功能关掉），但**不能整个挂掉** |
| **S** | **Soft state 软状态** | 允许系统存在**中间状态**（数据同步中），且中间状态**不影响系统整体可用性** |
| **E** | **Eventually consistent 最终一致性** | 不要求实时一致，但**经过一段时间后，数据最终会达到一致** |

> 💡 **一句话**：**BASE = 放弃强一致，换取高可用**。互联网微服务系统**绝大多数采用 BASE**。
> **典型案例**：你给朋友转账，他"暂时"没收到，但 30 秒后一定会收到 —— 这就是最终一致。

## 7.3 🔥 分布式事务六种方案（**必背 + 会选型**）

## 🧊 直觉：从"我全都要"到"各退一步"

分布式事务的本质难题：**原来一个数据库事务（BEGIN...COMMIT）能搞定的事，现在要跨越 3 个服务、3 个数据库，没有谁能统一指挥它们提交。**

| 方案 | 一句话 | 强度 | 侵入性 | 适用 |
|------|--------|------|--------|------|
| **2PC** | 协调者问一圈"你们能提交吗"，全说能才提交 | **强一致** | 低（中间件做） | 低并发、短事务、跨库转账 |
| **TCC** | **Try 预留 → Confirm 确认 → Cancel 取消** | 最终一致 | **高**（业务要写三段代码） | 支付、资金 |
| **Saga** | 长事务拆成**本地事务链 + 补偿动作** | 最终一致 | 中 | **微服务最常用**，长流程 |
| **本地消息表** | 业务与消息**同库同事务**写入 → 异步投递 | 最终一致 | 低 | 解耦、最终一致 |
| **事务消息** | MQ 保证"消息可靠投递 + 本地事务"原子性 | 最终一致 | 低 | RocketMQ，订单创建与库存扣减 |
| **Seata** | 阿里开源一站式框架，支持 AT/TCC/Saga | — | — | 落地选型 |

### 逐个展开（每个都要能说 2 句话）

**① 2PC 两阶段提交**
- 流程：**协调者**发 **prepare** → 参与者投票 → 全部同意则 **commit**，否则 **rollback**；
- 优点：**强一致**；缺点：**同步阻塞、性能差、协调者单点故障**；
- 适用：**低并发、短事务**、传统跨库场景。

**② TCC（Try‑Confirm‑Cancel）**
- **Try**：**预留资源**（冻结库存、冻结额度）；**Confirm**：确认执行（真正扣减）；**Cancel**：取消（释放预留）；
- 优点：一致性较好、性能好；缺点：**业务侵入性极高**，每个操作都要写三段逻辑，且要处理**幂等、空回滚、悬挂**；
- 适用：**支付、资金、交易核心**。

**③ Saga 模式**（**2025 真题考点，重点**）
- 思路：**长事务拆分为一系列本地事务**，每个本地事务都有对应的**补偿动作**；某步失败，**逆序执行前面各步的补偿**；
- 类比：订机票失败 → 退酒店 → 退租车（**逆序补偿**）；
- 适用：**长流程、跨服务**（订单 → 库存 → 支付）；
- **微服务中最常用**。

**④ 本地消息表**
- 做法：业务操作和"待发送消息"写在**同一个本地事务**里（同库），保证"**业务成功则消息一定在**"；再由后台任务异步投递消息；
- 优点：**解耦、最终一致**、不依赖 MQ 的事务特性；缺点：消息表与业务库耦合、有额外扫描开销。

**⑤ 事务消息（RocketMQ）**
- MQ 提供"**半消息 → 本地事务 → 提交/回滚 → 回查**"机制，保证**本地事务与消息发送的原子性**；
- 适用：订单创建与库存扣减这类"**本地操作 + 通知下游**"场景。

**⑥ Seata**
- 阿里开源分布式事务框架，支持 **AT / TCC / Saga** 三种模式，**一站式解决方案**；
- 答题时可作为**落地选型**提出来加分。

### 7.3.1 🔥 Saga 的两种实现模式（**2025 真题高频踩分点，必背**）

## 🧊 直觉：**"接龙" vs "总指挥"**

**协作式（Choreography）= 击鼓传花式接龙**
> 订单服务："我下单了！"（发事件）
> 库存服务听到 → 扣库存 → "我扣完了！"（发事件）
> 支付服务听到 → 扣款 → "我付完了！"
> 没有总指挥，大家靠**事件**自发串联。

**编排式（Orchestration）= 有一个总指挥（乐队指挥）**
> Saga 协调器："库存，扣！" → 库存："扣完了" → 协调器："支付，收钱！" → 支付："收完了" → 协调器："订单，完成！"
> 谁出错，协调器负责**按正确顺序通知前面的人补偿**。

| 模式 | 核心机制 | 优点 | 缺点 | 适用场景 |
|------|---------|------|------|---------|
| **协作式（Choreography / 协同）** | **无中心协调器**；各服务监听/触发**领域事件**，互相驱动下一步 | 耦合低、去中心、易扩展 | **流程分散、状态不可见、补偿顺序难控** | **简单短 Saga**（步骤少、无复杂补偿） |
| **编排式（Orchestration / 协调）** | 中央 **Saga 协调器（状态机）** 主动发命令、集中控制流程 | **状态可见、补偿顺序可控、强制幂等、易监控** | 协调器可能成中心节点（需高可用） | **步骤多、需补偿的复杂长流程**（支付/订单/转账） |

> 💬 **答题话术（必背）**：
> 支付、银行转账等**复杂长流程推荐编排式 Saga** —— 由协调器（状态机）集中控制，**状态可见、补偿顺序可控、可强制幂等**，便于排障与对账；**简单的事件驱动流程**可用**协作式**以降低中心依赖。
>
> 💡 **银行"跨单元转账"类题目**：应点明采用**编排式 Saga**，并强调"**事件表与业务表在同一个本地事务中提交**"是 **RPO=0** 的根本保证，**而不是依赖 MQ 的可靠性**。

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 概念题** | "简述 CAP 定理，并说明本系统应选择 CP 还是 AP。" |
| **② 选型题** | "订单创建需同时扣减库存，请设计分布式事务方案并说明选型理由。" |
| **③ 深挖题** | "Saga 模式有哪两种实现方式？本场景应选哪种？" |
| **④ 找茬题** | "订单与库存数据偶尔不一致，请分析原因并给出解决方案。" |

## ✍️ 怎么答

**【模板：分布式事务方案设计】**（**万能四步法**）

> 第一步 **定强度**：判断业务需要**强一致（CP）**还是**最终一致（AP）**。金融核心账务选 CP；互联网高并发业务选 AP。
> 第二步 **选方案**：
> - 强一致、短事务、低并发 → **2PC**；
> - 资金/支付、可写三段业务逻辑 → **TCC**；
> - 长流程、跨多服务 → **编排式 Saga**（协调器状态机）；
> - 本地操作 + 通知下游 → **事务消息（RocketMQ）/ 本地消息表**；
> - 一站式落地 → **Seata（AT/TCC/Saga）**。
> 第三步 **保可靠**：所有补偿与重试必须保证**幂等**（唯一键 + 去重表），消息保证可靠投递（confirm + 持久化 + 手动 ACK）。
> 第四步 **兜底**：建设**对账与补偿任务**，定时比对上下游数据，发现不一致自动修复或告警人工介入。

> 💬 **一句话总结（考场应急版）**："互联网高并发场景多用**最终一致性 + 消息队列 + 补偿/对账**。"

## ⚠️ 丢分点（**本章最密集**）

1. ❌ **说"CAP 三选二"而不解释** → 必须写"**P 是客观存在、必须满足，只在分区发生时在 C 与 A 间权衡**"。
2. ❌ **CP/AP 选反** → 金融/支付/账务 = **CP**；社交/电商浏览/内容 = **AP**。
3. ❌ **ZooKeeper / Eureka 归类错误** → ZooKeeper = **CP**；Eureka = **AP**（Eureka 宁可返回旧数据也要可用）。**这是选择题和案例都爱考的经典配对**。
4. ❌ **Saga 两种模式记混** → 记关键词：**编排 = 有协调器/状态机/状态可见**；**协作 = 事件驱动/无中心/状态难追踪**。
5. ❌ 只写"用 Saga"不写"**补偿**"和"**幂等**" → Saga 的灵魂是**补偿动作**，落地保障是**幂等**。
6. ❌ **TCC 三段顺序写错** → **Try（预留）→ Confirm（确认）→ Cancel（取消）**。
7. ❌ 认为"引入 MQ 就解决了分布式事务" → MQ 只保证**消息可靠**，业务一致性还需**幂等 + 补偿 + 对账**。
8. ❌ **BASE 的 "BA" 写成"基本可用 = 部分不可用"** → 准确说法是"允许**损失部分**可用性（响应降级/功能降级），但**系统整体不崩溃**"。

# 8. 云原生：12‑Factor / 七大原则 / RPO‑RTO
> 对应原文第 6 章

## 🧊 一句话直觉：**"云原生 = 为云而生的应用"**

传统应用：像**养宠物**。你给服务器起名叫"小花"，给它治病、喂它吃饭、精心照料，它死了你很伤心。

云原生应用：像**养牛（ cattle not pets）**。牛没有名字，编号 001‑999，哪头生病了直接换一头，你根本不在乎。

> **核心差别**：传统应用"**依赖这台特定的机器**"；云原生应用"**在哪跑都一样，随时可被替换**"。

**云原生四大支柱**：**微服务 + 容器（Docker）+ DevOps + 持续交付**

## 📖 原理拆解

### 8.1 🔥 云原生设计原则（**案例/论文双考，必背**）

#### A. 四类设计原则（**基础版 —— 论述"为何采用云原生"最规范**）

| # | 原则 | 内容 |
|---|------|------|
| 1 | **服务化** | 微服务拆分、API 化，服务自治、独立部署 |
| 2 | **弹性** | HPA、无状态、按需扩缩，流量高峰自动扩容 |
| 3 | **可观测性** | 日志 / 指标 / 链路**三支柱**统一采集 |
| 4 | **自动化** | CI/CD、IaC（基础设施即代码）、自动恢复（故障自愈） |

#### B. 🔥 七大架构设计原则（**新版官方教材高频，必背**）

> 🎯 **口诀：服 弹 可 观 韧，自 动 零 演 进** —— 谐音记：**"服弹可观韧，自动零演进"**

| # | 原则 | 内容 | 对应技术 |
|---|------|------|---------|
| 1 | **服务化原则** | 微服务拆分、API 化 | 微服务、DDD |
| 2 | **弹性原则** | 按需扩缩、无状态、故障自愈 | HPA、无状态 |
| 3 | **可观测原则** | Metrics / Logs / Traces 三支柱 | Prometheus、ELK、SkyWalking |
| 4 | **韧性原则**（容错） | 熔断、降级、故障隔离 —— **"雪崩防护"的顶层原则** | Sentinel、Mesh |
| 5 | **所有过程自动化原则** | CI/CD、自动化运维、IaC | Jenkins、GitLab CI、Terraform |
| 6 | **零信任原则** | 安全，**不默认内网可信，始终验证** | mTLS、RBAC、OPA |
| 7 | **架构持续演进原则** | 绞杀者、防腐层**渐进迁移** | 见第 16 章 |

> 💡 **三层体系（帮助记忆全局）**：
> **12‑Factor**（应用改造规范）+ **四大/七大原则**（架构设计原则）+ **K8s / Mesh**（落地技术底座）

### 8.2 🔥 12‑Factor 云原生十二要素（**案例高频改造踩分点**）

> **什么时候用**：题目问"**如何改造应用以适配云原生？**" —— 尽量覆盖下面要点。

| # | 要素 | 人话 | 为什么重要 |
|---|------|------|-----------|
| 1 | **基准代码** | **一份**代码库，**多份**部署（dev/test/prod） | 多份代码库 = 不是应用，是分布式系统 |
| 2 | **依赖** | **显式声明**所有依赖 | 不靠"机器上刚好装了" |
| 3 | **配置** | **配置与代码分离**，存**环境变量**，**禁止硬编码** | ⭐**最高频** |
| 4 | **后端服务** | 把数据库、MQ 当作**附加资源** | 换个地址就能换数据库 |
| 5 | **构建、发布、运行严格分离** | 打包 ≠ 部署 ≠ 运行 | 可回溯、可回滚 |
| 6 | **无状态进程** | 实例**不存本地会话数据** | ⭐**最高频**，见下 |
| 7 | **端口绑定** | 通过**端口**对外提供服务 | 不依赖外部容器注入 |
| 8 | **并发** | **水平扩展**，多实例 | 靠加进程而不是加线程 |
| 9 | **可丢弃** | 进程**快速启动、优雅关闭** | 支撑弹性伸缩 |
| 10 | **开发/生产环境等价** | 缩小环境差异 | 减少"我这儿能跑" |
| 11 | **日志** | 当作**事件流**，**不存本地** | ⭐容器随时销毁，本地日志会丢 |
| 12 | **管理进程** | 后台任务**一次性运行** | 与常驻进程同等对待 |

> 🔥 **最高频关键词：无状态**
> **云原生改造最高频关键词** —— **会话、缓存数据不能保存在容器本地**。
> 原因：容器**随时可能被销毁重建**（扩缩容、故障自愈、滚动更新），存在本地的东西会**全部丢失**，且负载均衡会把请求打到**别的实例**上。

> 💬 **答题话术**：改造包括①**配置外部化**（配置移出代码，存入配置中心/ConfigMap，通过环境变量注入，禁止硬编码）；②**无状态化改造**（Session 外置到 Redis，本地不存任何会话与业务数据）；③**日志事件流化**（日志输出到标准输出，由采集 Agent 统一收集，不写本地文件）；④**构建/发布/运行分离**（镜像作为唯一交付物）；⑤**进程快速启动与优雅关闭**（支撑弹性伸缩与滚动发布）。

### 8.3 🔥 容灾指标 RPO / RTO（**案例论述踩分点**）

| 指标 | 全称 | 定义 | 人话 | 举例 |
|------|------|------|------|------|
| **RPO** | Recovery Point Objective | 故障发生时**允许丢失的数据量**（时间维度） | **能丢多少数据** | "最多丢失最近 5 分钟的数据" |
| **RTO** | Recovery Time Objective | 故障发生后**允许的业务中断时长** | **多久能恢复** | "15 分钟内恢复服务" |

> 🎯 **记忆法**：**P = Point = 数据点（丢了几个点）**；**T = Time = 时间（停了多久）**。
> 或者：**RPO 管"丢多少"，RTO 管"停多久"**。

**关联与选型**

| 业务 | 目标 | 手段 |
|------|------|------|
| **金融核心** | **RPO ≈ 0** | **同步复制**（如 MySQL Group Replication）；**事件表与业务表同事务提交** |
| **互联网业务** | 分钟级 RPO 可接受 | **异步复制 + 对账补偿** |

> **容灾三阶段**（**答题万能框架**）：
> **检测**（探针 / 心跳）→ **隔离**（熔断 / 驱逐）→ **恢复**（HPA / 滚动更新 / 回滚）

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 原则题** | "简述云原生的设计原则。" / "该改造方案遵循（或违反了）哪些云原生原则？" |
| **② 改造题** | "如何将传统应用改造为云原生应用？" |
| **③ 容灾题** | "要求故障恢复时间 <15 分钟、数据零丢失，请设计容灾方案。" |
| **④ 辨析题** | "解释 RPO 与 RTO 的含义，并说明本系统应如何设定。" |

## ✍️ 怎么答

**【模板：云原生改造方案（场景 C）】**
> ① **容器化**：用 **Docker** 打包应用及其依赖为镜像，解决开发‑测试‑生产**环境不一致**；
> ② **编排调度**：部署 **K8s** 集群，实现自动扩缩容、故障自愈、滚动发布；
> ③ **无状态改造**：**Session 外置到 Redis**，本地不保存会话与业务数据，配置外置；
> ④ **配置分离**：配置存入 **ConfigMap / Secret**，通过**环境变量注入**；
> ⑤ **服务治理**：**API 网关 + 注册中心**；复杂场景引入 **Service Mesh**；
> ⑥ **可观测建设**：日志、指标、链路追踪**三支柱**；
> ⑦ **CI/CD 流水线**：实现自动化构建、测试、发布与**一键回滚**。

## ⚠️ 丢分点

1. ❌ **RPO / RTO 说反** —— 这是**经典送命题**。记：**RPO = 丢多少（Point/数据点）**，**RTO = 停多久（Time）**。
2. ❌ **七大原则漏掉"韧性"或"零信任"** —— 这两条是新版特色，老资料没有，最容易漏。用口诀"**服弹可观韧，自动零演进**"防漏。
3. ❌ 12 要素只背标题不背含义 —— 题目常问"**第 X 要素的含义及其作用**"。
4. ❌ **"配置外部化"只写"放到配置文件"** → 必须是**环境变量 / 配置中心 / ConfigMap**，且强调**禁止硬编码**。
5. ❌ 把"无状态"简单说成"不用 Session" → 准确说法是"**实例本地不保存任何会话与业务状态，状态外置到 Redis/数据库**"，从而支持**任意扩缩容与故障替换**。

# 9. Docker 容器
> 对应原文第 7 章

## 🧊 一句话直觉：**"集装箱"革命**

在集装箱发明之前，装卸货物全靠人工一件件搬，**换一艘船就要重新折腾一遍**，货物损坏率极高。

集装箱的魔法在于：**规格统一、内容封装、与运输工具解耦**。不管是卡车、火车还是轮船，都能直接吊装。

> **Docker 就是软件世界的集装箱**：把应用 + 运行环境 + 依赖库 + 配置**全部打包进一个"镜像"**，到哪儿跑都一样。

## 📖 原理拆解

| 概念 | 定义 | 类比 |
|------|------|------|
| **镜像（Image）** | **只读模板**，包含应用及全部依赖 | **集装箱里的货物清单 + 货物**（或"安装光盘"） |
| **容器（Container）** | **镜像的运行实例** | 从模板**跑起来的一份进程** |

**三大价值**

1. **解决"开发‑测试‑生产环境不一致"**（**最核心的考点**）："在我机器上是好的" 成为历史；
2. **轻量级**：**进程级隔离**，共享宿主机内核；
3. **启动快**：秒级启动（对比虚拟机的分钟级）。

### 容器 vs 虚拟机（**必考对比**）

| 对比项 | 虚拟机（VM） | 容器（Docker） |
|--------|-------------|---------------|
| **隔离级别** | **操作系统级**（每个 VM 有独立 OS 内核） | **进程级**（共享宿主机内核） |
| **镜像大小** | GB 级 | **MB 级** |
| **启动速度** | **分钟级** | **秒级** |
| **资源开销** | 大（每个 VM 跑一整套 OS） | **小** |
| **隔离性** | **强** | 较弱（共享内核） |
| **单机密度** | 几十个 | **成百上千个** |

> 💬 **答题话术**：Docker 相比虚拟机**启动快、开销小、密度高**，适合微服务与弹性伸缩；但**隔离性弱于虚拟机**，安全敏感场景可结合虚拟机使用（如容器运行在 VM 中）。

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 概念题** | "什么是 Docker 镜像与容器？二者关系是什么？" |
| **② 对比题** | "比较容器与虚拟机的区别。" |
| **③ 价值题** | "引入容器技术能解决哪些问题？" |

## ⚠️ 丢分点

1. ❌ 说"容器就是轻量虚拟机" → 不准确。**虚拟机虚拟的是硬件 + 独立 OS；容器是进程隔离、共享内核**。
2. ❌ 忘记"**环境一致性**"这个核心价值 —— 题目问"为什么用 Docker"，这是第一答案。
3. ❌ 把"镜像"和"容器"说反 → **镜像 = 静态只读模板；容器 = 动态运行实例**。一个类比：镜像是"类"，容器是"对象"。

# 10. Kubernetes（K8s）
> 对应原文第 8 章 · **考点最密集的一章**

## 🧊 一句话直觉：**K8s = 容器的"操作系统 / 大管家"**

Docker 解决了"**怎么打包**"，但当你有 **80 个服务 × 3 个实例 = 240 个容器**，分布在 20 台机器上时：

- 哪个容器该放哪台机器？（**调度**）
- 容器挂了谁负责重启？（**自愈**）
- 流量高峰怎么自动加实例？（**扩缩容**）
- 发布新版本怎么做到不停机？（**滚动更新**）
- 容器 IP 变了，别人怎么找到它？（**服务发现**）

> **K8s 就是回答这些问题的"容器编排平台"**：你告诉它"**我要跑 3 个订单服务实例**"，它负责让这 3 个实例**永远**保持健康运行。

**一句话定位**：**容器编排平台，大规模自动化管理容器集群。**

## 📖 原理拆解

### 10.1 核心概念（**逐个都要会，考试直接填空**）

| # | 概念 | 作用 | 一句话记忆 | 典型场景 |
|---|------|------|-----------|---------|
| 1 | **Pod** | **K8s 最小调度单元**；一个 Pod 可封装 1 个或多个容器 | **"K8s 不直接管容器，管的是 Pod"** | 主容器 + 日志 sidecar |
| 2 | **Deployment** | **无状态**应用管理：副本扩缩、**滚动更新**、灰度 | **"管无状态服务"** | Web 服务、微服务 |
| 3 | **StatefulSet** | **有状态**应用管理 | **"管数据库/中间件集群"** | MySQL、Redis、ZooKeeper |
| 4 | **DaemonSet** | 保证**每个（或指定）节点运行且只运行一个 Pod** | **"每台机器上派一个"** | **日志采集（Filebeat）**、**监控探针（node‑exporter）** |
| 5 | **Service** | 一组 Pod 的**统一访问入口**，负载均衡 | **"给会变的 Pod 一个固定门牌号"** | ClusterIP / NodePort / LB |
| 6 | **Ingress** | **七层 HTTP 反向路由** | **"按域名/路径转发"** | `a.com/order` → 订单服务 |
| 7 | **ConfigMap / Secret** | 存放**配置** / **敏感信息**（密码、证书） | **"配置与密钥外置"** | 对应 12‑Factor 的配置外置 |
| 8 | **HPA** | **水平**扩缩：增减 Pod **实例数**（**加机器**） | **"加机器"** | 基于 CPU / QPS 自动扩缩 |
| 9 | **VPA** | **垂直**扩缩：修改 Pod **CPU/内存规格**（**不加减实例**） | **"换大机器"** | 单实例资源不足 |

### 10.2 🔥 StatefulSet vs Deployment（**速记，必考**）

| 场景 | 用什么 | 理由 |
|------|--------|------|
| **数据库、Redis 集群、ZooKeeper、MQ**（**有状态**） | **StatefulSet** | 需要**稳定网络标识、有序启停、持久化存储** |
| **Web 服务、微服务**（**无状态**） | **Deployment** | 实例完全等价，随便扩缩替换 |

> 🎯 **一句话**：**有状态（数据库/中间件集群）→ StatefulSet；无状态（Web/微服务）→ Deployment。**

### 10.3 🔥 HPA vs VPA（**案例常考选型对比**）

| 维度 | **HPA（水平扩缩）** | **VPA（垂直扩缩）** |
|------|-------------------|-------------------|
| **做什么** | 增减 **Pod 实例数量** | 修改 Pod 的 **CPU/内存规格** |
| **类比** | **加机器**（多开几家分店） | **换大机器**（把小店换成大店） |
| **触发指标** | CPU 利用率、内存、**自定义指标（如 QPS）** | 历史资源使用量 |
| **是否需要无状态** | **需要**（实例无状态才能随便加） | 不需要（原地加大） |
| **是否有中断** | 扩容无中断（新起 Pod） | **通常需要重启 Pod** |
| **适用** | **无状态服务、流量波动大**（首选） | 单实例资源不足、难以水平扩展的服务 |

> 💬 **答题话术**：优先采用 **HPA** —— 通过增减**无状态实例数**应对流量波动，**扩容无中断、伸缩范围大**，是云原生的主流做法；**VPA** 适合**难以水平拆分**的单体/有状态服务，但调整规格**通常需要重启 Pod，会造成短暂中断**。

### 10.4 🔥🔥 K8s 探针（**独立考点，2025 真题填空/简答高频**）

## 🧊 直觉：三种"体检"

| 探针 | 类比 | 问的问题 |
|------|------|---------|
| **liveness（存活探针）** | **"你还活着吗？"（测心跳）** | 进程是不是**卡死了**（死锁但进程还在） |
| **readiness（就绪探针）** | **"你能开始接客吗？"（测能不能上班）** | 服务**启动好了没**、能不能处理请求 |
| **startup（启动探针）** | **"你是慢热型吗？我多给你点时间"** | 慢启动应用**还没起来**，别急着判定死亡 |

| 探针 | 作用 | **失败后果（必背）** |
|------|------|---------------------|
| **liveness 存活探针** | 检测容器进程是否活着 | 失败 → **重启 Pod** |
| **readiness 就绪探针** | 检测容器是否**准备好接流量** | 失败 → **摘除流量（不重启）**，从 Service 后端摘除 |
| **startup 启动探针** | 保护**慢启动**应用，启动阶段**不触发 liveness** | 失败 → 重启；**启动成功后交由 liveness 接管**，避免慢启动被误杀 |

> 💡 **为什么需要 readiness？** 一个 Java 服务进程起来了，但要加载配置、预热缓存、连数据库，**这 30 秒内它活着但不能服务**。如果只靠 liveness，流量会打到"活的但没准备好"的实例上，导致报错。所以 **readiness 负责"摘流量"，liveness 负责"重启"**。
>
> 💡 **为什么需要 startup？** 老系统启动要 3 分钟，而 liveness 默认 30 秒不通就重启 → **永远起不来（重启死循环）**。startup 探针给它一个**宽限期**。

### 10.5 不可变基础设施（**云原生核心概念**）

> **容器镜像一旦构建就不再修改**；任何配置/代码变更都**构建新镜像 + 滚动发布**，**禁止登录容器 `exec` 改配置**。

**好处**：环境一致、**可回溯**、杜绝"**雪花服务器**"（每台机器手工配置得独一无二，谁都不敢动）、故障可**整体替换**。

> ⚠️ **反义词：雪花服务器（Snowflake Server）** —— 手工维护、配置独一无二、无法复制重建的服务器。
> ⚠️ **对立概念：可变基础设施** —— 允许 SSH 登录机器改配置。**云原生明确反对这种做法**。

### 10.6 K8s 高频场景（**方案题素材**）

- **自动故障自愈**，重启异常 Pod；
- **滚动升级、不停机发布**，保留旧版本支持**一键回滚**；
- **弹性伸缩**应对流量高峰（HPA 基于 CPU/自定义指标如 QPS 扩容，流量结束自动缩容）；
- **Namespace 隔离**：多环境/多租户隔离，如"测试环境数据污染" → **每个 PR 独立 Namespace**；
- **探针/自愈**：liveness 失败自动重启 Pod，readiness 差异化设置，保障流量只进健康实例。

> 🎯 **K8s / Service Mesh / DevOps 三者分工一句话记忆（案例高频论述题标准答法）**：
> **K8s 管"生死扩缩容"（资源层），Service Mesh 管"调用与可靠"（通信层），DevOps 流水线管"快上快回滚"（交付层）。**

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 填空题** | "K8s 中最小调度单元是 \_\_\_；管理有状态应用应使用 \_\_\_。" |
| **② 辨析题** | "比较 HPA 与 VPA。" / "Deployment 与 StatefulSet 有何区别？" |
| **③ 探针题** | "K8s 有哪几种探针？各自失败后的处理方式是什么？" |
| **④ 场景题** | "某 Java 服务启动需 3 分钟，发布后总被重启，分析原因并解决。" |
| **⑤ 概念题** | "什么是不可变基础设施？有何好处？" |

## ✍️ 怎么答

**【模板：探针题】**
> K8s 提供三类探针：① **livenessProbe（存活探针）**：检测容器进程是否存活，失败则 **kubelet 重启 Pod**；② **readinessProbe（就绪探针）**：检测容器是否已准备好接收请求，失败则**将该 Pod 从 Service 的后端端点中摘除（不重启）**，保障流量只进入健康实例；③ **startupProbe（启动探针）**：为**慢启动应用**提供更长的启动宽限期，**启动成功前 liveness 不生效**，避免慢启动应用被反复重启，启动成功后交由 liveness 接管。

**【模板：慢启动被重启问题】**
> **原因**：liveness 探针的超时/失败阈值设置过短，**慢启动应用尚未完成初始化就被判定为不健康，被反复重启**，陷入重启循环。
> **解决**：配置 **startupProbe**，设置足够长的 `failureThreshold × periodSeconds` 覆盖应用最长启动时间；同时**区分 readiness 与 liveness** —— readiness 用于**启动期摘除流量**，liveness 用于**运行期故障重启**。

## ⚠️ 丢分点

1. ❌ **探针失败后果记混** → **liveness 失败 = 重启；readiness 失败 = 摘流量不重启**。这是**最高频考点**。
2. ❌ **HPA/VPA 说反** → **H = Horizontal = 加实例（横向）；V = Vertical = 加规格（纵向）**。
3. ❌ **DaemonSet 记成"部署 N 个副本"** → DaemonSet 是**每个节点一个**，不是"总共 N 个"。
4. ❌ **StatefulSet 只答"有状态"**，不答它的三大能力：**稳定网络标识、有序启停、持久化存储**。
5. ❌ 认为 Pod = 容器 → **Pod 是最小调度单元，一个 Pod 可含多个容器**（这也是 Sidecar 能实现的基础，与第 11 章联动）。
6. ❌ **Secret 当成加密存储** → Secret 只是 **Base64 编码**（不是加密），生产需配合 KMS/密管。这个细节能加分。

# 11. Service Mesh 服务网格 + 零信任安全
> 对应原文第 9 章 · **2025‑2026 新增热点**

## 🧊 一句话直觉：**给每个服务配一个"贴身秘书"**

**改造前**：每个服务自己写代码处理 —— 重试、熔断、鉴权、加密、埋点。80 个服务 × 5 种语言 = 重复实现 400 遍，改一个策略要改 80 个地方。

**Mesh 的做法**：给每个服务**配一个"贴身秘书"（Sidecar 代理）**，秘书坐在服务旁边，**所有进出的网络流量都经过秘书**。

```
【有 Mesh】
[订单服务] ←→ [秘书 Envoy]  ←──网络──→  [秘书 Envoy] ←→ [库存服务]
   业务代码                                              业务代码
 (只管业务)                                             (只管业务)
```

> **秘书负责**：限流、熔断、**mTLS 加密**、链路追踪、路由。
> **服务自己**：只管业务逻辑，**一行治理代码都不用写**。

**再一个类比**：Mesh 就像**给每个办公室门口装了一个智能门禁 + 快递收发室**，员工只管干活，进出的事全交给门禁系统。

## 📖 原理拆解

### 11.1 核心定义

一种**非侵入式**的微服务治理方案，将**流量治理逻辑从业务代码剥离**，放到 **Sidecar 代理进程**。

### 11.2 两大平面（**必背**）

| 平面 | 组成 | 职责 |
|------|------|------|
| **数据平面** | **Sidecar — Envoy** | **拦截服务之间的流量**，处理限流、熔断、**mTLS 加密**、链路追踪 |
| **控制平面** | **Istio Pilot** | **下发治理规则**，**不需要修改业务代码** |

> 🎯 记忆：**数据平面 = 干活的（每个服务旁边一个）；控制平面 = 发号施令的（一个就够）**。

### 11.3 优缺点（**辨析题必答**）

| 优点 | 缺点 |
|------|------|
| **业务代码零侵入** | **额外增加网络开销**（每个请求多一跳代理） |
| **多语言微服务统一治理** | **运维复杂度上升** |
| 治理能力集中配置、动态生效 | 排障链路变长 |

### 11.4 与 API 网关的区别（**见第 5 章，必背**）

> 网关管**南北向**（外部 → 服务）；Service Mesh 管**东西向**（服务间调用），治理更**细粒度**。
> **Mesh 不能替代网关**：网关负责**对外暴露、认证、限流入口**；Mesh 负责**内部服务间流量治理**。二者**南北 + 东西互补，常协同部署**。

### 11.5 🔥 微服务 / 分布式安全架构（**案例高频小问，云原生必背**）

| # | 措施 | 内容 |
|---|------|------|
| 1 | **零信任架构（Zero Trust）** | **永不信任、始终验证**；微服务之间用 **mTLS 双向加密**（Istio Sidecar 自动注入实现），**不默认内网可信** |
| 2 | **跨服务身份传递** | **JWT 令牌透传**，实现服务间身份认证 |
| 3 | **最小权限原则** | 服务账号 **RBAC**；K8s **RBAC + Namespace** 权限隔离 |
| 4 | **策略引擎 OPA**（Open Policy Agent） | 服务网格**细粒度访问控制**（如"订单服务只允许调支付服务"） |
| 5 | **网关安全边界** | API 网关做**统一认证/限流入口**，与 Mesh 东西向 mTLS 形成**南北 + 东西双层防护** |

> 💡 **零信任的核心反转**：传统安全是"**城堡 + 护城河**"（内网可信，守住边界就行）；零信任是"**内网同样不可信，每一次调用都要验证身份和授权**"。

### 11.6 高频协同场景（**答题话术**）

- **Mesh + Sentinel**：Istio Sidecar 接管通信（非侵入），**Sentinel** 做精细化熔断降级配置（如**失败率 > 50% 触发熔断**）；
- **Mesh + SkyWalking / Jaeger**：Sidecar **自动采集链路数据，无需业务埋点**，实现全链路可视化定位故障节点；
- **Mesh + OAuth2 Proxy / 零信任认证**：Sidecar 或入口网关集成 OAuth2 Proxy / mTLS，实现服务间**零信任认证**。

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 概念题** | "什么是 Service Mesh？其数据平面与控制平面分别做什么？" |
| **② 辨析题** | "Service Mesh 与 API 网关有何区别？能否替代网关？" |
| **③ 安全题** | "微服务架构下如何保障服务间通信安全？" |
| **④ 方案题** | "该系统服务数量多、语言异构，如何统一治理？" |

## ✍️ 怎么答

**【模板：微服务安全架构】**
> ① **零信任**：不默认内网可信，服务间通信启用 **mTLS 双向 TLS**（由 Service Mesh 的 Sidecar **自动注入、证书自动轮换**，业务零改造）；
> ② **身份传递**：统一认证（OAuth2/OIDC）颁发 **JWT**，跨服务调用时**透传令牌**，各服务本地校验实现无状态鉴权；
> ③ **最小权限**：基于 **RBAC** 为服务账号授权，K8s 中结合 **Namespace** 做租户/环境隔离；
> ④ **细粒度策略**：引入 **OPA 策略引擎**实现服务级访问控制（如仅允许订单服务调用支付服务）；
> ⑤ **边界防护**：**API 网关**统一认证、限流，与 Mesh 的东西向 mTLS 形成**南北 + 东西双层防护**。

## ⚠️ 丢分点

1. ❌ 只说"Mesh 是 Sidecar"，漏掉"**非侵入 / 业务代码零侵入**"这一核心价值。
2. ❌ **数据平面 / 控制平面职责搞反** → 数据平面（Envoy）**拦截和执行**；控制平面（Istio）**下发规则**。
3. ❌ **只答优点不答缺点** → 必须有"**额外网络开销、运维复杂度上升**"。
4. ❌ **mTLS 写成 TLS** → **mTLS = 双向 TLS**，**双方互相验证证书**。单向 TLS 只有客户端验证服务端。
5. ❌ 认为"零信任 = 更强的防火墙" → 零信任的本质是**"永不信任、始终验证"**，**取消内外网信任差异**。

# 12. Serverless 无服务器架构
> 对应原文第 10 章

## 🧊 一句话直觉：**"租车 vs 自己买车养车"**

- **传统方式（买车）**：买车、上牌、保险、保养、停车…… 就算一年只开 10 次，这些钱和精力也得花。
- **Serverless（租车/打车）**：**用的时候叫一辆，按里程付费，用完走人**，车归谁保养你根本不关心。

> **Serverless 不是"没有服务器"**，而是"**你不用管服务器**"—— 服务器依然存在，只是**由云厂商管**。

## 📖 原理拆解

**核心特点**
- **无需管理服务器**；
- **按实际资源消耗计费**（按调用次数 / 执行时长 / GB‑秒）；
- 平台**自动弹性扩缩**（从 0 到 N）。

| 优点 | 缺点 |
|------|------|
| **运维成本低** | 🔥**冷启动延迟**（首次调用要拉起运行环境） |
| **自动弹性** | **运行环境受限**（运行时种类、**执行时长上限**、并发限制） |
| 按量付费、闲置零成本 | 调试排障困难、厂商锁定风险 |

**适用场景（必背）**
- ✅ **事件驱动**（文件上传后触发处理）
- ✅ **定时任务**（每天凌晨生成报表）
- ✅ **短生命周期接口**
- ✅ **文件处理**（图片压缩、视频转码）

**不适合（必背）**
- ❌ **长连接**（WebSocket、IM）
- ❌ **高延迟敏感**（实时交易）
- ❌ **有状态长任务**（长时间运行的批处理）

> 💬 **答题话术模板**：Serverless 的核心是"**无服务器管理 + 按量计费 + 自动弹性**"；其权衡点是**冷启动延迟**；适用于**事件驱动/短时任务**，不适于**长连接、有状态长任务**业务。

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 概念题** | "什么是 Serverless？其核心特点是什么？" |
| **② 选型题** | "某图片处理服务流量极不规律，是否适合 Serverless？说明理由。" |
| **③ 辨析题** | "Serverless 与容器（K8s）如何选型？" |

## ✍️ 怎么答

**【模板：Serverless vs 容器选型】**
> **Serverless** 适合**事件驱动、流量波峰波谷明显、短时任务、无状态**的场景（如图片压缩、定时报表、Webhook），优势是**零运维、按量付费、自动弹性**；缺点是**冷启动延迟、执行时长受限、不适合长连接**。
> **容器/K8s** 适合**长驻服务、长连接、有状态、对延迟敏感、需要精细控制运行环境**的场景。
> 实际架构中常**混合使用**：核心在线服务用 K8s，边缘的异步/事件型任务用 Serverless。

## ⚠️ 丢分点

1. ❌ 把 Serverless 理解成"真的没有服务器" → 是**服务器管理责任的转移**，不是物理消失。
2. ❌ **忘记"冷启动"** → 这是 Serverless 的**招牌缺点**，不写必丢分。
3. ❌ **适用范围写反** → 记住"**三适合**：事件驱动/定时任务/短时任务"；"**三不适合**：长连接/延迟敏感/有状态长任务"。

# 13. Web 高可用基础架构 + 高并发设计模式
> 对应原文第 11 / 15 章

## 🧊 一句话直觉：**一家火爆餐厅的"分流术"**

| 餐厅做法 | 技术对应 |
|---------|---------|
| 门口**领位员**安排你坐哪桌 | **负载均衡**（Nginx / SLB） |
| 菜单、纸巾**提前摆在桌上**（不用每次找服务员要） | **CDN 缓存静态资源** |
| **热菜现做、凉菜预制**分开处理 | **动静分离** |
| 高峰期**门口排队发号**，超了就劝退 | **限流** |
| 前台**不记住**你是谁，凭**小票/会员卡**认人 | **无状态 + Session 外置** |
| 服务员都能查你的订单（不绑定某个服务员） | **Session 共享（Redis）** |
| 备菜区**提前备好**热门食材 | **多级缓存** |

## 📖 原理拆解

### 13.1 核心组件

| 组件 | 作用 | 考点 |
|------|------|------|
| **反向代理（Nginx）** | 客户端**统一入口**，**隐藏后端服务器** | 与正向代理区别（见下） |
| **负载均衡** | **轮询、加权轮询、最小连接数**，分发流量 | 算法选择与场景匹配 |
| **CDN** | 静态资源**就近访问**，**降低源站压力** | 回源、边缘缓存 |
| **动静分离** | 静态资源交给 CDN/对象存储，后端只处理**动态请求** | 降低后端压力 |
| **会话共享** | **Redis 存储 Session**，**禁止会话绑定单台服务器**（保证无状态） | ⭐高频 |

### 13.2 负载均衡算法（**补充，常考**）

| 算法 | 机制 | 适用 |
|------|------|------|
| **轮询（Round Robin）** | 依次分发 | 服务器性能相同 |
| **加权轮询** | 性能好权重大，多分点 | **服务器性能不均衡** |
| **最小连接数** | 分给当前连接最少的 | **长连接、请求耗时差异大** |
| **源地址哈希（IP Hash）** | 按客户端 IP 哈希固定到某台 | 需要**会话保持**（但**违背无状态原则**，不推荐） |

> ⚠️ **反向代理 vs 正向代理（易混）**：
> - **正向代理**：**代理客户端**（VPN、公司上网代理）—— 服务器不知道真实客户端是谁；
> - **反向代理**：**代理服务器端**（Nginx）—— **客户端不知道真实服务器是谁**。

### 13.3 高并发 Web / 云原生设计模式（**综合考法**）

| 模式 / 技术 | 作用 |
|------------|------|
| **负载均衡（Nginx/SLB）** | 分发流量到多实例，**提升吞吐** |
| **CDN + 边缘计算** | 静态资源**就近缓存**，**降低回源延迟** |
| **动静分离** | 动态请求走应用，静态资源走 **CDN/对象存储** |
| **无状态设计** | 服务不存本地状态，**Session 外置 Redis**，便于**水平扩展** |
| **Session 共享** | **Redis 集中存储 Session** |
| **多级缓存** | **本地缓存 + Redis + CDN**，**防缓存雪崩** |
| **限流熔断 + 降级** | 网关 / Sentinel / Mesh **多层防护**，**保核心链路** |
| **读写分离 / CQRS** | **读多写少**场景优化，**命令与查询分离** |

> 📌 **缓存三兄弟（穿透/击穿/雪崩）** 属 Redis 专项，详见 `08-数据库与数据设计-新手向拆解.md`；在本模块只需记住"**多级缓存 + 随机过期时间 + 熔断降级**"是通用对策。

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 架构题** | "设计一个支持百万并发的 Web 系统架构。" |
| **② 优化题** | "系统响应慢、源站压力大，如何优化？" |
| **③ 找茬题** | "使用了会话绑定（Session Sticky），存在什么问题？" |
| **④ 算法题** | "服务器性能不一，应选择哪种负载均衡算法？" |

## ✍️ 怎么答

**【模板：高并发 Web 架构设计（由外到内背）】**
> ① **DNS / CDN 层**：静态资源与热点内容推送到 **CDN** 边缘节点，实现**就近访问、降低源站压力**；
> ② **接入层**：**负载均衡（Nginx / SLB）** 将流量分发到多个应用实例，采用**加权轮询**（服务器性能不均）或**最小连接数**（请求耗时差异大）；
> ③ **应用层**：应用**无状态化**，**Session 外置到 Redis 实现会话共享**，支持任意水平扩展；
> ④ **缓存层**：构建**本地缓存 + Redis 分布式缓存 + CDN** 的**多级缓存**，热点数据预热，设置**随机过期时间**防雪崩；
> ⑤ **数据层**：**读写分离**（主库写、从库读），**分库分表**应对大数据量；
> ⑥ **异步与防护**：引入**消息队列削峰填谷**；网关与应用层配置**限流、熔断、降级**，保障核心链路；
> ⑦ **可观测与弹性**：建设三支柱监控，结合 **HPA** 自动扩缩容。

## ⚠️ 丢分点

1. ❌ **Session 方案答"会话绑定（Sticky Session）"** → **错误**！这是**反面典型**。必须答"**Session 外置 Redis 实现共享，保证无状态**"。理由：绑定后实例挂了用户就掉线，且无法弹性伸缩。
2. ❌ **反向代理/正向代理搞反** → 记住"**反向代理代理的是服务器**"。
3. ❌ 高并发题**只写"加缓存"** → 高并发是**分层体系**，必须**由外到内**（CDN → 负载均衡 → 应用无状态 → 多级缓存 → 读写分离 → MQ → 限流熔断）逐层展开，才够分。
4. ❌ 把 CDN 的作用说成"加速动态请求" → CDN 主要缓存**静态资源**，动态请求一般**回源**。

# 14. DDD 领域驱动与微服务拆分
> 对应原文第 12 章 · **近年权重显著提升，拆分题的标准答案**

## 🧊 一句话直觉：**"按业务切，不是按技术切"**

**错误拆法（按技术分层）**：
```
[ 用户controller服务 ] [ 商品controller服务 ] ...
[ 用户service服务   ] [ 商品service服务   ] ...
[ 用户DAO服务       ] [ 商品DAO服务       ] ...
```
→ 改一个"下单"业务要动 3 个服务，**分布式单体**，比单体还糟。

**正确拆法（按业务域/限界上下文）**：
```
[ 订单服务 ]（含订单的 controller/service/dao/数据库，全闭环）
[ 库存服务 ]
[ 支付服务 ]
```
→ 改下单业务，**只改订单服务**。

> **类比**：按业务拆 = **按科室分医院**（内科、外科、儿科，各科自己全权负责）；按技术拆 = **把所有医生放一层、所有护士放一层**（荒谬）。

## 📖 原理拆解（**核心概念**）

| 概念 | 定义 | 为什么重要 |
|------|------|-----------|
| **领域 / 子域** | 业务问题的范围（电商：订单域、商品域、支付域……） | 拆分的第一刀 |
| **限界上下文（Bounded Context）** | **模型的有效范围**；在这个边界内，术语和模型含义**唯一确定** | ⭐**微服务的拆分边界 ≈ 限界上下文边界** |
| **聚合根** | **聚合的唯一访问入口**，外部**只能通过聚合根**操作 | **一致性边界** |
| **防腐层（ACL）** | 新旧系统迁移中**隔离遗留系统脏模型**，防止污染新微服务领域模型 | 见第 16 章三大模式 |
| **实体 / 值对象 / 领域服务 / 领域事件** | 支撑领域建模的基本构造块 | 建模工具 |

> 💡 **"限界上下文"的通俗理解**：同一个词在不同部门含义不同 —— 电商里"**商品**"在**商品中心**指 SKU 与详情，在**订单中心**指订单行里的一个快照，在**仓储中心**指库存单位。
> 如果强行统一成一个模型，就会出现"**大泥球模型**"（谁都往里塞字段，最后谁都不敢改）。
> **限界上下文就是承认"不同边界里，同一个词可以有不同含义"**。

> 💬 **答题标准话术**：**微服务的拆分边界应基于 DDD 的限界上下文确定**；答题时"**按业务域 + 限界上下文拆分**"比"按技术层拆分"**规范得多**，是近年真题的**标准答案**。

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 拆分题** | "请为该系统划分微服务，说明划分依据。" |
| **② 概念题** | "什么是限界上下文？其与微服务的关系是什么？" |
| **③ 改造题** | "现有系统按技术层拆分导致改动频繁，应如何改进？" |

## ✍️ 怎么答

**【模板：微服务拆分方案】**
> ① 采用 **DDD 领域驱动设计**进行拆分：先识别**领域与子域**（核心域、支撑域、通用域）；
> ② 以**限界上下文**作为微服务边界，一个限界上下文对应一个（或一组）微服务，服务内**高内聚**、服务间**低耦合**；
> ③ 以**聚合根**作为**一致性边界**，聚合内用本地事务保证强一致，跨聚合/跨服务采用**最终一致性**（Saga / 事务消息 / 领域事件）；
> ④ 服务间通过**领域事件**异步协作，避免同步长调用；
> ⑤ 与遗留系统交互处引入**防腐层（ACL）**，隔离遗留脏模型，防止污染新领域模型；
> ⑥ 避免循环依赖，粒度适中，防止"**纳米服务**"。

## ⚠️ 丢分点

1. ❌ **按技术层拆分**（controller 一层、service 一层）→ **重大错误**，这叫"**分布式单体**"，是案例题的**反面教材**。
2. ❌ 只写"按业务拆分"不提"**限界上下文**" → 少了**标准术语**，显得不专业。
3. ❌ 把"聚合根"说成"数据库表" → 聚合根是**领域模型的访问入口和一致性边界**。
4. ❌ 忘记"**防腐层**" → 凡是涉及**遗留系统迁移**的题目，防腐层几乎是必答项。

# 15. 中间件与消息队列（MQ 可靠性三问）
> 对应原文第 14 章

## 🧊 一句话直觉：**MQ 就是一个"缓冲区/蓄水池"**

上游暴雨（瞬时 10 万请求）→ 蓄水池接住 → 下游按自己的节奏（每秒 2000）慢慢放水。

> 这就是"**削峰填谷**"。除此之外 MQ 还有两大价值：**异步解耦**（上游不用等下游）、**可靠投递**。

## 📖 原理拆解

### 15.1 常见中间件与考点

| 中间件 | 角色 | 案例题考点 |
|--------|------|-----------|
| **RocketMQ / Kafka** | **异步解耦、削峰填谷、日志采集** | **事务消息**保证最终一致；Kafka **分区 / 副本 / Consumer Group** |
| **Redis** | **缓存热点、分布式锁、限流计数** | 与 MQ 配合做**库存原子扣减（Lua 脚本）** |
| **Elasticsearch** | **日志 / 全文检索** | 配合 **ELK（EFK）** 做日志实时查询 |
| **ShardingSphere / MyCat** | **分库分表中间件** | **水平分片、读写分离** |

> 💡 **Kafka 三件套（了解即可，防超纲）**：
> - **分区（Partition）**：一个 Topic 切成多份，**并行吞吐**的来源；同时**分区内保证顺序**；
> - **副本（Replica）**：分区的备份，**高可用**的来源；
> - **Consumer Group**：一组消费者**共同消费**一个 Topic，**每个分区只能被组内一个消费者消费**（负载均衡）。

### 15.2 🔥🔥 MQ 可靠性三问（**必背，考场可直接默写**）

> **2025 真题"订单与库存偶尔不一致"即此类问题，需能独立成节作答。**

| 问题 | 根因 | **解决方案（必背）** |
|------|------|---------------------|
| **① 消息丢失** | 生产者发丢了 / MQ 宕机内存数据没了 / 消费者没处理就确认了 | **生产者确认（publisher confirm）** + 消息**持久化**（落盘） + 消费者**手动 ACK**（处理完才确认，**不自动提交**） |
| **② 重复消费** | 网络重传 / 消费者处理完但 ACK 丢失 → 消息被再次投递 | 消费端**幂等**：业务**唯一键 + 去重表 / Redis SETNX**，消费**前查重** |
| **③ 消息乱序** | 消息被分发到不同分区/队列，各自并行处理 | **同一业务键（订单 ID）路由到同一分区/队列**，**单分区内 FIFO**，保证顺序消费 |

> 🎯 **答题话术（考场可直接默写，一字不差）**：
> **丢失三件套（confirm + 持久化 + 手动 ACK）；重复靠幂等（唯一键去重表）；乱序靠同键同分区。**

### 15.3 可观测性深化（**OpenTelemetry，2025‑2026 趋势**）

| 概念 | 说明 |
|------|------|
| **OpenTelemetry（OTel）** | **统一采集标准**；**Collector 同时接收 Metrics / Logs / Traces 三支柱**，取代零散 SDK |
| **eBPF** | **无侵入式内核级监控**（如 Cilium Hubble 网络观测） |
| **SLO / SLI / Error Budget** | **SLI**（服务等级指标，如成功率）→ **SLO**（目标值，如 99.9%）→ **错误预算**（允许失败额度，如每月 43 分钟），用于**告警与发布门禁** |

> 💡 与三支柱的关系：**OTel 是统一采集层，三支柱是数据形态。**

### 15.4 信创与国产化（**论述题加分项，涉及"自主可控"必提**）

| 类别 | 国产替代 |
|------|---------|
| **中间件** | **东方通 TongWeb / 宝兰德 BES** 替代 Tomcat / WebLogic |
| **数据库** | **达梦 DM / 人大金仓 Kingbase** 替代 Oracle / MySQL |
| **国密算法** | **SM2**（**非对称加密/数字签名** → 网关认证）、**SM3**（**摘要/完整性校验**）、**SM4**（**对称加密** → 数据存储） |

> 💬 **答题话术模板**："若项目有**自主可控**要求，XX 组件可选用国产 **YY** 替代，并采用**国密 SMx 算法**保障安全合规。"

### 15.5 AI Infra 与云原生融合（**2026 新大纲热点，了解为主**）

- **AI Serving 架构**：**Triton Inference Server / vLLM / Ollama** 在 K8s 中以 **Deployment / StatefulSet** 部署，声明 **GPU 资源**；
- **GPU 虚拟化与调度**：**NVIDIA Device Plugin**（暴露 GPU 资源）、**MIG 多实例 GPU**、GPU 共享/分时复用提升利用率；
- **RAG 架构组件**：**向量数据库（Milvus / Faiss）**选型、Embedding 服务独立部署、语义搜索结果缓存；
- **Agent 编排**：**LangChain / LlamaIndex** 在微服务中集成（工具调用 → 后端服务）。

> 💡 **命题预测**：可能以"**设计支持大模型推理的云原生架构**"形式出题，既考 K8s 又考 AI 基础设施。

### 15.6 边缘计算与端边云协同（**IoT/AI 场景延伸，了解**）

| 层 | 职责 |
|---|------|
| **云端** | 中心管控 / 模型训练 / 全局决策 |
| **边缘端** | 近场计算 / **低时延推理** / **弱网自治** |
| **终端** | 数据采集 / 展示 |

- **框架**：**KubeEdge / SuperEdge** 边缘容器编排；
- **设备接入协议**：**MQTT / CoAP**（在设备接入层的角色）；
- 协同：**边缘 AI 推理 + 云端训练**，应对弱网/离线场景。

## 🎯 怎么考

| 问法 | 举例 |
|------|------|
| **① 可靠性题** | "如何保证消息不丢失？如何避免重复消费？" |
| **② 选型题** | "异步化改造应引入什么中间件？为什么？" |
| **③ 一致性题** | "订单与库存偶尔不一致，分析原因并给出方案。" |
| **④ 加分题** | "项目要求自主可控，架构选型上应注意什么？" |

## ✍️ 怎么答

**【模板：订单与库存偶尔不一致（2025 真题型）】**
> **可能原因**：①订单服务写库后发送扣减库存消息失败或丢失，导致库存未扣；②消息重复投递，库存被重复扣减；③消息乱序，先到的后处理；④消费端未做幂等；⑤本地事务与消息发送非原子（写库成功但消息未发/反之）。
>
> **解决方案**：
> ① **保证不丢**：生产者开启 **publisher confirm**，消息**持久化**落盘，消费者**手动 ACK**（业务处理成功后再确认）；
> ② **保证不重**：消费端实现**幂等**，以**订单号 + 操作类型**作为**唯一键**，通过**去重表或 Redis SETNX** 消费前查重；
> ③ **保证不乱序**：以**订单 ID 作为业务键路由到同一分区/队列**，单分区内 FIFO 顺序消费；
> ④ **保证原子性**：采用 **RocketMQ 事务消息**或**本地消息表**（业务与消息**同库同事务**提交），保证本地事务与消息发送的原子性；
> ⑤ **兜底**：建设**定时对账任务**比对订单与库存数据，发现不一致自动补偿或告警人工介入。

## ⚠️ 丢分点

1. ❌ **三问只答一问** → 题干常问"如何保证消息可靠"，**三个问题都要答全**（丢失/重复/乱序），这是标准配置。
2. ❌ **重复消费的答案是"去重"而不是"幂等"** → 关键词是**幂等**（同一操作执行多次结果一致），实现手段才是"唯一键 + 去重表"。
3. ❌ **乱序的方案答"加锁串行处理"** → 标准答案是"**同一业务键路由到同一分区**，利用分区内 FIFO"。加锁会严重牺牲吞吐。
4. ❌ **消费者 ACK 答"自动提交"** → 必须是**手动 ACK**，且是**业务处理完成后**再确认。
5. ❌ **信创题只写"用国产数据库"** → 完整答法要包含"**国产中间件（东方通/宝兰德）+ 国产数据库（达梦/人大金仓）+ 国密算法 SM2/SM3/SM4**"，并说明各自用途（SM2 签名/非对称、SM3 摘要、SM4 对称加密存储）。

# 16. 案例题万能答题框架（4 大场景）
> 对应原文第 13 章 · **背熟 = 直接得分**

## 🧊 直觉：案例题只有 4 类"剧本"

拿到题先**归类**，然后**套模板**。90% 的分布式/云原生案例题逃不出这 4 个剧本。

## 场景 A：单体系统改造为微服务

**【七步模板】**
1. **需求分析，业务域识别**；
2. 基于 **DDD 限界上下文**拆分微服务，**划分服务边界**；
3. **搭建基础设施**：注册中心、配置中心、API 网关；
4. **数据库拆分**，每个微服务**独立库**；
5. **增量迁移**，**绞杀者模式**逐步替换单体；
6. 建设**服务治理、监控告警、链路追踪**体系；
7. **容器化**，云原生改造，**CI/CD 流水线**。

### 🔥 数据迁移三阶段（**单体拆微服务落地细节，案例常考**）

> **双写**（新旧库同时写）→ **对账**（校验双写一致性）→ **切读**（读流量从旧库切到新库，**再停旧写**）

| 阶段 | 做什么 | 目的 |
|------|--------|------|
| **① 双写** | 同时写新库和旧库（旧库为主，保证业务不受影响） | 让新库**开始积累数据** |
| **② 对账** | 定时比对新旧库数据，修复差异 | **验证新库数据正确** |
| **③ 切读** | 读流量**灰度切到新库**，观察无误后**停止写旧库** | 完成迁移，**可回滚** |

> 💡 **核心目标**：**零数据丢失 + 业务不停机**。答题时强调"**每一步都可回退**"。

## 场景 A2：🔥 遗留系统渐进演化迁移三大模式（**独立考点，2024‑2025 真题**）

> 🎯 **区分口诀：流量拦截选绞杀者；新旧模型隔离选防腐层；单体内部组件逐步替换选抽象分支。**

| 模式 | 核心含义 | 适用场景 |
|------|---------|---------|
| **绞杀者模式（Strangler Fig）** | 新建微服务，**逐步拦截单体流量**，最终"绞杀"杀死单体 | **整体渐进替换，保业务连续** |
| **防腐层（ACL — Anticorruption Layer）** | 新旧系统中间加**适配层**，**隔离遗留系统脏模型**，**防止污染新领域模型**（DDD 配套） | **新旧模型语义不一致、需隔离** |
| **抽象分支模式（Branch by Abstraction）** | 单体内部**先抽抽象接口**，旧实现与新微服务实现**并存**，逐步切换 | **单体内部组件逐步替换，免大停机** |

**🧊 三个类比**
- **绞杀者**：像**爬山虎缠树** —— 新藤一点点长，最后把老树完全包住取代它。**从外面围攻**。
- **防腐层**：像**海关检疫** —— 外面的东西进来前先消毒翻译，**脏东西不许进来**。**在边界设卡**。
- **抽象分支**：像**装修时先装一个总闸门**，新旧水管都接到闸门上，**哪天切哪根都行**。**从内部改造**。

## 场景 B：系统出现雪崩 / 稳定性差

**【五步模板】**
1. **API 网关增加限流**；
2. 微服务引入**熔断、降级、超时重试**策略；
3. 增加**监控告警与链路追踪**；
4. 优化**分布式事务**方案，**减少长同步调用**；
5. **异步解耦**，消息队列**削峰填谷**。

（更完整的 7 条版本见第 6 章模板）

## 场景 C：云原生改造方案设计

**【七步模板】**（见第 8 章，此处略，核心：容器化 → 编排调度 → 无状态 → 配置分离 → 服务治理 → 可观测 → CI/CD）

## 场景 D：🔥 灰度 / 发布策略选型对比（**改造迁移大题高频**）

| 策略 | 机制 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **滚动发布** | **逐个替换 Pod**，不停机 | 资源占用低、**无停机** | **版本混合共存**一段时间 | **常规升级** |
| **蓝绿发布（红黑）** | **两套完整环境**，切流量 | **零停机、回滚快**（切回旧环境） | **双倍资源开销** | **关键系统、需秒级回滚** |
| **金丝雀（灰度）** | **小流量切新版本**，观察后全量 | **风险最低**，可早发现问题 | 需**流量路由**能力 | **云原生改造首选** |
| **红黑发布** | 类似蓝绿，新（红）起**全量接管**、旧（黑）**即下线** | 快速切换、回滚靠旧环境兜底 | 同蓝绿**资源翻倍** | 与蓝绿同族 |

> 💬 **答题话术**：默认推**金丝雀 / 渐进式发布** —— **风险最低、业务连续**，配合 **K8s + Service Mesh 的流量切分能力**实现按比例的灰度；关键系统对回滚速度要求极高时选**蓝绿/红黑**（代价是资源翻倍）。

**🧊 三个类比**
- **滚动**：**换轮胎时一个一个换**，始终有轮胎在地上。
- **蓝绿**：**准备两套一模一样的房子**，装修好新房，全家人一次搬过去；不满意再搬回来。
- **金丝雀**：**矿工带金丝雀下井** —— 先放一只鸟进去，鸟没事人才进去。**先试一点点**。

## ⚠️ 丢分点

1. ❌ **三大模式混用**：记住 —— **绞杀者 = 从外拦截流量**；**防腐层 = 隔离数据模型**；**抽象分支 = 从内替换组件**。
2. ❌ **数据迁移三阶段顺序写错** → 必须是 **双写 → 对账 → 切读**。（先写、再验、最后切）
3. ❌ **切读阶段忘记"再停旧写"** → 完整表述是"**切读 → 停旧写**"，漏了最后一步不闭环。
4. ❌ 发布策略只答"用灰度"不说明理由 → 必须答"**风险最低、可早发现问题、配合 K8s+Mesh 流量切分**"。
5. ❌ **蓝绿 vs 红黑** 分不清 → 二者同族，**红黑更强调"旧环境在切换后立即下线回收"**（更省资源一点），蓝绿是"两套环境长期并存"。答题时写"同族，红黑切换后旧环境即可释放"即可。

### 🔥 云原生架构图"万能骨架"（**填图题直接套**）

```
用户/移动端
   ↓
[ CDN ]                         ← 静态资源、边缘缓存
   ↓
[ Nginx 反向代理 / SLB 负载均衡 ]  ← 南北流量接入
   ↓
[ API 网关 Gateway ]             ← 认证、限流、路由、灰度
   ↓
[ 注册中心 Nacos ]  ← 服务注册与发现（旁路）
   ↓
[ Sidecar 代理（Envoy）]         ← Service Mesh，东西流量治理 + mTLS
   ↓
[ 微服务集群 ]（订单/库存/支付…，各自独立库）
   ↓
[ Redis 缓存 ]  [ MQ 消息队列 ]
   ↓

```

### 迁移三方案对比（**高频**）

| 方案 | 风险 | 成本 | 业务连续性 | 结论 |
|------|------|------|-----------|------|
| **一刀切（整体重写上线）** | **高** | 高 | **差** | 不推荐 |
| **渐进式（绞杀者）** | **低** | 中 | **好** | ✅ **默认推荐** |
| **重写式（完全重做）** | 高 | **最高** | 差 | 仅当遗留系统无法维护时考虑 |

> 💬 **话术**：从**风险、成本、业务连续性**三个维度对比，**推荐渐进式（绞杀者模式）** —— 逐步拦截流量、新老并存、每一步可回退，业务不中断。

## 📝 模拟题一：传统电商系统微服务改造

**【背景】**
某电商公司成立 8 年，核心系统为**单体架构**，所有功能（用户、商品、订单、库存、支付、物流）打包在一个 WAR 包中部署在 5 台服务器上，共用**一个 Oracle 数据库**。随着业务增长，出现以下问题：
- 改一行商品文案需要**整站重新发布**，发布窗口只能在凌晨 2 点；
- 大促期间**商品详情页访问量大**，但为了扩容只能整站复制，成本高；
- 一次支付模块的 Bug 导致**整个网站不可用** 2 小时。

公司决定进行微服务改造。

**【问题 1】（8 分）**
请指出该单体系统存在的主要问题，并说明微服务架构的哪些特征可以解决这些问题。

**【问题 2】（9 分）**
请给出该系统的微服务拆分方案，说明拆分依据与实施步骤。

**【问题 3】（8 分）**
改造后，订单创建需要同时扣减库存并调用支付，请设计分布式事务方案并说明理由。

---

### ✅ 参考答案

**【问题 1】**
**存在问题**：
① **耦合严重**，任何修改都需**整站重新发布**，发布效率低、风险高；
② **无法按需伸缩**，只能整站复制扩容，资源浪费；
③ **无故障隔离**，单个模块故障导致**整个系统不可用**；
④ **共享单一数据库**，模块间通过数据库紧耦合，无法独立演化；
⑤ 团队在**同一代码库**上协作，冲突频繁，难以并行开发。

**微服务特征的对应解决**：
① **单一职责 + 独立部署** → 商品服务可单独修改发布，不影响其他服务，发布时间窗口不再受限；
② **独立部署 + 弹性伸缩** → 仅对商品服务（详情页读多）扩容，按需分配资源；
③ **故障隔离** → 支付服务故障只影响支付链路，下单、浏览不受影响；
④ **去中心化数据管理（一服务一库）** → 解除数据库层面的耦合；
⑤ **去中心化治理** → 各团队自治，技术栈可选，并行开发。

> ⚠️ **易漏**：第 ④ 条"共享单一数据库"是**最容易被忽略的问题**，也是微服务改造的**核心难点**。

**【问题 2】**
**拆分依据 —— DDD 领域驱动**：
① 识别**领域与子域**：核心域（订单、支付、库存）、支撑域（商品、物流）、通用域（用户、权限）；
② 以**限界上下文**为微服务边界，划分为：**用户服务、商品服务、订单服务、库存服务、支付服务、物流服务**；每个服务**包含自身的接口层、业务逻辑层与数据访问层，全闭环**；以**聚合根**为一致性边界；
③ **避免按技术层拆分**（否则形成"分布式单体"）；粒度适中，避免"纳米服务"；避免循环依赖，服务间通过**领域事件**异步协作。

**实施步骤（七步）**：
① 需求分析与业务域识别；
② 基于 **DDD 限界上下文**划分服务边界；
③ 搭建基础设施：**注册中心（Nacos）、配置中心、API 网关**；
④ **数据库拆分**，每个服务独立库；采用**数据迁移三阶段：双写 → 对账 → 切读（再停旧写）**，保证零数据丢失与业务不停机；
⑤ **增量迁移**，采用**绞杀者模式**，新功能优先在微服务中实现，逐步拦截单体流量；与遗留系统交互处设置**防腐层（ACL）**隔离脏模型；
⑥ 建设**服务治理**体系：熔断降级限流 + 监控告警 + 链路追踪；
⑦ **容器化**（Docker）与 **K8s 编排**，建设 **CI/CD 流水线**。

**【问题 3】**
**选型判断**：订单创建属**长流程、跨多服务**的业务，且对吞吐要求高，**不适合 2PC（同步阻塞、性能差）**；建议采用**最终一致性（AP）**方案。

**方案**：**编排式 Saga + 事务消息 + 对账补偿**
① 采用**编排式 Saga**：引入 **Saga 协调器（状态机）** 统一编排"创建订单 → 扣减库存 → 发起支付"流程，**状态可见、补偿顺序可控、可强制幂等**，便于排障与对账；任一步失败则协调器**逆序调用补偿动作**（释放库存、取消订单）；
② 订单服务本地事务与消息发送采用 **RocketMQ 事务消息**（或**本地消息表**）保证**原子性**；
③ **消息可靠性**：生产者 **confirm** + 消息**持久化** + 消费者**手动 ACK**，保证不丢失；
④ **幂等**：以**订单号 + 操作类型**为唯一键，通过**去重表/Redis SETNX** 消费前查重，避免重复扣减；
⑤ **顺序性**：以**订单 ID 路由到同一分区**，单分区内 FIFO；
⑥ **兜底**：建设**定时对账任务**比对订单、库存、支付三方数据，不一致则自动补偿或告警人工介入。

> ⚠️ **易漏**：只写"用 Saga"不写"**编排式**"、不写"**补偿**"和"**幂等**"，最多只能拿一半分。

## 📝 模拟题二：云原生迁移与稳定性治理

**【背景】**
某在线教育公司将系统迁移到 K8s 后，出现以下现象：
- 现象 1：某 Java 服务启动需要 3 分钟，**发布后反复重启，始终无法启动**；
- 现象 2：大促期间，一个推荐服务响应变慢，随后**订单、支付服务相继不可用**，整个系统瘫痪；
- 现象 3：用户经常**被莫名登出**，尤其是在服务扩容之后；
- 现象 4：测试环境经常被别人的测试数据**污染**，排查困难。

**【问题 1】（6 分）**
针对现象 1，分析原因并给出解决方案。

**【问题 2】（7 分）**
针对现象 2，说明故障产生的原因（雪崩），并给出完整的治理对策。

**【问题 3】（6 分）**
针对现象 3 和现象 4，分别分析原因并给出解决方案。

**【问题 4】（6 分）**
该公司计划引入 Service Mesh。请说明 Service Mesh 的两大平面及其职责，并说明引入后是否可以取消 API 网关。

---

### ✅ 参考答案

**【问题 1】**
**原因**：**liveness 存活探针**的超时时间/失败阈值设置过短。该服务**启动需 3 分钟**，在未完成初始化时探针检测失败，**kubelet 判定容器不健康并重启**，重启后仍未就绪再次失败，形成**重启死循环**。

**解决方案**：
① 配置 **startupProbe（启动探针）**，设置 `failureThreshold × periodSeconds` **覆盖最长启动时间（>3 分钟）**；启动成功前 **liveness 不生效**，启动成功后交由 liveness 接管；
② 正确**区分 readiness 与 liveness**：**readiness** 用于启动期和临时不可用时**从 Service 后端摘除流量（不重启）**；**liveness** 用于运行期检测死锁等故障并**重启 Pod**；
③ 同时**优化应用启动速度**（懒加载、减少启动期同步阻塞），从根本缩短启动时间。

**【问题 2】**
**原因（雪崩）**：推荐服务响应变慢后，调用它的上游服务**线程/连接被长时间占用无法释放**；请求持续堆积导致**线程池/连接池耗尽**；故障沿调用链**向上游蔓延**，最终订单、支付等核心服务资源耗尽而不可用，形成**服务雪崩**。

**治理对策**：
① **入口限流**：API 网关配置**令牌桶限流**（允许桶容量内的合理突发），按 IP/用户/接口维度限制 QPS；
② **熔断**：引入 **Sentinel/Hystrix**，当下游**失败率或慢调用比例达阈值**（如失败率 >50%）自动熔断，**快速失败**，避免资源耗尽；
③ **降级**：为核心链路配置**兜底策略**，非核心的推荐服务可**直接降级返回默认推荐或空结果**，保障下单、支付核心链路；
④ **超时与重试**：设置合理超时时间；限制重试次数并采用**退避策略**，避免重试放大流量；重试必须配合**幂等**；
⑤ **资源隔离**：采用**线程池/信号量隔离**，将故障限制在单个依赖内；
⑥ **异步解耦**：引入**消息队列削峰填谷**，将非关键的同步调用改为异步；
⑦ **弹性与可观测**：配置 **HPA** 基于 CPU/QPS 自动扩容；建设**日志、指标、链路追踪三支柱**，设置 **SLO 告警**，早发现早止损。

**【问题 3】**
**现象 3（莫名登出）**：
- **原因**：**Session 存储在应用实例本地（有状态）**，扩容后新实例没有用户的 Session，或负载均衡将请求分发到不含该 Session 的实例，导致认证失败被登出。这**违反了云原生"无状态"原则（12‑Factor 第 6 条）**。
- **解决**：**Session 外置到 Redis** 实现**会话共享**；应用改造为**完全无状态**，本地不保存任何会话与业务数据；**禁止使用会话绑定（Session Sticky）**（实例故障会导致用户掉线且无法弹性伸缩）。

**现象 4（测试数据污染）**：
- **原因**：多团队/多分支**共用同一个测试环境的命名空间与数据库**，彼此数据互相干扰。
- **解决**：利用 **K8s Namespace** 做**环境/租户隔离**，为每个 PR 或每个特性分支创建**独立 Namespace 及独立的数据库实例/ Schema**，用完即销毁；结合 CI/CD 实现**按需创建、自动回收**的短生命周期环境。

**【问题 4】**
**两大平面**：
① **数据平面**：由 **Sidecar 代理（Envoy）** 组成，**拦截服务之间的流量**，处理限流、熔断、**mTLS 加密**、链路追踪；
② **控制平面**（Istio Pilot）：**统一管理和下发治理规则**，业务代码**零修改**。

**是否能取消 API 网关：不能。**
理由：**API 网关管南北流量**（客户端 → 后端服务），负责**对外统一入口、认证鉴权、限流、路由、灰度**；**Service Mesh 管东西流量**（服务与服务之间），负责内部服务间调用的非侵入治理（熔断、mTLS、链路追踪）。二者**南北 + 东西互补**，常**协同部署**（网关作入口 + Mesh 做内部治理），Mesh **不能替代**网关。

## 📝 模拟题三：跨单元转账与容灾（2025 真题型）

**【背景】**
某银行计划在两地三中心环境下建设**跨单元转账系统**，要求：
- 转账需跨越"账户所在单元 A"与"账户所在单元 B"；
- 任何故障下**数据不能丢失**（关键诉求）；
- 故障后 **15 分钟内恢复服务**；
- 项目要求**自主可控**。

**【问题 1】（6 分）**
请解释 RPO 与 RTO 的含义，并说明本系统的指标应如何设定。

**【问题 2】（10 分）**
请为该跨单元转账设计分布式事务方案。说明采用 Saga 的哪种实现模式、为什么，并说明如何保证数据不丢失。

**【问题 3】（9 分）**
请给出该系统的容灾设计方案，并说明在架构选型中如何满足"自主可控"要求。

---

### ✅ 参考答案

**【问题 1】**
- **RPO（Recovery Point Objective，恢复点目标）**：故障发生时**允许丢失的数据量**（以时间度量）。本系统为金融核心，**应设定 RPO = 0**（或 RPO≈0），即**不允许任何数据丢失**，需采用**同步复制**。
- **RTO（Recovery Time Objective，恢复时间目标）**：故障发生后**允许的业务中断时长**。本系统按题目要求设定为 **RTO < 15 分钟**，需依靠**自动故障检测与切换**（探针/心跳 + 自动切换/自动恢复）实现。

**实现手段**：
- **RPO=0**：采用**同步复制**（如 MySQL Group Replication / 单元间强同步），并坚持"**事件表与业务表在同一个本地事务中提交**"—— 这是 RPO=0 的**根本保证**，而**不是依赖 MQ 的可靠性**；
- **RTO<15min**：**检测**（探针/心跳）→ **隔离**（熔断/驱逐故障节点）→ **恢复**（自动故障转移 / 滚动更新 / 回滚），全流程自动化。

**【问题 2】**
**采用：编排式（Orchestration）Saga。**

**理由**：
① 跨单元转账**步骤多、涉及跨单元调用、需要严格补偿**（扣款、入账、冲正），属于**复杂长流程**；
② **编排式**由**中央 Saga 协调器（状态机）** 主动发命令、集中控制流程，具备**状态可见、补偿顺序可控、可强制幂等、易监控**的优势，便于**排障与对账**；
③ 若采用**协作式**（事件驱动、无中心协调器），会出现**流程分散、状态不可见、补偿顺序难控**的问题，不适合金融资金的严谨要求；
④ 协调器需**高可用部署**（多副本 + 选主），避免成为单点。

**保证数据不丢失（RPO=0）的关键措施**：
① **事件表与业务表在同一个本地事务中提交** —— 业务数据落库的同时，待处理的事件/消息也落库，**保证业务成功则事件一定存在**，这是 RPO=0 的根本保证；
② **不依赖 MQ 的可靠性作为唯一保障**：MQ 只作为**异步通知与解耦**手段；即使 MQ 不可用，仍可**基于事件表扫描重投**；
③ 消息侧仍配置**生产者 confirm + 持久化 + 消费者手动 ACK**；
④ **幂等**：以**转账流水号**为唯一键，通过**去重表/Redis SETNX** 消费前查重，确保重复消息不会重复入账；
⑤ **顺序性**：以**转账流水号/账户号路由到同一分区**，单分区 FIFO；
⑥ **对账兜底**：定时任务对账单元 A 与单元 B 的账务，发现不一致自动冲正补偿或告警人工介入。

> ⚠️ **易漏**：不写"**事件表与业务表同事务提交**"这条，本题至少丢 3 分 —— 这是该题的**隐藏踩分点**。

**【问题 3】**
**容灾设计方案（三阶段）**：
① **检测**：K8s **liveness/readiness 探针** + 服务**心跳** + 多维度监控告警（指标/日志/链路），秒级发现故障；
② **隔离**：**熔断**故障依赖、**驱逐**异常 Pod、将故障单元**摘除流量**（readiness 失败自动摘除）；
③ **恢复**：**HPA 自动扩容**补充容量、**滚动更新/一键回滚**恢复版本、单元间**自动故障转移**；平时开展**容灾演练**与**切换预案**验证。
④ **数据**：**同步复制**保障 RPO=0；定期**备份与恢复演练**；**两地三中心**部署，同城双活 + 异地灾备。
⑤ **发布**：采用**金丝雀/灰度发布**，配合 K8s + Mesh 流量切分，降低变更引入故障的风险。

**自主可控（信创）选型**：
① **数据库**：采用**国产数据库达梦 DM / 人大金仓 Kingbase** 替代 Oracle/MySQL；
② **中间件**：采用**东方通 TongWeb / 宝兰德 BES** 替代 Tomcat/WebLogic；
③ **国密算法**：**SM2**（**非对称加密与数字签名**，用于**网关认证、签名验签**）、**SM3**（**摘要/完整性校验**，用于报文防篡改）、**SM4**（**对称加密**，用于**敏感字段存储加密**）；
④ **服务器与操作系统**：采用国产 CPU（鲲鹏/飞腾）与国产 OS（麒麟/统信）；
⑤ 整体满足**等保与金融行业合规**要求。

> 💬 **话术模板**："若项目有**自主可控**要求，XX 组件可选用国产 **YY** 替代，并采用**国密 SMx 算法**保障安全合规。"

# 20. 一页纸速查清单

> **考前最后一眼，只看这一屏。**

```
【一句话定位】
K8s 管生死扩缩容（资源层） / Service Mesh 管调用与可靠（通信层） / DevOps 管快上快回滚（交付层）

【方向】南北 = 外部进来（网关）；东西 = 服务之间（Mesh / ESB）

【微服务六大特征】单一职责 · 独立部署 · 去中心化治理 · 去中心化数据(一服务一库) · 轻量通信 · 面向失败

【SOA vs 微服务】集成 vs 拆分；重ESB(智能管道) vs 哑管道；粗粒度 vs 细粒度；共享库 vs 独立库；集中治理 vs 去中心

【治理五件套】注册中心 + 配置中心 + 熔断降级限流 + 链路追踪 + 监控告警
【容错四件套】熔断(断开) / 降级(兜底) / 限流(限速率) / 超时重试(配幂等)
【可观测三支柱】Metrics(数值) + Logging(事件) + Tracing(链路)

【限流三算法】计数器(粗粒度/临界翻倍) | 漏桶(出水恒定) | 令牌桶(可突发/网关默认)

【CAP】P 必须满足 → 分区发生时选 C 还是 A → 金融 CP(ZooKeeper) / 互联网 AP(Eureka)
【BASE】基本可用 + 软状态 + 最终一致

【分布式事务六方案】2PC(强一致/低并发) | TCC(Try-Confirm-Cancel/侵入高) | Saga(长流程/微服务最常用)
                    | 本地消息表 | 事务消息(RocketMQ) | Seata(一站式)
【Saga 两种】编排式 = 协调器状态机(复杂长流程/推荐) | 协作式 = 事件驱动(简单短流程)

【MQ 三问】丢失 → confirm+持久化+手动ACK | 重复 → 幂等(唯一键去重表) | 乱序 → 同键同分区

【K8s】Pod(最小单元) | Deployment(无状态) | StatefulSet(有状态) | DaemonSet(每节点一个)
       Service(统一入口) | Ingress(七层路由) | ConfigMap/Secret(配置/密钥)
       HPA(加实例) vs VPA(加规格)
【探针】liveness 失败→重启 | readiness 失败→摘流量不重启 | startup 保护慢启动

【云原生】四支柱：微服务 + 容器 + DevOps + 持续交付
【四原则】服务化 · 弹性 · 可观测 · 自动化
【七原则】口诀：服弹可观韧，自动零演进
【12要素高频】配置外置 · 无状态 · 日志事件流 · 构建发布运行分离 · 快速启动优雅关闭
【RPO/RTO】RPO = 丢多少(金融≈0) | RTO = 停多久

【发布四策略】滚动(省资源/版本共存) | 蓝绿(双份资源/秒级回滚) | 金丝雀(风险最低/首选) | 红黑(同蓝绿族)
【遗留三模式】绞杀者(拦流量) | 防腐层(隔离模型) | 抽象分支(内部替换)
【数据迁移】双写 → 对账 → 切读(再停旧写)

【DDD】微服务边界 ≈ 限界上下文；聚合根 = 一致性边界；防腐层隔离脏模型

【容灾三阶段】检测(探针/心跳) → 隔离(熔断/驱逐) → 恢复(HPA/滚动更新/回滚)

【Serverless】优点：零运维/按量/自动弹性；缺点：冷启动/运行时受限；不适长连接

【安全】零信任(永不信任始终验证) + mTLS(双向证书) + RBAC/ABAC + OPA + 网关入口防护

【信创】达梦/人大金仓(库) + 东方通TongWeb/宝兰德BES(中间件) + SM2签名·SM3摘要·SM4对称

【架构图骨架】用户 → CDN → Nginx/SLB → API网关 → 注册中心(旁路) → Sidecar → 微服务(独立库)
              → Redis/MQ → 数据库 → 三支柱可观测
```
