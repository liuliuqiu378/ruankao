# 第 0 章 开考之前：先搞清楚这 25 分是怎么拿的

## 0.1 先建立直觉：案例分析不是写作文，是"按点给分"

**先破除一个误解**：案例分析不是写作文，它更像**填空 + 简答**。

- 阅卷老师手里有一张**评分要点表**（每个要点 1~2 分），他拿着你的答案在**找关键词**；
- 找到关键词就给分，找不到就不给；**写得多不加分，写得乱反而找不到**；
- 所以案例答题第一法则：**分条写、每条一个要点、把专业名词写在句首**。

> ❌ 错误示范：系统现在很慢，我觉得可能是因为数据太多了，然后查询又要关联好几张表，所以可以考虑加一些缓存……
>
> ✅ 正确示范：
> 1. **反规范化**：在订单表中冗余客户名称字段，减少订单表与客户表的多表连接，降低查询开销。
> 2. **建立索引**：在订单表的查询条件字段（用户 ID、创建时间）上建立联合索引，避免全表扫描。
> 3. **代价**：上述方案带来数据冗余与不一致风险，需通过事务同步或消息队列维护一致性。

**一句话口诀：一条一分，宁可多写三条不同角度的，也不要把一条写三段。**

## 0.4 万能答题五段式（任何技术方案题都能套）

只要题目问"请给出方案/分析/改进建议"，就按这 5 步写，**保证不漏点**：

```
① 问题定位：题干中的"XXX 慢/不一致/压力大"，本质是 XXX 问题
② 方案选择：建议采用 XXX（必须写出专有名词，如 水平分片 / Cache Aside / Saga）
③ 收益：2~4 条
④ 代价/风险：2~4 条            ← 新手最容易漏，也是区分度所在
⑤ 权衡结论 / 适用场景：1 句收尾
```

> ⚠️ **最大的丢分点：只写收益不写代价。**
> 案例题的评分要点几乎都是"收益 X 分 + 代价 X 分"，只写收益最多拿一半。
> **看到"分析""评价""说明"这类词，就必须写两面。**

# 第 1 章 数据库设计基本功：E‑R 图 → 关系模式 → 范式

> 这是**类型①专属考点**，也是整个数据库方向**最稳、最不该丢的分**。
> 理由：有标准答案、不需要工程经验、纯记忆 + 套规则。冲刺阶段必须保证这块拿满。

## 1.1 先建立直觉：设计数据库 = 整理一个乱糟糟的 Excel

想象你接手了一张"什么都往里塞"的超级大表：

| 订单号 | 下单日期 | 客户名 | 客户电话 | 商品名 | 商品单价 | 数量 |
| --- | --- | --- | --- | --- | --- | --- |
| 001 | 5.1 | 张三 | 1380000 | 键盘 | 199 | 1 |
| 002 | 5.1 | 张三 | 1380000 | 鼠标 | 99 | 2 |
| 003 | 5.2 | 李四 | 1390000 | 键盘 | 199 | 1 |

你会发现三个很别扭的地方：

1. **重复**：张三的信息写了两遍，键盘单价写了两遍 → 浪费空间；
2. **改起来烦**：张三换手机号要改 2 行，漏改一行就"数据打架" → **修改异常**；
3. **删不起**：003 是唯一一条"李四"的记录，删掉订单，李四这个人也消失了 → **删除异常**；
   反过来，新客户还没下单，你没法把他的信息录进去（没有订单号做主键）→ **插入异常**。

**范式（Normalization）干的事就是：把这张大表拆成几张干净的小表，消除上面的问题。**
而"**怎么拆**"，依据是**函数依赖**（谁决定谁）。

> **一句话直觉：范式 = 拆表的规矩；拆表的依据 = 谁决定谁。**

## 1.2 再讲原理（一）：数据库设计的六个阶段

**顺序必须背下来**（几乎每年都有一小问直接考"各阶段及成果物"）：

```
需求分析 → 概念结构设计 → 逻辑结构设计 → 物理结构设计 → 数据库实施 → 运行维护
```

| 阶段 | 干什么 | 产出物（背！） | 记忆 |
| --- | --- | --- | --- |
| 需求分析 | 收集要存什么、查什么 | **数据字典**、数据流图、业务规则 | 要什么 |
| 概念结构设计 | 抽象实体和关系，与具体数据库无关 | **E‑R 图** | 画什么 |
| 逻辑结构设计 | E‑R 图 → 关系模式，做**规范化** | 关系模式、主键、外键、范式分析 | 转成表 |
| 物理结构设计 | 考虑性能，**可以牺牲范式** | 索引、分区、**反规范化**、存储结构 | 怎么存得快 |
| 数据库实施 | 建库建表、数据迁移、测试 | — | 建起来 |
| 运行维护 | 备份、恢复、调优、安全管理 | — | 养起来 |

> 💡 **核心分界线（高频考）**：
> **逻辑设计**追求"少冗余、高范式"；**物理设计**追求"查得快、可以反范式"。
> 题目问"某某优化属于哪个阶段" → 建索引 / 反规范化 / 分片 / 读写分离 = **物理设计阶段**。

**数据字典**包括 5 项（背）：**数据项、数据结构、数据流、数据存储、处理过程**。

## 1.3 再讲原理（二）：E‑R 图三要素

| 要素 | 图形 | 含义 | 例子 |
| --- | --- | --- | --- |
| 实体 | 矩形 | 客观存在、可相互区分的事物 | 学生、课程、订单、商品 |
| 属性 | 椭圆 | 实体的特征 | 学号、姓名、单价 |
| 联系 | 菱形 | 实体之间的关联 | 学生"选课"课程 |

**联系的三种基数（考点核心）**：

| 联系 | 生活例子 | 口诀 |
| --- | --- | --- |
| 1:1 | 一个部门 ↔ 一个部门经理 | 两边都是"一" |
| 1:N | 一个部门 ↔ 多名员工；一个客户 ↔ 多笔订单 | 一边"一"，一边"多" |
| M:N | 学生 ↔ 课程；订单 ↔ 商品 | 两边都是"多" |

### E‑R 图 → 关系模式的转换规则（**必背，每年必考**）

| 情况 | 规则 | 例子 |
| --- | --- | --- |
| **实体** | 每个实体转一张表，实体属性 = 字段，实体主键 = 表主键 | 学生(**学号**, 姓名, 年龄) |
| **1:1 联系** | ① 建独立表；或 ② **并入任意一端**（对方主键当外键） | 管理(**职工号**, 部门号) 或 部门(部门号,…,经理职工号) |
| **1:N 联系** | **在 N 端（多的一方）加 1 端主键作外键** | 员工(**员工号**, 姓名, 部门号) |
| **M:N 联系** | **必须单独建表**；主键 = 两端主键**组合**；联系的属性一并纳入 | 选课(**学号, 课程号**, 成绩) |
| **多元联系（≥3 个实体）** | 也建独立表，主键为各端主键组合 | 供应(**供应商号, 零件号, 项目号**, 数量) |

> **记忆口诀：1:1 随便并，1:N 并在多，M:N 必须拆成表。**
> （"并在多"的直觉：一个员工只有一个部门号，但一个部门有很多员工，不可能在部门表里塞一列员工列表。）

## 1.4 例题：E‑R 图转关系模式（手把手）

**题干**：某图书商城，实体有
- 出版社：出版社编号、名称、地址、联系电话
- 图书：图书编号、书名、作者、单价
- 读者：读者编号、姓名、手机号

业务规则：
1. 一个出版社可以出版多本图书，一本图书只由一个出版社出版；
2. 一位读者可以订购多本图书，一本图书可被多位读者订购；订购需记录**订购数量**和**订购日期**。

**要求**：转换为关系模式，指出主键和外键。

**第 1 步：数实体 → 3 张表**

**第 2 步：判断联系基数**
- 出版社 ↔ 图书 = **1:N** → 外键放"多"端，即放**图书**表
- 读者 ↔ 图书 = **M:N** → **必须独立建表**，且"数量""日期"是联系的属性，放进这张表

**第 3 步：写关系模式（标准格式：表名(属性)，标注主键/外键）**

```
出版社(出版社编号, 名称, 地址, 联系电话)
    主键：出版社编号

图书(图书编号, 书名, 作者, 单价, 出版社编号)
    主键：图书编号
    外键：出版社编号 → 参照 出版社(出版社编号)

读者(读者编号, 姓名, 手机号)
    主键：读者编号

订购(读者编号, 图书编号, 订购数量, 订购日期)
    主键：(读者编号, 图书编号)      ← 组合主键
    外键：读者编号 → 参照 读者(读者编号)
          图书编号 → 参照 图书(图书编号)
```

> ✅ **得分点**：① 4 张表（M:N 单独一张）② 每张表主键 ③ 外键及参照关系 ④ 联系属性纳入订购表。
> ❌ **常见丢分**：把"订购数量/日期"塞进图书表；M:N 没独立建表；只写外键不写"参照哪张表"。

## 1.5 再讲原理（三）：函数依赖与候选键（范式的"语法"）

讲范式前必须先会这套"语言"。**全部用一张表讲清楚**：

R(**学号**, **课程号**, 姓名, 所在学院, 学院地址, 课程名, 成绩)

| 概念 | 定义 | 本表例子 |
| --- | --- | --- |
| **函数依赖 X→Y** | X 的值能唯一确定 Y 的值 | 学号→姓名；课程号→课程名 |
| **完全函数依赖** | Y 依赖整个 X，不依赖 X 的任一真子集 | (学号,课程号)→**成绩** |
| **部分函数依赖** | 复合候选键中，Y 只依赖其中一部分 | (学号,课程号)→**姓名**（只要学号就够）⚠️ 违反 2NF |
| **传递函数依赖** | X→Y，Y→Z，且 Y 不→X，则 X→Z 是传递依赖 | 学号→所在学院→**学院地址** ⚠️ 违反 3NF |
| **候选键** | 能唯一标识一行、且**再删一个属性就不唯一**的最小属性集 | (学号, 课程号) |
| **主键** | 从多个候选键中**选一个** | 选 (学号, 课程号) |
| **主属性** | 出现在**任一候选键中**的属性 | 学号、课程号 |
| **非主属性** | 不在任何候选键里的属性 | 姓名、所在学院、学院地址、课程名、成绩 |

> ⚠️ **丢分点 1：考试一律写"候选键"，不要只写"主键"。**
> 一张表可能有多个候选键（学号、身份证号都能唯一标识学生），判范式要看全部候选键，只写"主键"容易漏。
>
> ⚠️ **丢分点 2：主属性 ≠ 主键包含的属性。**
> 主属性 = **任一候选键**包含的属性。若"身份证号"也是候选键，它也是主属性——尽管它不是主键。

## 1.6 再讲原理（四）：四个范式，一层层加码

| 范式 | 一句话要求 | 判定方法 |
| --- | --- | --- |
| **1NF** | 字段不可再分（原子值） | 有没有"电话1、电话2"这种重复列，或"地址"里塞了省市区 |
| **2NF** | 在 1NF 上，**非主属性不能部分依赖候选键** | **只看复合候选键**；候选键是单字段 → 天然满足 2NF |
| **3NF** | 在 2NF 上，**非主属性不能传递依赖候选键** | 找 A→B→C 的链条 |
| **BCNF** | 在 3NF 上，**主属性也不能部分/传递依赖候选键** | 判定：**每个决定因素（箭头左边）都必须是候选键** |

> 💡 **BCNF 的最快判定法（考场秒杀）**：
> 列出题目的函数依赖集，**只要存在某个依赖 X→Y 中的 X 不是候选键，就不满足 BCNF**。

## 1.7 例题：判断范式等级（高频问法）

**题干**：R(学号, 姓名, 所在学院, 学院地址, 课程号, 课程名, 成绩)，函数依赖集

```
F = { 学号→姓名, 学号→所在学院, 所在学院→学院地址,
      课程号→课程名, (学号,课程号)→成绩 }
```

**问题**：R 最高属于第几范式？说明理由。若不属于 3NF，请分解至 3NF。

**第 1 问作答（套模板）**：

> **求候选键**：(学号, 课程号) 能唯一确定所有属性，且去掉任一属性都不能唯一确定，故候选键为 (学号, 课程号)；主属性为学号、课程号；非主属性为姓名、所在学院、学院地址、课程名、成绩。
>
> **判 1NF**：所有属性均为原子值，满足 1NF。
>
> **判 2NF**：存在**部分函数依赖**——非主属性"姓名"仅依赖于候选键的一部分"学号"（学号→姓名），"课程名"仅依赖于"课程号"。因此 R **不满足 2NF**。
>
> **结论**：R 最高属于 **1NF**。

> 📌 **写法规范**：**从低往高判，卡在哪层停在哪层**。判定为 1NF 后即可收笔，不必再写 3NF 分析（多写不扣分，但别写矛盾结论）。

**第 2 问作答（分解）**：

```
学生(学号, 姓名, 所在学院)        主键：学号
学院(所在学院, 学院地址)          主键：所在学院
课程(课程号, 课程名)              主键：课程号
选课(学号, 课程号, 成绩)          主键：(学号, 课程号)  外键：学号、课程号
```

**⚠️ 分解题的"后半分"——必须补写这两句，否则只拿一半分**：

> **无损连接性**：分解后"学生"与"学院"的公共属性为"所在学院"，且"所在学院"是"学院"关系的候选键；"选课"与"学生"的公共属性为"学号"，且"学号"是"学生"关系的候选键。因此该分解具有**无损连接性**，通过自然连接可还原原关系，不丢失也不增加信息。
>
> **函数依赖保持**：原依赖集 F 中的每条依赖均可在**某一个子关系内部**单独保持，无需跨表连接即可验证，因此该分解**保持了函数依赖**。

> 🔥 **这是全章最大的丢分点**：
> 很多考生写完 4 张表就收笔，但评分表里明确有"说明无损连接性""说明函数依赖保持"各 1~2 分。
> **做完分解题，无脑追加这两句话，属于白捡的分。**

**两个判定定理（写答案时直接用）**：
- **无损连接判定**：R 分解为 R1、R2，若「R1 ∩ R2」是 R1 或 R2 的**候选键（超码）**，则分解无损。
- **依赖保持**：所有原依赖都能在单个子关系中找到。
- **规律**：分解到 **3NF 通常既能无损又能保持依赖**；分解到 **BCNF 不保证保持依赖**（所以题目问"分解为 BCNF 并保持依赖"时要说明"不一定能做到"）。

## 1.8 BCNF 例题（拉开差距的小问）

**题干**：R(学生, 教师, 课程)，语义：一位教师只教一门课程；一门课程可由多位教师讲授；每个学生选定某门课后对应一位教师。
函数依赖：教师→课程，(学生, 课程)→教师。

**解析**：

- **求候选键**：(学生, 教师) 可确定课程（教师→课程），故是候选键；(学生, 课程) 可确定教师，故也是候选键。
- **主属性**：学生、教师、课程（**三个都是主属性**）→ **没有非主属性**。
- **判 3NF**：无非主属性，自然不存在"非主属性部分/传递依赖"，**满足 3NF**。
- **判 BCNF**：存在依赖 **教师→课程**，但"教师"不是候选键 → **不满足 BCNF**。
- **分解**：R1(**教师**, 课程)、R2(学生, **教师**) —— 满足 BCNF。

> ⚠️ **丢分点**：看到"没有非主属性"就写"满足 BCNF"。**BCNF 管的是主属性**，这是它与 3NF 的唯一区别，也是命题人最爱挖的坑。

## 1.9 本章速记卡

```
设计六阶段：需求 → 概念(E-R) → 逻辑(关系模式+范式) → 物理(索引/反范式) → 实施 → 运维
E-R 转换：1:1 随便并 | 1:N 并在多 | M:N 必拆表
范式递进：1NF 原子 → 2NF 消灭"部分" → 3NF 消灭"传递" → BCNF 主属性也不许"部分/传递"
BCNF 秒判：箭头左边不是候选键 → 不是 BCNF
分解题必写：无损连接 + 依赖保持（各 1~2 分，白送）
```

# 第 2 章 查询为什么慢：索引与 SQL 优化

## 2.1 先建立直觉：索引 = 书的目录

一本 1000 页的字典，让你找"软"字：

- **没目录**：从第 1 页翻到 1000 页 → **全表扫描（type=ALL）**；
- **有拼音目录**：查目录找到"ruan → 第 632 页"，直接翻过去 → **索引**；
- 目录本身也占几页纸 → **索引占用存储空间**；
- 每次加一个新字，目录也要改 → **索引降低写入性能**；
- 如果目录写的是"笔画数"，而同笔画的字一大堆 → 目录没用 → **区分度低的字段不宜建索引**（如"性别"）。

**索引的本质：用"额外的存储空间 + 写入时的维护成本"，换取"查询时少读磁盘"。**

## 2.2 再讲原理（一）：B+ 树、聚簇索引、回表

> **先厘清四者的"层级关系"（很多人背得滚瓜烂熟，却答不出关系）**：
> - **B+ 树 = 数据结构（载体/地基）**：它不是一种索引类型，而是索引在磁盘上的**物理形态**；
> - **聚簇索引 = 索引类型之一（正房）**：一棵 B+ 树，叶子节点装**整行数据**；
> - **二级索引 = 索引类型之二（偏房）**：也是一棵 B+ 树，叶子节点只装**索引列 + 主键**；
> - **回表 = 二者的联动动作**：二级索引查到主键 → 再回聚簇索引查一遍。
>
> 一句话：**B+ 树是地基，聚簇索引是正房（查一次就够），二级索引是偏房（查完还得回正房）。**

MySQL InnoDB 默认索引结构是 **B+ 树**，只需记三句话：

1. **真实数据全部存放在叶子节点**，非叶子节点只存导航用的键；
2. **叶子节点之间用双向指针连成链表** → 非常适合**范围查询**（找到起点后顺着链表扫）；
3. 树很"矮胖"，一般 **3~4 层可存千万级数据 → 查一次只需 3~4 次磁盘 IO**。

**两种索引（必考辨析）**：

| 类型 | 叶子节点存什么 | 一张表几个 | 关键概念 |
| --- | --- | --- | --- |
| **聚簇索引** | **完整的一行数据** | 只能 **1 个**（InnoDB 里就是主键） | 按主键顺序物理存储 |
| **非聚簇（二级）索引** | 索引列 + **主键值** | 可多个 | 查到主键后还要回聚簇索引取全量数据 = **回表** |

**什么是回表（高频名词）**：
用"用户名"索引查到主键 id=100，但你 `SELECT *` 需要全部字段，于是数据库拿 id=100 **再跑一遍主键索引**取完整行 —— 这一趟叫**回表**，多一次 IO，是很多慢查询的元凶。

**怎么消除回表？→ 覆盖索引（必考）**

> **覆盖索引**：查询需要的**所有字段都包含在索引里**，无需回表。

```sql
-- 已有索引 idx_name_age(name, age)
SELECT age FROM user WHERE name = '张三';   -- ✅ 覆盖索引，Extra: Using index
SELECT *   FROM user WHERE name = '张三';   -- ❌ 需要回表
```

> 💡 **答题金句（万能）**：
> "虽然建立了索引，但发生了**索引失效**或**频繁回表**，查询依然缓慢，可通过**覆盖索引**（将查询字段纳入联合索引）、避免在索引列上做运算等方式优化。"

## 2.3 再讲原理（二）：索引是怎么"生出来"的（生成规则与隐式索引）

**直觉**：聚簇索引是**必修课**（强制存在、没得选），二级索引是**选修课**（你写了它才有）。

**聚簇索引的优先级（InnoDB 强制规则，背下来）**：

1. 显式定义了 `PRIMARY KEY` → **主键就是聚簇索引**；
2. 没定义主键 → 挑**第一个 `NOT NULL UNIQUE`** 的列当聚簇索引；
3. 连这个都没有 → InnoDB **偷偷生成隐藏列 `ROW_ID`** 当聚簇索引（你看不见也用不了）。

> **结论**：不管你写不写主键，聚簇索引**永远存在**——它是 InnoDB 的物理存储根基。

**二级索引的两个"隐形来源"（考试挖坑点）**：

```sql
CREATE TABLE user (
    id    INT PRIMARY KEY,
    phone VARCHAR(20) UNIQUE,          -- ✅ UNIQUE 会自动创建二级索引（哪怕没写 KEY）
    name  VARCHAR(20),                 -- ❌ 啥也没写 → 没有索引
    dept_id INT,
    FOREIGN KEY (dept_id) REFERENCES dept(id)  -- ✅ 外键也会自动创建二级索引
);
```

| 建表语句 | 结果 |
| --- | --- |
| 只写 `id INT PRIMARY KEY` | 该表**只有聚簇索引，没有二级索引** |
| 写了 `KEY idx_name (name)` | 聚簇索引（id）+ 二级索引（name）**同时存在** |
| 写了 `UNIQUE` / `FOREIGN KEY` | 会**隐式**生成二级索引（题干问"哪些字段有索引"时别忘了它们） |

> ⚠️ **高频考法**：表上只有主键，问 `SELECT * FROM user WHERE name='张三'` 会怎么执行？
> 答：**能跑，但走全表扫描**——沿着聚簇索引的叶子节点链表从第一页翻到最后一页，逐行比对 name，数据量一大就慢到不能忍。这就是"必须有二级索引"的理由。

## 2.4 再讲原理（三）：物理页级查找过程——回表到底贵在哪？

**直觉**：把硬盘想象成一页页的纸。聚簇索引的叶子页就是"数据页"，二级索引的叶子页只是"查页码的小册子"。

以 `user(id PK, name, age, KEY idx_name(name))`、10 万行数据为例，对比三条 SQL：

| 场景 | SQL | 硬盘查找路径 | 磁盘 IO |
| --- | --- | --- | --- |
| **① 聚簇索引查找** | `SELECT * FROM user WHERE id=520` | 根页 → 中间层页 → 叶子页（**数据页，直接躺着整行数据**） | 约 **3~4 次**（= 树高） |
| **② 二级索引 + 回表** | `SELECT * FROM user WHERE name='赵六'` | 二级索引树（根→中→叶，叶子只有 `('赵六', 520)`）→ **拿 520 重新走一遍聚簇索引树** | 约 **6~8 次**（两棵树高之和） |
| **③ 二级索引 + 覆盖索引** | `SELECT id, name FROM user WHERE name='赵六'` | 二级索引树（根→中→叶），叶子页里 `id`、`name` 全都有 → **直接返回** | 约 **3~4 次**（不回表） |

> **闭上眼记这张图**：硬盘磁头在"索引页"和"数据页"之间来回跳，这就是回表的物理代价。
>
> **血的教训**：只要查询条件走的是**非主键的二级索引**，且 `SELECT` 后面跟着 **`*` 或索引里没有的字段**，数据库**必然**干"回表"这件傻事。
> **优化就一句话：把 `SELECT *` 改成只查索引里的字段（覆盖索引），立刻省掉一半 IO。**

## 2.5 再讲原理（四）：联合索引与最左前缀

**直觉**：联合索引 (a, b, c) 像字典目录按"拼音 → 声调 → 笔画"排序。
你必须**先按拼音找**，才能用声调；不能跳过拼音直接用声调。**这就是最左前缀原则。**

| 查询条件 | 能否用上 (a,b,c) | 原因 |
| --- | --- | --- |
| `a=1` | ✅ a | 匹配最左 |
| `a=1 AND b=2` | ✅ a,b | — |
| `a=1 AND b=2 AND c=3` | ✅ a,b,c | — |
| `b=2` | ❌ 不能 | 跳过了最左列 a |
| `a=1 AND c=3` | ⚠️ 只能 a | b 断了，c 用不上 |
| `a=1 AND b>10 AND c=3` | ⚠️ a,b | **范围查询之后的列无法继续用索引** |

> 🔥 **丢分点：范围查询的"截断"效应。**
> `WHERE a=1 AND b>10 AND c=3`，索引 (a,b,c) 里 c **用不上**。
> 所以设计联合索引时：**等值字段在前，范围字段在后**。

**联合索引字段顺序 5 原则（背）**：
1. **等值查询字段放前面**
2. **区分度高的字段放前面**
3. **范围查询字段放后面**
4. 排序（ORDER BY）、分组（GROUP BY）字段尽量纳入
5. 尽量让索引**覆盖查询字段**，减少回表

**例题**：请为下面的高频查询设计联合索引。

```sql
SELECT order_id, amount FROM orders
WHERE user_id = ? AND status = 'PAID' AND create_time BETWEEN ? AND ?
ORDER BY create_time;
```

> **答案**：建立联合索引 `(user_id, status, create_time)`；若追求极致可再追加查询字段形成覆盖索引 `(user_id, status, create_time, order_id, amount)`。
> **理由**：user_id、status 为等值查询字段放前面；create_time 为范围字段放后面；create_time 同时是排序字段，纳入索引可避免 filesort；将 order_id、amount 纳入索引可形成覆盖索引，避免回表。

## 2.6 再讲原理（五）：索引失效的 5 种场景（高频坑）

| # | 失效场景 | 反例 | 正例 |
| --- | --- | --- | --- |
| 1 | **索引列上做函数/运算** | `WHERE YEAR(create_time)=2025` | `WHERE create_time BETWEEN '2025-01-01' AND '2025-12-31'` |
| 2 | **隐式类型转换** | `WHERE phone = 13800138000`（phone 是 varchar） | `WHERE phone = '13800138000'`（加引号） |
| 3 | **前导模糊查询** | `LIKE '%手机'` / `LIKE '%手机%'` | `LIKE '手机%'`（前缀匹配可用索引） |
| 4 | **不满足最左前缀** | 索引 (a,b,c)，`WHERE b=1` | 补上 a 的条件或新建 (b) 索引 |
| 5 | **OR 连接非索引列** | `WHERE a=1 OR d=2`（d 无索引） | 给 d 建索引或改写为 UNION ALL |

**LIKE 的严谨表述（阅卷按这个给分）**：

| 写法 | 结论 |
| --- | --- |
| `LIKE 'abc%'` | **可以**利用 B+ 树索引进行前缀匹配定位 |
| `LIKE '%abc'` / `'%abc%'` | **无法利用 B+ 树索引快速定位**，通常退化为全索引扫描或全表扫描 |

> ⚠️ 补一句"**若查询字段全部包含在索引中，仍可能通过覆盖索引扫描完成查询**"—— 写上显得严谨，是加分项。

## 2.7 再讲原理（六）：索引下推 ICP（覆盖索引的"孪生兄弟"）

**直觉（点外卖版）**：
- **覆盖索引** = 外卖小票上直接印着你要的菜谱 → **不用上楼**（不回表）；
- **索引下推（ICP）** = 快递员在楼下先看小票，把不是你要的包裹**直接扔掉**，只搬正确的上楼 → **少上几趟楼**（少回表）。

**定义**：ICP（Index Condition Pushdown，MySQL 5.6 引入）把原本由 Server 层做的**索引字段筛选**，**下推到存储引擎层**执行：在**回表之前**就用索引页里已有的字段把不满足条件的记录筛掉。

**经典例子（背下来，案例题可直接写）**：

```sql
-- 假设联合索引 (name, age)
SELECT * FROM user WHERE name LIKE '张%' AND age = 20;
-- 假设姓"张"的有 10 万条，其中 20 岁的只有 100 条
```

| 是否开启 ICP | 底层执行流程 | 回表次数 |
| --- | --- | --- |
| **关闭**（老版本） | 引擎取出所有 `name LIKE '张%'` 的索引条目（10 万条）→ 拿 10 万个 id **全部回表** → 把 10 万整行交给 Server 层 → Server 层再过滤 `age=20`，扔掉 99.9% | **10 万次**（磁盘疯了） |
| **开启**（5.6+ 默认） | 引擎找到 `name LIKE '张%'` 的索引条目 → **在索引页里顺手检查 `age` 字段**，不等于 20 的直接丢弃 → 只把符合条件的 100 个 id 回表 | **约 100 次**（飞一般） |

**覆盖索引 vs 索引下推（终极对比，默写级）**：

| 对比维度 | 覆盖索引 | 索引下推（ICP） |
| --- | --- | --- |
| 解决什么 | **省掉回表动作**（查完二级索引就结束） | **减少回表行数**（回表前先过滤掉垃圾） |
| 针对 SQL 的哪部分 | **SELECT 后的字段列表** | **WHERE 后的筛选条件** |
| 生效前提 | 查询字段**全部**落在索引内 | 联合索引 + 存在**无法精确匹配**的条件（范围列 / 前缀模糊 / 范围之后的列） |
| 作用层次 | Server 层（优化器决定不回表） | **存储引擎层**（InnoDB 提前过滤） |
| 判据口诀 | "查询列全在索引里" | "联合索引 + 范围/前缀模糊 + 等值条件" |
| EXPLAIN 标志 | `Extra: Using index` | `Extra: Using index condition` |

> **答题金句（案例分析写上去就加分）**：
> "建议将 `SELECT *` 修改为仅查询必要字段，并建立 `(name, age, ...)` 的联合索引以实现**覆盖索引**，避免回表；同时 MySQL 优化器会利用**索引下推（ICP）**在存储引擎层提前过滤 `age` 条件，从而大幅减少回表次数与磁盘 IO 开销。"

## 2.8 再讲原理（七）：EXPLAIN 执行计划

考试可能给你一段 EXPLAIN 输出让你"指出问题并优化"。**只需看 4 个字段**：

| 字段 | 含义 | 考点 |
| --- | --- | --- |
| `type` | 访问类型 | 性能从优到差：**system > const > eq_ref > ref > range > index > ALL**；**目标至少达到 range**，出现 **ALL = 全表扫描，必须优化** |
| `key` | 实际用到的索引 | 为 **NULL** 说明**没用上索引** |
| `rows` | 预估扫描行数 | 越大代价越高 |
| `Extra` | 附加信息 | `Using index` = ✅ 覆盖索引，优秀；`Using index condition` = ✅ 走索引下推 ICP（回表前已过滤，好事）；`Using filesort` = ❌ 无法用索引排序，额外排序，**必须优化**；`Using temporary` = ❌ 用了临时表，需优化 |

**口诀**：`type` 看快慢，`key` 看用没用，`rows` 看代价，`Extra` 看排序。

## 2.9 再讲原理（八）：SQL 优化通用清单

1. **禁止 `SELECT *`**，只查需要的字段（减少回表与网络传输，更易命中覆盖索引）；
2. 不在索引列上做计算/函数；
3. **深度分页**用**游标（书签）分页**替代大 offset；
4. 优先 JOIN，谨慎使用子查询（子查询可能生成临时表）；
5. `UNION ALL` 代替 `UNION`（省去去重排序开销）。

**JOIN 优化 5 条**：
- **小表驱动大表**（小结果集做外层循环）；
- JOIN 字段**建立索引**；
- JOIN 字段**类型必须一致**（否则隐式转换导致索引失效）；
- 避免过多表 JOIN（一般不超过 3 张）；
- 不在 JOIN 条件中对字段做函数运算。

**深度分页例题（几乎每年变形考）**：

```sql
-- ❌ 慢：需扫描并丢弃前 100 万行
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;

-- ✅ 快：游标/书签分页（seek method），利用主键直接定位
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 20;
```

> **答题句**：深度分页场景下 `LIMIT offset, size` 需要**扫描并丢弃大量前置记录**，性能随 offset 增大急剧下降。可基于上一页最后一条记录的主键或有序字段（游标）分页，配合索引直接定位起始位置，显著减少扫描行数。

## 2.10 考试到底会考多"细"？（基础差专用：诊断题万能模板）

**先给你吃颗定心丸**：案例题**不会**考 B+ 树的节点分裂算法、不会让你算精确 IO 次数、不会问叶子页的物理页号。

**它只会换一种更"温柔"的方式考**：给你一段慢 SQL 或一份 EXPLAIN，让你**当医生去诊断**。而这恰恰是**最好拿分**的题型——答案是高度模板化的，记住公式就能拿 70% 的分。

**案例题里索引相关的问法，翻来覆去就 3 种**：

| 问法 | 考什么 |
| --- | --- |
| "已经建了索引，为什么还是慢？" | 索引失效 / 频繁回表 / 排序无法用索引 |
| "针对这个查询，索引应该怎么建？" | 联合索引顺序（等值在前、范围在后） |
| "系统响应慢，怎么优化？" | 覆盖索引 / 改写 SQL / 反规范化 / 读写分离 / 分片 |

**慢 SQL 诊断题四步答题法（按点给分，按顺序默写）**：

```
① 定位原因（2~3 分）：该 SQL 缓慢的原因是……
   · 索引列上使用函数/运算 → 索引失效
   · 隐式类型转换（varchar 字段传数字）→ 索引失效
   · 前导 % 模糊匹配 → 无法利用 B+ 树定位
   · 违反最左前缀（跳过中间列 / 范围列之后的字段失效）
   · 区分度极低的列建索引（性别、状态标记）→ 选择性差，不如全表扫
   · SELECT * + 二级索引 → 频繁回表，随机 IO 剧增
   · 排序/分组字段未纳入索引 → Using filesort

② 给出方案（4~6 分）：建议……
   · 改写 SQL，去掉索引列上的函数（YEAR(d)=2026 → d BETWEEN '2026-01-01' AND '2026-12-31'）
   · 避免 SELECT *，只查必要字段
   · 建立覆盖索引（WHERE 条件字段 + SELECT 查询字段一并纳入）
   · 调整联合索引顺序：等值在前、区分度高在前、范围在后、排序字段纳入
   · 深度分页改为游标分页

③ 说明代价（1~2 分）：索引占用额外存储空间，并降低写入性能（每次增删改都要维护索引），
                     因此索引数量应适度控制，并非越多越好。

④ 效果总结（1 分）：可减少全表扫描与回表次数，降低磁盘 IO，提升查询响应速度。
```

**万能金句（考场实在不会编，直接默写这句）**：

> "当前查询虽然存在索引，但由于（索引列上使用函数 / 隐式类型转换 / 违反最左前缀匹配 / 范围查询阻断后续字段 / 区分度低）导致索引失效或频繁回表。建议修改查询条件，或建立覆盖索引 (xxx, xxx) 以减少回表次数与磁盘 IO 开销；同时将排序字段纳入联合索引，避免 Using filesort。"

**基础差也能拿分的最小知识集（只背这 5 个关键词）**：

| 关键词 | 答题时怎么用 |
| --- | --- |
| **回表** | 二级索引查完，还要拿主键回聚簇索引再查一遍，多一次 IO |
| **覆盖索引** | 把查询字段全建进索引，直接返回，不用回表（**最香的方案**） |
| **最左前缀** | 联合索引 (a,b,c)：查 `b=1` 用不了；查 `a=1 AND c=1` 只能用 a |
| **索引失效** | 三兄弟：**函数、隐式转换、前导 %**（外加违反最左前缀、区分度低） |
| **分片/读写分离** | 单表数据量太大（千万级）索引也救不了，得水平拆分 |

## 2.11 本章速记卡

```
B+ 树是地基：聚簇 = 正房（叶子存整行，1 个），二级 = 偏房（叶子存主键，多个）
聚簇索引强制有（主键 → 首个 NOT NULL UNIQUE → 隐藏 ROW_ID）；UNIQUE/外键会隐式建二级索引
回表：二级索引树高 + 聚簇索引树高 ≈ 6~8 次 IO（比主键查询翻倍）
索引 = 目录；B+ 树 3~4 层 → 3~4 次 IO；叶子连成链表 → 擅长范围查询
聚簇索引 = 主键，叶子存整行；二级索引叶子存主键 → 回表
覆盖索引 = 查询字段全在索引里 → Using index，不回表
ICP = 回表前在引擎层先过滤 → Using index condition，少回表
联合索引：等值在前、区分度高在前、范围在后、排序纳入、尽量覆盖
索引失效：函数运算 | 隐式转换 | 前导 % | 不满足最左前缀 | OR 非索引列
EXPLAIN：type 至少 range（ALL 全表扫）、key 别为 NULL、rows 越小越好、
         Using index / Using index condition 好；Using filesort 必须改
深度分页：游标分页 WHERE id > last_id LIMIT n
诊断题四步：找原因 → 给方案 → 说代价 → 总结效果
```

# 第 3 章 规范化与反规范化（最高频考点）

## 3.1 先建立直觉：要不要把"客户名"抄一份到订单表？

第 1 章我们花了大力气把大表拆干净（规范化）。但拆干净之后有副作用：

> 订单列表页要显示"客户名称"，而客户名在客户表里 → **每次都要 JOIN 一次**。
> 订单表 3000 万行，客户表 500 万行，每次 JOIN 都很贵。

于是架构师说：**干脆把"客户名称"直接抄一份放进订单表吧！**

- **好处**：查订单列表不用 JOIN 了，快！
- **坏处**：客户改名了，订单表里那 3000 万个"客户名称"都得跟着改，漏一个就数据打架。

**这就是反规范化（Denormalization）：故意把数据重复放，用"冗余 + 不一致风险"换"查询性能"。**

> **一句话权衡（背下来，本章的印钞机）**：
> **规范化：减少冗余、消除异常，代价是查询需多表 JOIN、性能下降；**
> **反规范化：减少 JOIN、提升查询性能，代价是数据冗余、不一致风险、更新成本上升。**

## 3.2 再讲原理：反规范化的 4 种手段（背名字，考试要写专有名词）

| 手段 | 做法 | 例子 |
| --- | --- | --- |
| **增加冗余列** | 把别表的字段直接抄进来 | 订单表加 `customer_name` |
| **增加派生列** | 存**计算好**的结果 | 订单表加 `total_amount`（各商品金额之和） |
| **合并表** | 经常一起查的多张表合成一张大表 | 用户表 + 用户详情表 → 一张宽表 |
| **拆分表（垂直拆分）** | 把**很少访问**的字段（大文本、简介）拆到另一张表 | 商品表拆出"商品详情大字段表" |

> 💡 "拆分表"既是反规范化手段，也常作为**垂直分片**的答案，两处表述在考试中**可以通用**。

## 3.3 考试怎么考：反规范化的"固定三连问"

这道题的套路极其固定：

- 【问题 1】（4 分）指出该优化手段是什么 → 答"**反规范化（增加冗余列/合并表）**"
- 【问题 2】（6 分）说明收益与代价 → "减少 JOIN 提升查询性能 / 冗余与不一致风险、更新成本上升"
- 【问题 3】（8 分）**如何保证数据一致性？** ← **这才是大头分，也是最容易空白的一问**

### 一致性维护的 6 种方案（务必背全名）

| 方案 | 做法 | 特点 |
| --- | --- | --- |
| **事务内同步更新** | 改主表时，在**同一个事务**里同步改冗余字段 | 强一致，但耦合高、事务变大 |
| **数据库触发器** | 主表变化时由触发器自动更新冗余字段 | 自动，但数据库压力大、难调试 |
| **物化视图** | 预计算并存储结果，定期/实时刷新 | 数据库原生支持，适合统计类 |
| **定时任务同步** | 定时批量刷新冗余字段 | 实现简单，但**实时性差** |
| **消息队列异步同步** | 业务完成后发消息，消费方异步更新冗余数据 | 解耦、吞吐高，最终一致 |
| **Binlog 监听同步** | 用 Canal 等监听数据库变更日志，异步更新 | 对业务**零侵入**，最终一致 |

> **答题金句（直接背）**：
> "反规范化通过增加冗余字段减少多表连接，提升查询性能；但冗余字段与源数据存在**不一致风险**，需要通过**事务内同步更新、触发器、物化视图、定时任务、消息队列异步同步或 Binlog 监听（如 Canal）**等方式维护数据一致性。"

## 3.4 例题：完整走一遍

**题干**：某电商系统的"订单查询"页面需展示订单号、下单时间、订单金额、**买家昵称**、**收货地址**，涉及订单表、用户表、地址表三张表的连接查询。订单表数据量已达 2000 万，页面响应缓慢。架构师建议在订单表中增加"买家昵称"和"收货地址"字段。

**【问题 1】**该优化手段属于什么？会带来哪些问题？（6 分）
**【问题 2】**请给出保证数据一致性的方案。（8 分）

**参考答案**：

> **【问题 1】**
> 该手段属于**反规范化**中的"**增加冗余列**"（也可表述为"适度冗余设计"）。
> **收益**：订单查询时无需再与用户表、地址表进行多表连接（JOIN），降低连接开销，提升订单列表页的查询性能。
> **代价/问题**：① **数据冗余上升**，占用更多存储空间；② 用户修改昵称或收货地址后，订单表中的冗余字段与源数据**存在不一致风险**；③ 用户更新信息时需同步更新订单表冗余字段，**写操作成本上升**，写入性能下降；④ 需要额外的**一致性维护机制**，增加系统复杂度。
> **权衡结论**：该方案以**牺牲数据一致性和增加存储冗余**为代价换取查询性能，适用于**读多写少**的订单查询场景。

> **【问题 2】一致性维护方案**
> ① **事务内同步更新**：用户修改昵称/地址时，在同一本地事务中同步更新订单表冗余字段，保证强一致，但事务范围变大、耦合度高；
> ② **消息队列异步同步**：用户服务完成信息修改后发送消息，订单服务消费消息异步更新冗余字段，实现解耦与最终一致，需保证消息可靠投递与消费幂等；
> ③ **Binlog 监听（Canal）**：监听用户表的 Binlog 变更，异步更新订单表冗余字段，对业务代码零侵入；
> ④ **物化视图/定时任务**：对实时性要求不高的字段，可采用物化视图或定时批量同步，实现简单但实时性差。
> **结论**：对实时性要求高的字段建议采用**事务内同步 + 消息队列**结合的方式；对实时性要求低的字段采用定时同步，兼顾性能与一致性。

## 3.5 丢分点清单

- ❌ **"反规范化可以提升写入性能"** → 错！它一般**提升查询性能、增加写成本**（要维护冗余）。
  （官方答案口径：主流结论是"提升查询、增加写成本与一致性风险"。极少数场景如"预计算汇总值避免实时聚合"可降低写后查询压力，但考试按主流口径写最安全。）
- ❌ 只写收益不写代价 → 直接丢一半分。
- ❌ 被追问一致性时只写"用触发器"一条 → 至少给 3~4 种方案并对比。
- ❌ 把"增加冗余字段"说成"水平分片" → 分片是**拆表**，反规范化是**加字段/合表**，方向相反。

## 3.6 三大概念辨析表（必背，几乎每年考）

| 方案 | 动什么 | 核心目的 | 副作用 |
| --- | --- | --- | --- |
| **反规范化** | 不拆表，**增加冗余字段/合并表** | 减少 JOIN，提升查询性能 | 数据冗余、不一致风险、更新成本高 |
| **垂直分片（纵向拆分）** | **按字段（列）**把一张表拆成多张 | 减少单表 IO、降低锁冲突、冷热分离 | 查完整数据需 JOIN |
| **水平分片（横向拆分）** | **按行**把数据拆到多张结构相同的表 | 降低单表行数、分散存储与压力 | 跨分片查询/事务复杂 |

> **口诀：垂直切字段，水平切记录，反范式加冗余。**

# 第 4 章 分片（水平 / 垂直）

## 4.1 先建立直觉：一本太厚的字典，拆成上中下三册

单表 5000 万行，就像一本 5000 页的字典，翻起来又厚又慢。怎么办？

- **水平分片**：按"字母"拆成 A‑G、H‑N、O‑Z 三册。**每册结构完全一样，只是内容不同** → 查哪个字母就只翻那一册。
- **垂直分片**：把每页的"拼音、释义、例句"拆成三本。**每本字段不同，但用同一个词条编号关联** → 只想查读音时，不用捧着厚厚的释义本。

## 4.2 再讲原理

### 垂直分片（纵向拆分）
- **规则**：按**字段（列）**拆；各表字段互不重复，通常**保留相同主键**以便关联。
- **例子**：用户表 → 用户基础表（账号、密码、手机号）+ 用户扩展表（头像、简介、偏好）。
- **收益**：① 减少单表宽度，查热点字段时 IO 减少；② 冷热数据分离；③ 减少锁冲突。
- **代价**：查询完整用户信息需要 JOIN。

### 水平分片（横向拆分）
- **规则**：按**行**拆；各分片表**字段结构完全相同**，数据行不同。
- **三种分片策略**：

| 策略 | 做法 | 优点 | 缺点/风险 |
| --- | --- | --- | --- |
| **范围分片** | 按 ID 或时间区间 | 范围查询快，扩容简单 | **易产生热点**（新数据全落最新分片） |
| **哈希分片** | 分片键取模/哈希 | 数据**分布均匀**，无热点 | 扩容迁移量大；范围查询要扫全部分片 |
| **列表分片** | 按枚举值（地区、租户） | 业务语义清晰，便于隔离 | 某些枚举值数据量大 → 倾斜 |

- **收益**：① 单表行数下降、索引变小，查询加快；② 可分散到**多台数据库节点**，突破单机存储与性能瓶颈；③ 提升可用性（一个分片故障只影响部分数据）。
- **代价**：① **跨分片查询**复杂；② **跨分片事务**复杂；③ 跨分片分页/排序/聚合复杂；④ 运维复杂度上升。

## 4.3 分片键怎么选（高频追问）

**分片键** = 水平分片时用来决定"这行数据放哪个分片"的字段。

**4 条原则**：
1. **取值分布均匀**，避免热点分片；
2. **绝大多数查询都携带分片键**，减少跨分片查询；
3. **与查询模式匹配**：哈希适合随机单点查询，范围适合时间类范围查询；
4. **预留扩容方案**，优先考虑一致性哈希降低迁移量。

> ⚠️ **反面案例（爱考）**：用"**日期**"做分片键 → 当天新数据全部写入最新分片，产生**写入热点**，且历史分片闲置。

## 4.4 随之而来的三个必答追问

### 追问 1：自增主键失效 → 全局唯一 ID

水平分片后，每个分片各自自增，会**生成重复 ID**。必须引入全局 ID 生成机制：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **UUID** | 本地生成，简单 | 无序（作 InnoDB 主键会频繁页分裂）、空间大 |
| **数据库号段模式** | 简单，性能好 | 依赖数据库可用性 |
| **Redis 自增** | 性能高 | 依赖 Redis 可靠性 |
| **Snowflake 雪花算法** | 趋势递增、高性能、本地生成 | 依赖机器时钟，**时钟回拨**可能重复 |
| **分布式 ID 生成服务** | 统一管理，易扩容 | 架构复杂度提高 |

> **答题句**：水平分片后，单库自增主键无法保证全局唯一，需要引入全局唯一 ID 生成机制，如**数据库号段模式、雪花算法（Snowflake）或独立的分布式 ID 生成服务**。

### 追问 2：查询条件不带分片键怎么办？

**场景**：订单按 `user_id` 分片，但客服要按 `order_id` 查单 → 不知道去哪个分片找。

| 方案 | 说明 |
| --- | --- |
| **映射表** | 建一张 `order_id → user_id` 映射表，先查映射再定位分片 |
| **异构索引表** | 按另一维度再建一份索引表 |
| **搜索引擎** | 数据同步到 Elasticsearch，复杂查询走 ES |
| **数据冗余双写** | 按不同维度各存一份 |
| **基因法** | 生成订单号时**把用户 ID 的分片因子嵌入订单号**，凭订单号也能算出分片 |

> ⚠️ **"基因法"表述要谨慎**（术语太工程化），建议写：
> "可在订单号中**嵌入用户 ID 的分片因子**，使系统根据订单号也能计算出所在分片，避免全分片扫描。"

### 追问 3：扩容怎么迁移数据？

- **预分片**：一开始就多建逻辑分片（如 1024 个），扩容只是迁移分片位置；
- **一致性哈希**：节点变化时只迁移**相邻少量数据**；
- **双写迁移**：新旧分片同时写入，历史数据后台搬迁，校验一致后切换读流量；
- **按规则重路由**：适合范围分片。

## 4.5 例题（真题变形）

**题干**：某电商订单表数据量已达 5000 万，查询缓慢。项目组决定按 `user_id` 哈希分为 8 个分片。
**【问题 1】**（6 分）水平分片的收益与代价。
**【问题 2】**（6 分）分片后会遇到哪些新问题，如何解决？

**参考答案**：

> **【问题 1】收益**：① 单表数据量从 5000 万降至每片约 625 万，索引体积减小，查询性能提升；② 数据可分布到多个数据库节点，突破单机存储与并发瓶颈；③ 单分片故障只影响部分数据，可用性提升。
> **代价**：① 查询条件不含 `user_id` 时需**跨分片查询**，复杂度上升；② 跨分片事务需引入分布式事务，实现难度大；③ 跨分片的分页、排序、聚合统计复杂；④ 分片路由、扩容迁移、运维复杂度显著上升。

> **【问题 2】新问题与对策**：
> ① **全局唯一 ID**：单库自增主键不再唯一，改用**雪花算法/号段模式**生成全局唯一 ID；
> ② **非分片键查询**：如按订单号查询，可建立 `order_id → user_id` **映射表**、**异构索引表**，或将订单数据同步到 **Elasticsearch** 检索，也可在订单号中**嵌入用户 ID 分片因子**以直接定位分片；
> ③ **跨分片聚合/分页**：由中间件在各分片并行查询后**归并排序**，或借助**数据仓库/OLAP 引擎**做统计；
> ④ **跨分片事务**：引入 **2PC / TCC / Saga / 可靠消息最终一致性**等方案；
> ⑤ **扩容**：采用**一致性哈希**或**双写迁移**降低数据迁移量与业务影响。

## 4.6 丢分点

- ❌ 把水平分片写成"把字段拆开" → 拆字段是**垂直**分片。
- ❌ 只写"提升性能"，漏掉**跨分片查询/事务**这两个必答代价。
- ❌ 漏写**全局唯一 ID**（水平分片的必答项，几乎每次都有分）。
- ❌ 认为分片能替代读写分离 → 见下一章辨析。

# 第 5 章 读写分离

## 5.1 先建立直觉：银行的一个"存钱窗口"和三个"咨询窗口"

- 办存款、转账的窗口只有 **1 个**（慢、要动账本）→ **主库 Master**
- 咨询、查余额的窗口有 **3 个**（快、只看账本）→ **从库 Slave**
- 三个咨询窗口的员工，人手一份主窗口账本的**复印件**；主窗口每记一笔，就同步告诉他们 → **主从复制**

问题来了：**主窗口刚记完一笔，复印件还没更新，你去咨询窗口查，就查不到刚才那笔。**
→ 这就是**主从同步延迟**，读写分离题的**唯一核心考点**。

## 5.2 再讲原理

| 组成 | 职责 |
| --- | --- |
| **主库 Master** | 负责**写**操作（INSERT / UPDATE / DELETE） |
| **从库 Slave** | 负责**读**操作（SELECT），可有多个 |
| **复制机制** | 主库变更通过 binlog 同步到从库 |

**收益**：
1. 读请求分摊到多个从库，**大幅提升查询并发能力**（适合读多写少）；
2. 从库可作为**备份节点**，提高可用性，便于故障切换。

**代价（必写 3 条）**：
1. **主从同步延迟（最常考）**：写完后立刻查从库，可能读到旧数据；
2. 架构复杂度与运维成本上升；
3. 一致性由强一致退化为**最终一致性**。

### 主从复制的三种方式

| 方式 | 特点 | 一致性 | 性能 |
| --- | --- | --- | --- |
| **异步复制**（默认） | 主库提交后**不等**从库确认 | 最弱，可能丢数据 | 最高 |
| **半同步复制** | 主库提交后**等至少一个从库**确认收到日志 | 较强 | 中等 |
| **全同步复制** | 主库等**所有从库**执行完成 | 最强 | 最差 |

### 三种一致性读策略（解决"写完读不到"）

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| **强一致读（写后读主）** | 写操作后**立即**读取时，强制路由到主库 | 支付结果、提交订单 |
| **会话一致性** | 同一用户会话内，写后读走主库；其余读走从库 | 个人中心、我的订单 |
| **最终一致读** | 普通读全走从库，允许短暂延迟 | 商品详情、排行榜、评论列表 |

## 5.3 考试怎么考（这是"送分题"，务必拿满）

**经典题干**：某系统引入 MySQL 读写分离（1 主 3 从），上线后**用户提交订单后立刻刷新订单列表，偶尔看不到刚提交的订单**。请分析原因、收益代价，并给出改进方案。

**标准答案（背下来）**：

> **成因**：主库写入订单成功后，数据尚未同步复制到从库；查询请求被路由到从库，读取到旧数据，即**主从同步延迟**（主库 binlog 推送与从库回放存在时间差）。
>
> **收益**：① 读请求分发到 3 台从库，减轻主库压力，提升查询并发能力；② 从库可作为备份节点，提升可用性。
>
> **代价**：① 存在主从同步延迟，无法保证写完立即读到最新数据，牺牲一定一致性；② 主从复制与读写路由增加架构复杂度和运维成本。
>
> **改进方案**：
> ① **写后立即读强制走主库**（强一致读）；
> ② 采用**会话一致性**策略：用户会话内写后读走主库，其余请求走从库；
> ③ 对一致性要求高的场景改用**半同步复制**；
> ④ 从库延迟过高时通过中间件**自动摘除**延迟节点并告警；
> ⑤ 若允许改造架构，可采用**云原生存算分离数据库**（共享存储，读节点无延迟）。
>
> **权衡结论**：读写分离提升读性能与可用性，代价是数据同步延迟导致的一致性下降。

## 5.4 易混淆辨析：读写分离 vs 分库分表（必考）

| 维度 | 读写分离 | 分库分表（分片） |
| --- | --- | --- |
| **是否拆分数据** | ❌ **不拆**，每个从库都是**全量数据** | ✅ **拆**，每个分片只有一部分数据 |
| **解决什么** | 读**并发压力**大（读多写少） | 单表**数据量**太大（千万级以上） |
| **能减少单表行数吗** | ❌ 不能 | ✅ 能 |
| **典型代价** | 主从延迟 | 跨分片查询/事务复杂 |

> 🔥 **丢分点（年年有人栽）**：
> **"读写分离能解决单表 3000 万数据查询慢的问题" → 错！**
> 读写分离只是把同一份全量数据复制到多台机器，**每台机器上单表还是 3000 万行**，单个查询耗时不变，只是并发上来了。
> **单表数据量过大 → 必须分库分表（水平分片）。**

## 5.5 丢分点

- ❌ 说"从库可以替代备份" → 从库是**高可用**手段，不能替代**备份**（误删数据从库会同步删除）。
- ❌ 说"读写分离保证写完立刻读到" → 存在延迟。
- ❌ 只写"提升性能"，没写"主从延迟"这个代价。

# 第 6 章 事务与并发控制

## 6.1 先建立直觉：两个人同时操作同一个银行账户

张三账户 1000 元，两件事**同时**发生：

- 事务 A：转出 500（读 1000 → 减 500 → 写 500）
- 事务 B：转入 200（读 1000 → 加 200 → 写 1200）

不管控的话，最后余额可能是 500（B 的写覆盖了 A，200 元凭空消失）→ **丢失更新**。

再想一种情况：事务 A 看到"余额 500"，但那是 B 还没提交的中间值，结果 B 回滚了 → **脏读**。

**事务存在的意义：让并发操作像排队执行一样安全（ACID），同时尽量别排太长的队（性能）。**

## 6.2 再讲原理（一）：ACID

| 特性 | 含义 | 一句话 |
| --- | --- | --- |
| **A 原子性** | 事务中操作要么全做，要么全不做 | 全或不全 |
| **C 一致性** | 事务前后数据都满足完整性约束 | 转账前后总额不变 |
| **I 隔离性** | 并发事务之间互不干扰 | 看不见中间状态 |
| **D 持久性** | 提交后即使宕机也不丢失 | 落盘了 |

## 6.3 再讲原理（二）：并发的 4 类问题（必考）

> ⚠️ **务必写"四类"**，不要写"三类"（部分旧资料只写三类，考试以四类为准）。

| 问题 | 一句话 | 关键区别 |
| --- | --- | --- |
| **丢失更新** | 两个事务同时改，后写的覆盖先写的 | **写‑写**冲突 |
| **脏读** | 读到了别人**未提交**的数据 | 读的是**未提交**数据 |
| **不可重复读** | 同一事务内两次读**同一行**，值不一样 | 针对已提交的 **UPDATE / 单行内容** |
| **幻读** | 同一事务内两次**范围查询**，**行数**不一样 | 针对 **INSERT / DELETE / 结果集行数** |

> 🔥 **最大的丢分点：不可重复读 vs 幻读**
> - **不可重复读**：同一行，**内容变了**（被 UPDATE）→ 看"**值**"；
> - **幻读**：同一条件，**行数变了**（被 INSERT/DELETE）→ 看"**行数**"。
> 记忆：**不可重复读看值，幻读看行数。**

## 6.4 再讲原理（三）：四个隔离级别（背表）

**权衡规律：隔离级别越高 → 一致性越好 → 并发性能越低。**

| 隔离级别（低→高） | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| **读未提交** Read Uncommitted | ✅ 存在 | ✅ 存在 | ✅ 存在 |
| **读已提交** Read Committed | ❌ 解决 | ✅ 存在 | ✅ 存在 |
| **可重复读** Repeatable Read | ❌ 解决 | ❌ 解决 | ⚠️ **InnoDB 通过 MVCC + Next‑Key Lock 在很大程度上避免** |
| **串行化** Serializable | ❌ 解决 | ❌ 解决 | ❌ 解决 |

**必记事实**：
- **MySQL InnoDB 默认隔离级别 = 可重复读（RR）**；
- Oracle / SQL Server 默认多为**读已提交（RC）**；
- 串行化靠**加锁排队**实现，一致性最高但并发最差。

> ⚠️ **表述陷阱**：RR 下不要写"完全解决幻读"，要写"**基本解决 / 在很大程度上避免**"（当前读 + 未加间隙锁的极端场景仍可能出现）。写绝对化容易扣分。

## 6.5 再讲原理（四）：MVCC、快照读、当前读

**MVCC（多版本并发控制）**：给每行数据保存多个历史版本。
**直觉**：像文档的"修订历史"——你在读第 3 版时，别人正在写第 4 版，互不干扰，**读不加锁**。

| 概念 | 说明 | SQL 示例 |
| --- | --- | --- |
| **快照读** | 读**历史版本**，不加锁，靠 MVCC 实现 | `SELECT * FROM t WHERE id=1;` |
| **当前读** | 读**最新已提交**数据，并**加锁** | `SELECT ... FOR UPDATE;`<br>`SELECT ... LOCK IN SHARE MODE;`<br>`UPDATE / DELETE / INSERT` |

**Next‑Key Lock = 行锁 + 间隙锁**：
- **行锁**：锁住具体的某一行；
- **间隙锁**：锁住两条记录**之间的空隙**，防止别的事务往空隙里插新行 → **防止幻读的关键**。

> **答题句**：InnoDB 通过 **MVCC** 支持快照读（读不加锁，减少读写冲突，提升并发性能）；通过**行锁与间隙锁（Next‑Key Lock）**支持当前读下的并发控制，在很大程度上避免幻读。

## 6.6 再讲原理（五）：锁的分类

| 分类维度 | 类型 | 说明 | 适用 |
| --- | --- | --- | --- |
| 按态度 | **乐观锁** | 不加锁，更新时校验**版本号/时间戳** | 读多写少、冲突少 |
| | **悲观锁** | 访问前先加锁（`FOR UPDATE`） | 写冲突高 |
| 按粒度 | **行锁** | 锁单行（InnoDB） | 并发高、锁冲突小 |
| | **表锁** | 锁整表（MyISAM） | 并发低 |
| 按范围 | **间隙锁** | 锁索引记录之间的间隙 | 防止幻读 |

**乐观锁实现（能写出 SQL 更好）**：

```sql
UPDATE product SET stock = stock - 1, version = version + 1
WHERE id = 100 AND version = 5;   -- 影响行数为 0 说明被别人改过，需重试
```

## 6.7 考试怎么考

**常见问法 1**：请说明脏读、不可重复读、幻读的含义，并说明各隔离级别如何解决。
→ 直接默 6.3 表 + 6.4 表。

**常见问法 2（改错题）**：某系统为提升并发，将隔离级别设为"读未提交"，是否合适？

> **参考答案**：不合适。读未提交允许事务读取其他事务**未提交**的数据，会产生**脏读**，数据可靠性无法保证；且它带来的性能提升有限，却引入严重的正确性风险。建议采用**读已提交**（解决脏读）或**可重复读**（进一步解决不可重复读，MySQL 默认）；只有在严格要求无并发异常、且能接受串行执行代价的场景，才考虑**串行化**。

**常见问法 3**：如何解决"库存超卖"？

> **参考答案**：① **乐观锁**：商品表加 `version` 字段，更新时校验版本号，冲突则重试；② **悲观锁**：`SELECT ... FOR UPDATE` 先锁行再更新；③ **原子操作**：`UPDATE stock SET num = num - 1 WHERE id=? AND num > 0`，利用行锁与条件判断保证不超卖；④ **Redis 预扣减** + 异步落库（高并发秒杀场景）。

## 6.8 丢分点

- ❌ 把"不可重复读"和"幻读"说成一回事（**值变化 vs 行数变化**）。
- ❌ 漏掉"**丢失更新**"（只答三类）。
- ❌ 写"可重复读完全解决幻读"（应写"**在很大程度上避免/基本解决**"）。
- ❌ 隔离级别顺序写反（**读未提交 < 读已提交 < 可重复读 < 串行化**）。

# 第 7 章 分布式事务与数据一致性

## 7.1 先建立直觉：一笔订单要跨越 4 个部门盖章

用户下单需要：① 订单服务创建订单 → ② 库存服务扣库存 → ③ 积分服务加积分 → ④ 物流服务创建运单。
每个服务**各有自己的数据库**，本地事务管不到别人。问题是：**扣库存成功了，但加积分失败了，怎么办？**

> **直觉**：跨服务事务的核心矛盾是——
> **要么"所有人都先别动，等我确认"（强一致，但慢）；要么"先干活，出错就反向补偿"（最终一致，但快）。**

## 7.2 再讲原理（一）：CAP 与 BASE（理论地基）

### CAP 定理
分布式系统中，**一致性 C、可用性 A、分区容错性 P 三者不可兼得**。

**直觉**：两个机房之间光缆断了（P 必须接受，网络一定会出问题），此时：
- 要么**拒绝服务**，等网络恢复保证数据一致 → **CP**；
- 要么**继续服务**，但两边数据可能暂时不一样 → **AP**。

> **关键结论（背）**：**P 不可放弃**，实际只能在 **C 与 A 之间二选一**。

| 选项 | 含义 | 典型 |
| --- | --- | --- |
| **CP** | 保证一致性，牺牲可用性 | ZooKeeper、金融核心账务 |
| **AP** | 保证可用性，采用最终一致性 | 电商、社交、大多数互联网系统 |

### BASE 理论（CAP 中 AP 的延伸）
- **BA** Basically Available 基本可用（允许降级、响应变慢）
- **S** Soft state 软状态（允许中间状态存在）
- **E** Eventually consistent 最终一致性（一段时间后自动一致）

> **答题句**：互联网分布式系统通常遵循 **BASE 理论**，接受**最终一致性**，以换取高可用与高吞吐。

## 7.3 再讲原理（二）：6 种落地方案

### ① 2PC 两阶段提交
**流程**：协调者问所有人"准备好了吗"（Prepare，各参与者执行但**不提交**）→ 全部 OK 才发"提交"（Commit）。
- 优点：**强一致性**
- 缺点：**同步阻塞性能差**；协调者**单点故障**；第二阶段故障仍可能不一致
- 适用：**金融短事务**，一致性 > 性能

### ② 3PC 三阶段提交
在 2PC 基础上增加预询阶段 + 参与者**超时机制**，降低阻塞。
- 缺点：仍无法彻底消除不一致；**工业界极少落地**。
- 考试定位：知道它"缓解阻塞但未彻底解决一致性、落地少"即可。

### ③ TCC（Try‑Confirm‑Cancel）
- **Try**：**预留/冻结**资源（把库存冻结 1 件，不是真扣）
- **Confirm**：确认，真正执行业务
- **Cancel**：取消，释放预留资源
- 优点：**性能高，无长事务锁等待**
- 缺点：**业务侵入极强**，每个操作都要手写 Try/Confirm/Cancel 三段代码
- 适用：**短事务、高并发**，如电商下单扣库存、秒杀

### ④ Saga
把长事务拆成**一串本地短事务**，每个正向操作配一个**逆向补偿**操作，失败时**倒序执行补偿**。
- 优点：吞吐高，**不长期锁定资源**
- 缺点：只保证**最终一致性**，**不保证隔离性**（中间状态可能被其他事务看到）
- 适用：**长事务、跨多个异构服务**，如 订单 → 物流 → 支付回调

### ⑤ 本地消息表 / 可靠消息最终一致性
本地事务里"**改业务数据 + 插一条待发送消息**"（同一本地事务保证原子）→ 投递 MQ → 下游消费 → 失败重试 → 最终一致。
- 优点：实现简单、吞吐高、对业务侵入小
- 缺点：依赖 MQ 可靠性；需保证**消费端幂等**
- 适用：加积分、发券、通知等**允许延迟**的场景

### ⑥ 最大努力通知
发起方**尽力多次重试**通知（如支付结果通知商户），配合**接收方主动查询**。
- 特点：**一致性强度最低**
- 适用：**跨企业/跨机构**，如银行回调、第三方支付通知

## 7.4 🔥 选型决策树（本章最值钱的一页）

看到"分布式事务/跨服务一致性"，按这个顺序判断：

```
Q1. 是否要求【强一致】（账务、转账、资金、对账）？
    ├─ 是 → 2PC / XA（或直接用 NewSQL 分布式事务，如 TiDB）
    │       代价：性能低、可用性下降
    └─ 否（允许短暂不一致）→ 进入 Q2

Q2. 事务链路【长不长】、涉及服务【多不多】？
    ├─ 短事务 + 高并发（下单扣库存、秒杀）→ TCC
    └─ 长事务 + 跨多异构服务（订单+物流+支付回调）→ Saga

Q3. 能否接受【异步】？
    ├─ 能（加积分、发券、通知）→ 本地消息表 / 可靠消息最终一致性
    └─ 跨企业/跨机构（银行、第三方支付回调）→ 最大努力通知 + 主动查询
```

> 🔥 **最大的丢分点：TCC vs Saga 选错。**
> 判断标准只有一句话：**看事务执行时长**。
> - **TCC 的 Try 阶段就要锁定资源**。如果事务链路很长（订单 → 库存 → 物流 → 支付回调），资源被锁几十秒甚至几分钟，并发直接崩掉 → **必挂**。
> - **Saga 每一步都是本地短事务，做完就提交、就释放**，失败再反向补偿 → **长事务的唯一正解**。
>
> **金句（长事务选 Saga，直接抄）**：
> "该分布式事务涉及多个异构服务且执行链路较长（长事务），不推荐 TCC（Try 阶段会长期锁定库存等资源，导致并发骤降）。建议采用 **Saga 模式**，将长事务拆解为多个本地短事务，通过正向操作与反向补偿（如订单取消时触发退款并释放库存）实现最终一致性，显著降低资源锁定时间。"

## 7.5 TCC 的三个必答风险（考到 TCC 就有分）

| 问题 | 场景 | 应对 |
| --- | --- | --- |
| **幂等** | Confirm / Cancel 可能因网络重试被**重复调用** | 用事务 ID 去重；Confirm/Cancel 必须幂等 |
| **空回滚** | Try 请求超时未到达服务方，协调者触发了 Cancel；此时 Try 根本没执行 | Cancel 需识别"未执行 Try"的情况，**不能真的回滚业务** |
| **悬挂** | Cancel 先执行，Try 请求后到达 | Try 执行前先检查是否已 Cancel，若已 Cancel 则**不再执行**，否则资源被永久冻结 |

> **答题句**：TCC 方案需由业务侧实现**幂等控制、空回滚识别与悬挂防护**，否则在网络超时或重试场景下会导致数据异常。

## 7.6 例题（改错题，年年有）

**题干**：某银行转账系统，为保障转账业务的强一致性，项目组选择 TCC 分布式事务方案。请判断是否正确并说明理由。

> **参考答案**：**不正确**。
> ① TCC 属于**最终一致性**方案（Try‑Confirm‑Cancel 各阶段独立提交），**无法保证全局强一致性**；
> ② 银行转账属于**资金类强一致场景**，应优先选择 **2PC/XA**（强一致），或采用支持分布式强一致事务的 **NewSQL 数据库**（如 TiDB）；
> ③ TCC 适用于**高并发、允许短暂不一致的短事务**场景（如电商下单扣库存），且业务侵入极强，需自行实现幂等、空回滚、悬挂控制。
> ④ 若坚持使用最终一致方案，则须配合**对账系统 + 差错处理**兜底。

## 7.7 本章速记卡

```
CAP：P 必须接受 → CP（银行账务）/ AP（互联网，最终一致）
BASE：基本可用 + 软状态 + 最终一致
方案谱系（一致性从强到弱）：
  2PC(强一致,慢) → TCC(短事务高并发) → Saga(长事务补偿) → 本地消息表/可靠消息 → 最大努力通知(最弱)
选型第一刀：强一致？→ 2PC；否则看事务长短：短→TCC，长→Saga
TCC 三件套：幂等、空回滚、悬挂
```

# 第 8 章 缓存与数据库一致性

## 8.1 先建立直觉：前台小黑板 vs 后台账本

商店把"热销商品价格"写在**前台小黑板（缓存）**上，顾客问价直接看黑板，不用每次翻后台账本（数据库）。

- 价格调整时，是先改账本还是先擦黑板？
  - **先擦黑板，再改账本**：擦完黑板的瞬间，另一个营业员来问价，黑板空着 → 去翻账本（还是旧价）→ 把**旧价写回黑板** → 然后你才把账本改成新价。结果：**黑板上永远是错的旧价**。❌
  - **先改账本，再擦黑板**：擦黑板前短暂有人看到旧价，但擦完后有人来问，翻账本拿到**新价**写回黑板 → 最终正确。✅

**结论：先更新数据库，再删除缓存。** 这就是 **Cache Aside（旁路缓存）** 模式。

## 8.2 再讲原理（一）：Cache Aside 的标准流程

**读流程**：先读缓存 → 命中则返回 → **未命中则读数据库 → 把数据写入缓存 → 返回**
**写流程**：**更新数据库 → 删除缓存**

**为什么是"删除"缓存而不是"更新"缓存？（高频追问，3 条）**
1. **避免并发写导致脏数据**：两个并发写，更新缓存的先后顺序可能与数据库不一致，导致缓存里是旧值；
2. **更简单**：删除是一次操作，更新要构造完整缓存对象；
3. **避免无效计算**：写多读少时，每次都更新缓存是浪费（写了也没人读）。

> **答题句**：Cache Aside 模式采用**更新数据库后删除缓存**的策略，避免直接更新缓存在并发场景下产生脏数据，同时降低无效缓存更新的成本。

## 8.3 再讲原理（二）：其他写策略（了解即可，考得少）

| 策略 | 做法 | 特点 |
| --- | --- | --- |
| **Read Through** | 应用只与缓存交互，缓存负责读数据库 | 应用逻辑简化 |
| **Write Through** | 写缓存的同时，由缓存**同步**写入数据库 | 一致性强，但写性能受数据库限制 |
| **Write Behind / Write Back** | 写缓存后**异步批量**回写数据库 | 写入性能极高、可合并写；但**可能丢数据**、一致性弱。适合日志、计数、监控指标 |

## 8.4 延迟双删的严谨表述（考过会扣分的地方）

先更新数据库再删缓存，在**极端并发时序**下仍可能短暂不一致（比如"缓存刚好失效 + 并发读 + 并发写"叠加）。**延迟双删**（更新 DB → 删缓存 → 休眠一小会儿 → 再删一次）可以**降低**不一致概率，但**不能完全解决**。

> ⚠️ **考试千万别写绝对**：
> ❌ "采用延迟双删可以彻底解决缓存一致性问题"
> ✅ "延迟双删可以在一定程度上降低不一致概率，但不能完全解决缓存与数据库的一致性问题，通常需要结合**消息队列重试删除**或 **Binlog 订阅异步删除**（如 Canal）等机制。"

## 8.5 考试怎么考

**常见问法**：某系统采用"先删除缓存，再更新数据库"的方案，请分析存在的问题并给出改进方案。

> **参考答案**：
> **问题**：高并发下易产生脏数据。时序——① 线程 A 删除缓存；② 线程 B 读请求未命中缓存，查数据库拿到**旧值**并写入缓存；③ 线程 A 才完成数据库更新。此后缓存中一直是**旧值**，直到缓存过期。
> **改进**：改为 **Cache Aside**，即**先更新数据库，再删除缓存**。因为先更新 DB 再删缓存，即使删前有并发读，读到的也大概率是新值；即使极端情况下写入旧值，缓存删除后下次读会重新加载新值，不一致窗口极短。
> **进一步增强**：① 缓存设置合理 TTL 兜底；② 引入**延迟双删**；③ 通过 **Binlog 订阅（Canal）异步删除缓存**或**消息队列重试删除**，保证删除最终成功。
> **结论**：高性能缓存方案通常只能做到**最终一致性**；若要强一致，需付出性能代价（如分布式锁、串行化），需按业务容忍度权衡。

## 8.6 🔥 缓存三大问题：穿透、击穿、雪崩（必考，年年出）

**先建立直觉**：

| 问题 | 一句话 | 类比 |
| --- | --- | --- |
| **穿透** | 查**根本不存在**的数据，缓存和数据库都没有 → 每次都打到数据库 | 一直有人问"你们有火星产的手机吗"，黑板写不下（不存在），每次都要去翻账本 |
| **击穿** | **某一个热点 key** 过期，海量并发瞬间全打到数据库 | 最热销商品的价格刚好被擦掉，一万人同时问价，全去翻账本 |
| **雪崩** | **大批量 key 同一时刻**过期，或缓存服务整体宕机 | 整个小黑板被一次性全擦掉，所有问题都涌向账本 |

| 问题 | 关键点 | 解决方案（背） |
| --- | --- | --- |
| **穿透** | 查的是**不存在**的数据 | ① **缓存空对象**（空值也缓存，短 TTL，如 30~60 秒）；② **布隆过滤器**拦截无效 ID；③ 参数合法性校验（如 ID ≤ 0 直接拒绝）；④ 接口限流 |
| **击穿** | **单个热点 key** 失效 | ① 热点 key **永不过期**；② **逻辑过期**（见下）；③ **互斥锁重建缓存**；④ 缓存预热 |
| **雪崩** | **批量 key** 同时失效 / 缓存整体不可用 | ① 过期时间加**随机值**（`base + random(0,300)s`）打散；② **多级缓存**（本地缓存兜底）；③ 缓存预热；④ 服务**限流降级**；⑤ Redis **高可用集群** |

**布隆过滤器的三个缺点（爱考）**：① 存在**误判率**（假阳性：可能把不存在的判为存在）；② **一般不能删除元素**；③ **不能获取元素本身**。

### 击穿的两大解法对比（高频，可能出序列图）

| 方案 | 核心思路 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **互斥锁（物理过期）** | 缓存按 TTL 正常过期；未命中时**只有拿到锁的线程**查库重建 | 数据库只被一个线程访问，保护数据库 | 其他线程阻塞/轮询，响应时间变长 |
| **逻辑过期** | 缓存**永不过期**，存"数据 + 逻辑过期时间"；过期时**先返回旧数据**，异步更新 | 响应快，不阻塞 | 可能返回旧数据，一致性弱 |

**互斥锁方案的时序（真题考过填空，务必背）**：

```
线程1：查缓存(未命中) → 获取互斥锁(成功) → 查数据库 → 写缓存 → 释放锁 → 返回
线程2：查缓存(未命中) → 获取互斥锁(失败) → 休眠重试 → 再次查缓存(命中) → 返回
```

**序列图填空的 5 个要点**：
1. 两个线程都**先查缓存**，均未命中；
2. 线程1 成功获取互斥锁（`SET key value NX EX`）；
3. 线程2 获取锁失败，**不能去查数据库**，进入"**休眠重试**"；
4. 线程1 持锁执行"**查数据库 → 写缓存 → 释放锁**"；
5. 线程2 被唤醒后**先重新查询缓存**（不是直接加锁），此时缓存已重建 → 命中。

> ⚠️ **失分陷阱**：序列图最容易漏掉最后那步"**再次查询缓存**"。它体现的是"等别人重建好缓存后我直接复用"的设计思想，漏了就扣分。

## 8.7 丢分点

- ❌ **混淆"击穿"与"雪崩"**：击穿是**单个热点 key**，雪崩是**批量 key**。
- ❌ 说"缓存穿透是缓存宕机导致的" → 那是**雪崩**（缓存服务不可用）。
- ❌ 写"先删缓存再更新数据库"作为推荐方案 → 推荐的是**先更新 DB 再删缓存**。
- ❌ 只答"加缓存"，不写一致性与三大问题的应对。

# 第 9 章 NoSQL 与存储选型

## 9.1 先建立直觉：不同的东西要用不同的柜子装

- **账本**（结构化、要算得准、要事务）→ 带锁的铁柜 → **关系数据库**
- **随手取的零钱** → 桌面上的托盘，快 → **Redis**
- **一篇篇格式不固定的文章** → 文件夹，随便塞 → **MongoDB**
- **几十年的监控流水** → 仓库里的货架，按列堆 → **HBase**
- **人与人之间的关系网** → 一张关系图 → **图数据库**

## 9.2 再讲原理：选型对照表（背口诀就够）

| 特性 | 关系型 MySQL | KV‑Redis | 文档‑MongoDB | 列族‑HBase | 图‑Neo4j |
| --- | --- | --- | --- | --- | --- |
| 数据模型 | 二维结构化表 | 键‑值 | JSON/BSON 文档 | 列族 | 节点、边、关系 |
| 事务能力 | 完整 ACID 强一致 | 单命令原子；支持 Lua/事务但不保证回滚 | 单文档事务；多文档事务需权衡 | 弱 | 图事务 |
| 水平扩展 | 困难 | 容易 | 容易 | 极易 | 较难 |
| 擅长 | 结构化数据、事务、复杂 SQL | 简单单点读写 | 中等复杂文档查询 | 海量历史数据顺序扫描 | 关系、路径查询 |
| 典型场景 | 账务、订单交易 | 会话/热点缓存 | 日志、内容管理 | PB 级时序历史数据 | 社交网络、知识图谱 |

> **选型口诀（背）**：
> **交易账务选 MySQL，热点缓存选 Redis，日志内容 MongoDB，海量历史 HBase，关系图谱图数据库。**

## 9.3 考试怎么考

**问法**：某系统需要存储 XX 数据，请从 MySQL / Redis / MongoDB / HBase / Neo4j 中选择合适的存储并说明理由。

答题三步：① 说出**数据特点**（结构化？海量？关系密集？）② 给出**选型** ③ 说明**理由 + 代价**。

| 题干线索 | 选它 |
| --- | --- |
| 订单、账务、资金、强一致事务 | **MySQL / NewSQL** |
| 热点数据、会话、排行榜、计数器、分布式锁 | **Redis** |
| 商品详情、文章内容、字段不固定 | **MongoDB** |
| PB 级日志、历史流水、监控时序数据、离线扫描 | **HBase** |
| 社交好友、欺诈识别、知识图谱、路径查询 | **图数据库** |
| 海量数据 + 强一致事务 + 不想手动分库分表 | **NewSQL（TiDB / OceanBase）** |
| 全文检索、复杂多条件组合查询、日志分析 | **Elasticsearch** |
| 私有知识库、大模型问答、语义检索 | **向量数据库（Milvus / ES / pgvector）** |

> ⚠️ **丢分点**：只写选型不写理由；或把 Redis 当持久化存储（Redis 是缓存，重要数据要有持久化兜底）。

# 第 10 章 数据仓库、ETL 与多维建模

## 10.1 先建立直觉：收银台 vs 总经理驾驶舱

- **业务数据库（OLTP）**：收银员用的系统，每笔交易都要**实时、准确、可写**。关心"**这一笔**"。
- **数据仓库（OLAP）**：总经理看的报表，关心"**上个月华东区哪个品类卖得最好**"。数据**只读**、**定期批量导入**、**保存历史**。

> **一句话：OLTP 处理"当下的每一笔"，OLAP 分析"历史的整体趋势"。**

| 维度 | OLTP（业务库） | OLAP（数据仓库） |
| --- | --- | --- |
| 目的 | 支撑日常业务操作 | 支撑分析决策 |
| 操作 | 增、删、改、查 | 主要**查询**，基本不更新 |
| 数据 | 当前的、实时的、细节的 | 历史的、汇总的、集成的 |
| 模型 | 规范化（3NF），少冗余 | **反规范化**（星形/雪花），允许多余 |
| 关注 | 事务吞吐、响应时间 | 查询灵活、扫描性能 |

## 10.2 再讲原理（一）：ETL

**ETL = Extract（抽取）→ Transform（清洗转换）→ Load（加载）**

- **Extract**：从各业务系统（MySQL、日志、API）抽取数据；
- **Transform**：清洗（去重、补缺失、格式统一）、转换（编码映射、维度关联、聚合）；
- **Load**：加载进数据仓库。

> **CDC（变更数据捕获）**：通过监听 **Binlog** 近实时捕获业务库变更，替代定时全量抽取，实现业务库到数仓的**近实时同步**。

## 10.3 再讲原理（二）：星形模型 vs 雪花模型（必考）

**先建立直觉**：一张**事实表**（记录了"谁在什么时候买了什么、花了多少钱"）在中间，周围围着一圈**维度表**（时间、商品、门店、客户）。

- **星形模型**：维度表**直接连在事实表上**，维度表之间不相连，维度表**不规范化**（有冗余）。形状像星星 ⭐
- **雪花模型**：维度表**继续往下拆**（商品 → 品类 → 大类），形状像雪花 ❄

| 模型 | 结构 | 冗余 | 查询性能 | 适用 |
| --- | --- | --- | --- | --- |
| **星形** | 事实表 + 一层维度表 | 维度表**有冗余** | **高**（JOIN 少） | **最常用**，推荐 |
| **雪花** | 维度表继续规范化拆分 | **冗余低** | 较低（JOIN 多） | 维度层级复杂、存储空间敏感 |

> **答题权衡句**：星形模型查询性能高（JOIN 少），但维度表存在冗余；雪花模型冗余低、节省存储，但查询需要更多 JOIN，复杂度上升。**实际建模中星形模型更常用**。

## 10.4 再讲原理（三）：三个延伸考点

### 缓慢变化维 SCD（维度数据会变，怎么处理）

**场景**：客户搬家了，地址变了。历史订单该按新地址还是旧地址统计？

| 类型 | 做法 | 特点 |
| --- | --- | --- |
| **Type 1** | **直接覆盖**旧值 | 不保留历史 |
| **Type 2** | **新增一行**记录，保留历史版本（加生效时间/失效时间/版本号） | **最常用**，可追溯历史 |
| **Type 3** | **增加一个字段**保存上一次的旧值 | 只保留有限历史 |

### 事实表三种类型

| 类型 | 说明 | 例子 |
| --- | --- | --- |
| **事务事实表** | 记录**业务事件**（最细粒度） | 下单、支付、点击 |
| **周期快照事实表** | 按**固定周期**记录状态 | 每日库存快照、每月账户余额 |
| **累计快照事实表** | 记录业务**生命周期的多个关键节点** | 订单的创建/支付/发货/完成时间 |

### OLAP 五种基本操作（背）

| 操作 | 含义 | 例子 |
| --- | --- | --- |
| **上卷 Roll‑up** | 从细到粗汇总 | 从"日"汇总到"月"，从"城市"汇总到"省" |
| **下钻 Drill‑down** | 从粗到细展开 | 从"年销售额"下钻到"各月" |
| **切片 Slice** | 固定**某一个维度**的取值 | 只看"2025 年"的数据 |
| **切块 Dice** | 固定**多个维度**的取值范围 | 只看"2025 年 + 华东区 + 手机品类" |
| **旋转 Pivot** | 转换维度观察角度 | 行列互换 |

## 10.5 再讲原理（四）：数据分层与数据架构（近年热点）

| 概念 | 说明 |
| --- | --- |
| **数据仓库** | 面向分析的**结构化**数据集合（OLAP） |
| **数据湖** | 统一存储**原始**数据，支持结构化/半结构化/非结构化 |
| **湖仓一体** | 湖的灵活性 + 仓的管理性 |
| **数据中台** | 将数据**资产化、服务化**，支撑多业务应用 |
| **实时数仓** | 基于 Kafka + Flink 的实时 ETL，支持实时大屏/监控 |

**数仓经典分层（ODS → DWD → DWS → ADS，背）**：

| 层 | 名称 | 作用 |
| --- | --- | --- |
| **ODS** | 操作数据层 | **贴源**存储原始数据，不做处理 |
| **DWD** | 明细数据层 | 清洗、规范化后的**明细事实** |
| **DWS** | 汇总数据层 | 按主题**轻度聚合**（如用户当日行为汇总） |
| **ADS** | 应用数据层 | 面向报表/接口的**高度聚合**结果 |

**Lambda / Kappa 架构**：

| 架构 | 核心思想 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **Lambda** | 批处理层 + 速度层 + 服务层 | 离线准确，实时快速 | **两套逻辑**，维护复杂 | 既要历史准确又要实时统计 |
| **Kappa** | 全部用流处理，靠**重放**数据补历史 | 架构简单，统一流处理 | 对消息存储与计算能力要求高 | 实时性要求高、数据可重放 |
| **流批一体** | 同一套逻辑同时支持批和流 | 降低开发维护成本 | 对引擎要求高 | 实时数仓、统一计算平台 |

## 10.6 考试怎么考

**问法**：某公司各业务系统数据分散（数据孤岛），管理层需要经营分析报表与实时大屏。请设计数据架构。

> **参考答案（套模板）**：
> ① **数据采集**：通过 **ETL**（定时批量）与 **CDC**（监听 Binlog，近实时）将各业务系统数据接入统一数据平台（数据湖 / 数据仓库）；
> ② **分层建模**：按 **ODS（贴源）→ DWD（清洗明细）→ DWS（主题轻度汇总）→ ADS（应用聚合）** 分层加工，形成统一指标口径；
> ③ **建模方式**：采用**星形模型**组织事实表与维度表，兼顾查询性能与可理解性；对会变化的维度（如客户地址）采用**缓慢变化维 Type 2** 保留历史；
> ④ **分析支撑**：通过 **OLAP 引擎**支持上卷、下钻、切片、切块、旋转等多维分析；通过报表服务、数据 API 支撑经营分析与用户画像；
> ⑤ **实时部分**：实时大屏采用 **Kafka + Flink 实时数仓**（或 Lambda 架构）处理；
> ⑥ **治理保障**：建设**元数据管理、数据标准、数据质量监控、数据血缘分析**，保证指标口径一致、数据可信。

> ⚠️ **丢分点（本类型最致命）**：只答"MySQL 分库分表 + Redis 缓存"，完全没上升到**数据分层、湖仓一体、ETL/CDC**。这类题要的是**数据架构视角**，答性能优化等于跑题。

## 10.7 本章速记卡

```
OLTP=业务(写多、实时、规范化)  OLAP=分析(只读、历史、反规范化)

```

# 第 11 章 Redis 专项（近两年必考）

> 近年真题对 Redis 考查越来越深，**分布式锁、缓存击穿互斥锁序列图**几乎成为必考。

## 11.1 先建立直觉：Redis = 放在内存里的超级便利贴

数据放在内存里，读写都是微秒级 —— 但**内存贵且掉电丢失**，所以 Redis 有持久化机制，且通常**只放该放的东西**（热点数据、会话、计数、锁）。

## 11.2 再讲原理（一）：五种数据类型与选型（高频）

| 类型 | 核心特性 | 典型场景 | 真题 |
| --- | --- | --- | --- |
| **String** | 二进制安全，最大 512MB | 缓存、计数器、**分布式锁**、共享 Session | 2025：分布式锁选 String |
| **Hash** | 键值对嵌套（field‑value） | **购物车**、用户对象、商品详情 | — |
| **List** | 双向链表，有序可重复 | 消息队列、最新评论、粉丝列表 | — |
| **Set** | 无序不可重复，支持集合运算 | **用户画像标签**、抽奖、共同好友 | 2025：用户画像标签选 Set |
| **ZSet** | 按分数排序，元素唯一 | **排行榜**、延时队列、优先级队列 | 2025：销售周排行榜选 ZSet |

> **口诀**：缓存锁 String，对象 Hash，队列 List，去重用 Set，排序用 ZSet。

## 11.3 再讲原理（二）：持久化 RDB vs AOF

| 机制 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **RDB** | 定时生成**内存快照** `dump.rdb` | 文件紧凑，**恢复快**，适合备份容灾 | 可能丢失最后一次快照后的数据；BGSAVE 的 fork 在大内存下可能阻塞 |
| **AOF** | 记录所有**写命令**追加到日志 | 数据安全性高（`everysec` 最多丢 1 秒）；日志可读可修复 | 文件大、恢复慢；需定期 `BGREWRITEAOF` 重写 |
| **混合持久化**（4.0+） | AOF 重写时先以 RDB 存全量，后续增量用 AOF | **兼顾恢复速度和数据安全** | — |

> **答题模板**：RDB 适合备份和快速恢复，但可能丢数据；AOF 数据更安全但恢复慢；混合持久化兼顾二者。对数据安全性要求高的场景推荐 **AOF（everysec）或混合持久化**。

## 11.4 再讲原理（三）：内存淘汰策略

当内存满了，Redis 需要淘汰数据。**先分清两大家族**：

- **`volatile‑*`**：只在**设置了过期时间**的键里淘汰；
- **`allkeys‑*`**：在**所有键**里淘汰。

| 策略 | 范围 | 算法 |
| --- | --- | --- |
| volatile‑lru / allkeys‑lru | 过期键 / 所有键 | LRU（**最近最少使用**） |
| volatile‑lfu / allkeys‑lfu | 过期键 / 所有键 | LFU（**最不经常使用**） |
| volatile‑ttl | 过期键 | 淘汰**剩余 TTL 最小**的 |
| volatile‑random / allkeys‑random | 过期键 / 所有键 | 随机 |
| noeviction | — | 不淘汰，写入报错 |

> **答题模板**：缓存淘汰策略基于**局部性原理**，优先淘汰最近/最不常被访问的数据。`volatile‑lru` 仅针对设置了过期时间的键，`allkeys‑lru` 针对所有键。

## 11.5 再讲原理（四）：分布式锁（必考）

### 死锁问题（最经典）

```redis
SETNX lock_key 1        -- 加锁成功
EXPIRE lock_key 30      -- 若此时服务宕机，这行没执行 → 锁永不过期 → 死锁！
```

**正确做法：用原子命令一次性完成"设值 + 过期时间"**

```redis
SET lock_key <uuid> EX 30 NX
```

### 三大高频问题与解法（背表）

| 问题 | 原因 | 解决方案 |
| --- | --- | --- |
| **死锁** | SETNX 与 EXPIRE 非原子 | 使用 `SET key value EX NX` 原子命令 |
| **锁被误删** | 线程 A 超时后，线程 B 加锁，A 恢复后把 B 的锁删了 | 锁值用**唯一标识（UUID）**，删除时**校验值**（用 Lua 保证"判断+删除"原子） |
| **锁过期但业务未完成** | 业务执行时间 > 锁过期时间 | **看门狗机制**（如 Redisson）自动续期 |

### RedLock
向 **N 个独立 Redis 节点**请求加锁，**过半成功**才算加锁成功。适用：对锁可靠性要求极高的场景（资金、对账核心链路）。

## 11.6 再讲原理（五）：高可用三种形态

| 特性 | 主从模式 | 哨兵模式 | Cluster 集群 |
| --- | --- | --- | --- |
| 数据分布 | 全量复制 | 全量复制 | **分片（16384 槽位）** |
| 故障转移 | **手动**干预 | **自动**选举新主 | 从节点**自动晋升** |
| 优点 | 简单，读多写少 | 自动故障转移，高可用 | **水平扩展**，数据分片 |
| 缺点 | 单点故障 | 写性能受限 | 架构复杂 |

**主从复制**：全量复制（首次/断连较久，主库 `BGSAVE` 生成 RDB 发给从库）+ 增量复制（持续传播写命令）。

> **答题模板**：Redis 主从复制默认**异步复制**，存在同步延迟与数据丢失风险。对一致性要求高的场景可配置**半同步复制**或使用 `WAIT` 命令（会牺牲吞吐与延迟）。

## 11.7 丢分点

- ❌ 把"分布式锁"实现写成 `SETNX` + `EXPIRE` 两条命令（**必须强调原子性**）。
- ❌ 忘记写"锁值用 UUID，删除时校验"（否则扣"误删"那 1~2 分）。
- ❌ 混淆 `volatile-*` 与 `allkeys-*` 的作用范围。
- ❌ 把 Redis 当可靠持久化存储（它是缓存，宕机可能丢数据，重要数据必须有 DB 兜底）。

# 第 12 章 云原生数据库与 NewSQL

## 12.1 先建立直觉：把"厨师"和"冰箱"分开

传统数据库：**厨师（计算）和冰箱（存储）绑在一个房间里**。想多招个厨师？得整个房间复制一份，还得把食材（数据）搬过去，搬一整天。

云原生数据库：**所有厨师共用一个超大的中央冷库（共享存储）**。多招厨师？直接加人，**不用搬食材**，秒级到位。而且所有厨师看的是**同一份食材**，不存在"你看到的和我看到的不一样"（**无主从延迟**）。

## 12.2 再讲原理（一）：存算分离

| 组件 | 职责 | 特性 |
| --- | --- | --- |
| **计算节点** | SQL 解析、执行计划生成 | **无状态**，可秒级弹性扩缩容 |
| **存储层** | 数据持久化、副本管理、故障修复 | **分布式共享存储**，一份数据副本 |

**核心技术**：
- **日志即数据（Log‑Structured Storage）**：通过 Redo Log 实现存储，避免传统脏页刷盘；
- **共享存储**：所有计算节点共享同一份数据，**从物理上消除了传统主从复制的日志回放延迟**。

**核心优势**：弹性扩容（秒级加计算节点）、按量付费、**读写分离无延迟**、故障秒级恢复、单库容量大（突破 128TB）。

| 产品 | 特点 |
| --- | --- |
| **AWS Aurora** | 存算分离，兼容 MySQL/PostgreSQL，一写多读 |
| **阿里云 PolarDB** | 存算分离，一写多读，最大 100TB |
| **TiDB** | NewSQL，水平扩展 + ACID，计算‑存储分离 |

## 12.3 再讲原理（二）：NewSQL

**定义**：兼顾传统关系库的 **ACID 事务能力** 与 NoSQL 的**水平扩展能力**。代表：Google Spanner、**TiDB**、OceanBase、CockroachDB。

| 方案 | 事务能力 | 水平扩展 | 典型产品 |
| --- | --- | --- | --- |
| 传统关系库 | ✅ 强 ACID | ❌ 困难 | MySQL, Oracle |
| NoSQL | ❌ 弱 | ✅ 容易 | Redis, MongoDB, HBase |
| **NewSQL** | ✅ **强 ACID** | ✅ **容易** | TiDB, CockroachDB |

**TiDB 三组件（高频）**：

| 组件 | 职责 |
| --- | --- |
| **TiDB Server** | SQL 解析、执行计划生成（**无状态计算层**） |
| **PD** (Placement Driver) | 集群调度、**数据分片管理、再平衡**决策 |
| **TiKV** | 分布式 KV 存储引擎，基于 **Raft** 保证多副本一致 |

## 12.4 考试怎么考（答题金句，直接抄）

> 💡 **场景判断**：题干中"**分片规则频繁变更、运维压力大、扩缩容困难**" → 优先推荐 **NewSQL / 云原生数据库**替代手动分库分表。

**上云场景金句**：

> "本系统可选用**存算分离架构**（如 PolarDB / Aurora）。该架构下计算节点共享底层分布式存储，从物理层面消除了传统主从复制的日志回放延迟，读节点可见数据与主节点严格一致，无需在应用层做'强制读主库'的路由；同时计算节点无状态，支持**秒级弹性扩容**，契合促销峰值的弹性诉求。"

**传统手动分库分表的缺点**（用来对比）：应用层侵入、分片规则修改困难、运维成本高。

> ⚠️ **注意**：传统读写分离的主从延迟**仍是必考基础知识点**。云原生存算分离是对它的"演进升级"答案。
> **题干若限定"传统架构" → 写主从延迟与强制主库；题干若问"云原生改进" → 写存算分离。**

## 12.5 🔥 RAG 架构数据存储（2026 新大纲 AI 热点·弯道超车）

> 2026 新大纲新增"AI 系统架构设计"（AI 占比约 25%），案例题最爱考"结合场景选型"。
> **若题干出现"企业私有知识库""智能客服""大模型问答"，还答 MySQL 分库分表就完全跑题。**

**核心概念**：
- **RAG（检索增强生成）**：**先检索**相关知识片段，**再拼进 Prompt** 调用大模型，解决大模型**知识陈旧**与**幻觉**问题；
- **向量数据库**：存储文本经 Embedding 后的**高维向量**，支持 **ANN（近似最近邻）** 检索，如 Milvus、Elasticsearch、pgvector；
- **Embedding 模型**：把文本切片转为向量，语义相近的文本在向量空间距离更近。

**案例答题框架（题干出现"AI 问答/知识库"直接套用）**：

> "针对该智能问答/知识库场景，采用 **RAG（检索增强生成）**架构。核心数据流转如下：
> ① **离线阶段**：将私有文档切片后经 **Embedding 模型**转为向量，存入**向量数据库**（如 Milvus / Elasticsearch）；
> ② **在线阶段**：用户 Query 向量化后在向量库做 **ANN（近似最近邻）检索**，召回 **Top‑K** 相关片段；
> ③ 将片段与 Query 拼接成 Prompt 调用大模型生成答案。
> 该架构利用向量数据库解决大模型**知识陈旧与幻觉**问题；文档的元数据（来源、版本、权限）则存放于 **MySQL** 以便管理版本与权限；可结合**混合检索（向量 + BM25 关键词）**提升准确率，切片策略（chunk size）影响召回质量。"

> ⚠️ RAG 考点是"**向量数据库选型 + 检索增强生成的数据流**"，不要写成纯算法题。

# 第 13 章 补丁知识点（防冷门，各 2~4 分）

这些点冷门但**一旦考到就是白送分**，花 20 分钟过一遍性价比极高。

## 13.1 关系代数（与 SQL 对应）

| 运算 | 含义 | 对应 SQL |
| --- | --- | --- |
| **选择 σ** | 按条件筛选**行** | `WHERE` |
| **投影 π** | 选取**列** | `SELECT 列名` |
| **并 ∪ / 差 − / 交 ∩** | 集合运算（要求关系同构） | `UNION / EXCEPT / INTERSECT` |
| **笛卡尔积 ×** | 两关系所有元组组合 | 无连接条件的 JOIN |
| **连接 ⋈** | 按条件组合两关系 | `JOIN` |
| **除 ÷** | 求解"包含了**全部**"语义 | "查询选修了**全部**课程的学生" |

**连接类型**：
- **自然连接**：按同名同域属性**自动等值连接**并**去除重复列**；
- **等值连接**：按指定相等条件连接，**保留重复列**；
- **外连接（左/右/全）**：保留未匹配的**悬空元组**，缺失侧补 NULL。

> ⚠️ **丢分点**：自然连接 vs 等值连接的区别就是**去不去重列**。

## 13.2 完整性约束

| 类型 | 含义 | 实现 |
| --- | --- | --- |
| **实体完整性** | 主键唯一且非空 | PRIMARY KEY |
| **参照完整性** | 外键取值必须有效或为空 | FOREIGN KEY |
| **用户定义完整性** | 业务规则（金额非负、年龄范围） | CHECK / 触发器 |

## 13.3 视图、触发器、存储过程

| 对象 | 作用 |
| --- | --- |
| **视图** | 简化查询；**安全控制**（屏蔽敏感列）；屏蔽底层表结构变化（**逻辑独立性**） |
| **触发器** | 自动数据校验、级联更新、**审计日志** |
| **存储过程** | 封装业务逻辑，减少网络交互，提高执行效率 |

## 13.4 数据库安全

**措施清单（背）**：用户身份认证；**权限最小化**；角色管理；**视图隔离敏感字段**；数据加密（存储/传输/字段级）；**数据脱敏**（测试开发环境保护敏感数据）；**SQL 注入防护**（预编译参数化查询）；**审计日志**。

> **答题金句**：数据库安全应遵循**最小权限原则**，通过用户认证、角色授权、视图控制、数据加密和审计日志等手段保障数据的**机密性、完整性、可用性**。

## 13.5 备份恢复与容灾

| 概念 | 含义 |
| --- | --- |
| **全量备份** | 备份全部数据 |
| **增量备份** | 备份**上次备份**以来变化的数据 |
| **差异备份** | 备份**上次全量备份**以来变化的数据 |
| **日志备份** | 备份事务日志，用于**时间点恢复 PITR** |
| **RPO** | 恢复点目标：**允许丢失多少数据** |
| **RTO** | 恢复时间目标：**允许停机多久** |

> 🔥 **丢分点：RPO 与 RTO 写反！** 记忆法：**P = Point（数据点，丢多少数据）**，**T = Time（时间，停多久）**。

**答题模板**：

> "可采用**全量备份 + 增量备份 + 事务日志备份**相结合的方式。日常通过日志备份支持时间点恢复，同时建设主备或同城/异地容灾架构。若业务要求数据丢失少（**低 RPO**），采用同步或半同步复制；若要求恢复时间短（**低 RTO**），采用自动故障切换并定期做恢复演练。"

## 13.6 数据治理

| 概念 | 含义 |
| --- | --- |
| **元数据** | 描述数据的数据（Schema、血缘、指标口径） |
| **主数据** | 企业核心共享数据（客户、产品、组织） |
| **数据标准** | 统一数据定义、编码、格式 |
| **数据质量** | 准确性、完整性、一致性、及时性 |
| **数据血缘** | 数据的来源、加工过程和流向 |
| **数据安全分类分级** | 按敏感程度分级管理（**新大纲常考**） |

## 13.7 丢分点小结

- ❌ RPO / RTO 写反；
- ❌ 自然连接与等值连接混为一谈；
- ❌ 认为"从库 = 备份"；
- ❌ 安全措施只写"加密"一条（至少写 5 条）。

# 第 14 章 综合实战：一道完整真题走一遍全流程

## 14.1 真题

**题干**：某线上图书商城，初期数据库采用单库单表。随着用户规模增长，出现如下问题：
1. 图书订单表数据量超过 2500 万条，订单查询速度缓慢；
2. 网站商品详情页面访问量巨大，数据库读压力很高，写压力较小。

项目组给出两套优化方案：
- **方案 A**：引入读写分离架构，一主两从；
- **方案 B**：对订单表进行水平分片，按照用户 ID 哈希分片。

| 问题 | 分值 |
| --- | --- |
| 【问题 1】请分别说明方案 A、方案 B 主要解决什么问题 | 7 分 |
| 【问题 2】分析方案 A 带来的收益与代价 | 8 分 |
| 【问题 3】采用方案 B 水平分片之后，请分析收益与代价 | 10 分 |

## 14.2 ① 审题：划线索（3 分钟，这步不能省）

| 题干原话 | 翻译成技术语言 |
| --- | --- |
| "订单表超过 2500 万条，查询缓慢" | **单表数据量过大** → 需要**水平分片** |
| "商品详情页访问量巨大，读压力高，写压力小" | **读多写少** → 需要**读写分离** |
| "方案 A：读写分离" | 对应痛点 2 |
| "方案 B：用户 ID 哈希分片" | 对应痛点 1 |

> 💡 **这道题的题眼**：**两个方案解决的痛点不一样，绝不能混为一谈。** 命题人就是想看你会不会把"读压力大"和"单表数据量大"搞混。

## 14.3 ② 配分规划（决定写多少）

- 7 分题 → 写 2 段，每段 2~3 个要点；
- 8 分题 → 写 2 组（收益 + 代价），每组 2~3 条；
- 10 分题 → 写 2 组 + 1 段补充，每组 3~4 条。

**经验公式**：**1 分 ≈ 1 个要点 ≈ 1~1.5 行字**。10 分的题写到 12~15 行比较合适。

## 14.4 ③ 参考答案

### 【问题 1】（7 分）

> **方案 A（读写分离）**：将读请求分发到从库，减轻主库查询压力，解决网站商品详情页**读访问量巨大、读压力过高**的问题；**但不能解决单表海量数据查询缓慢的问题**。
>
> **方案 B（订单表水平分片）**：将海量订单**行数据**拆分到多个分片，降低单表数据量，解决订单表**数据量过大、订单查询缓慢**的问题。

### 【问题 2】（8 分）

> **收益**：
> ① 大量商品详情读请求分流至两台从库，减轻主库查询压力，提升查询性能与并发能力；
> ② 从库可作为主库备份节点，提升数据库可用性，便于故障切换。
>
> **代价**：
> ① 存在**主从数据同步延迟**，写后立刻查询可能读到旧数据，牺牲一定数据一致性；
> ② 主从复制与读写路由增加架构复杂度与运维成本；
> ③ 从库数量增加带来硬件成本上升，且**从库不能替代完整的数据备份机制**。

### 【问题 3】（10 分）

> **收益**：
> ① 订单数据分散到多个分片，每片单表数据量下降，索引体积减小，订单查询速度提升；
> ② 数据可分散存储到多个数据库节点，突破单机存储与并发瓶颈，提升整体存储容量与可用性；
> ③ 单分片故障只影响部分数据，故障影响面减小。
>
> **代价**：
> ① 查询条件**不带用户 ID 分片键**时需**跨分片查询**，查询复杂度上升；
> ② **跨分片事务**实现难度大，分布式事务复杂度上升；
> ③ 跨分片的**分页、排序、聚合统计**复杂，需中间件归并或引入 OLAP 引擎；
> ④ 分片路由、扩容迁移、运维复杂度显著上升。
>
> **补充措施**：
> ① 按用户 ID 哈希分片有利于用户维度查询，但**订单号查询、时间范围查询、商家维度查询**需要**映射表、异构索引表或搜索引擎（Elasticsearch）**支持；
> ② 水平分片后需引入**全局唯一 ID 生成机制**（号段模式 / 雪花算法）替代单库自增主键；
> ③ 扩容可采用**一致性哈希**或**双写迁移**，降低数据迁移量与业务影响。

## 14.5 ④ 失分陷阱复盘

| 陷阱 | 说明 |
| --- | --- |
| ❌ "读写分离能解决单表 2500 万数据查询慢" | 读写分离**不减少单表行数**，只能提升并发；解决大数据量要靠**水平分片** |
| ❌ 只写收益不写代价 | 本题 2/3 的分值在"代价"和"补充措施"上 |
| ❌ 把水平分片写成垂直分片 | 按用户 ID 分是**按行拆** = 水平分片 |
| ❌ 漏写全局唯一 ID | 这是水平分片的**必答配套项** |
| ❌ 漏写非分片键查询方案 | 10 分题，这种"追问型"补充就是拉开差距的地方 |

## 14.6 ⑤ 沉淀成模板

> **读写分离模板**：读写分离架构可分散**读压力**，提升查询性能与可用性；但是存在**主从同步延迟**，带来一致性下降的代价，需通过写后读主库或会话一致性应对。
>
> **水平分片模板**：水平分片降低**单表数据量**，提升查询性能与存储扩展能力；但是带来**跨分片查询、跨分片事务、跨分片聚合分页复杂**等代价，需配套**全局唯一 ID**与**非分片键查询方案**。

# 第 15 章 答题模板合集（考前一夜就背这个）

## 15.1 范式判断模板

```
1. 求候选键，区分主属性 / 非主属性
2. 判 1NF：属性是否原子
3. 判 2NF：有没有【非主属性】对候选键的【部分依赖】
4. 判 3NF：有没有【非主属性】对候选键的【传递依赖】
5. 判 BCNF：有没有【主属性】对候选键的部分/传递依赖（= 箭头左边是否都是候选键）
6. 结论：最高满足 xNF，理由是存在 XX 依赖
```

## 15.2 规范化拆分模板

```
1. 指出当前存在的异常（插入 / 删除 / 修改异常）
2. 给出函数依赖分析
3. 按 3NF 分解为多张关系，标注主键 / 外键
4. 显式说明：具有【无损连接性】+【保持函数依赖】   ← 白捡 2~4 分
5. 结论：消除冗余与异常，代价是查询需 JOIN
```

## 15.3 索引优化模板

```
1. 在 WHERE / JOIN / ORDER BY / GROUP BY 字段上建立索引
2. 采用联合索引，遵守【最左前缀】：等值在前、区分度高在前、范围在后
3. 将查询字段纳入索引实现【覆盖索引】，避免回表（回表 IO ≈ 两棵树高之和）
4. 避免索引失效：索引列不做函数运算、避免隐式类型转换、避免前导 % 模糊查询
5. 利用【索引下推 ICP】在存储引擎层提前过滤，减少回表行数
6. 配合 EXPLAIN 分析执行计划，目标：type 至少达到 range、key 不为 NULL、避免 Using filesort
7. 代价：索引占用额外存储并降低写入性能，索引数量应适度控制
```

## 15.4 反规范化模板

```
1. 手段：增加冗余字段 / 增加派生列 / 合并表 / 垂直拆分
2. 收益：减少多表连接（JOIN），提升查询性能
3. 代价：数据冗余上升、不一致风险、更新（写）成本上升
4. 一致性维护：事务内同步更新 / 触发器 / 物化视图 / 定时任务 / 消息队列 / Binlog 监听（Canal）
5. 结论：以一致性、存储为代价换查询性能，需权衡
```

## 15.5 水平分片模板

```
1. 方案：按某分片键（哈希 / 范围 / 列表）拆分数据到多个分片
2. 收益：单表数据量下降，查询性能提升，可分散存储与压力，提升可用性
3. 代价：跨分片查询、跨分片事务、跨分片聚合与分页复杂，运维复杂度上升
4. 配套：全局唯一 ID（号段 / 雪花算法）；非分片键查询用映射表 / 异构索引 /
       搜索引擎 / 订单号嵌入分片因子；扩容用一致性哈希或双写迁移
5. 结论：解决单表海量数据查询慢，代价是分布式复杂度上升
```

## 15.6 垂直分片模板

```
1. 方案：按字段（列）拆分表，通常保留相同主键
2. 收益：减少单表宽度与 IO、减少锁冲突、冷热数据分离
3. 代价：查询完整数据需多表 JOIN
4. 结论：缓解单表宽度与 IO 压力，代价是 JOIN 复杂度上升
```

## 15.7 读写分离模板

```
1. 方案：主库写、从库读，通过 binlog 主从复制同步
2. 收益：读压力分摊到多个从节点，查询性能与可用性提升
3. 代价：主从同步延迟，无法保证写完立即读到最新，一致性下降；运维复杂度上升
4. 应对：写后强一致读走主库 / 会话一致性 / 半同步复制 / 摘除高延迟从库 /
       云原生存算分离（共享存储无延迟）
5. 结论：提升读性能，代价是同步延迟与一致性下降
```

## 15.8 缓存一致性模板

```
1. 方案：Cache Aside —— 读：命中返回，未命中查库并回写缓存；写：更新数据库后删除缓存
2. 理由：删除优于更新 —— 避免并发写脏数据、实现简单、避免无效计算
3. 风险：极端并发下仍可能短暂不一致
4. 应对：延迟双删（降低概率，非万能）、删除重试、Binlog 异步删除、设置合理 TTL
5. 三大问题：穿透→空值缓存+布隆过滤器；击穿→互斥锁/逻辑过期/热点永不过期；
            雪崩→过期时间加随机值+多级缓存+预热+限流降级+高可用集群
6. 结论：高性能方案做到最终一致性，强一致需付出性能代价
```

## 15.9 分布式事务模板

```
1. 强一致场景（账务/转账/对账）→ 2PC / XA / NewSQL 分布式事务（牺牲性能与可用性）
2. 最终一致场景：
   - 短事务 + 高并发（下单扣库存、秒杀）→ TCC（需幂等、空回滚、悬挂控制）
   - 长事务 + 跨多异构服务（订单+物流+支付回调）→ Saga（正向 + 反向补偿）
   - 高吞吐异步（加积分、发券、通知）→ 本地消息表 / 可靠消息最终一致性
3. 跨企业/跨机构（支付回调、银行通知）→ 最大努力通知 + 接收方主动查询
4. 理论支撑：CAP（P 必选，C/A 二选一）、BASE（最终一致性）
5. 结论：按一致性要求、性能要求与事务长度权衡选择
```

## 15.10 数据仓库 / 数据平台模板

```
1. 采集：ETL（定时批量）+ CDC（Binlog 近实时）接入数据湖 / 数据仓库
2. 分层：ODS 贴源 → DWD 清洗明细 → DWS 主题汇总 → ADS 应用聚合
3. 建模：星形模型（事实表 + 维度表，查询快、常用）；维度变化用 SCD Type 2 保留历史
4. 服务：OLAP（上卷/下钻/切片/切块/旋转）+ 报表 + 数据 API + 用户画像
5. 实时：Kafka + Flink 实时数仓；Lambda（批+速）/ Kappa（全流重放）/ 流批一体
6. 治理：元数据、主数据、数据标准、数据质量、数据血缘、安全分类分级
```

# 第 16 章 十大丢分点总清单（考前 5 分钟过一遍）

| # | 丢分点 | 正确表述 |
| --- | --- | --- |
| 1 | **只写收益不写代价** | 看到"分析/评价/说明"就必须写两面，代价往往占一半分 |
| 2 | **不可重复读 vs 幻读混淆** | 不可重复读看**值（UPDATE）**，幻读看**行数（INSERT/DELETE）** |
| 3 | **漏掉"丢失更新"** | 并发问题是**四类**，不是三类 |
| 4 | **RR 下写"完全解决幻读"** | 应写"**在很大程度上避免 / 基本解决**" |
| 5 | **分解题漏写无损连接与依赖保持** | 做完分解无脑追加这两句，各 1~2 分 |
| 6 | **读写分离当成大数据量解法** | 读写分离只分散**读压力**；单表数据量大要**水平分片** |
| 7 | **水平/垂直分片说反** | **垂直切字段，水平切记录** |
| 8 | **RPO / RTO 写反** | R**P**O = 丢多少**数据**；R**T**O = 停多长**时间** |
| 9 | **延迟双删 / 缓存方案写绝对** | 写"**在一定程度上降低概率**"，并补充 Binlog/消息重试 |
| 10 | **TCC / Saga 选错** | 看**事务时长**：短事务高并发 → TCC；长事务多服务 → Saga |

**补充三个"表述安全"提醒**：

1. **B+ 树、ICP、MVCC、Next‑Key Lock**：题干没明确问 InnoDB 底层机制时，简化成"通过合理建立索引、使用覆盖索引、避免索引失效，减少全表扫描和回表次数，提升查询性能"——**别炫技，炫技容易偏题**。
2. **"基因法"**：建议写"在订单号中嵌入用户 ID 的分片因子，使根据订单号也能定位所在分片"，而不是只丢一个术语。
3. **TCC/Saga/2PC 按题干选**：银行转账强一致 → 2PC/XA；电商下单高并发允许短暂不一致 → TCC/Saga/可靠消息。
