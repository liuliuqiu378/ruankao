# 第 1 章 · 软件过程模型

> 🎯 **记忆策略**：每种模型只需记 3 件事 —— **①适合什么场景 ②最大优点 ③最大缺点**。

## 1.1 传统（预测型）模型

| 模型 | 核心思想 | 适用场景 | 优点 | 缺点 |
|------|---------|---------|------|------|
| **瀑布模型** | 线性顺序，上一阶段完成后进入下一阶段 | **需求明确且稳定** | 简单、易管理、文档完备 | **无法应对需求变化**；用户要到最后才能看到成果 |
| **V 模型** | 瀑布 + **开发与测试阶段一一对应** | 需求明确、重视测试 | **测试贯穿全程**，早期验证 | 同瀑布，灵活性差 |
| **原型模型** | 快速构建一个可运行原型，反复修改 | **需求不明确** | 快速明确需求 | 原型可能被误当成品；代码质量差 |
| **螺旋模型** | 四大象限循环：**制定计划 → 风险分析 → 实施工程 → 客户评估** | **大型、复杂、高风险**项目 | **强调风险分析** | 需专业风险评估；成本高；周期长 |
| **增量模型** | 分模块**分批交付**，先交付核心功能 | 需求可分块、需快速见效 | **第一个增量很快可用** | 需要良好的架构；增量划分要合理 |
| **喷泉模型** | 面向对象，各阶段**迭代、无间隙** | 面向对象开发 | 支持复用、无缝衔接 | 需大量人员，管理复杂 |
| **构件组装模型（CBSD）** | 用**已有构件**组装系统 | 有可复用构件库 | 开发快、成本低、质量高 | 构件匹配与接口适配难 |

> 🔴 **必背**：
> - **螺旋模型 = 风险驱动**（"螺旋的核心是风险分析"）
> - **V 模型的核心价值：开发与测试的对应关系**
> - **喷泉模型 = 面向对象 + 迭代 + 无间隙**

## 1.2 RUP（统一过程）

| 特性 | 内容 |
|------|------|
| **三大特点** | **用例驱动**、**以架构为中心**、**迭代和增量** |
| **四个阶段** | ① **初始**（Inception）：确定项目范围与愿景<br>② **细化**（Elaboration）：建立架构基线，解决高风险<br>③ **构造**（Construction）：大量编码，产出可交付版本<br>④ **移交**（Transition）：用户培训、Beta 测试、交付 |
| **九大核心工作流** | 6 个核心过程工作流（业务建模、需求、分析与设计、实现、测试、部署）+ 3 个支持工作流（配置与变更管理、项目管理、环境） |
| **每次迭代产出** | 一个**可运行的版本** |

> 🔴 **必背**：RUP 的**"4+1"是「4 个阶段 + 9 个工作流」**（注意与架构的"4+1 视图"区分，别混淆）。

## 1.3 敏捷方法（近年权重上升）

| 方法 | 核心实践 |
|------|---------|
| **Scrum** | **Sprint（冲刺，通常 2~4 周）**、产品待办列表（Product Backlog）、Sprint 待办列表、**每日站会（15 分钟）**、Sprint 评审、Sprint 回顾；角色：**PO（产品负责人）、Scrum Master、开发团队** |
| **XP（极限编程）** | **结对编程**、**测试驱动开发（TDD）**、持续集成、重构、简单设计、小版本发布 |
| **看板（Kanban）** | 可视化工作流 + **限制在制品（WIP）** + 拉动式 |
| **水晶方法** | 强调"人"与"沟通"，项目规模不同方法不同 |

> 🔴 **敏捷宣言四价值观**（必背）：
> 1. **个体和互动** 高于 流程和工具
> 2. **可工作的软件** 高于 详尽的文档
> 3. **客户合作** 高于 合同谈判
> 4. **响应变化** 高于 遵循计划
>
> 📌 注意：**"高于"≠"不要"**，右边仍有价值，只是左边更重要。这是常见陷阱表述。

## 1.4 DevOps

> **一句话**：**开发（Dev）+ 运维（Ops）**一体化，**打破部门墙**，通过自动化实现**快速、频繁、可靠**的交付。

**核心实践**：持续集成（CI）、持续交付/持续部署（CD）、基础设施即代码（IaC）、自动化监控、微服务、容器化

# 第 2 章 · 需求工程

## 2.1 需求的三个层次

| 层次 | 说明 | 例子 |
|------|------|------|
| **业务需求** | 组织/客户的高层目标 | "提升订单处理效率 30%" |
| **用户需求** | 用户要完成的任务 | "用户能在线查询订单状态" |
| **系统需求** | 系统的具体功能与约束，含：**功能需求**、**非功能需求**、**设计约束** | "查询接口响应时间 < 500ms"（非功能） |

> 🔴 **必背**：
> - **非功能需求 = 质量属性需求**（性能、安全性、可用性等）
> - **设计约束** = 限定解决方案的条件（如"必须用国产数据库""必须部署在政务云"）

## 2.2 需求工程四阶段

```
需求获取（Elicitation） → 需求分析（Analysis） → 需求规格说明（Specification） → 需求验证（Validation）
                                                            ↓
                                              需求管理（变更、跟踪、版本）
```

- **需求获取方法**：访谈、问卷调查、观察、头脑风暴、联合需求计划（JRP）、原型法、用例建模
- **需求验证**：评审、原型确认、测试用例生成 —— **确认"需求是对的"**
- **需求跟踪**：**正向跟踪**（需求→下游工作产品）、**逆向跟踪**（工作产品→需求）；双向跟踪
- **需求基线**：经过评审确认的需求集合，变更需走**变更控制流程**

## 2.3 需求变更控制流程（流程题常考）

```
① 提出变更申请
② 变更评估（影响分析：范围、进度、成本、质量）
③ CCB（变更控制委员会）审批
④ 实施变更
⑤ 验证变更
⑥ 通知相关干系人并更新文档
```

> 🔴 **必背**：**CCB = 变更控制委员会（Change Control Board）**，是变更的**决策机构**。

# 第 3 章 · 软件设计

## 3.1 内聚与耦合（🔴 必考，年年有）

> 🧠 **直觉比喻**：**耦合** = 模块之间的"来往密切程度"（**越低越好**）；**内聚** = 模块内部"团结程度"（**越高越好**）。
> 口诀：**"高内聚，低耦合"**。

### 内聚（7 种，由低到高）

| 等级 | 名称 | 说明 | 例子 |
|:----:|------|------|------|
| 1 | **偶然内聚**（巧合内聚） | 模块内各部分**毫无关系** | 把几个不相关的函数硬塞进一个模块 |
| 2 | **逻辑内聚** | 逻辑上**同类**（都做"输入"），但功能不同 | "读取各类输入"模块（读键盘、读文件、读网络） |
| 3 | **时间内聚** | 在同一**时间**执行 | "初始化模块"（初始化所有数据） |
| 4 | **过程内聚** | 按**特定次序**执行 | 按流程依次调用 |
| 5 | **通信内聚** | 操作**同一数据** | 对同一个表的增删改查 |
| 6 | **顺序内聚** | 上一个的输出是下一个的输入 | 读数据 → 处理数据 |
| 7 | **功能内聚** | 只完成**一个单一功能**（最强） | "计算个人所得税" |

> 🔴 **口诀**：**"偶逻时过通顺功"** → 谐音 **"偶落石锅通顺风"**

### 耦合（7 类，由低到高）

| 等级 | 名称 | 说明 |
|:----:|------|------|
| 1 | **非直接耦合** | 两个模块**无直接关系**，通过主模块控制（最理想） |
| 2 | **数据耦合** | 通过**参数**传递**简单数据值**（最常见、提倡） |
| 3 | **标记耦合** | 传递的是**数据结构**（如整个对象/记录），但只用到其中一部分 |
| 4 | **控制耦合** | 传递**控制信息**（如标志位），被调用方据此决定做什么 |
| 5 | **外部耦合** | 模块共享**同一个全局变量**之外的外部环境（如共享文件格式、协议） |
| 6 | **公共耦合** | 多个模块**访问同一全局数据区/公共环境** |
| 7 | **内容耦合**（最差） | 一个模块**直接访问另一个模块的内部数据**或**跳入其内部** |

> 🔴 **口诀**：**"非数标控外公内"** → 谐音 **"非属表控外公内"**
> **必背**：**提倡「数据耦合」，避免「公共耦合」，杜绝「内容耦合」**。

## 3.2 面向对象设计原则（SOLID，必考）

| 原则 | 全称 | 一句话 | 生活比喻 |
|:----:|------|--------|---------|
| **S** | 单一职责原则 SRP | 一个类**只负责一个职责** | 一个人只干一份工作，别又当厨师又当司机 |
| **O** | 开闭原则 OCP | **对扩展开放，对修改关闭** | 想加新功能请"加"，别"改"原来的 |
| **L** | 里氏替换原则 LSP | **子类必须能替换父类** | 能装"水果"的箱子，也能装"苹果" |
| **I** | 接口隔离原则 ISP | 客户端**不应依赖它不需要的接口** | 别把 100 个方法塞进一个接口 |
| **D** | 依赖倒置原则 DIP | **依赖抽象，不依赖具体实现** | 高层模块不依赖低层模块，二者都依赖抽象 |

**其他常见原则**（教材常提）：
- **迪米特法则（最少知识原则）**：一个对象应尽可能少地了解其他对象
- **合成复用原则**：**优先使用组合/聚合，少用继承**
- **接口分离**、**共同封闭**、**共同重用**

> 🔴 **必背**：
> - **开闭原则（OCP）是面向对象设计的最高目标**
> - **"组合优于继承"** = 合成复用原则
> - DIP 的落地手段通常就是**依赖注入（DI）**

## 3.3 设计模式（新大纲已弱化，了解分类即可）

| 类型 | 数量 | 常见模式 |
|------|:----:|---------|
| **创建型** | 5 | 单例、工厂方法、抽象工厂、建造者、原型 |
| **结构型** | 7 | 适配器、装饰器、代理、外观、桥接、组合、享元 |
| **行为型** | 11 | 策略、观察者、模板方法、迭代器、责任链、命令、状态、访问者、中介者、备忘录、解释器 |

# 第 4 章 · 软件测试

## 4.1 V 模型的对应关系（🔴 必考）

```
需求分析 ──────────────── 验收测试
概要设计 ───────────── 系统测试
详细设计 ───────── 集成测试
编码 ────── 单元测试
```

| 开发阶段 | 对应的测试级别 | 测试什么 |
|---------|--------------|---------|
| 编码 | **单元测试** | 单个模块/函数 |
| 详细设计 | **集成测试** | 模块之间的接口 |
| 概要设计 | **系统测试** | 整个系统的功能与非功能需求 |
| 需求分析 | **验收测试** | 是否满足用户需求（**Alpha / Beta 测试**） |

> 🔴 **口诀**：**"单集系验"**（单测→集成→系统→验收），对应**"编详概需"**（编码→详细设计→概要设计→需求分析）。

## 4.2 测试阶段（按目的）

| 阶段 | 说明 |
|------|------|
| **单元测试** | 测**模块内部逻辑**；多采用**白盒**；需写驱动模块与桩模块 |
| **集成测试** | 测**模块间接口**；策略：**一次性集成** vs **增量式**（自顶向下需**桩**模块、自底向上需**驱动**模块） |
| **确认（有效性）测试** | 验证软件是否满足**需求规格说明书**；多用**黑盒** |
| **系统测试** | 在**真实环境**下测整个系统，含**功能、性能、压力、安全、恢复性、兼容性**测试 |
| **验收测试** | 用户参与；**Alpha**（开发环境内，用户来测） vs **Beta**（用户实际环境中测） |
| **回归测试** | 修改后**重新执行**之前的测试，验证**未引入新错误**（自动化重点） |

> 🔴 **必背**：
> - **自顶向下集成需要「桩模块」，自底向上集成需要「驱动模块」**
> - **Alpha = 开发现场，用户来；Beta = 用户现场，用户测**

## 4.3 黑盒 vs 白盒

| 维度 | **黑盒测试** | **白盒测试** |
|------|-------------|-------------|
| 视角 | 不看内部结构，**只看功能** | 看**程序内部逻辑** |
| 阶段 | 确认测试、系统测试、验收测试 | 单元测试、集成测试 |
| 方法 | **等价类划分、边界值分析、因果图、决策表、错误推测、正交试验** | **逻辑覆盖**（语句、判定、条件、判定-条件、条件组合、路径）、基本路径测试 |
| 能否发现 | 功能错误、接口错误、性能问题 | 代码逻辑错误、路径错误、死代码 |

### 白盒逻辑覆盖强度（由弱到强，🔴 必考排序）

```
语句覆盖 < 判定覆盖 < 条件覆盖 < 判定-条件覆盖 < 条件组合覆盖 < 路径覆盖
```

> 🔴 **必背**：
> - **最弱 = 语句覆盖**（每条语句执行一次）
> - **最强 = 路径覆盖**（覆盖所有可能路径，通常不可行）
> - **条件组合覆盖** 比 **判定-条件覆盖** 更强

### 边界值分析（高频陷阱）

> 📌 **必背**：边界值要测 **min-1、min、min+1、正常值、max-1、max、max+1** 七个点。
> 例：输入范围 [1, 100] → 应测 **0、1、2、50、99、100、101**。

## 4.4 测试用例与环复杂度

```
McCabe 环形复杂度 V(G) = 边数 - 节点数 + 2 = 判定节点数 + 1 = 闭合区域数 + 1
V(G) 就是「独立路径数」= 至少需要的测试用例数（语句覆盖/路径覆盖的基本需求）
```
计算详见 👉 [07 第 6.1 节](./07-计算题专项.md#61-mccabe-环形复杂度必考)。

## 4.5 测试原则

1. **测试无法显示软件中潜在的所有错误**（测试只能证明有错，不能证明无错）
2. **尽早并持续地测试**
3. **程序员应避免测试自己写的程序**
4. **测试用例应包含合理的与不合理的输入**
5. **注意"群集现象"**：**80% 的错误集中在 20% 的模块中**（二八定律）
6. **测试应追溯到用户需求**

> 🔴 **必背**：**"测试不能证明软件没有错误"** —— 高频判断题。

# 第 5 章 · 软件维护与质量

## 5.1 维护的四种类型（🔴 必考，考"给场景判断属于哪类"）

| 类型 | 定义 | 占比 | 判别关键词 |
|------|------|:----:|-----------|
| **改正性维护** | 修复**已发现的 bug** | 17~21% | "修复缺陷""纠错""故障" |
| **适应性维护** | 适应**外部环境变化**（OS、数据库、法规、硬件升级） | 18~25% | "系统升级""迁移到新平台""政策变化" |
| **完善性维护** | **增强功能、改进性能**（用户主动提出的新需求） | **50~66%** | "新增功能""优化性能""提升体验" |
| **预防性维护** | 为**将来的**可维护性/可靠性做准备（重构、改注释） | ~4% | "重构""为将来做准备""改写以便日后维护" |

> 🔴 **必背**：
> - **占比最大的是「完善性维护」（约 50%以上）**
> - **"把旧系统改造以便将来好维护" = 预防性维护**（这是最常被认错的）

## 5.2 软件质量模型

### ISO/IEC 9126 六大特性（经典，教材常用）

| 特性 | 子特性 |
|------|--------|
| **功能性** | 适合性、准确性、互操作性、安全保密性、依从性 |
| **可靠性** | 成熟性、容错性、易恢复性 |
| **易用性** | 易理解性、易学性、易操作性、吸引性 |
| **效率** | 时间特性、资源利用性 |
| **可维护性** | 易分析性、易改变性、稳定性、易测试性 |
| **可移植性** | 适应性、易安装性、共存性、易替换性 |

> 🔴 **口诀**：**"功可易用效可维可移"** → 取首字：**功、可、易、效、维、移** → 谐音 **"功效容易维持转移"**

### ISO/IEC 25010（9126 的升级版，八大特性）

在 9126 基础上新增 **安全性** 与 **兼容性** 两个**一级特性**：
功能性、性能效率、**兼容性**、易用性、可靠性、**安全性**、可维护性、可移植性

### McCall 质量模型（三视角，了解）

| 视角 | 特性 |
|------|------|
| **产品运行** | 正确性、可靠性、效率、完整性（安全）、使用性 |
| **产品修改** | 可维护性、可测试性、灵活性 |
| **产品转移** | 可移植性、可复用性、互连性 |

## 5.3 CMMI 成熟度等级（🔴 必考五级）

| 等级 | 名称 | 特征 |
|:----:|------|------|
| 1 | **初始级**（Initial） | 无序，靠个人英雄主义，**过程不可预测** |
| 2 | **已管理级**（Managed） | 项目级有**基本管理**，过程**有计划、有跟踪**（需求管理、项目计划、配置管理、QA） |
| 3 | **已定义级**（Defined） | **组织级**标准过程，**过程被文档化、标准化** |
| 4 | **量化管理级**（Quantitatively Managed） | 过程**被量化管理和控制**，有**统计**数据支撑 |
| 5 | **优化级**（Optimizing） | 基于量化反馈**持续改进**、技术创新 |

> 🔴 **口诀**：**"初管定优，量在其中"** 或直接背：**初始 → 已管理 → 已定义 → 量化管理 → 优化**
> **关键区分**：
> - 2 级 vs 3 级：**2 级是"项目级"**，**3 级是"组织级"**
> - 3 级 vs 4 级：**4 级引入"量化/统计"**
> - 4 级 vs 5 级：**5 级是"持续改进"**

# 第 6 章 · 项目管理

> ⚠️ **本章所有计算**（关键路径、挣值分析、PERT、沟通渠道、EMV、赶工）见 👉 [07 计算题专项 第 7 章](./07-计算题专项.md#七项目管理计算)。本节只讲**概念与辨析**。

## 6.1 进度管理

| 概念 | 说明 |
|------|------|
| **活动** | 项目中的具体工作单元，消耗时间和资源 |
| **里程碑** | **持续时间为 0** 的重要时点（只标识事件，不是活动） |
| **总浮动时间** | 不影响**项目总工期**可拖延的时间 |
| **自由浮动时间** | 不影响**紧后活动最早开始**可拖延的时间 |
| **关键路径** | **总浮动为 0** 的活动连成的**最长**路径，决定项目最短工期 |
| 关键路径数量 | 可能**不止一条**（多条同样长） |
| 压缩工期手段 | **赶工**（加资源、加成本） / **快速跟进**（原本串行的改为并行，**增加返工风险**） |

> 🔴 **必背**：
> - **关键路径是网络图中「最长」的路径**（不是最短！很多人搞反）
> - **缩短工期的手段**：赶工（增加成本）vs 快速跟进（增加风险）
> - **CPM（关键路径法）** 假设资源无限；**PERT** 用三点估算法处理不确定性

## 6.2 成本管理

| 概念 | 说明 |
|------|------|
| **BAC** | 完工预算（Budget At Completion） |
| **PV / EV / AC** | 计划值 / 挣值 / 实际成本 |
| **CV / SV** | 成本偏差 / 进度偏差（**正数为好**） |
| **CPI / SPI** | 成本绩效 / 进度绩效指数（**>1 为好**） |
| **EAC / ETC / VAC** | 完工估算 / 完工尚需估算 / 完工偏差 |
| **成本类型** | 直接成本（可直接归属某项目）vs 间接成本（分摊）；可变成本 vs 固定成本；**沉没成本（不应影响决策）** |

> 🔴 **必背**：**沉没成本不应影响当前决策**（"来都来了"是错误逻辑）。

## 6.3 风险管理

```
风险识别 → 风险评估（概率 × 影响） → 风险应对 → 风险监控
```

**四种应对策略**

| 策略 | 适用 | 举例 |
|------|------|------|
| **规避** | 消除风险本身 | 改变方案、取消高风险功能 |
| **转移** | 把后果转给第三方 | **买保险、外包、签免责条款** |
| **减轻** | 降低发生概率或影响 | 增加测试、加冗余、做备份 |
| **接受** | 无法/不值得处理 | 建立应急储备，被动接受 |

> 🔴 **区分**：**转移 ≠ 减轻**。**转移是"后果给别人"，减轻是"后果变小了"**。

## 6.4 配置管理

| 概念 | 说明 |
|------|------|
| **配置项** | 纳入配置管理的产物（需求文档、设计文档、代码、测试用例、环境配置……） |
| **基线** | 经过正式评审并批准的配置项集合，**基线变更需走变更控制流程** |
| **三种基线** | **功能基线**（需求确认）、**分配基线**（设计确认）、**产品基线**（产品确认） |
| **配置库** | **开发库**（动态库，开发者自己控制）→ **受控库**（主库，变更需审批）→ **产品库**（静态库，存放最终产品） |
| **版本管理** | 版本号、分支、合并、标签 |
| **配置审计** | 功能审计（是否符合需求）+ 物理审计（交付物是否完整） |

> 🔴 **必背**：**开发库 → 受控库 → 产品库** 的演进顺序；**基线变更必须走 CCB 审批**。

## 6.5 质量管理

| 工具 | 用途 |
|------|------|
| **因果图（鱼骨图 / 石川图）** | 追溯问题的**根本原因** |
| **控制图** | 判断过程是否在**可控范围**（上下控制线） |
| **帕累托图（Pareto）** | **二八定律**，按发生频率排序，抓主要问题 |
| **流程图** | 展示过程步骤 |
| **直方图** | 展示数据分布 |
| **散点图** | 看两个变量的相关性 |
| **核查表** | 收集数据 |

> 🔴 **必背**：**帕累托图 = 二八定律**；**鱼骨图找原因**；**控制图看是否失控**。

## 6.6 沟通管理

```
沟通渠道数 = n(n-1) / 2       （计算见 07 第 7.4 节）
```
- **正式沟通**（报告、会议） vs **非正式沟通**（闲聊）
- **向上/向下/横向**沟通
- 沟通障碍：信息过载、缺乏反馈、语义歧义、层级过滤

<summary>参考答案</summary>

1. **风险驱动**（每个迭代都包含"风险分析"象限），适合大型、复杂、高风险项目
2. **集成测试**
3. **不是**。敏捷宣言的"高于"表示**优先级**，右边（文档）**仍有价值**，只是左边更重要
4. 非功能需求是**对系统质量属性的要求**（区别于"能做什么"的功能需求）。例：**"查询响应 < 500ms"（性能）**、**"系统需支持 7×24 可用"（可用性）**、**"密码必须加密存储"（安全性）**
5. **CCB（变更控制委员会）**
6. 由低到高：**偶然内聚 → 逻辑内聚 → 时间内聚 → 过程内聚 → 通信内聚 → 顺序内聚 → 功能内聚**（口诀"偶逻时过通顺功"）
7. **提倡「数据耦合」**；**杜绝「内容耦合」**（也应力求避免公共耦合）
8. **对扩展开放，对修改关闭** —— 新增功能应通过"扩展"实现，而不修改已有代码
9. **驱动模块**（自顶向下需要的是**桩模块**）
10. **最强 = 路径覆盖**；**最弱 = 语句覆盖**
11. **0、1、2、50、99、100、101**（min-1、min、min+1、正常值、max-1、max、max+1）
12. **预防性维护**（关键词是"为将来"）
13. **完善性维护**（占 50%~66%）
14. **2 级是「项目级」的过程管理**（单个项目有计划和跟踪）；**3 级是「组织级」**（过程被文档化、标准化，全组织统一并裁剪）
15. **快速跟进**（把原本串行的活动改为并行）。风险：**增加返工风险**（后续活动可能要基于未完成的前置工作返工）
