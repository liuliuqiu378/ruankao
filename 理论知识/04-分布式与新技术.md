# 第 1 章 · 分布式理论基础

## 1.1 CAP 定理（🔴 必考中的必考）

> **一句话**：分布式系统中，**C（一致性）、A（可用性）、P（分区容错性）三者不可兼得，最多同时满足两项**。
> 而**网络分区（P）在分布式系统中必然发生**，所以**实际只能在 C 和 A 之间二选一**。

| 字母 | 全称 | 含义 | 生活比喻 |
|:----:|------|------|---------|
| **C** | Consistency 一致性 | 所有节点在同一时刻看到**相同的数据** | 所有分店的价签永远一样 |
| **A** | Availability 可用性 | 每次请求都能**得到响应**（不保证是最新数据） | 每次打电话都有人接 |
| **P** | Partition Tolerance 分区容错性 | **网络分区**发生时系统仍能继续工作 | 分店之间断网了，各自还能营业 |

### 三种取舍

| 选择 | 含义 | 典型系统 |
|------|------|---------|
| **CP** | 保证一致性，**牺牲可用性**（分区时拒绝服务或阻塞） | ZooKeeper、etcd、**Redis（主从前）**、HBase、传统关系数据库（分布式事务） |
| **AP** | 保证可用性，**牺牲强一致性**（返回可能过期的数据，最终一致） | **Eureka**、Cassandra、DynamoDB、CouchDB |
| **CA** | 单机系统才可能（放弃分区容错，等于不是真正的分布式） | 单机 MySQL、Oracle |

> 🔴 **必背**：
> - **CAP 中的 P 是"必须选"的**（因为网络故障必然存在），所以真实选择只有 **CP 或 AP**。
> - **ZooKeeper / etcd = CP**；**Eureka = AP**（这是最高频的搭配题）。
> - **Nacos 同时支持 CP 和 AP**（通过切换）。

## 1.2 BASE 理论（对 CAP 中 AP 的延伸）

| 字母 | 全称 | 含义 |
|:----:|------|------|
| **B**A | Basically Available **基本可用** | 允许**损失部分可用性**（响应时间变长、功能降级） |
| **S** | Soft State **软状态** | 允许系统存在**中间状态**（数据副本间短暂不一致） |
| **E** | Eventually Consistent **最终一致性** | 经过一段时间后，数据**最终会一致** |

> 🔴 **必背**：
> - **ACID 是传统事务的"强一致"，BASE 是分布式的"最终一致"**。
> - **BASE = 对 CAP 中 AP 的补充**，核心是"**牺牲强一致换取高可用**"。

### 一致性模型（由强到弱）

```
强一致性 → 顺序一致性 → 因果一致性 → 会话一致性 → 单调读一致性 → 最终一致性
```
- **强一致性**：写完立即可读
- **最终一致性**：允许短暂不一致，最终收敛一致（**DNS、缓存、主从复制**）

## 1.3 分布式事务方案（🔴 必考）

| 方案 | 机制 | 一致性 | 优点 | 缺点 | 适用 |
|------|------|:------:|------|------|------|
| **2PC（两阶段提交）** | ① 准备阶段（投票：各参与者执行但不提交）<br>② 提交/回滚阶段 | 强一致 | 简单、保证 ACID | **同步阻塞**（资源锁定）<br>**协调者单点故障**<br>**数据不一致**（二阶段部分失败） | 传统数据库分布式事务 |
| **3PC（三阶段提交）** | CanCommit → PreCommit → DoCommit | 强一致 | 解决 2PC 的**阻塞**问题（引入超时机制） | 仍可能**数据不一致**；网络开销大 | 较少用 |
| **TCC** | **Try（预留资源）→ Confirm（确认）→ Cancel（取消）** | 最终一致（近强一致） | **性能好**，不锁数据库 | **对业务侵入大**（每个操作要写三个方法） | 金融、支付 |
| **Saga** | 长事务拆成多个本地事务，每个有**补偿操作**；失败则**反向补偿** | 最终一致 | 适合**长流程** | 无隔离性；补偿逻辑复杂 | 订单、旅行预订 |
| **本地消息表** | 业务与消息写入**同一个本地事务**，异步确保送达 | 最终一致 | 简单可靠 | 消息表与业务耦合 | 通用 |
| **MQ 事务消息** | 半消息 → 本地事务 → 提交/回滚 → 回查（RocketMQ） | 最终一致 | 解耦、可靠 | 依赖 MQ 能力 | 通用 |
| **最大努力通知** | 反复重试 + 对账 | 最终一致 | 简单 | 一致性最弱 | 通知类（如支付回调） |

> 🔴 **必背对比**：
> - **2PC 的核心缺点**：**同步阻塞 + 协调者单点 + 二阶段数据不一致**
> - **TCC 的核心代价**：**业务侵入大**（要写 Try/Confirm/Cancel）
> - **Saga 适用长事务**，靠**补偿**回滚
> - 主流开源实现：**Seata**（支持 AT/TCC/Saga/XA 模式）

## 1.4 共识算法

| 算法 | 特点 | 应用 |
|------|------|------|
| **Paxos** | 经典但**难理解难实现**；Basic Paxos / Multi-Paxos | 理论基础 |
| **Raft** | **易理解**（分解为**Leader 选举 + 日志复制 + 安全性**三个子问题） | **etcd**、Consul、TiDB、Nacos（CP 模式） |
| **ZAB** | ZooKeeper 专用，类似 Raft | **ZooKeeper** |
| **Gossip** |  Epidemic 协议，去中心化，最终一致 | Redis Cluster、Cassandra |

> 🔴 **必背**：
> - **Raft 的三个子问题**：**Leader 选举、日志复制、安全性**
> - **Raft 需要「多数派」（> N/2）存活才能工作** → 集群节点数通常取**奇数**（3、5、7）
> - **ZooKeeper 用 ZAB；etcd 用 Raft**
> - 需要多数派 → 3 节点容忍 1 台故障，5 节点容忍 2 台

## 1.5 分布式基础设施

| 技术 | 要点 |
|------|------|
| **分布式 ID** | **UUID**（无序，索引性能差）；**数据库号段**；**Redis INCR**；**雪花算法 Snowflake**（64 位 = 1符号位 + 41时间戳 + 10机器位 + 12序列号，**趋势递增**，需解决**时钟回拨**问题） |
| **分布式锁** | **Redis**：`SET key value NX PX 30000`（加锁原子性）+ **Lua 脚本解锁**（防误删，先比对 value）+ **看门狗续期**（Redisson）；**ZooKeeper**：临时顺序节点 |
| **分布式缓存** | 本地缓存（Caffeine）+ 分布式缓存（Redis）多级架构；缓存三兄弟见下 |
| **一致性 Hash** | 解决"节点变化时大量 key 重新映射"问题；引入**虚拟节点**解决**数据倾斜** |
| **负载均衡** | **L4（传输层，如 LVS，基于 IP+端口）** vs **L7（应用层，如 Nginx，基于 URL/内容）**；算法：轮询、加权轮询、最小连接、一致性 Hash |

### 缓存三兄弟（🔴 必考）

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| **缓存穿透** | 查询**根本不存在**的数据 → 每次都打到 DB | **布隆过滤器**、**缓存空值**（设短过期）、参数校验、接口限流 |
| **缓存击穿** | **单个热点 key** 过期瞬间，海量并发打到 DB | **互斥锁（分布式锁）**、**逻辑过期**（永不过期 + 后台异步更新）、热点数据预热 |
| **缓存雪崩** | **大批 key 同时过期** 或 **缓存服务宕机** → DB 压力骤增甚至崩溃 | **过期时间加随机值**、**多级缓存**、**Redis 集群高可用**（哨兵/Cluster）、**熔断降级**、限流 |

> 🔴 **必背**：**布隆过滤器"可能有误判（假阳性），但绝不会漏判（假阴性）"**。

### 缓存一致性策略

| 策略 | 做法 | 评价 |
|------|------|------|
| **Cache Aside（旁路缓存）** | 读：先查缓存，命中返回；未命中查 DB 并回写缓存<br>写：**先更新 DB，再删除缓存** | **最常用**，推荐 |
| Read/Write Through | 应用只跟缓存交互，缓存负责写 DB | 实现复杂 |
| Write Behind | 只写缓存，异步批量刷 DB | 性能好，可能丢数据 |

> 🔴 **必背**：**Cache Aside 模式下，写操作应该是「先更新数据库，再删除缓存」**（不是更新缓存！）。原因：更新缓存容易产生并发下的脏数据，且删除更轻量。

# 第 2 章 · 微服务架构

## 2.1 核心特征与组件

| 组件 | 作用 | 典型产品 |
|------|------|---------|
| **注册中心** | 服务注册与发现、健康检查 | Nacos、Eureka、Consul、ZooKeeper、etcd |
| **配置中心** | 集中管理配置，动态推送 | Nacos、Apollo、Spring Cloud Config |
| **API 网关** | **统一入口**：路由、认证、限流、日志、跨域 | Kong、Spring Cloud Gateway、APISIX |
| **服务调用** | 远程调用 | **OpenFeign**、gRPC、Dubbo |
| **负载均衡** | 客户端/服务端负载 | Ribbon、LoadBalancer |
| **熔断降级** | 防止**雪崩效应** | **Sentinel**、Hystrix、Resilience4j |
| **链路追踪** | 分布式调用链追踪 | **SkyWalking**、Zipkin、Jaeger |
| **限流** | 保护系统 | Sentinel（**令牌桶/漏桶/滑动窗口**） |

## 2.2 DDD 与微服务拆分（近年热点）

| 概念 | 含义 |
|------|------|
| **限界上下文（Bounded Context）** | 领域模型的**边界**，一个限界上下文 ≈ **一个微服务**（拆分的标准答案） |
| **聚合（Aggregate）/ 聚合根（Aggregate Root）** | 一致性边界；**聚合根是聚合的对外唯一入口** |
| **领域事件（Domain Event）** | 领域内发生的重要事件，用于**跨服务最终一致** |
| **实体 vs 值对象** | 实体有**唯一标识**、有生命周期；值对象**无标识**，只关心属性值 |
| **防腐层（ACL）** | 隔离外部系统（遗留系统）模型对内部的侵蚀 |
| **CQRS** | **命令查询职责分离**：写模型和读模型分离 |
| **事件溯源（Event Sourcing）** | 不存当前状态，存**事件序列**，状态由事件重放得到 |

> 🔴 **必背**：**微服务边界划分的"标准答案" = 按 DDD 的「限界上下文」拆分**。

## 2.3 微服务的问题与对策（案例常考）

| 问题 | 对策 |
|------|------|
| 服务雪崩 | 熔断、降级、限流、超时控制、舱壁隔离（线程池隔离） |
| 分布式事务 | Seata（AT/TCC/Saga）、最终一致性、消息事务 |
| 配置分散 | 配置中心 |
| 故障定位难 | **可观测性三支柱** |
| 服务依赖复杂 | 服务网格（Service Mesh）、依赖治理 |

### 可观测性三支柱（🔴 必背）

| 支柱 | 作用 | 工具 |
|------|------|------|
| **Logging 日志** | 记录**离散事件**（发生了什么） | ELK、Loki |
| **Metrics 指标** | **可聚合的数值**（趋势、告警） | Prometheus + Grafana |
| **Tracing 链路追踪** | **请求在多个服务间的完整路径**（一次请求经过哪些服务、各耗时多少） | SkyWalking、Jaeger |

## 2.4 12-Factor（云原生十二要素，云原生化改造的踩分点）

> 记住最常考的 6 条即可：
1. **基准代码**：一份代码库，多份部署
2. **依赖**：显式声明并隔离依赖
3. **配置**：**配置存储到环境变量/配置中心**（**配置外部化**，不写进代码）
4. **后端服务**：把后端服务（DB、MQ）当作**附加资源**
5. **进程**：**无状态**运行（状态外置到数据库/缓存）
6. **日志**：把日志当作**事件流**（输出到 stdout，由平台收集）
> 其他：构建/发布/运行严格分离、端口绑定、并发（通过进程模型扩展）、易处理（快速启动与优雅终止）、开发环境与线上等价、管理任务

> 🔴 **必背**：**无状态化 + 配置外部化 + 日志事件流** 是云原生改造的三大关键词。

# 第 3 章 · 消息队列

## 3.1 三大核心作用

| 作用 | 说明 | 例子 |
|------|------|------|
| **解耦** | 生产者不需要知道消费者 | 订单系统发消息，库存/物流/积分各自订阅 |
| **异步** | 非关键路径异步化，**降低响应时间** | 下单后异步发短信、发券 |
| **削峰填谷** | 缓冲突发流量，保护下游 | 秒杀场景，请求先入队，后端按能力消费 |

## 3.2 使用 MQ 的代价（案例常考）

- **系统可用性降低**（MQ 挂了，整条链路受影响）
- **系统复杂度提高**（要处理**重复消费、消息丢失、顺序性、积压**）
- **一致性问题**（异步带来的数据不一致）

## 3.3 三高问题与对策（🔴 必考）

| 问题 | 原因 | 对策 |
|------|------|------|
| **消息丢失** | ① 生产者发送失败 ② MQ 宕机未持久化 ③ 消费者未处理完就确认 | ① **生产者确认机制（Confirm）** + 失败重试<br>② **MQ 持久化**（消息落盘）+ 集群<br>③ **消费者手动 ACK**（处理完再确认） |
| **重复消费** | 网络重传、消费者 ACK 失败重试 | **消费端做幂等**（唯一 ID + Redis 去重表 / 数据库唯一索引 / 乐观锁） |
| **顺序性** | 多分区多消费者并发 | **同一 Key 路由到同一分区**（Kafka）；**单消费者单队列**（RabbitMQ） |
| **消息积压** | 消费速度 < 生产速度 | 临时扩容消费者、批量消费、优化消费逻辑、死信队列处理异常消息 |

> 🔴 **必背口诀**：**"丢（失）靠确认加持久，重（复）靠幂等，序靠同 Key。"**

## 3.4 主流 MQ 对比

| 维度 | **Kafka** | **RabbitMQ** | **RocketMQ** |
|------|-----------|--------------|--------------|
| 定位 | **高吞吐**日志/流处理 | **功能丰富**、企业级消息 | 阿里开源，兼顾吞吐与功能 |
| 吞吐量 | **最高**（百万级 TPS） | 万级 | 十万级 |
| 延迟 | 较高 | **最低**（微秒级） | 低 |
| 模型 | **发布-订阅**（分区） | 交换机/队列（路由丰富） | 发布-订阅 + 队列 |
| 特色 | 消息可**重放**、流处理（Kafka Streams） | 灵活的路由、死信队列、优先级队列 | **事务消息**、**定时/延迟消息**、消息轨迹 |
| 适用 | 日志采集、大数据、流计算 | 业务解耦、复杂路由 | 电商、金融（事务消息） |

# 第 4 章 · 云原生架构

## 4.1 云原生的定义与核心要素

> **一句话**：云原生 = **为云而生**的应用，**充分利用云计算的弹性、分布式、按需**优势。
> 四大要素：**微服务 + 容器化 + DevOps + 持续交付**。

## 4.2 容器与 Kubernetes

| 概念 | 说明 |
|------|------|
| **容器 vs 虚拟机** | 容器**共享宿主机操作系统内核**，**轻量、秒级启动**；虚拟机有独立 Guest OS，**重、隔离性强** |
| **Docker** | 镜像（分层、只读模板）+ 容器（运行实例）+ 仓库（Registry） |
| **K8s 核心对象** | **Pod**（最小调度单元，可含多个容器）、**Deployment**（无状态应用）、**StatefulSet**（有状态）、**DaemonSet**（每节点一个）、**Job/CronJob**（任务）<br>**Service**（服务发现与负载均衡）、**Ingress**（外部入口）、**ConfigMap/Secret**（配置/密钥）、**PVC/PV**（存储） |
| **K8s 能力** | **自动伸缩（HPA）**、自愈（重启/重建）、滚动更新与回滚、服务发现、配置管理、存储编排 |

> 🔴 **必背**：**K8s 的最小调度/部署单元是 Pod**（不是容器、不是 Node）。

## 4.3 Service Mesh（服务网格）

> **一句话**：把微服务的**通信、治理能力（熔断、限流、追踪、mTLS）**从业务代码抽离到**基础设施层（Sidecar 代理）**。

| 组成 | 说明 |
|------|------|
| **数据平面** | **Sidecar 代理**（**Envoy**），接管服务的所有进出流量 |
| **控制平面** | 管理和下发策略（**Istio** 的 Istiod） |

> 🔴 **必背**：
> - **Service Mesh 的核心机制 = Sidecar 模式**
> - 价值：**业务代码零侵入**；统一治理；多语言支持
> - 代价：**增加网络跳数 → 延迟增加**；运维复杂度高

## 4.4 Serverless

| 形态 | 含义 | 例子 |
|------|------|------|
| **FaaS** | 函数即服务，**按调用次数和执行时间付费** | AWS Lambda、阿里云函数计算 |
| **BaaS** | 后端即服务（数据库、存储、认证等托管服务） | Firebase、云数据库 |

- **优点**：免运维、**按需付费**、**自动弹性伸缩**
- **缺点**：**冷启动延迟**、不适合**长时运行任务**、**厂商锁定**、调试困难、状态管理受限

## 4.5 DevOps 与 CI/CD

| 概念 | 含义 |
|------|------|
| **CI（持续集成）** | 频繁合并代码 → **自动构建 → 自动测试** → 快速发现集成问题 |
| **CD** | **持续交付**（可随时发布，手动触发）+ **持续部署**（自动发布到生产） |
| **IaC** | **基础设施即代码**（Terraform、Ansible） |
| **GitOps** | 以 Git 为唯一事实源，声明式部署（ArgoCD） |

1. **服务化**（微服务/小服务）

3. **可观测性**（日志/指标/链路）

5. **自动化**（CI/CD、IaC）
6. **零信任安全**
7. **无状态与配置外部化**

# 第 5 章 · 大数据架构

## 5.1 Lambda vs Kappa（🔴 必考）

| 维度 | **Lambda 架构** | **Kappa 架构** |
|------|----------------|---------------|
| 结构 | **三层**：批处理层（Batch Layer）+ 加速层/流处理层（Speed Layer）+ 服务层（Serving Layer） | **两层**：**只有流处理层 + 服务层** |
| 核心思想 | **批流并存**，批层保证**准确**，流层保证**实时** | **一切皆流**，用**重放（Replay）**代替批处理 |
| 优点 | 兼顾**准确 + 实时**；容错性好 | **架构简单**，只需维护一套代码 |
| 缺点 | **维护两套代码（批 + 流）**，复杂度高、易不一致 | 对消息队列**重放能力**要求高；历史数据回溯成本高 |
| 适用 | 需**高准确 + 低延迟**并有复杂离线计算 | 实时性要求高、逻辑不频繁变更 |

> 🔴 **必背**：
> - **Lambda = 批处理层 + 速度层 + 服务层**（三层）
> - **Kappa = 去掉批处理层，用「流处理 + 消息重放」替代**（两层）
> - 答题话术：**"Lambda 的代价是维护两套代码；Kappa 用消息重放解决一致性问题，但对消息队列存储与重放能力要求高"**

## 5.2 核心技术栈

| 层次 | 技术 |
|------|------|
| **采集** | Flume、Logstash、Canal（binlog 同步）、DataX |
| **存储** | HDFS、HBase、对象存储（S3/OSS）、数据湖（Iceberg、Hudi、Delta Lake） |
| **批处理** | **MapReduce**（慢）、**Spark**（内存计算，快 **10~100 倍**）、Hive（SQL on Hadoop） |
| **流处理** | **Flink**（**真流式、低延迟、事件时间 + Watermark 处理乱序**）、Spark Streaming（**微批**）、Kafka Streams |
| **OLAP** | ClickHouse、Doris、Druid、Kylin（预计算） |
| **调度** | DolphinScheduler、Airflow、Azkaban |

> 🔴 **必背**：
> - **Flink = 真正的流式处理（逐条）**；**Spark Streaming = 微批处理（准实时）**
> - **Flink 处理乱序数据的机制 = 事件时间（Event Time）+ Watermark（水位线）**

## 5.3 数据仓库与维度建模

| 概念 | 说明 |
|------|------|
| **事实表** | 存**业务度量值**（如销售额、数量）；三种类型：**事务事实表、周期快照事实表、累积快照事实表** |
| **维表** | 存**描述性属性**（如时间、地区、商品、客户） |
| **星型模型** | 事实表 + **单层**维表（**维表未规范化**，有冗余）；**查询快**，最常用 |
| **雪花模型** | 维表**进一步规范化**（多级维表）；**省空间**，但 Join 多、查询慢 |
| **分层架构** | **ODS（原始数据层）→ DWD（明细层）→ DWS（汇总层）→ ADS（应用层/数据集市）** |
| **数据湖 vs 数据仓库** | 数据湖存**原始、多格式**（结构化/半结构化/非结构化），**Schema-on-Read**；数据仓库存**已清洗建模**的数据，**Schema-on-Write** |
| **湖仓一体**（Lakehouse） | 结合两者（Delta Lake / Iceberg / Hudi） |

> 🔴 **必背**：**星型模型（冗余、查询快） vs 雪花模型（规范、省空间）**；**数据湖 = Schema-on-Read，数仓 = Schema-on-Write**。

# 第 6 章 · AI 系统架构（2026 新增重点）

> ⚠️ 2026 新大纲明确新增「AI 系统架构设计」「大模型部署策略」「智能系统性能优化」三个专题，**占比约 25%**，务必重点准备。

## 6.1 基础概念

| 概念 | 说明 |
|------|------|
| **训练（Training）** | 用大量数据学习模型参数，**计算密集**（GPU 集群） |
| **推理（Inference）** | 用训练好的模型做预测，**延迟敏感** |
| **Token** | 模型处理文本的基本单位（中英文切分不同） |
| **Embedding** | 把文本/图像映射成**高维向量**，便于语义相似度计算 |
| **微调（Fine-tuning）** | 在预训练模型基础上用**特定领域数据**继续训练 |
| **提示工程（Prompt Engineering）** | 通过设计输入提示词引导模型输出 |
| **幻觉（Hallucination）** | 模型生成**看似合理但事实错误**的内容 |
| **温度（Temperature）** | 控制生成随机性，**越高越发散，越低越确定** |

## 6.2 RAG（检索增强生成）架构（🔴 核心考点）

> **解决什么问题**：LLM 只知道训练数据里的东西 → **知识过时 + 幻觉 + 无法接入私有数据**。

```
【离线·索引阶段】
  知识文档 → 切分（Chunking）→ 向量化（Embedding）→ 存入向量数据库

【在线·检索生成阶段】
  用户提问 → 问题向量化 → 向量库相似度检索（Top-K）
           → （可选）Rerank 重排序
           → 检索结果 + 问题 + 提示词模板 拼装 Prompt
           → LLM 生成答案 → 返回（附引用来源）
```

| 关键点 | 说明 |
|--------|------|
| **为什么需要 RAG** | 解决**知识时效性**、**幻觉**、**私有数据接入**、**可溯源** |
| **文档切分** | chunk 太大 → 噪声多；太小 → 语义不完整；常用 **固定大小 + 重叠** 或 **语义切分** |
| **向量数据库** | Faiss、Milvus、Pinecone、Weaviate、Qdrant、pgvector |
| **混合检索** | **向量检索（语义）+ 关键词检索（BM25）** 结合，提高召回 |
| **Rerank** | 用**交叉编码器（Cross-Encoder）**对召回结果精排 |

### RAG vs 微调（🔴 必考对比）

| 维度 | **RAG** | **微调（Fine-tuning）** |
|------|---------|------------------------|
| 本质 | **外挂知识库**（不改模型参数） | **改模型参数** |
| 知识更新 | **实时**（改文档即可） | 需重新训练，**成本高、周期长** |
| 幻觉 | 显著减少（有依据） | 不能根本解决 |
| 成本 | 低（只需向量库） | **高**（需 GPU 与数据标注） |
| 适用场景 | **知识问答、文档助手、客服** | **改变模型风格/格式、特定任务能力** |
| 可解释性 | **好**（可给出引用来源） | 差（黑盒） |

> 🔴 **必背**：**"要更新知识 → RAG；要改变行为/风格 → 微调"**。

## 6.3 Agent（智能体）

> **一句话**：**Agent = LLM（大脑）+ 规划（Planning）+ 工具（Tools）+ 记忆（Memory）**。

| 组成 | 说明 |
|------|------|
| **规划** | 任务分解、思维链（**Chain of Thought**）、ReAct（**Reasoning + Acting**） |
| **记忆** | 短期记忆（上下文窗口）、长期记忆（向量库） |
| **工具调用** | **Function Calling / Tool Use**：让模型调用外部 API、数据库、搜索 |
| **多 Agent 协作** | 多个角色分工协作（如产品经理 Agent + 开发 Agent + 测试 Agent） |

> 📌 **MCP（Model Context Protocol）**：标准化大模型与外部数据源/工具连接的协议（新兴热点）。

## 6.4 大模型部署策略（2026 新增专题）

| 策略 | 说明 | 适用 |
|------|------|------|
| **云端 API 调用** | 直接调大模型厂商 API | 快速验证、无算力、非敏感数据 |
| **私有化部署** | 模型部署在**自有服务器/专有云** | **数据敏感**、需合规、金融/政务/医疗 |
| **边缘/端侧部署** | 小模型部署在设备端（手机、IoT） | **低延迟、离线可用、隐私** |
| **混合部署** | 端侧小模型处理常规，复杂任务上云 | 成本与体验平衡 |

### 模型优化技术（性能优化专题）

| 技术 | 原理 | 效果 |
|------|------|------|
| **量化（Quantization）** | 降低权重精度（FP16 → **INT8 / INT4**） | **显存↓、推理↑**，精度略降 |
| **蒸馏（Distillation）** | 用大模型（教师）教小模型（学生） | **模型变小、变快**，能力部分保留 |
| **剪枝（Pruning）** | 去掉不重要的权重/神经元 | 模型变小、稀疏化 |
| **KV Cache** | 缓存 Attention 的 K/V，避免重复计算 | **显著降低自回归生成延迟**，显存占用↑ |
| **Continuous Batching** | 动态组批，新请求随时加入批次 | **吞吐量大幅提升** |
| **PagedAttention** | 分页管理 KV Cache（vLLM） | 显存碎片↓、吞吐↑ |
| **投机解码（Speculative Decoding）** | 小模型草稿 + 大模型并行验证 | **降低生成延迟** |

> 🔴 **必背**：**量化**（降精度换速度）、**蒸馏**（大模型教小模型）、**KV Cache**（缓存避免重复计算）是性能优化三大关键词。

## 6.5 智能系统性能指标（与质量属性绑定）

| 指标 | 全称 | 含义 | 对应质量属性 |
|------|------|------|-------------|
| **TTFT** | Time To First Token | **首 Token 延迟**（用户感知的"响应速度"） | 性能 |
| **TPOT** | Time Per Output Token | 每个输出 Token 的时间（**生成速度**） | 性能 |
| **端到端延迟** | End-to-End Latency | 完整请求到完整响应 | 性能 |
| **吞吐量** | Throughput | **tokens/s** 或 **请求数/s** | 性能 |
| **并发数** | Concurrency | 同时处理的请求数 | 性能 |
| **准确率 / 幻觉率** | — | 回答正确性 | **可靠性 / 安全性** |
| **可解释性** | Explainability | 能否说明"为什么这么答" | **可解释性（新增质量属性）** |

> 🔴 **应试要点**：2026 大纲明确要求**把 AI 需求（推理延迟、模型准确率、可解释性）与质量属性（性能、可靠性、安全性）结合**。
> 答题模板：**"AI 系统的性能需求不能只用 QPS 描述，还应包括 TTFT（首 token 延迟）与 TPOT（生成速度）；其可靠性需求体现为模型准确率与幻觉率的约束，并需通过 RAG + 人工审核 + 内容安全过滤来保障。"**

# 第 8 章 · 区块链

| 概念 | 说明 |
|------|------|
| **本质** | **去中心化的分布式账本**，数据**不可篡改、可追溯** |
| **核心特性** | 去中心化、**不可篡改**、**可追溯**、**共识信任**、**智能合约** |
| **区块结构** | 区块头（**版本号、前一区块哈希、Merkle 根、时间戳、难度、Nonce**）+ 区块体（交易列表） |
| **链式结构** | 每个区块包含**前一区块的哈希** → 改任一区块，后续全部失效 |

## 共识机制（🔴 必考对比）

| 机制 | 原理 | 优点 | 缺点 | 应用 |
|------|------|------|------|------|
| **PoW**（工作量证明） | **算力竞赛**（挖矿） | 安全、去中心化程度高 | **耗电、慢**（比特币 10 分钟/块） | **比特币**、早期以太坊 |
| **PoS**（权益证明） | 按**持有币量与时间**决定出块权 | **节能、快** | 富者愈富；安全模型不同 | **以太坊 2.0** |
| **DPoS**（委托权益证明） | 持币者**投票选出**少量见证人出块 | **极快**（秒级） | 中心化程度高 | EOS、TRON |
| **PBFT**（实用拜占庭容错） | 多轮投票，容忍 **≤1/3 恶意节点** | **低延迟、高吞吐、无需挖矿** | 节点数不能太多 | **联盟链**（Hyperledger Fabric、FISCO BCOS） |

> 🔴 **必背**：
> - **公有链（比特币/以太坊）多用 PoW/PoS；联盟链（Fabric）多用 PBFT/Raft**
> - **PoW 最大缺点是"能耗高、性能低"**
> - **PBFT 能容忍不超过 1/3 的恶意节点**（即总节点数 ≥ 3f+1）

# 第 9 章 · 安全架构

## 9.1 安全五要素（信息安全的基本属性）

| 要素 | 含义 |
|------|------|
| **机密性（Confidentiality）** | 信息**不被泄露**给未授权者（→ **加密**） |
| **完整性（Integrity）** | 信息**不被篡改**（→ **消息摘要/哈希、数字签名**） |
| **可用性（Availability）** | 授权者**随时可用**（→ 冗余、抗 DDoS） |
| **可控性** | 对信息的传播与内容具有控制能力 |
| **不可否认性（Non-repudiation）** | 行为不可抵赖（→ **数字签名**） |

> 🔴 **必背**：**数字签名保证「完整性 + 不可否认性」；加密保证「机密性」**。

## 9.2 密码学基础

| 类型 | 特点 | 算法 |
|------|------|------|
| **对称加密** | **同一密钥**，快，适合**大量数据** | **DES（56位）、3DES、AES（128/192/256）、RC4、SM4** |
| **非对称加密** | **公钥加密，私钥解密**，慢（**慢 100~1000 倍**），适合**密钥交换/小数据/签名** | **RSA、ECC、ElGamal、SM2、SM9** |
| **摘要（哈希）** | **不可逆**、定长输出、防篡改 | **MD5（128位）、SHA-1（160位）、SHA-256、SM3（256位）** |

> 🔴 **必背区分**：
> - **加密 ≠ 摘要**：加密**可逆**（能解密），摘要（哈希）**不可逆**
> - **数字签名 = 对摘要用私钥加密**（验证：用公钥解密得到摘要并比对）
> - **数字信封 = 用对称密钥加密数据 + 用接收方公钥加密对称密钥**（兼顾速度与安全）

## 9.3 访问控制模型（🔴 必考）

| 模型 | 核心 | 优点 | 缺点 |
|------|------|------|------|
| **DAC**（自主访问控制） | 资源所有者**自主决定**谁能访问 | 灵活 | 安全性弱 |
| **MAC**（强制访问控制） | 系统按**安全标签/密级**强制控制 | **最安全** | 僵化、不灵活 |
| **RBAC**（基于角色的访问控制） | **用户 → 角色 → 权限** | **最常用**，易管理 | 角色爆炸；无法表达复杂条件 |
| **ABAC**（基于属性的访问控制） | 基于**主体/客体/环境属性**动态决策 | **最灵活、细粒度** | 复杂、性能开销大 |

> 🔴 **必背**：**RBAC 引入"角色"作为中间层，解耦用户与权限**（用户变多、权限变多都不会爆炸）。
> **ABAC 是"动态、细粒度"的**，可根据时间、地点、设备、风险等级等属性决策（**零信任的核心**）。

## 9.4 零信任架构

> **核心理念**：**"从不信任，始终验证"（Never Trust, Always Verify）**。

| 传统边界安全 | 零信任 |
|-------------|--------|
| 内网可信，外网不可信 | **内外网都不可信** |
| 一次认证，长期有效 | **持续验证**（每次访问都验证） |
| 以网络位置为信任依据 | **以身份 + 设备 + 行为 + 环境**为依据 |
| 边界防御（防火墙/VPN） | **微隔离 + 最小权限 + 动态授权** |

> 🔴 **必背关键词**：**持续验证、永不信任、最小权限、微隔离、动态访问控制（多为 ABAC）**。

## 9.5 常见攻击与防护

| 攻击 | 说明 | 防护 |
|------|------|------|
| **SQL 注入** | 把 SQL 拼进输入参数 | **预编译（PreparedStatement）**、参数化查询、输入校验、ORM |
| **XSS 跨站脚本** | 注入恶意脚本到页面执行 | **转义输出**、CSP、HttpOnly Cookie |
| **CSRF 跨站请求伪造** | 诱导用户发起非本意请求 | **Token 校验**、Referer 校验、SameSite Cookie |
| **DDoS** | 海量请求耗尽资源 | **流量清洗、CDN、限流、扩容** |
| **中间人攻击** | 截获通信 | **HTTPS/TLS**、证书校验 |
| **重放攻击** | 重复发送合法请求 | **时间戳 + Nonce + 签名** |
| **暴力破解** | 尝试大量密码 | **验证码、锁定策略、限速、多因素认证** |
| **会话劫持** | 窃取 Session | HTTPS、Session 过期、绑定 IP/设备 |

## 9.6 等级保护 2.0（🔴 必考）

> **标准**：GB/T 22239-2019《网络安全等级保护基本要求》

| 等级 | 名称（等保 2.0 监管强度） | 适用 |
|:----:|--------------------------|------|
| 第一级 | **自主保护级** | 一般系统，损害公民/法人权益 |
| 第二级 | **指导保护级** | 损害公民/法人**严重**权益或社会秩序 |
| 第三级 | **监督保护级** | **社会秩序、公共利益严重损害**（多数企业系统的定级目标） |
| 第四级 | **强制保护级** | **国家安全**严重损害 |
| 第五级 | **专控保护级** | 国家安全**特别严重**损害 |

> 📌 **补充**：GB 17859-1999《计算机信息系统安全保护等级划分准则》的五级名称为：**用户自主保护级、系统审计保护级、安全标记保护级、结构化保护级、访问验证保护级**。（两套名称容易混淆，选择题注意题干引用的是哪个标准）

**等保 2.0 的主要变化**
- 从"信息系统安全"扩展到"**网络安全**"
- 新增对象：**云计算、移动互联、物联网、工业控制系统、大数据**
- 强调**"一个中心，三重防护"**：**安全管理中心** + **安全计算环境 + 安全区域边界 + 安全通信网络**

> 🔴 **必背**：**"一个中心（安全管理中心），三重防护（计算环境 / 区域边界 / 通信网络）"**。

## 9.7 数据脱敏与隐私计算

| 技术 | 说明 |
|------|------|
| **数据脱敏** | 对敏感数据变形（掩码、加密、替换、泛化），用于**非生产环境/测试** |

| **可信执行环境（TEE）** | 硬件级安全隔离 enclave |

<details>
<summary>参考答案</summary>

1. 因为**网络分区（P）在分布式系统中必然发生**，无法避免。所以实际只能在 **C（一致性）和 A（可用性）** 之间取舍，即 **CP 或 AP**
2. **ZooKeeper = CP**；**Eureka = AP**
3. **① 同步阻塞**（参与者持有资源锁，等待协调者）；**② 协调者单点故障**；**③ 二阶段提交时网络失败会导致数据不一致**
4. - **穿透**：查不存在的 key → 布隆过滤器 / 缓存空值 / 参数校验
   - **击穿**：单个热点 key 过期瞬间高并发 → 互斥锁 / 逻辑过期 / 热点预热
   - **雪崩**：大批 key 同时过期或缓存集群宕机 → 过期时间加随机值 / 多级缓存 / 集群高可用 / 熔断降级
5. **不会漏判（无假阴性）**，但**可能误判（有假阳性）**
6. 按 **DDD 的限界上下文（Bounded Context）** 划分
7. **日志（Logging）+ 指标（Metrics）+ 链路追踪（Tracing）**
8. - **不丢失**：生产者 Confirm 确认 + 消息持久化 + 消费者手动 ACK
   - **不重复消费**：**消费端做幂等**（唯一 ID + 去重表 / 数据库唯一索引 / 乐观锁）
9. **Kafka**：**吞吐量极高**（百万级），适日志与流处理；**RabbitMQ**：**延迟极低、路由灵活**，适业务解耦
10. **Sidecar 模式**（在每个服务旁部署代理 Envoy 接管流量，治理能力下沉到基础设施层）
11. **Lambda = 批处理层 + 速度层 + 服务层（三层，维护两套代码）；Kappa = 只有流处理层 + 服务层（两层），用「消息队列重放」替代批处理**
12. **Flink 是真正的逐条流式处理；Spark Streaming 是微批处理（准实时）**。Flink 用 **事件时间（Event Time）+ Watermark（水位线）** 处理乱序
13. **知识需要频繁更新、需要引用来源、要接私有数据 → RAG**；**需要改变模型的行为风格/输出格式/特定任务能力 → 微调**
14. **RBAC = 用户→角色→权限**（静态、基于角色）；**ABAC = 基于主体/客体/环境属性动态决策**（动态、细粒度，零信任的基础）。**零信任 = 从不信任、始终验证、最小权限、微隔离**
15. **一个中心 = 安全管理中心**；**三重防护 = 安全计算环境 + 安全区域边界 + 安全通信网络**

</details>
