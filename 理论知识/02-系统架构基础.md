# 第 1 章 · 架构是什么

## 1.1 一句话定义

> **软件架构 = 构件（Component）+ 连接件（Connector）+ 约束（Constraint）+ 它们的组合拓扑。**

| 要素 | 生活比喻 | 软件含义 |
|------|---------|---------|
| **构件** | 房子的**房间/墙/梁** | 可独立部署、可替换的功能单元（模块、服务、类库、数据库） |
| **连接件** | **门、走廊、管道** | 构件之间的交互机制（函数调用、消息、RPC、事件、共享数据） |
| **约束** | **建筑规范**（承重、防火） | 必须遵守的规则（协议、接口规范、性能要求） |

## 1.2 4+1 视图模型（必考，记名字+对应关系）

| 视图 | 关注者 | 关注内容 |
|------|--------|---------|
| **逻辑视图** | 最终用户 | 功能需求：系统提供给用户什么（类图、对象模型） |
| **开发视图**（实现视图） | 程序员 | 软件模块的组织管理（包、子系统、分层） |
| **进程视图** | 系统集成人员 | 运行时特性：并发、同步、性能、伸缩性 |
| **物理视图** | 系统工程师 | 软件到硬件的映射：部署、网络拓扑 |
| **+1：场景（用例）视图** | 全部 | 用典型用例把前四个视图串起来（**架构设计的驱动力**） |

> 🔴 **口诀**：**"逻辑管功能，开发管代码，进程管运行，物理管部署，场景串全场。"**

## 1.3 架构演化的典型阶段（了解即可）

```
单体应用 → 垂直拆分（按业务线）→ 分布式服务（RPC/SOA/ESB）
        → 微服务 → 服务网格（Service Mesh）→ 云原生 / Serverless
```

# 第 2 章 · 架构风格（核心，必考）

> 🎯 **复习策略**：架构风格每年**必考 2~4 题**，考法是**给一段场景描述，问你属于哪种风格**，或**问某风格的优缺点/适用场景**。
> 所以记忆重点不是定义，而是 **"识别特征" + "一句话优点" + "一句话缺点"**。

## 2.1 五大经典风格族（这是分类骨架，必须先记住）

```
软件架构风格
│
├─ ① 数据流风格      → 批处理序列、管道-过滤器
├─ ② 调用/返回风格    → 主程序-子程序、面向对象、层次结构
├─ ③ 独立构件风格    → 进程通信、事件驱动（隐式调用）
├─ ④ 虚拟机风格      → 解释器、基于规则的系统
├─ ⑤ 仓库（数据中心）风格 → 数据库系统、黑板系统、超文本系统
│
└─ 其他：C2、REST、微服务、Serverless、事件溯源……
```

> 🔴 **口诀**：**"数调独虚仓"**（数=数据流，调=调用返回，独=独立构件，虚=虚拟机，仓=仓库）→ 谐音 **"树掉独须藏"**

## 2.2 逐风格速记（重点记：识别特征 + 优点 + 缺点 + 典型例子）

### ① 数据流风格

| 风格 | 识别特征 | 优点 | 缺点 | 典型例子 |
|------|---------|------|------|---------|
| **批处理序列** | 一个步骤**全部处理完**才传给下一步；每步是独立程序 | 简单；适合批量数据 | 无交互、延迟高 | 离线报表、ETL |
| **管道-过滤器** | 数据像水流一样经过一串"过滤器"，每个只做一件事**流式**处理 | 构件可复用、可重组；支持并发 | **不适合交互式**；难共享全局状态；数据格式转换开销 | **编译器**（词法→语法→语义→代码生成）、Shell 管道、日志处理 |

> 🧠 **比喻**：**工厂流水线**。原料从一端进，经过切割、打磨、喷漆，成品从另一端出。每个工位只干一件事。

> 🔴 **必背**：管道-过滤器的**典型例子是编译器**；它的**致命缺点是"不适合交互式应用"**。

### ② 调用/返回风格

| 风格 | 识别特征 | 优点 | 缺点 | 典型例子 |
|------|---------|------|------|---------|
| **主程序-子程序** | 单线程控制，主程序调用子程序 | 简单直观 | 紧耦合；难复用 | 早期结构化程序 |
| **面向对象** | 数据 + 操作封装成对象，通过**消息**交互 | 高内聚低耦合、易复用、易扩展 | 对象标识改变会影响调用方；分布式调用开销 | 绝大多数业务系统 |
| **层次结构（分层）** | 分成若干层，**上层调用下层**，不能跨层 | 支持复用、易维护、易替换某层 | 性能损耗（层层转发）；难确定层次粒度 | **OSI 七层**、MVC、经典三层（表现/业务/数据） |

> 🧠 **比喻**：分层架构 = **公司层级汇报**，员工 → 主管 → 总监 → 老板，不能越级。

> 🔴 **分层架构必背**：
> - 优点：**支持基于抽象程度递增的系统设计，容易扩展，支持复用，支持标准化**
> - 缺点：**并非所有系统都容易分层**；**跨层调用会破坏架构**（出现"性能倒挂"时可能需要"跨层"权衡）

### ③ 独立构件风格

| 风格 | 识别特征 | 优点 | 缺点 | 典型例子 |
|------|---------|------|------|---------|
| **进程通信** | 独立的进程通过**消息传递**显式交互 | 分布部署、容错 | 显式调用，耦合仍存在 | 分布式系统、RPC |
| **事件驱动（隐式调用）** | 构件**不直接调用**对方，而是**触发/广播事件**；谁知道、谁响应，触发者**不知道** | **强解耦**、易扩展（加新订阅者无需改原系统）、易复用 | 触发者**无法控制**处理顺序与结果；**正确性难保证**；调试困难 | **GUI 事件**、消息中间件（发布-订阅）、**观察者模式**、事件总线 |

> 🧠 **比喻**：**小区广播喇叭**。喊一嗓子"3 号楼停水"，谁关心谁自己去处理，喊的人根本不知道谁会响应。

> 🔴 **必背**：事件驱动的**核心特征是"构件之间不直接交互，通过事件间接交互"**，关键词是 **"隐式调用"**、**"触发者不知道接收者"**。

### ④ 虚拟机风格

| 风格 | 识别特征 | 优点 | 缺点 | 典型例子 |
|------|---------|------|------|---------|
| **解释器** | 自定义一套"伪代码"，逐条解释执行 | **灵活、可定制化**（用户可自定义规则） | **性能差**（解释执行慢） | **JVM**、脚本引擎、**规则引擎**、工作流引擎、低代码平台 |
| **基于规则的系统** | 知识库 + 规则解释器 + 工作内存，规则形如 `IF…THEN…` | 适合专家系统、决策类 | 规则冲突难管理；性能 | 专家系统、风控引擎、**Drools** |

> 🧠 **比喻**：**同声传译**。你说中文，翻译官逐句翻给外国人听 —— 灵活但慢。

### ⑤ 仓库（数据中心）风格

| 风格 | 识别特征 | 优点 | 缺点 | 典型例子 |
|------|---------|------|------|---------|
| **数据库系统** | 中央**共享数据** + 若干独立处理构件 | 数据集中管理、易保证一致性 | 中央数据结构成为**瓶颈** | 传统 MIS、CRUD 系统 |
| **黑板系统** | 中央黑板（共享知识）+ 多个**独立知识源**，知识源**主动**响应黑板变化、逐步逼近解 | 适合**没有确定解法**的复杂问题；多知识源协同 | 难以建模；**无确定求解策略**；性能差 | **语音识别、图像识别、专家系统、信号处理** |
| 超文本系统 | 网状链接的非线性信息组织 | 灵活 | 易"迷航" | Web、Wiki |

> 🧠 **比喻**：黑板 = **一群专家围着一块黑板**。有人写一个线索，其他人看到后补充，直到得出答案。**没人规定先后顺序**。

> 🔴 **黑板系统必背**：适用于**"无确定性求解策略"的问题**，典型场景是**语音识别、图像识别、模式识别**。
> 这是与"管道-过滤器"最大的区别：管道是**固定流程**，黑板是**灵感的、逐步逼近的**。

### ⑥ 其他常见风格（近年高频）

| 风格 | 核心特征 | 优点 | 缺点 | 适用 |
|------|---------|------|------|------|
| **REST** | 面向**资源**，用 HTTP 动词（GET/POST/PUT/DELETE）操作，**无状态** | 简单、轻量、易缓存、跨平台 | 无状态带来重复数据传输；不适合强事务 | 开放 API、前后端分离 |
| **微服务** | 按**业务能力**拆成小而独立的服务，**独立开发、部署、伸缩、技术异构** | 独立部署、易扩展、团队自治、容错 | **分布式复杂度高**、运维成本高、事务难 | 大型复杂系统、多团队协作 |
| **SOA / ESB** | 服务总线（ESB）做**协议转换、路由、格式转换、编排** | 集成遗留系统；服务复用 | **ESB 容易成为瓶颈和单点**；重、复杂 | 企业内部系统集成 |
| **Serverless** | "函数即服务"，**无需管理服务器**，按调用付费 | 免运维、按需付费、自动伸缩 | **冷启动**延迟；不适合长任务；厂商锁定 | 事件驱动型轻任务、Webhook |
| **C2 风格** | 构件只能通过**连接件**通信，上方请求、下方通知，**无直接依赖** | 强解耦 | 复杂 | GUI 架构 |

> 🔴 **微服务 vs SOA（必考对比）**
> | 维度 | SOA | 微服务 |
> |------|-----|--------|
> | 集成方式 | **ESB（中心化总线）** | **去中心化**（API 网关 + 轻量协议） |
> | 服务粒度 | 粗粒度 | 细粒度 |
> | 通信协议 | 重（SOAP/WS-*） | 轻（REST/gRPC） |
> | 数据存储 | 倾向共享数据库 | **每个服务独立数据库** |
> | 治理 | 集中式治理 | 去中心化治理 |

## 2.3 架构风格选型速判（考试实用）

| 题干关键词 | 选哪个 |
|-----------|--------|
| "数据要依次经过多个处理步骤""流式处理""可重组复用" | **管道-过滤器** |
| "编译器""词法分析→语法分析" | **管道-过滤器** |
| "某个事件发生时要通知多个模块""模块之间不需要互相知道" | **事件驱动（隐式调用）** |
| "语音识别""图像识别""没有确定解法""专家协同" | **黑板系统** |
| "用户可自定义规则""规则引擎""IF-THEN" | **基于规则的系统 / 解释器** |
| "跨平台""解释执行" | **解释器** |
| "分层""只能上层调用下层""MVC""表现层/业务层/数据层" | **层次结构** |
| "数据集中在中央""多模块共享数据" | **仓库 / 数据库系统** |
| "批处理""离线""一次处理完再传给下一步" | **批处理序列** |
| "资源""无状态""HTTP 动词""前后端分离" | **REST** |
| "独立部署""每个服务独立数据库""小而自治" | **微服务** |
| "集成遗留系统""协议转换""服务编排""总线" | **SOA / ESB** |
| "按调用次数付费""不用管服务器""事件触发的短任务" | **Serverless** |

# 第 3 章 · 质量属性与架构战术

## 3.1 六大质量属性（核心，必考）

> 💡 **先建立一个认知**：质量属性 = **衡量架构好坏的尺子**。它不是"功能"（能不能下单），而是"**下这个单要多久、会不会失败、能不能防住攻击、以后加功能好不好加**"。

| 质量属性 | 关注什么 | 典型量化指标 | 典型场景描述 |
|----------|---------|-------------|-------------|
| **性能** (Performance) | 多快、能扛多少 | 响应时间、吞吐量(TPS/QPS)、并发数 | "系统需在 1 秒内响应 95% 的请求" |
| **可用性** (Availability) | 多久能用 | 可用度（几个 9）、MTBF、MTTR | "系统年停机时间不超过 5 分钟" |
| **安全性** (Security) | 防攻击、防泄露 | 认证/授权/审计/加密覆盖率 | "阻止 99% 的未授权访问" |
| **可修改性** (Modifiability) | 改起来难易 | 修改成本、修改耗时 | "新增一种支付方式需 2 人周内完成" |
| **可测试性** (Testability) | 好不好测 | 测试覆盖率、缺陷检出率 | "能在 1 小时内完成回归测试" |
| **易用性** (Usability) | 好不好用 | 学习时间、操作效率、错误率 | "新用户 10 分钟内能完成注册下单" |

> 📌 有的教材还会单列 **可靠性(Reliability)、可移植性、功能性、互操作性**，合称"七大/九大"。
> 🔴 **区分"可用性"与"可靠性"**：
> - **可靠性** = **不发生故障**的能力（强调"不中断"）
> - **可用性** = **可正常使用的时间比例**（允许短暂中断后自动恢复）
> - 例：系统每分钟崩 1 秒 —— **可靠性很差**，但**可用性仍有 98%**。

## 3.2 架构战术（质量属性 → 手段，必考）

> **战术** = "为了达到某个质量属性，架构师可以采用的**具体设计手段**"。案例和选择题都爱考"给出某属性，说出 2~3 个战术"。

| 质量属性 | 常用战术（背 3~4 个就够） |
|----------|--------------------------|
| **性能** | **资源需求**：减少处理量（缓存、增量更新）、限制待处理事件（限流、队列）、控制采样频率<br>**资源管理**：并发（多线程）、增加可用资源（扩容、分片）<br>**资源仲裁**：调度策略（优先级队列、FIFO） |
| **可用性** | **故障检测**：心跳、Ping/Echo、异常检测<br>**故障恢复**：**冗余**（主动/被动/备用）、**故障转移**、回滚、重试<br>**故障预防**：移除单点、事务、进程监视器 |
| **安全性** | **抵抗攻击**：身份认证、授权、**加密**、完整性校验（消息摘要/数字签名）、限制暴露<br>**检测攻击**：入侵检测、日志审计<br>**从攻击中恢复**：恢复状态、审计追踪 |
| **可修改性** | **局部化修改**：高内聚低耦合、**接口与实现分离**、信息隐藏<br>**防止连锁反应**：隐藏信息、维持接口稳定、使用中间件/适配器<br>**推迟绑定时间**：配置化、策略模式、依赖注入 |
| **可测试性** | **输入输出**：记录/回放、接口与实现分离、增加可观测接口<br>**内部监控**：内置监视器、断言、日志 |
| **易用性** | **运行时**：用户模型、系统模型、反馈（进度条、错误提示）<br>**设计时**：界面与业务逻辑分离、MVC |


> 🔴 **必背速记**：
> - **可用性三板斧**：**心跳检测 → 冗余备份 → 故障转移**
> - **可修改性三板斧**：**高内聚低耦合 → 接口隔离 → 推迟绑定（配置化）**
> - **性能三板斧**：**减量（缓存）→ 并发（多线程）→ 增容（扩容分片）**

## 3.3 质量属性场景六要素（ATAM 会用到）

一个完整的场景描述应包含：

| 要素 | 内容 | 例子 |
|------|------|------|
| **刺激源** | 谁发出的 | 用户 / 黑客 / 系统内部 |
| **刺激** | 发生了什么 | 提交查询请求 / 发起攻击 |
| **环境** | 什么状态下 | 系统正常运行 / 超载状态 |
| **制品** | 作用于哪个部分 | 整个系统 / 数据库 |
| **响应** | 系统怎么做 | 返回处理结果 / 拒绝并记录日志 |
| **响应度量** | 好到什么程度（**必须可量化**） | 95% 请求在 1 秒内返回 |

> 🔴 **关键**：**"响应度量"必须可量化**，否则场景无效。这是选择题常考的"哪个不是合格的场景描述"。

# 第 4 章 · 架构评估（ATAM / SAAM）

## 4.1 三种概念区分（🔴 最高频，年年考）

| 概念 | 定义 | 一句话 |
|------|------|--------|
| **敏感点 (Sensitivity Point)** | 对**某一个**质量属性有显著影响的架构决策 | 影响**一个**属性 |
| **权衡点 (Tradeoff Point)** | 对**多个**质量属性都有影响，且**影响方向相反**的架构决策 | 影响**多个**属性，且是**矛盾的** |
| **风险点 (Risk Point)** | 架构决策中**潜在存在问题的、可能导致隐患**的地方 | 有**风险**的决策 |
| **非风险点 (Non-Risk Point)** | 经过分析判断**不会带来隐患**的架构决策 | 安全、无隐患 |

> 🧠 **记忆法**：
> - **敏感点**：动它，**一个**指标变 —— "**敏**感是**单**点反应"（敏→单）
> - **权衡点**：动它，**多个**指标变，且**此消彼长** —— "权**衡**要**衡**量多方"（衡→多）
> - 🔴 **关键判别**：**权衡点一定是敏感点，但敏感点不一定是权衡点**。
>   （因为它至少影响一个以上的属性，自然对每个单独属性也是"敏感"的。）

> **例题**："加密级别提高"这个决策 —— 安全性↑，性能↓。
> → 影响 **两个**属性且方向相反 → **权衡点**。

## 4.2 ATAM（架构权衡分析方法）

> **定位**：目前**最主流**的架构评估方法，案例题必考。

### 四个阶段（九步，记住"四阶段 + 九步"框架）

| 阶段 | 步骤 |
|------|------|
| **① 表述阶段** | 1. 介绍 ATAM 方法<br>2. 描述业务动机<br>3. 描述架构 |
| **② 调查分析阶段** | 4. 确定架构方法<br>5. **生成质量属性效用树**<br>6. 分析架构方法（产出：敏感点/权衡点/风险点/非风险点） |
| **③ 测试阶段** | 7. 集体讨论并确定场景优先级<br>8. 分析架构方法（用上一步的场景） |
| **④ 报告阶段** | 9. 结果的表述（**产出评估报告**） |

> 🔴 **必背**：
> - **ATAM 的核心产出**：**质量属性效用树 + 敏感点/权衡点/风险点/非风险点 + 评估报告**
> - **ATAM 适用于**：在架构**早期**，在**多个候选架构**之间做**权衡**（关键词：**权衡**）
> - 参与角色：评估小组 + **项目决策者** + **架构涉众**（用户、开发、测试、运维等）

### 效用树（Utility Tree）

```
效用（系统总体"好不好用"）
  └── 质量属性
        └── 质量属性细化子属性
              └── 质量属性场景
                    └── [优先级：(重要度, 实现难度)]
```
> 例：性能 → 响应时间 → "用户提交订单后 1 秒内返回结果"（H, M）
> 优先级表示法：**(H, H) 高重要度、高实现难度** —— 这类场景是**风险点**。

## 4.3 SAAM 与 CBAM

| 方法 | 侧重 | 关键词 |
|------|------|--------|
| **SAAM**（软件架构分析方法） | **最早的**评估方法，侧重**可修改性**（场景 + 架构描述） | **可修改性**、简单、适合**单个**架构 |
| **ATAM** | 在 **多个质量属性** 之间做**权衡** | **权衡**、效用树、敏感点/权衡点 |
| **CBAM**（成本效益分析方法） | 在 ATAM 基础上引入**经济学建模**（ROI，投资回报率） | **成本效益**、ROI、效用-成本比 |

> 🔴 **必背对比**：
> - **只评估可修改性 → SAAM**
> - **多属性权衡 → ATAM**
> - **要考虑成本/收益、算 ROI → CBAM**

# 第 5 章 · 特定领域架构与中间件

## 5.1 DSSA（特定领域软件架构）

> **一句话**：**针对某一特定领域**（如电信、金融、航空电子）提炼出的**可复用架构**，用于该领域内**一系列应用**的开发。

| 概念 | 含义 |
|------|------|
| **领域模型** | 该领域共有的需求与概念模型 |
| **参考架构** | 该领域通用的架构模板 |
| **参考需求** | 该领域通用的需求集合 |
| **DSSA 的建立过程** | 领域分析 → 领域设计 → 领域实现 |

**参与人员**：领域专家、领域分析师、领域设计人员、领域实现人员。

> 🔴 **DSSA 的关键特征**：**垂直域**（同一领域内的一族系统）+ **可复用**。

## 5.2 产品线（Software Product Line）

> **一句话**：围绕**一组公共的可管理特征**，**共享**一组**可复用资产**（构件、架构、文档、测试用例），系统地开发一族产品。

- **核心资产库** = 架构 + 构件 + 文档 + 测试 + 过程定义
- 与 DSSA 关系：**DSSA 是产品线的技术基础**

## 5.3 中间件（分类必考）

| 类型 | 作用 | 典型产品 |
|------|------|---------|
| **消息中间件（MOM）** | 异步解耦、削峰填谷 | Kafka、RabbitMQ、RocketMQ |
| **应用服务器** | 提供运行环境与容器服务（事务、连接池、JNDI） | Tomcat、WebLogic、WebSphere、JBoss |
| **数据访问中间件** | 屏蔽数据库差异 | ORM（MyBatis/Hibernate）、ODBC/JDBC |
| **远程过程/对象调用中间件** | 跨进程调用 | RPC（Dubbo、gRPC）、RMI、CORBA |
| **事务（交易）中间件** | 保证分布式事务一致性 | Seata、Tuxedo |
| **Web 服务器中间件** | 处理 HTTP | Nginx、Apache |
| **分布式对象中间件** | 跨语言跨平台对象调用 | CORBA、EJB |

<summary>参考答案</summary>

1. **构件 + 连接件 + 约束**
2. **进程视图**
3. **编译器**；**不适合交互式应用**（且难共享全局状态）
4. **黑板系统**。因为语音识别**没有确定的求解策略**，需要多个知识源（声学模型、语言模型等）协同、逐步逼近解
5. 构件之间**不直接调用**，而是通过**触发/广播事件**间接交互；**触发者不知道有哪些接收者**，也无法控制处理顺序与结果
6. **SOA 用 ESB（中心化总线）做集成；微服务是去中心化的**（API 网关 + 轻量协议如 REST/gRPC）
7. **冷启动延迟**、不适合长时运行任务、厂商锁定、调试与监控困难
8. **可靠性 = 不发生故障的能力**（强调不中断）；**可用性 = 可正常使用的时长比例**（允许短暂中断后恢复）
9. **心跳检测（故障检测）→ 冗余备份 → 故障转移**
10. **高内聚低耦合（局部化）→ 接口隔离（防连锁反应）→ 推迟绑定时间（配置化）**
11. **权衡点是对多个质量属性都有影响、且影响方向相反的架构决策**。关系：**权衡点一定是敏感点；敏感点不一定是权衡点**
12. **质量属性效用树 + 敏感点/权衡点/风险点/非风险点 + 架构评估报告**
13. **CBAM**（成本效益分析方法，在 ATAM 基础上引入经济学建模）
14. 刺激源、刺激、环境、制品、响应、**响应度量**。其中 **响应度量必须可量化**
15. **管道-过滤器有固定的处理流程**（数据流经一串确定的过滤器）；**黑板系统没有确定的求解策略**，多个独立的知识源主动响应黑板上的变化，逐步逼近解
